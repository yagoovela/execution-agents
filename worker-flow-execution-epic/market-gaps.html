The gaps

UNLOCKED BY THE EPIC

Resume a failed run from the node that failed

no retryFrom / resumeFrom / replayRun anywhere

Standard in the category and absent here. The data model already supports it — node_executions records the resolved input and the output per node per run. What is missing is an engine that can start mid-graph, and the backend loop cannot, because it rebuilds state from the top.

Why it is cheap for us

Impossible today, near-free once the graph lives in a workflow: "resume from node X" is scheduler state seeded from the completed set.

UNLOCKED BY THE EPIC

Human-in-the-loop and approval steps

no approval / waitFor / pauseRun in app-api

Pause, ask a person, continue — a frequent enterprise requirement. Impossible today for a structural reason: the backend loop holds the run in memory and cannot wait a day for a human.

Why it is cheap for us

A Temporal workflow can wait indefinitely on a signal with no resources held. One of the strongest reasons to want the graph workflow that has nothing to do with scale.

UNLOCKED BY THE EPIC

App-native triggers — watching, not just callable

all current triggers are push-in

Every trigger we have requires something else to call us. The category default is the opposite: trigger on a new Sheets row, a new Slack message, a new Stripe event.

Why it is cheap for us

We already have the hard half — the adapters and their credentials. What is missing is a durable cursor per connection, polled on a schedule, which is exactly what Temporal Schedules give.

CHEAP AND INDEPENDENT

Evals and regression testing

flux.controller.ts:574–706

No eval surface exists — greps for eval, dataset, regression, goldenSet and assertion find nothing relevant. But batch processing already takes a CSV of inputs, runs the flow per row and stores per-row outputs.

Why it is cheap for us

Add an expected-output column and a scorer and that is an eval harness; add "run it on every version" and it is regression testing. Without it, nobody can safely change a prompt in a flow that matters — the biggest reason AI automations stall after the demo.

CHEAP AND INDEPENDENT

Inbound idempotency keys

flux.service.ts:5030–5044

Outbound delivery is deduped well — a run-scoped SET with EX and NX plus a content hash. Inbound has nothing: a webhook provider that retries its delivery, which Stripe and Slack both do routinely, creates a second run and a second charge.

Why it is cheap for us

The pattern is already in the codebase. It just points the wrong way.

CHEAP AND INDEPENDENT

Cost observability a customer can act on

token_transactions exists; no surface does

Cost per node and per run is recorded, so the data exists. What does not exist is a surface: cost per flow over time, trend, forecast, an alert before a budget is hit.

Why it is cheap for us

The spend ceiling makes this urgent rather than optional — a ceiling with no forecast is a surprise, and reporting is what makes it humane.

CHEAP AND INDEPENDENT

Trace export to the customer's own stack

RunLogCollector already has the material

Teams running AI in production increasingly want traces in the observability tool they already pay for. We have a hierarchical run log with tokens, cost and timings per node, and no export.

Why it is cheap for us

An OpenTelemetry exporter reuses everything the observability task is already touching.

CHEAP AND INDEPENDENT

Environments, diff and rollback per flow

flow_version_history exists

Version history exists and the MCP surface has versioning, so this is half-built. Missing: a dev/staging/prod notion per flow, a readable diff between versions, and one-click rollback.

Why it is cheap for us

The storage is there. This is product surface over existing data.

The strategic one

We orchestrate; we do not yet agent

The largest strategic gap is not a feature — it is a category. We call flows "agents": the MCP tools are create_agent, run_agent, list_agents. But the execution model is a deterministic graph, where a human draws every edge and every path is decided in advance. The MCP node resolves a fixed toolName from node data (mcp_flux_node.service.ts:43) — the model does not choose the tool. Meanwhile the category's centre of gravity moved to autonomous agents: give a model a goal and a toolbox, let it decide the sequence, loop until done, ask for help when stuck.

Both models are legitimate, and deterministic graphs are better for compliance, cost predictability and debuggability — the reasons enterprises reject autonomous agents. The risk is not that the graph model is wrong. It is being sold as "agents" while a buyer comparing against an autonomous-agent product expects something else, and finds out during the trial. And we are unusually well placed to add it: an agent node needs a tool catalogue, multi-provider models, and a durable runtime that can loop safely with a ceiling. We have the first two, and the third is exactly what this epic builds — the loop ceiling, the cost ceiling and the recursion guard are the three things that make an autonomous loop safe to sell rather than terrifying. The MCP tool catalogue is the unfair advantage: competitors adding an agent node must first build a tool registry.

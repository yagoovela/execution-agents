The verdict

An adversarial read of the design — including of our own prior conclusions — against one question: what breaks, what costs money, and what can be abused when this runs with many agents, many workers, and real parallelism.

SOLID

The data model holds

persist-node-success.ts:59–63

Every write lands on a row the activity owns, and every execution has its own row. This was true before anyone planned for parallelism, which is the best kind of foundation to find. It is the reason parallel siblings cannot lose each other's writes.

CRITICAL

The control plane does not

flux.service.ts:5611

Recursion, loops, spend, tenancy and database connections are all uncapped. Each was harmless while one sequential process was the natural throttle. Every one of them becomes a fleet-wide problem the moment the loop is parallel.

What to do

Fix the ceilings before removing the throttle.

HIGH

Two security gaps get worse after migration

worker.controller.ts:87

The claim-check endpoint authorises nothing beyond a key prefix, and its single shared secret will sit on every worker replica. Unvalidated URL fetchers move into a host that holds the database password and the integrations key.

🔥

Runaway and abuse

Three uncapped paths that convert directly into unbounded spend or unbounded load. The plan as written makes two of them worse.

CRITICAL

Sub-flow recursion has no depth limit and no cycle detection

flux.service.ts:5611–5622 · 5732 · 5815

Flow Caller calls the whole orchestrator — this.apiV2() — for the selected flow. Searching for visited, cycle, depth or MAX_DEPTH across the flux service returns nothing; parentFlowId is threaded for billing attribution only. Flow A pointing at B, and B pointing back at A, recurses until the process dies. Each level is a complete run: its own scheduler state, its own node_executions rows, its own run-log tree, its own token spend. No malice required — two people composing reusable flows produce this by accident.

What to do

The plan makes this worse: B6 turns sub-flows into Temporal child workflows. Today the recursion is bounded, crudely, by one process's memory. As child workflows it becomes a fork bomb the platform will faithfully sustain across the fleet, durably retried. A depth counter with a hard ceiling plus a visited-flow set is required before B6.

HIGH

The loop ceiling can be switched off from the node's own data

folw/helpers/helpers.ts:2075–2110

evaluateLoopCondition applies loopLimitCheck only when loopBehavior is "continue". On the other branch the limit is computed, reported to the UI, and then not applied — finalResult becomes the user condition alone. And even on the capped branch, loopCount is node.data.loopCount, which is user data. An always-true condition on a node whose behaviour is not "continue" loops with no ceiling.

What to do

Whether "stop" was meant to bypass the counter or not, a system-level maximum should exist regardless of node configuration.

HIGH

No budget ceiling for a run

product.service.ts:265–284

assertCompletionCredits is a boolean gate: for INTRO products it checks trialTokens > 0; otherwise having a subscription is enough. Per node, getUserProductFromFlow checks entitlement to a model, not remaining budget. Charges are recorded after the fact into token_transactions. Nothing decrements an allowance and nothing aborts a run that has already overspent.

What to do

For a paid account, the two findings above convert directly into unbounded provider spend, and the first signal is the invoice. Enforce a per-run ceiling at charge time — the same call that already records the spend, and the only place that works once the worker owns the loop.

MEDIUM

Nothing limits concurrent runs per tenant

jobs/apiV2Job/apiV2Job.processor.ts:33

No throttle and no per-tenant concurrency cap anywhere in the flux or job paths. Today this is partly masked: the Bull processor declares @Process with no concurrency option, so each backend replica runs one queued run at a time. That accidental serialisation is doing real protective work.

What to do

Task B5 removes it deliberately. Without a per-tenant cap, one org's wide graph occupies the whole fleet and starves every other tenant — a fairness bug, not a capacity bug. Our B5 spec says "pick a cap"; that is too weak.

🚪

Entry points, email, crons and Redis

This section exists because the first review missed it. It covered Redis only as the notification transport and crons only as the retention job, and it never looked at how a run is admitted. The gap contained the most severe finding in this document.

CRITICAL

The webhook entry point is unauthenticated and runs any flow

flux.controller.ts:340–341 · 352–362

POST /flux/api-v2-webhook is decorated @Public(), so it opts out of the global auth guard, and it resolves the flow from a query parameter. The where is an OR array whose first branch has no public condition, which makes the second dead: any flow matches, public or private. Scanning the rest of the handler for a secret, a token or an ownership check finds only "if (!flow)". Anyone who knows a flow id can execute that flow and charge its owner — the only barrier is that the id is a UUID, and flow ids travel through published interfaces, chatbot routes, shared links and the MCP surface.

What to do

Combined with no rate limiting, no per-run cost ceiling, no per-tenant cap and unbounded sub-flow recursion, one leaked flow id is an unbounded unauthenticated spend against one customer. This outranks everything else in the review — it is live, not a scaling concern.

HIGH

There is no rate limiting anywhere

no ThrottlerModule in back/src

No ThrottlerModule, no @Throttle, no ThrottlerGuard anywhere. Every run-creating route accepts unlimited requests, and each request creates a run. The Bull processor's accidental serialisation throttles execution, not admission — the queue still grows without bound and the rows, logs and dedup keys are written on the way in.

What to do

Limits keyed by the thing that pays: API key, organisation, and flow for the webhook route. Not by IP, which is meaningless for server-to-server callers.

HIGH

Fourteen crons, no leader election

14 @Cron sites in back/src

Greps for leader, isLeader, CRON_ENABLED or an advisory-lock guard return nothing, so every cron fires on every replica. Some is waste — five separate purges all at EVERY_DAY_AT_3AM, each per replica, against the same tables in the same minute. Some is not: POP3 polling runs EVERY_10_SECONDS per replica, and the stuck-run marker every ten minutes per replica.

What to do

One mechanism for all fourteen, not fourteen guards. An advisory lock per job name needs no new dependency and degrades correctly — a replica that cannot take the lock skips.

HIGH

User-scheduled flows fire once per replica

schedule.controller.ts:157–159 · 179 · 242 · 332

Scheduled runs use NestJS's in-process registry, so each replica holds its own copy of every active schedule and fires it independently — N replicas means N runs, each charged. Two aggravations: the bulk re-registration hides inside getAllSchedules(), a plain method with no route decorator that registers crons as a side effect; and the cron callback awaits apiV2 as an argument to queue.add, so the flow already ran synchronously inside the callback and only its result reaches the queue.

What to do

Fixing the duplication without fixing the enqueue just duplicates it more efficiently. The zombie-cron cleanup already in that file is the one part doing the right thing — keep it.

MEDIUM

Redis carries three unrelated responsibilities

flux.service.ts:5030–5044

Redis backs the Bull queues, the worker to backend pub/sub, and the delivery dedup keys. The dedup itself is a correct pattern — SET key with EX and NX, run-scoped — and it is what stops a retried run from emailing a customer twice.

What to do

Two things to verify from infrastructure: under allkeys-lru the dedup keys are evictable, and the failure mode is duplicate customer emails and webhooks — they are correctness state, not cache. And losing one instance loses admission, visibility and duplicate suppression together, while parallel dispatch raises the pub/sub rate substantially.

CRITICAL

The email trigger trusts a forgeable header

mail.service.ts:434 · 453–487

Agents are also started by email. The flow is resolved from the local part of the recipient address — the format the service advertises is uuid@upload.fluxprompt.com — and the message becomes the flow's input. For a private flow the entire authorisation is the From header matched against a user and compared to the flow owner. Greps for dkim, spf, dmarc and authentication-results in app-api/mail return nothing: nothing verifies the message came from the address it claims.

What to do

This is not an authorisation check — it is a request for the attacker to type the owner's email address, which is not secret. Arguably worse than the webhook route, which at least required a UUID. Verify the sender, or move the secret into the address so possession of it is the credential.

HIGH

A public flow's email trigger is an open prompt-injection surface

mail.service.ts:503–556

For a public flow there is no sender check at all, and the From, Subject and body are injected directly into the flow's varInputNode. Whoever sends the email controls the prompt.

What to do

If that flow contains a push node, a third-party integration or a Flow Caller, the sender is driving side effects with the owner's credentials — Slack messages, Notion writes, Stripe charges — from an unauthenticated email. Those integration nodes are exactly the ones this epic is migrating.

HIGH

The mail poll runs per replica with nothing deduplicating messages

mail.service.ts:132 · 314

The POP3 cron is one of the fourteen without leader election, so it fires every ten seconds per replica. There is no message-id dedup and no lock: messages are fetched, processed, and only then deleted, so the window spans the whole batch including enqueueing the runs.

What to do

Being fair: POP3 requires the server to lock the maildrop for the session, so a well-behaved provider refuses the second replica and duplicates may not happen today. That is the problem — correctness depends on a lock the code does not take and cannot observe. Move to IMAP or an API and the failure becomes duplicate runs, charged, with nothing to catch it.

CRITICAL

Three of the four ways to start a run are effectively unauthenticated

the pattern, not a single line

The API route uses an API key. The webhook route uses nothing, and its public predicate is dead. The email trigger uses a forgeable header, or nothing at all for public flows. Scheduled runs authenticate the owner at creation, but fire once per replica. None of the four is rate limited.

What to do

Every ceiling this review proposes — cost, tenancy, recursion, loops — is downstream of admission. Fixing admission last would mean building all of them and still leaving the front door open.

🗄️

The application database

Temporal's own store is out of scope. The database that matters is the shared application Postgres, because every worker replica contends for it.

CRITICAL

The worker pool has no configured maximum

worker/src/modules/database/database.service.ts:13

new Pool({host, port, user, password, database}) — no max. node-postgres defaults to 10 connections per pool, per process. The worker runs maxConcurrentActivityTaskExecutions: 10, so each replica can hold ten busy connections, and connections scale linearly with replicas. Postgres max_connections is a hard wall, and the failure mode is not slowness — it is "too many clients already" for the API too, because they share the database. No connection proxy appears anywhere in the compose files or infra.

What to do

This is the single biggest obstacle to running multiple workers, and it is one line of config plus a capacity decision. Settle it before B5 — and before scaling the worker at all.

MEDIUM

Five to six writes per node, multiplied by fan-out

persist-node-success.ts · node-execution-store.ts

One successful node writes node_executions.outputData, a flows_nodes.data JSONB merge, the node_executions input row, a token_transactions insert, execution_logs, and a space_run_logs upsert — before Redis and before S3. Parallel dispatch multiplies that by the width of the ready set, and loops multiply it again, with the execution-identity task adding a row per iteration rather than reusing one.

What to do

None of this is wrong. It is a number that must be sized deliberately rather than discovered, and the epic never states it.

MEDIUM

flows_nodes.data is hot, fat and contended

flux.service.ts:3276 · 3868 · 7978 · 8031 · 8083 · 8210

Merged on every node completion and read by the builder UI, carrying previewResponses, contentData and text. The previewResponses trim uses strict equality — responses.length === 10 at six sites — so any array that gets past ten by another path never trims again. Under loops, the same node's row is merged once per iteration, serialised by row lock.

What to do

Parallel siblings on different nodes are fine. The same node is not.

HIGH

The claim check routes large payloads through the API

persist-node-success.ts:32–57 · resolve-claim-ref.ts:38–51

Payloads over 256 KB are offloaded via POST /worker/store-payload and fetched back via /worker/get-payload, because the worker has no S3 client. So the escape valve for large data is a synchronous hop into the very service the migration is trying to take out of the path. Under fan-out, every wide node's payload becomes an API request.

What to do

Giving the worker its own S3 credentials removes a class of coupling. The credential-surface counter-argument is weaker than it looks: the worker already holds the database password and the integrations encryption key.

SOLID

Retention already exists, and it was thought through

cronJobs/purgeNodeExecutions/purgeNodeExecutions.service.ts:7 · 18

A daily 03:00 job slims by company or PHI override, slims by age, deletes past NODE_EXEC_DELETE_AFTER_DAYS (default 30) and past MAX_PER_NODE rows per node. Someone thought about growth before it hurt.

What to do

Revisit the thresholds when execution identity starts writing a row per loop iteration — the per-node cap becomes load-bearing then.

Security

Two gaps that migration makes more dangerous, and two boundaries that are genuinely well placed.

HIGH

The claim-check endpoint authorises nothing

worker.controller.ts:87–95 · 45

The only validation is that the key is a string starting with "node-exec/". There is no check that the key belongs to the caller's run, tenant, or anything else. Any holder of the internal API key can read any node output of any customer, by key. The controller is behind InternalApiGuard, which is the right boundary — but it is a single shared secret, and after this epic that secret sits on every worker replica.

What to do

Blast radius grows with the fleet. Bind the key to its execId and nodeId and verify the caller's claim — the key already encodes them.

HIGH

No SSRF protection on user-controlled URLs

downloader.controller.ts:34

The downloader takes a user URL, and the scraper, api-caller and crawling paths do too. Searching those modules for private-range or metadata-IP blocking — 127.0.0.1, 169.254, localhost, isPrivate — returns nothing. A node pointing at the cloud metadata endpoint or an internal hostname is the textbook case.

What to do

This is pre-existing, not created by the epic — but the epic moves these callers into the worker, which sits in a different network position, holding the database password and the integrations key. That is a decision deserving a sentence in the task, and it currently gets none.

SOLID

Scripting is isolated in Lambda

scripting.service.ts:23–24 · 213

The scripting node dispatches to AWS Lambda — code-executor-js and code-executor-python — rather than evaluating in the worker. The largest arbitrary-code surface in the product is already isolated at the strongest available boundary.

What to do

Do not let a future optimisation pull it back in-process to save a Lambda invocation.

MEDIUM

Secret redaction has exactly one chokepoint

the run-log collector

redactSecrets is the only place credentials are scrubbed before reaching space_run_logs. The observability task moves that collector.

What to do

A refactor that drops the hook turns a logging change into a credential disclosure. The test for it should be treated as non-negotiable, not as one bullet among several.

📦

What else belongs in the worker

Four things still in the back, and — usefully — nothing left in the front beyond what is already planned.

HIGH

Outbound delivery is fire-and-forget with no retry

flux.service.ts:4907–5200

The 300-line block at the end of every run sends emails through three paths and fires HTTP callbacks with axios.post, each wrapped in a catch. Nothing is retried — a customer's webhook endpoint being down for thirty seconds loses the notification, with a log line as the only trace.

What to do

The cleanest activity candidate left: pure external I/O, and the hard part is already done. The Redis dedup keys exist precisely so a repeated attempt does not double-send, so retry is safe today and simply missing.

HIGH

CSV batches are a detached loop inside the API process

flux.controller.ts:560 · 574–706

processBatch is called unawaited, so the request returns and the work continues detached in the backend process. It is a sequential for loop over rows, each running a complete flow, with four to five database round trips per row on bookkeeping alone. A deploy, restart or scale-down mid-batch kills the loop silently and the batch stalls at lastProcessedLine with a non-terminal status.

What to do

It is also the largest amplifier of every missing ceiling: a thousand-row CSV is a thousand full runs from one API-key call, against no rate limit, no per-run cost ceiling and no per-tenant cap. A batch is a durable workflow with a child per row and a concurrency cap.

MEDIUM

Temporal Schedules are not used at all

no ScheduleClient in worker or back/src/temporal

Greps for ScheduleClient, scheduleClient and createSchedule across the worker and back/src/temporal return nothing. The platform's native scheduling is unused, while user schedules are held in an in-process registry that fires once per replica.

What to do

This amends the earlier recommendation: Temporal Schedules give by construction what an advisory lock would build by hand — one fire per schedule, durability across deploys, plus pause, backfill and last-run visibility. Locks stay right for the fourteen framework crons, which have no reason to become workflows.

SOLID

The front is clean

no polling or dispatch found during a run

Searching the published interface, the chatbot pages and the node components for work performed during a run — setInterval, refetchInterval, polling loops, node-by-node dispatch — finds nothing. The front's only run-time roles are starting a run and receiving socket events.

What to do

The nine front-driven node types were the exception and already have tasks. So the answer to "is there anything in the front that should be in the worker" is no, beyond what is already planned — which is a good sign about where the boundary sits.

Where our own analysis fails

The requester asked for scepticism about the analysis itself. Five places where our prior conclusions do not survive contact with scale.

CRITICAL

We never mentioned Temporal workflow history limits

no continueAsNew anywhere in worker/src

A Temporal workflow accumulates history events, and both event count and history size are bounded. The worker uses no continueAsNew — a grep returns nothing. Our graph-workflow task proposes one workflow owning an entire flow run. For a large graph, a long loop, or an arrayNode over a big list, history grows with every activity scheduled and completed and every large input passed. That workflow will eventually be terminated by the platform, and it will happen to the biggest, most valuable customer runs first.

What to do

The graph task must specify continueAsNew at an iteration or node-count boundary, and must pass state by reference rather than by value — which the id-based transport already makes possible. We missed this because we reasoned about Postgres and never about workflow history as a storage medium.

HIGH

Our parallelism gate is necessary but not sufficient

TASK-B5

Gating on "every executable node in the flow is migrated" correctly prevents the mixed-mode lost update. It says nothing about provider concurrency. Fan-out produces bursts against OpenAI, Anthropic, Replicate and the integration APIs, and the first symptom is 429s attributed to the customer as node failures.

What to do

A per-provider, per-tenant concurrency budget is needed — not just "pick a cap".

HIGH

A single run-log tree is a sequential idea

TASK-E1

RunLogCollector maintains one hierarchical tree in memory. Under parallel siblings, branches are written concurrently. Our task offers two options — worker keeps the tree, or backend rebuilds from events — as if they were equivalent. They are not: keeping the tree in the workflow makes workflow state grow with the run, which collides directly with the history limit above.

What to do

Event-sourced reconstruction is the only option compatible with both parallelism and history limits. The task should say so instead of leaving it open.

MEDIUM

We treated own-row writes as proof of parallel safety

It is sufficient for lost updates, and that conclusion stands. It is not sufficient for ordering. Two siblings writing their own rows cannot clobber each other, but a downstream node reading both has no guarantee about which is visible when, and the Object Caller has real ordering requirements.

What to do

The scheduler's dependency edges are the answer — but that is an argument, and our documents asserted the conclusion without making it.

MEDIUM

The blocking wait is partly load-bearing

flux.service.ts:507

We treated await handle.result() as pure waste. It also provides back-pressure: while the backend blocks, it is not starting more work.

What to do

Removing it without the per-tenant cap and the connection ceiling replaces a slow system with an unstable one. The removal is still right; the ordering is not optional.

👤

Usability nobody specified

Not blockers. Decisions — and shipping parallelism without making them means making them by accident.

MEDIUM

Several nodes running at once

The builder shows per-node status. With fan-out, several nodes are running simultaneously, and "which node is the run on" stops having a single answer — including in the cancel footprint the product shows today.

MEDIUM

Cancellation becomes partial

Cancelling a parallel run leaves some siblings completed, some aborted, some never started. The user-facing meaning of a cancelled run needs a decision.

MEDIUM

Side-effect ordering stops being incidental

Two independent push nodes fire in graph order today; in parallel they do not. Any customer relying on that incidental ordering will experience it as a regression.

MEDIUM

Error attribution with a batch in flight

Fail-fast today stops at the first error. With several nodes in flight, several can fail simultaneously — which one names the run?

🧱

What is solid

Scepticism cuts both ways. These are good, they were not accidents, and the plan should protect them.

SOLID

Own-row writes

persist-node-success.ts:59–63

persistNodeSuccess only ever merges into rows the activity owns. This is the property that makes parallelism possible at all, and it was already true before anyone planned for it.

SOLID

One row per execution

node_executions

Run isolation by construction — the entity comment states the intent outright: parallel runs never overwrite each other.

SOLID

The claim-check pattern

Correct pattern, wrong transport. Keep the pattern; give the worker its own storage credentials.

SOLID

Typed error taxonomy

worker/src/modules/nodes/shared/node-error.ts

Retry semantics derived from error type is exactly right, and it is what keeps a user's typo from retrying for thirty minutes.

SOLID

An advisory-lock precedent already in the codebase

third-party-integration/oauth-token.repo.ts:7

pg_advisory_xact_lock is already used for the OAuth refresh race — a working pattern for the Object Caller ordering problem, with no new dependency.

SOLID

Reference-based input resolution already shipped

app-api/flux/prefetch/

The prefetch executor resolves each node's input by reference behind a flag. The model we proposed already exists; the work is to widen it, not to design it.

SOLID

A pure, portable scheduler

app-api/flux/scheduler.ts

No injection, no database, single source of ordering truth, consumed by the engine and the MCP write service alike.

Passo 1.7 — Refresh de token Google (condicional)

Bloco em flux.service.ts:2620-2643. Se o flow tem algum pullData/pushData com provider = 'google' e o usuário tem googleRefreshToken, troca o refresh token por um access_token fresco e guarda numa variável local que os handlers de pullData/pushData vão consumir na Fase 3.
Contexto: este é o único ponto do fluxo de execução que fala com o OAuth2 do Google. Access tokens do Google expiram em ~1h, então todo run refaz o refresh antes de despachar os handlers de dados Google (Sheets, etc.). Se qualquer uma das condições falha, access_token continua string vazia e os handlers downstream chamam Google sem token (= 401 na hora).
Cadeia de operações em 1.7
ADetecta google data node → BGate + OAuth2Client init → CrefreshAccessToken → Google → DConsumidores downstream
Resultado final: variável local access_token (string) fica preenchida (ou vazia se o gate não abriu), pronta pra ser passada em { accessToken: access_token } pros handlers de pushData/pullData em Fase 3.
A Detecta google data node
flux.service.ts:2620-2626
const hasGoogleDataNode = nodes?.find(n => (n.type === 'pushData' || n.type === 'pullData') && (n.data?.provider ?? 'google') === 'google');
Propósito: Descobrir se vale a pena gastar uma chamada de rede pro Google. Se nenhum nó do flow é pullData/pushData com provider Google, o refresh é desnecessário e pula.
Em resumo: pense nessa parte como um vigia rápido que olha o agente inteiro antes de ligar pro Google. Ele varre a lista de nós procurando alguém que puxe ou empurre dados do Google (Sheets, basicamente) e, se não achar ninguém interessado, nem se dá o trabalho de continuar — a variável access_token nasce vazia e todo o resto do passo é ignorado. É uma economia de tempo importante: a maioria dos agentes não usa Google, então esse vigia evita uma chamada de rede desnecessária. Detalhe curioso: nós antigos sem o campo provider são tratados como Google por padrão, então dados legados ainda disparam o refresh.

🎯 Fallback ?? 'google'
Nodes antigos criados antes do campo provider existir não têm essa chave — o ?? assume que ausente = Google. Se o front hoje só grava provider explícito, o fallback é rede de segurança pra dados legados.

Consequência: um node novo criado sem setar provider (ex.: MCP mal configurado — [[project_mcp_node_schemas]]) é tratado como Google e pode disparar o refresh sem necessidade.
📎 Por que só pullData/pushData?
Google Sheets é o único provider Google integrado no motor de execução. Outras integrações Google (Gmail, Docs) vivem em mail.service.ts/etc., cada uma com seu próprio OAuth2Client isolado.
🔧 find vs some
Poderia ser nodes?.some(...) — mais claro semanticamente ("existe algum?"). Usar find aloca o node mas descarta; overhead irrelevante em produção, mas é um smell.
B Gate + new OAuth2Client()
flux.service.ts:2628-2635
if (user.googleRefreshToken && hasGoogleDataNode) { const client = new OAuth2Client({ clientId, clientSecret, redirectUri }); ... }
Propósito: Só entra no fluxo de refresh se as duas condições valem: o user já autenticou com Google alguma vez (tem googleRefreshToken) e o flow atual precisa. Se qualquer uma falha, access_token fica string vazia.
Em resumo: aqui entra o porteiro duplo. Ele só libera o refresh se você conseguir carimbar dois cartões ao mesmo tempo: (1) o usuário já se logou no Google alguma vez e deixou um googleRefreshToken guardado no cadastro dele, (2) o agente que está prestes a rodar realmente tem um nó Google esperando dados. Se algum dos cartões faltar, o porteiro fecha a porta em silêncio e a variável access_token continua vazia — sem alarme, sem erro. Passando o gate, o código monta um OAuth2Client novinho (um por run, sem reciclar) já com clientId, clientSecret e redirect prontos pra conversar com o Google no próximo passo. Fica de olho no typo lendário GOOGLE_LOGIN_CLIENT_SECRECT — a env var precisa ter o typo pra funcionar.

C client.refreshAccessToken()
flux.service.ts:2636-2642
client.setCredentials({ refresh_token }); const token = await client.refreshAccessToken(); access_token = token.credentials.access_token;
Propósito: Fazer o roundtrip pro oauth2.googleapis.com/token trocando o refresh_token por um access_token novo (validade ~1h). Guarda só o access_token na variável do escopo pai.
Em resumo: aqui é o cartório: você entrega o refresh token (a "carteira permanente") e o Google devolve um access token novo, válido por mais ou menos uma hora. Primeiro o código chama setCredentials, que só arruma a papelada localmente (sem rede), e depois dispara o refreshAccessToken() — esse sim vai até o servidor do Google, espera a resposta bloqueando o run inteiro, e volta com o crachá novo. Só o campo access_token é guardado, o resto (expiry_date, scope, id_token) vai pro lixo. Sem try/catch: se o Google recusar (token revogado, quota estourada), o run inteiro morre — mesmo que 90% dos nós nem sejam do Google.

⚠️ Sem try/catch — falha afunda a run
refreshAccessToken() não está protegido. Se o Google devolver erro (refresh token revogado, quota, timeout), a exceção sobe pra apiV2(), que só tem um try/catch alto no orquestrador — o run inteiro morre, mesmo que 90% dos nodes não sejam Google.

Se o user revogou permissão pelo Google Account settings, todo run de qualquer flow com um único pullData/pushData Google quebra até ele reautenticar.
🎯 Descarta expiry_date
O SDK do Google devolve token.credentials.expiry_date mas o código ignora. Consequência: se um run for muito longo (> 1h), o access_token vai expirar no meio da execução — chamadas de pullData/pushData tardias podem retornar 401 mesmo tendo passado no refresh no início.

Cenário raro (arrays gigantes ou loops), mas latente.

D Consumidores downstream do access_token
flux.service.ts:3407, 3425, 4209, 4227
// Fase 3: pullDataService.pullData({ ..., accessToken: access_token }) / pushDataService.pushData({ ..., accessToken: access_token })
Propósito: Mapear pra onde o access_token preparado aqui vai desaguar. Nada é feito com ele em 1.7 — o valor só vive numa variável até os handlers de Fase 3 pegarem.
Em resumo: essa não é uma função em si — é o carteiro mostrando pra onde o access_token vai ser entregue lá na frente. O token fica guardado numa variável local do escopo do apiV2() e só sai de lá quando os handlers da Fase 3 pedem: pullDataService.pullData, pushDataService.pushData, e as versões que rodam dentro de um arrayNode (iterando). Todo mundo recebe o mesmo token, sem revalidação. Detalhe importante: se o gate (B) não abriu, esses handlers ainda são chamados normalmente, só que com accessToken: '' — o Google vai responder 401 quando o nó de fato executar, porque não existe validação early-fail. Também note a troca de convenção: local é access_token (snake, formato do Google), parâmetro é accessToken (camel, padrão TS do backend).

⚠️ Token vazio = handler tenta chamar Google sem auth
Se o gate (B) não abriu, access_token continua ''. Os handlers ainda são chamados normalmente — passa string vazia como accessToken. Google responde 401 no meio da execução.

Não existe validação em pullData/pushData pra abortar cedo se accessToken for falsy. É failure implícita: o erro só aparece quando o node executa.
🎯 Ciclo de vida do token
Início do run (aqui, 1.7): refresh 1x
Durante o run: token compartilhado por closure (mesma string em N handlers)
Fim do run: variável descartada — próximo run refaz o refresh

Sem cache. Runs consecutivos do mesmo user gastam 1 chamada Google cada.
🔧 Divergência snake_case/camelCase
Local: access_token (snake, alinhado com o formato do Google).
Parâmetro dos handlers: accessToken (camel, alinhado com o padrão TS do backend).

Mapeamento manual no call site — se alguém renomear a variável local, tem que atualizar os 4 call sites.
Resumo — o que sai de 1.7:
• access_token = string com Bearer token do Google (ou '' se o gate não abriu)
• Nenhum outro side effect: nada é gravado em DB, nenhum log estruturado, nenhum cache
• I/O: 0 ou 1 POST em oauth2.googleapis.com/token (sequencial, blocking)
• Consumido em Fase 3 pelos handlers de pullData/pushData (top-level e dentro de arrayNode)
Observações para migração:
• Não é essencial pra maioria dos runs — a maior parte dos flows não tem pullData/pushData Google. O gate (A+B) pula 100% do custo.
• Pode ficar no backend mesmo com worker: cada handler Google no worker também pode fazer seu próprio refresh (é o padrão em google_sheets.service.ts). Mas isso multiplica N calls Google por run se tiver múltiplos nós — o refresh centralizado do backend é mais eficiente.
• Alternativa: worker recebe o access_token via workflow args (já refeito pelo backend). Vantagem: 1 refresh por run, worker fica burro. Desvantagem: se o run for > 1h (não é o caso hoje), token expira no meio.
• Corrigir o typo SECRECT: coordenar mudança de env var em produção + dev + CI simultaneamente. Não é trivial.
• Envolver em try/catch: hoje uma falha aqui derruba o run inteiro. Se envolver, um user com token revogado ainda executa nós não-Google — mas os Google failam com 401 downstream. Discussão sobre fail early vs fail late.
• Adicionar log estruturado (hoje nada é logado — sucesso ou falha). Um console.log('[GoogleRefresh]', { userId, ok }) ajudaria a diagnosticar problemas de reauth.

☈ Deep dive — Step 2.3

DAG validation

The fail-fast gate between assembling the graph and starting to spend resources.

1 What this step is

Step 2.3 (validateDag()) runs right after buildDag (2.2) and before the parallel wave loop (PHASE 3). It is a <strong>pure</strong> step. Only reads the DAG structure, no I/O. Serves as the last point where the workflow can abort <em>without having spent anything</em>. No row in <code>node_executions</code>, no LLM token, no external call.

The rule is simple. <strong>If the DAG passes here, it can only fail for real runtime reasons</strong> (LLM went down, HTTP 500, timeout). Never for invalid structural data. That guarantee is what lets us treat the PHASE 3 guards (deadlock at 3.2, failures at 3.6) as purely defensive.

Where it lives: inside the Temporal workflow, immediately after <code>buildDag(snapshot)</code>. Runs on the already-built DAG (not on the raw snapshot). Some checks need the adjacency list and <code>inDegree</code>, not only the raw topology.

2 What it validates

Four classes of error. Each catches a different category of structural bug. All cause <em>fail-fast</em>. The workflow throws a non-retryable exception and goes straight to PHASE 4 (finalisation in failed mode).

2.3.a Remaining cycles

buildDag (2.2) already runs DFS to detect and remove back-edges. If something slipped through (algorithm bug, corrupted data, malformed graph that fooled the detection), the result is a cycle that survives to runtime. Without this check, the wave loop (3.1) could never reach <code>inDegree === 0</code> on the cycle's nodes. It would only fall into the <em>deadlock guard</em> at <strong>3.2</strong>, without context on what caused it.

Example
Prompt(NodeA) = "Based on {{NodeB.output}}, ..."
Prompt(NodeB) = "Based on {{NodeA.output}}, ..."

Detection A → B and B → A. buildDag removes one of the back-edges. If both were created as implicit refs and the "which to remove" criterion failed, the cycle survives. validateDag fails with <code>CycleDetectedError({ cycle: [A, B] })</code>.
Error thrown CycleDetectedError. Includes the list of nodes in the cycle for debug. Cost avoided Silent deadlock discovered only after trying to execute all other flow branches. Why here Only possible to know if the DAG is acyclic after buildDag. Before that the structure still has back-edges.
2.3.b {{...}} refs pointing to non-existent nodes

Classic scenario: user renamed/deleted a node but another node still has <code>{{OldName.field}}</code> hidden in the middle of a 500-line prompt. buildDag can still build a valid graph (it ignores refs without a target). When the consumer node runs at 3.4.1, <code>substitutePlaceholders</code> will find the orphan ref and explode.

Example
Flow has: Topic, WebSearch, Compare, Article.
User deletes <code>WebSearch</code> but forgets to clear Compare's prompt:
Prompt(Compare) = "Compare {{WebSearch.results}} and {{NewsSearch.results}}"

Without validation Topic runs (5s, real cost). Compare starts substituting. <code>{{WebSearch.results}}</code> becomes <code>undefined</code>. Prompt becomes garbage. LLM runs with corrupted prompt. Charges tokens. Returns useless response.

With validation InvalidReferenceError({ node: "Compare", brokenRefs: ["WebSearch.results"] }) before any dispatch.
Error thrown InvalidReferenceError. Lists which node has which broken ref. Cost avoided All of the broken node's dependencies run for nothing (tokens, time, external API quotas). Why here buildDag already scanned the refs to create implicit deps. Only need to cross the ref list with the existing <code>nodeIds</code> set. Cost O(refs).
2.3.c Incompatible types between source and target

Each node type declares its <strong>input handles</strong> (what it expects to receive) and <strong>output handles</strong> (what it produces). An edge links A's output-handle to B's input-handle. If types do not match, B's dispatch will receive garbage or fail on coercion.

Example
Edge: PdfExtractor.file_bytes → TextGenerator.prompt_text.
Types: Binary → String (incompatible).

Without validation Silent conversion turns the binary into <code>[object ArrayBuffer]</code>. LLM runs with a corrupted prompt.

With validation TypeMismatchError({ edge: [PdfExtractor, TextGenerator], expected: "String", got: "Binary" }).
Error thrown TypeMismatchError. Identifies the edge and the mismatch. Cost avoided LLM executions with corrupted prompts. Useless results billed as success. Note Only validates <em>explicit</em> edges. <code>{{...}}</code> refs have dynamic type (the value can be anything). Their mismatch can only be caught at runtime.
2.3.d Essential orphan nodes

Some node types are marked as <strong>essential</strong>. If they are in the flow, execution needs to reach them for it to be considered valid. Examples: <code>outputNode</code>, <code>responseNode</code>, <code>webhookResponse</code>. If one of them was disconnected (e.g. user deleted the last edge arriving into it), the flow "finishes successfully" but produces no output. Worse than failing. It fails silently.

Example
Chatbot flow: UserMessage → TextGen → ResponseNode.
User deletes the edge between TextGen and ResponseNode.

Without validation Execution runs. TextGen produces output. ResponseNode is unreachable, pruned in buildDag. Flow finishes "successfully". Client receives no answer. User sees "system error" with no real error log.

With validation OrphanEssentialNodeError({ nodes: ["ResponseNode"] }). Execution fails with a clear error saying the response is not connected.
Error thrown OrphanEssentialNodeError. Lists disconnected essential nodes. Cost avoided Silent failure. The hardest bug class to debug because it produces no error log. Note The list of "essential" types is static, defined per node type in the registry. Non-essential orphans are only pruned (skipped), without failing.

3 Why inside the workflow, and not in the backend

Natural question: why not run this validation at <strong>1.2 / 1.3</strong> (backend, before enqueue)? That way the error would return directly to the client in the HTTP response, without even starting a workflow.

The answer is: <strong>the backend does not have the DAG</strong>. It has the raw topology (nodes and edges). The DAG only exists after buildDag runs. buildDag is what scans refs, classifies edges, removes back-edges. Without the DAG, the backend could only do superficial validations (syntax, required fields). Duplicating buildDag's logic in the backend would violate the "backend only enqueues" principle.

Check Possible in backend? Possible in workflow? Reason
2.3.a. Cycles. No Yes Needs buildDag to run first to know if cycles still remain after back-edge removal.
2.3.b. Broken refs. Partial Yes Backend could do a text scan. The ref parser lives in the workflow. Duplicating it is risk.
2.3.c. Types. Partial Yes Backend does not load the type registry. Only knows nodeType IDs.
2.3.d. Orphans. No Yes Needs the <em>reachable</em> list, which comes from buildDag's BFS.
Side benefits of running in the workflow:
• Runs on the <em>frozen snapshot</em> (1.3), not on the live config that the user may have edited between validation and execution.
• Idempotent and retryable by Temporal. If the worker crashes mid-flight, replay is cheap (pure query, no side-effect).
• Centralises the guarantee. Any entry path (the 6 legacy endpoints) goes through the same validator. Cannot be "bypassed" by calling an alternative endpoint.

4 How it sustains the 3.2 invariant

∞

The 3.2 deadlock guard only works because validateDag exists

Step 3.2 checks "<code>readySet.size === 0 && pending.size > 0</code>?" and fails with <code>DeadlockError</code> if true. Its documentation explicitly says "<em>should not happen if validateDag passes</em>".

Without 2.3, 3.2 would be the <em>primary</em> line of defence against broken DAGs. Every deadlock would appear without context. With 2.3 passing, 3.2 becomes a <strong>purely secondary</strong> defence. If it fires in prod, it is an engine bug (buildDag or validateDag failed to cover a case), not the user's flow. This completely changes the debug playbook.

Same relationship with <strong>3.4.1</strong> (substitutePlaceholders). Without ref validation, its error would be common and ambiguous ("broken ref at runtime"). With validation, if it fails, it is because the ref points to something that <em>should exist but is not in the OutputStore</em>. Sequencing problem, not config. The bug's scope shrinks a lot.

5 What changes with this step (with vs without)

Concrete scenario: a research agent flow with 8 nodes, where the penultimate node has a broken ref. Comparing the two paths:

Without validateDag (current architecture)
1
Backend enqueues, workflow starts. ~50ms. No real cost.
2
Waves 1–5 run OK (searches, extractions, comparisons). ~45s of execution + ~15k LLM tokens billed.
3
Wave 6 starts. Dispatches the node with the broken ref. INSERT into node_executions (status=running).
4
substitutePlaceholders explodes. <code>{{DeletedNode.x}}</code> = undefined. Alternative 1: LLM runs with garbage prompt. More tokens spent.
⚠
Execution fails after 45s + $0.30 spent.
Partial error callbacks. Inconsistent node_executions. User sees error without context.
With validateDag (v2 architecture)
1
Backend enqueues, workflow starts. ~50ms. No real cost.
2
Bootstrap: loadTopology → buildDag → <strong>validateDag</strong>. ~10ms. Pure, no I/O.
✓
Detects broken ref. Aborts immediately.
flow_executions.status = failed with <code>InvalidReferenceError</code> pointing to exactly which node and which ref.
3
Single error callback. User sees a clear message. 0 tokens spent, 0 external calls, 0 dirty rows in node_executions.
4
Editor can visually highlight the node with the broken ref. Diagnosis is immediate because the error carries the nodeId.
At scale, the effect is large. In production with hundreds of executions per hour, every 1% of flows with broken refs translates into thousands of dollars/month in wasted tokens and support pages of "my agent ran but did not give me a response". validateDag pays back its own implementation cost quickly.

6 What validateDag does not do

Scope is deliberately restricted. The following validations do <strong>not</strong> live here:

Credits, permissions, model access

Runs at 1.2 (backend). Does not depend on the DAG. Failing early (before enqueue) saves a round-trip to Temporal.

Runtime placeholder value validation

E.g. prompt has <code>{{X.y}}</code> where X exists but <code>y</code> is not in the real output. Can only be known after X runs. Lives at 3.4.1. validateDag does not try to predict output fields.

Prompt semantics check

E.g. empty prompt, prompt larger than the model's context window. These are per-node problems, handled at dispatch or by the provider itself.

Estimated cost / budget limit

Orthogonal. If it exists, it would be a separate step 2.3.5 (with business rules, not DAG structure rules).

Rule of thumb: validateDag validates <em>graph structure</em>. Business (credits, quotas, budget) lives in the backend. Runtime value semantics lives at dispatch. Each layer sees the smallest set of invariants it needs.

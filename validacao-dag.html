Validação do DAG

O portão fail-fast entre montar o grafo e começar a gastar recursos.

1 O que é essa etapa

O passo 2.3 (validateDag()) roda logo depois do buildDag (2.2) e antes do loop de ondas paralelas (FASE 3). É um passo puro. Só leitura da estrutura do DAG, sem I/O. Serve como o último ponto onde o workflow pode abortar sem ter gasto nada. Nenhuma linha em node_executions, nenhum token de LLM, nenhuma chamada externa.

A regra é simples. Se o DAG passa aqui, ele só pode falhar por motivos de runtime real (LLM caiu, HTTP 500, timeout). Nunca por dado estrutural inválido. Essa garantia é o que permite tratar os guards da FASE 3 (deadlock em 3.2, falhas em 3.6) como puramente defensivos.

Onde ele mora: dentro do workflow Temporal, imediatamente após buildDag(snapshot). Roda sobre o DAG já construído (não sobre o snapshot cru). Alguns checks precisam da adjacency list e do inDegree, não só da topologia bruta.

2 O que valida

São quatro classes de erro. Cada uma pega uma categoria diferente de bug estrutural. Todas causam fail-fast. O workflow lança exceção non-retryable e vai direto para a FASE 4 (finalização em modo failed).

2.3.a Ciclos remanescentes

O buildDag (2.2) já roda DFS para detectar e remover back-edges. Se algo passou (bug do algoritmo, dado corrompido, grafo malformado que enganou a detecção), o resultado é um ciclo que sobrevive até o runtime. Sem essa checagem, o loop de ondas (3.1) nunca conseguiria chegar a inDegree === 0 nos nós do ciclo. Cairia só no deadlock guard de 3.2, sem contexto do que causou.

Exemplo
Prompt(NodeA) = "Baseado em {{NodeB.output}}, ..."
Prompt(NodeB) = "Baseado em {{NodeA.output}}, ..."

Detecção A → B e B → A. buildDag remove uma das back-edges. Se ambas foram criadas como refs implícitas e o critério de "qual remover" falhou, o ciclo sobra. validateDag falha com CycleDetectedError({ cycle: [A, B] }).
Erro lançado CycleDetectedError. Inclui a lista de nós no ciclo para debug. Custo evitado Deadlock silencioso descoberto só após tentar executar todas as outras branches do flow. Por que aqui Só dá para saber se o DAG é acíclico depois do buildDag. Antes disso a estrutura ainda tem back-edges.
2.3.b Refs {{...}} apontando para nós inexistentes

Cenário clássico: usuário renomeou/deletou um nó mas outro nó ainda tem {{OldName.field}} escondido no meio de um prompt de 500 linhas. O buildDag consegue até construir um grafo válido (ignora refs sem alvo). Quando o nó consumidor rodar em 3.4.1, o substitutePlaceholders vai encontrar a ref órfã e explodir.

Exemplo
Flow tem: Topic, WebSearch, Compare, Article.
Usuário deleta WebSearch mas esquece de limpar o prompt do Compare:
Prompt(Compare) = "Compare {{WebSearch.results}} e {{NewsSearch.results}}"

Sem validação Topic roda (5s, custo real). Compare começa a substituir. {{WebSearch.results}} vira undefined. Prompt vira lixo. LLM roda com prompt corrompido. Cobra token. Retorna resposta inútil.

Com validação InvalidReferenceError({ node: "Compare", brokenRefs: ["WebSearch.results"] }) antes de qualquer dispatch.
Erro lançado InvalidReferenceError. Lista qual nó tem qual ref quebrada. Custo evitado Todas as dependências do nó quebrado rodam à toa (tokens, tempo, quotas de API externa). Por que aqui O buildDag já escaneou as refs para criar deps implícitas. Só falta cruzar a lista de refs com o set de nodeIds existentes. Custo O(refs).
2.3.c Tipos incompatíveis entre source e target

Cada tipo de nó declara seus input handles (o que ele espera receber) e output handles (o que ele produz). Uma aresta liga um output-handle de A a um input-handle de B. Se os tipos não batem, o dispatch de B vai receber lixo ou falhar na coerção.

Exemplo
Aresta: PdfExtractor.file_bytes → TextGenerator.prompt_text.
Tipos: Binary → String (incompatível).

Sem validação A conversão silenciosa transforma binário em [object ArrayBuffer]. LLM roda com prompt corrompido.

Com validação TypeMismatchError({ edge: [PdfExtractor, TextGenerator], expected: "String", got: "Binary" }).
Erro lançado TypeMismatchError. Identifica a aresta e o mismatch. Custo evitado Execuções LLM com prompts corrompidos. Resultados inúteis cobrados como sucesso. Nota Só valida arestas explícitas. Refs {{...}} têm tipo dinâmico (o valor pode ser qualquer coisa). O mismatch delas só dá para pegar em runtime.
2.3.d Nós órfãos essenciais

Alguns tipos de nó são marcados como essenciais. Se estão no flow, a execução precisa alcançá-los para ser considerada válida. Exemplos: outputNode, responseNode, webhookResponse. Se um deles ficou desconectado (ex: usuário deletou a última aresta que chegava nele), o flow "termina com sucesso" mas não produz saída. Pior que falhar. Falha silenciosamente.

Exemplo
Flow chatbot: UserMessage → TextGen → ResponseNode.
Usuário deleta a aresta entre TextGen e ResponseNode.

Sem validação Execução roda. TextGen produz saída. ResponseNode é unreachable, podado em buildDag. Flow termina "com sucesso". Cliente não recebe resposta. Usuário vê "erro do sistema" sem log de erro real.

Com validação OrphanEssentialNodeError({ nodes: ["ResponseNode"] }). Execução falha com erro claro apontando que a resposta não está conectada.
Erro lançado OrphanEssentialNodeError. Lista nós essenciais desconectados. Custo evitado Falha silenciosa. Classe de bug mais difícil de debugar porque não gera log de erro. Nota A lista de tipos "essenciais" é estática, definida por tipo de nó no registry. Nós não essenciais órfãos são só podados (skipped), sem falhar.

3 Por que dentro do workflow, e não no backend

Uma pergunta natural: por que não rodar essa validação no 1.2 / 1.3 (backend, antes do enqueue)? Assim o erro voltaria direto para o cliente no HTTP response, sem nem iniciar workflow.

A resposta é: o backend não tem o DAG. Ele tem a topologia crua (nós e arestas). O DAG só existe depois do buildDag rodar. O buildDag é que faz o scan de refs, classifica arestas, remove back-edges. Sem DAG, o backend só poderia fazer validações superficiais (sintaxe, campos obrigatórios). Duplicar a lógica do buildDag no backend violaria o princípio "backend só enfileira".

Check Possvíel no backend? Possível no workflow? Motivo
2.3.a. Ciclos. Não Sim Precisa do buildDag rodar antes para saber se ainda há ciclos após remoção de back-edges.
2.3.b. Refs quebradas. Parcial Sim Backend poderia fazer scan textual. O parser de refs vive no workflow. Duplicar é risco.
2.3.c. Tipos. Parcial Sim Backend não carrega o registry de tipos. Só conhece IDs de nodeType.
2.3.d. Órfãos. Não Sim Precisa da lista de reachable, que sai do BFS do buildDag.
Benefícios colaterais de rodar no workflow:
• Roda sobre o snapshot congelado (1.3), não sobre a config viva que o usuário pode ter editado entre a validação e a execução.
• É idempotente e retryable pelo Temporal. Se o worker cair no meio, replay é barato (query pura, sem side-effect).
• Centraliza a garantia. Qualquer path de entrada (os 6 endpoints legados) passa pelo mesmo validador. Não dá para "burlar" chamando um endpoint alternativo.

4 Como sustenta o invariante do 3.2

∞

O deadlock guard do 3.2 só funciona porque validateDag existe

O passo 3.2 checa "readySet.size === 0 && pending.size > 0?" e falha com DeadlockError se sim. A documentação dele diz explicitamente "não deve acontecer com validateDag passando".

Sem o 2.3, o 3.2 seria a linha de defesa primária contra DAGs quebrados. Todo deadlock apareceria sem contexto. Com o 2.3 passando, o 3.2 vira defesa puramente secundária. Se disparar em prod, é bug do engine (buildDag ou validateDag falharam em cobrir um caso), não do flow do usuário. Isso muda completamente o playbook de debug.

Mesma relação com o 3.4.1 (substitutePlaceholders). Sem validação de refs, o erro dele seria comum e ambíguo ("ref quebrada em runtime"). Com validação, se ele falhar, é porque a ref aponta para algo que deveria existir mas não está no OutputStore. Problema de sequenciamento, não de config. Escopo do bug fica muito menor.

5 O que muda com esse passo (com vs sem)

Cenário concreto: um flow de agente de pesquisa com 8 nós, onde o penúltimo nó tem uma ref quebrada. Comparando os dois caminhos:

Sem validateDag (arquitetura atual)
1
Backend enfileira, workflow inicia. ~50ms. Sem custo real.
2
Ondas 1–5 rodam OK (buscas, extrações, comparações). ~45s de execução + ~15k tokens LLM cobrados.
3
Wave 6 começa. Dispatch do nó com ref quebrada. INSERT em node_executions (status=running).
4
substitutePlaceholders explode. {{DeletedNode.x}} = undefined. Alternativa 1: LLM roda com prompt lixo. Mais tokens gastos.
⚠
Execução falha depois de 45s + $0.30 gastos.
Callbacks de erro parciais. node_executions inconsistente. Usuário vê erro sem contexto.
Com validateDag (arquitetura v2)
1
Backend enfileira, workflow inicia. ~50ms. Sem custo real.
2
Bootstrap: loadTopology → buildDag → validateDag. ~10ms. Puro, sem I/O.
✓
Detecta ref quebrada. Aborta imediatamente.
flow_executions.status = failed com InvalidReferenceError apontando exatamente qual nó e qual ref.
3
Callback único de erro. Usuário vê mensagem clara. 0 tokens gastos, 0 chamadas externas, 0 linhas sujas em node_executions.
4
Editor pode destacar visualmente o nó com a ref quebrada. Diagnóstico é imediato porque o erro traz o nodeId.
Em escala, o efeito é grande. Em produção com centenas de execuções por hora, cada 1% de flows com refs quebradas se traduz em milhares de dólares/mês em tokens desperdiçados e páginas de suporte "meu agente rodou mas não me deu resposta". O validateDag paga o próprio custo de implementação rapidamente.

6 O que o validateDag não faz

Escopo é deliberadamente restrito. As seguintes validações não vivem aqui:

Créditos, permissões, acesso a modelos

Rodam no 1.2 (backend). Não dependem do DAG. Falhar cedo (antes de enfileirar) economiza um round-trip ao Temporal.

Validação de valores de placeholders em runtime

Ex: prompt tem {{X.y}} onde X existe mas y não está na saída real. Isso só dá para saber depois de X executar. Fica no 3.4.1. O validateDag não tenta prever campos de saída.

Verificação de semântica de prompt

Ex: prompt vazio, prompt maior que context window do modelo. São problemas do nó individualmente, tratados no dispatch ou pelo próprio provider.

Custo estimado / limite de orçamento

Ortogonal. Se existir, seria um passo 2.3.5 separado (com regras de business, não de estrutura de DAG).

Regra prática: validateDag valida estrutura do grafo. Negócio (créditos, quotas, orçamento) fica no backend. Semântica de valores runtime fica no dispatch. Cada camada vê o menor conjunto de invariantes que precisa.

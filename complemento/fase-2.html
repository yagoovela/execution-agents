A The immutable DAG already exists as pure code
scheduler.ts:152 · 295 · 352 · 412
Confirming that the graph builder the v2 describes does not need writing.
// scheduler.ts — no injection, no database, pure function export function buildSchedulerState(nodes, edges, starterId): SchedulerState export function nextReady(state): string | null // ← returns ONE id export function markCompleted(state, id): void export function completeCondition(state, id, handle): void
How it is today
It is already the single source of ordering truth, consumed by flux.service.ts in three places and even by the MCP write service. No NestJS, no database, no I/O.
How it will be
The same module, consumed by the worker. The only change parallelism requires is a sibling of nextReady that drains the whole set instead of one id — markCompleted and markDead are already set-based and already tolerate out-of-order completion, which is what parallel siblings produce.
A decision comes first
Shared package or copy-port. The repos are separate submodules with no common build graph; the integrations migration chose copy-port for reasons that do not apply here, because these two modules drag no dependencies.
If copy-port wins
A drift test that fails when the copies diverge — not a comment asking for care. And the back does not run jest in CI, so say how that test will actually run.
B The OutputStore key must name one execution
node_execution.entity.ts · fetch-node-row.ts:31-47 · persist-node-success.ts:7-9
Making the identifier that travels between nodes name an execution of a node, not “a node within a run”.
-- no unique constraint on (execId, nodeId) INSERT INTO node_executions (...) -- no ON CONFLICT UPDATE node_executions SET outputData = $1 WHERE "execId" = $2 AND "nodeId" = $3 -- ← every matching row SELECT ... FROM node_executions WHERE "execId" = $1 AND "nodeId" = $2 -- rows[0], no ORDER BY
How it is today
Inside a loop the same nodeId runs several times under the same execId. Today it is contained because the single-node path mints a fresh execId per click — but it stops being contained the moment a consumer reads an upstream's output by that pair.
How it will be
Either node_executions.id, which is already the PK, becomes the reference that travels; or an iteration discriminator joins the key. Pick one and write down why, because the choice constrains input resolution and control flow. Alongside: ORDER BY on every read that can match more than one row, and a targeted persistNodeSuccess.
Careful with billing
sumChargesByExecution aggregates by the same pair. In a loop, “every matching row” may have been the intended behaviour — confirm the total does not change.
Why before and not after
Fixing this later means swapping the transport underneath running code.
C Reference-based resolution is already in production
flux/prefetch/ · flux.service.ts:1402-1421 · 3198
Confirming that the model phase 2 proposes does not need designing.
isPrefetchMode() // FLUX_EXEC_MEMORY_MODE === 'prefetch' (default: legacy) canUsePrefetchForFlow(nodes) // every node of the flow in the whitelist (17 types) scanPlaceholderRefs() // discovers only the refs the node uses loadOutputsByRefs() // fetches only those node_executions rows OutputPointer { rowId, type, size }
How it is today
The prefetch executor already builds a small schemaForNode instead of mutating the global one, and already carries outputs as pointers. It is in production behind a flag, defaulting to legacy, with a whitelist that excludes every Temporal type and every control-flow type.
How it will be
Measure first: how many production flows satisfy the whitelist, and how many ran with the flag on. A flag on legacy whose whitelist excludes every LLM node may be shipped and dormant. Then either widen and relocate that executor, or implement resolution in the worker and retire it — both are valid answers; leaving it undecided is not.
What changes meaning
node_executions.input stops being a precondition for running and becomes a record of what the node ran with. It keeps being written — history and debugging depend on it.
D Snapshot and DAG in workflow state grow with the run
worker/src — no continueAsNew
Stopping phase 2's own mechanism from blowing up on the largest runs.
$ grep -r "continueAsNew" worker/src (no results)
How it is today
A Temporal workflow accumulates history events, and both the count and the size are bounded. One workflow per run grows with every activity scheduled and completed and every value passed — and is terminated by the platform on exactly the largest and most valuable runs.
How it will be
continueAsNew at an explicit boundary: iteration count or node count. Pick the number and prove it by running a graph past it. And state by reference, never by value — which the execution key from topic B makes possible: the workflow carries ids, and the payloads stay in Postgres and S3.
This is what our own analysis missed
We reasoned about Postgres and never about workflow history as a storage medium. Worth measuring: run the widest and the longest flow that exists and record count and size at the end, against the platform's limits.
E The v2's cycle validation is intra-graph
flux.service.ts:5611-5622
Telling apart two problems that look the same and are not.
// flowCallerNode re-enters the whole orchestrator const nestedFlowResult = await nodeCancelContext.run(undefined, () => this.apiV2({ body, user, flowId: flowIdSelected, ... })); // no depth counter, no visited set
How it is today
Phase 2's gate validates cycles between nodes of the same flow. That does not catch flow A calling B calling A: flowCallerNode re-enters the whole orchestrator, and each level is a complete run with its own scheduler, its own rows, its own log tree and its own spend.
How it will be
A depth counter and a visited-flow set carried in the run context — the same context that crosses the boundary into a child workflow. Two distinct refusals, because they are distinct mistakes: cycle always refused, with no legitimate case; depth refused with the chain named, so the author can see which composition got too deep.
Measure before refusing
Walk the stored flows, compute the real nesting depth and detect existing cycles. A ceiling that refuses a working customer flow is worse than the recursion it prevents.
Why before phase 3½
Today the recursion hits one process's memory. As a child workflow, a durable platform sustains it across the fleet, with retries.

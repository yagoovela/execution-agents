A Control flow belongs to the workflow
flux.service.ts:6742 · 3738
Recognising that two of the special nodes do not compute a value — they decide what runs.
// conditionNode node.data.currentLoopCounter += 1; // mutates in place newIds = findConnectedNodes(nodes, edges, source).allIds; // rewrites the queue // arrayNode const nodesToProcess = flowNodes.slice(idxFirstId, idxLoopingToId + 1);
How it is today
An activity's return value does not reshape the caller's iteration. arrayNode is a for over a sub-graph by index arithmetic over the ordered node list — remove the loop and there is nothing left to extract.
How it will be
Condition and loop semantics as deterministic workflow control flow, calling completeCondition. computeLoopBody already exists in the scheduler — use it, rather than re-deriving the body by index as the inline version does. And determinism on replay: counter and result coming from an activity result or from workflow state, never from time or randomness.
The v2 read this right
Treating them as their own lanes is correct: they genuinely break “one dispatch, one output”.
Replay test
Take a completed history and re-execute it. Non-determinism shows up here and nowhere else.
B A child workflow turns recursion into a fleet problem
flux.service.ts:5400 · 5717
Stopping phase 3½ from turning a contained bug into a distributed incident.
// today: bounded, crudely, by one process's memory flowCallerNode → this.apiV2({ flowId: selectedFlow, ... }) // tomorrow, as a child workflow: the platform sustains it and retries
How it is today
Flow A pointing at B and B back at A recurses until something dies. Each level is a complete run. Two people composing reusable flows produce this by accident.
How it will be
The depth ceiling and the visited set from the phase 2 topic, carried in a context that crosses the child-workflow boundary. Without it, phase 3½ is a durable fork bomb.
Mandatory ordering
The guard must exist before sub-flows become child workflows, not after.
C The loop ceiling can be switched off by the node's data
folw/helpers/helpers.ts:2075-2110
Having a maximum number of iterations that holds regardless of node configuration.
if (loopBehavior === 'continue') { finalResult = userConditionResult && loopLimitCheck; // capped } else { finalResult = userConditionResult; // NO ceiling }
How it is today
On the second branch the limit is computed, reported to the UI through loopStatus and the socket event, and then not applied. And on the capped branch the limit is node.data.loopCount — user data.
How it will be
A system maximum applied on both branches, independent of loopBehavior and of loopCount. The node's own limit still holds where it is lower: it is a ceiling, not a replacement. And a distinct stop reason, otherwise the user reads “limit exceeded” and goes looking for a limit they never configured.
It applies to arrayNode too
A processorArray of a hundred thousand items is the same runaway with another shape.
Where to put the number
An env var, with a generous default, above the largest real loop found in the stored flows — the intent is to stop the unbounded case, not to second-guess a legitimately long loop.
D The Object Caller breaks the semantics too
flux.service.ts:6834
Migrating the only mutating node whose logic is genuinely extractable.
objectCallerData // in-memory array for the run, passed by reference sessionStateService.readLatest({ scopeType:'object', ... }) onMutateObjectCallerData(...) // publishes the change back into the run
How it is today
It mutates data, not control flow — which is why it is the only one in the group with extractable logic, about 130 lines. The work is entirely in what has to exist around it.
How it will be
An object-state callback (read and write) and a session-state one mirroring readLatest and appendEntries. And an explicit answer on ordering: today the engine serialises every Object Caller in a run through one in-memory array; two callers on the same object must stay ordered once they are independent activities.
Do not leave ordering for later
Either an advisory lock, or an idempotent activity. Pick one and say why — do not ship hoping the order holds.
The pattern is already in the repo
pg_advisory_xact_lock in the OAuth token repo solves the same shape of race.

A Moving the loop and turning on parallelism are two deploys
flux.service.ts:507 · 3227 · process-agent.workflow.ts
Reaching the wave loop without losing the ability to say what broke.
// today: the back blocks on every node const handle = await this.temporalService.client.start('processSingleNode', {...}); await handle.result(); // ← accidental back-pressure // the parallel loop was already written, and commented out: // worker/src/modules/temporal/workflows/process-agent.workflow.ts // "It will not be used for the time being; the logic has already been removed." // in-degree per node · readyToRun · Promise.all
How it is today
Every migrated node is a synchronous round trip with more latency than inline, and with no parallelism between siblings. The wave design already exists in that commented-out file.
How it will be
Ship the graph workflow sequential first — allReady returning one id is exactly today's behaviour. Prove order equivalence over stored flows, node for node. Only then raise the batch size, in a second deploy, gated per flow.
Why the order is not optional
Two changes hide inside “move the graph”: relocating the loop, and letting it dispatch more than one. Together, a rollback cannot say which broke. Apart, each is a flag.
The back-pressure goes with it
The blocking wait also stops the back from starting more work. Removing it without the ceilings trades a slow system for an unstable one.
B The database hits its ceiling before throughput does
database.service.ts:13 · worker.service.ts:20-22
Knowing how many worker replicas this database can take — today nobody does.
this.pool = new Pool({ host, port, user, password, database }); // ↑ no max → node-postgres uses 10 per process maxConcurrentActivityTaskExecutions: 10
How it is today
Each replica can hold ten busy connections, and the total scales linearly with replicas against a max_connections shared with the API. The failure mode is not slowness, it is too many clients already on customer requests. No connection proxy appears anywhere in the infrastructure.
How it will be
An explicit max, plus idleTimeoutMillis and connectionTimeoutMillis, so a saturated pool fails fast with a clear error instead of hanging the activity until its startToCloseTimeout. And the arithmetic written down: max_connections versus API replicas × pool + worker replicas × pool + migrations + operators. That sentence is the deliverable.
PgBouncer in transaction mode
Decouples replica count from connection count. Transaction mode forbids session state — and pg_advisory_xact_lock is transaction-scoped, so it survives.
It blocks before parallelism
This gates not only phase 3, but adding any worker replica today.
C Nothing limits what a run spends
product.service.ts:265-284
Putting the cost ceiling where it keeps working once the worker owns the loop.
async assertCompletionCredits(user) { // INTRO → trialTokens > 0 ; otherwise, having a subscription is enough if (userProduct?.product?.type === ProductType.INTRO) { if ((currentUser?.trialTokens ?? 0) <= 0) throw this.insufficientQuotaError(); } } // ← boolean gate, not a budget
How it is today
Per node, getUserProductFromFlow checks entitlement to a model, not remaining budget. Charges are recorded after the fact in token_transactions. Nothing decrements an allowance and nothing aborts a run that has already overspent — on a paid account, the first signal is the invoice.
How it will be
A per-run ceiling checked at charge time, in the same call that already records the spend: it is the only place that keeps working with the loop in the worker, and it needs no new plumbing, because /worker/charge-tokens already carries the execId. Abort with a typed error carrying the ceiling and the spend, rather than degrading silently.
Measure against history
Compute what the proposed ceiling would have done to every real stored run. Any run that legitimately completed and would be aborted is a false refusal, and that count must be zero before shipping.
The ceiling derives from the plan
A single number is wrong at both ends of the customer range. A column on the product, with a conservative default and a per-org override.
D Parallelism is only safe with full coverage
folw/contants.ts:2018-2062 · persist-node-success.ts:59-63
Making sure no node in the flow writes into another's row while siblings run together.
// worker: writes into its OWN row UPDATE flows_nodes SET data = coalesce(data,'{}'::jsonb) || $1::jsonb WHERE node_id = $2 AND flow_id = $3 // back inline: writes into the TARGET's row addConnectToNodes({ edges, nds, nodeData }) → modifyData(nodes, targetId, ...)
How it is today
All-backend is safe because it is serial. All-worker is safe because every write is own-row. Mixing the two and running in parallel is a lost update — and it shows up rarely and reproduces badly.
How it will be
Per-flow eligibility read from the dispatch registry: run in parallel only when every executable node in the flow is a migrated type. If a flow is not eligible, the answer is to migrate the nodes that are missing — never to loosen the check.
The test that justifies the gate
Force an ineligible flow through the parallel path and demonstrate the corruption: two writers on one row, one write disappearing. Without having seen that, nobody keeps the gate strict.
How much is left
Production dispatches seven types plus nine providers. Track A is what makes the v2's premise true.
E Notifications do not cross replicas
flux.service.ts:2288 · 5293-5307 · gateway.ts:69,76
Delivering a run event to the right client with more than one backend replica.
chatbotSocketByRun[runId] = socketId; // ← process-local Map // worker → Redis → @EventPattern → gateway.emit(...) // inline → gateway.emit(...) directly
How it is today
A run whose socket was registered on replica A cannot be notified from replica B. Already broken today, without depending on the migration. And there are two mechanisms — the direct socket and the Redis pub/sub — which will drift.
How it will be
One path only: everything publishes to Redis and the socket layer merely consumes. A Redis adapter for Socket.io, so any replica can deliver to any connected client. And typed statuses — PENDING, RUNNING, COMPLETED, FAILED, CANCELLED are free strings on both sides of a process boundary, the worst place for a typo.
Before parallelism
Parallel dispatch multiplies the event rate. And per-node ordering starts to matter: a RUNNING cannot arrive after the same node's COMPLETED.

A Admission: three of the four entry points do not authenticate
flux.controller.ts:470-471 · 352-362 · mail.service.ts:453-487
Deciding who is entitled to create a run. Today that decision is barely taken at all.
@Public() @Post('/api-v2-webhook') // ... const flow = await Flow.findOne({ where: [ { id: query.flowId }, // ← no public condition { id: query.flowId, public: true } ] }); if (!flow) { /* ... */ } // ← the only check
How it is today
@Public() takes the route out of the global guard. The where is an OR whose first branch has no public condition, which kills the second: any flow matches, public or private. Scanning the rest of the handler for a secret, a token or an owner finds only the if (!flow). Whoever knows a flow id executes that flow and charges its owner. Email is worse: a private flow is authorised by the From header, which anyone forges, and a public flow has no check at all — with the sender controlling the prompt.
How it will be
A per-flow secret verified before anything else, and the public predicate made to mean something. For email, either sender verification (DKIM/SPF/DMARC) or the secret inside the address — <flowId>+<token>@… — so that holding the address is the credential. Rate limits keyed by whoever pays: API key, organisation and flow. All of it in report-only mode first, against real traffic, before actually refusing.
Migrating matters more than fixing
Customer integrations call this URL today. Turning verification on cold breaks every automation silently, and the failure reads as “my automation stopped”. Optional secret with a deprecation window and a metric counting unauthenticated calls per flow, then enforce.
Why rate limiting is part of this
Bull's serialisation limits execution, not admission. The queue grows without bound and the rows, logs and dedup keys are written on the way in regardless.
B Every scheduled trigger counts once per replica
schedule.controller.ts:157-159 · 179 · 242 · mail.service.ts:132
Making a schedule fire once, rather than once per backend replica.
// inside the cron callback, in-process: await this.scheduleQueue.add('schedule-job', { ... job: await this.fluxService.apiV2({ ... }) // ← the run already executed here }); this.schedulerRegistry.addCronJob(body.name, schedule);
How it is today
Schedules live in NestJS's in-process registry, so each replica holds its own copy and fires independently: N replicas, N runs, each charged. And apiV2 is awaited as an argument to queue.add — the flow already ran synchronously inside the callback, and only its result reaches the queue. The thirteen framework @Crons have the same problem, with no leader election, including the POP3 poll every ten seconds.
How it will be
Temporal Schedules for user schedules: one fire per schedule by construction, durable across deploys, with pause, backfill and last-run visibility. An advisory lock per job name for the thirteen framework crons, which are internal maintenance and have no reason to become workflows. And the callback stops awaiting the run — the queue becomes the owner of execution.
The lock already exists in the code
pg_advisory_xact_lock is already used in the OAuth token repo. It needs no new dependency and degrades correctly: the replica that cannot take the lock skips.
What to preserve
The zombie-cron cleanup — stop, delete and soft-delete when the flow is gone — is the part of that file already doing the right thing.
C The batch has no phase in the v2 at all
flux.controller.ts:560 · 574-706
A CSV batch is a sequence of complete runs. Today nothing orchestrates it.
this.processBatch(batchFile, batchFile.flow, body.batchId).catch(...) // ↑ no await: the request returns and the work continues detached in the process for (let rowIndex = startRow; rowIndex <= endRow; rowIndex++) { const currentBatch = await BatchProcessingFile.findOne(...) // 4-5 round trips const responseOrError = await this.fluxService.apiV2({ ... }) // a complete run await rowRecord.save(); }
How it is today
A sequential for of complete runs, detached inside the API process, with four to five database round trips per row on bookkeeping alone. A deploy, restart or scale-down mid-way kills the loop silently and the batch stalls at lastProcessedLine with a non-terminal status, with nothing to resume it.
How it will be
A batch workflow with a child per row, a concurrency cap, and the pointer as workflow state rather than a re-read column. continueAsNew at a row boundary, because a large CSV is exactly the case that exhausts history. The stop endpoint becomes workflow cancellation, which also cancels the rows in flight — better than today, where stopping sets a flag the loop consults.
The largest multiplier
A thousand rows is a thousand complete runs from one API-key call, against no rate limit, no per-run cost ceiling and no per-tenant cap.
The bookkeeping disappears
Re-reading the batch on every iteration exists because the loop cannot trust its own memory across restarts. A workflow can.

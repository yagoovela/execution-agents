A The error taxonomy already exists
worker/src/modules/nodes/shared/node-error.ts
Confirming that the piece the v2's RetryPolicy depends on is already in the worker.
UserConfigError · IntegrationError · ProviderError · TimeoutError · SystemError
How it is today
Retry semantics derived from the error type is exactly right, and it is what keeps a user's typo from retrying for thirty minutes.
How it will be
The per-node-type RetryPolicy phase 6 proposes derives from it. Nothing to build — what is missing is each new node throwing the right subclass, and that is an item in the definition of done.
Credit it rather than rebuild it
Worth saying explicitly that this part is already solved, otherwise someone reimplements it.
B Fix the defects before duplicating the code
flux.service.ts:3276,3868,7978,8031,8083,8210 · 4537,4553
Not paying twice for a bug that already exists.
if (responses.length === 10) { ... } // strict equality, at SIX sites runLogCollector?.endNode(genericRunLogNode, {...}); // :4537 runLogCollector?.endNode(genericRunLogNode, {...}); // :4553 — again
How it is today
One element is appended per run, so the cap normally holds — but any array that gets past ten by another path never trims again, and grows without bound inside flows_nodes.data, which is the known front-end performance offender. The duplicate endNode is harmless today and will confuse whoever ports the collector.
How it will be
Change it to >=, and measure how many real arrays already got past ten before deciding on a backfill — an unnecessary data migration is its own risk. One test per fix, failing first: seed a node with eleven responses, run it, assert the array does not grow.
Also on this list
api-caller-polling.ts has no importer — the polling already lives in the worker as execute-polling. Prove it across all repos and origin/production before deleting.
C Seven registration layers, all load-bearing
docs/worker/ · skills/node-worker-migration
Making it possible to add a node type without producing a node that does nothing.
module · enum · temporal.module · activities.service · worker.service · configs.ts (proxy) · process-single-node.workflow (case) // miss one: a node that appears to run and does nothing, // or "Node type X not supported" from the default branch
How it is today
The documentation in docs/worker/ already exists — and describes sql-querier, audio-transcriber and mcp, which is to say a system more migrated than the one that runs. And the skill an agent loads describes a ten-type enum from July.
How it will be
Audit before writing: for each existing page, does it describe production, a branch, or an intention? Then the contract generated from the dispatch registry, with a spec that fails when it and the worker enum diverge. Documentation that can go stale silently will.
The negative control here is real
Someone who has never done it adds a node following only the page. If they produce a node that silently does nothing, the page is wrong — and that is exactly the failure the seven-layer chain produces.

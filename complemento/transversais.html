A Coverage — the v2's premise
registro de dispatch · A1..A9
The v2 assumes every node is an activity. Making that true.
// today, in production: isTemporalNode → 7 tipos + integrações por provider → 9 providers // the rest stays inline in the back
How it is today
Four uncoordinated lists answer “does the worker run this type?”, and a fifth — basedOnType — decides which fields of a node a placeholder may reference, hand-maintained with no check.
How it will be
One derived registry, with the five lists reading from it. Behaviour-neutral by construction: same types dispatched, same refusals. The inconsistencies it exposes are fixed by the tasks that own them, not by this step.
Why first
Every later task writes into that registry. If it is still five lists, each one pays the tax and one of them will get it wrong.
B Hygiene — two implementations do not coexist
flux.service.ts (handlers inline) · folw/contants.ts:2032
Deleting what the migration replaced, so the back stops being a second implementation.
// while both exist: // they drift silently (someone fixes a bug on one side only) // or both fire (duplicate Stripe charge, duplicate Slack message)
How it is today
The inline twin does not coexist neutrally. And the cross-node write in addConnectToNodes is what makes mixed mode unsafe.
How it will be
The twin dies with its node's task, while the behaviour is fresh — not in a sweep months later. The cross-node write goes path by path, as each path's last inline caller leaves. When the last executable node migrates, addConnectToNodes should have no caller on the run path; if it does, something was missed.
Negative control
Before deleting, point the flag back at the inline path and confirm it works. After deleting, confirm the flag-off path fails loudly — a deleted path that fails silently is indistinguishable from a node that produced nothing.
C Egress — decide it with the move
downloader.controller.ts:34 · scraper · api_call
Deciding what a node may fetch before moving the fetcher to a host with more privilege.
// no private-range blocking in any of these modules GET /downloader?url=<qualquer coisa> // 169.254.169.254 · localhost · internal hostname
How it is today
This is pre-existing, not created by the migration. But the migration moves those fetchers into the worker, which sits in a different network position holding the database password and the integrations key.
How it will be
An egress policy at the shared fetch layer: resolve the hostname and check the resolved address, not the string; block loopback, link-local and private ranges; and re-check on redirect, which is the standard bypass. Plus the worker's network position written down: if it reaches less than the API, moving is a security improvement and worth saying so.
Report-only mode first
This rule refuses network traffic, the most disruptive kind of refusal. Sample the real stored URLs, classify them, and only then enforce.
D Claim check — guarding is not authorising
worker.controller.ts:87-95 · 45
Making a claim-check key redeemable only by the run it belongs to.
if (typeof body.key !== 'string' || !body.key.startsWith('node-exec/')) throw new BadRequestException('Invalid claim-check key'); const stream = await this.awsService.getFile(body.key); // ← and nothing else
How it is today
The only validation is a prefix. Whoever holds the internal key reads any node's output for any customer. The route sits behind InternalApiGuard, which is the right boundary — but it is a single shared secret, and this epic puts it on every worker replica.
How it will be
The caller states which execId and nodeId it is acting for; the endpoint parses the key and refuses when they disagree. The worker already has both. Same treatment for /worker/store-payload: nobody should write a payload into another run's key.
It can be superseded
Giving the worker its own S3 credentials removes both endpoints from the path. If that decision is taken, this task ceases to exist — check before starting.

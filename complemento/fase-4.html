A The run-log tree cannot live in the workflow
RunLogCollector · space_run_logs
Preserving the nested timeline once the loop leaves the backend process.
RunLogCollector: árvore em memória por run startNode / endNode · innerSteps · subRun startLoopBody / startLibrarySubRun → outra instância debounce → scheduleUpsert → space_run_logs
How it is today
The product's nested timeline depends on the hierarchy, not just on the events. And the collector lives in the backend process for the duration of the run.
How it will be
The backend rebuilds the tree from events the worker emits — which is already the shape of the Temporal path, where the worker emits status through Redis and writes execution_logs. Keeping the tree inside the workflow makes state grow with the run and collides with phase 2's history limit, so that option is discarded and should not be reopened.
The classic bug is already known
Using runLogCollector where loopRunLogCollector was meant makes iterations siblings of the loop rather than children. Reproduce it deliberately, then guard it with a test.
What gets better
The AsyncLocalStorage chargeContext goes with it: the worker always passes execId and nodeId explicitly over HTTP, which is the superior pattern. Less code, fewer competing patterns.
B redactSecrets is the only scrubbing point
dentro do RunLogCollector
Not turning a logging refactor into a credential disclosure.
redactSecrets(...) // the only place credentials are cleaned // before reaching space_run_logs
How it is today
It is the only point. Leaking into space_run_logs is a security event, not a logging bug.
How it will be
The hook stays, with a test of its own: put a credential through a node and assert it does not appear in space_run_logs; break redactSecrets and watch the test go red. Non-negotiable, not one bullet among several.
It changes home with the collector
A refactor that drops the hook fails no test today.
C Emails and callbacks are fire-and-forget
flux.service.ts:4907-5200 · 5030-5044
Stopping what a run sends from vanishing when the destination is down for thirty seconds.
// ~300 lines at the end of every run await this.mailService.sendMail(...) // three email paths axios.post(callbackUrl, payload).catch(...) // no retry // idempotency ALREADY exists: await this.redisClient.set(key, '1', 'EX', 86400, 'NX')
How it is today
Nothing is retried. A customer's webhook endpoint down for thirty seconds loses the notification, with a log line as the only trace.
How it will be
One delivery activity per channel, with a retry policy chosen per channel — a customer callback can persist; an email should not persist against a rate-limited relay. The dedup keys move with it, unchanged: they are the reason retry is safe. And a terminal failure starts appearing in the run log, not only in Winston.
The cleanest candidate left
Pure external I/O, no engine state, and the hard part is already done.
The test that proves the dedup
Run the activity twice for the same run and node and watch the key suppress the second; delete the key and watch it double-send. That second half is what proves the key is structural rather than decorative.

Algoritmo do DAG

Como o workflow decide o que roda, em que ordem e o que pode rodar em paralelo

1 O que é o DAG aqui

DAG (Directed Acyclic Graph) é a estrutura de dados que o workflow constrói uma vez, no início do run (passo 2.2 da arquitetura v2), e usa para dirigir todo o loop de execução da FASE 3.

A ideia central é simples: um nó só pode rodar quando todas as coisas de que ele depende já rodaram. Nós que não dependem uns dos outros podem rodar em paralelo. O DAG é a forma matemática de representar essas dependências, e o algoritmo de "ondas topológicas" é a forma de executá-lo maximizando paralelismo.

Por que "acíclico": se A depende de B e B depende de A, ninguém pode começar. O algoritmo detecta e remove ciclos (chamados back-edges) antes de começar a executar.

2 Os dois tipos de dependência

Aqui está o ponto crítico que a maioria dos DAGs de ferramentas de flow ignoram: a dependência não vem só das arestas visíveis do canvas. Ela pode vir também das refs {{...}} escondidas dentro do texto de configuração do nó. O algoritmo precisa considerar os dois.

Tipo A Arestas explícitas (edges do canvas)

São os "fios" que o usuário desenha ligando nó a nó no editor. Ficam salvos na tabela flows_nodes_edges. Cada aresta tem um source, um target e um type (control, condition, data, side-effect).

Toda aresta explícita é dependência — o nó target não pode começar antes de o source terminar.

Tipo B Refs {{...}} dentro do texto do nó

São placeholders que o usuário digita dentro dos campos do nó — prompts de LLM, corpos de requisição HTTP, expressões de script, etc. Nem toda ref é dependência de nó: depende do alvo que ela referencia.

DEP {{TextGen1.output}} — aponta pra saída de outro nó do flow  cria dep
DEP {{WebSearch_results}} — mesma coisa via alias humanizado  cria dep
SEM DEP {{input.body.topic}} — vem do request/trigger, não de um nó  sem dep
SEM DEP {{context.user.email}} — vem do contexto global (user/space)  sem dep
SEM DEP {{env.MY_API_KEY}} — vem de variáveis do workspace  sem dep

Consequência prática: se o algoritmo só olhasse as arestas, um nó com {{TextGen1.output}} no prompt sem aresta explícita para TextGen1 tentaria rodar antes de TextGen1. Resultado: substituição falharia e o run quebraria. Por isso o passo 2.2 escaneia refs além das arestas.

3 O algoritmo passo a passo

Rodando dentro do workflow Temporal, sobre o snapshot congelado no enqueue. Puro, sem I/O — só transformação de dados.

1
Seed com todos os nós
Cria mapa nodes: Map<nodeId, {type, ...}> a partir da topologia. Inicializa adjacency: Map<nodeId, Set<nodeId>> vazio e inDegree: Map<nodeId, number> zerado.
2
Processa arestas explícitas
Para cada aresta (source, target, type) da topologia:
• Adiciona target em adjacency[source]
• Incrementa inDegree[target]
• Guarda o type pra usar em pruning de conditionNode
3
Escaneia refs {{...}} em cada nó
Para cada nó N:
• Percorre todos os campos textuais da config (prompt, promptData, textData, contentData, corpos de request, expressões de script, etc.)
• Aplica regex /\{\{([^}]+)\}\}/g pra extrair as refs
• Para cada ref: descobre o alvo. Se for outro nó do flow ({{X.field}} onde X é um nodeId ou label válido) → adiciona aresta implícita X → N se ainda não existir; incrementa inDegree[N].
• Se for input/context/env → ignora (não cria dep).
4
Detecta e remove back-edges (ciclos)
Roda DFS a partir dos nós de entrada (in-degree=0 antes da remoção). Se um DFS visita um nó já na pilha atual, a aresta que fecha o ciclo é uma back-edge → é removida da adjacency e o inDegree do target é decrementado.
Nota: back-edges são normalmente erros de config (ref circular). Em runtime a gente escolhe remover em vez de falhar pra não travar flows que casualmente têm ciclos benignos.
5
Poda nós inalcançáveis
Faz BFS a partir dos nós com inDegree === 0 após passo 4. Nós não visitados = unreachable → marca como skipped, tira do pending.
6
Retorna estruturas imutáveis
• adjacency — final, não muda no run
• inDegree — inicial; será decrementado ao longo do run (mas isso é state, não muda a estrutura do DAG)
• edgeTypes — pra decisões de condition/side-effect na FASE 3
• pending — set inicial de nós a executar (todos menos os skipped)

4 Exemplo concreto

Flow simples: pesquisa em duas fontes em paralelo, junta os resultados e escreve um artigo.

Nós e sua configuração

Duas observações importantes:

1. Compare só tem refs, nenhuma aresta explícita — o usuário digitou {{WebSearch.results}} no prompt sem desenhar fios. Mesmo assim, o algoritmo captura essas deps no passo 3 do algoritmo e coloca Compare corretamente na onda 3. Sem esse scan, ele iria pra onda 1 e falharia na substituição.

2. Article tem ref: Topic mesmo estando 3 ondas depois. O algoritmo detecta e adiciona a aresta implícita, mas isso não afeta a onda em que Article roda — como já depende de Compare (que depende de WebSearch/NewsSearch, que dependem de Topic), Topic já vai estar completo quando a onda 4 começar. É belt-and-suspenders — a dep é registrada por segurança, sem custo real.

5 Trace de execução — onda por onda

Estado inicial após o passo 2.2 rodar:

◇ Estado inicial (antes da onda 1)
pending = { Topic, WebSearch, NewsSearch, Compare, Article }
completed = { }
inDegree = { Topic: 0, WebSearch: 1, NewsSearch: 1, Compare: 2, Article: 2 }

readySet = { Topic }  // único com in-degree=0
Promise.all([ dispatch(Topic) ])  // 1 activity só
→ Topic termina, output = { topic: "Machine Learning" }
outputStore.append(Topic, output)
decrementa inDegree dos sucessores de Topic:
  WebSearch: 1 → 0
  NewsSearch: 1 → 0
  Article: 2 → 1  // via ref implícita

② Onda 2 — paralelismo real

Promise.all([ dispatch(WebSearch), dispatch(NewsSearch) ])  // 2 activities em paralelo!
→ Ambas rodam ao mesmo tempo. Se cada uma leva 3s, onda 2 dura ~3s (não 6s).
outputStore.append(WebSearch, ...)  +  outputStore.append(NewsSearch, ...)
decrementa inDegree de Compare:
  Compare: 2 → 1 → 0  // duas decrementadas (uma por WebSearch, outra por NewsSearch)
completed = { Topic, WebSearch, NewsSearch }
③ Onda 3
readySet = { Compare }
Promise.all([ dispatch(Compare) ])
→ Activity resolve {{WebSearch.results}} e {{NewsSearch.results}} lendo do node_executions dos dois; roda LLM.
outputStore.append(Compare, ...)
decrementa inDegree de Article: 1 → 0
completed = { Topic, WebSearch, NewsSearch, Compare }
④ Onda 4
readySet = { Article }
Promise.all([ dispatch(Article) ])
→ Resolve {{Compare.text}} e {{Topic.topic}} do outputStore; roda LLM final.
outputStore.append(Article, ...)
completed = { Topic, WebSearch, NewsSearch, Compare, Article }
✓ Fim do loop
readySet = { }  pending = { } → sai do loop, vai pra FASE 4 (finalização)
Ganho de paralelismo: se o legacy executasse esse flow em série, o tempo total seria a soma de todos (5 nós × tempo médio). Com ondas paralelas, o tempo total é a soma das ondas — na onda 2, WebSearch e NewsSearch dividem o tempo. Em flows com muitas branches paralelas (agentes de pesquisa multi-fonte, geração de N variações, etc.), o ganho é linear com a largura do grafo.

6 Casos especiais que o algoritmo precisa tratar

Nó condition

Um conditionNode tem múltiplos handles de saída (ex: true/false, ou N branches nomeadas). Durante a construção do DAG, todas as arestas de saída viram deps normais. Mas em runtime (FASE 3.5), quando o condition avalia e escolhe UM handle, os outros são marcados como dead: os sucessores das arestas mortas têm seu inDegree decrementado como se o predecessor tivesse "completado", mas o output é vazio. Sem isso, sucessores de handles não-tomados ficariam no pending pra sempre.

Nó com efeito colateral independente

Certos nós (apiCaller, mcpNode, pushData) rodam pelo efeito, não pelo output. Se o grafo de refs nunca os inclui como dep de ninguém, uma implementação ingênua acharia que eles são "unreachable" e pularia. O algoritmo classifica esse tipo de aresta como side-effect na etapa 2 e os preserva no pending mesmo sem dependentes.

Refs em campos aninhados

Refs podem aparecer dentro de arrays, objetos JSON, expressões, etc. O escaneamento (passo 3) precisa ser recursivo em toda a estrutura do node_data. Refs em campos que não são de execução (label, cor, posição no canvas) são ignoradas — o escanner tem uma lista dos campos "executáveis" por tipo de nó.

Refs para nó que não existe no snapshot

Pode acontecer: usuário renomeou/deletou um nó mas outro nó ainda tem {{OldName.field}}. O passo 2.3 (validateDag) — logo depois do buildDag — falha o run rápido com InvalidReferenceError, apontando qual nó tem qual ref quebrada. Sem validateDag, o run iria até o nó com a ref quebrada, gastaria créditos das dependências, e só quebraria no meio.

arrayNode (fan-out real)

O arrayNode não expande no DAG estático — ele é um nó só no grafo. Quando executa (FASE 3.5), dispara um ChildWorkflow que constrói seu próprio DAG para as N iterações do array. O DAG pai vê o arrayNode como uma unidade atômica; a paralelização das iterações é interna ao child workflow. Isso mantém o DAG raiz pequeno mesmo com loops grandes.

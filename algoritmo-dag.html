DAG algorithm

How the workflow decides what runs, in what order, and what can run in parallel.

1 What the DAG is here

DAG (Directed Acyclic Graph) is the data structure the workflow builds once at the start of execution (step 2.2 of the v2 architecture). Used to drive the entire PHASE 3 execution loop.

The core idea is simple. <strong>A node can only run once everything it depends on has finished</strong>. Nodes that do not depend on each other can run <strong>in parallel</strong>. The DAG is the mathematical way of representing those dependencies. The "topological waves" algorithm is the way to execute it while maximising parallelism.

Why "acyclic": if A depends on B and B depends on A, nobody can start. The algorithm detects and removes cycles (called <em>back-edges</em>) before starting to execute.

2 The two kinds of dependency

Here is the critical point most flow-tool DAGs miss. <strong>Dependency does not come only from edges visible on the canvas</strong>. It can also come from <code>{{...}}</code> refs hidden inside the node's config text. The algorithm has to consider both.

Type A Explicit edges (canvas edges)

The "wires" the user draws linking node to node in the editor. Stored in the <code>flows_nodes_edges</code> table. Each edge has a <code>source</code>, a <code>target</code> and a <code>type</code> (control, condition, data, side-effect).

Every explicit edge is a dependency. The <code>target</code> node cannot start before <code>source</code> finishes.

Type B {{...}} refs inside the node's text

Placeholders the user types inside the node's fields (LLM prompts, HTTP request bodies, script expressions, etc.). Not every ref is a node dependency. It depends on the <em>target</em> it references.

Practical consequence: if the algorithm only looked at edges, a node with <code>{{TextGen1.output}}</code> in the prompt <em>without an explicit edge to TextGen1</em> would try to run before <code>TextGen1</code>. Result: substitution would fail and execution would break. That is why step 2.2 <strong>scans refs beyond edges</strong>.

3 The algorithm step by step

Runs inside the Temporal workflow, over the snapshot frozen at enqueue. Pure, no I/O. Only data transformation.

1
Seed with all nodes
Builds map nodes: Map<nodeId, {type, ...}> from the topology. Initialises empty adjacency: Map<nodeId, Set<nodeId>> and zeroed inDegree: Map<nodeId, number>.
2
Process explicit edges
For each <code>(source, target, type)</code> edge in the topology:
• Adds target to adjacency[source].
• Increments inDegree[target].
• Stores the type for use in conditionNode pruning.
3
Scan {{...}} refs in each node
For each node N:
• Walks every text field in the config (<code>prompt</code>, <code>promptData</code>, <code>textData</code>, <code>contentData</code>, request bodies, script expressions, etc.).
• Applies regex /\{\{([^}]+)\}\}/g to extract refs.
• For each ref, discovers the <em>target</em>. If it is another node in the flow (<code>{{X.field}}</code> where X is a valid nodeId or label), adds implicit edge <code>X → N</code> if not present. Increments <code>inDegree[N]</code>.
• If it is input/context/env, ignores. No dep created.
4
Detect and remove back-edges (cycles)
Runs DFS from the entry nodes (in-degree=0 before removal). If a DFS visits a node already on the current stack, the edge that closes the cycle is a back-edge. It is <strong>removed</strong> from the adjacency and the target's <code>inDegree</code> is decremented.
Note: back-edges are usually config errors (circular ref). At runtime, we chose to remove instead of failing. Avoids blocking flows that happen to have benign cycles.
5
Prune unreachable nodes
Runs BFS from nodes with inDegree === 0 after step 4. Nodes not visited are unreachable. Marks as skipped. Removes from pending.
6
Return immutable structures
• adjacency. Final, does not change during execution.
• inDegree. Initial. Will be decremented throughout execution (but that is <em>state</em>, does not change the DAG structure).
• edgeTypes. For condition/side-effect decisions in PHASE 3.
• pending. Initial set of nodes to execute (all except the skipped).

Simple flow: searches two sources in parallel, joins the results and writes an article.

Two important observations:

1. Compare only has refs, no explicit edges. The user typed <code>{{WebSearch.results}}</code> in the prompt without drawing wires. Even so, the algorithm captures those deps at step 3 and correctly places <code>Compare</code> in wave 3. Without that scan, it would go to wave 1 and fail substitution.

2. Article has <code>ref: Topic</code> even though it's 3 waves later. The algorithm detects and adds the implicit edge. This <strong>does not affect the wave</strong> where <code>Article</code> runs. It already depends on <code>Compare</code> (which depends on <code>WebSearch</code>/<code>NewsSearch</code>, which depend on <code>Topic</code>). <code>Topic</code> will already be complete when wave 4 starts. It is belt-and-suspenders. The dep is recorded for safety, at no real cost.

② Wave 2. Real parallelism.

→ Both run at the same time. If each takes 3s, wave 2 lasts ~3s (not 6s).
outputStore.append(WebSearch, ...)  +  outputStore.append(NewsSearch, ...)
decrement inDegree of Compare:
  Compare: 2 → 1 → 0  // two decrements (one by WebSearch, one by NewsSearch)
completed = { Topic, WebSearch, NewsSearch }
③ Wave 3
readySet = { Compare }
Promise.all([ dispatch(Compare) ])
→ Activity resolves {{WebSearch.results}} and {{NewsSearch.results}} by reading from node_executions of both; runs LLM.
outputStore.append(Compare, ...)
decrement inDegree of Article: 1 → 0
completed = { Topic, WebSearch, NewsSearch, Compare }
④ Wave 4
readySet = { Article }
Promise.all([ dispatch(Article) ])
→ Resolves {{Compare.text}} and {{Topic.topic}} from the outputStore; runs final LLM.
outputStore.append(Article, ...)
completed = { Topic, WebSearch, NewsSearch, Compare, Article }
✓ End of loop
readySet = { }  pending = { } → exits loop, goes to PHASE 4 (finalisation)
Parallelism gain: if the legacy ran this flow serially, total time would be the sum of all (5 nodes × average time). With parallel waves, total time is the sum of the <em>waves</em>. In wave 2, WebSearch and NewsSearch share the time. On flows with many parallel branches (multi-source research agents, generating N variations, etc.), the gain is linear with the graph's width.

6 Special cases the algorithm handles

Condition node

A <code>conditionNode</code> has multiple output handles (e.g. true/false, or N named branches). During DAG construction, all output edges become normal deps. At runtime (PHASE 3.5), when the condition evaluates and picks ONE handle, the others are marked <strong>dead</strong>. Successors of dead edges have their <code>inDegree</code> decremented as if the predecessor had "completed", but with an empty output. Without this, successors of untaken handles would remain in <code>pending</code> forever.

Node with independent side effect

Some nodes (<code>apiCaller</code>, <code>mcpNode</code>, <code>pushData</code>) run for the <em>effect</em>, not for the output. If the ref graph never includes them as anyone's dep, a naive implementation would treat them as "unreachable" and skip them. The algorithm classifies this kind of edge as <code>side-effect</code> in step 2. Preserves them in <code>pending</code> even without dependents.

Refs in nested fields

Refs can appear inside arrays, JSON objects, expressions, etc. The scan (step 3) must be recursive across the entire <code>node_data</code> structure. Refs in fields that are <em>not</em> for execution (label, colour, canvas position) are ignored. The scanner has a list of "executable" fields per node type.

Refs to a node not in the snapshot

Can happen. User renamed/deleted a node, but another node still has <code>{{OldName.field}}</code>. Step 2.3 (<code>validateDag</code>), right after <code>buildDag</code>, fails the execution fast with <code>InvalidReferenceError</code>. Points to which node has which broken ref. Without <code>validateDag</code>, execution would run up to the node with the broken ref, spending dependency credits, and only break in the middle.

arrayNode (real fan-out)

<code>arrayNode</code> does not expand in the static DAG. It is <strong>a single node</strong> in the graph. When it runs (PHASE 3.5), it fires a <code>ChildWorkflow</code> that builds its own DAG for the N array iterations. The parent DAG sees the arrayNode as an atomic unit. The iterations' parallelisation is internal to the child workflow. This keeps the root DAG small even with large loops.

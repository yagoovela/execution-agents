1.3 Cria linha flow_executions + congela snapshot + persiste trigger inputs imutável 4 tabelas novas
Em uma única transação:
• INSERT flow_executions nova (status=queued). Gera flowExecutionId.
• INSERT bulk em flow_execution_snapshots(execution_id, node_id, node_data) nova. Copia a config atual de cada nó no momento exato do enqueue.
• INSERT bulk em flow_execution_edge_snapshots nova. Mesma ideia para arestas.
• INSERT em flow_execution_trigger_inputs(execution_id, raw_body) nova. Payload cru: variableInputs[] (com base64/links/isExtraction/typeOCR) + atalho dataInput. Não faz upload S3 nem OCR aqui. Só persiste raw.

⚠ Hoje só existe flow_execution_status (linha leve com callback_url/output/tokens). As 4 tabelas acima fazem parte da proposta e precisam de migration.

Por que agora, no backend? Se o usuário editar o flow depois (às 12h32), o snapshot da execução de 12h30 permanece congelado. Edits não vazam para a execução em curso.
Por que separar OCR para a Fase 2? Extração de PDF/imagem pode levar dezenas de segundos. Fazer aqui bloqueia o retorno de flowExecutionId. Cliente ficaria esperando. Ao deixar para a activity resolveTriggerInputs (2.4), a API responde em milissegundos. O OCR corre dentro do workflow com retry/cancel nativos.

Carrega snapshot, constrói DAG imutável, prepara OutputStore
2.1 Activity loadFlowTopology(flowExecutionId) essencial só topologia
Lê de flow_execution_snapshots apenas: nodeIds, nodeType por id, adjacency list, edgeIds + tipo de aresta.

2.2 buildDag(snapshot) — puro, in-workflow essencial
Adjacency list · in-degree por nó · classifica arestas (control/condition/data/side-effect) · scan de refs {{...}} para criar deps implícitas · detecta e remove back-edges · calcula unreachable.
Poda nós puramente visuais (comment, label, group). Nunca entram em pending/readySet. Hoje (v1) eles atravessam o loop como no-op silencioso, gastando ciclo de dispatch.
Poda também varInputNode do set de dispatch. Já foram materializados como outputs em 2.4 (resolveTriggerInputs). No DAG figuram só como fonte de arestas, sem in-degree.
DAG resultante é imutável para o resto da execução.

2.4 Activity resolveTriggerInputs(flowExecutionId) essencial
Lê flow_execution_trigger_inputs.raw_body persistido em 1.3. Traduz em data resolvido para cada varInputNode. Por varInput no request:
• Se dataInput string veio sozinho, injeta no primeiro varInputNode do snapshot (atalho do chatbot/API pública).
• Se isExtraction === true e tem links/files: sub-activity extractTextFromFile por fonte. Faz upload S3 para os base64. Chama ExtractionService.extractTextFromLink com typeOCR ∈ { mistral_ocr | mistral_vision | google_ocr }. Cada extração é uma sub-activity separada (retryable, cancelável, isolada).
• Se isExtraction === false: só upload S3 para os base64, sem OCR. Só armazena URLs.
• Sem arquivos: data mínimo só com text.

Escreve o resultado em node_executions com executor='trigger-input' (uma linha por varInput). O outputData vira a saída desses nós para o OutputStore. O varInputNode nunca precisa ser dispatched no loop de ondas.

Publica em Redis + WebSocket. Cliente recebe flowExecutionId em modo running.
Por que dentro do workflow? Se o worker cair no meio, Temporal reexecuta o workflow do zero. Todas essas activities são idempotentes (query, não escrita). Nenhum estado in-memory sobrevive fora do workflow. Recuperação é grátis.

3.5 await Promise.all(...) — barreira da wave
Wave só termina quando todos os nós dela terminam (ou falham). Sem stragglers escondidos.
↓
3.6 Política de falha
fail-fast (default): qualquer erro cancela o workflow. Propaga cancelation às activities in-flight.
best-effort (opt-in por flag no flow): marca o nó falho. Continua com os nós que não dependem dele.
↓
3.7 Reduce in-degree dos sucessores
Para cada nó completado com sucesso, decrementa in-degree dos filhos no DAG. Se condition, marca handles dead antes. Volta a 3.1.
Contraste com o loop atual: hoje o backend faz while (scheduledId !== null) serial, com blocking-wait em handle.result() a cada nó Temporal. Perde todo o paralelismo do worker. Aqui, a wave só termina quando todos os nós dela terminam. O worker executa cada activity de forma independente.

4.9 Cleanup do snapshot da execução novo
Activity DELETE FROM flow_execution_snapshots WHERE execution_id = ? + análogo em flow_execution_edge_snapshots.

Por que deletar: o snapshot é escafolde só da execução. Depois de concluída, tudo que foi consumido pela execução está registrado em node_executions (entrada resolvida + saída). Manter o snapshot vira dado morto.
Trade-off aceito: perde-se o template pré-substituição (ex: "Resuma {{X.output}}"). A entrada pós-substituição está em node_executions.inputData, que é o que interessa para auditoria/replay.

6
FASE 6 — Erros e retry transversal
Uniformiza o que hoje é ad-hoc. Temporal RetryPolicy por tipo de nó.
6.1 RetryPolicy por tipo de nó
LLM (textGenerator): 3 tentativas, backoff exponencial 2s→8s, non-retryable em context_length_exceeded.
HTTP (apiCaller, integrações): 5 tentativas, backoff 1s→30s, non-retryable em 4xx (exceto 429).
Script (scripting, mathFunction): 1 tentativa (erros são bugs, não flakiness).
External (Elevenlabs, Ideogram, FAL): 3 tentativas com jitter.
↓
6.2 Non-retryable errors
Validação, permission denied, out-of-credits: marca o nó falho imediatamente, sem retry.
Categorias explícitas em errorCategory (mantém compatibilidade com o campo atual).
↓
6.3 Compensating activity (opcional)
Para nós com side-effect externo (push para Slack, INSERT em DB externo), há a opção de compensating activity para rollback quando o flow falhar.
Opt-in por tipo de nó. Não é default.

FASE 7 — Cross-cutting na v2 transversal
O que precisa migrar junto. Hoje mora no backend.

Concerns transversais que a refatoração afeta

MCP tracking Hoje mcpRunStatusService.markRunning() é chamado em apiV2Job.processor.ts:48 e markFinished() em 63-108/133-152 pelo processor da Bull queue. Na v2: vira activity dedicada trackMcpRun chamada no bootstrap do workflow (fase 2) e na finalização (fase 4). O processor deixa de existir junto com a queue.
RunLogCollector · SpaceRunLogs Hoje runLogCollector.createRoot() + spaceRunLogsService.scheduleUpsert() rodam inline em flux.service.ts:2371-2437. Na v2: signal assíncrono initRunLog (2.6) + activity finalizeRunLog (4.3). Instância do collector vive dentro do workflow, não é injetada de fora.
Token / custo · billing Hoje chargeContext.enterWith({ execId, nodeId }) (AsyncLocalStorage) captura o custo por nó em flux.service.ts:3316-3322. Na v2: cada activity recebe { flowExecutionId, nodeId } como input e escreve em token_transactions diretamente. Sem ALS.
Chat / sessão sessionStateService.readContents()/appendEntries() continuam iguais. Rodam via activity (dentro do workflow, fase 2.4 e 4.6). Não muda API do serviço, só de onde é chamado.
Chatbot socket Hoje chatbotSocketByRun em memória do backend (flux.service.ts:2288). Na v2: workflow emite eventos via WS gateway. Backend faz o fanout para o socket certo com base em flowExecutionId. Estado in-memory por processo desaparece.
Refresh de credencial (Google OAuth etc.) Hoje flux.service.ts:2699-2722 (pré-loop, gate pullData/pushData). Na v2: a própria activity do nó chama sub-activity refreshCredentialsForNode com cache Redis TTL 55min (3.4.4). Deixa de ser gate global.
Path /process/single-node-legacy (worker→backend). Deletar. SingleNodeLegacyService em src/temporal/single-node-legacy/ e o endpoint POST /process/single-node-legacy só existem enquanto sobrar algum tipo de nó não migrado. Pré-condição da v2: migração completa de todos os tipos para activity/child workflow no worker. Feito isso, esse módulo inteiro é removido junto com os sets MIGRATED_TEMPORAL_NODE_TYPES / LEGACY_SINGLE_RUN_NODE_TYPES.
Feature flag NODE_CANCEL_IN_FLIGHT_FLAG Deletar. Ver Fase 5. Cancel é signal nativo.

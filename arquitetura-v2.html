v2 architecture — the proposal

Proposal for the new architecture: bootstrap in Temporal, an immutable DAG, a parallel wave loop, lanes for the special nodes, cancellation by signal and retry by policy. Companion to index.html, which shows how it works today.

1.3 Insert flow_executions row + freeze snapshot + persist trigger inputs immutable 4 new tables
In a single transaction:
• INSERT flow_executions new (status=queued). Generates flowExecutionId.
• Bulk INSERT into flow_execution_snapshots(execution_id, node_id, node_data) new. Copies each node's current config at the exact moment of enqueue.
• Bulk INSERT into flow_execution_edge_snapshots new. Same idea for edges.
• INSERT into flow_execution_trigger_inputs(execution_id, raw_body) new. Raw payload: variableInputs[] (with base64/links/isExtraction/typeOCR) + dataInput shortcut. No S3 upload or OCR here. Just persist raw.

⚠ Today only flow_execution_status exists (light row with callback_url/output/tokens). The 4 tables above are part of the proposal and need a migration.

Why now, in the backend? If the user edits the flow later (at 12:32), the 12:30 execution snapshot stays frozen. Edits do not leak into the running execution.
Why defer OCR to Phase 2? PDF/image extraction can take tens of seconds. Doing it here blocks returning flowExecutionId. The client would wait. Deferring it to the resolveTriggerInputs activity (2.4) makes the API respond in milliseconds. OCR runs inside the workflow with native retry/cancel.

PHASE 2 — Workflow bootstrap inside Temporal
Loads snapshot, builds immutable DAG, prepares OutputStore
2.1 Activity loadFlowTopology(flowExecutionId) essential topology only
Reads from flow_execution_snapshots only: nodeIds, per-id nodeType, adjacency list, edgeIds + edge type.
<strong>Never</strong> loads <code>node_data</code> (heavy config: prompts, scripts, textData). It stays in the snapshot and is read on-demand by each node's activity.
Idempotent (pure query, retryable).
↓
›
2.2 buildDag(snapshot) — pure, in-workflow essential
Adjacency list · in-degree per node · classifies edges (control/condition/data/side-effect) · scan for {{...}} refs to create implicit deps · detects and removes back-edges · computes unreachable.
<strong>Prunes purely visual nodes</strong> (<code>comment</code>, <code>label</code>, <code>group</code>). They never enter <code>pending</code>/<code>readySet</code>. Today (v1) they traverse the loop as a silent no-op, burning a dispatch cycle.
<strong>Also prunes <code>varInputNode</code></strong> from the dispatch set. They were already materialised as outputs in 2.4 (<code>resolveTriggerInputs</code>). In the DAG they only appear as edge <em>sources</em>, with no in-degree.
The resulting DAG is immutable for the rest of the execution.

2.3 validateDag() — fail fast essential
Gate between "assemble the graph" (2.2) and "start spending resources" (Phase 3). Validates: remaining cycles · {{...}} refs pointing to non-existent nodes · incompatible types · essential orphan nodes.
A failure here means the flow is invalid. Nothing runs. Sustains the invariant behind the 3.2 deadlock guard.

2.4 Activity resolveTriggerInputs(flowExecutionId) essential
Reads flow_execution_trigger_inputs.raw_body persisted in 1.3. Translates it into resolved data for each varInputNode. Per varInput in the request:
• If <code>dataInput</code> string came alone, injects it into the first <code>varInputNode</code> of the snapshot (chatbot/public API shortcut).
• If <code>isExtraction === true</code> and there are <code>links</code>/<code>files</code>: one <strong><code>extractTextFromFile</code></strong> sub-activity per source. Uploads base64 to S3. Calls <code>ExtractionService.extractTextFromLink</code> with <code>typeOCR ∈ { mistral_ocr | mistral_vision | google_ocr }</code>. Each extraction is a separate sub-activity (retryable, cancellable, isolated).
• If <code>isExtraction === false</code>: only S3 upload for the base64, no OCR. Only stores URLs.
• No files: minimal <code>data</code> with only <code>text</code>.

Writes the result to node_executions with executor='trigger-input' (one row per varInput). The outputData becomes each node's output in the OutputStore. varInputNode never needs to be dispatched in the wave loop.
↓
2.5 initOutputStore append-only
A Map<nodeId, ReadonlyOutput> structure versioned by wave. Seeded with the outputs of the varInputNodes already resolved in 2.4 (reads from node_executions where executor='trigger-input').
Replaces the mutable nodeSubstitutionSchema. It is never modified, only grows via .append().
↓
2.6 initRunLog via signal signal cross
<code>runLogCollector.createRoot()</code> fired as an <strong>async signal</strong>. Does not block the first wave's dispatch.
↓
2.7 Emit "flow started"
Publishes to Redis + WebSocket. Client receives flowExecutionId in running mode.
Why inside the workflow? If the worker crashes mid-flight, Temporal re-executes the workflow from zero. All these activities are idempotent (query, not write). No in-memory state survives outside the workflow. Recovery is free.

PHASE 3 — Parallel wave loop parallel temporal
Heart of the new architecture · replaces the serial while (scheduledId !== null)
🌊 while (pending.size > 0)
3.1 Compute readySet essential
readySet = { n ∈ pending | in-degree(n) === 0 }. Atomic DAG snapshot.
↓
3.2 Guard: readySet.size === 0 && pending.size > 0?
Deadlock. Invalid DAG or a branch stuck by a dead condition. Fails the workflow with DeadlockError.
(Should not happen if validateDag passed.)
↓
3.3 Guard: pending.size === 0?
Success. All nodes resolved. Exit the loop → PHASE 4.
↓
3.4 Parallel dispatch — await Promise.all(readySet.map(dispatchNode)) parallel
Each node in readySet runs in parallel. Sub-steps below run per node, isolated from each other.
Per-node sub-steps (run in parallel across nodes)

↓
3.5 await Promise.all(...) — wave barrier
Wave only finishes when all its nodes finish (or fail). No hidden stragglers.
↓
3.6 Failure policy
fail-fast (default): any error cancels the workflow. Propagates cancellation to in-flight activities.
best-effort (opt-in via flag on the flow): marks the failed node. Continues with the nodes that do not depend on it.
↓
3.7 Reduce successors' in-degree
For each successfully completed node, decrement children's in-degree in the DAG. For conditions, mark dead handles first. Go back to 3.1.
Contrast with today's loop: the backend runs a serial while (scheduledId !== null), with a blocking-wait on handle.result() per Temporal node. It loses all of the worker's parallelism. Here, the wave only finishes when all its nodes finish. The worker runs each activity independently.

PHASE 3.5 — Composite nodes (conditionNode · arrayNode · fluxBox/libraryNode/nodesBox) child workflow
MUTATING_NODE_TYPES. They break the "1 dispatch = 1 output" semantics and become dedicated lanes inside the wave.
◆ conditionNode
Activity: evaluateCondition
Resolves predicate using the OutputStore snapshot. Returns the taken handle.
↓
Signal pruneBranch to the workflow
Marks non-taken handles as dead. Descendants of those handles are removed from pending.
↓
Immutable DAG, pruning only marks
Never modifies edges. Structure stays the same. Only the pending set shrinks.
◆ arrayNode
startChild('ArrayIterationWorkflow')
Real fan-out: N iterations in parallel (with configurable maxConcurrent).
↓
Each iteration = sub-DAG
The array body becomes a sub-DAG executed per iteration. Each one has its own local OutputStore.
↓
Fan-in: aggregate results
When all iterations finish, aggregates into a final array and calls outputStore.append() on the parent store.
◆ fluxBox · libraryNode · nodesBox
startChild('processAgent')
Explicit recursion. Same engine, child workflow with input mapping. Creates its own flow_executions + flow_execution_trigger_inputs rows from callerData (map varNodeId → { text, files, links, typeOCR }). Replaces the 3 current inline handlers (flux.service.ts:5464-5533 nodesBox · 5819+ libraryNode/fluxBox).
↓
Reuses resolveTriggerInputs (2.4) — Redis cache
The sub-flow goes through the entire Phase 2, including resolveTriggerInputs. If the file/link was already extracted in the parent execution (or in a prior execution), the extract:{sha256(fileUrl)}:{typeOCR} cache returns directly.
Gain vs v1: today each nesting level pays OCR from scratch (flux.service.ts:5464-5533 for nodesBox, 5819+ for libraryNode/fluxBox). In v2, N levels mean 1 real OCR + N-1 cache hits.
↓
Inherited cancellation
Signal cancelFlow on the parent propagates to the child automatically. No extra code.
↓
Output becomes the parent node's input
On completion, the child's output is append()-ed to the parent's OutputStore as the output of the composite node (fluxBox/libraryNode/nodesBox).

Activity with RetryPolicy. Double Redis dedup: runId 24h TTL + content hash 90s.

sessionStateService.appendEntries() + ChatLog. Only if runType === 'chatbot'.
↓
4.7 Mark flow_executions finished
Status=completed/failed/cancelled, tokens, cost, duration.
↓
4.8 Emit "flow completed"
WS + Redis. Client stops polling.
↓
4.9 Cleanup the execution snapshot new
Activity DELETE FROM flow_execution_snapshots WHERE execution_id = ? + analogous on flow_execution_edge_snapshots.

Why delete: the snapshot is scaffolding only for the execution. Once it's finished, everything the execution consumed is recorded in node_executions (resolved input + output). Keeping the snapshot becomes dead data.
Accepted trade-off: the pre-substitution template is lost (e.g. "Summarise {{X.output}}"). The post-substitution input lives in node_executions.inputData, which is what matters for audit/replay.

6
PHASE 6 — Errors and retry cross-cutting
Standardises what is ad-hoc today. Temporal RetryPolicy per node type.
6.1 RetryPolicy per node type
LLM (textGenerator): 3 attempts, exponential backoff 2s→8s, non-retryable on context_length_exceeded.
HTTP (apiCaller, integrations): 5 attempts, backoff 1s→30s, non-retryable on 4xx (except 429).
Script (scripting, mathFunction): 1 attempt (errors are bugs, not flakiness).
External (Elevenlabs, Ideogram, FAL): 3 attempts with jitter.
↓
6.2 Non-retryable errors
Validation, permission denied, out-of-credits: mark the node failed immediately, no retry.
Explicit categories in errorCategory (keeps compatibility with the current field).
↓
6.3 Compensating activity (optional)
For nodes with an external side-effect (push to Slack, INSERT into an external DB), there is an option for a compensating activity to roll back when the flow fails.
Opt-in per node type. Not the default.

1.3 Cria row flow_executions + congela snapshot + persiste trigger inputs imutável
Em uma única transação:
• INSERT flow_executions (status=queued) → gera flowExecutionId
• INSERT bulk em flow_execution_snapshots(execution_id, node_id, node_data) — copia a config atual de cada nó no momento exato do enqueue
• INSERT bulk em flow_execution_edge_snapshots — mesma ideia para arestas
• INSERT em flow_execution_trigger_inputs(execution_id, raw_body) — payload cru: variableInputs[] (com base64/links/isExtraction/typeOCR) + dataInput shortcut. Não faz upload S3 nem OCR aqui — só persiste raw.

Por que agora, no backend? Se o usuário editar o flow depois (às 12h32), o snapshot da execução de 12h30 permanece congelado — edits não vazam pro run em curso.
Por que separar OCR pra Fase 2? Extração de PDF/imagem pode levar dezenas de segundos. Fazer aqui bloqueia o retorno de flowExecutionId — cliente ficaria esperando. Deixando pra activity resolveTriggerInputs (2.4), a API responde em ms e o OCR corre dentro do workflow com retry/cancel nativos.

FASE 2 — Bootstrap do workflow dentro do Temporal
Carrega snapshot, constrói DAG imutável, prepara OutputStore
2.1 Activity loadFlowTopology(flowExecutionId) essencial só topologia
Lê de flow_execution_snapshots apenas: nodeIds, nodeType por id, adjacency list, edgeIds + tipo de aresta.
Nunca carrega node_data (config gorda: prompts, scripts, textData) — isso fica no snapshot e é lido on-demand pela activity de cada nó.
Idempotente (query pura, retryable).
↓
›
2.2 buildDag(snapshot) — puro, in-workflow essencial
Adjacency list · in-degree por nó · classifica arestas (control/condition/data/side-effect) · scan de refs {{...}} para criar deps implícitas · detecta e remove back-edges · calcula unreachable.
Poda nós puramente visuais — comment, label, group: nunca entram em pending/readySet. Hoje (v1) eles atravessam o loop como no-op silencioso, gastando ciclo de dispatch.
Poda também varInputNode do set de dispatch — eles já foram materializados como outputs em 2.4 (resolveTriggerInputs). No DAG figuram só como fonte de arestas, sem in-degree.
DAG resultante é imutável para o resto do run.

2.3 validateDag() — falha rápida essencial
Portão entre "montar o grafo" (2.2) e "começar a gastar recursos" (Fase 3). Valida: ciclos remanescentes · refs ({{...}}) apontando pra nós inexistentes · tipos incompatíveis · nós órfãos essenciais.
Falha aqui = flow inválido, não roda nada. Sustenta o invariante do deadlock guard 3.2.

2.4 Activity resolveTriggerInputs(flowExecutionId) essencial
Lê flow_execution_trigger_inputs.raw_body persistido em 1.3 e traduz em data resolvido pra cada varInputNode. Por varInput no request:
• Se dataInput string veio sozinho → injeta no primeiro varInputNode do snapshot (shortcut do chatbot/API pública).
• Se isExtraction === true e tem links/files: sub-activity extractTextFromFile por fonte — upload S3 pros base64, ExtractionService.extractTextFromLink com typeOCR ∈ { mistral_ocr | mistral_vision | google_ocr }. Cada extração é uma sub-activity separada (retryable, cancelável, isolada).
• Se isExtraction === false: só upload S3 pros base64, sem OCR — só armazena URLs.
• Sem arquivos → data mínimo só com text.

Escreve o resultado em node_executions com executor='trigger-input' (uma row por varInput). O outputData vira o "output" desses nós pro OutputStore — varInputNode nunca precisa ser dispatched no loop de ondas.
↓
2.5 initOutputStore append-only
Estrutura Map<nodeId, ReadonlyOutput> versionada por wave. Seed com os outputs dos varInputNodes já resolvidos em 2.4 (lê de node_executions onde executor='trigger-input').
Substitui o nodeSubstitutionSchema mutável — nunca é modificado, só cresce com .append().
↓
2.6 initRunLog via signal signal cross
runLogCollector.createRoot() disparado como signal assíncrono — não bloqueia o dispatch da primeira wave.
↓
2.7 Emit "flow started"
Publica em Redis + WebSocket. Cliente recebe flowExecutionId em modo running.
Por que dentro do workflow? Se o worker cair no meio, Temporal reexecuta o workflow do zero. Todas essas activities são idempotentes (query, não escrita). Nenhum estado in-memory sobrevive fora do workflow — recuperação é grátis.
3
FASE 3 — Loop de ondas paralelas paralelo temporal
Coração da nova arquitetura · substitui o while (scheduledId !== null) serial
🌊 while (pending.size > 0)
3.1 Compute readySet essencial
readySet = { n ∈ pending | in-degree(n) === 0 } — snapshot atômico do DAG
↓
3.2 Guard: readySet.size === 0 && pending.size > 0?
Deadlock — DAG inválido ou branch travado por condition dead. Falha o workflow com DeadlockError.
(Não deve acontecer com validateDag passando.)
↓
3.3 Guard: pending.size === 0?
Sucesso — todos os nós resolvidos. Sai do loop → FASE 4.
↓
3.4 Dispatch paralelo — await Promise.all(readySet.map(dispatchNode)) paralelo
Cada nó do readySet executa em paralelo. Sub-passos abaixo rodam por nó, isolados entre si.
Sub-passos por nó (executam em paralelo entre nós)
3.4.1
Fetch dirigido + substitutePlaceholders(node, outputStore.snapshot())
Activity faz 2 queries pequenas:
• SELECT node_data FROM flow_execution_snapshots WHERE execution_id = ? AND node_id = ? — só a config deste nó
• Para cada {{X.output}} referenciado, SELECT output_data FROM node_executions WHERE id = outputStore.get(X) — só os outputs referenciados
Depois roda a substituição pura, isolada. Nenhum estado global é tocado.
Isso é, nativamente, o modo prefetch atual — sem opt-in, sem whitelist.
3.4.2
chooseExecutor(node.type) — 3 rotas: (a) activity local rápida, (b) activity com timeout longo (LLM/HTTP), (c) ChildWorkflow para nós compostos (array, subflow).
3.4.3
INSERT node_executions (status=running, inputData resolvido, waveIndex).
3.4.4
Dispatch com StartToCloseTimeout e RetryPolicy do tipo do nó. Activity ou startChild() dependendo do 3.4.2.
Se o nó precisa de credencial externa (ex: pullData/pushData Google), a própria activity chama a sub-activity refreshCredentialsForNode(nodeId, provider) como pré-step — com cache Redis TTL (~55min) por {workspaceId, provider, userId} pra evitar refresh duplicado quando múltiplos nós do mesmo flow usam o mesmo provider.
3.4.5
outputStore.append(nodeId, output) — append-only. Versão do store incrementa por wave, mas nenhum output anterior é sobrescrito.
3.4.6
UPDATE node_executions (status=completed/failed, outputData ou claimRef para payloads > threshold → S3).
3.4.7
Emit status via signal → WS + RunLogCollector. Não-bloqueante.
↓
3.5 await Promise.all(...) — barreira da wave
Wave só termina quando todos os nós dela terminam (ou falham). Sem stragglers escondidos.
↓
3.6 Política de falha
fail-fast (default): qualquer erro cancela workflow, propaga cancelation às activities in-flight.
best-effort (opt-in por flag no flow): marca nó falho, continua com nós que não dependem dele.
↓
3.7 Reduce in-degree dos sucessores
Para cada nó completado com sucesso, decrementa in-degree dos filhos no DAG. Se condition, marca handles dead antes → volta a 3.1.
Contraste com o loop atual: hoje o backend faz while (scheduledId !== null) serial, com blocking-wait em handle.result() a cada nó Temporal (perde todo o paralelismo do worker). Aqui, a wave só termina quando todos os nós dela terminam, e o worker executa cada activity de forma independente.

Quebram a semântica "1 dispatch = 1 output" — tratados como lanes específicas dentro da wave
◆ conditionNode
Activity: evaluateCondition
Resolve predicado usando snapshot do OutputStore. Retorna handle tomado.
↓
Signal pruneBranch ao workflow
Marca handles não-tomados como dead. Descendentes desses handles são removidos do pending.
↓
DAG imutável, pruning só marca
Nunca altera arestas. Estrutura permanece igual — apenas o set pending encolhe.
◆ arrayNode
startChild('ArrayIterationWorkflow')
Fan-out real: N iterações em paralelo (com maxConcurrent configurável).
↓
Cada iteração = sub-DAG
Body do array vira um sub-DAG executado por iteração. Cada uma tem seu OutputStore local.
↓
Fan-in: agrega resultados
Ao terminar todas as iterações, agrega em array final e faz outputStore.append() no store pai.
◆ subflowNode (nodesBox · libraryNode · fluxBox)
startChild('FlowExecutionWorkflow')
Recursão explícita — mesma engine, workflow filho com input mapping. Cria a própria row flow_executions + flow_execution_trigger_inputs a partir de callerData (mapa varNodeId → { text, files, links, typeOCR }).

Sub-flow passa pela Fase 2 completa, incluindo o resolveTriggerInputs. Se o arquivo/link já foi extraído no run pai (ou em run anterior), o cache extract:{sha256(fileUrl)}:{typeOCR} retorna direto.
Ganho vs v1: hoje cada nível de aninhamento paga OCR do zero (flux.service.ts:5464-5533 para nodesBox, 5819+ para libraryNode/fluxBox). Em v2, N níveis = 1 OCR real + N-1 cache hits.

WS + Redis. Cliente encerra polling.
↓
4.9 Cleanup do snapshot da execução novo
Activity DELETE FROM flow_execution_snapshots WHERE execution_id = ? + análogo em flow_execution_edge_snapshots.

Por quê deletar: o snapshot é escafolde só do run. Depois de concluído, tudo que foi consumido pelo run está registrado em node_executions (input resolvido + output). Manter o snapshot vira dado morto.
Trade-off aceito: perde-se o template pré-substituição (ex: "Resuma {{X.output}}") — mas o input pós-substituição está em node_executions.inputData, que é o que interessa pra auditoria/replay.

6
FASE 6 — Erros e retry transversal
Uniformiza o que hoje é ad-hoc · Temporal RetryPolicy por tipo de nó
6.1 RetryPolicy por tipo de nó
LLM (textGenerator): 3 tentativas, backoff exponencial 2s→8s, non-retryable em context_length_exceeded.
HTTP (apiCaller, integrações): 5 tentativas, backoff 1s→30s, non-retryable em 4xx (exceto 429).
Script (scripting, mathFunction): 1 tentativa (erros são bugs, não flakiness).
External (Elevenlabs, Ideogram, FAL): 3 tentativas com jitter.
↓
6.2 Non-retryable errors
Validação, permission denied, out-of-credits → marca nó falho imediatamente, sem retry.
Categorias explícitas em errorCategory (mantém compatibilidade com o campo atual).
↓
6.3 Compensating activity (opcional)
Para nós com side-effect externo (push para Slack, INSERT em DB externo), possibilidade opcional de compensating activity para rollback quando o flow falhar.
Opt-in por tipo de nó — não é default.

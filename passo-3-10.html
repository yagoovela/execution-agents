Passo 3.10 — Notificação WebSocket

Bloco em flux.service.ts:2288 (setup do socket map) · emitNodeStatus em vários pontos (~1837, 2158) · retorno final em 5293-5307. Notifica o cliente em tempo real via NotificationsGateway (Socket.io) sobre status por nó.
Em resumo — o que esse passo faz
  • Avisa o cliente em tempo real: ao longo do run, cada mudança de status por-nó ('RUNNING' → 'COMPLETED'/'FAILED'/'CANCELLED') é emitida via WebSocket, permitindo que o editor pinte a borda do cartão do nó em amarelo/verde/vermelho conforme execução progride.
  • Agenda interna de chatbot socket: um Map<runLogProcessId, socketId> mantido no FluxService. Populado só quando o request veio com socketId (endpoints tipo /flux/chatbot-api-socket); no fim do run o finally deleta a entry pra não vazar memória.
  • emitNodeStatus é o locutor: wrapper fino sobre NotificationsGateway.sendToUser. Payload é map por nodeId — { execId, flowId, userId, nodes: { [nodeId]: { status, userMessage } } }. É efêmero — só vale enquanto o socket está conectado; refresh perde o estado (que é reidratado via HTTP + RunLogNode persistido).
  • Gateway = "carteiro" por userId: NotificationsGateway mantém Map<userId, socket[]> internamente; ao emitir, itera todas as conexões daquele user (multi-device — laptop + celular veem updates simultâneos). Sem Redis adapter Socket.io — blocker pra escala horizontal, mas aceitável hoje em single-node prod.
  • Retorno final em 5293-5307: { message[], nodeError, totalTokensUsed, totalCost }. Cada outputObjectNode vira um item de message (via arrayDataToText pra concatenar textData). O socket handling real do chatbot fica no controller — não aqui. Sem streaming intermediário no apiV2; token-by-token de LLM é responsabilidade do worker via Redis pub/sub durante commandTextNode.
  • Saída: emissões incrementais por-nó ao longo do run + objeto de resposta consolidado no return; fire-and-forget — se socket cair, mensagem se perde (cliente reconecta e busca estado via HTTP). É UX-only: run completa mesmo sem socket funcionando.
Contexto: nem toda notificação é feita nesse passo específico — o diagrama coloca 3.10 como "envia iteração + finalResult" no retorno final, mas o emitNodeStatus é chamado em vários pontos durante o run pra atualizar UI em tempo real. Cliente do editor (canvas) subscribe ao socket e vê status per-nó mudando conforme execução progride.

AchatbotSocketByRun (Map interna)
flux.service.ts:356 (declaração), 2288 (populate)
private readonly chatbotSocketByRun = new Map<string, string>() // runLogProcessId → socketId
Propósito: Map estático interno do FluxService que relaciona runLogProcessId → socketId. Popular só se veio socketId no request (endpoints de chatbot). Usado quando precisa enviar mensagem específica pro socket que iniciou o run.
Em resumo: pensa nesse Map como uma agenda que o service mantém aberta no processo do backend. Alguns endpoints (o /flux/chatbot-api-socket, por exemplo) vêm com socketId — o cliente do chatbot mandou o request e ficou esperando resposta no mesmo socket persistente. O backend precisa saber, no meio do run, "pra quem devolver esse pedaço da resposta". Salva na agenda: chatbotSocketByRun.set(runLogProcessId, socketId). Ao longo do run, emitNodeStatus e outros pontos podem consultar essa agenda (via runLogProcessId, que carregam) pra descobrir qual socket avisar. No final (passo 5.3), o finally chama this.chatbotSocketByRun.delete(runLogProcessId) — cleanup pra não vazar memória. Uma agenda por processo do Node.js — não é distribuído. Se o backend tá em N pods e o socket foi aberto no pod 1 mas o run está no pod 2, essa agenda não ajuda (o socket não é acessível cross-process). Em prod hoje com um processo por pod isso funciona porque o Bull enfileira o job no mesmo pod onde o socket ficou, ou porque não usa chatbot com múltiplos pods. Refactor futuro tem que resolver isso via Redis pub/sub ou similar.
// flux.service.ts:356 private readonly chatbotSocketByRun = new Map<string, string>(); // flux.service.ts:2287-2289 (dentro do apiV2) if (socketId) { this.chatbotSocketByRun.set(runLogProcessId, socketId); }
🎯 Só quando veio socketId
Endpoints como /flux/api-v2 não passam socketId — não populam. /flux/chatbot-api-socket sim. Isso permite que emissões por-nó cheguem só onde faz sentido (usuário de chatbot vendo streaming).
⚠️ Não é distribuído
Map local no processo. Se backend escalar horizontalmente sem sticky sessions, socket aberto no pod A e run rodando no pod B não conseguem se comunicar. Trade-off aceitável em single-node prod, blocker em multi-pod.
BemitNodeStatus (per-node)
flux.service.ts:2146-2182
private emitNodeStatus({ execId, flowId, userId, nodeId, status, userMessage }): void
Propósito: Chamado em vários pontos do run pra emitir status atual do nó via WebSocket. Wrapper fino sobre NotificationsGateway.sendToUser. Formato: { execId, flowId, userId, nodes: { [nodeId]: { status, userMessage } } }. Cliente ouvinte atualiza cartão visual do nó em tempo real.
Em resumo: é o locutor do run — anuncia status por nó pra quem estiver ouvindo do outro lado do socket. Formato do payload é map por nodeId: mesmo evento pode carregar update de múltiplos nós (mas na prática, essa função sempre emite 1 por vez). Chamado em pontos específicos: (i) quando recordLegacyNodeStart abre uma row em node_executions — status='RUNNING'; (ii) quando handler termina — status='COMPLETED' ou 'FAILED'; (iii) em cancelamento — status='CANCELLED' (via emitCancelledRunStatuses); (iv) no final do run inteiro — via retorno. Cliente do editor tem listener que faz: "recebi update pra nó X com status Y? Muda a borda visual pra amarelo/verde/vermelho". É como as UIs mostram progresso realtime. Diferente do RunLogNode (que é persistido pra histórico), essa emissão é efêmera — só vale enquanto o socket tá conectado; refresh perde tudo.
private emitNodeStatus({ execId, flowId, userId, nodeId, status, userMessage }) { this.notificationsGateway.sendToUser({ execId, flowId, userId, nodes: { [nodeId]: { status, userMessage } }, }); }
🎯 Status literais
Strings: 'RUNNING', 'COMPLETED', 'FAILED', 'CANCELLED'. Sem enum — string literal espalhada em vários pontos. Cliente confia na convenção.
📎 userMessage opcional
Quando presente, cliente pode mostrar tooltip com detalhe (ex: mensagem de erro amigável em FAILED, quantos itens em COMPLETED de arrayNode).
🔧 forwardRef pra evitar circular
Injetado com @Inject(forwardRef(() => NotificationsGateway)) em flux.service.ts:410 — porque NotificationsGateway depende do FluxService pra resolver algumas queries (evita circular dependency).
CNotificationsGateway.sendToUser
gateway/notifications.gateway.ts (Socket.io)
sendToUser(payload: { execId, flowId, userId, nodes: Record<nodeId, { status, userMessage }> }): void
Propósito: Gateway NestJS + Socket.io. Emite evento específico pro userId — mantém internamente um Map<userId, socket[]>. Quando sendToUser é chamado, itera todas as conexões daquele user e emite o payload via WebSocket.
Em resumo: é o carteiro que sabe pra qual endereço enviar cada carta. O NotificationsGateway mantém uma tabela interna de userId → sockets ativos (o cliente subscribeu quando abriu o editor). Quando o backend chama sendToUser({ userId, ... payload }), ele busca todas as conexões daquele user e socket.emit('flowUpdate', payload) em cada uma. Isso permite múltiplos dispositivos — se o usuário abriu o editor no laptop e no celular, ambos veem updates simultâneos. Aqui não tem Redis pub/sub direto pra WebSocket (o Redis do sistema é usado pra Bull queue e email dedup, mas não pra pub/sub de eventos WS). Trade-off: simples e rápido, mas se backend escalar em N pods sem sticky, um user pode estar conectado no pod 1 e o run rodar no pod 2 — o carteiro não sabe entregar. Solução clássica seria Redis Adapter do Socket.io — não tá em uso hoje.
C1 Socket.io emit por userId
Payload vai pra todas as conexões daquele userId. Cliente subscribeu quando abriu o editor — recebe cada update por-nó em tempo real. Payload leve (~200 bytes por nó).

Propósito: É o "3.10 do diagrama" no sentido de retornar o resultado consolidado pro chamador. Não é WebSocket direto — o caller (endpoint HTTP) recebe esse objeto e devolve pro cliente. Se o request veio de chatbot com socket, o retorno é emitido no socket pelo endpoint controller (não aqui).
Em resumo: a linha 5293 é o último ato do apiV2 — build do objeto de resposta. Contém: message[] (mapeando cada outputObjectNode em { timestamp, text, outputId }), nodeError (string amigável construída em 4.5, ou null se sucesso), totalTokensUsed e totalCost. Esse retorno é o que o endpoint controller recebe (após todo o run terminar) e devolve pro cliente HTTP como JSON — ou, no caso de chatbot com socket, emite pelo socket antes de fechar. O comentário na linha 5292 diz "This is the response to the user by websocket" — sugere que a intenção era enviar via socket, mas o código apenas return. O socket handling real fica no controller ou no consumer (Bull processor). Sem cronograma de streaming aqui — o message vai tudo de uma vez no final. Streaming intermediário (por token de LLM) é responsabilidade do handler do worker (via Redis pub/sub durante execução do commandTextNode), fora do escopo desse return.

Passo 4.1 — Detecção de nós não-processados

Bloco em flux.service.ts:4735-4778. Após loop principal terminar, compara schedState.nodeIds com completed ∪ dead. Se sobrar algum id, loga error (Winston) com error_type='flow_truncated' — mas só se run não foi cancelado nem parou por node failure/loop.
Contexto: não é bloqueante — apenas observabilidade. Detecta bugs de scheduler ou branches órfãs. Se todos os nós reachable já eram esperados em cadeias que não seriam completadas por design (ex: loop stoppedByLoopBehavior), o check é skipado — não é warning nesses casos.

AunprocessedNodeIds calc
flux.service.ts:4735-4737
const unprocessedNodeIds = [...schedState.nodeIds].filter(nid => !schedState.completed.has(nid) && !schedState.dead.has(nid));
Propósito: Diferença set-teórica: nós reachable menos os que já foram processados (completed) menos os que foram podados (dead). O que sobra é "não-processado" — nunca foi executado por algum motivo.
Em resumo: é o check post-mortem. Depois que o loop terminou (por natural exhaustion ou por break), pergunta: "quem foi convidado pra festa mas nunca chegou nem foi expulso?". Compara schedState.nodeIds (todos os reachable) contra completed (chegaram e saíram) e dead (foram cancelados/podados por branch). O restante é o ghost — nodes que deveriam ter rodado mas ficaram presos, geralmente porque tinham dependência em algum nó que nunca completou (ou por bug no scheduler que esqueceu de destravá-los, ou por design como stoppedByNodeFailure/stoppedByCancel/stoppedByLoopBehavior). Não afeta retorno nem UI — só vai pro Winston pra debug. Em runs normais, sempre vazio (todos os nós reachable rodam ou morrem). Em runs abortados por qualquer razão, tem lista de nós que não chegaram na vez deles — natural, não é bug.

nodeIds - (completed + dead). O processedNodeIds (do fn B de 3.2) tem outra lista — mas essa é usada pro log final, não pra unprocessed.
📎 Spread do Set
[...schedState.nodeIds] converte Set em array pra usar .filter. Custo O(n) em nós reachable.
BCancel footprint (path especial)
flux.service.ts:4738-4758
if (stoppedByCancel) { const footprint = resolveCancelledRunFootprint(...); await runCancellationService.markCancelled(...); emitCancelledRunStatuses(...); }
Propósito: Se run foi cancelado, precisa fazer bookkeeping extra: marca no service de cancellation qual foi o último nó a rodar, quais ficaram pendentes, e emite status='CANCELLED' via WebSocket pra cada nó pendente. Cliente vê UI cinza em cada nó não-executado.
Em resumo: quando cancel acontece, o unprocessedNodeIds fica grande (tudo depois do ponto de cancel), mas em vez de logar isso como "flow truncado" (que seria alarme falso), o backend faz cleanup específico de cancel: (1) resolveCancelledRunFootprint calcula qual nó parou o run (stoppedAtNodeId) e o resto que ficou pendente (notExecutedNodeIds); (2) runCancellationService.markCancelled persiste esses detalhes no banco (marca a row de flow_run_states como cancelado com metadata); (3) emitCancelledRunStatuses dispara WebSocket pra cada id pendente com status='CANCELLED'. UI recebe múltiplos updates e pinta cada nó pendente de cinza. Esse footprint é útil pra dashboard "onde exatamente o cancel aconteceu?".
if (stoppedByCancel) { const footprint = resolveCancelledRunFootprint({ nodeIds: schedState.nodeIds, completed: schedState.completed, dead: schedState.dead, lastExecutedNodeId, nodes: myUpdatedNodes, }); await this.runCancellationService.markCancelled({ runId: runLogProcessId, stoppedAtNodeId: footprint.stoppedAtNodeId, notExecutedNodeIds: footprint.notExecutedNodeIds, }); this.emitCancelledRunStatuses({ /* runId, flowId, userId, nodeIds */ }); }
🎯 Cancel é first-class
Não é só "erro suprimido" — tem service dedicado (runCancellationService), tabela dedicada (flow_run_states), notificação dedicada. Path bem separado.
🔧 lastExecutedNodeId
Populado ao longo do loop em 3.2 (a cada iteração). Aqui é usado pra saber onde exatamente o cancel pegou — informação valiosa pra debug e telemetria.
CGate: quando logar warning
flux.service.ts:4759-4763
if (unprocessedNodeIds.length > 0 && !stoppedByLoopBehavior && !stoppedByNodeFailure && !stoppedByCancel) { loggerService.error(...) }
Propósito: Warning só se: (i) tem nós não-processados; (ii) run não parou por loop behavior (loop natural exhaustion não é bug); (iii) run não falhou (fail-fast deixa nós pendentes por design); (iv) run não foi cancelado (também deixa nós pendentes). Só warn se for cenário inesperado.
Em resumo: é a peneira dos motivos legítimos. Tem 3 razões válidas pra ter nós não-processados sem ser bug: (1) o loop tinha um arrayNode que terminou naturalmente e deixou o resto do subgrafo desconectado (stoppedByLoopBehavior=true); (2) algum nó falhou fatal (stoppedByNodeFailure=true) — fail-fast semantics; (3) usuário cancelou (stoppedByCancel=true). Nesses 3 casos, é esperado ter unprocessed — não loga. Só loga se nenhum desses aconteceu, mas ainda assim sobrou nó não-executado — isso é bug no scheduler ou grafo mal montado. Rara em produção normal — quando aparece nos logs, alguém precisa investigar. Uma vez detectado, o log traz unprocessedNodeIds.slice(0, 20) (limita pra não estourar log com agentes gigantes) e flow_truncated como error_type.
🪜 4 condições combinadas (AND)
1unprocessedNodeIds.length > 0tem nó órfão
2!stoppedByLoopBehaviornão foi loop natural
3!stoppedByNodeFailurenão foi fail-fast
4!stoppedByCancelnão foi cancel
5todas as 4 verdadeLOG error (flow_truncated)
⚠️ Rare log = high signal
Quando aparece nos logs, é sinal forte de bug. Não é ruído — cada instância vale ser investigada.

Setado no handler de conditionNode em 3.11 quando idxCondition < -1. Loop iterativo terminou naturalmente.
DloggerService.error (Winston)
flux.service.ts:4765-4777
this.loggerService.error({ message: 'Flow run ended before processing all connected nodes...', metadata: { status: 500, error_type: 'flow_truncated', ... } });
Propósito: Log estruturado Winston com error_type='flow_truncated'. Payload: mensagem com contagem (processed/total), ids não-processados (max 20), flowId, sessionId, user. Vai pra stdout (captured pelo container/log aggregator em prod).
Em resumo: Winston, o logger padrão de NestJS na base. Nível 'error' — mais alto que warn ou info, disparado por telemetria. O error_type: 'flow_truncated' é chave-clave pra dashboards de alertas (SRE monitora essa string). A mensagem inclui contagem (processedNodeIds.size/allNodesIds.length) — dá contexto rápido: "processou 8 de 12 nós". Slicing em 20 (unprocessedNodeIds.slice(0, 20)) é defensivo — se algum agente tem 500 nós órfãos, log ficaria enorme. Estrutura padrão do project (metadata JSON, sem PII de conteúdo).
this.loggerService.error({ message: `Flow run ended before processing all connected nodes (${processedNodeIds.size}/${allNodesIds.length})`, metadata: { status: 500, error_type: 'flow_truncated', user: user as User, other: { flowId, sessionId: sessionId || 'default', unprocessedNodeIds: unprocessedNodeIds.slice(0, 20), }, }, });
🎯 Sem side effects
Só log. Não modifica estado, não retorna, não altera Fase 4.2+ downstream. Puro observability.
Resumo — o que sai de 4.1:
• Em run normal (sem stop flags): nenhum log, unprocessedNodeIds deveria estar vazio
• Em cancel: runCancellationService.markCancelled + emitStatuses (WebSocket)
• Em bug: log Winston com flow_truncated + ids afetados
• Pura observabilidade — não altera retorno do run
Observações para migração:
• É diagnóstico — se scheduler no worker for confiável, esse check pode virar assertion (throw em dev, log em prod).
• Cancel footprint precisa continuar existindo pra UX de cancel — dashboard mostra "cancelou no nó X" pro usuário.
• Pode ficar por último no plano de migração — não bloqueia nada.

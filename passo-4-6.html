Passo 4.6 — persistInputNodeData para outputObjectNode

Bloco em flux.service.ts:4893-4905. Filtra currentFlux por type === 'outputObjectNode' e persiste text/textData de cada em flows_nodes.data via persistInputNodeData. Promise.all paralelo.
Em resumo — o que esse passo faz
  • Salva o resultado dos outputs no "desenho" do agente: pega todos os nós do tipo outputObjectNode desse run e grava o text/textData deles direto em flows_nodes.data. É a etapa de arquivamento visual, feita em paralelo com Promise.all.
  • Por que gravar no flows_nodes.data? quando o usuário reabre o editor, o canvas já carrega os nós dessa tabela — então o card do output aparece com "seu último resultado" sem precisar de query extra em node_executions.
  • Dispatch por versionamento: o helper privado persistInputNodeData escolhe entre updateSingleNodeDataInHistory() (quando o run rodou numa versão congelada) ou updateSingleNodeData() (working copy live). Merge parcial — só text e textData são tocados, resto do JSONB fica intacto.
  • Custo em perf: essa persistência é exatamente o ofensor de flows_nodes.data gordo — a cada run, o JSONB desses nós cresce, e o FE sente ao abrir agentes grandes.
  • Saída: N UPDATEs paralelos (N = número de outputObjectNodes), sem retorno — puro side effect pra UX de reabertura do editor.
Contexto: os outputObjectNodes são os "outputs" finais do agente — o que o cliente vê como resultado. Aqui esses outputs são persistidos em flows_nodes.data mesmo depois do run terminar. Assim, se o usuário abrir o editor depois, vê a última resposta gerada por cada output — persistência visual.

Assim, ao reabrir, o cartão do output já mostra "seu último resultado" sem query extra. Filtragem por type === 'outputObjectNode' — só esse tipo tem essa persistência. Promise.all paralelo — se agente tem 3 outputs, 3 UPDATEs simultâneos. Isso muda o modelo [[project_jsonb_fat_fields]] — flows_nodes.data continua ganhando campos gordos (text, textData), o que segue sendo ofensor de perf de FE em agentes grandes. Provavelmente vai ser refactor: os outputs também deveriam ir pra node_executions como o path Temporal já faz.

Propósito: Dispatch entre 2 services baseado em flowVersionHistoryId presente ou não. Se tem history id → flowNodeService.updateSingleNodeDataInHistory() (versão histórica); senão → flowNodeService.updateSingleNodeData() (live flow).
Em resumo: método privado que decide onde escrever. Flux tem versionamento — cada run pode estar rodando uma versão específica do flow (histórica) ou a versão atual (live). Se flowVersionHistoryId foi passado no request, o run está numa versão fixa: escreve em flow_version_history row. Senão, escreve na live table flows_nodes. Cascata simples: switch por presença do ID. As chamadas viram UPDATE em uma das duas tabelas com o mesmo shape de payload (id + data merge). O data passado inclui só { text, textData } — não sobrescreve o restante do flows_nodes.data. 🎯 2 lugares potenciais
Sistema tem versionamento manual (deploy de versões). Run pode rodar contra deploy fixo ou live. Persistir no lugar certo mantém a consistência UX.
⚠️ Contribui pro JSONB gordo
Cada run, flows_nodes.data desses outputs recebe novo text/textData. Row cresce por run. Em agentes populares, JSONB fica pesado — piorando perf de open-flow (memória [[project_jsonb_fat_fields]]).
Resumo — o que sai de 4.6:
• N UPDATEs paralelos em flows_nodes.data ou flow_version_history (N = número de outputObjectNodes)
• Outputs finais persistidos no canvas — usuário vê ao reabrir editor
• Sem impact no retorno — só side effect
Observações para migração:
• Contribui pra JSONB gordo — ofensor de perf conhecido. Refactor deveria migrar pra node_executions.
• Versionamento adiciona complexidade — 2 tabelas fazem essencialmente a mesma coisa. Unificar num modelo (com discriminator column) simplificaria.
• Promise.all é bom pattern, mas se um UPDATE falha, os outros continuam mas o Promise.all rejeita — behavior pode ser inesperado. Considerar Promise.allSettled.

Flow Version. How it works today.

Context for Step 1.3 of the v2 architecture (creates flow_executions row + freezes snapshot). Documents the current flow versioning model (flow_versions, flow_versions_histories, flow.deployedVersionId, currentHistoryId). v2 replaces it with a table dedicated to per-execution snapshots.
Em resumo. O versionamento de hoje em 5 pontos.
  • Versões são criadas em 3 momentos específicos: (1) ao habilitar version control (cria V 1.0 deployada + Staging draft); (2) ao criar branch manual (endpoint /versions/create); (3) ao publicar (endpoint /versions/push-to-production, com bump automático de major ou minor). Autosave nunca cria versão nova.
  • Cada versão tem um ponteiro mutável currentHistoryId que aponta para a linha de flow_versions_histories "ativa". Nodes e edges são pendurados nessa history via FK flow_version_history_id. Trocar o ponteiro significa trocar o snapshot que a versão "é".
  • Salvar edições na Staging não cria uma nova history. A rotina saveToVersion() upserta in-place as linhas de flows_nodes/flows_nodes_edges que já estão penduradas no currentHistoryId da versão. O snapshot que chamamos de "imutável" é reescrito por baixo.
  • Executar lê o snapshot via resolveExecutionHistoryId(). Resolve flow.deployedVersionId → version.currentHistoryId com SELECT fresco do Postgres em cada chamada. Sem lock, sem cache.
  • Consequência crítica: um push-to-production no meio de uma execução faz UPDATE flows_versions SET current_history_id = novo. Se a execução consultar resolveExecutionHistoryId novamente depois disso (multi-fase, retry, node paralelo), a segunda metade passa a ler um snapshot diferente. Não há garantia de reprodutibilidade. É esse buraco que o Passo 1.3 da v2 fecha, criando flow_execution_snapshots por execução.
Por que este documento existe: ao ler o Passo 1.3 da v2 ("INSERT bulk em flow_execution_snapshots. Congela config no momento exato do enqueue"), é fácil pensar: "mas já existe flow_versions, não dá para reaproveitar?". A resposta é não. As tabelas atuais parecem versionamento, mas suas linhas são mutáveis por design. Este HTML é a evidência de código para justificar por que uma tabela nova é necessária. ⚠️ Padrão importante: o dado real do agente (nodes/edges) não fica dentro das linhas de flows_versions_histories. 💡 Por que duas versões iniciais?
O modelo mental é "produção + próxima release". V 1.0 é read-only (execução usa ela como default). Staging é a editável (o canvas grava aqui). Publicar copia Staging → deployedVersion.

É o mesmo padrão de trunk vs release-branch em VCS tradicional, só que sem histórico linear. Só dois ponteiros mutáveis.
🎯 Momento único de igualdade
Este é o único instante da vida do flow em que "V 1.0" e "Staging" apontam para conjuntos iguais de nodes/edges (linhas duplicadas, IDs diferentes).

Depois do primeiro save na Staging, as duas divergem para sempre até o próximo pushToProduction.

B flowService.saveToVersion() upsert mutável
src/app-api/folw/flow.service.ts:476-535

Propósito: persistir edições do canvas quando o flow está em modo versionado. Em resumo: a função que quebra a expectativa de imutabilidade. Apesar de chamarmos as histories de "snapshots", esta rotina não cria snapshot novo em save. Se você aponta uma execução para essa versão enquanto o usuário está editando, a execução vai colher linhas em estado inconsistente entre o momento em que consultou nodes e o momento em que consultou edges (não há transação de leitura).

Propósito: publica uma versão-fonte (tipicamente Staging) na versão deployada. Não cria uma versão-produção nova. Reusa a mesma linha de flows_versions com isDeployed=true. Em resumo: imagine que o flow tem duas prateleiras. A de "produção" (V 1.0) e a de "rascunho" (Staging). Nenhuma execução vai ler "V 1.0" depois desse publish, porque resolveExecutionHistoryId sempre pega o currentHistoryId atual da versão deployada.

⚠️ Ponto exato onde a "imutabilidade" quebra
A etapa 5 não cria uma versão-produção nova. Ela troca o ponteiro da mesma linha. Isso é intencional (design de "só uma versão deployada por vez"). Significa que qualquer execução em curso que resolva flow.deployedVersionId → currentHistoryId antes vs. depois da etapa 5 vê snapshots diferentes. Ver card E.
💡 Nome semver mas não semver de verdade
A distinção major/minor é heurística, não semântica. O critério é "a source é a mesma da última vez?", não "houve breaking change?". Publicar duas vezes seguidas de Staging: ambos minor. Publicar de um branch draft manual novo depois de Staging: major. Isso não corresponde a semver clássico. É só uma convenção para separar "release iterativa" de "release de linha nova".
🎯 History acumulada é audit trail, não é usável
Depois de N publishes, a versão deployada tem N linhas em flows_versions_histories. Só a última (a que o currentHistoryId aponta) é acessível pela execução. As histories antigas ficam ali como trilha morta. Dá para listar via findByVersionId(versionId) (flow-version-history.service.ts:36-49). Não há endpoint que faça rollback. Para usar uma history antiga, teria que criar uma versão-branch nova apontando para ela manualmente.

⚠️ node_executions grava historyId no momento do INSERT
Quando um node executa, o backend faz INSERT em node_executions com o flowVersionHistoryId resolvido naquele instante. E Race — publish no meio de uma execução análise
análise cruzada: flow-version.controller.ts:208 vs. flow.service.ts:82-100
Cenário: execução do flow F começa em T0; usuário publica em T2; execução continua em T3.
Propósito: demonstrar em código o motivo pelo qual o Passo 1.3 da v2 precisa criar uma tabela nova de snapshots (flow_execution_snapshots) em vez de reutilizar flow_versions_histories. Não é uma função. É a interação entre C (publish) e D (resolve) quando cruzam no tempo.
Em resumo: a versão "deployada" parece imutável se você olhar apenas a linha (o ID nunca muda). O conteúdo dela vive num ponteiro (currentHistoryId) que pode ser reescrito a qualquer segundo por um publish. Como a execução não faz early-binding, ela consulta o ponteiro de novo a cada nó ou fase. Dá para terminar uma execução onde a metade inicial rodou com o snapshot X e a metade final rodou com o snapshot Y. Isso não é edge case teórico. É o comportamento default do sistema. A única razão pela qual isso raramente causa bugs visíveis é que publishes não são frequentes o suficiente para cruzar com execuções frequentes. E a maioria das execuções é curta. Não há garantia arquitetural. É sorte estatística.
⏱️ Linha do tempo do race
T0
Execução do flow F começa. Estado: flow.deployedVersionId = V1 · V1.currentHistoryId = S1 · nodes/edges vinculados a S1.
Chama resolveExecutionHistoryId(flow). Resolve S1. Carrega topologia inicial de S1.
T1
Node 1 executa. createNodeExecution() faz INSERT em node_executions com flowVersionHistoryId = S1. Saída persiste normalmente.
T2
Outro usuário publica Staging. Endpoint /versions/push-to-production executa. Etapa 4 cria S2. Etapa 5 faz UPDATE flows_versions SET current_history_id = S2 WHERE id = V1.
Nenhum lock impede isso. A execução em curso não tem transação aberta na linha de flow_versions.
T3
Node 2 executa. Chama resolveExecutionHistoryId(flow) de novo (por exemplo, dentro de executeSingleNode em flux.service.ts:790-791). Query fresca lê V1.currentHistoryId = S2. Retorna S2.
createNodeExecution() faz INSERT em node_executions com flowVersionHistoryId = S2.
T4+
Se Node 2 precisa ler dependências que foram consultadas com historyId = S2, mas S2 tem nodes/edges diferentes de S1, as entradas podem sair inconsistentes. Ex: um node de branch removido em S2 pode ainda ter saída em node_executions como se tivesse rodado. Não é acessível como dependência a partir da nova topologia.
↓
Por que não há proteção em código hoje
1. resolveExecutionHistoryId não recebe uma "execução ativa" como contexto. Só o flow.
2. flowVersionService.findById() é uma query pura, sem lock (findOne({ relations: ['flow'] })).
3. O publish (pushToProduction) não checa se há execuções pendentes daquele flow antes de sobrescrever.
4. O snapshot cache (flow.snapshot JSONB) é ortogonal. Invalidado por save, mas não por publish. Nem é usado pela execução completa.
análise: 4 pontos combinam para tornar o race inevitável no modelo atual
↓
O que a v2 propõe (Passo 1.3)
INSERT bulk em uma tabela nova flow_execution_snapshots(execution_id, node_id, node_data). Cópia da config atual de cada nó no momento exato do enqueue. Referenciada por flowExecutionId, não por flowVersionHistoryId. A partir daí, todo consumo dentro do workflow lê desse snapshot, que nunca é alterado por nenhum publish subsequente.

Ganho: imutabilidade real por execução, sem depender de tabelas de versionamento.

⚠️ Observável em produção
Rodando uma query em node_executions agrupando por execId e contando DISTINCT flowVersionHistoryId:

SELECT execId, COUNT(DISTINCT flowVersionHistoryId) c FROM node_executions GROUP BY execId HAVING c > 1

Se aparecer c > 1 em alguma linha, aquela execução pegou o race. Não é hipotético. O dado grava o evento.
💡 Por que raramente estoura
1. Publishes são operações raras (não é autosave).
2. Execuções típicas são de segundos, minutos no máximo.
3. A maioria dos flows tem workflow serial curto. O intervalo entre resolveExecutionHistoryId consecutivos é pequeno.

Flows longos (loop, webhook wait, aprovação humana) sim ficam expostos. O comportamento não é errado. A execução termina. Só é não reprodutível.
🔧 Alternativas que não resolveriam
Cache do historyId no início da execução? Ajuda parcialmente. O backend também é acessado por adapters legados que não passam pelo Temporal. Cada um teria que implementar o cache.

Lock em flow_versions durante a execução? Bloqueia publishes por segundos/minutos. Inaceitável em produção.

Tabela nova por execução (v2) é a única saída sem trade-off operacional grave.
🎯 O que grava historyId "estável"
node_executions.flowVersionHistoryId é write-once. Uma vez inserido, não é atualizado (só output, isError, etc. são updated). O audit trail depois do fato é confiável. O problema é a execução em progresso, não a análise post-mortem.
Resumo. O que este documento estabelece.
• Versões são criadas em 3 momentos (enable, create branch, publish). Nunca em save/autosave.
• flows_versions.currentHistoryId é um ponteiro mutável. Publish o reescreve. Save reescreve as linhas filhas apontadas por ele.
• Execução resolve o snapshot via SELECT fresco em cada chamada. Sem cache, sem lock, sem early-binding.
• Como a resolução é repetida N vezes por execução e o ponteiro é global por versão, não existe garantia de leitura consistente por execução.
• A tabela node_executions grava o historyId no INSERT. Dá para detectar execuções afetadas. Não dá para prevenir a inconsistência.
Implicação direta para o Passo 1.3 da arquitetura v2:
• Reaproveitar flows_versions_histories como "snapshot de execução" não funciona. As linhas são compartilhadas entre execuções e mutáveis por publish.
• A tabela nova (flow_execution_snapshots) é obrigatória. Precisa ser (a) escrita no enqueue, dentro da mesma transação que cria a linha de flow_executions; (b) referenciada por flowExecutionId, não por versionId; (c) read-only depois de escrita. Sem UPDATE em nenhum caminho.
• Retirar currentHistoryId como fonte de verdade durante a execução é a mudança conceitual central. A execução passa a ser identificada pelo próprio ID, não pela versão.
• flow_versions e flow_versions_histories continuam existindo para o ciclo de edição e publicação. Deixam de ser lidos por execução ativa. Isso simplifica os 8 pontos de consumo em flux.service.ts. A maioria vira leitura de flow_execution_snapshots pelo ID.

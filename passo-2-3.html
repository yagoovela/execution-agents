Passo 2.3 — generateSchemaFromNodes (schema de substituição)

Bloco em node-reference-substitution.service.ts:82-143. Constrói o mapa de substituição in-memory que resolve placeholders {{...}} em tempo de execução. Cada nó vira até 3 chaves no mapa: UUID puro, UUID normalizado (pontos → underscores), e label lowercase — todas apontando pra mesma entry (compartilhada por referência).
Contexto: este é o motor de referência — o que faz um node poder escrever {{model_1}} ou {{Persona Model}} no prompt e receber o output do node upstream substituído. A basedOnType (whitelist estática)
node-reference-substitution.service.ts:25-80
private readonly basedOnType: Record<nodeType, string[]>
Propósito: Definir quais campos de node.data valem a pena publicar no schema, por tipo de nó. Nó não listado é ignorado; campo não listado (mesmo existindo em data) não vira substituível.
Em resumo: pense nesta whitelist como o cadastrador do sistema de referência — é uma lista escrita à mão dizendo "para cada tipo de nó, esses aqui são os campos que podem ser citados via {{placeholder}}". Um commandTextNode, por exemplo, expõe prompt, persona, content, text; um sqlQuerier expõe host, query e etc. Se o tipo do nó nem aparece no cadastro, ele é ignorado sem log; se o campo não está listado, ele existe em memória mas ninguém consegue referenciar. É por isso que criar um novo tipo de nó e esquecer de atualizar esta lista gera bug silencioso: o placeholder simplesmente não resolve, sem barulho nenhum.

Propósito: Iterar sobre todos os nodes, ignorar os não-mapeados, e pra cada mapeado montar uma entry extraindo os campos da whitelist. Retorna o schema final.

C Extração de value (flatten de object)
node-reference-substitution.service.ts:105-127
for (const field of relevantFields) { let value = node.data[field]; if (object) value = value.text ?? value.content ?? value.result ?? JSON.stringify(value); entry[field] = value; }
Propósito: Normalizar o valor pra sempre ser string. Se node.data[field] é objeto (comum em outputs), tenta extrair text/content/result; se nada bate, cai em JSON.stringify. Se é undefined, não cria a chave.
Em resumo: imagine essa parte como o tradutor que garante que tudo que vai pro schema saia como texto — porque, no final, o {{placeholder}} vai ser jogado dentro de um prompt de LLM, e prompt é string. Se o campo já é primitivo (string/número/boolean), passa direto; se é objeto, ela tenta pescar em ordem: primeiro text, depois content, depois result; se nenhum bate, serializa o objeto inteiro como JSON. Se o campo está undefined, nem cria a entrada. Detalhe importante: essa ordem text > content > result é silenciosa e frágil — se um handler grava os dois, quem ganha é text, e mudar essa precedência num refactor pode quebrar coisas sem aviso. Também é aqui que a memória infla: um único result de 2MB fica inteiro no schema e é replicado em cada substituição.
🪜 Cascata de coerção
1 node.data[field] === undefined skip (não adiciona)
2 value é primitivo grava direto
3a objeto com value.text entry[field] = value.text
3b senão, com value.content entry[field] = value.content
3c senão, com value.result entry[field] = value.result
3d fallback JSON.stringify(value)
↓
Resultado: entry[field]: string | number | boolean
Nunca objeto — sempre coerced. Isso permite String.replace funcionar direto no applySubstitutionToObject.
⚠️ Precedência text > content > result
Se o objeto tem ambos text e content setados (raro mas acontece), text ganha. Se um handler grava {text: 'x', content: {...json_grande...}}, o placeholder {{node}} resolve pra 'x', não pra JSON.

Se essa precedência mudar em refactor, quebra silenciosamente handlers que dependem dela.
🎯 JSON.stringify fallback
Quando o objeto não tem nenhum dos 3 campos padrão, vira JSON serializado. Ex.: modelSettings em commandTextNode. O prompt final vai ter uma string JSON literal — não é bonito mas funciona pra LLM ler.
🔧 Grande contribuidor de RAM
content/result podem ser payloads gigantes (respostas de LLM, resultados SQL). Se um único node tem result de 2MB, o schema carrega esses 2MB e todo {{node}} substituído replica isso na string final. Ver [[project_jsonb_fat_fields]] pro pattern relacionado.
D 3-key indexing (stable/ref/label)
node-reference-substitution.service.ts:129-140
schema[stableKey] = entry; schema[refKey] = entry; schema[labelKey] = entry; // 3 keys, MESMA referência
Propósito: Aceitar 3 formatos diferentes de placeholder pro mesmo nó: UUID puro, UUID normalizado, e label humano. Todos apontam pra mesma referência — atualização em uma vaza pras outras.
Em resumo: pense nesta etapa como o cartório que registra o mesmo nó sob três nomes diferentes, mas todos apontando pro mesmo endereço. O nó vai pro arquivo: (1) sob o UUID puro (a1b2-...), (2) sob o UUID com pontos trocados por underscore (porque ponto em placeholder é usado como field access {{x.y}}), e (3) sob o label humano lowercase sem espaço (personamodel). O truque legal é que os três slots guardam a mesma referência pro objeto entry — então quando o output é atualizado depois, uma única mutação já reflete nas três chaves de graça. Isso é o que permite o usuário escrever {{Persona Model}}, {{a1b2_c3d4_...}} ou usar o UUID cru no template e todos resolverem pro mesmo valor. Perigo: se dois nós tiverem o mesmo label, o segundo sobrescreve o primeiro no slot do label, e {{persona}} vira ambíguo silenciosamente.
schema[stableKey] = entry; // UUID puro: schema['a1b2-...'] const refKey = stableKey.replace(/\./g, '_'); if (refKey !== stableKey) { schema[refKey] = entry; // UUID normalizado: schema['a1b2___'] } if (labelKey && labelKey !== stableKey && labelKey !== refKey) { schema[labelKey] = entry; // label lowercase: schema['personamodel'] }
↓
D1 stableKey = node.id
UUID puro do node. Sempre presente (skip acima se ausente).
↓
D2 refKey = id.replace(/\./g, '_')
Normaliza pontos (não permitidos em placeholder path {{x.y}} — colidiria com field access). Só entra no schema se difere do stableKey.
↓
D3 labelKey (opcional)
Só se o label do node existe e não colide com as outras 2 chaves. Permite user escrever {{Persona Model}} no prompt e o replacer buscar schema.personamodel depois de normalizar.
⚠️ Colisão de labels
2 nós com o mesmo label → o último ganha no schema. {{persona}} vira ambíguo. Front deveria proibir labels duplicados; se não, silenciosamente ignora um.
🎯 Compartilhamento de referência
As 3 chaves apontam pro MESMO objeto entry. Isso é intencional: updateSchemaWithNodeOutput só precisa mutar via uma chave e as outras 2 refletem automaticamente. Elegante.
🔧 Placeholder syntax suportada
{{<key>.<field>}} ou {{<key>}} (só a chave, resolve pro fallback do primeiro campo). O replacePlaceholders (linhas 5-22) faz split por . e caminha o objeto.
E Ciclo de vida do schema no run
flux.service.ts:3149, 3281, 3389+ · node-reference-substitution.service.ts:145-216
// 1x generate (aqui) → N× applySubstitutionToObject + updateSchemaWithNodeOutput (loop) → onMutateSchema (callback pra reatribuição)
Propósito: Mostrar como o schema criado aqui é consumido e mutado ao longo do run. Não é regenerado — é vivido. Cada nó completado enriquece o schema com seu output.
Em resumo: se as etapas anteriores construíram a agenda de referências, esta aqui é o carteiro que fica indo e vindo com essa agenda durante toda a execução. O ciclo por nó vira: (1) antes do handler rodar, chama applySubstitutionToObject que troca todos os {{...}} pelos valores do schema; (2) o handler executa em cima do nó já preenchido e produz um output; (3) esse output é gravado de volta no schema via updateSchemaWithNodeOutput pra ficar disponível pros nós seguintes; (4) como o schema é reatribuído (novo objeto raiz via spread), o callback onMutateSchema avisa "atenção, use esta nova referência agora". A memória [[project_substitution_engine]] alerta que existem 57 lugares no FluxService tocando esse ciclo — por isso qualquer refactor do engine precisa mexer em todos ao mesmo tempo, não dá pra fazer troca cirúrgica.

🎯 Por que spread em updateSchemaWithNodeOutput?
const updatedSchema = { ...schema } cria novo objeto raiz, mas as entries permanecem compartilhadas. Mutação pontual não invalida referências antigas — mas reatribuição sim, daí o callback onMutateSchema.
🔧 processFlowWithSubstitution — legacy
Método na linha 241-267 do service que faz o mesmo ciclo (generate → apply → execute → update). Não é usado pela Fase 3 (que faz manualmente), mas está exportado. Possível dead code ou usado por endpoint alternativo.
Resumo — o que sai de 2.3:
• nodeSubstitutionSchema: { [key]: { [field]: string } } — mapa in-memory pronto pra applySubstitutionToObject
• 1 a 3 chaves por node (UUID puro + UUID normalizado + label lowercase)
• Valores coerced pra string (via text ?? content ?? result ?? JSON.stringify)
• Zero I/O; puro CPU; O(N × F) onde F é ~4 campos por tipo
Observações para migração:
• Ver memória [[project_substitution_engine]]: 57 sync sites em FluxService. Refactor requer tocar em todos simultaneamente.
• Worker não tem esse engine — recebe cada nó já pré-substituído (aplica applySubstitutionToObject antes do handoff). Migração pro worker preserva essa boundary.
• A basedOnType é hand-maintained (igual MCP schema catalog). Ao adicionar novo tipo de nó com campo referenciável, tem que atualizar. Sem CI check — bug silencioso.
• O result/content/text flattening carrega payloads gigantes pra memória. Não é seguro só preview-truncar (ver [[project_node_field_taxonomy]]) — placeholder pode precisar do valor completo.
• Alternativa longo prazo: index-only schema — o schema guarda só {nodeId, field}, e o resolver busca o valor real sob demanda. Elimina duplicação em memória mas complica cache.
• processFlowWithSubstitution (linhas 241-267) parece dead code — validar antes de qualquer limpeza.

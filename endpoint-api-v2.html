POST /flux/api-v2 — 3 modos de resposta

Sync rápido · Sync lento com polling · Callback assíncrono

1 Visão geral

O endpoint canônico para disparar execução de agente. Suporta três modos de resposta que dependem de dois fatores: se o caller passou callback_url, e se o flow completa em menos de 2 minutos.

MétodoPOST

AuthAPI-key (header)
Timeout de espera síncrona2 min
Timeout do workflow6h (Temporal)

3 Árvore de decisão dos 3 modos

Backend recebe request

↓

Request tem callback_url?
NÃO — Modo síncrono
Backend chama handle.result({ timeout: '2m' }) e espera.
Modo A — Sync rápido Flow completa em <2min → retorna 200 com o output completo
Modo B — Sync lento Passa de 2min → retorna 202 com URL de polling. Workflow continua rodando.
SIM — Modo assíncrono
Backend não espera — retorna imediato e delega notificação ao workflow.
Modo C — Callback Retorna 200 imediato com flowExecutionId. Workflow POSTa no callback_url ao terminar.

4 Modo A — Sync rápido (< 2 min, sem callback)

Fluxo típico do caller que espera resposta HTTP 200 OK
Quando este modo: caller não passou callback_url e o flow completa em menos de 2 minutos. Backend segura a conexão HTTP até o workflow acabar e entrega o output no response.
1 Caller → Backend   POST /flux/api-v2?flowId=X com body
2 Backend → DB   INSERT flow_executions (status=queued) + bulk INSERT em flow_execution_snapshots
3 Backend → Temporal   client.start('FlowExecutionWorkflow', { flowExecutionId })
4 Backend ⏳ handle.result({ timeout: '2m' }) — bloqueia até o workflow terminar OU passar 2min
5 Workflow → Temporal   retorna output após ~30s (ex.: agente completou)
6 Temporal → Backend   handle.result() resolve com o payload de output
7 Backend → Caller   200 OK + JSON com flowExecutionId, output, tokens, cost

Response — 200 OK

200 OK { "flowExecutionId": "a1b2c3...", "status": "completed", "output": { "OutputNodeLabel1": "resultado final do agente...", "OutputNodeLabel2": [...] }, "tokens": { "total": 4523, "input": 1200, "output": 3323 }, "cost": 0.0234, "durationMs": 28450 }

5 Modo B — Sync lento (≥ 2 min, sem callback)

Backend desiste da espera, workflow continua sozinho 202 Accepted
Quando este modo: caller não passou callback_url mas o flow demora mais de 2 minutos. Backend faz timeout no handle.result, retorna URL de polling e o workflow continua rodando independentemente — desligar o HTTP não afeta a execução.
1 Caller → Backend   POST /flux/api-v2?flowId=X
2 Backend → passos 2-3 iguais ao Modo A (snapshot + start)
3 Backend ⏳ handle.result({ timeout: '2m' }) — bloqueia esperando…
4 Backend ✕ Após 2min sem completar → WorkflowExecutionTimeoutError. Backend captura mas não cancela o workflow.
5 Backend → Caller   202 Accepted + flowExecutionId + URL de polling
6 Workflow ... Continua rodando (mais alguns minutos). Independente do backend.
7 Workflow → DB   Ao terminar, FASE 4 escreve output em node_executions e status em flow_executions
8 Caller → Backend   GET /flux/api-v2/executions/{flowExecutionId} (polling) — retorna status atual + output se completo

Response — 202 Accepted

202 Accepted { "flowExecutionId": "a1b2c3...", "status": "running", "statusUrl": "https://api.flux.example/flux/api-v2/executions/a1b2c3...", "message": "Execution exceeded 2min sync window. Poll statusUrl or use callback_url next time." }
Importante: o timeout do backend (2 min) é totalmente independente do timeout do workflow no Temporal (default 6h). Se a conexão HTTP cair antes dos 2min, o workflow ainda continua rodando — o cliente pode consultar o status a qualquer momento via polling.

6 Modo C — Callback (com callback_url)

Backend retorna 200 imediato, callback recebe o output quando pronto 200 OK (imediato)
Quando este modo: caller passou ?callback_url=https://meu-servico/webhook. Ideal para orquestração assíncrona (o caller não precisa manter conexão aberta e nem fazer polling).
1 Caller → Backend   POST /flux/api-v2?flowId=X&callback_url=https://...
2 Backend → DB   INSERT flow_executions (com callback_url guardado na row) + snapshot
3 Backend → Temporal   start('FlowExecutionWorkflow', { flowExecutionId, callbackUrl })
4 Backend → Caller   200 OK imediato com flowExecutionId + statusUrl. Backend não espera.
5 Workflow ... Roda no seu tempo (segundos ou horas). FASE 3 executa ondas paralelas normalmente.
6 Workflow → Callback URL   FASE 4.5: activity POSTa no callback_url com o output. Retry policy: 5 tentativas com backoff exponencial.
7 Callback URL → Workflow   Retorna 2xx = entregue com sucesso. 4xx/5xx = re-tenta segundo policy.

Response inicial — 200 OK

200 OK { "flowExecutionId": "a1b2c3...", "status": "queued", "statusUrl": "https://api.flux.example/flux/api-v2/executions/a1b2c3...", "callbackAt": "https://meu-servico/webhook", "message": "Execution enqueued. Callback will fire on completion." }

Payload que o Backend POSTa no callback_url

POST https://meu-servico/webhook Headers: Content-Type: application/json X-Flux-Execution: a1b2c3... X-Flux-Event: flow.completed X-Flux-Signature: sha256=<HMAC do body com secret do workspace> Body: { "flowExecutionId": "a1b2c3...", "status": "completed", // ou "failed", "cancelled" "output": { "OutputNodeLabel1": "..." }, "tokens": { "total": 4523 }, "cost": 0.0234, "durationMs": 184300, "error": null // preenchido se status !== "completed" }
Entrega garantida: Temporal executa o callback como uma activity com RetryPolicy (5 tentativas, backoff exponencial de 1s até 60s). Se após 5 falhas o receptor ainda estiver fora, a activity vira falha não-recuperável e o Backend registra em flow_executions.callback_status = 'failed'. O caller pode consultar via polling mesmo assim.
Dedup dupla: callback herda o padrão já existente na FASE 4.5 — deduplicação por flowExecutionId em Redis (TTL 24h) + hash SHA-256 do body (TTL 90s). Evita entrega dupla se o worker crashar entre o POST e a confirmação.

7 Endpoint de polling

Rota GET /flux/api-v2/executions/:flowExecutionId

Usado pelos modos B (polling manual) e C (opcional, se o caller quer também checar status). Lê de flow_executions + node_executions para montar a resposta.

Response — enquanto rodando (200 OK)

200 OK { "flowExecutionId": "a1b2c3...", "status": "running", "progress": { "completed": 3, "failed": 0, "pending": 2, "total": 5 }, "startedAt": "2026-08-21T14:32:10Z", "tokens": { "total": 1234 }, "cost": 0.008 }

Response — completou (200 OK)

200 OK { "flowExecutionId": "a1b2c3...", "status": "completed", "output": { /* mesmo shape do modo A */ }, "tokens": {...}, "cost": 0.0234, "durationMs": 184300, "finishedAt": "2026-08-21T14:35:14Z" }

Response — falhou (200 OK — retorna status, não HTTP error)

200 OK { "flowExecutionId": "a1b2c3...", "status": "failed", "error": { "nodeId": "TextGen1", "category": "llm.rate_limited", "message": "OpenAI returned 429 after 5 retries" }, "finishedAt": "..." }

Response — não existe (404)

404 Not Found { "error": "flow_execution_not_found" }

Nota importante: uma vez que o workflow foi enfileirado (temporal.start retornou), o endpoint nunca retorna 5xx. Erros de execução do flow (nó falhou, LLM deu timeout, etc.) são reportados no output.status/error do body em 200 (modo A) ou via polling/callback (modos B/C).

9 Detalhes técnicos importantes

Timeout do backend ≠ timeout do workflow

O handle.result({ timeout: '2m' }) é um timeout do lado do Backend (SDK do Temporal esperando pela conclusão). O workflow em si tem timeout próprio configurado no StartWorkflowOptions.workflowExecutionTimeout, tipicamente 6h. Se o backend faz timeout aos 2min, ele apenas desiste de esperar — o workflow continua com seu próprio timer.

Idempotência do POST

WorkflowId = flowExecutionId + WorkflowIdReusePolicy = REJECT_DUPLICATE garantem que uma segunda chamada do backend com o mesmo flowExecutionId (crash + retry) não dispara uma segunda execução. Mas o backend gera novo flowExecutionId a cada request, então requests repetidos do caller são runs distintos — se quiser idempotência no nível do request, o caller deve enviar um Idempotency-Key no header (opcional, pode virar feature futura).

Callback URL — validação

  • Precisa ser HTTPS (rejeitado em modo dev com HTTP se NODE_ENV=production)
  • Não pode apontar pra IPs privados (SSRF prevention) — validação de DNS + faixas RFC1918/loopback
  • Não pode apontar pro próprio domínio da API (loop protection)
  • Tem timeout de 30s por tentativa; após 5 retries falhos, marca callback como failed

Ordem de garantia do callback

O callback dispara depois de todos os passos de FASE 4 completarem (persist output, flow_logs, chat session, etc.). Se você recebe o webhook, todos os artefatos do run já estão no banco — é seguro consultar o polling endpoint no callback handler pra pegar detalhes extras (per-node breakdown, telemetria).

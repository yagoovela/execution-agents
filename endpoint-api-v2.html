◈ POST /flux/api-v2

POST /flux/api-v2. 3 response modes.

Fast sync · Slow sync with polling · Async callback.

1 Overview

The canonical endpoint for triggering agent execution. Supports three response modes that depend on <strong>two factors</strong>. Whether the caller passed <code>callback_url</code>. Whether the flow completes in under 2 minutes.

MethodPOST
Path/flux/api-v2
AuthAPI-key (header)
Sync wait timeout2 min
Workflow timeout6h (Temporal)

Backend receives request

4 Mode A. Fast sync (< 2 min, no callback).

Typical caller flow waiting for the HTTP response 200 OK
When this mode: caller <em>did not</em> pass <code>callback_url</code> and the flow completes in under 2 minutes. Backend keeps the HTTP connection open until the workflow finishes. Delivers the output in the response.
1 Caller → Backend   POST /flux/api-v2?flowId=X with body
2 Backend → DB   INSERT flow_executions (status=queued) + bulk INSERT into flow_execution_snapshots
3 Backend → Temporal   client.start('FlowExecutionWorkflow', { flowExecutionId })
4 Backend ⏳ handle.result({ timeout: '2m' }). Blocks until the workflow finishes OR 2min elapses.
5 Workflow → Temporal   returns output after ~30s (e.g., agent completed).
6 Temporal → Backend   handle.result() resolves with the output payload.
7 Backend → Caller   200 OK + JSON with flowExecutionId, output, tokens, cost.

Response. 200 OK.

200 OK { "flowExecutionId": "a1b2c3...", "status": "completed", "output": { "OutputNodeLabel1": "agent final result...", "OutputNodeLabel2": [...] }, "tokens": { "total": 4523, "input": 1200, "output": 3323 }, "cost": 0.0234, "durationMs": 28450 }

5 Mode B. Slow sync (≥ 2 min, no callback).

Backend gives up waiting, workflow continues on its own 202 Accepted
When this mode: caller <em>did not</em> pass <code>callback_url</code> but the flow takes over 2 minutes. Backend times out on <code>handle.result</code>. Returns a polling URL. <strong>The workflow keeps running independently</strong>. Dropping the HTTP does not affect execution.
1 Caller → Backend   POST /flux/api-v2?flowId=X
2 Backend → steps 2-3 same as Mode A (snapshot + start)
3 Backend ⏳ handle.result({ timeout: '2m' }). Blocks waiting…
4 Backend ✕ After 2min without completing, <code>WorkflowExecutionTimeoutError</code>. Backend catches but does <strong>not cancel</strong> the workflow.
5 Backend → Caller   202 Accepted + flowExecutionId + polling URL.
6 Workflow ... Keeps running (a few more minutes). Independent of the backend.
7 Workflow → DB   On completion, PHASE 4 writes the output to node_executions and status to flow_executions.
8 Caller → Backend   GET /flux/api-v2/executions/{flowExecutionId} (polling). Returns current status + output if complete.

Response. 202 Accepted.

202 Accepted { "flowExecutionId": "a1b2c3...", "status": "running", "statusUrl": "https://api.flux.example/flux/api-v2/executions/a1b2c3...", "message": "Execution exceeded 2min sync window. Poll statusUrl or use callback_url next time." }
Important: the <em>backend</em> timeout (2 min) is totally independent from the <em>workflow</em> timeout at Temporal (default 6h). If the HTTP connection drops before 2min, the workflow still keeps running. The client can check status at any time via polling.

6 Mode C. Callback (with callback_url).

Backend returns 200 immediately. Callback receives output when ready. 200 OK (immediate)
When this mode: caller passed <code>?callback_url=https://my-service/webhook</code>. Ideal for async orchestration. The caller does not need to keep a connection open or poll.
1 Caller → Backend   POST /flux/api-v2?flowId=X&callback_url=https://...
2 Backend → DB   INSERT flow_executions (with <code>callback_url</code> stored on the row) + snapshot.
3 Backend → Temporal   start('FlowExecutionWorkflow', { flowExecutionId, callbackUrl })
4 Backend → Caller   200 OK immediately with <code>flowExecutionId</code> + <code>statusUrl</code>. Backend does not wait.
5 Workflow ... Runs in its own time (seconds or hours). PHASE 3 executes parallel waves normally.
6 Workflow → Callback URL   PHASE 4.5. Activity POSTs to <code>callback_url</code> with the output. Retry policy: 5 attempts with exponential backoff.
7 Callback URL → Workflow   Returns 2xx = delivered. 4xx/5xx = retries per policy.

Initial response. 200 OK.

200 OK { "flowExecutionId": "a1b2c3...", "status": "queued", "statusUrl": "https://api.flux.example/flux/api-v2/executions/a1b2c3...", "callbackAt": "https://my-service/webhook", "message": "Execution enqueued. Callback will fire on completion." }

Payload the Backend POSTs to callback_url.

POST https://my-service/webhook Headers: Content-Type: application/json X-Flux-Execution: a1b2c3... X-Flux-Event: flow.completed X-Flux-Signature: sha256=<HMAC of body with workspace secret> Body: { "flowExecutionId": "a1b2c3...", "status": "completed", // or "failed", "cancelled" "output": { "OutputNodeLabel1": "..." }, "tokens": { "total": 4523 }, "cost": 0.0234, "durationMs": 184300, "error": null // populated if status !== "completed" }
Guaranteed delivery: Temporal runs the callback as an <em>activity</em> with <code>RetryPolicy</code> (5 attempts, exponential backoff from 1s to 60s). If after 5 failures the receiver is still down, the activity becomes a non-recoverable failure. Backend records in <code>flow_executions.callback_status = 'failed'</code>. The caller can still poll anyway.
Double dedup: callback inherits the pattern already in PHASE 4.5. Dedup by <code>flowExecutionId</code> in Redis (TTL 24h) + body SHA-256 hash (TTL 90s). Avoids double delivery if the worker crashes between POST and confirmation.

7 Polling endpoint

Route GET /flux/api-v2/executions/:flowExecutionId

Used by modes B (manual polling) and C (optional, if the caller also wants to check status). Reads from flow_executions + node_executions to build the response.

Response. While running (200 OK).

200 OK { "flowExecutionId": "a1b2c3...", "status": "running", "progress": { "completed": 3, "failed": 0, "pending": 2, "total": 5 }, "startedAt": "2026-08-21T14:32:10Z", "tokens": { "total": 1234 }, "cost": 0.008 }

Response. Completed (200 OK).

200 OK { "flowExecutionId": "a1b2c3...", "status": "completed", "output": { /* same shape as mode A */ }, "tokens": {...}, "cost": 0.0234, "durationMs": 184300, "finishedAt": "2026-08-21T14:35:14Z" }

Response. Failed (200 OK. Returns status, not HTTP error).

200 OK { "flowExecutionId": "a1b2c3...", "status": "failed", "error": { "nodeId": "TextGen1", "category": "llm.rate_limited", "message": "OpenAI returned 429 after 5 retries" }, "finishedAt": "..." }

Response. Does not exist (404).

404 Not Found { "error": "flow_execution_not_found" }

Important note: once the workflow has been enqueued (temporal.start returned), <strong>the endpoint never returns 5xx</strong>. Flow execution errors (node failed, LLM timeout, etc.) are reported in the body's <code>output.status</code>/<code>error</code> in <code>200</code> (mode A) or via polling/callback (modes B/C).

9 Important technical details

Backend timeout ≠ workflow timeout

<code>handle.result({ timeout: '2m' })</code> is a <strong>backend-side</strong> timeout (Temporal SDK waiting for completion). The workflow itself has its own timeout configured on <code>StartWorkflowOptions.workflowExecutionTimeout</code>, typically 6h. If the backend times out at 2min, it just <em>gives up waiting</em>. The workflow keeps its own timer.

POST idempotency

<code>WorkflowId = flowExecutionId</code> + <code>WorkflowIdReusePolicy = REJECT_DUPLICATE</code> ensure that a second backend call with the same <code>flowExecutionId</code> (crash + retry) does not fire a second execution. The backend generates a new <code>flowExecutionId</code> per request. Repeated caller requests are distinct executions. For request-level idempotency, the caller must send an <code>Idempotency-Key</code> header (optional, may become a future feature).

Callback URL. Validation.

  • Must be HTTPS (rejected in dev mode with HTTP if NODE_ENV=production).
  • Cannot point to private IPs (SSRF prevention). DNS validation + RFC1918/loopback ranges.
  • Cannot point to the API's own domain (loop protection).
  • Has 30s timeout per attempt. After 5 failed retries, marks callback as failed.

Callback ordering guarantee

The callback fires <strong>after</strong> every PHASE 4 step completes (persist output, flow_logs, chat session, etc.). If you receive the webhook, every artefact of the execution is already in the database. It is safe to query the polling endpoint in the callback handler to fetch extra detail (per-node breakdown, telemetry).

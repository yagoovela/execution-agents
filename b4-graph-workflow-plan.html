B4 — Mover o laço do DAG para um workflow do Temporal

Move o laço de execução do DAG do back para um workflow do Temporal. Sem paralelismo nesta task — cada nó despacha um por vez. O código já suporta lote; fica configurado como um. A B5 ativa o lote trocando o for por Promise.all.

⚡ TL;DR

O que move: o laço while de flux.service.ts vira o workflow processFlowWorkflow no worker, dono do SchedulerState.

Como se liga: env var FLUX_FLOW_ENGINE_MODE=back|workflow. Default back. Rollback sem redeploy.

Invariante do estado: o workflow carrega só IDs — nodeIds, completed, outputStore: Map<nodeId, nodeExecutionId>. Payloads ficam em DB/S3. continueAsNew a cada 500 execuções protege o histórico do Temporal.

Bridge temporária: nós ainda inline (arrayNode, fluxBox, libraryNode, conditionNode e cia.) saem via uma activity que chama o back. A B6 remove essa bridge quando portar esses tipos para child workflows.

O ponto-chave da arquitetura: o processor é agnóstico ao motor. Ele chama apiV2() e lê o resultado — sem saber se veio do laço inline ou do workflow. A mudança é cirúrgica: um if no início de apiV2(). Isso é o que torna a B4 revertível por uma env var, sem redeploy.
Benefício colateral: fecha o gap de dispatch do full-run.

Hoje o laço while em apiV2 precisa de uma if (node.type === 'X') processNodeViaTemporal(…) por tipo. Em 2026-10-15, cinco tipos worker-routed ainda não tinham esse branch — eles só rodavam em single-node, não em agente completo.

O modo workflow da B4 usa dispatch genérico (startChild('processSingleNode') pra qualquer tipo). Nenhum branch dedicado por tipo. Qualquer tipo worker-routed roda em full-run sem código novo em apiV2. Esse gap desaparece como efeito colateral da flag estar on.

Assinatura

Payload de entrada: ~500 bytes. Nunca contém node_data, edges[], output resolvido. Só IDs.

Estado carregado entre iterações e através de continueAsNew

interface SerializedSchedulerState {
  // Scheduler state — tudo id e contador
  nodeIds: string[];
  forwardDeps: [string, string[]][];
  conditionEdges: [string, SchedEdge[]][];      // SchedEdge = só source/target/handles
  totalPreds: [string, number][];
  resolvedPreds: [string, number][];
  deadPreds: [string, number][];
  gatingPairs: string[];                       // pares "A->B"
  totalGatingPreds: [string, number][];
  resolvedGatingPreds: [string, number][];
  deadGatingPreds: [string, number][];
  ready: string[];
  completed: string[];
  dead: string[];
  scheduled: string[];
  // OutputStore — ponte para o conteúdo real
  outputStore: [string, string][];           // [nodeId, nodeExecutionId]
  // Metadata
  starterSourceId: string;
}
Tamanho estimado: O(nodes + edges) × ~30 bytes. Fluxo gigante (1000 nós / 2000 arestas) ≈ 100KB. Confortável sob o limite de 2MB por fronteira activity ↔ workflow. Payloads reais (node_data, outputData) ficam em node_executions ou S3 via __claimRef; o workflow nunca enxerga.

O loop

export async function processFlowWorkflow(args) {
  let state: SchedulerState;
  let outputStore: Map<string, string>;
  let executionsSoFar = args.executionsSoFar ?? 0;

  if (args.carriedState) {
    state = deserializeState(args.carriedState);
    outputStore = new Map(args.carriedState.outputStore);
  } else {
    // Fase 2.1 do arquitetura-v2 — topology only, zero node_data
    const topology = await loadFlowTopologyActivity({
      runId: args.runId, flowId: args.flowId,
    });
    state = buildSchedulerState(topology.nodes, topology.edges, args.starterSourceId);
    outputStore = new Map();
    await emitFlowStartedActivity({ runId: args.runId });
  }

  while (state.completed.size + state.dead.size < state.nodeIds.size) {
    const readySet = allReady(state);                     // Fase 3.1

    if (readySet.length === 0) {                           // Fase 3.2 — STALL DETECTOR
      const stuck = unprocessedIds(state);
      throw ApplicationFailure.create({
        type: 'FlowSchedulerStall',
        message: `scheduler stall at ${state.completed.size + state.dead.size}/${state.nodeIds.size} — stuck ids: ${stuck.slice(0, 20).join(',')}`,
        nonRetryable: true,
      });
    }

    for (const nodeId of readySet) {                      // B4: batch 1 — B5 vira Promise.all
      const nodeType = topology.nodeTypeById.get(nodeId)!;
      const result = hasWorkerModule(nodeType)
        ? await startChild(processSingleNode, {
            args: [nodeId, args.userId, args.sessionId, args.flowId, ...],
            workflowId: `${args.runId}:${nodeId}`,
          }).result()
        : await runInlineNodeInBackActivity({            // bridge temp (removida pela B6)
            runId: args.runId, flowId: args.flowId, nodeId, nodeType,
            outputStoreSnapshot: [...outputStore],
          });

      outputStore.set(nodeId, result.nodeExecutionId);     // 3.4.5 append-only

      if (nodeType === 'conditionNode') {                    // 3.7 propagar
        completeCondition(state, nodeId, result.takenHandle!);
      } else if (result.status === 'completed' || result.status === 'COMPLETED') {
        markCompleted(state, nodeId);
      } else {
        markDead(state, nodeId);
      }

      executionsSoFar += 1;

      if (executionsSoFar >= HISTORY_BOUNDARY) {              // 300 — Decisão B
        await continueAsNew<typeof processFlowWorkflow>({
          ...args,
          carriedState: serializeStateWithStore(state, outputStore),
          executionsSoFar: 0,
        });
      }
    }
  }

  return await aggregateFlowResultActivity({ runId: args.runId });
}

Nova função em scheduler.ts (back + ported no worker)

// Drena todos os ids prontos, marca cada um scheduled.
// nextReady continua existindo para o laço do back (até C2 aposentar o laço).
export function allReady(state: SchedulerState): string[] {
  const drained: string[] = [];
  while (state.ready.length) {
    const id = state.ready.shift()!;
    if (state.dead.has(id) || state.completed.has(id) || state.scheduled.has(id)) continue;
    state.scheduled.add(id);
    drained.push(id);
  }
  return drained;
}
Nota da spec: antes de escrever allReady(), confere se o SDK do Temporal já oferece primitiva de ready-set dispatch. Decisão registrada no PR — não há primitiva específica; usamos a função pura acima. A D16 não muda em nenhum dos casos.

⚠️ A bridge temporária: runInlineNodeInBackActivity

Esta activity existe por uma única razão: arrayNode, fluxBox, libraryNode, nodesBox, conditionNode e integrações com provider não-migrado ainda não têm worker module. Até a B6 portar esses tipos como child workflows, o back é o único lugar que sabe executá-los. A bridge é a ponte entre as duas realidades.

A B4 não elimina a espera bloqueante para todos os fluxos.

Elimina em fluxos puros worker-routed. O handle.result() por nó some: há um único handle.result() por run inteiro, aguardando o workflow.

Não elimina em fluxos com arrayNode ou sub-flows. O caminho é:
1. Workflow despacha arrayNode para a bridge.
2. Back entra no arm inline e itera.
3. Cada iteração chama processNodeViaTemporal para nós worker-routed do body.
4. Cada chamada vira um await handle.result().

A B6 fecha isso. arrayNode vira startChild('ArrayIterationWorkflow') e sub-flows viram startChild('processFlowWorkflow'). Aí o workflow pai não espera mais o back — o Temporal faz o relacionamento.
Lembrete de limpeza. Quando a B6 shipar os child workflows, três coisas viram dead code juntas: a activity runInlineNodeInBackActivity, o endpoint /internal/execute-inline-node e os arm inline que atendem a esse endpoint. O PR da B4 deve registrar essa dependência explicitamente, para que ninguém esqueça de remover depois.

6
Controles negativos — paralisação, cancelamento, nó-não-processado
três requisitos da spec que precisam sobreviver à mudança
obrigatório 6.1 — Detecção de paralisação (markCompleted quebrado)
O cenário: a activity de um nó termina com sucesso, mas o markCompleted está quebrado e não propaga para os successors. Resultado: state.ready vazia, nada rodando, nada despachável. O workflow fica em silêncio até estourar o workflowExecutionTimeout.

A mecânica da detecção: depois de aplicar o resultado de cada activity, checa se allReady() === [] enquanto completed + dead < nodeIds.size. Se bater, lança ApplicationFailure(FlowSchedulerStall) listando os IDs presos. Falha em milissegundos. nonRetryable: true.

O teste: injeta um scheduler onde markCompleted é no-op. Assert WorkflowFailedError com cause.type === 'FlowSchedulerStall'.
Red/green: com scheduler quebrado, red; restaurado, green. É assim que se prova que o teste captura o bug.
6.2 — Nó-não-processado (flow_truncated)
Hoje no back: quando o laço while fecha, se restaram nós fora de completed/dead, o back loga flow_truncated. Warning silencioso — o run já acabou.

No workflow: o invariante do loop while (completed + dead < nodeIds.size) impede a saída silenciosa. Três caminhos possíveis:
→ Bug no scheduler: stall detector dispara.
→ Cancelamento: handler de cancel dispara.
→ Caso normal: todos processaram e o loop sai limpo.

O teste: fluxo onde o upstream é marcado dead. Afirma que o filho propaga via deadGatingPreds, não via "não processado silencioso".
obrigatório 6.3 — Cancelamento end-to-end
Dois caminhos de cancelamento, ambos precisam funcionar:

(a) Cancelamento externo do workflow. Alguém chama handle.cancel(). O Temporal propaga CancelledFailure no workflow. Um try/catch envolve o loop, dispara markRunCancelledActivity({stoppedAtNodeId, notExecutedNodeIds}) e re-lança.

(b) Cancelamento em-vôo da activity. O Temporal propaga cancellationSignal para a activity em execução. As activities verificam via Context.current().cancellationSignal. Na bridge, o cancel é propagado ao back via cancelRunKey; o back responde com 499 ou similar; a activity levanta CancelledFailure.

Fonte de verdade inalterada: o runCancellationService (Redis TTL) segue sendo o único source of truth. O workflow consulta via activity, igual o back faz hoje.
7
Equivalência de ordem — o portão de saída da onda
com batch 1, qualquer divergência é defeito de port
A verificação mais importante da task.

Com batch 1, o workflow precisa executar os nós na mesma ordem exata do laço do back. Qualquer divergência é defeito de port. Este é o último momento em que esse defeito é barato de ver.

Itens herdados da B3b — validar antes de ship
republicados pelo commit c160809
A B3b deixou 4 itens na projeção de input do worker (worker/src/modules/nodes/shared/project-node-input.ts). Antes de corrigir um, a B4 valida se ainda aplica ao graph workflow. Se não aplicar, registra o porquê no PR e fecha.
10.1 — Source sem seed row é droppada silenciosamente
O problema: RunData.nodes só guarda sources que estão nos outputs do run ou em run_seed_nodes. Um nó adicionado ao fluxo depois do run começar não tem nenhum dos dois, então sua edge projeta nada e o target recebe entrada vazia sem erro.

A decisão: no modo workflow, o graph workflow pode ver um nó assim? Se sim, fazer o target falhar da mesma forma que falha uma source completed sem output. Se não, documentar o porquê.
10.2 — Ciclo de nós que ainda não rodaram
O problema: RunData.fromSeed pula um upstream que já está sendo carregado do seed. Dentro de um ciclo, um nó é projetado sem essa source. conditionNode loops não têm gating, então chegam ao worker hoje.

A validação: hoje o scheduler do back dropa back edges, então um ciclo encontra a projeção só na primeira passada (dev run 842aeff8 matched na B3b). Re-checar quando o graph workflow rodar um loop mais de uma vez — pode exigir mudança na projeção.
10.3 — Starter edges droppadas por id vs. isDependencyEdge
O problema: o worker dropa edges cujo source é starterSourceId. A regra do produto para quais edges carregam data é isDependencyEdge em flux/scheduler.ts, que também deixa de fora GLOBAL_HANDLE sources e edges sem targetHandle.

A decisão: usar isDependencyEdge se o graph workflow ler edges do mesmo jeito. Isso unifica a regra em um só lugar e alinha worker com o scheduler da B2.
10.4 — Cleanups pequenos (quando mexer no código)
Dois ajustes pequenos:
→ RunInputResolution.seedSnapshotId pode ler snapshotIds[0] diretamente.
→ backOnlyProjectionNodes(...).length === 0 pode virar um check de some.

Nenhum muda comportamento. Entram no PR se a B4 tocar nesses arquivos para resolver 10.1-10.3.

Step 1.5b — fluxObject reset with clearOnExecution

Block in flux.service.ts:2525-2558. For every fluxObject node with truthy data.clearOnExecution, executes 3 actions. First, clears session state in Postgres if it's chat or session-enabled. Second, persists the reset on the node's live row. Third, reapplies the reset in memory in updatedFlows.
In short — what this step does
  • Locates fluxObjects with the flag on. updatedFlows.filter(isFluxObjectClearOnExecution). It's a pure helper at node-output-reset.ts:137-143 that tests node.type === 'fluxObject' && Boolean(node.data.clearOnExecution). If there are none, the whole block is skipped.
  • Loop with 2 side effects per node. For each nodeToClear, tests fluxObjectPersistsEntries(node). Returns true if data.chat === true or data.sessionEnabled === true. If yes, calls sessionStateService.clear, which runs DELETE on rows in that scope on Postgres.
  • Persists the reset in progress. Calls persistNodeDataToLiveRow passing buildFluxObjectClearOnExecution(node). Resolves to { entries: [] } by default. Or to a complex structure with userSessionsChat when there is a non-default selected session. Writes to flow_version_history (if versioned) or directly to flow_nodes.
  • Reapplies in memory on updatedFlows. After the loop, updatedFlows.map re-runs buildFluxObjectClearOnExecution on every node, not just the "clear" ones. If the result is not empty (only returns non-empty for fluxObject with flag), it does a spread merge. The in-memory array ends up aligned with what was written.
  • Two sources of truth in sync (DB and memory). The design is complex (writes and then reapplies in memory), but it guarantees that anyone reading the node from that point on sees the clean state. So do those querying the DB.
Context. clearOnExecution is opt-in per node. The user toggles it in the editor to say that on every execution the history should be forgotten. Without this mechanism, chats accumulate indefinitely across executions.

A isFluxObjectClearOnExecution(node)

export function isFluxObjectClearOnExecution<T>(node: T): boolean
Purpose. Identify nodes of type fluxObject that have the clearOnExecution flag on. It's the entry gate for this block. If the filter returns an empty array, everything else is skipped.
In short. A lean check. Is it of type fluxObject? Does it have clearOnExecution truthy? The check uses Boolean() because clearOnExecution can arrive as undefined (falsy), {} (empty object, truthy) or { field: true } (truthy). An empty object still triggers the clear. It makes sense in the domain. If the user set the field, even empty, it's explicit opt-in. Other types exist (fluxBox, libraryNode) that also use clearOnExecution, but with different semantics. They are handled in step 1.7a. Only fluxObject has this special session-state-plus-persist logic.

B fluxObjectPersistsEntries(node)
node-output-reset.ts:145-149 (impl) + flux.service.ts:2531 (use)
export function fluxObjectPersistsEntries<T>(node: T): boolean
Purpose. Sub-gate inside the loop. Only calls sessionStateService.clear if the node is chat or has sessions. Without this gate, the clear would run for normal fluxObjects (no session) and do a useless DELETE on Postgres.
In short. Not every fluxObject stores data in session state. Only those in chat mode (data.chat === true) or with sessions enabled (data.sessionEnabled === true). This gate distinguishes them. If the node is a static key-value store, session state is empty. Not worth running DELETE. If it's chat or session, it needs to scan the table. It's optimization and correctness. Avoids unnecessary queries. Doesn't run session clear code on nodes that have no session to clear.
B1 Implementation. Union of 2 flags

C sessionStateService.clear({ scopeType, scopeId, sessionKey, ownerUserId })
session-state.service.ts:189-199 + flux.service.ts:2532-2540
async clear(scope: SessionStateScope): Promise<void>
Purpose. Deletes all rows from the session_state_entry table matching the scope (chat, scopeId, sessionKey and optional ownerUserId). The scope here is type='chat', id='{flowId}:{nodeId}', sessionKey=data.selectedChat || 'default'.
In short. Erases all session state for that node or session. The scope is composite. scopeType = 'chat' (fixed here). scopeId = flowId:nodeId (built by buildNodeScopeId). sessionKey = data.selectedChat || 'default' (which chat session to clear). And ownerUserId if provided. The service builds a dynamic where. If ownerUserId is undefined, it doesn't go into the WHERE. Clears cross-user in that scope. In practice this doesn't happen because it always passes user?.id. Then it calls sessionStateRepository.delete(where). Hard delete, no soft-delete. It's irreversible. Each call here deletes 1 to N rows in Postgres.

🎯 resolveSessionKey normalizes
resolveSessionKey('') returns 'default'. The trim plus fallback happens inside the service. buildNodeScopeId(flowId, nodeId) = `${flowId}:${nodeId}`. Simple concatenation with :.
⚠️ Failure propagates in the flow
The await here is inside the main try of apiV2. If it fails, it propagates to the general catch and the entire execution fails. There is no retry or soft-fail. The clear is hard-required.
⚠️ ownerUserId optional in where
If user?.id is undefined, the where doesn't filter by owner. It deletes cross-user. It's only safe because, in practice, user is always populated at this point (validated earlier).
🔧 Scope types
SessionScopeType = 'chat' | 'object' | 'memory' | 'counter'. Here it uses only chat. object is used in clearObjects (1.7b). Each scope has different semantics, but the same table.
D persistNodeDataToLiveRow + buildFluxObjectClearOnExecution
flux.service.ts:2543-2548, 2235-2262 + node-output-reset.ts:151-169
await this.persistNodeDataToLiveRow(flowId, nodeId, buildFluxObjectClearOnExecution(node), flowVersionHistoryId)
Purpose. Writes the reset to Postgres. It's a partial patch of that node's data. The frontend canvas immediately reflects that fluxObject was zeroed. Without this write, the DB would keep the old state until the worker's persistNodeSuccess overwrites it.
In short. The buildFluxObjectClearOnExecution helper builds the patch that goes to the DB. It has two modes. If selectedChat === 'default' or there is no userSessionsChat, the patch is { entries: [] }. Only zeroes entries. If there is a non-default named session, the patch is more complex. { entries: [], userSessionsChat: [...map that zeroes entries of the active session] }. Preserves the other sessions and clears the selected one. Then persistNodeDataToLiveRow applies this patch. If the execution is versioned (flowVersionHistoryId present), it updates the version history snapshot. Otherwise, it updates the live row in flow_nodes. Bug on failure. There is a catch inside the persist itself. It logs the error but doesn't propagate. Execution proceeds even if the write fails. The DB can end up out of sync with memory if something goes wrong here, but execution itself continues.
D1 buildFluxObjectClearOnExecution. Patch resolver
export function buildFluxObjectClearOnExecution(node) { if (!isFluxObjectClearOnExecution(node)) return {}; const data = node.data; const selectedChat = data.selectedChat || 'default'; if (selectedChat === 'default' || !Array.isArray(data.userSessionsChat)) { return { entries: [] }; } return { entries: [], userSessionsChat: data.userSessionsChat.map( session => session?.id === selectedChat ? { ...session, entries: [] } : session, ), }; }

🎯 Why 2 modes in the patch?
selectedChat = 'default'. The user is on the default chat. Only clears entries. No userSessionsChat to modify. Named session. There are several sessions in the array. Only zeroes entries of the active one, preserving the others.
📎 persistNodeDataToLiveRow docstring
"Persist a node's run-time data to the live flow JSON so the canvas reflects it. Used for values the worker never writes back (persistNodeSuccess): a data-input node's resolved value, and the entries a Small Memory node drops at the start of a clear-on-execution run."
⚠️ Log-only catch. Silent sync
If the UPDATE fails (deadlock, connection dropped), the log is recorded, but execution continues. The DB is temporarily out of sync with memory, until the next persist overwrites it.
🔧 flowNodeService methods
updateSingleNodeData(flowId, nodeId, patch). JSONB merge update on flow_nodes.data. updateSingleNodeDataInHistory(historyId, nodeId, patch). Same, but on the version history snapshot.
E Reapplies in memory via updatedFlows.map
flux.service.ts:2551-2557
updatedFlows = updatedFlows.map(nd => { const reset = buildFluxObjectClearOnExecution(nd); ... });
Purpose. Reapplies the reset in memory to every node in updatedFlows. Only returns a non-empty patch for fluxObject with the flag. The others return unchanged. Syncs memory and DB.
In short. After writing the resets to the DB, the in-memory array updatedFlows still holds the old state. The previous loop only wrote to Postgres. This second pass, a .map, calls buildFluxObjectClearOnExecution for each node in the array. The helper returns {} if the node is not a fluxObject with the flag. Returns the patch otherwise. If it returned {}, returns the node unchanged. If it returned a non-empty patch, does { ...nd, data: { ...nd.data, ...reset } }. Shallow merge. Result. The in-memory array is aligned with what was persisted. The pattern is slightly redundant. Calls buildFluxObjectClearOnExecution for all of them, when only the fluxObjects with the flag matter. Cost is low. Logic stays centralized in a single helper.

🎯 Why call it on all of them?
The helper is pure and cheap. Calling on all and testing the result is simpler than having two steps (filter plus apply). Cost is one function call per node.
📎 Shallow merge
data: { ...nd.data, ...reset }. Spread merge. If reset has { entries: [] }, it overrides data.entries. If it has userSessionsChat: [...], it overrides the whole thing (no deep merge).
⚠️ Redundancy with worker's D3
When the worker later executes this fluxObject, persistNodeSuccess may overwrite it. If the worker doesn't respect the reset and overwrites with old entries, the DB reverts to the dirty state. There is no explicit contract. It's correct only by convention.
🔧 buildFluxObjectClearOnExecution is called 2x
Once in D (to build the persist patch). Once here in E (to build the merge patch). The call is idempotent and cheap. Pure helper.
Summary. What comes out of 1.5b:
updatedFlows mutated. fluxObject with clearOnExecution on have data.entries = []. Optionally, data.userSessionsChat re-mapped.
DB updated. Same changes persisted via flow_nodes or flow_version_history.
Session state deleted. For chat or session-enabled fluxObjects, relevant rows in session_state_entry are erased.
I/O. 1 DELETE (chat or session) plus 1 UPDATE per node with the flag. Serial, no batching.
Migration notes:
The helpers (isFluxObjectClearOnExecution, fluxObjectPersistsEntries, buildFluxObjectClearOnExecution) are pure functions in node-output-reset.ts. Replicable 1 to 1 in the worker.
sessionStateService.clear depends on Postgres. If the worker needs to clear, it must round-trip to the backend or receive a connection to the session_state_entry table.
persistNodeDataToLiveRow is write-through. If the worker runs it, it must have the same two branches (live vs. version-history) and the same log-only-catch behavior.
The in-memory reapply (E) only makes sense while the execution loop shares memory. In the worker, the canonical version of nodes would come from start-args. The backend would have to do the reset before starting the workflow.
Medium-high priority. Chats without clearOnExecution respected would keep permanent history. Breaks the semantics of several agents.
Caution. The other types with clearOnExecution (fluxBox, libraryNode) are handled in 1.7a with different logic. Don't mix them up.

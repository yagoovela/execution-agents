Passo 1.5b — Reset de fluxObject com clearOnExecution

Bloco em flux.service.ts:2525-2558. Para todo node fluxObject com data.clearOnExecution truthy: (1) limpa session state no Postgres se for chat/session-enabled, (2) persiste o reset no live node row, (3) reaplica o reset em memória no updatedFlows.
Em resumo — o que esse passo faz
  • Acha os fluxObject com flag ligada: updatedFlows.filter(isFluxObjectClearOnExecution) — helper puro em node-output-reset.ts:137-143 que testa node.type === 'fluxObject' && Boolean(node.data.clearOnExecution). Se não há nenhum, o bloco todo é pulado.
  • Loop com 2 side effects por node: pra cada nodeToClear, testa fluxObjectPersistsEntries(node) — que devolve true se data.chat === true ou data.sessionEnabled === true. Se sim, chama sessionStateService.clear que DELETE-a as rows daquele scope no Postgres.
  • Persiste o reset in-flight: chama persistNodeDataToLiveRow passando buildFluxObjectClearOnExecution(node) — que resolve pra { entries: [] } por default ou pra estrutura complexa com userSessionsChat se tiver sessão selecionada não-default. Grava no flow_version_history (se versionado) ou direto no flow_nodes.
  • Reaplica em memória no updatedFlows: depois do loop, updatedFlows.map re-executa buildFluxObjectClearOnExecution em todos os nodes (não só os "clear"). Se o resultado não é vazio (só volta não-vazio pros fluxObject com flag), faz spread merge — assim o array em memória fica alinhado com o que foi gravado.
  • Duas fontes de verdade — banco + memória — em sync: o design é meio complicado (grava e depois re-aplica em memória) mas garante que quem lê o node dali pra frente vê o estado limpo, e quem consultar o banco também.
Contexto: clearOnExecution é um opt-in por node — o usuário liga no editor pra dizer "toda vez que rodar, esquece o histórico". Sem esse mecanismo, chats acumulam infinitamente entre runs.

export function isFluxObjectClearOnExecution<T>(node: T): boolean
Propósito: Identificar nodes tipo fluxObject que têm o flag clearOnExecution ligado. É a "porta de entrada" desse bloco — se o filter devolver array vazio, todo o resto é pulado.
Em resumo: uma verificação bem enxuta: "é do tipo fluxObject? e tem clearOnExecution caindo pra truthy?". A verificação usa Boolean() porque clearOnExecution pode chegar como (a) undefined = falso, (b) {} objeto vazio = truthy! (c) { campo: true } = truthy. Ou seja, um objeto vazio ali dentro ainda dispara o clear — o que faz sentido no domain: se o usuário setou o campo, mesmo vazio, é opt-in explícito. Investigação: existem outros types (fluxBox, libraryNode) que também usam clearOnExecution, mas com semântica diferente — eles são tratados no passo 1.7a. Só o fluxObject tem essa lógica especial de session state + persist.

🎯 Por que Boolean()?
data.clearOnExecution pode ser undefined, um objeto {}, ou { field: true }. Boolean({}) = true (objeto vazio é truthy em JS), então mesmo config vazio dispara o clear.
📎 fluxObject vs fluxBox/libraryNode
Todos podem ter clearOnExecution, mas só fluxObject tem session state persistente (chat entries) — os outros só têm output fields simples (tratados no passo 1.7a).
🔧 Generic T
Signature <T extends { type?: string; data?: Record<string, any> }> — trabalha com qualquer objeto que tenha type+data. Não amarra numa entity específica.
B fluxObjectPersistsEntries(node)
node-output-reset.ts:145-149 (impl) + flux.service.ts:2531 (uso)
export function fluxObjectPersistsEntries<T>(node: T): boolean
Propósito: Sub-gate dentro do loop: só chama sessionStateService.clear se o node é chat ou tem sessions. Sem esse gate, o clear rodaria pra fluxObjects "normais" (sem session) e faria DELETE inútil no Postgres.
Em resumo: nem todo fluxObject guarda coisas no session state — só os que estão em chat mode (data.chat === true) ou com sessions ligadas (data.sessionEnabled === true). Esse gate distingue: se o node é só um armazém estático de chaves-valor, o session state está vazio e não vale a pena rodar DELETE. Se é chat/session, aí sim precisa varrer a tabela. É otimização + correção: evita queries desnecessárias e não rodar código de "clear session" em nodes que não têm session pra limpar.

Propósito: Deleta todas as rows da tabela session_state_entry que casam com o scope (chat + scopeId + sessionKey [+ ownerUserId]). Escopo aqui é type='chat', id='{flowId}:{nodeId}', sessionKey=data.selectedChat || 'default'.
Em resumo: é o furacão que passa e apaga tudo do session state daquele node/sessão. ⚠️ Falha silenciosa nesse fluxo

D persistNodeDataToLiveRow + buildFluxObjectClearOnExecution
flux.service.ts:2543-2548, 2235-2262 + node-output-reset.ts:151-169
await this.persistNodeDataToLiveRow(flowId, nodeId, buildFluxObjectClearOnExecution(node), flowVersionHistoryId)
Propósito: Grava no Postgres o reset — patch parcial do data desse node — pra que o canvas do frontend reflita imediatamente que aquele fluxObject foi zerado. Sem esse write, o banco continuaria com o estado velho até persistNodeSuccess do worker regravar.
Em resumo: a helper buildFluxObjectClearOnExecution monta o patch — o que precisa ir pro banco. Tem dois modos: (1) se selectedChat === 'default' ou não há userSessionsChat, o patch é só { entries: [] } — zerar as entries. (2) se tem sessão nomeada não-default, o patch é bem mais complexo: { entries: [], userSessionsChat: [...map que zera entries da sessão ativa]} — preserva as outras sessões mas limpa a selecionada. Depois, persistNodeDataToLiveRow aplica esse patch: se o run é versionado (flowVersionHistoryId presente), atualiza o snapshot do version history; senão, atualiza a live row em flow_nodes. Bug se falhar: dá catch dentro do próprio persist, loga o erro mas não propaga — o run continua mesmo se o write falhar. Ou seja, o banco pode ficar dessincronizado com a memória se algo der errado aqui, mas o run em si prossegue.

🎯 Por que 2 modos no patch?
selectedChat = 'default' = usuário está no chat padrão, só limpa entries. Não há userSessionsChat pra mexer. Sessão nomeada = tem várias sessions no array; só zera as entries da ativa, preservando as outras.
📎 Docstring do persistNodeDataToLiveRow
"Persist a node's run-time data to the live flow JSON so the canvas reflects it. Used for values the worker never writes back (persistNodeSuccess): a data-input node's resolved value, and the entries a Small Memory node drops at the start of a clear-on-execution run."
⚠️ Log-only catch — sync silencioso
Se o UPDATE falhar (deadlock, connection dropped), log é gravado mas o run continua. Banco fica dessincronizado com memória temporariamente até o próximo persist regravar.
🔧 flowNodeService métodos
updateSingleNodeData(flowId, nodeId, patch) — update JSONB merge no flow_nodes.data. updateSingleNodeDataInHistory(historyId, nodeId, patch) — mesmo mas no snapshot do version history.
E Reaplica em memória via updatedFlows.map
flux.service.ts:2551-2557
updatedFlows = updatedFlows.map(nd => { const reset = buildFluxObjectClearOnExecution(nd); ... });
Propósito: Reaplica o reset em memória em todos os nodes de updatedFlows — só volta patch não-vazio pros fluxObject com flag; os outros retornam do jeito que estavam. Sync memory ↔ banco.
Em resumo: depois de gravar no banco os resets, o array em memória updatedFlows ainda está com o estado velho — o loop anterior só escreveu no Postgres. Essa segunda passada, um .map, chama buildFluxObjectClearOnExecution pra cada node do array — a helper devolve {} se o node não é fluxObject-com-flag, e devolve o patch caso contrário. Se veio {}, retorna o node inalterado. Se veio patch não-vazio, faz { ...nd, data: { ...nd.data, ...reset } } — merge shallow. Resultado: o array em memória fica alinhado com o que foi persistido. O jeito é ligeiramente redundante (chama buildFluxObjectClearOnExecution pra todos, quando só os fluxObjects com flag interessam), mas o custo é baixo e a lógica fica centralizada em uma helper única.

🎯 Por que chamar em todos?
A helper é pura e barata. Chamar em todos e testar o resultado é mais simples que ter dois passos (filtrar + aplicar). O custo é uma call de function por node.
📎 Merge shallow
data: { ...nd.data, ...reset } — spread merge. Se reset tem { entries: [] }, sobrescreve data.entries. Se tem userSessionsChat: [...], sobrescreve inteiro (não faz deep merge).
⚠️ Redundância com D3 do worker
Quando o worker rodar esse fluxObject depois, persistNodeSuccess pode regravar. Se o worker não respeitar o reset e regravar entries velhas, o banco volta pro estado sujo. Sem contract explícito — só correto por convenção.
🔧 buildFluxObjectClearOnExecution é chamada 2x
Uma vez em D (pra montar patch pro persist), uma vez aqui em E (pra montar patch pro merge). Chamada é idempotente e barata — helper pura.
Resumo — o que sai de 1.5b:
• updatedFlows mutado: fluxObject com clearOnExecution ligado têm data.entries = [] (e opcionalmente data.userSessionsChat re-mapeado)
• Banco atualizado: mesmas mudanças persistidas via flow_nodes ou flow_version_history
• Session state deletado: pra fluxObjects chat/session-enabled, rows relevantes em session_state_entry apagadas
• I/O: 1 DELETE (chat/session) + 1 UPDATE por node com flag — em série (sem batch)
Observações para migração:
• As helpers (isFluxObjectClearOnExecution, fluxObjectPersistsEntries, buildFluxObjectClearOnExecution) são funções puras em node-output-reset.ts — replicáveis 1:1 no worker.
• sessionStateService.clear depende do Postgres — se o worker precisar limpar, precisa: (a) fazer round-trip pro backend, ou (b) receber conexão pra tabela session_state_entry.
• persistNodeDataToLiveRow é write-through: se o worker rodar isso, precisa ter as mesmas duas branches (live vs version-history) e o mesmo comportamento log-only-catch.
• A "reaplicação em memória" (E) só faz sentido enquanto o loop de execução compartilha memória. No worker, a versão canônica dos nodes viria dos start-args — o backend teria que reset antes de dar start no workflow.
• Prioridade média-alta: chats sem clearOnExecution respeitado ficariam com histórico eterno, o que quebra semântica de vários agents.
• Watch out: os outros types com clearOnExecution (fluxBox, libraryNode) são tratados no 1.7a com lógica diferente — não misturar!

Passo 1.5b — Reset de fluxObject com clearOnExecution

Bloco em flux.service.ts:2525-2558. Para todo node fluxObject com data.clearOnExecution truthy, executa 3 ações. Primeiro, limpa session state no Postgres se for chat ou session-enabled. Segundo, persiste o reset na linha live do node. Terceiro, reaplica o reset em memória em updatedFlows.
Em resumo — o que esse passo faz
  • Localiza os fluxObject com flag ligada. updatedFlows.filter(isFluxObjectClearOnExecution). É um helper puro em node-output-reset.ts:137-143 que testa node.type === 'fluxObject' && Boolean(node.data.clearOnExecution). Se não há nenhum, o bloco todo é pulado.
  • Loop com 2 side effects por node. Para cada nodeToClear, testa fluxObjectPersistsEntries(node). Devolve true se data.chat === true ou data.sessionEnabled === true. Se sim, chama sessionStateService.clear, que faz DELETE das linhas daquele scope no Postgres.
  • Persiste o reset em curso. Chama persistNodeDataToLiveRow passando buildFluxObjectClearOnExecution(node). Resolve para { entries: [] } por default. Ou para estrutura complexa com userSessionsChat quando há sessão selecionada não-default. Grava em flow_version_history (se versionado) ou direto em flow_nodes.
  • Reaplica em memória em updatedFlows. Depois do loop, updatedFlows.map re-executa buildFluxObjectClearOnExecution em todos os nodes, não só nos "clear". Se o resultado não é vazio (só volta não vazio para fluxObject com flag), faz spread merge. O array em memória fica alinhado com o que foi gravado.
  • Duas fontes de verdade em sync (banco e memória). O design é complexo (grava e depois reaplica em memória), mas garante que quem lê o node dali para frente vê o estado limpo. Quem consulta o banco também.
Contexto. clearOnExecution é opt-in por node. O usuário liga no editor para dizer que a cada execução o histórico deve ser esquecido. Sem esse mecanismo, chats acumulam indefinidamente entre execuções.

Propósito. Identificar nodes do tipo fluxObject que têm o flag clearOnExecution ligado. É a porta de entrada desse bloco. Se o filter devolve array vazio, todo o restante é pulado.
Em resumo. Uma verificação enxuta. É do tipo fluxObject? Tem clearOnExecution truthy? A verificação usa Boolean() porque clearOnExecution pode chegar como undefined (falso), {} (objeto vazio, truthy) ou { campo: true } (truthy). Um objeto vazio ainda dispara o clear. Faz sentido no domínio. Se o usuário atribuiu o campo, mesmo vazio, é opt-in explícito. Existem outros types (fluxBox, libraryNode) que também usam clearOnExecution, mas com semântica diferente. São tratados no passo 1.7a. Só o fluxObject tem essa lógica especial de session state mais persist.

🎯 Por que Boolean()?
data.clearOnExecution pode ser undefined, um objeto {} ou { field: true }. Boolean({}) = true. Objeto vazio é truthy em JavaScript. Mesmo config vazia dispara o clear.
📎 fluxObject versus fluxBox e libraryNode
Todos podem ter clearOnExecution. Só fluxObject tem session state persistente (chat entries). Os outros têm apenas output fields simples (tratados no passo 1.7a).
🔧 Generic T
Signature <T extends { type?: string; data?: Record<string, any> }>. Aceita qualquer objeto que tenha type e data. Não amarra numa entidade específica.

🎯 resolveSessionKey normaliza
resolveSessionKey('') retorna 'default'. O trim mais fallback é feito dentro do serviço. buildNodeScopeId(flowId, nodeId) = `${flowId}:${nodeId}`. Concatenação simples com :.
⚠️ Falha propaga no fluxo
O await aqui está dentro do try principal do apiV2. Se falha, propaga ao catch geral e a execução inteira falha. Não há retry ou soft-fail. O clear é hard-required.
⚠️ ownerUserId opcional no where
Se user?.id vem undefined, o where não filtra por owner. Deleta cross-user. É seguro apenas porque, na prática, user sempre vem preenchido nessa altura (validado antes).
🔧 Tipos de scope
SessionScopeType = 'chat' | 'object' | 'memory' | 'counter'. Aqui usa só chat. O object é usado em clearObjects (1.7b). Cada scope tem semântica diferente, mas a mesma tabela.
D persistNodeDataToLiveRow + buildFluxObjectClearOnExecution
flux.service.ts:2543-2548, 2235-2262 + node-output-reset.ts:151-169
await this.persistNodeDataToLiveRow(flowId, nodeId, buildFluxObjectClearOnExecution(node), flowVersionHistoryId)
Propósito. Grava no Postgres o reset. É um patch parcial do data desse node. O canvas do frontend reflete imediatamente que aquele fluxObject foi zerado. Sem esse write, o banco continuaria com o estado antigo até o persistNodeSuccess do worker regravar.
Em resumo. O helper buildFluxObjectClearOnExecution monta o patch que vai ao banco. Tem dois modos. Se selectedChat === 'default' ou não há userSessionsChat, o patch é { entries: [] }. Só zera as entries. Se tem sessão nomeada não-default, o patch é mais complexo. { entries: [], userSessionsChat: [...map que zera entries da sessão ativa] }. Preserva as outras sessões e limpa a selecionada. Depois, persistNodeDataToLiveRow aplica esse patch. Se a execução é versionada (flowVersionHistoryId presente), atualiza o snapshot do version history. Caso contrário, atualiza a linha live em flow_nodes. Bug em falha. Há catch dentro do próprio persist. Registra o erro, mas não propaga. A execução prossegue mesmo se o write falha. O banco pode ficar dessincronizado com a memória se algo dá errado aqui, mas a execução em si continua.

🎯 Por que 2 modos no patch?
selectedChat = 'default'. O usuário está no chat padrão. Só limpa entries. Não há userSessionsChat a modificar. Sessão nomeada. Tem várias sessions no array. Só zera as entries da ativa, preservando as outras.
📎 Docstring do persistNodeDataToLiveRow
"Persist a node's run-time data to the live flow JSON so the canvas reflects it. Used for values the worker never writes back (persistNodeSuccess): a data-input node's resolved value, and the entries a Small Memory node drops at the start of a clear-on-execution run."
⚠️ Log-only catch. Sync silencioso
Se o UPDATE falha (deadlock, connection dropped), o log é registrado, mas a execução continua. O banco fica dessincronizado com a memória temporariamente, até o próximo persist regravar.
🔧 Métodos do flowNodeService
updateSingleNodeData(flowId, nodeId, patch). Update JSONB merge em flow_nodes.data. updateSingleNodeDataInHistory(historyId, nodeId, patch). Mesmo, mas no snapshot do version history.
E Reaplica em memória via updatedFlows.map
flux.service.ts:2551-2557
updatedFlows = updatedFlows.map(nd => { const reset = buildFluxObjectClearOnExecution(nd); ... });
Propósito. Reaplica o reset em memória em todos os nodes de updatedFlows. Só volta patch não vazio para os fluxObject com flag. Os outros retornam sem alteração. Sincroniza memória e banco.
Em resumo. Depois de gravar os resets no banco, o array em memória updatedFlows ainda está com o estado antigo. O loop anterior só escreveu no Postgres. Esta segunda passada, um .map, chama buildFluxObjectClearOnExecution para cada node do array. O helper devolve {} se o node não é fluxObject com flag. Devolve o patch caso contrário. Se veio {}, retorna o node inalterado. Se veio patch não vazio, faz { ...nd, data: { ...nd.data, ...reset } }. Merge shallow. Resultado. O array em memória fica alinhado com o que foi persistido. O padrão é ligeiramente redundante. Chama buildFluxObjectClearOnExecution para todos, quando só os fluxObjects com flag interessam. O custo é baixo. A lógica fica centralizada num helper único.

🎯 Por que chamar em todos?
O helper é puro e barato. Chamar em todos e testar o resultado é mais simples que ter dois passos (filtrar mais aplicar). O custo é uma chamada de função por node.
📎 Merge shallow
data: { ...nd.data, ...reset }. Spread merge. Se reset tem { entries: [] }, sobrescreve data.entries. Se tem userSessionsChat: [...], sobrescreve inteiro (não faz deep merge).
⚠️ Redundância com D3 do worker
Quando o worker executar esse fluxObject depois, persistNodeSuccess pode regravar. Se o worker não respeita o reset e regrava entries antigas, o banco volta ao estado sujo. Não há contrato explícito. Só é correto por convenção.
🔧 buildFluxObjectClearOnExecution é chamado 2x
Uma vez em D (para montar o patch do persist). Uma vez aqui em E (para montar o patch do merge). A chamada é idempotente e barata. Helper puro.
Resumo. O que sai de 1.5b:
updatedFlows mutado. fluxObject com clearOnExecution ligado têm data.entries = []. Opcionalmente, data.userSessionsChat re-mapeado.
Banco atualizado. Mesmas mudanças persistidas via flow_nodes ou flow_version_history.
Session state deletado. Para fluxObjects chat ou session-enabled, linhas relevantes em session_state_entry apagadas.
I/O. 1 DELETE (chat ou session) mais 1 UPDATE por node com flag. Em série, sem batch.
Observações para migração:
Os helpers (isFluxObjectClearOnExecution, fluxObjectPersistsEntries, buildFluxObjectClearOnExecution) são funções puras em node-output-reset.ts. Replicáveis 1 para 1 no worker.
sessionStateService.clear depende do Postgres. Se o worker precisa limpar, precisa fazer round-trip ao backend ou receber conexão para a tabela session_state_entry.
persistNodeDataToLiveRow é write-through. Se o worker executa isso, precisa ter as mesmas duas branches (live versus version-history) e o mesmo comportamento log-only-catch.
A reaplicação em memória (E) só faz sentido enquanto o loop de execução compartilha memória. No worker, a versão canônica dos nodes viria dos start-args. O backend teria que fazer o reset antes de dar start no workflow.
Prioridade média-alta. Chats sem clearOnExecution respeitado ficariam com histórico permanente. Quebra a semântica de vários agentes.
Atenção. Os outros types com clearOnExecution (fluxBox, libraryNode) são tratados no 1.7a com lógica diferente. Não misturar.

Passo 2.2 — Variáveis mutáveis de execução

Bloco em flux.service.ts:3146-3197. Declara todo o estado in-memory que o loop principal da Fase 3 muta a cada iteração. Cópia dos nós, schema de substituição, entrada do usuário, sets de progresso, flags de parada e setup de cancelamento. É onde a RAM cresce em execuções grandes.
Em resumo — o que esse passo faz
  • Abre a mesa de trabalho da execução. Cria as três estruturas centrais que os handlers manipulam o tempo todo. myUpdatedNodes (cópia viva dos nós). myTexts (coleção de outputs textuais). nodeSubstitutionSchema (dicionário {{label}} → valor). É a principal fonte de pressão de RAM em execuções grandes.
  • Formata a entrada do usuário como chat message. Pega o primeiro variableInputs[0] do request e empacota como {role:'user', content, timestamp}. Fica pronto para prependar no histórico antes de despachar para o LLM. Se veio arquivo, cola a URL no content com \n.
  • Instala os trackers de progresso. processedNodeIds (quais nós já rodaram). lastExecutedNodeId (para saber onde cancelar). idx (contador de debug). scheduledId (variável de controle do while; quando vem null, o loop encerra).
  • Prepara três botões de emergência. As flags stoppedByLoopBehavior, stoppedByNodeFailure e stoppedByCancel começam false. Podem ser ativadas durante a execução para indicar por que o loop parou antes do fim natural.
  • Configura o cancelamento. Decide se a execução deve escutar cancel (sub-runs herdam do pai). Resolve a cancelRunKey. Faz o único I/O do passo. Um await no featureFlagsService para descobrir se o cancel in-flight (interromper nó no meio) está ligado.
  • Saída. Cerca de 13 variáveis no escopo do try do apiV2(). Capturadas por closure pelos handlers da Fase 3. É o maior blocker para migrar handlers para o worker. Quase tudo aqui é estado mutado por closure.
Contexto. A maioria dessas variáveis existe porque o loop mistura orquestração (scheduler) com estado do domínio (nós atualizados, tokens gastos, etc.). Cada handler da Fase 3 pode ler ou mutar qualquer uma delas. Este é o principal blocker para migrar handlers para o worker. O worker não tem acesso a nada disso. Recebe cada nó já pré-substituído e retorna output puro.

A myUpdatedNodes + myTexts + nodeSubstitutionSchema
flux.service.ts:3146-3152
let myUpdatedNodes = [...newFlows]; let myTexts = []; let nodeSubstitutionSchema = generateSchemaFromNodes(myUpdatedNodes);
Propósito. Estado central da execução. A "verdade viva" dos nós enquanto o loop roda. myUpdatedNodes começa como cópia rasa do array preparado nas Fases 1. Cada handler que grava output muta esse array. nodeSubstitutionSchema é o mapa {{label}} → valor que applySubstitutionToObject usa em cada iteração.
Em resumo. Este bloco é a mesa de trabalho onde o agente monta tudo. Antes de executar nó por nó, o backend abre três estruturas na memória. Cópia da lista de nós, atualizada a cada saída (o myUpdatedNodes). Coleção vazia para acumular o texto que os nós gerarem (o myTexts). Um dicionário rápido de referências (quem responde por {{label}}, quem responde por {{nodeId}}), que é o schema de substituição. Todo handler da Fase 3 manipula essas três estruturas o tempo todo. É onde a RAM cresce em agentes grandes. Esse estado vivo cresce junto com previewResponses, contentData e streams parciais.

⚠️ Fonte principal de pressão de RAM
O myUpdatedNodes carrega todo o node.data. Inclui previewResponses (10 últimas respostas), contentData, text, streams parciais. A cada iteração, handlers pesados podem clonar ou expandir. Em agente com 50 text-gen e 20 arrayNode loops, chega a centenas de MB. Ver [[project_jsonb_fat_fields]].
🎯 Por que let e não const?
myUpdatedNodes e nodeSubstitutionSchema são reatribuídos em alguns pontos do loop, não só mutados. Exemplo. Dentro do arrayNode, newNodes = [...myUpdatedNodes] e depois myUpdatedNodes = newNodes. O callback onMutateSchema também reatribui o schema inteiro.

B object (user input formatado)
flux.service.ts:3157-3177
const object = [{ role: 'user', content: inputText + inputFileUrl, timestamp: ... }]
Propósito. Empacota a entrada do usuário no shape de chat message ({role, content, timestamp}). Fica pronta para ser prependada no histórico de chat quando a execução começa. Só o primeiro variableInput é considerado.
Em resumo. Esta etapa é o carteiro. Pega o que o usuário digitou no request e transforma em uma mensagem no formato que o LLM entende ({role:'user', content:'...', timestamp:'...'}). Se veio anexo, cola a URL no final do texto com um \n. Essa mensagem é prependada no histórico do chat antes do despacho para o modelo. Só olha o primeiro item de variableInputs. Se o cliente mandou vários, os outros ficam ignorados aqui e só chegam nos handlers específicos depois.
const object = [{ role: 'user', content: body?.variableInputs?.[0]?.inputText + (body?.variableInputs?.[0]?.inputFileUrl ? `\n${...inputFileUrl}` : ''), timestamp: new Date().toLocaleString('en-US', { /* 7 opts */ }), }];
↓
Uso downstream
Consumido pelos handlers de chat (fluxObject e commandTextNode com chat=true) para prependar o turno do usuário no entries[] antes de enviar ao LLM.
⚠️ Só variableInputs[0]
Se o request mandar múltiplos inputs (chat multi-turno, múltiplos arquivos), só o índice 0 vira object. Os demais só chegam via body.variableInputs nos handlers específicos.
🎯 Timestamp em en-US
Formato. M/D/YYYY, H:MM:SS AM/PM. Salvo direto no entries do chat sem normalizar para ISO. Se o cliente ou log downstream tenta parsear como ISO, quebra.
🔧 inputFileUrl concat
Se veio arquivo, a URL é anexada ao content com \n. O LLM tem que interpretar isso como "aqui está o link do arquivo" sem hint estruturado. Simples e frágil. Melhor seria content: [{type:'text'}, {type:'file_url'}] multimodal.
C processedNodeIds + lastExecutedNodeId + idx + scheduledId
flux.service.ts:3179, 3183, 3196-3197
const processedNodeIds = new Set<string>(); let lastExecutedNodeId = null; let idx = 0; let scheduledId: string | null;
Propósito. Trackers de progresso do loop. processedNodeIds é o histórico "quem já rodou" (usado para dedupe e skip). lastExecutedNodeId serve para o finishCancelledNode. idx é contador visual (log/debug). scheduledId é a variável de controle do while.
Em resumo. Este bloco é o registro de presença do loop. processedNodeIds é o Set que anota quem já rodou. Evita rodar duas vezes em um subrun. lastExecutedNodeId é o último a ser chamado. Importante para saber onde parar se o usuário cancelar no meio. idx é apenas um contador de posição para debug. scheduledId é a variável-chave. O while lê essa variável a cada volta. Enquanto o scheduler devolve um id, o loop continua. Quando vem null, a execução acaba. Junto com totalTokensUsed e totalCost, declarados antes, formam o painel de instrumentos da execução.

D stoppedByLoopBehavior + stoppedByNodeFailure + stoppedByCancel
flux.service.ts:3180-3182
let stoppedByLoopBehavior = false; let stoppedByNodeFailure = false; let stoppedByCancel = false;
Propósito. Três flags booleanas não exclusivas que indicam por que o loop parou antes do fim natural. Usadas na finalização para reportar status correto ao caller e aos logs.
Em resumo. São três botões de emergência. Começam desligados e podem ser ativados durante a execução. O primeiro (stoppedByLoopBehavior) é o arrayNode sinalizando "atingi a condição de parada configurada". O segundo (stoppedByNodeFailure) é um handler que lançou erro fatal e a execução não pode continuar. O terceiro (stoppedByCancel) é o usuário disparando o cancel pela API. Nenhum é exclusivo. Teoricamente os três podem virar true na mesma iteração. No fim, quem reporta o status é a última flag ativada. O ideal seria trocar essas três variáveis por um único enum status. Refactor futuro.
🚩 Quem seta cada flag
1 stoppedByLoopBehavior arrayNode com stopOn* config
2 stoppedByNodeFailure handler lança erro fatal (ver 3.8)
3 stoppedByCancel usuário cancelou a execução (3.5 cancel check)
↓
Consumo
Cada uma gera break no while ou skip. Na finalização, o runLogCollector.finalize() recebe status derivado dessas flags.
🎯 Não exclusivas
Teoricamente as três podem virar true na mesma iteração (um handler falha e, ao mesmo tempo, o usuário cancela dentro de um arrayNode). A prioridade no report é a última ativada. Não há tie-break explícito.
⚠️ 3 booleans em vez de 1 enum
status: 'ok' | 'loop' | 'failure' | 'cancel' resolveria a ambiguidade e reduziria a superfície de bugs de "esqueci de setar essa flag". Refactor trivial. Quebra call-sites que verificam individualmente.
🔧 stoppedByCancel. Novo pós-doc
Introduzido junto com o feature flag NODE_CANCEL_IN_FLIGHT_FLAG. As outras duas vieram do doc original.
E Cancellation setup
flux.service.ts:3184-3194
const cancelWatchEnabled = shouldWatchCancellation({...}); const cancelRunKey = resolveCancelRunKey({...}); const inFlightEnabled = await featureFlagsService.isEnabled(NODE_CANCEL_IN_FLIGHT_FLAG);
Propósito. Configura o mecanismo de cancelamento. Decide se a execução deve escutar pedidos de cancel (não se aplica a sub-runs, por exemplo). Calcula a runKey que o cliente usa para solicitar cancel. Busca o feature flag para saber se o cancel in-flight (durante a execução de um nó) está ativo.
Em resumo. O backend monta o botão de emergência da execução. Primeiro pergunta se vale a pena escutar cancel para este tipo de execução. Sub-runs não escutam. Quem escuta é o pai. Depois calcula qual é a chave que o cliente vai usar para pedir cancel. Se é sub-run, herda a do pai. Cancelar o pai cancela os filhos automaticamente. Por último, faz um await no serviço de feature flag para descobrir se o modo agressivo está ligado. Esse modo interrompe um nó no meio da execução, não só entre nós. É o único I/O deste passo inteiro. Se o feature flag service ficar lento, atrasa toda execução de agente.

Retorna false se é sub-run (fluxBox ou libraryNode dentro de outra execução) ou se o runType não suporta cancel. Sub-runs herdam o watch do pai.

E3 await featureFlagsService.isEnabled(NODE_CANCEL_IN_FLIGHT_FLAG)
Único await de I/O em toda 2.2. Consulta o service de feature flags. Se true, o cancel pode interromper um nó no meio da execução. Se false, só entre nós.
flux.service.ts:3192-3194
🎯 NODE_CANCEL_IN_FLIGHT_FLAG
Feature flag experimental que ativa o cancelWatch por nó. Sem ela, o cancel só é checado entre iterações do while. Não interrompe um nó em execução. Com ela, cada nó ganha um cancelWatch que verifica periodicamente e pode abortar.
⚠️ Fetch de feature flag é blocking
É um await no meio do setup do loop. Se o serviço de feature flag ficar lento, atrasa toda execução de agente. Vale cachear o valor por curta janela ou pré-resolver no boot.
🔧 Herança de cancel
fluxBox e libraryNode passam parentCancelRunKey ao chamar apiV2() para o sub-flow. Cancel do pai equivale ao cancel do filho porque compartilham a mesma key.
Resumo — o que sai de 2.2.
• myUpdatedNodes, myTexts, nodeSubstitutionSchema. Estado central do domínio.
• object. Mensagem do usuário formatada para chat.

Observações para migração.
• Este é o maior blocker para o worker. Quase tudo aqui é estado mutado por closure. O worker precisa receber cada nó pré-substituído e devolver output puro. myUpdatedNodes, nodeSubstitutionSchema e myTexts ficam obrigatoriamente no backend.
• O myUpdatedNodes é o principal driver da pressão de RAM em execuções grandes (ver [[project_jsonb_fat_fields]]). Migrar handlers pesados (textGenerator, imageGenerator, sqlQuerier) para o worker não resolve. O problema é o schema in-memory, não o handler.
• onUpdateTokens, onMutateSchema e onMutateObjectCallerData são callbacks que dependem de closure. No worker, isso vira await http.post('/worker/charge-tokens', ...). Um round-trip por evento.
• Idealmente, o 2.2 vira uma classe RunState encapsulada. Handlers recebem e retornam via métodos explícitos em vez de mutar variáveis livres. Trabalho grande. Destrava o worker.
• inFlightEnabled deveria ser buscado antes do loop (já é) com cache. Não é caso de latência crítica hoje.
• As flags de stop viram um enum runStatus em um refactor futuro. Semântica melhor e tie-break explícito.

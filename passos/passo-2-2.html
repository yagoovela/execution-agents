Step 2.2 — Mutable execution variables

Block at flux.service.ts:3146-3197. Declares all the in-memory state that the Phase 3 main loop mutates on every iteration. Node copy, substitution schema, user input, progress sets, stop flags and cancellation setup. This is where RAM grows in large executions.
In summary — what this step does
  • Opens the execution workbench. Creates the three central structures that handlers manipulate all the time. myUpdatedNodes (live copy of nodes). myTexts (collection of textual outputs). nodeSubstitutionSchema ({{label}} → value dictionary). This is the main source of RAM pressure in large executions.
  • Formats user input as chat message. Takes the first variableInputs[0] from the request and packages it as {role:'user', content, timestamp}. Ready to be prepended to the history before dispatching to the LLM. If a file came in, appends the URL to content with \n.
  • Installs the progress trackers. processedNodeIds (which nodes already ran). lastExecutedNodeId (to know where to cancel). idx (debug counter). scheduledId (control variable of the while; when it returns null, the loop ends).
  • Prepares three emergency buttons. The flags stoppedByLoopBehavior, stoppedByNodeFailure and stoppedByCancel start false. They can be activated during execution to indicate why the loop stopped before the natural end.
  • Sets up cancellation. Decides whether the execution should listen for cancel (sub-runs inherit from the parent). Resolves the cancelRunKey. Does the only I/O of this step. An await on featureFlagsService to find out whether in-flight cancel (interrupt a node midway) is on.
  • Output. About 13 variables in the try scope of apiV2(). Captured by closure by the Phase 3 handlers. This is the biggest blocker for migrating handlers to the worker. Almost everything here is closure-mutated state.
Context. Most of these variables exist because the loop mixes orchestration (scheduler) with domain state (updated nodes, spent tokens, etc). Every Phase 3 handler can read or mutate any of them. This is the main blocker for migrating handlers to the worker. The worker has no access to any of it. It receives each node already pre-substituted and returns pure output.

A myUpdatedNodes + myTexts + nodeSubstitutionSchema
flux.service.ts:3146-3152

Purpose. Central execution state. The "living truth" of the nodes while the loop runs. myUpdatedNodes starts as a shallow copy of the array prepared in Phase 1. In summary. This block is the workbench where the agent assembles everything. Before executing node by node, the backend opens three memory structures. It is where RAM grows in large agents. This live state grows along with previewResponses, contentData and partial streams.

⚠️ Main source of RAM pressure
myUpdatedNodes carries all of node.data. Includes previewResponses (last 10 responses), contentData, text, partial streams. On every iteration, heavy handlers can clone or expand. In an agent with 50 text-gens and 20 arrayNode loops, it reaches hundreds of MB. See [[project_jsonb_fat_fields]].
🎯 Why let and not const?
myUpdatedNodes and nodeSubstitutionSchema are reassigned at some points in the loop, not just mutated. Example. Inside arrayNode, newNodes = [...myUpdatedNodes] then myUpdatedNodes = newNodes. The onMutateSchema callback also reassigns the whole schema.
🔧 newFlows. Origin
It is the updatedFlows from Phase 1 (after 1.6 and 1.7) renamed to newFlows somewhere above line 3146. Already includes all chat, object and Google token hydrations.
B object (formatted user input)
flux.service.ts:3157-3177
const object = [{ role: 'user', content: inputText + inputFileUrl, timestamp: ... }]
Purpose. Packages the user input in chat message shape ({role, content, timestamp}). Ready to be prepended to the chat history when execution begins. Only the first variableInput is considered.
In summary. This step is the mailman. Takes what the user typed in the request and turns it into a message in the format the LLM understands ({role:'user', content:'...', timestamp:'...'}). If a file came in, appends the URL at the end of the text with a \n. This message is prepended to the chat history before dispatching to the model. Only looks at the first item of variableInputs. If the client sent several, the rest are ignored here and only reach the specific handlers later.
const object = [{ role: 'user', content: body?.variableInputs?.[0]?.inputText + (body?.variableInputs?.[0]?.inputFileUrl ? `\n${...inputFileUrl}` : ''), timestamp: new Date().toLocaleString('en-US', { /* 7 opts */ }), }];
↓
Downstream usage
Consumed by chat handlers (fluxObject and commandTextNode with chat=true) to prepend the user's turn in entries[] before sending to the LLM.
⚠️ Only variableInputs[0]
If the request sends multiple inputs (multi-turn chat, multiple files), only index 0 becomes object. The others only reach the specific handlers via body.variableInputs.
🎯 Timestamp in en-US
Format. M/D/YYYY, H:MM:SS AM/PM. Saved straight into the chat entries without ISO normalization. If the client or a downstream log tries to parse it as ISO, it breaks.
🔧 inputFileUrl concat
If a file came in, the URL is appended to content with \n. The LLM has to interpret this as "here is the file link" without a structured hint. Simple and fragile. Better would be multimodal content: [{type:'text'}, {type:'file_url'}].

Purpose. Loop progress trackers. processedNodeIds is the "who has already run" history (used for dedupe and skip). lastExecutedNodeId serves finishCancelledNode. idx is a visual counter (log/debug). scheduledId is the control variable of the while.
In summary. This block is the loop's attendance sheet. processedNodeIds is the Set that records who has already run. Prevents running twice in a subrun. lastExecutedNodeId is the last one to be called. Important to know where to stop if the user cancels midway. idx is just a position counter for debug. scheduledId is the key variable. The while reads it on every turn. While the scheduler returns an id, the loop keeps going. When null comes back, execution ends. Together with totalTokensUsed and totalCost, declared earlier, they form the execution instrument panel.

D stoppedByLoopBehavior + stoppedByNodeFailure + stoppedByCancel
flux.service.ts:3180-3182
let stoppedByLoopBehavior = false; let stoppedByNodeFailure = false; let stoppedByCancel = false;
Purpose. Three non-exclusive boolean flags that indicate why the loop stopped before its natural end. Used at finalization to report the correct status to the caller and to the logs.
In summary. Three emergency buttons. They start off and can be flipped during execution. The first (stoppedByLoopBehavior) is the arrayNode signaling "I hit the configured stop condition". The second (stoppedByNodeFailure) is a handler that threw a fatal error and the execution cannot continue. The third (stoppedByCancel) is the user firing cancel via the API. None is exclusive. In theory all three can turn true on the same iteration. In the end, the last flag activated is the one reported. Ideally, these three variables would be replaced by a single status enum. Future refactor.
🚩 Who sets each flag
1 stoppedByLoopBehavior arrayNode with stopOn* config
2 stoppedByNodeFailure handler throws fatal error (see 3.8)
3 stoppedByCancel user cancelled the execution (3.5 cancel check)
↓
Consumption
Each one triggers break in the while or a skip. At finalization, runLogCollector.finalize() receives status derived from these flags.
🎯 Non-exclusive
In theory all three can become true on the same iteration (a handler fails and, at the same time, the user cancels inside an arrayNode). Priority in the report is the last one activated. There is no explicit tie-break.
⚠️ 3 booleans instead of 1 enum
status: 'ok' | 'loop' | 'failure' | 'cancel' would resolve the ambiguity and reduce the "forgot to set this flag" bug surface. Trivial refactor. Breaks call-sites that check individually.
🔧 stoppedByCancel. Added post-doc
Introduced together with the feature flag NODE_CANCEL_IN_FLIGHT_FLAG. The other two came from the original doc.
E Cancellation setup
flux.service.ts:3184-3194
const cancelWatchEnabled = shouldWatchCancellation({...}); const cancelRunKey = resolveCancelRunKey({...}); const inFlightEnabled = await featureFlagsService.isEnabled(NODE_CANCEL_IN_FLIGHT_FLAG);
Purpose. Configures the cancellation mechanism. Decides whether the execution should listen for cancel requests (does not apply to sub-runs, for instance). Computes the runKey the client uses to request cancel. Fetches the feature flag to know whether in-flight cancel (during a node's execution) is on.
In summary. The backend wires up the execution's emergency button. First it asks whether it is worth listening for cancel for this run type. Sub-runs do not listen. The parent does. Then it computes which key the client will use to request cancel. If it is a sub-run, it inherits the parent's key. Cancelling the parent cancels children automatically. Finally, it awaits the feature flag service to find out whether aggressive mode is on. This mode interrupts a node mid-execution, not just between nodes. It is the only I/O of this entire step. If the feature flag service is slow, every agent execution is delayed.
E1 shouldWatchCancellation({ runType, isNestedRun })
Returns false if it is a sub-run (fluxBox or libraryNode inside another execution) or if the runType does not support cancel. Sub-runs inherit the parent's watch.

E3 await featureFlagsService.isEnabled(NODE_CANCEL_IN_FLIGHT_FLAG)
Only I/O await in the whole 2.2. Queries the feature flags service. If true, cancel can interrupt a node mid-execution. If false, only between nodes.
flux.service.ts:3192-3194
🎯 NODE_CANCEL_IN_FLIGHT_FLAG
Experimental feature flag that turns on the per-node cancelWatch. Without it, cancel is only checked between while iterations. Does not interrupt a running node. With it, each node gets a cancelWatch that checks periodically and can abort.
⚠️ Feature flag fetch is blocking
It is an await in the middle of the loop setup. If the feature flag service is slow, every agent execution is delayed. Worth caching the value for a short window or pre-resolving at boot.
🔧 Cancel inheritance
fluxBox and libraryNode pass parentCancelRunKey when calling apiV2() for the sub-flow. Parent cancel is equivalent to child cancel because they share the same key.

Migration notes.
• This is the biggest blocker for the worker. Almost everything here is closure-mutated state. The worker needs to receive each pre-substituted node and return pure output. myUpdatedNodes, nodeSubstitutionSchema and myTexts have to stay on the backend.
• myUpdatedNodes is the main driver of RAM pressure in large executions (see [[project_jsonb_fat_fields]]). Migrating heavy handlers (textGenerator, imageGenerator, sqlQuerier) to the worker does not solve it. The problem is the in-memory schema, not the handler.
• onUpdateTokens, onMutateSchema and onMutateObjectCallerData are callbacks that depend on closure. On the worker, this becomes await http.post('/worker/charge-tokens', ...). One round-trip per event.
• Ideally, 2.2 becomes an encapsulated RunState class. Handlers receive and return via explicit methods instead of mutating free variables. Big work. Unblocks the worker.
• inFlightEnabled should be fetched before the loop (it already is) with caching. Not a critical latency case today.
• Stop flags become a runStatus enum in a future refactor. Better semantics and explicit tie-break.

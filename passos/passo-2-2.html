Passo 2.2 — Variáveis mutáveis de execução

Bloco em flux.service.ts:3146-3197. Declara todo o estado in-memory que o loop principal da Fase 3 vai mutar em cada iteração: cópia dos nós, schema de substituição, input do user, sets de progresso, flags de parada e setup de cancelamento. É onde a RAM cresce em runs grandes.
Em resumo — o que esse passo faz
  • Abre a "mesa de trabalho" do run: cria as três estruturas centrais que os handlers vão mexer o tempo todo — myUpdatedNodes (cópia viva dos nós), myTexts (sacola de outputs textuais) e nodeSubstitutionSchema (o dicionário {{label}} → valor). É a principal fonte de pressure de RAM em runs grandes.
  • Formata o input do usuário como chat message: pega o primeiro variableInputs[0] do request, empacota como {role:'user', content, timestamp} pra ser prependado no histórico antes de despachar pra LLM. Se veio arquivo, cola a URL no content com \n.
  • Instala os "trackers de progresso": processedNodeIds (quem já rodou), lastExecutedNodeId (pra saber onde cancelar), idx (contador de debug) e scheduledId (variável de controle do while — quando vem null, loop encerra).
  • Prepara três "botões de emergência": flags stoppedByLoopBehavior, stoppedByNodeFailure, stoppedByCancel começam false e podem ser setadas durante o run pra indicar por que o loop parou antes do fim natural.
  • Configura o cancelamento: decide se este run deve escutar cancel (sub-runs herdam do pai), resolve a cancelRunKey e faz o único I/O deste passo — um await no featureFlagsService pra saber se cancel in-flight (interromper nó no meio) está ligado.
  • Saída: ~13 variáveis no escopo do try do apiV2(), capturadas por closure pelos handlers da Fase 3 — este é o maior blocker pra migrar handlers pro worker, porque quase tudo aqui é estado mutado por closure.
Contexto: a maioria dessas variáveis existem porque o loop mistura orquestração (scheduler) com estado do domínio (nodes atualizados, tokens gastos, etc.). Cada handler de Fase 3 pode ler ou mutar qualquer uma delas. Isso é o principal blocker pra migrar handlers pro worker — o worker não tem acesso a nada disso; recebe cada nó já pré-substituído e retorna output puro.

A myUpdatedNodes + myTexts + nodeSubstitutionSchema
flux.service.ts:3146-3152
let myUpdatedNodes = [...newFlows]; let myTexts = []; let nodeSubstitutionSchema = generateSchemaFromNodes(myUpdatedNodes);
Propósito: Estado central do run — a "verdade viva" dos nós enquanto o loop roda. myUpdatedNodes começa como cópia rasa do array preparado nas Fases 1 e é mutado a cada handler que grava output; nodeSubstitutionSchema é o mapa {{label}} → valor que applySubstitutionToObject usa em cada iteração.
Em resumo: pense nesse bloco como a mesa de trabalho onde o agente vai montar tudo. Antes de começar a executar nó por nó, o backend abre três "gavetas" na memória: uma cópia da lista de nós que vai sendo pintada de novo a cada saída (o myUpdatedNodes), uma sacolinha vazia pra ir juntando o texto que os nós gerarem (o myTexts), e um dicionário rápido de referências — quem responde por {{label}}, quem responde por {{nodeId}} — que é o schema de substituição. Todo handler da Fase 3 vai mexer nessas três coisas o tempo todo, e é justamente aqui que a RAM engorda em agentes grandes, porque esse "estoque vivo" cresce junto com previewResponses, contentData e streams parciais.

myUpdatedNodes e nodeSubstitutionSchema são reatribuídos em alguns pontos do loop (não só mutados). Ex.: dentro do arrayNode, newNodes = [...myUpdatedNodes] depois myUpdatedNodes = newNodes. O onMutateSchema callback também reatribui o schema inteiro.

B object (user input formatado)
flux.service.ts:3157-3177
const object = [{ role: 'user', content: inputText + inputFileUrl, timestamp: ... }]
Propósito: Empacotar o input do usuário no shape de chat message ({role, content, timestamp}) pra ser prependado no histórico de chat quando o run começa. Só o primeiro variableInput é considerado.
Em resumo: essa é a etapa do carteiro — pega o que o usuário digitou no request e transforma numa "carta" no formato que a LLM entende ({role:'user', content:'...', timestamp:'...'}). Se veio anexo, cola a URL no final do texto com um \n. É essa carta que vai ser prependada no histórico do chat antes de despachar pro modelo. Detalhe importante: ela só olha o primeiro item de variableInputs — se o cliente mandou vários, os outros ficam sendo ignorados aqui e só chegam nos handlers específicos mais tarde.
const object = [{ role: 'user', content: body?.variableInputs?.[0]?.inputText + (body?.variableInputs?.[0]?.inputFileUrl ? `\n${...inputFileUrl}` : ''), timestamp: new Date().toLocaleString('en-US', { /* 7 opts */ }), }];

Uso downstream
Consumido pelos handlers de chat (fluxObject + commandTextNode com chat=true) pra prependar o turno do user no entries[] antes de mandar pra LLM.
⚠️ Só variableInputs[0]
Se o request mandar múltiplos inputs (chat multi-turno, múltiplos arquivos), só o índice 0 vira object. Os demais só chegam via body.variableInputs nos handlers específicos.
🎯 Timestamp em en-US
Formato: M/D/YYYY, H:MM:SS AM/PM. Salvo direto no entries do chat sem normalizar pra ISO. Se o cliente/log downstream tenta parsear como ISO, quebra.
🔧 inputFileUrl concat
Se veio arquivo, a URL é apendada ao content com \n. LLM tem que interpretar isso como "aqui tá o link do arquivo" sem hint estruturado. Simples mas frágil — melhor seria content: [{type:'text'}, {type:'file_url'}] multimodal.
C processedNodeIds + lastExecutedNodeId + idx + scheduledId
flux.service.ts:3179, 3183, 3196-3197
const processedNodeIds = new Set<string>(); let lastExecutedNodeId = null; let idx = 0; let scheduledId: string | null;
Propósito: Trackers de progresso do loop. processedNodeIds é o histórico "quem já rodou" (usado pra dedupe/skip); lastExecutedNodeId serve pra finishCancelledNode; idx é contador visual (log/debug); scheduledId é a variável de controle do while.
Em resumo: aqui é o caderninho de presença do loop. processedNodeIds é o Set que anota quem já rodou (pra ninguém rodar duas vezes num subrun); lastExecutedNodeId é o "último a ser chamado" — importante pra saber onde parar caso o user cancele no meio; idx é só um contador de posição pra debug; e scheduledId é a variável-chave, a que o while lê a cada volta: enquanto o scheduler devolve um id, o loop continua; quando vem null, a festa acabou. Junto com totalTokensUsed/totalCost declarados lá em cima, formam o "painel de instrumentos" da execução.

D stoppedByLoopBehavior + stoppedByNodeFailure + stoppedByCancel
flux.service.ts:3180-3182
let stoppedByLoopBehavior = false; let stoppedByNodeFailure = false; let stoppedByCancel = false;
Propósito: 3 flags booleanas mutuamente não-exclusivas que indicam por que o loop parou antes do fim natural. Usadas na finalização pra reportar status corretos ao caller / logs.
Em resumo: são três botões de emergência que ficam desligados no começo e podem ser apertados durante o run. O primeiro (stoppedByLoopBehavior) é o arrayNode dizendo "olha, atingi minha condição de parada configurada"; o segundo (stoppedByNodeFailure) é um handler que estourou um erro fatal e não dá pra continuar; o terceiro (stoppedByCancel) é o user apertando "cancelar" pela API. Nenhum deles é exclusivo — teoricamente os três podem virar true na mesma iteração, e no fim quem reporta o status é a última flag setada. O ideal seria trocar essas três variáveis por um único enum status, mas isso é refactor pra depois.
🚩 Quem seta cada flag
1 stoppedByLoopBehavior arrayNode com stopOn* config
2 stoppedByNodeFailure handler lança erro fatal (ver 3.8)
3 stoppedByCancel user cancelou o run (3.5 cancel check)
↓
Consumo
Cada uma gera break no while ou skip. Na finalização, o runLogCollector.finalize() recebe status derivado dessas flags.
🎯 Não exclusivas
Teoricamente as 3 podem virar true na mesma iteração (um handler falha, ao mesmo tempo user cancela, dentro de um arrayNode). Prioridade no report é a última setada — não há tie-break explícito.
⚠️ 3 booleans em vez de 1 enum
status: 'ok' | 'loop' | 'failure' | 'cancel' resolveria a ambiguidade e reduziria a superfície de bugs de "esqueci de setar essa flag". Refactor trivial mas quebra call sites que checam individualmente.
🔧 stoppedByCancel — novo pós-doc
Introduzido junto com o feature flag NODE_CANCEL_IN_FLIGHT_FLAG. As outras 2 vieram do doc original.
E Cancellation setup
flux.service.ts:3184-3194
const cancelWatchEnabled = shouldWatchCancellation({...}); const cancelRunKey = resolveCancelRunKey({...}); const inFlightEnabled = await featureFlagsService.isEnabled(NODE_CANCEL_IN_FLIGHT_FLAG);
Propósito: Configurar o mecanismo de cancelamento. Decide se este run deve escutar pedidos de cancel (não vale pra sub-runs, por exemplo), calcula a runKey que o cliente vai usar pra pedir cancel, e busca o feature flag pra ver se o cancel in-flight (durante execução de um nó) está ativo.
Em resumo: aqui o backend monta o botão de pânico do run. Primeiro pergunta "vale a pena ficar de olho em cancel pra esse tipo de execução?" (sub-runs não escutam — quem escuta é o pai); depois calcula qual é a chave que o cliente vai usar pra pedir cancel (se é sub-run, herda a do pai — cancelar o pai cancela os filhos automaticamente, elegante); e por último faz um await no serviço de feature flag pra descobrir se o modo agressivo está ligado — o modo que interrompe um nó no meio da execução, não só entre nós. Esse é o único I/O desse passo inteiro, e se o feature flag service ficar lento, atrasa qualquer execução de agente.

E3 await featureFlagsService.isEnabled(NODE_CANCEL_IN_FLIGHT_FLAG)
Único await de I/O em toda 2.2. Consulta o service de feature flags. Se true, cancel pode interromper um nó no meio da execução; se false, só entre nós.
flux.service.ts:3192-3194
🎯 NODE_CANCEL_IN_FLIGHT_FLAG
Feature flag experimental que ativa o cancelWatch por nó. Sem ela, cancel só é checado entre iterações do while (não interrompe um nó em execução). Com ela, cada nó ganha um cancelWatch que checa periodicamente e pode abortar.
⚠️ Fetch de feature flag é blocking
É um await no meio do setup do loop. Se o service de feature flag ficar lento, atrasa toda execução de agente. Vale cachear o valor por curta janela ou pré-resolver no boot.
🔧 Herança de cancel
fluxBox/libraryNode passam parentCancelRunKey quando chamam apiV2() pro sub-flow. Cancel do parent = cancel do child porque compartilham a mesma key. Elegante.
Resumo — o que sai de 2.2:
• myUpdatedNodes · myTexts · nodeSubstitutionSchema — estado central do domínio
• object — mensagem do user formatada pra chat
• processedNodeIds · lastExecutedNodeId · idx · scheduledId — progresso
• 3 flags de stop
• cancelWatchEnabled · cancelRunKey · inFlightEnabled — cancellation
• I/O: 1 await (feature flag)
Observações para migração:
• Este é o maior blocker pra o worker: quase tudo aqui é estado mutado por closure. O worker precisa receber cada nó pré-substituído e devolver output puro — myUpdatedNodes, nodeSubstitutionSchema, myTexts ficam obrigatoriamente no backend.
• myUpdatedNodes é o principal driver da pressure de RAM em runs grandes (ver [[project_jsonb_fat_fields]]). Migrar handlers pesados (textGenerator, imageGenerator, sqlQuerier) pro worker não resolve isso — o problema é o schema in-memory, não o handler.
• onUpdateTokens/onMutateSchema/onMutateObjectCallerData são callbacks que dependem de closure. No worker isso vira await http.post('/worker/charge-tokens', ...) — 1 round-trip por evento.
• Idealmente 2.2 vira uma classe RunState encapsulada, e handlers recebem/retornam via metódos explícitos em vez de mutar variáveis livres. Trabalho grande mas destrava o worker.
• inFlightEnabled deveria ser fetch antes do loop (já é) mas com cache. Não é caso pra latência crítica hoje.
• As flags de stop viram um enum runStatus num refactor futuro — semântica melhor + tie-break explícito.

Passo 4.3 — flowLogsService.createLog()

Bloco em flux.service.ts:4802-4822. Serviço em flow_logs/flow_logs.service.ts. Faz INSERT em execution_logs (tabela persistida como flow_log pelo TypeORM). Grava o resultado final da execução: status, error, tokens, cost e run_type. Envolvido em try/catch para não derrubar quando o log falhar.
Em resumo — o que esse passo faz
  • É o registro contábil do agente. Cada execução vira uma linha em execution_logs (nome da tabela: flow_log). Resumo final do ocorrido, sem detalhes por nó.
  • Grava os campos essenciais. status, error_message, error_status_code, spent_tokens, cost, run_type (api, canvas, chatbot, batch, etc.), flowId e mcpTokenId quando a chamada veio via MCP.
  • Alimenta dashboards e billing. Analytics filtra por run_type. Billing soma cost por company. "Meus runs recentes" filtra por flowId. Toda leitura de log relacional passa por aqui.
  • Try/catch defensivo. Se o INSERT falhar (banco indisponível, timeout), o Winston registra log_creation_failed. A execução não derruba. Prefere sucesso sem log a execução falhada por causa de log.
  • Saída. Uma linha nova em execution_logs. Em caso raro, log Winston de falha. Nada mais. O retorno da API não usa o valor devolvido.
Contexto. Este é o log relacional da execução. Separado do space_run_logs, que é o JSONB hierárquico do RunLogCollector. Cada execução vira 1 linha aqui. Queries para dashboards, analytics e billing por account leem desta tabela.

⚠️ Falha silenciosa
Se o INSERT falhar, a execução ainda retorna sucesso para o cliente. O log fica perdido. Ocorre raramente. Pode gerar discrepâncias em relatórios (o cliente contabiliza 100 execuções, o dashboard mostra 95).
🔧 mcpTokenId
Preenchido apenas quando o request veio do endpoint MCP (Model Context Protocol). Rastreia qual token MCP disparou a execução. Serve para rate-limiting e billing por MCP client.

flow_logs/entities/flow_log.entity.ts
@Entity('flow_log') class FlowLog { id: uuid, flowId, status, error_message, spent_tokens: number, cost: number, run_type: enum, createdAt, updatedAt, ... }
Propósito. Entity TypeORM. O nome da tabela é flow_log (singular), embora o serviço se chame flowLogs. Colunas indexadas por flowId para queries do tipo "meus runs recentes". Uma linha por execução. PK sequencial.
Em resumo. Tabela clássica de audit trail. Cada linha é uma execução. As chaves de query são flowId (todas as execuções do flow), userId (indireto via flow.userId), run_type, status e faixa de createdAt. As colunas de billing (spent_tokens, cost) são number, não bigint. Basta para os volumes atuais. error_message é TEXT (comporta mensagens longas de LLM). error_status_code é string, não int. Decisão infeliz, mas funciona porque só é exibido em UI. Sem soft-delete. Os logs seguem retention até o TTL configurado no admin.

Observações para migração.
• Tabela relacional simples. Fácil de migrar. O worker pode gravar direto se conectar no mesmo Postgres.
• Try/catch defensivo é bom padrão. Manter.
• Status como string livre vira dívida técnica. Enum tipado ajudaria.
• Uma linha por execução é modelo escalável. Sem necessidade de refactor grande.
• Deve migrar cedo. O sistema depende para billing e analytics.

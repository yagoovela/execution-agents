Step 4.3 — flowLogsService.createLog()

Block in flux.service.ts:4802-4822. Service in flow_logs/flow_logs.service.ts. Does an INSERT in execution_logs (table persisted as flow_log by TypeORM). Writes the execution's final result: status, error, tokens, cost and run_type. Wrapped in try/catch to not break when the log fails.
In summary — what this step does
  • It's the agent's accounting record. Every execution becomes a row in execution_logs (table name: flow_log). Final summary of what happened, without per-node details.
  • Writes the essential fields. status, error_message, error_status_code, spent_tokens, cost, run_type (api, canvas, chatbot, batch, etc.), flowId and mcpTokenId when the call came via MCP.
  • Feeds dashboards and billing. Analytics filters by run_type. Billing sums cost per company. "My recent runs" filters by flowId. Every relational log read passes through here.
  • Defensive try/catch. If the INSERT fails (database unavailable, timeout), Winston records log_creation_failed. The execution doesn't break. Prefers success without log to execution failed because of log.
  • Output. A new row in execution_logs. In rare cases, Winston failure log. Nothing more. The API return doesn't use the returned value.
Context. This is the execution's relational log. Separate from space_run_logs, which is the hierarchical JSONB of the RunLogCollector. Each execution becomes 1 row here. Queries for dashboards, analytics and billing per account read from this table.

⚠️ Silent failure
If the INSERT fails, the execution still returns success to the client. The log gets lost. Occurs rarely. May generate discrepancies in reports (the client counts 100 executions, the dashboard shows 95).

Filled only when the request came from the MCP (Model Context Protocol) endpoint. Tracks which MCP token triggered the execution. Serves rate-limiting and billing per MCP client.

@Entity('flow_log') class FlowLog { id: uuid, flowId, status, error_message, spent_tokens: number, cost: number, run_type: enum, createdAt, updatedAt, ... }
Purpose. TypeORM entity. The table name is flow_log (singular), although the service is called flowLogs. Columns indexed by flowId for queries like "my recent runs". One row per execution. Sequential PK.
In summary. Classic audit trail table. Each row is an execution. The query keys are flowId (all executions of the flow), userId (indirect via flow.userId), run_type, status and createdAt range. The billing columns (spent_tokens, cost) are number, not bigint. Enough for current volumes. error_message is TEXT (holds long LLM messages). error_status_code is string, not int. Unfortunate decision, but works because it's only displayed in the UI. No soft-delete. The logs follow retention until the TTL configured in the admin.

Notes for migration.

• Defensive try/catch is good pattern. Keep it.
• Status as free string becomes tech debt. Typed enum would help.
• One row per execution is a scalable model. No need for big refactor.
• Should migrate early. The system depends on it for billing and analytics.

Passo 4.3 — flowLogsService.createLog()

Bloco em flux.service.ts:4802-4822 · service em flow_logs/flow_logs.service.ts. INSERT em execution_logs (tabela persistida como flow_log pelo TypeORM). Grava resultado final do run: status, error, tokens, cost, run_type. Try/catch pra não crashar se log falhar.
Em resumo — o que esse passo faz
  • É o livro-caixa do agente: cada run vira uma linha em execution_logs (table name flow_log) — resumo final do que rolou, sem detalhes por nó.
  • Grava os campos essenciais: status, error_message, error_status_code, spent_tokens, cost, run_type (api/canvas/chatbot/batch...), flowId e mcpTokenId se veio via MCP.
  • Alimenta dashboards e billing: analytics filtra por run_type, billing soma cost por company, "meus runs recentes" filtra por flowId. Toda leitura de log relacional passa por aqui.
  • Try/catch defensivo: se o INSERT falha (DB down, timeout), Winston loga log_creation_failed mas o run não crasha — prefere sucesso sem log a run falhado por causa de log.
  • Saída: uma row nova em execution_logs, ou (raro) Winston log de falha. Nada mais — o retorno da API não usa o valor devolvido.
Contexto: este é o log relacional do run — separado do space_run_logs (que é o JSONB hierárquico do RunLogCollector). Cada run vira 1 row aqui. Query pra dashboards, analytics, billing por account — todas leem daqui.

⚠️ Falha silenciosa
Se INSERT falhar, run ainda retorna sucesso pro cliente — mas log fica perdido. Rare mas pode causar discrepâncias em relatórios ("cliente diz que rodou 100 runs, dashboard mostra 95").
🔧 mcpTokenId
Preenchido só se request veio do MCP (Model Context Protocol) endpoint. Rastreia qual token MCP disparou a execução — pra rate-limiting e billing por MCP client.

@Entity('flow_log') class FlowLog { id: uuid, flowId, status, error_message, spent_tokens: number, cost: number, run_type: enum, createdAt, updatedAt, ... }
Propósito: Entity TypeORM. Table name é flow_log (singular) apesar do service se chamar flowLogs. Colunas indexadas por flowId pra queries de "meus runs recentes". Uma row por run — pk sequential.
Em resumo: tabela clássica de audit trail — cada linha é um run. Chave pra queries: filtrar por flowId (todos os runs desse flow), userId (indireto via flow.userId), run_type, status, faixa de createdAt. Colunas de billing (spent_tokens, cost) são number — não bigint — o que basta pra volumes atuais. error_message é TEXT (pode ter mensagens longas de LLM). error_status_code é string (não int) — decisão infeliz mas funciona porque só mostra em UI. Sem soft-delete — logs são retention até TTL configurado em admin.

Observações para migração:
• Tabela relacional simples — fácil de migrar. Worker pode escrever direto se conectar no mesmo Postgres.
• Try/catch defensivo é bom pattern — manter.
• Status livre string vira dívida técnica; enum tipado ajudaria.
• Row-per-run é modelo escalável — sem necessidade de refactor grande.
• Deve migrar cedo — sistema depende pra billing e analytics.

Passo 1.0b — Resolução do runTypeEnum

Bloco em flux.service.ts:2339-2374. Traduz a string runType (vinda do controller) no enum FlowLogRunType. Enum tem 12 valores; o switch cobre 8 explícitos + 3 via includes() no default + 1 fallback WEBHOOK.
Em resumo — o que esse passo faz
  • Default pra 'webhook': se runType chega vazio/undefined, vira 'webhook' — é a linha 2339 const runTypeValue = runType || 'webhook'. Isso quer dizer que "não passei runType" = "veio de um webhook", que é a convenção histórica.
  • Switch com 8 casos exatos: string-match direto pros valores api, batch, chatbot, formapi, public-api, cronjob, email, mcp. Cada um mapeia direto pro membro do enum.
  • Default com 2 sub-branches por substring: se cair no default, ainda testa runTypeValue.includes('flow-caller-node') ou .includes('library-node') — substring, não igualdade — pra pegar variações (por exemplo flow-caller-node-abc). Se nada bate, cai pra WEBHOOK.
  • Enum FlowLogRunType tem 12 valores: além dos 11 tratados aqui, existe MANUAL — que nunca é resolvido por esse switch (é assinado por outros caminhos, como testes ou execuções manuais fora do apiV2).
  • Usado em 3 lugares depois: flowLogsService.createLog({ run_type: runTypeEnum }) no passo 4.3, runLogDoc.runType = runTypeEnum antes do flushNow do SpaceRunLog em 4.4, e outra vez no flushNow no path de erro (5.x). É metadata pura — não muda comportamento de execução, só de billing/relatório.
Contexto: essa resolução acontece antes do try, então qualquer erro aqui (impossível na prática — é uma string switch pura) explodiria fora do error-handling do run. Zero I/O, zero throw esperado.

Em resumo: pense num despachante que recebe uma etiqueta em texto (que pode ser suja) e devolve uma etiqueta oficial do sistema. Primeiro passa por um mapa exato de 8 casos (api, batch, chatbot, formapi, public-api, cronjob, email, mcp) — cada string vira o enum correspondente. Se não bater, o default é mais espertinho: testa se a string contém flow-caller-node (usado quando um flow chama outro) ou library-node (quando um library node dispara execução) — o .includes() aqui é intencional porque o chamador pode ter suffix (flow-caller-node-{parentId}) e ainda precisa ser reconhecido. Curiosidade: o enum tem 12 valores, mas MANUAL nunca é atingido por esse switch — é aplicado em outros caminhos (fora do apiV2).

🎯 Por que .includes() no default?
flow-caller-node e library-node às vezes chegam com sufixo contextual (ex.: nome do node que disparou). O .includes() deixa isso passar sem quebrar. Os outros 8 casos são strings exatas porque vêm de fontes controladas (controllers específicos).
⚠️ MANUAL não atingível aqui
O enum tem MANUAL = 'manual', mas não há case para 'manual' — se alguém passar runType: 'manual', cai no default sem match, e vira WEBHOOK. Bug potencial se algum dia um caller começar a usar essa string esperando MANUAL.

Investigação: MANUAL só aparece no enum, sem nenhum lugar no repo usando essa string via runType. Provavelmente vestigial ou usado em testes/seed.
⚠️ Precedência do .includes()
if (v.includes('flow-caller-node')) vem antes de library-node. Se uma string contivesse ambas (bizarro mas legal em JS), ganha FLOW_CALLER_NODE. Não é um caso real, mas ordem importa se algum dia colidirem.
🔧 Where runType comes from
Controllers em flux.controller.ts passam strings hardcoded quando chamam apiV2. Por exemplo: chatbot passa 'chatbot', cronJobs.service passa 'cronjob', mcp-call.controller passa 'mcp'. Não vem do body do request.

Propósito: runTypeEnum é write-only metadata: nunca controla lógica de execução, só é gravado em logs (FlowLog + SpaceRunLog) pra analytics/billing filtrar depois. Zero uso em decisões de fluxo.
Em resumo: depois de resolvida, essa variável só serve pra marcar — como um carimbo que vai junto no relatório. Ela vai pra três lugares e não influencia mais nada: (1) o FlowLog que registra o run inteiro no Postgres, (2) o RunLogDoc que vai virar registro no Mongo do SpaceRunLog, e (3) o mesmo RunLogDoc no path de erro (quando o run falha). Todas as três chamadas passam runTypeEnum como campo puro de metadata. Ou seja, nunca vai ter um "if (runTypeEnum === CHATBOT)" no meio do loop — o comportamento em runtime é o mesmo pra todos os tipos.

🔧 Impacto downstream
Filtros de dashboard, exports de billing, analytics — tudo lê o run_type gravado. Se o switch mapear errado, o dashboard "conta" o run no bucket errado (WEBHOOK em vez de CHATBOT, por exemplo).
Resumo — o que sai de 1.0b:
• runTypeValue = string normalizada (com fallback pra 'webhook')
• runTypeEnum = FlowLogRunType (um dos 11 valores atingíveis via switch)
• Zero I/O, zero throw — puro string → enum lookup
• Uso downstream: só em createLog (passo 4.3), flushNow success (4.4) e error path (5.x)
Observações para migração:
• Trivialmente replicável — é só um switch. Pode ir pro worker ou ficar no backend antes de start-args, sem diferença.
• Se o worker gerar o FlowLog diretamente, precisa receber a string runType e replicar o mesmo mapping (incluindo os .includes() do default).
• Watch out: o enum MANUAL não é atingido por esse switch. Se algum caminho novo passar 'manual' esperando o enum MANUAL, precisa adicionar um case 'manual' aqui — hoje cai silenciosamente em WEBHOOK.
• Uso puramente metadata, não afeta execução. Prioridade baixa na migração — pode ficar por último.

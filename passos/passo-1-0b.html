Step 1.0b — runTypeEnum resolution

Block at flux.service.ts:2339-2374. Translates the runType string (from the controller) into the FlowLogRunType enum. The enum has 12 values. The switch covers 8 explicitly, plus 3 via includes() in the default, plus 1 WEBHOOK fallback.
In short — what this step does
  • Defaults to 'webhook'. If runType arrives empty or undefined, it becomes 'webhook'. See line 2339 const runTypeValue = runType || 'webhook'. Absence of runType equals webhook origin. It is the historical convention.
  • Switch with 8 exact cases. Direct string match for the values api, batch, chatbot, formapi, public-api, cronjob, email, and mcp. Each one maps directly to the enum member.
  • Default with 2 sub-branches by substring. If it lands in the default, it still tests runTypeValue.includes('flow-caller-node') or .includes('library-node'). It is substring, not equality. This catches variations like flow-caller-node-abc. If nothing matches, it falls back to WEBHOOK.
  • The FlowLogRunType enum has 12 values. Beyond the 11 handled here, there is MANUAL. It is never resolved by this switch. It is assigned by other paths, such as tests or manual runs outside apiV2.
  • Consumed in 3 places downstream. flowLogsService.createLog({ run_type: runTypeEnum }) in step 4.3. runLogDoc.runType = runTypeEnum before the SpaceRunLog flushNow in 4.4. And again in the error path flushNow (5.x). Pure metadata. Does not change execution behavior, only billing and reporting.
Context. This resolution happens before the try. Any error here would explode outside the execution's error handling. In practice, it is impossible. It is a pure string switch. Zero I/O, zero expected throw.

Purpose. Normalizes the runType string parameter into a typed value from the FlowLogRunType enum. It is a typed lookup with a semantic fallback for strings that carry extra context, such as flow-caller-node-xyz.
In short. The block takes a text label (which may arrive with noise) and returns an official system label. First it runs through an exact map of 8 cases: api, batch, chatbot, formapi, public-api, cronjob, email, and mcp. Each string becomes the matching enum. If nothing matches, the default applies extra logic. It tests whether the string contains flow-caller-node (used when a flow calls another) or library-node (when a library node fires an execution). The use of .includes() here is intentional. The caller may append a suffix (flow-caller-node-{parentId}) and still needs to be recognized. If nothing matches, the last default is WEBHOOK. That is also the || default at the top. The enum has 12 values, but MANUAL is never reached by this switch. It is applied by other paths outside apiV2.

🎯 Why .includes() in the default?
flow-caller-node and library-node sometimes arrive with a contextual suffix (for example, the name of the node that fired). .includes() lets them through without breaking. The other 8 cases are exact strings because they come from controlled sources (specific controllers).
⚠️ MANUAL is not reachable here
The enum has MANUAL = 'manual', but there is no case for 'manual'. If someone passes runType: 'manual', it lands in the default without a match and becomes WEBHOOK. A potential bug if some caller ever starts using that string expecting MANUAL.

MANUAL only shows up in the enum. There is no place in the repo using that string via runType. Probably vestigial or used in tests and seeds.
⚠️ .includes() precedence
if (v.includes('flow-caller-node')) comes before library-node. If a string were to contain both (not a real case, but valid in JavaScript), FLOW_CALLER_NODE wins. The order matters if they ever collide.
🔧 Origin of runType
Controllers in flux.controller.ts pass hardcoded strings when they call apiV2. For example, the chatbot passes 'chatbot', cronJobs.service passes 'cronjob', and mcp-call.controller passes 'mcp'. It does not come from the request body.

Purpose. runTypeEnum is write-only metadata. It never controls execution logic. It is only written to logs (FlowLog and SpaceRunLog) so analytics and billing can filter later. Zero use in flow decisions.
In short. Once resolved, this variable only serves as a label. It works like a stamp in the report. It goes to three places and does not influence anything else. First, the FlowLog that records the entire execution in Postgres. Second, the RunLogDoc that becomes a Mongo record in SpaceRunLog. Third, the same RunLogDoc in the error path (when the execution fails). All three calls pass runTypeEnum as pure metadata field. There is never an if (runTypeEnum === CHATBOT) in the middle of the loop. The runtime behavior is the same for every type.

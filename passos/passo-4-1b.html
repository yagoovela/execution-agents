Step 4.1b — flow-global.data.logs cleanup

Block in flux.service.ts:4851-4855. Five lines. After everything (the loop, the cancel from 4.1a, the error check), the backend locates the flow-global node in myUpdatedNodes by id substring. Zeroes the data.logs array in-place. It's the last state mutation before the final persistence of the node array to the database.
In summary — what this step does
  • Locates by substring, not by type. myUpdatedNodes.find(n => n.id.includes('flow-global')). Doesn't consult the type, only checks if the id contains flow-global. It exists to be resistant to inconsistencies between type: 'globalStarter' and the legacy naming flow-global-starter_*.
  • Resets logs to empty array. If located and the node has data, does globalNode.data.logs = []. In-place mutation. Differs from the closure mutation via callback pattern (like onMutateSchema or onMutateObjectCallerData in 1.5).
  • Why zero it out. Historically the globalStarter node accumulated logs from all executions in data.logs. Today those logs have migrated to the dedicated flow_logs table via flowLogsService.createLog, called right after at 4869. The array in data.logs became vestigial. If it persists filled, it goes back to the database and inflates the flows_nodes row for no reason.
  • The same snippet exists in the migration. internal/services/flow_logs_migration.service.ts:53-65 does an identical find (same substring). Except it reads the logs to migrate them to flow_logs. This cleanup at the end of the execution ensures the next execution doesn't persist an inflated version.
  • Downstream. After this reset, another addConnectToNodes runs (line 4934) via currentFlux. The final array goes to persistence via persistNodeDataToLiveRow on the outputObjectNode (line 4962). There's no explicit UPDATE for flow-global at this point. The cleanup here exists more for in-memory state (still used in runLogCollector) than for the database.

A myUpdatedNodes.find(n => n.id.includes('flow-global'))
flux.service.ts:4851
const globalNode = myUpdatedNodes.find(n => n.id.includes('flow-global'));
Purpose. Locate the sole globalStarter type node in the execution's node array. Uses an id substring heuristic instead of the type field. It's defensive. In old bases or seed data there may be cases where the type doesn't match but the id does.
In summary. The direct alternative would be to filter by n.type === 'globalStarter'. Over the years, flows were created with different conventions. Some have type: 'globalStarter'. Others only keep the id in the format flow-global-starter_<random>. The substring guarantees finding it in both cases. Every globalStarter id contains the string flow-global. Typical formats are flow-global-starter_0.13579 or flow-global-starter_<uuid>. Regardless of type, if the id contains flow-global, that's the node. It's the same logic used in the log migration in flow_logs_migration.service.ts.

⚠️ Substring "flow-global" has latent false-positive
If someone creates a flow with a node id like my-flow-global-var or flow-global-config, the .find() matches it instead of globalStarter. It doesn't block because the data.logs check in B probably fails. It's a latent trap if naming is loose.
🎯 Why not use type
In utils/clean-fluxbot-flow.ts:14-19 the same cleanup happens with filter by node.type === 'globalStarter'. Not here. Probable reason. The type may not be loaded in myUpdatedNodes in all code paths. The array went through multiple addConnectToNodes and mutations.

Substring is the safer common denominator.
🔧 Duplicated constant
The mcp-write.service.ts:41 has GLOBAL_STARTER_ID_SUBSTRING = 'flow-global-starter'. Here uses the literal 'flow-global' (shorter). Divergence. If an id were flow-global-config (without starter), the MCP wouldn't confuse, but this code would.
B globalNode.data.logs = []
flux.service.ts:4853-4855
if (globalNode?.data) { globalNode.data.logs = []; }
Purpose. Discard the data.logs array in-place on the globalStarter object. That array is vestigial. The source of truth for execution logs has migrated to the flow_logs table. If it persists with data inside, the next flow read brings a larger payload with no value.
In summary. The globalStarter node historically carried a logs array inside data. Each execution pushed information there. Today it's redundant. The official logs go to the flow_logs table via flowLogsService.createLog, called a few milliseconds later (line 4869). Keeping the array filled duplicates data. When persisting myUpdatedNodes in flows_nodes.data, the row inflates unnecessarily. The logic is simple. Locates the node, checks if it has data (defensive guard) and reassigns logs as an empty array. It's direct object mutation, not substitution via callback. The object inside myUpdatedNodes changes in-place. Whoever holds a reference to it sees the new state.
B1 Guard before mutation

🎯 What was written in data.logs
Historically. Array of execution logs. Each entry had runType, timestamp, status, tokens, etc.

Today. In the migration (flow_logs_migration.service.ts:65-71), the first 50 are copied to the flow_logs table. The original row in flows_nodes ceases to be the source of truth.
⚠️ In-place mutation breaks the convention
In the same file, the dominant pattern is reassigning arrays via let plus callback. Here is the exception. globalNode.data.logs = [] changes the inner object of the array.

If someone adds an observer for myUpdatedNodes, this mutation escapes detection. The parent array's reference doesn't change.

Summary — what comes out of 4.1b.
• myUpdatedNodes with the flow-global having data.logs = []. Untouched when the node was not located.

• Downstream. The runLogCollector.finalize, the final addConnectToNodes and the persistence of the outputObjectNode start from this already-clean array.
Notes for migration.
• Trivial to replicate in the worker. No dependency, no query, no I/O. Only a mutation on a JSON object.
• The substring as detection heuristic can become a shared constant. The mcp-write.service.ts already has GLOBAL_STARTER_ID_SUBSTRING = 'flow-global-starter'. Centralizing in flux/constants.ts for both to use would make sense. This step uses 'flow-global' (shorter). Subtle divergence.
• If the data.logs array is definitively retired (nothing reads or writes it), this cleanup becomes dead code. Can be removed. It's worth investigating logs.push history before deleting.
• Lowest priority. It's defense against vestigial data. If the worker doesn't write to data.logs during execution, this reset doesn't even need to happen there.

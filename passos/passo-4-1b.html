Passo 4.1b — Limpeza flow-global.data.logs

Bloco em flux.service.ts:4851-4855. Cinco linhas. Depois de tudo — do loop, do cancel (4.1a), da checagem de erros — o backend acha o nó flow-global no myUpdatedNodes por substring de id e zera o array data.logs in-place. É a última mutação de estado antes da persistência final do array de nós no banco.
Em resumo — o que esse passo faz
  • Acha por substring, não por type: myUpdatedNodes.find(n => n.id.includes('flow-global')). Não pergunta o type, só olha se o id tem "flow-global" dentro. Existe pra ser resistente a inconsistências entre type: 'globalStarter' e o naming legado flow-global-starter_*.
  • Reseta logs pra array vazio: se achou e ele tem data, faz globalNode.data.logs = []. Mutação in-place — difere do padrão de closure mutation via callback (como onMutateSchema, onMutateObjectCallerData em 1.5).
  • Por que zerar? Historicamente o node globalStarter acumulava logs de todos os runs em data.logs. Hoje esses logs migraram pra tabela dedicada flow_logs (via flowLogsService.createLog, chamado logo depois em 4869). O array em data.logs virou vestigial — se persistir cheio, ele volta pro DB inflando a row do flows_nodes sem necessidade.
  • Mesmo trecho existe em migração: internal/services/flow_logs_migration.service.ts:53-65 faz um find idêntico (mesma substring) só que lendo os logs pra migrar pra flow_logs — depois disso essa limpeza no fim do run garante que a próxima run não persista uma versão inchada.
  • Downstream: depois desse reset, mais um addConnectToNodes corre (linha 4934) via currentFlux, depois o array final vai pra persistência via persistNodeDataToLiveRow nos outputObjectNode (linha 4962) — mas não há UPDATE explícito pro flow-global nesse ponto. A limpeza aqui existe mais pro estado em memória (que ainda é usado no runLog collector) do que pro DB.

A myUpdatedNodes.find(n => n.id.includes('flow-global'))
flux.service.ts:4851
const globalNode = myUpdatedNodes.find(n => n.id.includes('flow-global'));
Propósito: Localizar o único nó do tipo globalStarter no array de nodes do run, usando uma heurística de substring de id em vez do campo type. É defensivo — em bases antigas ou seeded data pode haver casos onde o type não bate mas o id sim.
Em resumo: pense nele como um reconhecimento facial pela camiseta em vez do RG. O jeito "certo" seria filtrar por n.type === 'globalStarter'. Só que ao longo dos anos os flows foram criados com convenções diferentes: alguns têm type: 'globalStarter', outros o id foi só 'flow-global-starter_<random>'. A substring garante achar em ambos os casos. Todo id de globalStarter contém a string "flow-global" (formatos típicos: flow-global-starter_0.13579, flow-global-starter_<uuid>). Assim, independentemente do que o type diga, se o id tem "flow-global" no meio, é aquele nó. É a mesma lógica usada na migração de logs em flow_logs_migration.service.ts.

⚠️ Substring "flow-global" tem falso-positivo latente
Se alguém criar um flow com id de nó tipo my-flow-global-var ou flow-global-config, o .find() vai casar com ele em vez do globalStarter. Não bloqueia porque o teste de data.logs em B provavelmente falha, mas é uma armadilha esperando pra explodir se o naming for lax.
🎯 Por que não usar type?
Em utils/clean-fluxbot-flow.ts:14-19 a mesma limpeza acontece com filtro por node.type === 'globalStarter'. Aqui não. Provável razão: o type pode não estar carregado no myUpdatedNodes em todos os fluxos de código (o array passou por múltiplos addConnectToNodes e mutations).

Substring é o denominador comum mais seguro.
🔧 Constante duplicada
mcp-write.service.ts:41 tem GLOBAL_STARTER_ID_SUBSTRING = 'flow-global-starter'. Aqui usa o literal 'flow-global' (mais curto). Divergência: se um id fosse flow-global-config (sem "starter"), o MCP não confundiria mas este código sim.
B globalNode.data.logs = []
flux.service.ts:4853-4855
if (globalNode?.data) { globalNode.data.logs = []; }
Propósito: Descartar o array data.logs in-place no objeto do globalStarter. Esse array é vestigial — a fonte de verdade dos logs de run migrou pra tabela flow_logs. Se persistir com dados dentro, a próxima leitura do flow traz um payload maior sem valor.
Em resumo: pense nele como esvaziar o lixeirão antes de sair do escritório. O nó globalStarter historicamente carregou um array logs dentro do data — cada run empurrava informação lá. Isso hoje é redundante: os logs oficiais vão pra tabela flow_logs via flowLogsService.createLog, chamado alguns milissegundos depois (linha 4869). Manter o array preenchido significa que, ao persistir o myUpdatedNodes em flows_nodes.data, você duplica dados — inflando a row sem necessidade. Então: acha o nó, checa se tem data (guard defensive), e reatribui logs pra array vazio. É mutação direta do objeto, não substituição via callback — o objeto dentro de myUpdatedNodes muda in-place e quem tiver referência a ele vê o novo estado.

⚠️ Mutação in-place = quebra convenção
No mesmo arquivo, o padrão dominante é: arrays são reatribuídos via let + callback. Aqui é a exceção — globalNode.data.logs = [] muda o objeto interno do array.

Se alguém adicionar um observer/watcher pra myUpdatedNodes depois, essa mutação escapa da detecção porque a referência do array pai não muda.

Resumo — o que sai de 4.1b:
• myUpdatedNodes com o flow-global tendo data.logs = [] (ou intacto se não achou o nó)
• Sem side effects em banco, sem WebSocket, sem novas chamadas — só uma mutação in-place
• Downstream: runLogCollector.finalize, addConnectToNodes final e persistência dos outputObjectNode partem desse array já limpo
Observações para migração:
• Trivial de replicar no worker. Nenhuma dependência, nenhuma query, sem I/O — só uma mutação num objeto JSON.
• Substring como heurística de detecção pode virar constante compartilhada: mcp-write.service.ts já tem GLOBAL_STARTER_ID_SUBSTRING = 'flow-global-starter'. Valeria centralizar em flux/constants.ts pra ambos usarem — o que este passo usa ('flow-global', mais curto) diverge sutilmente.
• Se o array data.logs for definitivamente aposentado (nada lê nem escreve), essa limpeza vira código morto — pode ser removida. Vale investigar histórico de logs.push antes de deletar.
• Prioridade: baixíssima. É defesa contra dado vestigial. Se o worker não escrever em data.logs durante a run, esse reset nem precisa acontecer lá.

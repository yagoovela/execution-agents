finalize(params: { output, totalTokens, totalCost, status, errorMessage }): RunLogDocument | null
Purpose. Closes the root document. Fills endedAt, durationMs, the redacted output, total tokens and cost, status (success or error) and errorMessage. Calls buildRunLogSummary to populate doc.summary. If it's a sub-collector (parent is not null), it also sums tokens and cost into the parentNode.
In summary. It's the official closing of the log document. The RunLogDocument is in memory being mutated since 1.4 (createRoot). Nodes were added and updated. Sub-runs were created. The finalize signs the document. Sets the end timestamp. Computes the total duration. Redacts the final output (all outputObjectNode) via redactSecrets. Persists total tokens and cost in the doc. Decides the status based on nodesWithError.length > 0. error if there's an error. success otherwise. Cancel is handled before by another path. Calls buildRunLogSummary(doc), which walks the entire tree (root.nodes, innerSteps and subRuns recursively). Builds a summary with error and warning counts. Includes the output nodes without output ("empty output warning"). If it's a sub-collector (parent is not null), the last action is to sum totalTokens and totalCost into the parentNode. Propagates the sub-flow's cost to the parent. Each hierarchical level aggregates the children's cost. Returns the doc to the caller (function B) to do the flushNow.

buildRunLogSummary
Recursive. Walks doc.nodes, innerSteps and subRun. Collects errors, warnings (empty outputs) and counters. Returns RunLogSummary with errorCount, errors[], warningCount, warnings[], outputNodeCount and emptyOutputNodeCount.
run-log-collector.ts:108-128
🎯 Aggregates cost for the parent
Sub-collectors (fluxBox or libraryNode that fired sub-runs) sum totalTokens and totalCost into the parentNode. When you look at the parent's total cost, the aggregated cost of the children is already there.
📎 buildRunLogSummary is recursive
Walks the entire tree (root, innerSteps and subRun). O(n) cost over nodes. In gigantic executions with many sub-flows, it can be measurable.
🔧 Empty-output warning
If an outputObjectNode doesn't have text populated, it enters summary.warnings. A console.log warns the dev right away ("successful execution, but empty outputs").
BspaceRunLogsService.flushNow(params)
space_run_logs.service.ts:122-130
async flushNow(params: { processId, spaceId, rootFlowId, logData: RunLogDocument }): Promise<SpaceRunLog>
Purpose. Counterpart of scheduleUpsert. Cancels the pending timer for this processId. Does synchronous upsert immediately. Called at execution end to guarantee that the final doc version reaches the database before return.
In summary. The scheduleUpsert schedules delivery with debounce. The flushNow writes now. Reason. At the end of the execution, it's necessary to guarantee that space_run_logs has the final doc version before the backend returns to the client. Without it, the client could query the timeline immediately and see stale state (in_progress). The implementation is simple. The cancelPendingFlush(processId) clears any prior setTimeout. The upsertRun(params) does the synchronous INSERT or UPDATE via TypeORM. Returns the entity. Called once per execution. In nested executions, only the root calls flushNow (line 4833: if (runLogDoc && !isNestedRunLog)).
async flushNow(params: { processId: string; spaceId: string; rootFlowId: string; logData: RunLogDocument; }): Promise<SpaceRunLog> { this.cancelPendingFlush(params.processId); // cancels timer return this.upsertRun(params); // synchronous UPSERT }

space_run_logs.service.ts (upsertRun)
🎯 Synchrony at the end
The debounce serves long executions. Avoids excessive intermediate writes. At the end, the synchronous write ensures final consistency.
⚠️ JSONB can get large
Executions with many nodes and long outputs can generate logData of several MB. Upsert with large JSONB is slow. The row size grows indefinitely. There's no paging. The whole row needs to be read for the UI to show the timeline.
🔧 Only root calls flushNow
Sub-collectors (fluxBox or libraryNode) were already serialized as subRun in the root doc. Only the root writes. Avoids duplication.

Notes for migration.
• The RunLogCollector is cross-cutting and essential. The timeline UX depends on it. The migration needs to preserve the hierarchy (innerSteps plus subRun).
• Large JSONB in space_run_logs can become a scale problem. Consider partitioning by processId or using pagination.
• The synchronous flushNow at the end of execution adds latency (roughly 50 to 200ms). Acceptable today. To optimize UX, it can become async fire-and-forget with optional wait.
• If the worker migrates, the collector needs to serialize to the backend via API or queue. Today it lives in the same process.

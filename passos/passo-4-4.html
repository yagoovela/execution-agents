Passo 4.4 — RunLogCollector.finalize + flushNow

Bloco em flux.service.ts:4824-4862. O finalize() está em run-log-collector.ts:372-402. O flushNow() em space_run_logs.service.ts:122-130. Fecha o RunLogDocument em memória. Calcula o summary. Cancela o debounce. Escreve de forma imediata em space_run_logs.
Em resumo — o que esse passo faz
  • Fecha o documento. O finalize() encerra o RunLogDocument em memória. Define endedAt. Calcula durationMs. Ofusca o output via redactSecrets. Grava totalTokens, totalCost e status.
  • Constrói o summary hierárquico. O buildRunLogSummary percorre a árvore (raiz, innerSteps e subRun recursivo). Conta erros e warnings. Inclui warning de output vazio para outputObjectNode sem text.
  • Sub-collectors propagam custo. Em sub-run (fluxBox ou libraryNode), soma tokens e cost no parentNode. Cada nível hierárquico agrega o custo dos filhos automaticamente.
  • O flushNow força o write final. Cancela o timer pendente. Faz upsert síncrono em space_run_logs com o JSONB completo. Só a raiz escreve. Evita duplicação com sub-runs.
  • Saída. Linha em space_run_logs com o RunLogDocument serializado. Try/catch defensivo. Se a persistência falhar, o Winston grava log. A execução não derruba.
Contexto. Par simétrico de createRoot (do passo 1.4). Se o scheduleUpsert fazia write debounced ao longo da execução, aqui força um write final e síncrono. Só roda para a raiz, não para sub-run. Os filhos são serializados dentro do doc raiz.
ArunLogCollector.finalize(params)
run-log-collector.ts:372-402
finalize(params: { output, totalTokens, totalCost, status, errorMessage }): RunLogDocument | null
Propósito. Fecha o documento raiz. Preenche endedAt, durationMs, o output ofuscado, tokens e cost totais, status (success ou error) e errorMessage. Chama buildRunLogSummary para popular doc.summary. Se é sub-collector (parent não é nulo), também soma tokens e cost no parentNode.
Em resumo. É o encerramento oficial do documento de log. O RunLogDocument está em memória sendo mutado desde 1.4 (createRoot). Nós foram adicionados e atualizados. Sub-runs foram criados. O finalize assina o documento. Define o timestamp de fim. Calcula a duração total. Ofusca o output final (todos os outputObjectNode) via redactSecrets. Persiste tokens e cost totais no doc. Decide o status com base em nodesWithError.length > 0. error se há erro. success caso contrário. Cancel é tratado antes por outro caminho. Chama buildRunLogSummary(doc), que percorre a árvore inteira (root.nodes, innerSteps e subRuns de forma recursiva). Monta um sumário com contagem de erros e warnings. Inclui os nós de output sem output ("empty output warning"). Se é sub-collector (parent não é nulo), a última ação é somar totalTokens e totalCost no parentNode. Propaga o custo do sub-flow para o pai. Cada nível hierárquico agrega o custo dos filhos. Retorna o doc para o caller (função B) fazer o flushNow.
finalize(params): RunLogDocument | null { if (!this.enabled) return null; const doc = this.rootDoc ?? this.subDoc; const endedAt = new Date(); doc.endedAt = endedAt.toISOString(); doc.durationMs = endedAt.getTime() - this.startedAtMs; doc.output = redactSecrets(params.output); doc.totalTokens = params.totalTokens; doc.totalCost = params.totalCost; doc.status = params.status; doc.errorMessage = params.errorMessage; doc.summary = buildRunLogSummary(doc); // warnings de outputs vazios (linha 385) if (this.parentNode && !this.rootDoc) { this.parentNode.tokens = (this.parentNode.tokens ?? 0) + params.totalTokens; this.parentNode.cost = (this.parentNode.cost ?? 0) + params.totalCost; } this.flushRoot(); return doc; }

buildRunLogSummary
Recursivo. Percorre doc.nodes, innerSteps e subRun. Coleta erros, warnings (outputs vazios) e contadores. Retorna RunLogSummary com errorCount, errors[], warningCount, warnings[], outputNodeCount e emptyOutputNodeCount.
run-log-collector.ts:108-128
🎯 Agrega custo para o parent
Sub-collectors (fluxBox ou libraryNode que dispararam sub-runs) somam totalTokens e totalCost no parentNode. Ao ver o custo total do parent, o custo agregado dos filhos já aparece.
📎 buildRunLogSummary é recursivo
Percorre a árvore inteira (raiz, innerSteps e subRun). Custo O(n) em nós. Em execuções gigantes com muitos sub-flows, pode ser mensurável.
🔧 Warning de output vazio
Se um outputObjectNode não tem text populado, entra em summary.warnings. Um console.log avisa o dev na hora ("execução com sucesso, mas outputs vazios").
BspaceRunLogsService.flushNow(params)
space_run_logs.service.ts:122-130
async flushNow(params: { processId, spaceId, rootFlowId, logData: RunLogDocument }): Promise<SpaceRunLog>
Propósito. Contrapartida do scheduleUpsert. Cancela o timer pendente para este processId. Faz upsert síncrono imediatamente. Chamado no fim da execução para garantir que a versão final do doc chega ao banco antes do retorno.
Em resumo. O scheduleUpsert agenda a entrega com debounce. O flushNow escreve agora. Motivo. No fim da execução, é preciso garantir que space_run_logs tem a versão final do doc antes do backend retornar para o cliente. Sem isso, o cliente poderia consultar a timeline imediatamente e ver estado antigo (in_progress). A implementação é simples. O cancelPendingFlush(processId) limpa qualquer setTimeout anterior. O upsertRun(params) faz o INSERT ou UPDATE síncrono via TypeORM. Retorna a entity. Chamado uma vez por execução. Em execuções aninhadas, só o root chama flushNow (linha 4833: if (runLogDoc && !isNestedRunLog)).
async flushNow(params: { processId: string; spaceId: string; rootFlowId: string; logData: RunLogDocument; }): Promise<SpaceRunLog> { this.cancelPendingFlush(params.processId); // cancela timer return this.upsertRun(params); // UPSERT síncrono }

space_run_logs.service.ts (upsertRun)
🎯 Sincronia no fim
O debounce serve para execuções longas. Evita write intermediário excessivo. No fim, o write síncrono garante consistência final.
⚠️ JSONB pode ficar grande
Execuções com muitos nós e outputs longos podem gerar logData de vários MB. Upsert com JSONB grande é lento. O tamanho da linha cresce indefinidamente. Não há paging. A linha inteira precisa ser lida para a UI mostrar a timeline.
🔧 Só a raiz chama flushNow
Sub-collectors (fluxBox ou libraryNode) já foram serializados como subRun no doc raiz. Só a raiz escreve. Evita duplicação.

Em resumo. Dupla filtragem. Primeiro, runLogCollector?.enabled && runLogSpaceId. Feature gate. Se o coletor foi criado desativado ou a execução não tem space (por exemplo, execução em contexto pessoal sem space), o bloco não entra. Depois, if (runLogDoc && !isNestedRunLog). Se é sub-run (chamado pelo parent via fluxBox ou libraryNode), o parent vai fazer flushNow com o doc completo (que já contém o sub como subRun). Chamar flushNow no sub duplicaria e poderia sobrescrever com estado incompleto. Try/catch reforça a defesa. Se o flushNow explodir por banco indisponível ou linha muito grande, o Winston grava log. A execução não derruba. Também há console.log('[SpaceRunLog persisted]') para debug em dev. Inclui a contagem de nós capturados.

Resumo — o que sai de 4.4.
• RunLogDocument finalizado (endedAt, durationMs, output, status, summary).
• Linha em space_run_logs em upsert com o JSONB completo do doc.
• Sub-runs propagam tokens e cost para o parent.
• Try/catch. Falha aqui não derruba a execução.
Observações para migração.
• O RunLogCollector é cross-cutting e essencial. A UX de timeline depende dele. A migração precisa preservar a hierarquia (innerSteps mais subRun).
• JSONB grande em space_run_logs pode virar problema de escala. Considerar particionar por processId ou usar paginação.
• O flushNow síncrono no fim da execução adiciona latência (aproximadamente 50 a 200ms). Aceitável hoje. Se otimizar UX, pode virar async fire-and-forget com espera opcional.
• Se o worker migrar, o coletor precisa serializar para o backend via API ou fila. Hoje vive no mesmo processo.

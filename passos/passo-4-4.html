Bloco em flux.service.ts:4824-4862. finalize() em run-log-collector.ts:372-402. flushNow() em space_run_logs.service.ts:122-130. Fecha o RunLogDocument em memória, calcula summary, cancela debounce, escreve imediato em space_run_logs.
Em resumo — o que esse passo faz
  • Assina o documento embaixo: finalize() fecha o RunLogDocument em memória — seta endedAt, calcula durationMs, redige o output via redactSecrets e grava totalTokens/totalCost/status.
  • Constrói o summary hierárquico: buildRunLogSummary percorre a árvore (root + innerSteps + subRun recursivo) contando erros e warnings — inclui "empty output warning" pra outputObjectNodes sem text.
  • Sub-collectors propagam custo: se é sub-run (fluxBox/libraryNode), soma tokens e cost no parentNode. Cada nível hierárquico agrega o custo dos filhos automaticamente.
  • flushNow força o write final: se o debounce é o Correios, o flushNow é o motoboy — cancela o timer pendente e faz UPSERT síncrono em space_run_logs com o JSONB completo. Só o root escreve (evita duplicação com sub-runs).
  • Saída: row em space_run_logs com o RunLogDocument serializado. Try/catch defensivo — se persistência falhar, Winston log mas run não crasha.
Contexto: par simétrico de createRoot (do passo 1.4). Se scheduleUpsert era write debounced ao longo do run, aqui força write final e sincronizo. Só roda pra root (não sub-run) — filhos são serializados dentro do doc raiz.

Em resumo: é o encerramento oficial do documento de log. O RunLogDocument tá em memória sendo mutado desde 1.4 (createRoot) — nós foram adicionados/atualizados, sub-runs criados, tudo. Finalize é o momento de assinar embaixo: seta timestamp de fim, calcula duração total, redige o output final (todos os outputObjectNodes) — passa por redactSecrets antes. Persiste tokens/cost totais no doc. Decide status baseado em nodesWithError.length > 0 ('error' se tem erro, 'success' caso contrário — cancel é tratado antes por outro caminho). E chama buildRunLogSummary(doc) que percorre a árvore inteira (root.nodes + innerSteps + subRuns recursivo) e monta um sumário com contagem de erros e warnings (nós output sem output — "empty output warning"). Se é sub-collector (parent != null), a última coisa é somar totalTokens e totalCost no parentNode, propagando o custo do sub-flow pro pai. Interessante — cada nível hierárquico agrega o custo dos filhos. Retorna o doc pra que o caller (fn B) faça o flushNow.

🎯 Agrega custo pro parent
Sub-collectors (fluxBox/libraryNode que dispararam sub-runs) somam totalTokens/totalCost no parentNode. Assim, ao ver custo total do parent, você já vê o custo agregado dos filhos automaticamente.
📎 buildRunLogSummary é recursivo
Percorre árvore inteira (root + innerSteps + subRun). Custo O(n) em nós — em runs gigantes com muitos sub-flows pode virar mensurável.
🔧 Warning de output vazio
Se um outputObjectNode não tem text populado, entra em summary.warnings. Log console pra dev ver na hora ("run 'sucesso' mas outputs vazios").
BspaceRunLogsService.flushNow(params)

async flushNow(params: { processId, spaceId, rootFlowId, logData: RunLogDocument }): Promise<SpaceRunLog>
Propósito: Contrapartida do scheduleUpsert. Cancela timer pendente pra este processId, faz UPSERT síncrono agora. Chamado no fim do run pra garantir que a versão final do doc chegou no banco antes de retornar.
Em resumo: se o scheduleUpsert é o Correios devagar (agenda entrega debounced), o flushNow é o motoboy — vai agora. Motivo: no fim do run, precisa garantir que space_run_logs tem a versão final do doc antes do backend retornar pro cliente. Se dependesse do debounce, o cliente poderia consultar timeline imediatamente e ver estado antigo (in_progress). Implementação simples: cancelPendingFlush(processId) limpa qualquer setTimeout anterior e upsertRun(params) faz o INSERT/UPDATE síncrono via TypeORM. Retorna a entity. Só chamado uma vez por run — em runs aninhados, só o root chama flushNow (linha 4833: if (runLogDoc && !isNestedRunLog)).
async flushNow(params: { processId: string; spaceId: string; rootFlowId: string; logData: RunLogDocument; }): Promise<SpaceRunLog> { this.cancelPendingFlush(params.processId); // cancela timer return this.upsertRun(params); // UPSERT síncrono }

space_run_logs.service.ts (upsertRun)
🎯 Sync no fim
Debounce serve pra runs longos (evita hammer intermediário). No fim, sync garante consistência final.
⚠️ JSONB pode ficar gigante
Runs com muitos nós e outputs longos podem gerar logData de MBs. UPSERT com JSONB grande é lento; row size cresce indefinidamente. Não tem paging — a row inteira precisa ser lida pra UI mostrar timeline.
🔧 Só root faz flushNow
Sub-collectors (fluxBox/libraryNode) já foram serializados como subRun no doc raiz. Só o root escreve — evita duplicação.

Observações para migração:
• RunLogCollector é cross-cutting e essencial — UX de timeline depende. Migração precisa preservar hierarquia (innerSteps + subRun).
• JSONB gigante em space_run_logs pode virar problema de escala — considerar particionar por processId ou paginação.
• flushNow síncrono no fim do run adiciona latência (~50-200ms). Aceitável hoje, mas se otimizar UX, pode virar async fire-and-forget com espera opcional.
• Se worker migrar, coletor precisa serializar pra o backend (via API ou fila) — hoje vive no mesmo processo.

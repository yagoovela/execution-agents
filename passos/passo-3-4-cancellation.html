Cancellation check — feature flag NODE_CANCEL_IN_FLIGHT

Block scattered in flux.service.ts:3184-3194 (setup), 3229-3239 (check between nodes), 3251-3269 (start watch per node) and 4516-4530 (finish when aborted). System that lets the user cancel a running execution. Today only enabled for runType='canvas'.
In short — what this step does
  • Gatekeeper decides if execution is cancellable. shouldWatchCancellation only enables watch for runType='canvas' (editor) or sub-runs that inherit from parent. API, chatbot, webhook and batch are not cancellable. Request-response semantics don't make sense to interrupt from the server.
  • Watcher between nodes, passive polling. Before each while iteration, isCancelRequested(runKey) queries flow_run_states (with 1.5s in-memory cache). If cancel pending, sets stoppedByCancel=true and does break. Doesn't interrupt anything in execution. Just prevents starting the next node.
  • Watcher inside node (feature flag OFF in prod). If NODE_CANCEL_IN_FLIGHT_FLAG is enabled, startNodeCancelWatch sets up a 2s setInterval per node with AbortController. When poll detects cancel, calls controller.abort(). Cost: 100 nodes = 100 parallel timers. Likely reason the flag is still off.
  • Cooperative abort via ALS. nodeCancelContext (another AsyncLocalStorage) carries the AbortSignal for global fetch and axios interceptors. Every HTTP request made by the handler gets the signal automatically. If aborts, throws AbortError. The handler doesn't even need to know cancel exists. Not preemptive. Synchronous SQL or in-memory computation keeps running.
  • Finisher cleans up and persists. After AbortError, finishCancelledNode nulls out errorMessage (cancel is not error. UI shows gray, not red). Does UPDATE on node_executions to executionStatus='CANCELLED', fires WebSocket, marks in scheduler and exits the loop.
  • Exit. Happy path becomes 100% no-op. If cancelled, execution ends with "clean cancelled" status (not fatal error) and Phase 4 closes cleanup normally.
Context. This is the only step in the diagram new post-doc. Didn't exist in the original documented version. Was added later to support the "cancel" button in the editor. Works at two levels. (1) Check between nodes (whenever watchEnabled=true). (2) Check during node execution via AbortSignal in fetch and axios (only when feature flag NODE_CANCEL_IN_FLIGHT_FLAG is enabled).

A shouldWatchCancellation + resolveCancelRunKey

cancelWatchEnabled = shouldWatchCancellation({ runType, isNestedRun }) · cancelRunKey = resolveCancelRunKey({ runLogProcessId, parentRunId })
Purpose. Setup once per execution, before the while starts. Decides if execution is eligible to observe cancellation and which key to use to query the status (parentRunId in nested executions, own processId otherwise).
In short. It's the gatekeeper that answers three questions before execution starts.
(1) "Does this execution type allow cancel?" Only canvas (from editor) allows. API, chatbot, form, batch and webhook don't. Intentional. Synchronous request-response makes no sense to cancel from server side without client asking.
(2) "Is this a sub-run inheriting from a parent?" If yes, inherits watch from parent. Cancelling parent propagates to all children.
(3) "Which key to use to query cancellation?" If nested, uses root id (all children query same key and cancel together). If top-level, uses own processId.
Then comes the second layer. Even with watch enabled, only if feature flag NODE_CANCEL_IN_FLIGHT_FLAG is on does cancel during node execution work (polling and AbortSignal). Without the flag, only checks cancel between nodes. An LLM streaming the response continues to the end, even if user clicked "cancel". The flag is off in production today. Suggests two things. (a) System is new and hasn't gone through large-scale test battery. (b) Cost of running 60 parallel setIntervals in large executions is still being evaluated.

🎯 Why only canvas cancels?
API executions (runType='api') have "request-response" semantics. Client is already waiting synchronously. Cancelling from server side without client asking would be confusing.

Canvas, on the other hand, is execution in the editor. User clicks "cancel" and expects a real stop.
📎 Nested inherits watch
A fluxBox or libraryNode calls apiV2 recursively for the sub-flow. Since isNestedRun=true, watch is enabled on the child too. So, cancelling parent propagates. Child queries same cancelRunKey (parent) and sees the cancel request.
🔧 Stringly-typed feature flag
'node_cancel_in_flight' as string literal in NODE_CANCEL_IN_FLIGHT_FLAG. Gradual rollout. Can be enabled per space or user via featureFlagsService. Default setup: OFF in production (today).
B runCancellationService.isCancelRequested(runId)
executions_logs/run-cancellation.service.ts:62-79 · flux.service.ts:3229-3239
async isCancelRequested(runId: string): Promise<boolean> · check at top of while
Purpose. Check between nodes. At start of each while iteration, queries if any client requested cancel. If yes, sets stoppedByCancel=true and does break. Doesn't interrupt node in execution. Just prevents starting the next one.
In short. It's a watcher at the doorframe of the next node. Before letting each node enter execution, the watcher looks at the "cancellation list" (flow_run_states table). If the current agent runId is there, closes the door. stoppedByCancel = true and break. The node doesn't even start running. It's deliberately polite. Doesn't interrupt anything in execution, only prevents the next. If user clicked "cancel" while a textGenerator is streaming, this watcher only acts after streaming ends. To interrupt mid-execution you need the in-flight watch (fn C). Since it's not worth querying Postgres every 100ms in an execution with 100 fast nodes, the service has an in-memory cache with 1500ms TTL. If queried less than 1.5s ago, returns cached result without hitting the DB. User may have up to 1.5s delay between clicking "cancel" and seeing effect. This is indistinguishable from normal UI latency. If cancel is confirmed, cleanup goes to normal Phase 4 (doesn't become error), execution ends with cancelled status, and client sees appropriate message.

🎯 Cache TTL=1500ms
Avoids hammering Postgres in long executions with many nodes. Trade-off. Can take up to 1.5s for cancel to be observed. Acceptable for "cancel" UX. User doesn't notice difference between 200ms and 1500ms.
⚠️ Cancel between nodes ≠ abort of current node
If a textGenerator is streaming response and user clicks cancel during streaming, this check does not interrupt. Just prevents starting the next node. To interrupt mid-execution, you need the in-flight watch (fn C) and the fetch and axios interceptors (fn D).
🔧 How cancel is set
POST /executions_logs/runs/:runId/cancel calls executionsLogsService.requestRunCancellation(user, runId), which:
• Validates permissions and status (only canvas, execution must be running)
• Calls runCancellationService.requestCancel({ runId, flowId, userId })
• INSERT into flow_run_states
• interruptStepsInFlight(runId) for immediate abort
C startNodeCancelWatch({ runId, nodeId, isCancelRequested })
flux/node-cancel-watch.ts:56-93 · flux.service.ts:3251-3261
shouldStartNodeCancelWatch({ watchEnabled, inFlightEnabled }) ? startNodeCancelWatch({...}) : null
Purpose. If both watchEnabled and inFlightEnabled are true, creates a watcher PER NODE that polls every 2s (CANCEL_POLL_MS=2000) for isCancelRequested. When it detects cancel, calls controller.abort() on the AbortController delivered via cancelWatch.entry.
In short. If the door watcher (fn B) is passive, this is the watcher inside the room. While the node runs, this watcher taps the clock every 2 seconds asking "so now, did they cancel?". When the answer is yes, pulls the bell rope: controller.abort(). An AbortSignal runs through all fetch and axios in progress inside that node. Each throws AbortError. It's like a cooperative alarm. HTTP calls choose to respect the signal (modern web standard). The watcher returns 3 things to the loop.
• entry: the AbortSignal and metadata to be injected into ALS nodeCancelContext.
• wasAborted(): function the loop calls later to know if abort occurred.
• stop(): to clean up the setInterval when node ends. Without it, timers leak.
Critical perf point. An agent with 100 nodes has 100 setIntervals running simultaneously, each querying Postgres. With 1.5s cache still yields ~66 queries per second. That's why the feature flag is OFF in prod today. Real and definitive solution will come with Temporal. Native WorkflowHandle.cancel(), no polling, no timer, no constant cost.
// flux/node-cancel-watch.ts:56-93 — summary export function shouldStartNodeCancelWatch(params) { return params.watchEnabled && params.inFlightEnabled; } export function startNodeCancelWatch(params) { const controller = new AbortController(); let aborted = false; const timer = setInterval(async () => { if (await params.isCancelRequested(params.runId)) { aborted = true; controller.abort(); clearInterval(timer); } }, CANCEL_POLL_MS); return { entry: { signal: controller.signal, runId, nodeId }, wasAborted: () => aborted, stop: () => clearInterval(timer), }; }

🎯 Watch is PER-NODE, not per-run
Each while iteration creates a new watcher with a new AbortController. Each node has its own async chain and needs its own AbortSignal for the fetch and axios interceptors.
🔧 CANCEL_POLL_MS
Constant in node-cancel-watch.ts. Value 2000ms. Customizable via pollMs param of startNodeCancelWatch. Backend hardcodes 2s at the call site.
D nodeCancelContext (AsyncLocalStorage<AbortSignal>)
flux/node-cancel-watch.ts:19-21 · node-cancel-fetch.ts:17-35 · node-cancel-interceptor.ts:21-30
export const nodeCancelContext = new AsyncLocalStorage<NodeCancelEntry | undefined>()
Purpose. Same pattern as chargeContext. ALS that carries the AbortSignal of the current node. Global wrappers of fetch and axios read this ALS and inject the signal into every HTTP call made by the node handler. Cooperative via AbortController.
In short. If chargeContext is an invisible badge of "who's being charged", nodeCancelContext is an invisible badge of "who has cancellation alarm". Same mechanic. AsyncLocalStorage injected before the handler runs. The difference is who consumes it. Instead of billing service, it's global fetch and axios interceptors. Functions wrapping window.fetch and the axios instance. Before each HTTP request made by the handler, they read the signal from ALS and inject it into the call's init.signal. Native fetch and axios respect AbortSignal. If aborts, throws AbortError. Elegance. Handler doesn't even need to know cancel exists. Calls fetch('https://api.openai.com/...') normally. If watch aborted, this fetch throws AbortError as if it were timeout. The loop's try catches this at if (cancelWatch?.wasAborted()) and calls finishCancelledNode. Fragility. It's cooperative. If the handler does heavy synchronous SQL or in-memory computation without I/O, the abort interrupts nothing. Only the next HTTP call. Not preemptive. In sub-runs, the loop does nodeCancelContext.run(undefined, ...) to disable the parent context. If something escapes this scope, a handler may see undefined and the abort silences.

AbortSignal signals. Fetch and axios respect it and throw AbortError. If a handler does direct SQL query or heavy synchronous computation, the abort does not interrupt. Only the next HTTP call.

Not preemptive. It's what single-threaded Node.js can offer without worker_threads.
⚠️ Nested resets to undefined
In nested executions, the loop does nodeCancelContext.run(undefined, ...) at some call sites (flux.service.ts:5612, 5977). Intentional. Sub-run has its own watcher. If something escapes this scope, a handler may see undefined and disable the abort. Fragility that needs testing.

E finishCancelledNode({ ... })
flux.service.ts:2056-2107 · call site 4516-4530
await this.finishCancelledNode({ execId, node, flowId, myUpdatedNodes, schedState, userId, runType, elapsedMs, abortObserved, inFlightEnabled });
Purpose. Cleanup and persistence of the cancelled state. Called after the handler returns (after AbortError). Clears errors that may have been set by the abort, marks executionStatus='CANCELLED' in node_executions, fires WebSocket to notify the client and marks in the scheduler to stop the loop.
In short. It's the finisher that does cleanup after the alarm rang. When watch aborts and fetch or axios throws AbortError, the handler returns leaving the node in a somewhat confusing state. It may have written errorMessage to node.data ("network error"), may have partial output, may have left leftovers. This function comes after to clean up.
(1) Nulls out error fields. Cancel is not error for UX. Must be handled as its own state (gray, not red).
(2) UPDATE on node_executions setting executionStatus='CANCELLED' and cancelledAt=NOW(). Precise audit trail.
(3) Fires WebSocket so client can update UI in real time ("this node was cancelled").
(4) Marks the node in the scheduler so Phase 4 doesn't find it as "unprocessed".
(5) Sets stoppedByCancel = true and break. Exits while immediately.
Phase 4 then closes execution with "clean cancelled" status, not error. Also stores metrics. elapsedMs (how long the node ran before being cancelled) and abortObserved (whether cancel was observed by in-flight or only between nodes). Serve telemetry and measure system effectiveness in production. Only breaks the loop at this level. If it's sub-run, parent also needs to detect cancel on its next iteration.
// flux.service.ts:4516-4530 — call site if (cancelWatch?.wasAborted()) { await this.finishCancelledNode({ execId: runLogProcessId, node, flowId, myUpdatedNodes, schedState, userId: user.id, runType, elapsedMs: Date.now() - nodeStartedAtMs, abortObserved: Boolean(cancelWatch?.wasAborted()), inFlightEnabled, }); stoppedByCancel = true; break; }
↓
🪜 finishCancelledNode does
1 Clears errorMessage / errorStatusCode in node.data nulls out — cancel is not error
2 recordLegacyNodeCancelled(...) UPDATE node_executions SET executionStatus='CANCELLED', cancelledAt=NOW()
3 emitNodeStatus (WebSocket) notifies client with cancelled status
4 Marks in scheduler completed/dead so Phase 4 doesn't find as pending
5 stoppedByCancel = true; break exits while immediately
🎯 Cancel ≠ error
A cancelled node does not become a node with errorMessage. Phase 4.5 (friendly error preparation) MUST NOT report "execution failed at node X" when the reason was cancel. That's why finishCancelledNode explicitly clears error fields before persisting.

UI visually differentiates. Cancelled = gray / grayed out. Error = red.
📎 elapsedMs goes to telemetry
elapsedMs = Date.now() - nodeStartedAtMs. Uses the timer marked at 3.2. Goes to the cancellation log as a metric ("how long the node ran before being cancelled").
⚠️ Only breaks the loop at this level
If this is a sub-run (nested), the break only exits the sub-run's while. The caller (fluxBox handler in parent) receives the return and needs to handle the cancel too. Today parent still checks isCancelRequested on the next iteration and cancels too.
🔧 abortObserved param
Differentiates cancel observed by in-flight watch (fetch or axios threw AbortError) versus cancel only detected between nodes. Goes to telemetry. Measures effectiveness of in-flight.
Summary — what comes out of the Cancellation check:
• Happy path (no cancel): 100% no-op. Goes straight to step 3.5.
• Cancel between nodes detected: stoppedByCancel=true, break. Without executing node.
• Cancel during node: AbortError propagates, handler returns, finishCancelledNode records in node_executions, WebSocket, break.
• Phase 4 then sees: stoppedByCancel does not become fatal error. Execution ends "cancelled" clean.
Migration notes:
• System is new. Was added after the original doc. Still has parts marked with feature flag OFF (NODE_CANCEL_IN_FLIGHT_FLAG). May not be fully stable for production. Validate before migrating.
• Cancel base (via Postgres poll + WebSocket + status column) is portable. nodeCancelContext is ALS. Doesn't work when handler runs in the worker (different process). The worker would have to have its own mechanism. Temporal already supports workflow cancel natively via WorkflowHandle.cancel().
• Ideal for migration: align backend cancel with native Temporal cancel. Backend calls handle.cancel() when isCancelRequested=true. Worker respects via Context.current().cancelled. Much more robust than polling + AbortSignal.
• setInterval per node (60 nodes = 60 timers × 500ms each, today 2s) is CPU and DB source. If left on by default without optimization, becomes perf offender.
• It's cross-cutting and opt-in. Can wait for later in the migration plan. Temporal migration itself gives cancel semantics almost for free via workflowHandle.cancel(). Prioritize this after worker migrates.
• 1500ms cache plus 2000ms poll has latent race condition. Can have up to 3.5s delay between click and effective cancel. Acceptable, but document.

Cancellation check — feature flag NODE_CANCEL_IN_FLIGHT

Bloco espalhado em flux.service.ts:3184-3194 (setup), 3229-3239 (check entre nós), 3251-3269 (start watch por nó) e 4516-4530 (finish quando abortado). Sistema que permite o usuário cancelar uma execução em andamento. Hoje só habilitado para runType='canvas'.
Em resumo — o que esse passo faz
  • Porteiro decide se a execução é cancelável. shouldWatchCancellation só libera watch para runType='canvas' (editor) ou sub-runs que herdam do pai. API, chatbot, webhook e batch não são canceláveis. Semântica request-response não faz sentido interromper do servidor.
  • Vigia entre nós, polling passivo. Antes de cada iteração do while, isCancelRequested(runKey) consulta flow_run_states (com cache in-memory de 1.5s). Se cancel pendente, seta stoppedByCancel=true e faz break. Não interrompe nada em execução. Só evita começar o próximo nó.
  • Vigia dentro do nó (feature flag OFF em prod). Se NODE_CANCEL_IN_FLIGHT_FLAG estiver ligada, startNodeCancelWatch monta um setInterval de 2s por nó com AbortController. Quando o poll detecta cancel, chama controller.abort(). Custo: 100 nós = 100 timers paralelos. Provável motivo do flag ainda estar off.
  • Aborto cooperativo via ALS. nodeCancelContext (outra AsyncLocalStorage) carrega o AbortSignal para interceptors globais de fetch e axios. Cada request HTTP feita pelo handler ganha o signal automaticamente. Se aborta, levanta AbortError. O handler nem precisa saber que existe cancel. Não é preemptivo. SQL síncrono ou cálculo em memória continua rodando.
  • Encerrador limpa e persiste. Depois do AbortError, finishCancelledNode zera errorMessage (cancel não é erro. UI mostra cinza, não vermelho). Faz UPDATE em node_executions para executionStatus='CANCELLED', dispara WebSocket, marca no scheduler e sai do loop.
  • Saída. Caminho feliz vira 100% no-op. Se cancelou, a execução termina com status "cancelado limpo" (não erro fatal) e a Fase 4 fecha o cleanup normalmente.
Contexto. Este é o único passo do diagrama novo pós-doc. Não existia na versão original documentada. Foi adicionado depois para atender o botão "cancelar" no editor. Funciona em dois níveis. (1) Checagem entre nós (sempre que watchEnabled=true). (2) Checagem durante o nó via AbortSignal em fetch e axios (só quando feature flag NODE_CANCEL_IN_FLIGHT_FLAG está ligada).

Propósito. Setup uma vez por execução, antes do while começar. Decide se a execução é elegível para observar cancelamento e qual chave usar para consultar o status (parentRunId em execuções aninhadas, processId próprio caso contrário).
Em resumo. É o porteiro que responde três perguntas antes da execução começar.
(1) "Este tipo de execução permite cancelar?" Só canvas (do editor) permite. API, chatbot, form, batch e webhook não. É intencional. Request-response síncrono não faz sentido cancelar do lado servidor sem o cliente pedir.
(2) "Este é um sub-run herdando de um pai?" Se sim, herda watch do pai. Cancelar o pai propaga para todos os filhos.
(3) "Qual chave usar para consultar cancelamento?" Se é nested, usa o id do root (todos os filhos consultam a mesma chave e cancelam juntos). Se é top-level, usa o próprio processId.
Depois vem a segunda camada. Mesmo com watch habilitado, só se a feature flag NODE_CANCEL_IN_FLIGHT_FLAG estiver ligada é que o cancel durante a execução do nó funciona (polling e AbortSignal). Sem a flag, só checa cancel entre nós. Um LLM streaming a resposta continua até terminar, mesmo se o usuário clicou "cancelar". A flag está desligada em produção hoje. Sugere duas coisas. (a) O sistema é novo e ainda não passou em bateria de testes em larga escala. (b) O custo de rodar 60 setIntervals paralelos em execuções grandes ainda está sendo avaliado.

🎯 Por que só canvas cancela?
Execuções de API (runType='api') têm semântica "request-response". O cliente já está esperando síncrono. Cancelar do lado servidor sem cliente pedir seria confuso.

Já canvas é execução no editor. O usuário clica "cancelar" e espera parada real.
📎 Nested herda watch
Um fluxBox ou libraryNode chama apiV2 recursivamente para o sub-flow. Como isNestedRun=true, o watch é habilitado no filho também. Assim, cancelar o pai propaga. O filho consulta a mesma cancelRunKey (pai) e vê o cancel request.
🔧 Feature flag stringly-typed
'node_cancel_in_flight' como string literal em NODE_CANCEL_IN_FLIGHT_FLAG. Rollout gradual. Dá para ativar por espaço ou user via featureFlagsService. Setup padrão: OFF em produção (hoje).
B runCancellationService.isCancelRequested(runId)
executions_logs/run-cancellation.service.ts:62-79 · flux.service.ts:3229-3239
async isCancelRequested(runId: string): Promise<boolean> · check no topo do while
Propósito. Checagem entre nós. No início de cada iteração do while, consulta se algum cliente pediu cancel. Se sim, seta stoppedByCancel=true e faz break. Não interrompe nó em execução. Só evita começar o próximo.
Em resumo. É um vigia no batente da porta do próximo nó. Antes de deixar cada nó entrar em execução, o vigia olha na "lista de cancelamento" (tabela flow_run_states). Se o runId do agente atual está lá, fecha a porta. stoppedByCancel = true e break. O nó nem começa a rodar. É deliberadamente polido. Não interrompe nada em execução, só previne o próximo. Se o usuário clicou "cancelar" enquanto um textGenerator está streaming, esse vigia só age depois que o streaming terminar. Para interromper mid-execution precisa do watch in-flight (fn C). Como não vale a pena consultar Postgres a cada 100ms numa execução com 100 nós rápidos, o serviço tem um cache in-memory com TTL de 1500ms. Se consultou faz menos de 1.5s, retorna o resultado do cache sem hit no banco. O usuário pode ter até 1.5s de atraso entre clicar "cancelar" e ver efeito. Isso é indistinguível de latência normal de UI. Se cancel é confirmado, o cleanup vai para Fase 4 normal (não vira erro), a execução termina com status cancelado, e o cliente vê a mensagem apropriada.

B2 Tabela flow_run_states
Linha inserida pelo endpoint POST /executions_logs/runs/:runId/cancel (executions_logs.controller.ts:101-111). Campos: runId, flowId, userId, requestedAt, deletedAt. Existência da linha = cancel pendente.
🎯 Cache TTL=1500ms
Evita hammer no Postgres em execuções longas com muitos nós. Trade-off. Pode demorar até 1.5s para o cancel ser observado. Aceitável para UX de "cancelar". O usuário não nota diferença entre 200ms e 1500ms.
⚠️ Cancel entre nós ≠ abort do nó atual
Se um textGenerator está streaming resposta e o usuário clica cancelar durante o streaming, esta checagem não interrompe. Só evita começar o próximo nó. Para interromper mid-execution, precisa do watch in-flight (fn C) e dos interceptors de fetch e axios (fn D).
🔧 Como o cancel é setado
POST /executions_logs/runs/:runId/cancel chama executionsLogsService.requestRunCancellation(user, runId), que:
• Valida permissões e status (só canvas, execução precisa estar running)
• Chama runCancellationService.requestCancel({ runId, flowId, userId })
• INSERT em flow_run_states
• interruptStepsInFlight(runId) para abort imediato
C startNodeCancelWatch({ runId, nodeId, isCancelRequested })
flux/node-cancel-watch.ts:56-93 · flux.service.ts:3251-3261
shouldStartNodeCancelWatch({ watchEnabled, inFlightEnabled }) ? startNodeCancelWatch({...}) : null
Propósito. Se ambos watchEnabled e inFlightEnabled forem true, cria um watcher POR NÓ que faz polling a cada 2s (CANCEL_POLL_MS=2000) para isCancelRequested. Quando detectar cancel, chama controller.abort() no AbortController que foi entregue via cancelWatch.entry.
Em resumo. Se o vigia da porta (fn B) é passivo, este é o vigia dentro da sala. Durante o nó rodar, esse watcher bate no relógio a cada 2 segundos perguntando "e agora, cancelaram?". Quando a resposta é sim, puxa a corda do sino: controller.abort(). Um AbortSignal corre por todos os fetch e axios em andamento dentro daquele nó. Cada um levanta AbortError. É como um alarme cooperativo. As chamadas HTTP escolhem respeitar o signal (padrão web moderno). O watcher devolve 3 coisas ao loop.
• entry: o AbortSignal e metadata para ser injetado na ALS nodeCancelContext.
• wasAborted(): função que o loop chama depois para saber se ocorreu abort.
• stop(): para limpar o setInterval quando o nó termina. Sem isso, timers vazam.
Ponto crítico de perf. Um agente com 100 nós tem 100 setIntervals rodando ao mesmo tempo, cada um consultando Postgres. Com cache 1.5s ainda dá ~66 queries por segundo. É por isso que a feature flag está OFF em prod hoje. Solução real e definitiva vai vir com Temporal. WorkflowHandle.cancel() nativo, sem polling, sem timer, sem custo constante.
// flux/node-cancel-watch.ts:56-93 — resumo export function shouldStartNodeCancelWatch(params) { return params.watchEnabled && params.inFlightEnabled; } export function startNodeCancelWatch(params) { const controller = new AbortController(); let aborted = false; const timer = setInterval(async () => { if (await params.isCancelRequested(params.runId)) { aborted = true; controller.abort(); clearInterval(timer); } }, CANCEL_POLL_MS); return { entry: { signal: controller.signal, runId, nodeId }, wasAborted: () => aborted, stop: () => clearInterval(timer), }; }

⚠️ setInterval por nó = memory footprint
Se um agente tem 100 nós, isso é 100 setIntervals de 2s executando em paralelo. Cada um chama isCancelRequested. Com cache de 1500ms, ainda assim vira 66 queries por segundo no Postgres.

Talvez seja um dos motivos da feature flag estar OFF em prod hoje.
🎯 Watch é PER-NODE, não per-run
Cada iteração do while cria um novo watcher com um novo AbortController. Cada nó tem seu próprio async chain e precisa do próprio AbortSignal para os interceptors de fetch e axios.
🔧 CANCEL_POLL_MS
Constante em node-cancel-watch.ts. Valor 2000ms. Customizável via param pollMs do startNodeCancelWatch. Backend hardcoda 2s no call-site.
D nodeCancelContext (AsyncLocalStorage<AbortSignal>)
flux/node-cancel-watch.ts:19-21 · node-cancel-fetch.ts:17-35 · node-cancel-interceptor.ts:21-30
export const nodeCancelContext = new AsyncLocalStorage<NodeCancelEntry | undefined>()
Propósito. Mesmo padrão de chargeContext. ALS que carrega o AbortSignal do nó atual. Wrappers globais de fetch e axios leem essa ALS e injetam o signal em toda chamada HTTP feita pelo handler do nó. Cooperativa via AbortController.
Em resumo. Se o chargeContext é um crachá invisível de "quem está cobrando", o nodeCancelContext é um crachá invisível de "quem tem alarme de cancelamento". Mesma mecânica. AsyncLocalStorage injetada antes do handler rodar. A diferença é quem consome. Em vez de serviço de billing, são interceptors globais de fetch e axios. Funções que envolvem window.fetch e o instance do axios. Antes de cada request HTTP feito pelo handler, leem o signal da ALS e o injetam no init.signal da chamada. Fetch e axios nativos respeitam AbortSignal. Se aborta, levanta AbortError. Elegância. O handler nem precisa saber que existe cancel. Chama fetch('https://api.openai.com/...') normalmente. Se o watch abortou, esse fetch levanta AbortError como se fosse timeout. O try do loop pega isso em if (cancelWatch?.wasAborted()) e chama finishCancelledNode. Fragilidade. É cooperativa. Se o handler fizer SQL síncrono pesado ou cálculo em memória sem I/O, o abort não interrompe nada. Só a próxima chamada HTTP. Não é preemptivo. Em sub-runs, o loop faz nodeCancelContext.run(undefined, ...) para desligar o contexto do parent. Se algo escapar desse escopo, um handler pode ver undefined e o abort silencia.

↳ Consumo: node-cancel-interceptor.ts:21-30 (axios interceptor)
Interceptor do axios (request). Lê currentNodeAbortSignal() (helper que faz nodeCancelContext.getStore()?.signal), injeta em config.signal. Mesmo mecanismo.
🎯 Cooperativa, não hard-kill
AbortSignal sinaliza. Fetch e axios respeitam e levantam AbortError. Se um handler fizer SQL query direto ou cálculo síncrono pesado, o abort não interrompe. Só a próxima chamada HTTP.

Não é preemptivo. É o que Node.js single-threaded pode oferecer sem worker_threads.
⚠️ Nested reseta para undefined
Em execuções aninhadas, o loop faz nodeCancelContext.run(undefined, ...) em alguns call-sites (flux.service.ts:5612, 5977). É intencional. Sub-run tem seu próprio watcher. Se algo escapar desse escopo, um handler pode ver undefined e desligar o abort. Fragilidade que precisa de teste.

E finishCancelledNode({ ... })
flux.service.ts:2056-2107 · call site 4516-4530
await this.finishCancelledNode({ execId, node, flowId, myUpdatedNodes, schedState, userId, runType, elapsedMs, abortObserved, inFlightEnabled });
Propósito. Cleanup e persistência do estado cancelado. Chamado depois do handler retornar (após AbortError). Limpa erros que possam ter sido setados pelo abort, marca executionStatus='CANCELLED' em node_executions, dispara WebSocket avisando o cliente e marca no scheduler para parar o loop.
Em resumo. É o encerrador que faz o cleanup depois que o alarme tocou. Quando o watch aborta e fetch ou axios levanta AbortError, o handler retorna deixando o nó num estado meio confuso. Pode ter escrito errorMessage em node.data ("network error"), pode ter saída parcial, pode ter deixado sujeira. Esta função vem depois para limpar.
(1) Zera os campos de erro. Cancel não é erro para UX. Tem que ser tratado como estado próprio (cinza, não vermelho).
(2) UPDATE em node_executions setando executionStatus='CANCELLED' e cancelledAt=NOW(). Audit trail preciso.
(3) Dispara WebSocket para o cliente atualizar a UI em tempo real ("esse nó foi cancelado").
(4) Marca o nó no scheduler para a Fase 4 não achar como "não processado".
(5) Seta stoppedByCancel = true e break. Sai do while imediatamente.
A Fase 4 então fecha a execução com status "cancelado limpo", não com erro. Também guarda métricas. elapsedMs (quanto o nó rodou antes de ser cancelado) e abortObserved (se o cancel foi observado pelo in-flight ou só entre nós). Servem para telemetria e para medir a eficácia do sistema em produção. Só quebra o loop deste nível. Se é sub-run, o parent precisa também detectar o cancel na sua próxima iteração.
// flux.service.ts:4516-4530 — call site if (cancelWatch?.wasAborted()) { await this.finishCancelledNode({ execId: runLogProcessId, node, flowId, myUpdatedNodes, schedState, userId: user.id, runType, elapsedMs: Date.now() - nodeStartedAtMs, abortObserved: Boolean(cancelWatch?.wasAborted()), inFlightEnabled, }); stoppedByCancel = true; break; }
↓
🪜 finishCancelledNode faz
1 Limpa errorMessage / errorStatusCode em node.data nulls out — cancel não é erro
2 recordLegacyNodeCancelled(...) UPDATE node_executions SET executionStatus='CANCELLED', cancelledAt=NOW()
3 emitNodeStatus (WebSocket) notifica cliente com status cancelado
4 Marca no scheduler completed/dead pra Fase 4 não achar como pending
5 stoppedByCancel = true; break sai do while imediatamente
🎯 Cancel ≠ erro
Um nó cancelado não vira nó com errorMessage. A Fase 4.5 (preparação de erro amigável) NÃO deve reportar "execution failed at node X" quando o motivo foi cancel. Por isso finishCancelledNode explicitamente limpa os campos de erro antes de persistir.

UI diferencia visualmente. Cancelado = cinza / grayed out. Erro = vermelho.
📎 elapsedMs vai pra telemetria
elapsedMs = Date.now() - nodeStartedAtMs. Usa o timer marcado em 3.2. Vai para o log de cancelamento como métrica ("quanto tempo o nó rodou antes de ser cancelado").
⚠️ Só quebra o loop deste nível
Se este é um sub-run (nested), o break só sai do while do sub-run. O caller (handler do fluxBox no parent) recebe o retorno e precisa lidar com o cancel também. Hoje o parent ainda checa isCancelRequested na próxima iteração e cancela também.
🔧 abortObserved param
Diferencia cancel observado pelo watch in-flight (fetch ou axios levantou AbortError) versus cancel só detectado entre nós. Vai para telemetria. Mede a eficácia do in-flight.
Resumo — o que sai do Cancellation check:
• Caminho feliz (sem cancel): 100% no-op. Passa direto para o passo 3.5.
• Cancel entre nós detectado: stoppedByCancel=true, break. Sem executar nó.
• Cancel durante nó: AbortError propaga, handler retorna, finishCancelledNode registra em node_executions, WebSocket, break.
• Fase 4 depois vê: stoppedByCancel não vira erro fatal. A execução termina "cancelado" limpo.
Observações para migração:
• Sistema é novo. Foi adicionado depois do doc original. Ainda tem partes marcadas com feature flag OFF (NODE_CANCEL_IN_FLIGHT_FLAG). Pode não estar totalmente estável para produção. Validar antes de migrar.
• Base do cancel (via Postgres poll + WebSocket + status column) é portável. nodeCancelContext é ALS. Não funciona quando o handler roda no worker (outro processo). O worker teria que ter seu próprio mecanismo. Temporal já suporta workflow cancel nativamente via WorkflowHandle.cancel().
• Ideal na migração: alinhar cancel do backend com cancel nativo do Temporal. Backend chama handle.cancel() quando isCancelRequested=true. O worker respeita via Context.current().cancelled. Muito mais robusto que polling + AbortSignal.
• setInterval por nó (60 nós = 60 timers × 500ms cada, hoje 2s) é fonte de CPU e BD. Se ficar ligado por padrão sem otimização, vira ofensor de perf.
• É cross-cutting e opt-in. Pode ficar para depois no plano de migração. A migração para o Temporal por si só dá cancel semântica quase de graça via workflowHandle.cancel(). Priorizar isso depois do worker migrar.
• Cache de 1500ms mais poll de 2000ms tem race condition latente. Pode ter até 3.5s de delay entre o clique e o cancel efetivo. Aceitável, mas documentar.

Step 4.1 — Unprocessed nodes detection

Block in flux.service.ts:4735-4778. After the main loop finishes, compares schedState.nodeIds with completed ∪ dead. If any id remains, writes an error via Winston with error_type='flow_truncated'. The log only fires when the execution was neither cancelled nor stopped by node failure or loop.
In summary — what this step does
  • Runs the post-mortem check. After the loop finishes, computes nodeIds - (completed + dead). Detects reachable nodes that were never executed nor pruned.
  • Cancel has its own cleanup. If the execution was cancelled, computes the stoppedAtNodeId. Persists it in runCancellationService. Fires a WebSocket with status CANCELLED for each pending node. The client sees the grey UI on each one.
  • Filters out the legitimate reasons. Only writes a warning if orphan nodes remain and the execution didn't stop due to natural loop, node failure or cancel. In those 3 cases, unprocessed is expected.
  • When it shows up, it's a real bug. The Winston log fires with error_type='flow_truncated' and unprocessedNodeIds.slice(0, 20). It's a high-signal string, monitored by SRE in dashboards.
  • Output. Pure observability. Doesn't change the execution's return nor affect 4.2 onward. Only emits logs. In the cancel case, updates WebSocket and the cancellation database.
Context. Not blocking. Deals only with observability. Detects scheduler bugs or orphan branches. When all reachable nodes were already expected in chains that wouldn't be completed by design (for example, loop stoppedByLoopBehavior), the check is skipped. In those cases there's no warning.

AunprocessedNodeIds calc
flux.service.ts:4735-4737
const unprocessedNodeIds = [...schedState.nodeIds].filter(nid => !schedState.completed.has(nid) && !schedState.dead.has(nid));
Purpose. Performs a set difference. Takes the reachable nodes and removes the processed ones (completed) and the pruned ones (dead). What remains is considered unprocessed. Those nodes never executed for some reason.
In summary. This is the post-mortem check. After the loop finishes by natural exhaustion or by break, the code asks which nodes were summoned but never got to run nor were discarded. Compares schedState.nodeIds (all reachable) against completed (ran and left) and dead (cancelled or pruned by branch). The remainder is a list of ghost nodes. Those nodes should have run but got stuck. Usually the cause is a dependency on some node that never completed. It can also be a scheduler bug that forgot to unblock them. Or it can be by design in stoppedByNodeFailure, stoppedByCancel or stoppedByLoopBehavior. Doesn't affect return nor UI. Only goes to Winston for debug. In normal executions, the list is always empty. All reachable nodes run or die. In executions aborted for any reason, the list contains the nodes that didn't get their turn. It's natural, not a bug.

🎯 Simple set difference
nodeIds - (completed + dead). The processedNodeIds coming from function B of 3.2 has another list. That second one is used in the final log, not for unprocessed.
📎 Set spread
[...schedState.nodeIds] converts the Set into an array to use .filter. O(n) cost over reachable nodes.
BCancel footprint (special path)
flux.service.ts:4738-4758
if (stoppedByCancel) { const footprint = resolveCancelledRunFootprint(...); await runCancellationService.markCancelled(...); emitCancelledRunStatuses(...); }
Purpose. If the execution was cancelled, the backend does extra bookkeeping. Marks in the cancellation service which was the last node to run and which stayed pending. Emits status CANCELLED via WebSocket for each pending node. The client sees the grey UI on each non-executed node.
In summary. When cancel happens, unprocessedNodeIds grows. It ends up containing everything that came after the cancel point. Logging that as "truncated flow" would be a false alarm. The backend does a specific cleanup. First, resolveCancelledRunFootprint computes which node stopped the execution (stoppedAtNodeId) and the pending list (notExecutedNodeIds). Second, runCancellationService.markCancelled persists those details in the database. Marks the flow_run_states row as cancelled with metadata. Third, emitCancelledRunStatuses fires WebSocket for each pending id with status CANCELLED. The UI receives multiple updates and paints each pending node grey. The footprint is useful for the dashboard to show where the cancel happened.
if (stoppedByCancel) { const footprint = resolveCancelledRunFootprint({ nodeIds: schedState.nodeIds, completed: schedState.completed, dead: schedState.dead, lastExecutedNodeId, nodes: myUpdatedNodes, }); await this.runCancellationService.markCancelled({ runId: runLogProcessId, stoppedAtNodeId: footprint.stoppedAtNodeId, notExecutedNodeIds: footprint.notExecutedNodeIds, }); this.emitCancelledRunStatuses({ /* runId, flowId, userId, nodeIds */ }); }
🎯 Cancel is first-class
It's not just a suppressed error. It has a dedicated service (runCancellationService), a dedicated table (flow_run_states) and a dedicated notification. The path is well separated.
🔧 lastExecutedNodeId
Populated along the 3.2 loop, at each iteration. Here it identifies where cancel hit. Valuable info for debug and telemetry.
CGate: when to log warning
flux.service.ts:4759-4763
if (unprocessedNodeIds.length > 0 && !stoppedByLoopBehavior && !stoppedByNodeFailure && !stoppedByCancel) { loggerService.error(...) }
Purpose. The warning only appears under four simultaneous conditions. There must be unprocessed nodes. The execution can't have stopped by loop behavior. Natural loop exhaustion is not a bug. The execution can't have failed. Fail-fast leaves nodes pending by design. The execution can't have been cancelled. Cancel also leaves nodes pending. Only writes warning in an unexpected scenario.
In summary. This is the filter for the legitimate reasons. There are 3 valid reasons to have unprocessed nodes without it being a bug. First, the loop had an arrayNode that ended naturally and left the rest of the subgraph disconnected (stoppedByLoopBehavior=true). Second, some node failed fatally (stoppedByNodeFailure=true). Fail-fast semantics. Third, the user cancelled (stoppedByCancel=true). In those 3 cases the unprocessed is expected. The log doesn't fire. It only fires if none of those happened and there's still an unexecuted node. That indicates scheduler bug or badly assembled graph. Rare in normal production. When it appears in the logs, someone needs to investigate. The log carries unprocessedNodeIds.slice(0, 20). The slice limits volume for gigantic agents. The error_type is flow_truncated.

DloggerService.error (Winston)
flux.service.ts:4765-4777
this.loggerService.error({ message: 'Flow run ended before processing all connected nodes...', metadata: { status: 500, error_type: 'flow_truncated', ... } });
Purpose. Structured log via Winston with error_type='flow_truncated'. The payload carries the message with count (processed/total), unprocessed ids (max 20), flowId, sessionId and user. Written to stdout. In production, it's captured by the container or the log aggregator.
In summary. Winston is the default NestJS logger on the base. The error level is the highest and triggers telemetry. The error_type: 'flow_truncated' is the key for alert dashboards. SRE monitors that string. The message includes the count (processedNodeIds.size/allNodesIds.length). Gives quick context, for example "processed 8 out of 12 nodes". The slice(0, 20) over unprocessedNodeIds is defensive. Without it, an agent with 500 orphan nodes would generate a huge log. The structure is the project's standard (JSON metadata, no content PII).
this.loggerService.error({ message: `Flow run ended before processing all connected nodes (${processedNodeIds.size}/${allNodesIds.length})`, metadata: { status: 500, error_type: 'flow_truncated', user: user as User, other: { flowId, sessionId: sessionId || 'default', unprocessedNodeIds: unprocessedNodeIds.slice(0, 20), }, }, });
🎯 No side effects
Only writes a log. Doesn't modify state, doesn't return anything, doesn't change Phase 4.2 onward. Pure observability.
Summary — what comes out of 4.1.
• In normal execution, without stop flags, there's no log. The unprocessedNodeIds should be empty.
• On cancel, fires runCancellationService.markCancelled plus emitStatuses via WebSocket.
• On bug, a Winston log fires with flow_truncated and the affected ids.
• Pure observability. Doesn't change the execution's return.
Notes for migration.
• It's diagnostic. If the scheduler in the worker is reliable, this check can turn into an assertion. Throw in dev, log in production.
• The cancel footprint needs to keep existing for cancel UX. The dashboard shows "cancelled at node X" to the user.
• Can go last in the migration plan. Doesn't block anything.

Passo 4.1 — Detecção de nós não-processados

Bloco em flux.service.ts:4735-4778. Depois que o loop principal termina, compara schedState.nodeIds com completed ∪ dead. Se sobrar algum id, grava um error via Winston com error_type='flow_truncated'. O log só sai quando a execução não foi cancelada nem parou por node failure ou loop.
Em resumo — o que esse passo faz
  • Faz o check post-mortem. Depois que o loop termina, calcula nodeIds - (completed + dead). Detecta nós reachable que nunca foram executados nem podados.
  • Cancel tem cleanup próprio. Se a execução foi cancelada, calcula o stoppedAtNodeId. Persiste em runCancellationService. Dispara WebSocket com status CANCELLED para cada nó pendente. O cliente vê a UI cinza em cada um.
  • Filtra os motivos legítimos. Só grava warning se sobrou nó órfão e a execução não parou por loop natural, node failure ou cancel. Nesses 3 casos, o unprocessed é esperado.
  • Quando aparece, é bug real. O log Winston sai com error_type='flow_truncated' e unprocessedNodeIds.slice(0, 20). É uma string de alto sinal, monitorada por SRE em dashboards.
  • Saída. Pura observabilidade. Não altera o retorno da execução nem afeta 4.2 em diante. Apenas emite logs. No caso de cancel, atualiza WebSocket e o banco de cancelamento.
Contexto. Não é bloqueante. Trata apenas de observabilidade. Detecta bugs de scheduler ou branches órfãs. Quando todos os nós reachable já eram esperados em cadeias que não seriam completadas por design (por exemplo, loop stoppedByLoopBehavior), o check é pulado. Nesses casos não há warning.

AunprocessedNodeIds calc
flux.service.ts:4735-4737
const unprocessedNodeIds = [...schedState.nodeIds].filter(nid => !schedState.completed.has(nid) && !schedState.dead.has(nid));
Propósito. Faz uma diferença de conjuntos. Toma os nós reachable e remove os processados (completed) e os podados (dead). O que sobra é considerado não-processado. Esses nós nunca executaram por algum motivo.
Em resumo. Este é o check post-mortem. Depois que o loop termina por natural exhaustion ou por break, o código pergunta quais nós foram convocados mas nunca chegaram a rodar nem foram descartados. Compara schedState.nodeIds (todos os reachable) contra completed (rodaram e saíram) e dead (cancelados ou podados por branch). O restante é uma lista de nós fantasmas. Esses nós deveriam ter rodado mas ficaram presos. Em geral a causa é dependência em algum nó que nunca completou. Também pode ser bug no scheduler que esqueceu de destravá-los. Ou pode ser por design em stoppedByNodeFailure, stoppedByCancel ou stoppedByLoopBehavior. Não afeta retorno nem UI. Só vai para o Winston para debug. Em execuções normais, a lista fica sempre vazia. Todos os nós reachable rodam ou morrem. Em execuções abortadas por qualquer razão, a lista contém os nós que não chegaram na vez deles. É natural, não é bug.

nodeIds - (completed + dead). O processedNodeIds vindo da função B de 3.2 tem outra lista. Essa segunda é usada no log final, não para unprocessed.
📎 Spread do Set
[...schedState.nodeIds] converte o Set em array para usar .filter. Custo O(n) em nós reachable.
BCancel footprint (path especial)
flux.service.ts:4738-4758
if (stoppedByCancel) { const footprint = resolveCancelledRunFootprint(...); await runCancellationService.markCancelled(...); emitCancelledRunStatuses(...); }
Propósito. Se a execução foi cancelada, o backend faz bookkeeping extra. Marca no serviço de cancellation qual foi o último nó a rodar e quais ficaram pendentes. Emite status CANCELLED via WebSocket para cada nó pendente. O cliente vê a UI cinza em cada nó não executado.
Em resumo. Quando o cancel acontece, o unprocessedNodeIds cresce. Ele passa a conter tudo o que vinha depois do ponto de cancel. Registrar isso como "flow truncado" seria alarme falso. O backend faz um cleanup específico. Primeiro, resolveCancelledRunFootprint calcula qual nó parou a execução (stoppedAtNodeId) e a lista pendente (notExecutedNodeIds). Segundo, runCancellationService.markCancelled persiste esses detalhes no banco. Marca a linha de flow_run_states como cancelada com metadata. Terceiro, emitCancelledRunStatuses dispara WebSocket para cada id pendente com status CANCELLED. A UI recebe múltiplos updates e pinta cada nó pendente de cinza. O footprint é útil para o dashboard mostrar onde o cancel aconteceu.
if (stoppedByCancel) { const footprint = resolveCancelledRunFootprint({ nodeIds: schedState.nodeIds, completed: schedState.completed, dead: schedState.dead, lastExecutedNodeId, nodes: myUpdatedNodes, }); await this.runCancellationService.markCancelled({ runId: runLogProcessId, stoppedAtNodeId: footprint.stoppedAtNodeId, notExecutedNodeIds: footprint.notExecutedNodeIds, }); this.emitCancelledRunStatuses({ /* runId, flowId, userId, nodeIds */ }); }
🎯 Cancel é first-class
Não é apenas um erro suprimido. Tem serviço dedicado (runCancellationService), tabela dedicada (flow_run_states) e notificação dedicada. O caminho é bem separado.
🔧 lastExecutedNodeId
Populado ao longo do loop em 3.2, a cada iteração. Aqui identifica onde o cancel pegou. Informação valiosa para debug e telemetria.
CGate: quando logar warning
flux.service.ts:4759-4763
if (unprocessedNodeIds.length > 0 && !stoppedByLoopBehavior && !stoppedByNodeFailure && !stoppedByCancel) { loggerService.error(...) }
Propósito. O warning só aparece em quatro condições simultâneas. Deve haver nós não-processados. A execução não pode ter parado por loop behavior. Loop natural exhaustion não é bug. A execução não pode ter falhado. Fail-fast deixa nós pendentes por design. A execução não pode ter sido cancelada. Cancel também deixa nós pendentes. Só grava warning em cenário inesperado.
Em resumo. Esta é a filtragem dos motivos legítimos. Existem 3 razões válidas para ter nós não-processados sem ser bug. Primeiro, o loop tinha um arrayNode que terminou naturalmente e deixou o resto do subgrafo desconectado (stoppedByLoopBehavior=true). Segundo, algum nó falhou fatal (stoppedByNodeFailure=true). Semântica fail-fast. Terceiro, o usuário cancelou (stoppedByCancel=true). Nesses 3 casos o unprocessed é esperado. O log não sai. Só sai se nenhum desses aconteceu e ainda assim sobrou nó não executado. Isso indica bug no scheduler ou grafo mal montado. Raro em produção normal. Quando aparece nos logs, alguém precisa investigar. O log traz unprocessedNodeIds.slice(0, 20). O slice limita o volume para agentes gigantes. O error_type é flow_truncated.

DloggerService.error (Winston)
flux.service.ts:4765-4777
this.loggerService.error({ message: 'Flow run ended before processing all connected nodes...', metadata: { status: 500, error_type: 'flow_truncated', ... } });
Propósito. Log estruturado via Winston com error_type='flow_truncated'. O payload traz mensagem com contagem (processed/total), ids não-processados (máximo 20), flowId, sessionId e user. Sai em stdout. Em produção, é capturado pelo container ou pelo log aggregator.
Em resumo. O Winston é o logger padrão do NestJS na base. Nível error é o mais alto e dispara telemetria. O error_type: 'flow_truncated' é a chave para dashboards de alertas. O SRE monitora essa string. A mensagem inclui a contagem (processedNodeIds.size/allNodesIds.length). Dá contexto rápido, por exemplo "processou 8 de 12 nós". O slice(0, 20) em unprocessedNodeIds é defensivo. Sem ele, um agente com 500 nós órfãos geraria um log enorme. A estrutura é o padrão do projeto (metadata JSON, sem PII de conteúdo).
this.loggerService.error({ message: `Flow run ended before processing all connected nodes (${processedNodeIds.size}/${allNodesIds.length})`, metadata: { status: 500, error_type: 'flow_truncated', user: user as User, other: { flowId, sessionId: sessionId || 'default', unprocessedNodeIds: unprocessedNodeIds.slice(0, 20), }, }, });
🎯 Sem side effects
Apenas grava log. Não modifica estado, não retorna nada, não altera a Fase 4.2 em diante. Pura observabilidade.
Resumo — o que sai de 4.1.
• Em execução normal, sem stop flags, não há log. O unprocessedNodeIds deve estar vazio.
• Em cancel, dispara runCancellationService.markCancelled mais emitStatuses via WebSocket.
• Em bug, sai log Winston com flow_truncated e os ids afetados.
• Pura observabilidade. Não altera o retorno da execução.
Observações para migração.
• É diagnóstico. Se o scheduler no worker for confiável, este check pode virar assertion. Throw em dev, log em produção.
• O cancel footprint precisa continuar existindo para a UX de cancel. O dashboard mostra "cancelou no nó X" para o usuário.
• Pode ficar por último no plano de migração. Não bloqueia nada.

Step 3.7 — Per-node token/cost accounting

Block at flux.service.ts:2280-2283 (closure), 3248-3249 (before snapshot), 3296-3297 (second read) and 4537-4546 (delta in endNode). No table and no service. Pure arithmetic on global execution variables, plus mutation closure.
In short — what this step does
  • Accounts for token spend and cost per node. Pure arithmetic over global execution variables (totalTokensUsed, totalCost). No service and no table. Only two variables live in the apiV2() scope.
  • Closure onUpdateTokens for the legacy path. Works like a change tray passed as an argument to the legacy handlers (LLM, image, audio, embedding). Each handler calls onUpdateTokens(delta, cost). The closure adds to the accumulators. It works because Node.js is single-threaded. No lock, no race.
  • Per-node delta via before/after snapshot. At the start of the node try, it saves genericTokensBefore = totalTokensUsed. After the handler, it computes the delta as current value minus snapshot. The delta goes to the RunLogNode in 3.9. It is robust as long as there is no parallelism between nodes.
  • AsyncLocalStorage for implicit propagation. chargeContext injects { execId, nodeId } into the ALS before the handler. When ProductService.updateTokens (shared with the public API) inserts a row into token_transactions, it queries the ALS to know which node to attribute the charge to.
  • Temporal path uses HTTP and SUM in the database. Handlers in the worker cannot touch the closure. It is another process. They charge via /worker/charge-tokens. On the return of processNodeViaTemporal, the backend calls sumChargesByExecution(execId, nodeId). It aggregates from the database and adds to totalTokensUsed. There is per-node overhead of HTTP and SQL. Ensures consistency between paths.
  • Output. totalTokensUsed and totalCost reflect post-node consumption. Delta attributed to the RunLogNode. Row in token_transactions written as audit trail. Two mechanisms converge into a single in-memory source of truth.
Context. Billing is cross-cutting (memory [[project_execution_architecture]]). The execution total lives in totalTokensUsed and totalCost. It is mutated by callback when LLM, API, or embedding calls charge tokens. The per-node delta is computed by before/after difference. Two possible sources. Legacy handlers call onUpdateTokens(delta, cost) directly. Temporal handlers charge via HTTP /worker/charge-tokens. Later, sumChargesByExecution(execId, nodeId) aggregates from the database.

AonUpdateTokens (closure)
flux.service.ts:2280-2283
const onUpdateTokens = (tokensUsed: number, cost: number) => { totalTokensUsed += tokensUsed; totalCost += cost; };
Purpose. Callback closure created at the start of apiV2(). Passed as an argument to all legacy handlers that perform charging (LLM, embedding, and others). Each handler calls onUpdateTokens(delta, cost) after each charged operation. The closure mutates the variables of the parent scope.
In short. It works like a change tray on the apiV2() table. Whenever a handler consumes tokens (called the LLM, generated an embedding, transcribed audio), it reports the consumption via onUpdateTokens(300, 0.002). The closure accepts the value and adds to the global accumulators of the execution. It is a closure. The function is defined in the apiV2 scope and accesses the variables totalTokensUsed and totalCost. Mutating inside the function directly changes the execution variables. Without going through a service, without I/O, without distributed consistency. It is simple, synchronous, and works because everything lives in the same process. Each handler receives this reference by argument, not by injection. It is a functional dependency injection pattern. Temporal handlers do not call this closure. They charge by HTTP directly on /worker/charge-tokens. The backend later reads via sumChargesByExecution (fn D). No worker, no HTTP, and no lock. There is no real parallelism either.
let totalTokensUsed = 0; let totalCost = 0; const onUpdateTokens = (tokensUsed: number, cost: number) => { totalTokensUsed += tokensUsed; totalCost += cost; };
↓
A1 Passed to legacy handlers
Handlers such as voiceNode, imageGeneratorNode, webSearchNode, audioReaderNode, and commandContentNode receive onUpdateTokens as argument. They call it during execution. Dispatch at flux.service.ts:3380, 3615, 3706, 3722, 3712.
🎯 No lock, single-threaded works
Node.js is single-threaded on the event loop. Mutating totalTokensUsed += x never causes a race. There are no 2 handlers truly running in parallel. Only one await is suspended at a time. In any refactor that introduces real parallelism (worker_threads, cluster), this closure needs to become an atomic operation.
⚠️ No idempotency
If a handler mistakenly calls onUpdateTokens twice (retry or bug), the sum happens twice. No dedup. Different from token_transactions on the Temporal path, which at least has a PK.
🔧 Closes over 2 variables
The closure captures totalTokensUsed and totalCost by reference. The variables are let, not const. Even with const, the closure reads the current value of the variable, not a snapshot. Reassignment outside affects the reading.
BNode before/after snapshot
flux.service.ts:3248-3249, 3296-3297, 4537-4546
genericTokensBefore = totalTokensUsed; ... [handler runs] ... delta = totalTokensUsed - genericTokensBefore;
Purpose. Universal pattern to attribute charging to the right node. At the start of the node try (lines 3248 and 3296, with double safety), it snapshots the global accumulators. After the handler finishes, it computes the delta as current value minus snapshot. It goes to the endNode in 3.9.
In short. It is the before-and-after ruler. The execution total goes up all the time. Each handler charges. Each iteration charges. To know how much came from this specific node, mark the total before the node starts (genericTokensBefore) and the total after (totalTokensUsed). The difference is the attributable spend. Simple and robust as long as there is no parallelism between nodes. If 2 nodes ran in parallel, the deltas would cross. There would be no way to know who spent what just from the difference. The snapshot appears twice (3248 and 3296) for double safety. Line 3248 comes right after try { opens. 3296 sits inside the block where the RunLog is being created. It is an explicit reset to ensure any charge from runLogCollector.startNode does not leak into the node delta. It should not happen, but it is defensive. The final delta is written into the RunLogNode in 3.9 (endNode), with tokens: totalTokensUsed - genericTokensBefore. This way the timeline UI shows tokens and cost per node, not only the execution total.
// line 3248-3249 let genericTokensBefore = totalTokensUsed; let genericCostBefore = totalCost; // line 3296-3297: reset after startNode genericTokensBefore = totalTokensUsed; genericCostBefore = totalCost; // [... handler runs ...] // line 4539-4540: delta computation in endNode tokens: totalTokensUsed - genericTokensBefore, cost: totalCost - genericCostBefore,
🎯 Why 2 snapshots?
Line 3248 happens during variable initialization. Line 3296-3297 happens after startNode. It ensures a reset. If startNode or redactSecrets trigger any path that charges tokens, it stays out of the node delta. It is unlikely, but defensive.
⚠️ Can the delta go negative?
Not in normal code. totalTokensUsed only grows. But if someone decides to compensate (subtract tokens on error), the delta can go negative. endNode passes the raw value to the RunLogNode. The RunLogNode persists the number. In the future it can become a bug if someone sums without checking the sign.
🔧 Snapshot as value copy
Numbers in JS are values, not references. genericTokensBefore = totalTokensUsed copies the number. Changing totalTokensUsed later does not affect the snapshot.
CchargeContext (AsyncLocalStorage)
product/charge-context.ts:1-8 · product.service.ts:1013-1015
chargeContext = new AsyncLocalStorage<{ execId, nodeId }>() · getStore() read in updateTokens
Purpose. Bridges the charger (generic provider services) and where to persist (execId and nodeId of the current execution). Injected in 3.4, before the handler. Read by ProductService.updateTokens when it inserts a row into token_transactions.
In short. Looking only at onUpdateTokens from fn A, it seems the charge lives only in backend memory. In fact, when a handler calls anthropicService.chat(...), that service internally also calls productService.updateTokens(delta, cost). That call inserts a row into token_transactions on Postgres. There is a problem. ProductService is shared with public API routes. How does it know this charge belongs to this agent and this node? Via chargeContext.getStore(). 3.4 injected { execId, nodeId } into the AsyncLocalStorage before the handler started. When ProductService reads the ALS, it picks those ids and writes them into the metadata column of the row. So, two charges happen in parallel. onUpdateTokens adds to the execution total in memory. ProductService inserts a row with per-node identification in the database. The memory becomes the synchronous return of the execution (Phase 4 consumes it). The database becomes an audit trail and source for sumChargesByExecution later (fn D).
↳ ProductService.updateTokens — product.service.ts:1013-1015
const chargeCtx = chargeContext.getStore(); // ALS lookup execId = execId ?? chargeCtx?.execId ?? null; nodeId = nodeId ?? chargeCtx?.nodeId ?? null; // INSERT INTO token_transactions ({ execId, nodeId, tokens, cost, ... })
🎯 Fallback for explicit argument
execId = execId ?? chargeCtx?.execId. If the caller passed it explicitly, it is respected. It only uses ALS as fallback. Lets other callers (public API) not need the context.
📎 Two sources of truth
Memory (totalTokensUsed) and database (token_transactions) may diverge. If onUpdateTokens is called but the ProductService INSERT fails, memory has the value and the database does not. There is no automatic reconciliation. In practice, if ProductService fails, the LLM request would fail earlier.
DsumChargesByExecution (Temporal path)
flux.service.ts:709-716 · tokenTransactionService
const { tokens, cost } = await tokenTransactionService.sumChargesByExecution(execId, nodeId)
Purpose. Temporal handlers charge via HTTP /worker/charge-tokens on the worker. They do not have access to the onUpdateTokens closure. After the workflow finishes, the backend aggregates those charges from the database by {execId, nodeId}. It adds to the execution's totalTokensUsed and totalCost.
In short. Handlers on the worker cannot call the closure. It is another process. It is another memory. The solution: each activity that charges tokens calls HTTP /worker/charge-tokens passing { execId, nodeId, tokens, cost }. The endpoint on the backend inserts a row into token_transactions. When processNodeViaTemporal returns, the backend calls tokenTransactionService.sumChargesByExecution(execId, nodeId). The query is SELECT SUM(tokens), SUM(cost) FROM token_transactions WHERE exec_id = $1 AND node_id = $2. The result is added directly to totalTokensUsed and totalCost. There are 2 billing propagation paths. A single final source of truth: the sum in backend memory. It is elegant. It has round-trip cost: HTTP plus SQL per Temporal node. In large executions, with many migrated nodes, it is considerable overhead. Ensures consistency between paths.
D1 Worker charges via HTTP
The chargeTokensActivity activity calls /worker/charge-tokens with { execId, nodeId, tokens, cost }. It is step W7 in the diagram.
↓
D2 Backend aggregates on return
await tokenTransactionService.sumChargesByExecution(execId, nodeId). SUM on token_transactions by (execId, nodeId). Adds to totalTokensUsed and totalCost.
🎯 Idempotent by design
If the worker retries a charge activity, the INSERT into token_transactions may duplicate. If the chargeTokens activity has a unique PK, it is safe. Check if there is a unique constraint on (execId, nodeId, iterationIndex) or similar.
⚠️ Per-node overhead
HTTP call and SQL SUM per Temporal node. In an agent with 50 migrated nodes, that is 100 extra round-trips (charge and sum). Could be batched. Today it happens one by one.
🔧 Both paths sum in the same place
Legacy path: onUpdateTokens mutates memory directly. Temporal path: sumChargesByExecution reads from the database and adds to memory. After 3.7 runs (or the Temporal equivalent), totalTokensUsed reflects both paths.
Summary — what comes out of 3.7.
• totalTokensUsed and totalCost reflect post-node consumption.
• Delta attributed to the RunLogNode in 3.9 (tokens and cost).
• Row in token_transactions written (via ProductService or HTTP worker).
• 2 mechanisms: legacy closure and AsyncLocalStorage/HTTP Temporal.
Notes for migration.
• The onUpdateTokens closure becomes obsolete once everything is on the worker. Everyone charges via HTTP /worker/charge-tokens. Good sign: less code, fewer concurrent patterns.
• The chargeContext ALS also goes away. The worker always passes execId and nodeId explicitly by API.
• The before/after snapshot remains useful as a pattern. If the worker parallelizes, dedup by PK on token_transactions is needed. Accumulator subtraction won't be enough.
• It is cross-cutting and essential for billing. Must be migrated together with the main loop. A clear HTTP contract between worker and backend is required.

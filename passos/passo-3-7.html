Passo 3.7 — Contabilidade token/custo por nó

Bloco em flux.service.ts:2280-2283 (closure), 3248-3249 (snapshot antes), 3296-3297 (segunda leitura) e 4537-4546 (delta no endNode). Sem tabela e sem serviço. Aritmética pura em variáveis globais da execução, mais closure de mutação.
Em resumo — o que esse passo faz
  • Contabiliza gasto de tokens e custo por nó. Aritmética pura sobre variáveis globais da execução (totalTokensUsed, totalCost). Sem serviço e sem tabela. Só duas variáveis vivem no escopo do apiV2().
  • Closure onUpdateTokens para o path legacy. Funciona como uma caixinha de troco passada por argumento aos handlers legacy (LLM, imagem, áudio, embedding). Cada handler chama onUpdateTokens(delta, cost). A closure soma nos acumuladores. Funciona porque Node.js é single-threaded. Sem lock e sem race.
  • Delta por nó via snapshot antes e depois. No início do try do nó, guarda genericTokensBefore = totalTokensUsed. Depois do handler, calcula delta como valor atual menos snapshot. O delta vai para o RunLogNode em 3.9. É robusto enquanto não há paralelismo entre nós.
  • AsyncLocalStorage para propagação implícita. O chargeContext injeta { execId, nodeId } na ALS antes do handler. Quando o ProductService.updateTokens (compartilhado com API pública) insere linha em token_transactions, consulta a ALS para saber a qual nó atribuir a cobrança.
  • Path Temporal usa HTTP e SUM no banco. Handlers no worker não podem tocar a closure. É outro processo. Cobram via /worker/charge-tokens. No retorno do processNodeViaTemporal, o backend chama sumChargesByExecution(execId, nodeId). Agrega do banco e soma em totalTokensUsed. Existe overhead per-node de HTTP e SQL. Garante consistência entre paths.
  • Saída. totalTokensUsed e totalCost refletem o consumo pós-nó. Delta atribuído ao RunLogNode. Linha em token_transactions gravada como audit trail. Dois mecanismos convergem em uma única fonte de verdade em memória.
Contexto. Billing é cross-cutting (memória [[project_execution_architecture]]). O total da execução vive em totalTokensUsed e totalCost. É mutado por callback quando chamadas de LLM, API ou embedding cobram tokens. O delta por nó é calculado por diferença antes e depois. Duas fontes possíveis. Handlers legacy chamam onUpdateTokens(delta, cost) direto. Handlers Temporal cobram via HTTP /worker/charge-tokens. Depois, sumChargesByExecution(execId, nodeId) agrega do banco.

AonUpdateTokens (closure)
flux.service.ts:2280-2283
const onUpdateTokens = (tokensUsed: number, cost: number) => { totalTokensUsed += tokensUsed; totalCost += cost; };
Propósito. Callback closure criada no início do apiV2(). Passada por argumento para todos os handlers legacy que fazem cobrança (LLM, embedding e outros). Cada handler chama onUpdateTokens(delta, cost) após cada operação cobrada. A closure muta as variáveis do escopo pai.
Em resumo. Funciona como uma caixinha de troco em cima da mesa do apiV2(). Sempre que um handler consome tokens (chamou o LLM, gerou embedding, transcreveu áudio), reporta o consumo via onUpdateTokens(300, 0.002). A closure aceita o valor e soma nos acumuladores globais da execução. É closure. A função é definida no escopo do apiV2 e acessa as variáveis totalTokensUsed e totalCost. Mutar dentro da função altera direto as variáveis da execução. Sem passar por serviço, sem I/O, sem consistência distribuída. É simples, síncrono e funciona porque tudo mora no mesmo processo. Cada handler recebe essa referência via argumento, não via injeção. É padrão de dependency injection funcional. Handlers Temporal não chamam essa closure. Cobram por HTTP direto no /worker/charge-tokens. O backend depois lê via sumChargesByExecution (fn D). Sem worker, sem HTTP e sem lock. Também não há paralelismo real.
let totalTokensUsed = 0; let totalCost = 0; const onUpdateTokens = (tokensUsed: number, cost: number) => { totalTokensUsed += tokensUsed; totalCost += cost; };
↓
A1 Passado aos handlers legacy
Handlers como voiceNode, imageGeneratorNode, webSearchNode, audioReaderNode e commandContentNode recebem onUpdateTokens como argumento. Chamam durante a execução. Dispatch em flux.service.ts:3380, 3615, 3706, 3722, 3712.
🎯 Sem lock, single-threaded funciona
Node.js é single-threaded no event loop. Mutar totalTokensUsed += x nunca gera race. Não existem 2 handlers rodando em paralelo de verdade. Só um await fica suspenso por vez. Em qualquer refactor que introduza paralelismo real (worker_threads, cluster), essa closure precisa virar operação atômica.
⚠️ Sem idempotência
Se um handler chamar onUpdateTokens duas vezes por engano (retry ou bug), a soma acontece duas vezes. Não há dedup. Diferente do token_transactions do path Temporal, que pelo menos tem PK.
🔧 Fecha sobre 2 variáveis
A closure captura totalTokensUsed e totalCost por referência. As variáveis são let, não const. Mesmo com const, a closure lê o valor atual da variável, não um snapshot. Reatribuição fora afeta a leitura.
BSnapshot before/after do nó
flux.service.ts:3248-3249, 3296-3297, 4537-4546
genericTokensBefore = totalTokensUsed; ... [handler roda] ... delta = totalTokensUsed - genericTokensBefore;
Propósito. Padrão universal para atribuir cobrança ao nó certo. No início do try do nó (linhas 3248 e 3296, com segurança dupla), tira snapshot dos acumuladores globais. Depois que o handler termina, calcula delta como valor atual menos snapshot. Vai para o endNode em 3.9.
Em resumo. É a régua antes e depois. O total da execução sobe o tempo todo. Cada handler cobra. Cada iteração cobra. Para saber quanto foi desse nó específico, marca-se o total antes do nó começar (genericTokensBefore) e o total depois (totalTokensUsed). A diferença é o gasto atribuível. Simples e robusto enquanto não há paralelismo entre nós. Se 2 nós rodassem em paralelo, os deltas se cruzariam. Não haveria como saber quem gastou o quê só pela diferença. O snapshot aparece duas vezes (3248 e 3296) por segurança dupla. A linha 3248 vem logo após o try { abrir. A 3296 fica dentro do bloco onde o RunLog está sendo criado. É reset explícito para garantir que qualquer cobrança do runLogCollector.startNode não vaze para o delta do nó. Não deveria acontecer, mas é defensivo. O delta final é escrito no RunLogNode em 3.9 (endNode), com tokens: totalTokensUsed - genericTokensBefore. Assim a UI de timeline mostra tokens e custo por nó, não só o total da execução.
// linha 3248-3249 let genericTokensBefore = totalTokensUsed; let genericCostBefore = totalCost; // linha 3296-3297: reset após startNode genericTokensBefore = totalTokensUsed; genericCostBefore = totalCost; // [... handler roda ...] // linha 4539-4540: cálculo do delta em endNode tokens: totalTokensUsed - genericTokensBefore, cost: totalCost - genericCostBefore,
🎯 Por que 2 snapshots?
A linha 3248 acontece durante a inicialização das variáveis. A linha 3296-3297 acontece depois do startNode. Garante reset. Se o startNode ou redactSecrets ativarem algum path que cobre tokens, fica fora do delta do nó. É improvável, mas defensivo.
⚠️ Delta pode ficar negativo?
Não em código normal. totalTokensUsed só cresce. Mas se alguém decidir compensar (subtrair tokens em caso de erro), o delta pode ficar negativo. O endNode passa o valor cru para o RunLogNode. O RunLogNode persiste o número. Futuramente pode virar bug se alguém somar sem checar sinal.
🔧 Snapshot em cópia por valor
Numbers em JS são valores, não referências. genericTokensBefore = totalTokensUsed copia o número. Mudar totalTokensUsed depois não afeta o snapshot.
CchargeContext (AsyncLocalStorage)
product/charge-context.ts:1-8 · product.service.ts:1013-1015
chargeContext = new AsyncLocalStorage<{ execId, nodeId }>() · getStore() lido em updateTokens
Propósito. Faz a ponte entre quem está cobrando (serviços de provider genéricos) e onde persistir (execId e nodeId da execução atual). Injetado em 3.4, antes do handler. Lido pelo ProductService.updateTokens quando insere linha em token_transactions.
Em resumo. Só olhando o onUpdateTokens do fn A, parece que a cobrança vive só na memória do backend. Na verdade, quando um handler chama anthropicService.chat(...), esse serviço internamente também chama productService.updateTokens(delta, cost). Essa chamada insere linha em token_transactions no Postgres. Existe um problema. O ProductService é compartilhado com rotas API públicas. Como ele sabe que essa cobrança pertence a este agente e a este nó? Via chargeContext.getStore(). O 3.4 injetou { execId, nodeId } na AsyncLocalStorage antes do handler começar. Quando o ProductService lê a ALS, pega esses ids e escreve na coluna metadata da linha. Assim, duas cobranças acontecem em paralelo. onUpdateTokens soma no total da execução em memória. ProductService insere linha com identificação por nó no banco. A memória vira o retorno síncrono da execução (Fase 4 consome). O banco vira audit trail e fonte para sumChargesByExecution depois (fn D).
↳ ProductService.updateTokens — product.service.ts:1013-1015
const chargeCtx = chargeContext.getStore(); // ALS lookup execId = execId ?? chargeCtx?.execId ?? null; nodeId = nodeId ?? chargeCtx?.nodeId ?? null; // INSERT INTO token_transactions ({ execId, nodeId, tokens, cost, ... })
🎯 Fallback para argumento explícito
execId = execId ?? chargeCtx?.execId. Se o caller passou explícito, respeita. Só usa ALS como fallback. Permite que outros callers (API pública) não precisem do contexto.
📎 Duas fontes de verdade
Memória (totalTokensUsed) e banco (token_transactions) podem divergir. Se onUpdateTokens é chamado mas o INSERT do ProductService falha, memória tem valor e banco não. Não há reconciliação automática. Na prática, se o ProductService falha, o request de LLM falharia antes.
DsumChargesByExecution (path Temporal)
flux.service.ts:709-716 · tokenTransactionService
const { tokens, cost } = await tokenTransactionService.sumChargesByExecution(execId, nodeId)
Propósito. Handlers Temporal cobram via HTTP /worker/charge-tokens no worker. Não têm acesso à closure onUpdateTokens. Depois que o workflow termina, o backend agrega essas cobranças do banco por {execId, nodeId}. Soma em totalTokensUsed e totalCost da execução.
Em resumo. Handlers no worker não podem chamar a closure. É outro processo. É outra memória. A solução: cada activity que cobra tokens chama HTTP /worker/charge-tokens passando { execId, nodeId, tokens, cost }. O endpoint no backend insere linha em token_transactions. Quando processNodeViaTemporal retorna, o backend chama tokenTransactionService.sumChargesByExecution(execId, nodeId). A query é SELECT SUM(tokens), SUM(cost) FROM token_transactions WHERE exec_id = $1 AND node_id = $2. O resultado é somado direto em totalTokensUsed e totalCost. Existem 2 caminhos de propagação de billing. Uma única fonte de verdade final: a soma em memória do backend. É elegante. Tem custo de round-trip: HTTP mais SQL por nó Temporal. Em execuções grandes, com muitos nós migrados, é overhead considerável. Garante consistência entre paths.
D1 Worker cobra via HTTP
A activity chargeTokensActivity chama /worker/charge-tokens com { execId, nodeId, tokens, cost }. É o passo W7 do diagrama.
↓
D2 Backend agrega ao retornar
await tokenTransactionService.sumChargesByExecution(execId, nodeId). SUM em token_transactions por (execId, nodeId). Soma em totalTokensUsed e totalCost.
🎯 Idempotente por design
Se o worker retentar uma activity de cobrança, o INSERT em token_transactions pode duplicar. Se a activity chargeTokens tem PK única, é seguro. Verificar se existe unique constraint em (execId, nodeId, iterationIndex) ou similar.
⚠️ Overhead per node
HTTP call e SQL SUM por nó Temporal. Em um agente com 50 nós migrados, são 100 round-trips extras (charge e sum). Poderia ser batched. Hoje acontece um a um.
🔧 Os dois paths somam no mesmo lugar
Path legacy: onUpdateTokens muta a memória direto. Path Temporal: sumChargesByExecution lê do banco e soma na memória. Depois de 3.7 rodar (ou o equivalente para Temporal), totalTokensUsed reflete os dois caminhos.
Resumo — o que sai de 3.7.
• totalTokensUsed e totalCost refletem o consumo pós-execução do nó.
• Delta atribuído ao RunLogNode em 3.9 (tokens e cost).
• Linha em token_transactions gravada (via ProductService ou HTTP worker).
• 2 mecanismos: closure legacy e AsyncLocalStorage/HTTP Temporal.
Observações para migração.
• A closure onUpdateTokens fica obsoleta quando tudo estiver no worker. Todos cobram via HTTP /worker/charge-tokens. É bom sinal: menos código, menos padrões concorrentes.
• A ALS chargeContext também some. O worker sempre passa execId e nodeId explícitos por API.
• O snapshot antes e depois continua útil como padrão. Se o worker paralelizar, precisa de dedup por PK em token_transactions. Não bastará subtração de acumuladores.
• É cross-cutting e essencial para billing. Deve ser migrado junto com o loop principal. É preciso contract HTTP claro entre worker e backend.

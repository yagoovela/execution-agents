Passo 3.9 — runLogCollector.endNode()

Bloco em run-log-collector.ts:337-370. Chamado em flux.service.ts:4537-4546 (path sucesso) e 4672-4682 (path erro no catch). Fecha o RunLogNode criado em 3.4. Preenche saída, tokens, custo, duração e status. Dispara flush para o banco.
Em resumo — o que esse passo faz
  • Fecha a pasta do nó no RunLog. Em 3.4, o startNode abriu o RunLogNode com status in_progress. Esse passo é a reunião de fechamento. Preenche saída, tokens, custo, duração e status final. Sempre em par. Quem abre precisa fechar. Se não, fica in_progress para sempre. É sinal visual de execução interrompida.
  • Muta o node in-place. O caller passa a referência direto. Não busca no bucket. Preenche endedAt. Calcula durationMs. Aplica redactSecrets em output e rawResponse. Copia tokens e cost a partir do delta calculado em 3.7. Copia metadados opcionais: attempts, modelId, modelProvider e execId.
  • Status binário via truthy check. Se params.errorMessage foi passado como truthy, status vira 'error' e copia os 4 campos de erro. Se não, status vira 'success'. Sem "warning", "partial success" ou "cancelled". Cancel vive em outro caminho, o finishCancelledNode. Simples, mas frágil. errorMessage: '' passaria como sucesso.
  • Dispara flush debounced. Mesmo mecanismo do 3.4. flushRoot() agenda UPSERT em space_run_logs. O debounce evita sobrecarga no Postgres em execuções longas. O flushNow em 4.4 força write imediato no fim.
  • Bug latente conhecido. Nas linhas 4537-4546 e 4549-4562 do flux.service.ts, o mesmo bloco de endNode aparece duplicado (copy-paste). É idempotente. Não quebra nada. Gasta 2 vezes o redactSecrets e reseta o debounce timer duas vezes. Fix trivial: deletar o segundo bloco.
  • Saída. RunLogNode deste nó com status 'success' ou 'error'. durationMs, saída ofuscada, tokens, custo e metadata. UPSERT em space_run_logs agendado via debounce.
Contexto. Par simétrico do startNode em 3.4. A assinatura do RunLog é always-paired. Quem abre precisa fechar. Se algo escapar sem fechar (por exemplo, a execução falhou entre 3.4 e 3.9), o registro fica com status='in_progress' para sempre. É indicador visual de execução interrompida.

O node é null. É o caso de fluxBox e libraryNode. Eles não têm RunLogNode direto. O startNode retornou null para eles.

Os campos rawResponse, attempts, modelId, modelProvider e execId são opcionais. Só preenche quando params.X !== undefined. Handlers que não passam esses valores (por exemplo, mathFunction) não escrevem undefined no doc. O campo fica simplesmente ausente.

Mesmo utility de 3.4-C. Percorre output recursivamente. Troca campos como apiKey, Authorization, password e authToken por [REDACTED]. Aplica em output e rawResponse.

BStatus success vs error
run-log-collector.ts:360-368
if (params.errorMessage) { node.status = 'error'; ...err fields... } else { node.status = 'success'; }
Propósito. Decide o status baseado em uma única variável. errorMessage presente significa erro. É elegante, mas frágil. Se um handler com bug passar errorMessage: '' achando que "não tem erro", o falsy check aceita como sem erro. Passar errorMessage: null ou undefined funciona.
Em resumo. É a decisão binária: sucesso ou erro. Não existe estado "warning", "partial success" ou "cancelled" nesse fluxo. O cancelled vive em outro caminho. O finishCancelledNode do sistema de cancelamento tem sua própria lógica. Aqui só olha um campo. Se params.errorMessage foi passado como truthy, status vira 'error' e as 4 propriedades de erro são copiadas para o node (errorMessage, errorDevMessage, errorCategory, errorField). Se não, status='success'. Simples, mas com efeito cascata pesado. A Fase 4.2 depois filtra myUpdatedNodes.filter(n => n.data?.errorMessage) para decidir se cria FlowLog como error. A Fase 4.5 monta a string amigável a partir do primeiro nó com erro. Toda a UX de erro depende dessa flag ser setada corretamente aqui.
if (params.errorMessage) { // truthy check node.status = 'error'; node.errorMessage = params.errorMessage; node.errorDevMessage = params.errorDevMessage; node.errorCategory = params.errorCategory; node.errorField = params.errorField; } else { node.status = 'success'; }
⚠️ Truthy check
if (params.errorMessage) rejeita string vazia, null, undefined e 0. Bug potencial. O handler seta errorMessage: '' achando que é "sem erro". Passa como sucesso. errorField pode ainda estar presente. Causa estado inconsistente. A versão robusta seria errorMessage != null && errorMessage !== ''.
🎯 Sem status 'cancelled'
Cancel vive em outro path (finishCancelledNode). Nunca chega aqui. O break do 3.4-cancellation impede.
🔧 Sem status 'partial'
Nem status intermediário, nem warning. É coerente com o fail-fast de 3.8. A timeline mostra só verde, vermelho ou cinza.
CflushRoot() após update
run-log-collector.ts:369
this.flushRoot();
Propósito. Mesmo mecanismo do 3.4. Depois de atualizar o node, chama o callback registrado. É o spaceRunLogsService.scheduleUpsert(). Serve para agendar UPSERT debounced em space_run_logs. Sem write direto. Sempre passa pelo debounce.
Em resumo. Igual ao 3.4. Cada modificação no doc dispara um flush. O flush é debounced. Evita sobrecarga no Postgres. O timer é único por processId. Cada nó que atualiza reseta o timer. O UPSERT final acontece só depois que ficar quieto por N milissegundos. Isso é fundamental. Uma execução com 50 nós teria mais de 100 writes (start e end de cada) sem debounce. Com debounce, agrupa em poucos UPSERTs por segundo. No fim da execução, o flushNow em 4.4 força write imediato. Cancela o debounce e escreve o estado final agora.
C1 scheduleUpsert (debounce)
Cancela timer anterior. Executa setTimeout(FLUSH_DEBOUNCE_MS). UPSERT em space_run_logs quando o timer dispara.

DDuplicação de chamada — dead code

runLogCollector?.endNode(genericRunLogNode, { output, tokens, cost, errorMessage, rawResponse, attempts, modelId, modelProvider }); // chamada 2 vezes consecutivas
Propósito. É bug latente e dead code. As linhas 4537-4546 e 4549-4562 fazem exatamente a mesma chamada de endNode, com os mesmos argumentos. Nenhum efeito prático além de dobrar o overhead. O diagrama principal cita isso na descrição do 3.9.
Em resumo. É um bug conhecido. Ao ler o código do flux.service.ts em 4537, aparece o bloco if (genericRunLogNode) { ... endNode(...) }. Descendo, aparece exatamente o mesmo bloco em 4549. É copy-paste deixado por erro. As duas chamadas passam os mesmos parâmetros. A segunda apenas reescreve os mesmos campos com os mesmos valores e dispara um segundo flush. Não quebra nada. É idempotente. endedAt, durationMs e demais campos recebem os mesmos valores na segunda chamada. O new Date() é chamado 2 vezes com milissegundos de diferença. durationMs fica igual em resolução de milissegundos. Só dobra o custo. 2 vezes o redactSecrets. 2 vezes o flushRoot. O debounce timer é resetado duas vezes seguidas. É item de cleanup para qualquer refactor. Remover o bloco 4549-4562 é seguro.
// linhas 4533-4547 — primeira chamada if (genericRunLogNode) { const genericUpdatedNode = myUpdatedNodes.find(n => n.id === node.id); runLogCollector?.endNode(genericRunLogNode, { output: genericUpdatedNode?.data, tokens: totalTokensUsed - genericTokensBefore, cost: totalCost - genericCostBefore, // ... }); } // linhas 4549-4562 — cópia idêntica (dead code) if (genericRunLogNode) { // mesmo bloco copiado - REMOVER }
⚠️ Overhead duplicado
Cada chamada executa 3 coisas. Mutação em 8 propriedades do node. redactSecrets(output), que percorre recursivamente. flushRoot(), que reseta o debounce timer. Fazer 2 vezes não muda a semântica. Só o custo.
🎯 Como aconteceu
Provavelmente refactor mal terminado. Alguém extraiu a lógica para um bloco reutilizável e não removeu o original. Ou merge que resolveu conflito duplicando. É bandeira vermelha em code review. Teste unitário não pega. O comportamento é idêntico.
🔧 Fix é remover o segundo bloco
Deletar linhas 4549-4562. Nenhum outro código depende. Pode ser feito sozinho, sem impacto em outros passos.
Resumo — o que sai de 3.9.

Observações para migração.
• O bug do endNode duplicado deve ser removido antes de qualquer refactor grande. Evita confundir futuros leitores.
• O coletor hierárquico é essencial para a UX de timeline (memória [[project_execution_architecture]]). A migração para o worker precisa preservar a semântica de innerSteps e subRun.
• O padrão start/end simétrico é robusto. Exige garantia de que endNode sempre roda. Um try/finally ao redor do handler seria mais seguro que endNode espalhado em vários paths hoje (sucesso, erro, cancel).

Step 3.9 — runLogCollector.endNode()

Block at run-log-collector.ts:337-370. Called at flux.service.ts:4537-4546 (success path) and 4672-4682 (error path in the catch). Closes the RunLogNode created in 3.4. Fills in output, tokens, cost, duration, and status. Triggers a flush to the database.
In short — what this step does
  • Closes the node folder in the RunLog. In 3.4, startNode opened the RunLogNode with status in_progress. This step is the closing meeting. Fills in output, tokens, cost, duration, and final status. Always in pairs. Whoever opens must close. If not, it stays in_progress forever. It is a visual sign of an interrupted execution.
  • Mutates the node in-place. The caller passes the reference directly. It does not look up the bucket. Fills in endedAt. Computes durationMs. Applies redactSecrets on output and rawResponse. Copies tokens and cost from the delta computed in 3.7. Copies optional metadata: attempts, modelId, modelProvider, and execId.
  • Binary status via truthy check. If params.errorMessage was passed as truthy, status becomes 'error' and copies the 4 error fields. If not, status becomes 'success'. No "warning", "partial success", or "cancelled". Cancel lives on another path, finishCancelledNode. Simple, but fragile. errorMessage: '' would pass as success.
  • Triggers debounced flush. Same mechanism as 3.4. flushRoot() schedules an UPSERT on space_run_logs. The debounce avoids Postgres overload on long executions. flushNow in 4.4 forces an immediate write at the end.
  • Known latent bug. At lines 4537-4546 and 4549-4562 of flux.service.ts, the same endNode block appears duplicated (copy-paste). It is idempotent. It does not break anything. It spends 2x the redactSecrets and resets the debounce timer twice. Trivial fix: delete the second block.
  • Output. This node's RunLogNode with status 'success' or 'error'. durationMs, redacted output, tokens, cost, and metadata. UPSERT in space_run_logs scheduled via debounce.
Context. Symmetric pair of startNode in 3.4. The RunLog signature is always-paired. Whoever opens must close. If something escapes without closing (for example, the execution failed between 3.4 and 3.9), the record stays with status='in_progress' forever. It is a visual indicator of an interrupted execution.

endNode(node: RunLogNode | null, params: EndNodeParams): void
Purpose. Receives the RunLogNode created in 3.4 and fills in all final fields. Computes durationMs. Applies redactSecrets on output and rawResponse. If errorMessage was passed, status becomes 'error'. If not, it becomes 'success'.
In short. startNode in 3.4 opened the node folder with an in_progress stamp. This is the closing meeting. It receives the same node reference. It does not look up the bucket. The caller passes it directly. It computes how long it took: durationMs = endedAt - startedAt. It fills in the redacted output. redactSecrets(params.output) strips secrets before persisting. It fills in tokens and cost, computed in fn B of step 3.7 as delta. It fills in optional metadata: rawResponse, attempts, modelId, modelProvider, and execId. The if errorMessage on line 360 is the binary decision. If an error message came in, status='error' and fills in errorMessage, errorDevMessage, errorCategory, and errorField. If not, status='success'. No "cancelled" here. Cancel is set by finishCancelledNode on another flow (3.4-cancellation). After filling in, it calls flushRoot(). It is the same mechanism from 3.4 to schedule a debounced UPSERT on space_run_logs. The early-return on line 338 (!this.enabled || !node) protects for 2 cases. Collector disabled (feature gate). The node is null. It is the case of fluxBox and libraryNode. They have no direct RunLogNode. startNode returned null for them.
endNode(node: RunLogNode | null, params: EndNodeParams): void { if (!this.enabled || !node) return; const endedAt = new Date(); node.endedAt = endedAt.toISOString(); node.durationMs = endedAt.getTime() - new Date(node.startedAt).getTime(); node.output = redactSecrets(params.output); node.tokens = params.tokens; node.cost = params.cost; // [rawResponse, attempts, modelId, modelProvider, execId — optional] if (params.errorMessage) { node.status = 'error'; node.errorMessage = params.errorMessage; // [errorDevMessage, errorCategory, errorField] } else { node.status = 'success'; } this.flushRoot(); }

BStatus success vs error
run-log-collector.ts:360-368
if (params.errorMessage) { node.status = 'error'; ...err fields... } else { node.status = 'success'; }
Purpose. Decides the status based on a single variable. errorMessage present means error. It is elegant, but fragile. If a buggy handler passes errorMessage: '' thinking "no error", the falsy check accepts it as no error. Passing errorMessage: null or undefined works.
In short. It is the binary decision: success or error. There is no "warning", "partial success", or "cancelled" state in this flow. cancelled lives on another path. The finishCancelledNode from the cancellation system has its own logic. Here it only looks at one field. If params.errorMessage was passed as truthy, status becomes 'error' and the 4 error properties are copied to the node (errorMessage, errorDevMessage, errorCategory, errorField). If not, status='success'. Simple, but with a heavy cascading effect. Phase 4.2 later filters myUpdatedNodes.filter(n => n.data?.errorMessage) to decide whether to create the FlowLog as error. Phase 4.5 builds the friendly string from the first node with error. All error UX depends on this flag being set correctly here.
if (params.errorMessage) { // truthy check node.status = 'error'; node.errorMessage = params.errorMessage; node.errorDevMessage = params.errorDevMessage; node.errorCategory = params.errorCategory; node.errorField = params.errorField; } else { node.status = 'success'; }
⚠️ Truthy check
if (params.errorMessage) rejects empty string, null, undefined, and 0. Potential bug. A handler sets errorMessage: '' thinking it means "no error". It passes as success. errorField may still be present. Causes inconsistent state. The robust version would be errorMessage != null && errorMessage !== ''.
🎯 No 'cancelled' status
Cancel lives on another path (finishCancelledNode). It never gets here. The 3.4-cancellation break prevents it.
🔧 No 'partial' status
No intermediate status, no warning. It is coherent with the fail-fast of 3.8. The timeline shows only green, red, or gray.
CflushRoot() after update
run-log-collector.ts:369
this.flushRoot();
Purpose. Same mechanism as 3.4. After updating the node, calls the registered callback. It is spaceRunLogsService.scheduleUpsert(). Serves to schedule a debounced UPSERT on space_run_logs. No direct write. It always goes through the debounce.
In short. Same as 3.4. Every doc change triggers a flush. The flush is debounced. Avoids Postgres overload. The timer is unique per processId. Each node that updates resets the timer. The final UPSERT happens only after it stays quiet for N milliseconds. This is fundamental. An execution with 50 nodes would have more than 100 writes (start and end of each) without debounce. With debounce, it groups into a few UPSERTs per second. At the end of the execution, flushNow in 4.4 forces an immediate write. It cancels the debounce and writes the final state now.
C1 scheduleUpsert (debounce)
Cancels previous timer. Runs setTimeout(FLUSH_DEBOUNCE_MS). UPSERT on space_run_logs when the timer fires.

DCall duplication — dead code
flux.service.ts:4537-4546 (1st) · 4549-4562 (2nd)
runLogCollector?.endNode(genericRunLogNode, { output, tokens, cost, errorMessage, rawResponse, attempts, modelId, modelProvider }); // called 2 times consecutively
Purpose. It is a latent bug and dead code. Lines 4537-4546 and 4549-4562 make exactly the same endNode call, with the same arguments. No practical effect besides doubling the overhead. The main diagram mentions this in the 3.9 description.
In short. It is a known bug. When reading the flux.service.ts code at 4537, the block if (genericRunLogNode) { ... endNode(...) } appears. Scrolling down, exactly the same block appears at 4549. It is copy-paste left by mistake. Both calls pass the same parameters. The second one just rewrites the same fields with the same values and triggers a second flush. It does not break anything. It is idempotent. endedAt, durationMs, and other fields receive the same values on the second call. new Date() is called 2 times with milliseconds of difference. durationMs stays the same at millisecond resolution. It only doubles the cost. 2x the redactSecrets. 2x the flushRoot. The debounce timer is reset twice in a row. It is a cleanup item for any refactor. Removing block 4549-4562 is safe.
// lines 4533-4547 — first call if (genericRunLogNode) { const genericUpdatedNode = myUpdatedNodes.find(n => n.id === node.id); runLogCollector?.endNode(genericRunLogNode, { output: genericUpdatedNode?.data, tokens: totalTokensUsed - genericTokensBefore, cost: totalCost - genericCostBefore, // ... }); } // lines 4549-4562 — identical copy (dead code) if (genericRunLogNode) { // same block copied - REMOVE }
⚠️ Duplicated overhead
Each call runs 3 things. Mutation on 8 node properties. redactSecrets(output), which walks recursively. flushRoot(), which resets the debounce timer. Doing it 2 times does not change the semantics. Only the cost.
🎯 How it happened
Probably an unfinished refactor. Someone extracted the logic into a reusable block and did not remove the original. Or a merge that resolved a conflict by duplicating. It is a red flag in code review. A unit test does not catch it. The behavior is identical.
🔧 Fix is to remove the second block
Delete lines 4549-4562. No other code depends on it. Can be done alone, without impact on other steps.

Notes for migration.
• The duplicated endNode bug should be removed before any large refactor. Avoids confusing future readers.
• The hierarchical collector is essential for the timeline UX (memory [[project_execution_architecture]]). Migrating to the worker needs to preserve the innerSteps and subRun semantics.
• The symmetric start/end pattern is robust. It requires a guarantee that endNode always runs. A try/finally around the handler would be safer than the endNode scattered in several paths today (success, error, cancel).

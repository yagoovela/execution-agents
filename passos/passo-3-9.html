Passo 3.9 — runLogCollector.endNode()

Bloco em run-log-collector.ts:337-370 · chamado em flux.service.ts:4537-4546 (path sucesso) e 4672-4682 (path erro no catch). Fecha o RunLogNode criado em 3.4, preenche saída/tokens/custo/duração/status, dispara flush pro banco.
Em resumo — o que esse passo faz
  • Fecha a "pasta" do nó no RunLog: se em 3.4 o startNode abriu o RunLogNode com status in_progress, esse passo é a reunião de fechamento — preenche saída, tokens, custo, duração e status final. Sempre em par: quem abre precisa fechar (senão fica in_progress pra sempre, sinal visual de run interrompido).
  • Muta o node in-place: o caller passa a referência direto — não busca no bucket. Preenche endedAt, calcula durationMs, aplica redactSecrets em output e rawResponse, copia tokens/cost (do delta calculado em 3.7), e metadados opcionais (attempts, modelId, modelProvider, execId).
  • Status binário via truthy check: se params.errorMessage foi passado como truthy, status vira 'error' e copia os 4 campos de erro; senão status vira 'success'. Sem "warning", "partial success" ou "cancelled" (cancel vive em outro caminho, o finishCancelledNode). Simples, mas frágil: errorMessage: '' passaria como sucesso.
  • Dispara flush debounced: mesmo mecanismo do 3.4 — flushRoot() agenda UPSERT em space_run_logs. Debounce evita hammer no Postgres em runs longos; o flushNow em 4.4 força write imediato no fim.
  • Bug latente conhecido: nas linhas 4537-4546 e 4549-4562 do flux.service.ts o mesmo bloco de endNode aparece duplicado (copy-paste). É idempotente (não quebra nada), mas gasta 2× redactSecrets + reset duplo do debounce timer. Fix trivial: deletar o segundo bloco.
  • Saída: RunLogNode deste nó com status 'success'/'error', durationMs, output redigido, tokens, custo, metadata; UPSERT em space_run_logs agendado via debounce.
Contexto: par simétrico do startNode em 3.4. Assinatura do RunLog é always paired: quem abre precisa fechar. Se algo escapar sem fechar (ex: run crashou entre 3.4 e 3.9), o registro fica com status='in_progress' pra sempre — indicador visual de run interrompido.

BStatus success vs error
run-log-collector.ts:360-368
if (params.errorMessage) { node.status = 'error'; ...err fields... } else { node.status = 'success'; }
Propósito: Decide status baseado em uma única variável: errorMessage presente = erro. Elegante mas frágil — se um handler bugado passar errorMessage: '' (string vazia) achando que "não tem erro", o falsy check aceita como sem-erro. Mas passar errorMessage: null ou undefined é OK.
Em resumo: é a decisão binária — sucesso ou erro. Não existe estado "warning", nem "partial success", nem "cancelled" nesse fluxo. O cancelled vive em outro caminho (o finishCancelledNode do sistema de cancelamento tem sua própria lógica). Aqui só olha um campo: se params.errorMessage foi passado como truthy, status vira 'error' e as 4 propriedades de erro são copiadas pro node (errorMessage, errorDevMessage, errorCategory, errorField). Se não, status='success'. Simples, mas com efeito cascata pesado — Fase 4.2 depois vai filtrar myUpdatedNodes.filter(n => n.data?.errorMessage) pra decidir se cria FlowLog como error, e Fase 4.5 monta a string amigável a partir do primeiro nó com erro. Toda a UX de erro depende dessa flag ser setada certo aqui.
if (params.errorMessage) { // truthy check node.status = 'error'; node.errorMessage = params.errorMessage; node.errorDevMessage = params.errorDevMessage; node.errorCategory = params.errorCategory; node.errorField = params.errorField; } else { node.status = 'success'; }
⚠️ Truthy check
if (params.errorMessage) rejeita '' (string vazia), null, undefined, 0. Bug potencial: handler seta errorMessage: '' achando que "sem erro" — passa como sucesso, mas errorField pode ainda estar presente, causando estado inconsistente. Robustez seria errorMessage != null && errorMessage !== ''.
🎯 Sem status 'cancelled'
Cancel vive em outro path (finishCancelledNode). Nunca chega aqui — o break do 3.4-cancellation impede.
🔧 Sem status 'partial'
Nem status intermediário nem warning. Coerente com fail-fast de 3.8. Timeline mostra só verde/vermelho/cinza.
CflushRoot() após update
run-log-collector.ts:369
this.flushRoot();
Propósito: Mesmo mecanismo do 3.4. Depois de atualizar o node, chama o callback registrado — que é spaceRunLogsService.scheduleUpsert() — pra agendar UPSERT debounced em space_run_logs. Sem write direto — sempre passa pelo debounce.
Em resumo: igual ao 3.4. Cada modificação no doc dispara um flush, que é debounced pra evitar hammer no Postgres. O timer é único por processId — cada nó que atualiza reseta o timer, então o UPSERT final acontece só depois que ficar quieto por N ms. Isso é fundamental porque um run com 50 nós teria 100+ writes (start + end de cada) sem debounce. Com debounce, agrupa em poucos UPSERTs por segundo. E no fim do run, o flushNow em 4.4 força write imediato — cancelando o debounce e escrevendo o estado final agora.

As duas chamadas passam os mesmos parâmetros; a segunda simplesmente reescreve os mesmos campos com os mesmos valores e dispara um segundo flush. Em prática, não quebra nada (é idempotente porque endedAt, durationMs, etc. dão os mesmos valores na segunda chamada — o new Date() é chamado 2× com milissegundos de diferença, mas durationMs fica igual em resolução ms). Apenas dobra: 2× o custo de redactSecrets, 2× o flushRoot (que reseta o debounce timer duas vezes seguidas). Item de cleanup pra qualquer refactor: remover o bloco 4549-4562 é seguro.

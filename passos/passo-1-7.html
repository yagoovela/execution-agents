Step 1.7 — Google token refresh (conditional)

Block in flux.service.ts:2620-2643. When the flow has some pullData or pushData with provider = 'google' and the user has googleRefreshToken, exchanges the refresh token for a new access_token. The value is stored in a local variable. The pullData/pushData handlers consume it in Phase 3.
In short — what this step does
  • Decides whether calling Google is worthwhile. Scans the nodes looking for any pullData or pushData with Google provider. Most agents don't use it. The check saves a network call. Old nodes without provider fall back to the default 'google'.
  • Passes through the double gate. Only enters the refresh when both conditions are true. The user has googleRefreshToken stored. The flow has a Google node. If one fails, access_token starts empty and the step is silently skipped.
  • Exchanges the refresh token for an access token. Instantiates an OAuth2Client per execution, no pool, with clientId, clientSecret and redirectUri. Calls local setCredentials. Makes the blocking POST to oauth2.googleapis.com/token. Only the access_token is kept. Fields such as expiry_date are discarded.
  • No try/catch, no structured log. If Google refuses (revoked token, quota), the exception propagates and takes down the entire execution. This is true even when 90% of the nodes are not Google. There is no observability over success or failure. The environment variable GOOGLE_LOGIN_CLIENT_SECRECT keeps the typo due to historical dependency.
  • Output. Local variable access_token. Contains a Bearer string valid for about 1h or '' when the gate closes. Captured by closure. Passed as accessToken to the pullData/pushData handlers in Phase 3, including inside arrayNode. If the token is empty, the handlers call Google and get 401 in the middle of the execution.
Context. This is the only place in the execution flow that calls Google's OAuth2. Google access tokens expire in about 1h. Every execution re-runs the refresh before dispatching the Google data handlers (Sheets, etc.). If any condition fails, access_token stays as an empty string. Downstream handlers call Google without a token and receive 401 immediately.
Operation chain in 1.7
ADetects google data node → BGate + OAuth2Client init → CrefreshAccessToken → Google → DDownstream consumers
Final result. The local access_token variable ends up filled or empty (when the gate does not open). Ready to be passed as { accessToken: access_token } to the pushData/pullData handlers in Phase 3.

🎯 Fallback ?? 'google'
Old nodes created before the provider field existed do not have this key. The ?? assumes absent equals Google. If the front only writes explicit provider today, the fallback works as a safety net for legacy data.

Consequence. A new node created without setting provider (for example, misconfigured MCP — [[project_mcp_node_schemas]]) is treated as Google. It may trigger the refresh unnecessarily.
📎 Why only pullData/pushData?
Google Sheets is the only Google provider integrated into the execution engine. Other Google integrations (Gmail, Docs) live in mail.service.ts and similar services. Each has its own isolated OAuth2Client.
🔧 find vs some
Could be nodes?.some(...), semantically clearer ("is there any?"). Using find allocates the node and discards it. The overhead is irrelevant in production, but it's a smell.
B Gate + new OAuth2Client()
flux.service.ts:2628-2635
if (user.googleRefreshToken && hasGoogleDataNode) { const client = new OAuth2Client({ clientId, clientSecret, redirectUri }); ... }
Purpose. Only enters the refresh flow when both conditions hold. The user has already authenticated with Google at some point (has googleRefreshToken). The current flow needs it. If either fails, access_token stays as an empty string.
In short. This is where the double gate kicks in. It only allows the refresh when both conditions pass. First. The user has logged into Google at some point and left a googleRefreshToken stored. Second. The agent about to run has a Google node waiting for data. If any condition fails, the gate closes silently. The access_token variable stays empty. No alarm, no error. Once past the gate, the code builds a new OAuth2Client (one per execution, no recycling) with clientId, clientSecret and redirect ready to talk to Google in the next step. Beware of the typo in GOOGLE_LOGIN_CLIENT_SECRECT. The env var must keep the typo to work.

C client.refreshAccessToken()
flux.service.ts:2636-2642
client.setCredentials({ refresh_token }); const token = await client.refreshAccessToken(); access_token = token.credentials.access_token;
Purpose. Do the roundtrip to oauth2.googleapis.com/token. Exchange the refresh_token for a new access_token, valid for about 1h. Store only the access_token in the parent scope variable.
In short. This step is the registry office. You hand over the refresh token (the permanent wallet) and Google returns a new access token, valid for about one hour. First the code calls setCredentials, which sorts the paperwork locally, no network. Then it fires refreshAccessToken(), which goes to Google's server. Blocks the entire execution waiting for the response. Returns with the new badge. Only the access_token field is kept. The rest (expiry_date, scope, id_token) is discarded. No try/catch. If Google refuses (revoked token, quota exceeded), the entire execution dies. This is true even when 90% of the nodes are not Google.

⚠️ No try/catch. Failure crashes the execution
refreshAccessToken() is not protected. If Google returns an error (revoked refresh token, quota, timeout), the exception bubbles up to apiV2(). The only try/catch is at the orchestrator. The entire execution dies, even when 90% of the nodes are not Google.

If the user revoked permission in Google Account settings, every execution of any flow with a single Google pullData/pushData breaks until they re-authenticate.
🎯 Discards expiry_date
Google's SDK returns token.credentials.expiry_date. The code ignores it. Consequence. If an execution is very long (more than 1h), the access_token expires mid-run. Late pullData/pushData calls may return 401 even though the initial refresh succeeded.

Rare scenario (huge arrays or loops), but latent.

// Phase 3: pullDataService.pullData({ ..., accessToken: access_token }) / pushDataService.pushData({ ..., accessToken: access_token })
Purpose. Maps where the access_token prepared here will flow. Nothing is done with it in 1.7. The value lives in a variable until the Phase 3 handlers consume it.
In short. This part is not a function. It shows where the access_token will be delivered later. The token stays in a local variable of the apiV2() scope. It only leaves when the Phase 3 handlers request it. Consumers. pullDataService.pullData. pushDataService.pushData. The versions running inside an arrayNode (iterating). All receive the same token, without revalidation. If the gate (B) did not open, the handlers are still called normally, with accessToken: ''. Google returns 401 when the node actually executes. There is no early-fail validation. Note the convention shift. The local variable is access_token (snake, Google's format). The parameter is accessToken (camel, backend TS standard).

⚠️ Empty token. Handler tries to call Google without auth
If the gate (B) did not open, access_token stays empty. The handlers are still called normally. They pass an empty string as accessToken. Google returns 401 in the middle of the execution.

There is no validation in pullData/pushData to abort early when accessToken is falsy. It is an implicit failure. The error only shows when the node executes.
🎯 Token lifecycle
Execution start (here, 1.7). Refresh once.
During the execution. Token shared by closure (same string across N handlers).
End of execution. Variable discarded. The next execution redoes the refresh.

No cache. Consecutive executions from the same user cost 1 Google call each.
🔧 snake_case/camelCase divergence
Local. access_token (snake, aligned with Google's format).
Handler parameter. accessToken (camel, aligned with the backend TS standard).

The mapping is manual at the call-site. Renaming the local variable requires updating the 4 call-sites.
Summary — what leaves 1.7.
• access_token. String with Google Bearer token, or '' when the gate does not open.
• No other side effects. Nothing is written to the DB. No structured log. No cache.
• I/O. Zero or one POST to oauth2.googleapis.com/token, sequential, blocking.
• Consumed in Phase 3 by the pullData/pushData handlers, top-level and inside arrayNode.
Migration notes.
• Not essential for most executions. Most flows don't have Google pullData/pushData. The gate (A+B) skips 100% of the cost.
• Can stay in the backend even with the worker. Each Google handler in the worker can also do its own refresh (that's the pattern in google_sheets.service.ts). That multiplies N Google calls per execution when there are multiple nodes. The centralized refresh in the backend is more efficient.
• Alternative. The worker receives the access_token via workflow args, already refreshed by the backend. Advantage. One refresh per execution. The worker stays simple. Disadvantage. If the execution passes 1h (not the case today), the token expires mid-run.
• Fixing the SECRECT typo. Requires coordinating the env var change in production, dev and CI simultaneously. Not trivial.
• Wrap in try/catch. Today a failure here crashes the entire execution. If wrapped, a user with a revoked token still runs non-Google nodes. The Google ones fail with 401 downstream. Discussion about fail early vs fail late.
• Add structured log. Today nothing is logged, success or failure. A console.log('[GoogleRefresh]', { userId, ok }) would help diagnose reauth issues.

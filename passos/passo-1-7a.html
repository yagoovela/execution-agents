Passo 1.7a — Reset de nós com clearOnExecution por tipo

Bloco em flux.service.ts:2724-2812. Um .map gigantesco em updatedFlows que trata duas hierarquias distintas de reset: (1) outputObjectNode sempre limpa (fora do gate), (2) todo o resto testa clearOnExecution truthy e cai numa árvore de sub-branches por tipo. No fim, conditionNode zera o loop counter também fora do gate.
Em resumo — o que esse passo faz
  • Um único .map — três fatiamentos distintos: pra cada node em updatedFlows, primeiro testa se é outputObjectNode (limpeza incondicional), depois se clearOnExecution é truthy (aí cai numa árvore por tipo), e por último se é conditionNode (zera currentLoopCounter). Os dois "sempre limpa" (outputObjectNode e conditionNode) ignoram o gate do clearOnExecution.
  • outputObjectNode — reset incondicional: tudo dele é output derivado, sempre limpa text: '' e textData: []. Não tem sentido preservar entre runs — o output é sempre re-gerado.
  • fluxBox / libraryNode com clearOnExecution: clearOnExecution aqui é um objeto { campo1: true, campo2: false }. Faz Object.entries e zera cada campo cuja flag é true. Isso é por-campo, não wholesale.
  • Types que resetam por default: commandTextNode, voiceBoxNode, imageGenerator, commandContentNode, audioReaderNode, apiCaller, mcpNode — se clearOnExecution truthy, zeram text: '' e canceled: false. Sub-branches: voiceBoxNode retorna cedo com { canceled: false, audioUrl: '' }; commandContentNode adiciona text.result = ''; apiCaller/mcpNode adicionam { response: null, errorMessage: null, errorStatusCode: null }.
  • conditionNode.currentLoopCounter — sempre 0: zerado fora do gate. Necessário porque loop counters seriam eternos entre runs. Mutação in-place — não retorna node novo, muta a referência (footgun sutil).
Contexto: essa é a "segunda pasada" de reset — o passo 1.5b tratou fluxObjects; agora 1.7a trata todos os outros types que têm output ou state runtime. Existe uma versão consolidada dessa lógica em node-output-reset.ts (clearStaleNodeOutput, buildClearOnExecutionReset), mas o apiV2 ainda usa o if/else inline aqui — discrepância viva.

A outputObjectNode — reset incondicional
flux.service.ts:2725-2734
if (nd.type === 'outputObjectNode') { return { ...nd, data: { ...nd.data, text: '', textData: [] } }; }
Propósito: Zera o output do outputObjectNode em todos os runs, sem gate. É o único type que faz reset incondicional dentro desse .map — o resto tudo depende do clearOnExecution.
Em resumo: outputObjectNode é o "endpoint" do agent — o que o run vai devolver como resposta. Seu output é sempre re-gerado a partir dos nodes upstream, então não faz sentido preservar entre runs. Por isso, o reset é hardcoded, não depende de flag. Duas keys são zeradas: text pra string vazia e textData pra array vazio — que é o formato que o output do agent tem (texto puro + array de itens estruturados). O return corta o resto do .map pra esse node — não passa pelo gate do clearOnExecution nem pelo bloco do conditionNode. Bug latente: um outputObjectNode que também tivesse data.currentLoopCounter (impossível na prática, mas em teoria) não seria zerado — o return atalha.

Return curto no .map
O return curta o resto do map pra esse node — nenhum outro branch (clearOnExecution, conditionNode) é testado.
🎯 Por que sem gate?
O output do agent é sempre re-gerado. Preservar text entre runs enganaria o próximo run mostrando a resposta velha se algo falhar no meio.
📎 Duplicação com clearRunOutputForSeed
clearRunOutputForSeed (passo 1.7b) também zera outputObjectNode.text = ''. Redundância intencional — sob-e desce mais uma vez pra garantir.
⚠️ Return corta subsequent branches
Se um outputObjectNode tivesse também currentLoopCounter (não tem em prática), o zero-loop-counter não roda. Feature: outputObjectNode nunca tem loop counter.
B Gate clearOnExecution (truthy)
flux.service.ts:2736-2738
const clearOnExecution = nd?.data?.clearOnExecution || false;
if (clearOnExecution) { ... }
Propósito: Porta única de entrada pros branches por-tipo. Só entra se clearOnExecution for truthy (undefined vira false pelo || false). Tudo lá dentro depende disso — quem não tem a flag, atravessa o gate sem reset.
Em resumo: a mesma lógica de Boolean(clearOnExecution) do 1.5b, mas em vez de Boolean(), usa || false. Diferença sutil: Boolean({}) = true, mas ({}) || false também = {} (que é truthy, então o if passa). Efeito prático: idêntico. O gate simplesmente separa "todo mundo com opt-in de clearing" (dentro do bloco) de "quem não quer" (nada acontece). Nota importante: fluxObjects também têm clearOnExecution mas foram tratados no 1.5b — se um fluxObject caísse aqui (impossível em prática, mas se o filter do 1.5b falhasse), esse bloco não sabe o que fazer com ele (não tem branch pra fluxObject).

🚪 Que types entram no bloco?
1 fluxBox / libraryNode branch por-campo (FN C)
2 commandTextNode, voiceBoxNode, imageGenerator, commandContentNode, audioReaderNode, apiCaller, mcpNode branch por-type (FN D)

🎯 Diferença semântica
Em fluxBox/libraryNode, clearOnExecution é objeto ({key: bool}). Nos outros, é boolean. A branch acomoda os dois shapes sem checar formato explicitamente.
⚠️ fluxObject cai no gate mas sem branch
Um fluxObject com clearOnExecution truthy passaria o gate mas não tem branch aqui — ficaria inalterado. Só funciona porque o 1.5b já cuidou dele em memória.
🔧 || false vs Boolean()
x || false devolve x se truthy, senão false. Boolean(x) devolve true/false. Aqui o if trata igual, mas clearOnExecution na variável fica com o valor original — importante pro FN C que precisa iterar as chaves.
C fluxBox / libraryNode — clear por campo
flux.service.ts:2739-2752
if (nd.type === 'fluxBox' || nd.type === 'libraryNode') { Object.entries(clearOnExecution).forEach(...) }
Propósito: Iterar as chaves de clearOnExecution (objeto {key: bool}) e zerar cada campo do data cujo flag é true — se a chave já existe no data.
Em resumo: pra fluxBox e libraryNode, o usuário no editor pode escolher por campo qual output resetar — o clearOnExecution não é boolean, é um dicionário tipo { output1: true, output2: false, output3: true }. Esse branch itera esse dicionário: pra cada par (key, shouldClear), se shouldClear === true e key existe em newData, zera pra string vazia. Curioso: se o output1 for um array ou objeto no schema, ainda vira '' — o clear é sempre string vazia, sem respeitar shape. Pode causar bugs downstream se algum handler esperar array e receber string. A helper equivalente em node-output-reset.ts:94-114 (buildClearOnExecutionReset) é mais defensiva (usa && data[key] !== '' pra não regravar quando já vazio), mas a versão inline do apiV2 não.

E conditionNode.currentLoopCounter = 0
flux.service.ts:2807-2809
if (nd.type === 'conditionNode') { nd.data.currentLoopCounter = 0; }
Propósito: Zerar o contador de loops fora do gate de clearOnExecution. É a única mutação in-place no .map — muta nd.data.currentLoopCounter diretamente sem retornar node novo.
Em resumo: conditionNode tem um contador de iterações usado pra terminar loops (semelhante a "for count < 10"). Esse contador deve começar em zero pra cada run — se ficasse com o valor do run passado, o loop terminaria imediatamente ou não sairia. Curiosidade: o reset é mutação in-place — nd.data.currentLoopCounter = 0 muta o objeto original, não retorna novo. Isso é diferente do resto do .map, que sempre spread cria novos. É um footgun sutil porque se algum código de fora tiver referência pro node original, essa mutação aparece lá também. Em prática, funciona porque o getFlow.nodes foi processado pelo stripStaleErrorState (passo 1.5a) que já criou cópias — a referência original do banco não é mais compartilhada. Mas fica como "convenção sem contract".

Efeito no updatedFlows
O node retornado é o mesmo objeto (mutado in-place), não uma cópia. Se algum código já leu nd.data.currentLoopCounter antes desse map, viu o valor velho — a mutação só afeta reads depois.
⚠️ Única mutação in-place do .map
Todos os outros branches criam objetos novos via spread. Só o conditionNode muta a referência original. Inconsistência de estilo — pode ser refactor accident ou intenção obscura.
🎯 Fora do gate clearOnExecution
Loop counter sempre reseta, independente de flag. Faz sentido: um loop counter velho quebra semântica de loop.
📎 Onde currentLoopCounter é usado
No handler do conditionNode na fase 3 do apiV2. Incrementa a cada iteração do loop, testa contra data.maxLoop pra decidir se continua.
🔧 Como isso combina com outputObjectNode
Se um node é ambos outputObjectNode e conditionNode (impossível no schema), o return de A curta antes de E. Em prática, types são exclusivos.
Resumo — o que sai de 1.7a:
• updatedFlows mutado: outputObjectNode zerado (sempre); nodes com clearOnExecution truthy resetados por type
• conditionNode.currentLoopCounter = 0 em todos os conditionNodes
• Alocações: N nodes novos (spread), 1 mutação in-place (conditionNode)
• Zero I/O — puro compute em memória
Observações para migração:
• Discrepância crítica com node-output-reset.ts: esse .map inline é uma versão legacy das helpers em node-output-reset.ts. As helpers têm o jsonRequestBody: '' pro apiCaller e são mais defensivas. Migração deve usar as helpers e deletar o inline — mas testar rigorosamente por causa da assimetria.
• Mutação in-place do currentLoopCounter quebra pattern de imutabilidade — no worker, precisaria retornar node novo ou explicitar contract.
• A árvore de branches por type é manutenção infeliz: adicionar um novo node type que precisa reset exige tocar aqui, clearStaleNodeOutput, buildFluxObjectClearOnExecution, clearRunOutputForSeed. Fácil esquecer.
• Prioridade média-alta: se o worker rodar sem esse reset, resposta do run anterior "vaza" pro novo — bug visível pra usuário.
• Watch out: se qualquer parte migrar antes das outras, os dois paths podem divergir silenciosamente (backend legacy resetando um jeito, worker resetando outro). Consolidar tudo em node-output-reset.ts antes de migrar.

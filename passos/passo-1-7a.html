Passo 1.7a — Reset de nós com clearOnExecution por tipo

Bloco em flux.service.ts:2724-2812. Um .map extenso em updatedFlows. Trata duas hierarquias distintas de reset. Primeira. O outputObjectNode sempre limpa, fora do gate. Segunda. Todo o resto testa clearOnExecution truthy e cai em uma árvore de sub-branches por tipo. No final, conditionNode zera o loop counter, também fora do gate.
Em resumo — o que esse passo faz
  • Um único .map com três fatiamentos distintos. Para cada nó em updatedFlows, primeiro testa se é outputObjectNode (limpeza incondicional). Depois testa se clearOnExecution é truthy (cai em uma árvore por tipo). Por último, testa se é conditionNode (zera currentLoopCounter). Os dois "sempre limpa" (outputObjectNode e conditionNode) ignoram o gate do clearOnExecution.
  • outputObjectNode com reset incondicional. Todo o conteúdo é output derivado. Sempre limpa text: '' e textData: []. Não faz sentido preservar entre execuções. O output é sempre regerado.
  • fluxBox e libraryNode com clearOnExecution. Aqui clearOnExecution é um objeto { campo1: true, campo2: false }. Executa Object.entries e zera cada campo cuja flag é true. O reset é por campo. Não é wholesale.
  • Types que resetam por default. commandTextNode, voiceBoxNode, imageGenerator, commandContentNode, audioReaderNode, apiCaller, mcpNode. Se clearOnExecution é truthy, zeram text: '' e canceled: false. Sub-branches. voiceBoxNode retorna cedo com { canceled: false, audioUrl: '' }. commandContentNode adiciona text.result = ''. apiCaller e mcpNode adicionam { response: null, errorMessage: null, errorStatusCode: null }.
  • conditionNode.currentLoopCounter sempre 0. Zerado fora do gate. Necessário porque loop counters seriam eternos entre execuções. É mutação in-place. Não retorna nó novo. Muta a referência. Footgun sutil.
Contexto. Esta é a segunda passada de reset. O passo 1.5b tratou fluxObjects. O 1.7a trata todos os outros types que têm output ou state runtime. Existe uma versão consolidada dessa lógica em node-output-reset.ts (clearStaleNodeOutput, buildClearOnExecutionReset). O apiV2 ainda usa o if/else inline aqui. Discrepância ativa.
Cadeia em 1.7a
AoutputObjectNode (sempre) → BGate clearOnExecution → CfluxBox/libraryNode (por campo) → D7 types com fallback (voice/apiCaller/commandContent/...) → EconditionNode.currentLoopCounter = 0
Resultado. updatedFlows tem output limpo nos types listados. Todos os conditionNodes ficam com currentLoopCounter = 0.
A outputObjectNode — reset incondicional
flux.service.ts:2725-2734
if (nd.type === 'outputObjectNode') { return { ...nd, data: { ...nd.data, text: '', textData: [] } }; }
Propósito. Zera o output do outputObjectNode em todas as execuções, sem gate. É o único type que faz reset incondicional dentro deste .map. O resto depende do clearOnExecution.
Em resumo. O outputObjectNode é o endpoint do agente. É o que a execução devolve como resposta. Seu output é sempre regerado a partir dos nós upstream. Não faz sentido preservar entre execuções. Por isso o reset é hardcoded. Não depende de flag. Duas chaves são zeradas. text vira string vazia. textData vira array vazio. É o formato do output do agente (texto puro e array de itens estruturados). O return corta o resto do .map para este nó. Não passa pelo gate do clearOnExecution nem pelo bloco do conditionNode. Bug latente. Um outputObjectNode que também tivesse data.currentLoopCounter (impossível na prática, mas em teoria) não seria zerado. O return atalha.
A1 Branch incondicional
if (nd.type === 'outputObjectNode') { return { ...nd, data: { ...nd.data, text: '', textData: [], }, }; }
flux.service.ts:2725-2734
↓
Return curto no .map
O return corta o resto do map para este nó. Nenhum outro branch (clearOnExecution, conditionNode) é testado.
🎯 Por que sem gate?
O output do agente é sempre regerado. Preservar text entre execuções enganaria a próxima execução mostrando a resposta antiga se algo falhar no meio.
📎 Duplicação com clearRunOutputForSeed
clearRunOutputForSeed (passo 1.7b) também zera outputObjectNode.text = ''. É redundância intencional. Passa de novo para garantir.
⚠️ Return corta os branches seguintes
Se um outputObjectNode tivesse currentLoopCounter (não tem na prática), o reset do loop counter não roda. Feature. outputObjectNode nunca tem loop counter.
B Gate clearOnExecution (truthy)
flux.service.ts:2736-2738
const clearOnExecution = nd?.data?.clearOnExecution || false;
if (clearOnExecution) { ... }
Propósito. Porta única de entrada para os branches por tipo. Só entra quando clearOnExecution é truthy. Undefined vira false pelo || false. Todo o conteúdo depende dessa condição. Quem não tem a flag atravessa o gate sem reset.
Em resumo. Mesma lógica de Boolean(clearOnExecution) do 1.5b. Em vez de Boolean(), usa || false. Diferença sutil. Boolean({}) é true. ({}) || false resulta em {} (truthy, então o if passa). Efeito prático idêntico. O gate separa quem tem opt-in de clearing (entra no bloco) de quem não tem (nada acontece). Nota importante. Os fluxObjects também têm clearOnExecution, mas foram tratados no 1.5b. Se um fluxObject caísse aqui (impossível na prática, mas se o filter do 1.5b falhasse), o bloco não saberia lidar. Não tem branch para fluxObject.

🚪 Que types entram no bloco?
1 fluxBox / libraryNode branch por-campo (FN C)
2 commandTextNode, voiceBoxNode, imageGenerator, commandContentNode, audioReaderNode, apiCaller, mcpNode branch por-type (FN D)
3 outros types com clearOnExecution truthy nada acontece
🎯 Diferença semântica
Em fluxBox e libraryNode, clearOnExecution é objeto ({key: bool}). Nos outros, é boolean. O branch acomoda os dois shapes sem verificar o formato explicitamente.
⚠️ fluxObject cai no gate mas sem branch
Um fluxObject com clearOnExecution truthy passaria o gate, mas não tem branch aqui. Ficaria inalterado. Só funciona porque o 1.5b já cuidou dele em memória.
🔧 || false vs Boolean()
x || false devolve x quando truthy, senão false. Boolean(x) devolve true ou false. Aqui o if trata igual. Mas clearOnExecution na variável fica com o valor original. Importante para o FN C, que precisa iterar as chaves.
C fluxBox / libraryNode — clear por campo
flux.service.ts:2739-2752
if (nd.type === 'fluxBox' || nd.type === 'libraryNode') { Object.entries(clearOnExecution).forEach(...) }
Propósito. Itera as chaves de clearOnExecution (objeto {key: bool}). Zera cada campo do data cuja flag é true. A condição é que a chave já exista no data.
Em resumo. Para fluxBox e libraryNode, o usuário no editor pode escolher por campo qual output resetar. O clearOnExecution não é boolean. É um dicionário como { output1: true, output2: false, output3: true }. Este branch itera o dicionário. Para cada par (key, shouldClear), se shouldClear === true e a chave existe em newData, zera para string vazia. Detalhe. Se output1 for um array ou objeto no schema, ainda vira ''. O clear é sempre string vazia. Não respeita o shape. Pode causar bugs downstream se algum handler esperar array e receber string. A helper equivalente em node-output-reset.ts:94-114 (buildClearOnExecutionReset) é mais defensiva. Usa && data[key] !== '' para não regravar quando já vazio. A versão inline do apiV2 não faz isso.

🎯 Sempre string vazia
Não importa se o campo original é array, objeto ou number. O clear é sempre ''. É a convenção do sistema. Output limpo equivale a string vazia.
⚠️ Discrepância com node-output-reset.ts
A helper buildClearOnExecutionReset (node-output-reset.ts:94-114) é mais correta. Usa data[key] !== '' para evitar regravar quando já vazio. Retorna só o patch, não o data todo. A versão inline aqui é legacy. Ainda não migrada para usar a helper.

Bug latente. Se algum handler regravar output entre execuções, esta versão inline pode zerar dados novos que acabaram de ser gravados.
🔧 shouldClear === true strict
=== true. Comparação estrita. Strings como 'true' ou 1 não passam. Só literal boolean.

E conditionNode.currentLoopCounter = 0
flux.service.ts:2807-2809
if (nd.type === 'conditionNode') { nd.data.currentLoopCounter = 0; }
Propósito. Zerar o contador de loops fora do gate de clearOnExecution. É a única mutação in-place no .map. Muta nd.data.currentLoopCounter diretamente sem retornar nó novo.
Em resumo. O conditionNode tem um contador de iterações usado para terminar loops (semelhante a "for count < 10"). O contador deve começar em zero para cada execução. Se ficasse com o valor da execução anterior, o loop terminaria imediatamente ou não sairia. Observação. O reset é mutação in-place. nd.data.currentLoopCounter = 0 muta o objeto original. Não retorna novo. É diferente do resto do .map, que sempre cria novos via spread. É um footgun sutil. Se algum código externo tiver referência para o nó original, essa mutação aparece lá também. Na prática, funciona porque o getFlow.nodes foi processado pelo stripStaleErrorState (passo 1.5a), que já criou cópias. A referência original do banco não é mais compartilhada. Mas fica como convenção sem contract.
E1 Mutação in-place
if (nd.type === 'conditionNode') { nd.data.currentLoopCounter = 0; // nota: sem return — cai no return nd default lá embaixo } return nd; // default do .map
flux.service.ts:2807-2811
↓
Efeito no updatedFlows
O nó retornado é o mesmo objeto, mutado in-place, não uma cópia. Se algum código já leu nd.data.currentLoopCounter antes deste map, viu o valor antigo. A mutação só afeta leituras posteriores.
⚠️ Única mutação in-place do .map
Todos os outros branches criam objetos novos via spread. Só o conditionNode muta a referência original. Inconsistência de estilo. Pode ser refactor accident ou intenção obscura.
🎯 Fora do gate clearOnExecution
O loop counter sempre reseta, independente de flag. Faz sentido. Um loop counter antigo quebra a semântica de loop.
📎 Onde currentLoopCounter é usado
No handler do conditionNode na Fase 3 do apiV2. Incrementa a cada iteração do loop. Testa contra data.maxLoop para decidir se continua.
🔧 Como isso combina com outputObjectNode
Se um nó fosse outputObjectNode e conditionNode ao mesmo tempo (impossível no schema), o return do A cortaria antes do E. Na prática, os types são exclusivos.
Resumo — o que sai de 1.7a.
• updatedFlows mutado. outputObjectNode zerado sempre. Nós com clearOnExecution truthy resetados por type.
• conditionNode.currentLoopCounter = 0 em todos os conditionNodes.
• Alocações. N nós novos (spread) e uma mutação in-place (conditionNode).
• Zero I/O. Puro compute em memória.
Observações para migração.
• Discrepância crítica com node-output-reset.ts. Este .map inline é uma versão legacy das helpers em node-output-reset.ts. As helpers têm jsonRequestBody: '' para apiCaller e são mais defensivas. A migração deve usar as helpers e apagar o inline. Teste rigorosamente por causa da assimetria.
• A mutação in-place de currentLoopCounter quebra o pattern de imutabilidade. No worker, precisa retornar nó novo ou explicitar o contract.
• A árvore de branches por type dificulta a manutenção. Adicionar um novo node type que precisa de reset exige tocar aqui, em clearStaleNodeOutput, buildFluxObjectClearOnExecution e clearRunOutputForSeed. Fácil esquecer.
• Prioridade média-alta. Se o worker rodar sem esse reset, a resposta da execução anterior vaza para a nova. Bug visível para o usuário.
• Atenção. Se qualquer parte migrar antes das outras, os dois caminhos podem divergir silenciosamente. O backend legacy resetaria de um jeito. O worker de outro. Consolide tudo em node-output-reset.ts antes de migrar.

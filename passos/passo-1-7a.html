Step 1.7a — Reset of nodes with clearOnExecution by type

Block in flux.service.ts:2724-2812. A large .map over updatedFlows. Handles two distinct reset hierarchies. First. outputObjectNode always clears, outside the gate. Second. Everything else tests clearOnExecution truthy and falls into a tree of sub-branches by type. At the end, conditionNode zeroes the loop counter, also outside the gate.
In short — what this step does
  • A single .map with three distinct slices. For each node in updatedFlows, first tests whether it is outputObjectNode (unconditional clear). Then tests whether clearOnExecution is truthy (falls into a tree by type). Lastly, tests whether it is conditionNode (zeroes currentLoopCounter). The two "always clear" (outputObjectNode and conditionNode) ignore the clearOnExecution gate.
  • outputObjectNode with unconditional reset. All its content is derived output. Always clears text: '' and textData: []. It makes no sense to preserve it across executions. The output is always regenerated.
  • fluxBox and libraryNode with clearOnExecution. Here clearOnExecution is an object { field1: true, field2: false }. Runs Object.entries and zeroes each field whose flag is true. The reset is per-field. Not wholesale.
  • Types that reset by default. commandTextNode, voiceBoxNode, imageGenerator, commandContentNode, audioReaderNode, apiCaller, mcpNode. If clearOnExecution is truthy, they zero text: '' and canceled: false. Sub-branches. voiceBoxNode returns early with { canceled: false, audioUrl: '' }. commandContentNode adds text.result = ''. apiCaller and mcpNode add { response: null, errorMessage: null, errorStatusCode: null }.
  • conditionNode.currentLoopCounter always 0. Zeroed outside the gate. Necessary because loop counters would be eternal across executions. It is an in-place mutation. Does not return a new node. Mutates the reference. Subtle footgun.
Context. This is the second reset pass. Step 1.5b handled fluxObjects. Step 1.7a handles all other types that have output or runtime state. There is a consolidated version of this logic in node-output-reset.ts (clearStaleNodeOutput, buildClearOnExecutionReset). apiV2 still uses the inline if/else here. Active discrepancy.
Chain in 1.7a
AoutputObjectNode (always) → BclearOnExecution gate → CfluxBox/libraryNode (per-field) → D7 types with fallback (voice/apiCaller/commandContent/...) → EconditionNode.currentLoopCounter = 0
Result. updatedFlows has clean output on the listed types. All conditionNodes end with currentLoopCounter = 0.
A outputObjectNode — unconditional reset
flux.service.ts:2725-2734
if (nd.type === 'outputObjectNode') { return { ...nd, data: { ...nd.data, text: '', textData: [] } }; }
Purpose. Zeroes outputObjectNode output on every execution, no gate. It is the only type that does an unconditional reset inside this .map. The rest depend on clearOnExecution.
In short. outputObjectNode is the agent's endpoint. It is what the execution returns as the response. Its output is always regenerated from upstream nodes. It does not make sense to preserve it across executions. That's why the reset is hardcoded. Does not depend on a flag. Two keys are zeroed. text becomes empty string. textData becomes empty array. It is the agent output format (plain text and array of structured items). The return cuts the rest of the .map for this node. It does not go through the clearOnExecution gate nor the conditionNode block. Latent bug. An outputObjectNode that also had data.currentLoopCounter (impossible in practice, but in theory) would not be zeroed. The return short-circuits.

Short-circuit return in .map
The return cuts the rest of the map for this node. No other branch (clearOnExecution, conditionNode) is tested.
🎯 Why no gate?
The agent's output is always regenerated. Preserving text across executions would trick the next execution into showing the old response if something failed midway.
📎 Duplication with clearRunOutputForSeed
clearRunOutputForSeed (step 1.7b) also zeroes outputObjectNode.text = ''. It is intentional redundancy. Runs again to make sure.
⚠️ Return cuts subsequent branches
If an outputObjectNode had currentLoopCounter (it does not in practice), the loop counter reset would not run. Feature. outputObjectNode never has a loop counter.
B clearOnExecution gate (truthy)
flux.service.ts:2736-2738
const clearOnExecution = nd?.data?.clearOnExecution || false;
if (clearOnExecution) { ... }
Purpose. Single entry point for the branches by type. Only enters when clearOnExecution is truthy. Undefined becomes false via || false. All of the content depends on this condition. Nodes without the flag pass the gate without reset.
In short. Same logic as Boolean(clearOnExecution) from 1.5b. Instead of Boolean(), uses || false. Subtle difference. Boolean({}) is true. ({}) || false yields {} (truthy, so the if passes). Practical effect identical. The gate separates who opts in to clearing (enters the block) from who does not (nothing happens). Important note. fluxObjects also have clearOnExecution, but were handled in 1.5b. If a fluxObject fell here (impossible in practice, but if the 1.5b filter failed), the block would not know how to handle it. There is no branch for fluxObject.

🚪 Which types enter the block?
1 fluxBox / libraryNode per-field branch (FN C)
2 commandTextNode, voiceBoxNode, imageGenerator, commandContentNode, audioReaderNode, apiCaller, mcpNode per-type branch (FN D)
3 other types with clearOnExecution truthy nothing happens
🎯 Semantic difference
In fluxBox and libraryNode, clearOnExecution is an object ({key: bool}). In the others, it is a boolean. The branch accommodates both shapes without explicitly checking the format.
⚠️ fluxObject falls into the gate but no branch
A fluxObject with clearOnExecution truthy would pass the gate, but there is no branch here. It would remain unchanged. This only works because 1.5b already took care of it in memory.
🔧 || false vs Boolean()
x || false returns x when truthy, otherwise false. Boolean(x) returns true or false. Here the if treats them the same. But clearOnExecution in the variable keeps its original value. Important for FN C, which needs to iterate the keys.
C fluxBox / libraryNode — per-field clear
flux.service.ts:2739-2752
if (nd.type === 'fluxBox' || nd.type === 'libraryNode') { Object.entries(clearOnExecution).forEach(...) }
Purpose. Iterates the keys of clearOnExecution (object {key: bool}). Zeroes each field in data whose flag is true. The condition is that the key must already exist in data.
In short. For fluxBox and libraryNode, the user in the editor can pick which output to reset per field. clearOnExecution is not a boolean. It is a dictionary such as { output1: true, output2: false, output3: true }. This branch iterates the dictionary. For each pair (key, shouldClear), if shouldClear === true and the key exists in newData, sets it to empty string. Detail. If output1 is an array or object in the schema, it still becomes ''. The clear is always an empty string. Does not respect the shape. May cause downstream bugs if a handler expects an array and receives a string. The equivalent helper in node-output-reset.ts:94-114 (buildClearOnExecutionReset) is more defensive. Uses && data[key] !== '' to avoid rewriting when already empty. The apiV2 inline version does not.

🎯 Always empty string
Regardless of whether the original field is an array, object or number. The clear is always ''. It is the system's convention. Clean output equals empty string.

The buildClearOnExecutionReset helper (node-output-reset.ts:94-114) is more correct. Uses data[key] !== '' to avoid rewriting when already empty. Returns only the patch, not the full data. The inline version here is legacy. Not yet migrated to use the helper.

Latent bug. If some handler rewrites output between executions, this inline version may zero fresh data that has just been written.

=== true. Strict comparison. Strings like 'true' or 1 do not pass. Only literal boolean.

Purpose. Generic reset for the 7 types that have flat output (not per-field like fluxBox). Special sub-branches. voiceBoxNode has an early return with audioUrl. commandContentNode applies text.result: ''. apiCaller and mcpNode apply response: null and the error fields.

It is special because it uses audioUrl instead of text. Returns directly with { canceled: false, audioUrl: '' }. All 7 types receive text: '' and canceled: false as base, plus the specific newData. Observation. audioReaderNode, commandTextNode and imageGenerator have no special newData. E conditionNode.currentLoopCounter = 0
flux.service.ts:2807-2809
if (nd.type === 'conditionNode') { nd.data.currentLoopCounter = 0; }
Purpose. Zero the loop counter outside the clearOnExecution gate. It is the only in-place mutation in the .map. Mutates nd.data.currentLoopCounter directly without returning a new node.
In short. conditionNode has an iteration counter used to end loops (similar to "for count < 10"). The counter must start at zero for each execution. If it kept the previous execution's value, the loop would end immediately or never leave. Observation. The reset is an in-place mutation. nd.data.currentLoopCounter = 0 mutates the original object. Does not return a new one. Different from the rest of the .map, which always creates new ones via spread. Subtle footgun. If some external code holds a reference to the original node, this mutation shows up there too. In practice, it works because getFlow.nodes was processed by stripStaleErrorState (step 1.5a), which already created copies. The original DB reference is no longer shared. But it stands as a convention without a contract.
E1 In-place mutation
if (nd.type === 'conditionNode') { nd.data.currentLoopCounter = 0; // note: no return — falls into the default return nd below } return nd; // .map default

↓
Effect on updatedFlows
The returned node is the same object, mutated in-place, not a copy. If some code already read nd.data.currentLoopCounter before this map, it saw the old value. The mutation only affects subsequent reads.
⚠️ Only in-place mutation in the .map
All other branches create new objects via spread. Only conditionNode mutates the original reference. Style inconsistency. Could be a refactor accident or obscure intent.
🎯 Outside the clearOnExecution gate
The loop counter always resets, regardless of any flag. Makes sense. An old loop counter breaks loop semantics.
📎 Where currentLoopCounter is used
In the conditionNode handler in Phase 3 of apiV2. Increments on every loop iteration. Tests against data.maxLoop to decide whether to continue.
🔧 How this combines with outputObjectNode
If a node were outputObjectNode and conditionNode at the same time (impossible in the schema), the return in A would cut before E. In practice, types are exclusive.
Summary — what leaves 1.7a.
• updatedFlows mutated. outputObjectNode always zeroed. Nodes with clearOnExecution truthy reset by type.
• conditionNode.currentLoopCounter = 0 on every conditionNode.
• Allocations. N new nodes (spread) and one in-place mutation (conditionNode).
• Zero I/O. Pure in-memory compute.
Migration notes.
• Critical discrepancy with node-output-reset.ts. This inline .map is a legacy version of the helpers in node-output-reset.ts. The helpers have jsonRequestBody: '' for apiCaller and are more defensive. The migration should use the helpers and delete the inline. Test rigorously due to the asymmetry.
• The in-place mutation of currentLoopCounter breaks the immutability pattern. In the worker, it must return a new node or make the contract explicit.
• The tree of branches by type makes maintenance hard. Adding a new node type that requires reset requires touching here, clearStaleNodeOutput, buildFluxObjectClearOnExecution and clearRunOutputForSeed. Easy to forget.
• Medium-to-high priority. If the worker runs without this reset, the previous execution's response leaks into the new one. Bug visible to the user.
• Attention. If any part migrates before the others, the two paths may silently diverge. Legacy backend resets one way. Worker another. Consolidate everything in node-output-reset.ts before migrating.

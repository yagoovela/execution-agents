Step 4.6 — persistInputNodeData for outputObjectNode

Block at flux.service.ts:4893-4905. Filters currentFlux by type === 'outputObjectNode'. Persists text and textData of each node into flows_nodes.data via persistInputNodeData. Runs in parallel with Promise.all.
In short — what this step does
  • Saves the output result on the agent's "drawing". Takes every outputObjectNode from this execution. Writes their text and textData straight into flows_nodes.data. This is the visual archiving step. Runs in parallel with Promise.all.
  • Why write to flows_nodes.data. When the user reopens the editor, the canvas already loads the nodes from this table. The output card shows "your last result" without needing an extra query on node_executions.
  • Versioning dispatch. The private helper persistInputNodeData chooses between updateSingleNodeDataInHistory() and updateSingleNodeData(). Uses the first when the execution ran against a frozen version. Uses the second on the live working copy. Partial merge. Only text and textData are touched. The rest of the JSONB stays intact.
  • Performance cost. This persistence is exactly the fat flows_nodes.data offender. On every execution, the JSONB of these nodes grows. The frontend feels it when opening large agents.
  • Output. N parallel UPDATEs, where N is the number of outputObjectNodes. No return value. Pure side effect for the editor-reopen UX.
Context. outputObjectNodes are the agent's final outputs. The client sees their value as the result. Here those outputs get persisted into flows_nodes.data even after the execution ends. If the user reopens the editor later, they see the last response each output produced. Visual persistence.

BpersistInputNodeData (private)
flux.service.ts:2189-2216
private async persistInputNodeData(flowId, nodeId, data, flowVersionHistoryId): Promise<void>
Purpose. Dispatch between two services based on flowVersionHistoryId. If the id exists, calls flowNodeService.updateSingleNodeDataInHistory() (historical version). Otherwise, calls flowNodeService.updateSingleNodeData() (live flow).
In short. Private method that decides where to write. Flux has versioning. Each execution can run against a specific flow version (historical) or the current version (live). If the request carried flowVersionHistoryId, the execution is on a fixed version. Writes to a row in flow_version_history. Otherwise, writes to the live flows_nodes table. Simple cascade: switch on the presence of the id. The calls become UPDATEs on one of the two tables with the same payload shape (id + merge of data). The data passed in only contains { text, textData }. It doesn't overwrite the rest of flows_nodes.data. Partial merge guaranteed by the service through a TypeORM patch or raw SQL.

🎯 Two potential places
The system has manual versioning (version deploys). An execution can run against a fixed deploy or against the live version. Persisting to the right place keeps the UX consistent.
⚠️ Contributes to the fat JSONB
On every execution, the flows_nodes.data of these outputs receives new text and textData. The row grows per execution. On popular agents the JSONB gets heavy. Worsens open-flow performance (memo [[project_jsonb_fat_fields]]).
Summary — what leaves 4.6:
• N parallel UPDATEs on flows_nodes.data or flow_version_history. N is the number of outputObjectNodes.
• Final outputs persisted on the canvas. The user sees them when reopening the editor.
• No impact on the return value. Side effect only.
Migration notes:
• Contributes to the fat JSONB. Known performance offender. The refactor should migrate to node_executions.
• Versioning adds complexity. Two tables do essentially the same thing. Unifying into one model with a discriminator column would simplify things.
• Promise.all is a good pattern. However, if one UPDATE fails, the others keep going and Promise.all rejects. The behavior may surprise. Consider Promise.allSettled.

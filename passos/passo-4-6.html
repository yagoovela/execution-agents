Passo 4.6 — persistInputNodeData para outputObjectNode

Bloco em flux.service.ts:4893-4905. Filtra currentFlux por type === 'outputObjectNode'. Persiste text e textData de cada nó em flows_nodes.data via persistInputNodeData. Roda Promise.all paralelo.
Em resumo — o que esse passo faz
  • Salva o resultado dos outputs no "desenho" do agente. Pega todos os nós do tipo outputObjectNode dessa execução. Grava o text e o textData deles direto em flows_nodes.data. É a etapa de arquivamento visual. Roda em paralelo com Promise.all.
  • Motivo para gravar em flows_nodes.data. Quando o usuário reabre o editor, o canvas já carrega os nós dessa tabela. O card do output aparece com "seu último resultado" sem precisar de query extra em node_executions.
  • Dispatch por versionamento. O helper privado persistInputNodeData escolhe entre updateSingleNodeDataInHistory() e updateSingleNodeData(). Usa o primeiro quando a execução rodou numa versão congelada. Usa o segundo na working copy live. Merge parcial. Só text e textData são tocados. O resto do JSONB fica intacto.
  • Custo em performance. Essa persistência é exatamente o ofensor de flows_nodes.data gordo. A cada execução, o JSONB desses nós cresce. O frontend sente ao abrir agentes grandes.
  • Saída. N UPDATEs paralelos, onde N é o número de outputObjectNodes. Sem retorno. Puro side effect para a UX de reabertura do editor.
Contexto. Os outputObjectNodes são os outputs finais do agente. O cliente vê o valor deles como resultado. Aqui esses outputs são persistidos em flows_nodes.data mesmo depois da execução terminar. Se o usuário abrir o editor depois, vê a última resposta gerada por cada output. Persistência visual.

BpersistInputNodeData (privado)

private async persistInputNodeData(flowId, nodeId, data, flowVersionHistoryId): Promise<void>
Propósito. Dispatch entre dois serviços com base em flowVersionHistoryId. Se o id existe, chama flowNodeService.updateSingleNodeDataInHistory() (versão histórica). Caso contrário, chama flowNodeService.updateSingleNodeData() (live flow).
Em resumo. Método privado que decide onde escrever. Flux tem versionamento. Cada execução pode rodar uma versão específica do flow (histórica) ou a versão atual (live). Se o request trouxe flowVersionHistoryId, a execução está numa versão fixa. Escreve em uma linha de flow_version_history. Caso contrário, escreve na tabela live flows_nodes. Cascata simples: switch pela presença do id. As chamadas viram UPDATE em uma das duas tabelas com o mesmo shape de payload (id + merge do data). O data passado inclui só { text, textData }. Não sobrescreve o restante do flows_nodes.data. Merge parcial garantido pelo serviço via patch do TypeORM ou raw SQL.

🎯 Dois lugares potenciais
O sistema tem versionamento manual (deploy de versões). Uma execução pode rodar contra um deploy fixo ou contra a versão live. Persistir no lugar certo mantém a consistência da UX.
⚠️ Contribui para o JSONB gordo
A cada execução, o flows_nodes.data desses outputs recebe novo text e textData. A linha cresce por execução. Em agentes populares, o JSONB fica pesado. Piora a performance de open-flow (memória [[project_jsonb_fat_fields]]).
Resumo — o que sai de 4.6:
• N UPDATEs paralelos em flows_nodes.data ou flow_version_history. N é o número de outputObjectNodes.
• Outputs finais persistidos no canvas. O usuário vê ao reabrir o editor.
• Sem impacto no retorno. Apenas side effect.
Observações para migração:
• Contribui para o JSONB gordo. Ofensor de performance conhecido. O refactor deveria migrar para node_executions.
• Versionamento adiciona complexidade. Duas tabelas fazem essencialmente a mesma coisa. Unificar num modelo com coluna discriminadora simplificaria.
• Promise.all é bom padrão. Porém, se um UPDATE falha, os outros continuam e o Promise.all rejeita. O comportamento pode surpreender. Considerar Promise.allSettled.

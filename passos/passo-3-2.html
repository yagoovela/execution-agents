A myUpdatedNodes.find(node => node.id === id)
flux.service.ts:3241
const node = myUpdatedNodes.find(node => node.id === id);
Purpose. Linear lookup by id in the myUpdatedNodes array. Returns a reference, not a copy. Any mutation on node.data in the next steps hits the same object the next find will encounter.
In summary. This is the run's live archive. The scheduler handed over just a label (id), but the loop needs the employee's whole folder. The folder holds every document other nodes already touched: updated schema, filled contentData, accumulated previewResponses. find opens that folder in the shared archive (myUpdatedNodes) and hands over the original folder, not a photocopy. Anything scribbled or written on it shows up for the next person who opens the same folder. That's what lets handlers write node.data.text = 'LLM response' and the next node already see that output. If find misses (some handler removed the node from the array but the scheduler still has that id in the queue — latent bug, no known repro), the loop does not crash. It just moves to the next iteration with a silent if (node) { ... }. It's O(n). On agents with 1000+ nodes, this per-iteration linear search becomes quadratic. Cheap today, offender tomorrow.
A1 Mutable node array of the run
myUpdatedNodes was initialized at the top of apiV2() from newFlows (nodes loaded in 1.3). It is reassigned by several handlers throughout the loop:
• Temporal handlers: myUpdatedNodes = result.myUpdatedNodes (new array)
• inline handlers: myUpdatedNodes = [...nodes]
• arrayNode: rewrites during iteration

A2 node found?
if (node) { ... }. The whole loop body lives inside that guard. If find returns undefined, the loop moves to the next iteration without executing 3.3-3.11.

Why would that happen? If a handler removed an id from the array but the scheduler still holds that id in ready (latent bug, no known repro).
flux.service.ts:3244
⚠️ O(n) cost per node
Array.find is linear in the size of myUpdatedNodes. On agents with 100+ nodes that's 100 inner iterations × 100 nodes in the loop = 10,000 comparisons. Cheap today. Scaling to 1,000+ nodes goes O(n²).

A Map<id, node> would solve it in O(1). Would require maintenance every time myUpdatedNodes is reassigned.
🎯 Reassignment vs mutation
Some handlers reassign myUpdatedNodes (new array). Others mutate fields in place on node.data. Both live together. To find out which, you have to read the specific handler. Consistency is not guaranteed.
🔧 Silent skip when node = undefined
The if (node) guard swallows the case without a log. If the scheduler scheduled an id that no longer exists in myUpdatedNodes, the loop just moves to the next one. Without marking as completed or dead. That may cause a warning in Phase 4 (unprocessed nodes), but no crash.
B processedNodeIds.add + tokens/cost snapshot
flux.service.ts:3245-3250
processedNodeIds.add(id); lastExecutedNodeId = id; genericTokensBefore = totalTokensUsed; genericCostBefore = totalCost; nodeStartedAtMs = Date.now();
Purpose. Records for later use: (i) that this id was seen by the loop (used in the Phase 4.1 warning about unprocessed nodes); (ii) snapshot of how many tokens and how much cost were already spent before this node. The delta is attributed to the node at 3.7 and 3.9.
In summary. This is the employee's entry punch card. Before work starts, the system logs 4 things.
(1) "This one passed through today" (processedNodeIds). Becomes the audit trail for Phase 4 to detect orphan nodes.
(2) "This was the last one in" (lastExecutedNodeId). If the run blows up, the top-level catch knows where it stopped.
(3) Snapshot of the total tokens and cost spent so far across the entire run up to this moment. After the node runs, step 3.9 does the subtraction totalTokensUsed - genericTokensBefore and knows exactly how many tokens this node consumed.
(4) Marks the start timestamp to compute durationMs.
None of this runs the node. It's just counter setup. The subtle bit is the snapshot. The totalTokensUsed and totalCost accumulators are run-global, updated via the onUpdateTokens callback during LLM streaming. The only way to know "how much only this node cost" is via that before-after snapshot. Simple pattern, essential for per-node billing.
processedNodeIds.add(id); lastExecutedNodeId = id; let genericRunLogNode: RunLogNode | null = null; let genericTokensBefore = totalTokensUsed; // pre-execution snapshot let genericCostBefore = totalCost; const nodeStartedAtMs = Date.now(); // timer for durationMs

nodeStartedAtMs is used in the cancellation branch (line 4525: elapsedMs: Date.now() - nodeStartedAtMs) and in the RunLogNode's durationMs. Marking here ensures the timer captures all of the node's setup (substitution, RunLog, dispatch), not just the execution itself.

Used by the top-level catch (5.1) to report where it stopped when something blows up. Also appears in error webhook logs. It's a string, updated every iteration. If the run crashes mid-node, this field points to it.

C previewResponses (read from in-JSONB cache)
flux.service.ts:3270-3274
let responses = []; if (node?.data?.previewResponses?.length) { responses = [...node?.data?.previewResponses]; }
Purpose. Copies (spread) the preview responses already persisted in flows_nodes.data into a local array. Handlers for nodes that produce preview (voiceBoxNode, imageGenerator, audioReaderNode, etc.) use this array as the base to build the next history item.
In summary. This is the node's latest-photos carousel. Picture a panel in the UI showing "see the last 10 responses this node generated". Those histories live inside the JSONB of flows_nodes.data.previewResponses. The loop clones that array into local scope at the start of each execution. Handlers producing preview (TTS, image, audio, HTML) receive that array as an argument, append the new item at the end, and at step 3.6 (L4) write it back to the DB. If it already has 10 items, the oldest is dropped (shift) to keep the carousel bounded. The check is === 10, not >= 10. If, due to a bug, the array arrived with 11+, only one is removed. The next persistence goes over-size. Latent bug. Critical point for migration. previewResponses is the top FE perf offender in large agents. Each item can carry long text, base64 image, whole contentData. Times 10 versions per node times 100 nodes gives 1000 live blobs in JSONB. Handlers migrated to the worker (textGenerator, scripting, etc.) no longer receive this array. They persist to node_executions.outputData, the desired pattern.
let responses = []; if (node?.data?.previewResponses?.length) { responses = [...node?.data?.previewResponses]; // shallow clone } if (responses.length === 10) { responses.shift(); // removes the oldest }

C1 Passed via args to handlers
The responses array is passed to handlers like voiceBoxNode, audioReaderNode, commandContentNode, imageGenerator. Each pushes the new item and writes node.data.previewResponses = responses on output. It's persisted in flows_nodes.data at step 3.6 (L4).
flux.service.ts:3372, 3651, 6972, 7911
⚠️ Ring buffer only handles len === 10
The check is if (responses.length === 10). If, due to some bug, the array arrived with 11+ items (e.g. two handlers wrote in strange order), the shift happens only once. It stays at 10 or more on the next persistence.

Not robust. Should be while (responses.length >= 10).
🎯 Why 10?
Arbitrary limit to prevent flows_nodes.data from growing unbounded per node with manual rerun history. It's the "latest responses carousel" shown in the canvas UI. Lets the user navigate recent runs without persisting everything in node_executions.
⚠️ Source of the fat JSONB
previewResponses is the champion RAM and heavy-perf field in flows_nodes.data. Each item can hold long text, base64 image, whole contentData. Keeping 10 versions per node times 100 nodes gives 1000 live blobs in JSONB. That's why large agents have the FE freezing when opening the canvas.
🔧 The Temporal path doesn't use this
Handlers migrated to the worker (textGenerator, scripting, etc.) do not receive the responses array. The worker persists output to node_executions.outputData. It does not replicate it in flows_nodes.data.previewResponses. Only the inline (legacy) path keeps this cache.
Summary — what leaves 3.2:
• node: live reference into the myUpdatedNodes array (mutable).
• processedNodeIds got 1 new entry (audit trail).
• lastExecutedNodeId = id of the current node.
• genericTokensBefore and genericCostBefore: snapshot to compute delta at 3.7.
• nodeStartedAtMs: timer for durationMs and cancellation telemetry.
• responses: local array with up to 10 preview responses (only used by the inline path).
• No I/O. 100% in-memory.
Migration notes:
• myUpdatedNodes.find is coupled to the "backend is the sole orchestrator" model. In the worker, each activity receives the node by payload. No live array, no find.
• previewResponses must leave flows_nodes.data. It's the top FE perf offender (memory [[project_jsonb_fat_fields]]). Migration will move it to node_executions. That's already the Temporal path pattern.
• The tokens and cost snapshot via a loop local variable does not survive in a model where each node is an isolated activity. The worker charges individually via HTTP /worker/charge-tokens (step W7). The backend aggregates later via sumChargesByExecution (T6).
• Bookkeeping (processedNodeIds, lastExecutedNodeId) is today used in Phase 4/5 for warnings and diagnostics. In the worker, that info can come from Temporal's own WorkflowHistory (more reliable). Essential, easy to reimplement.
• The ring-buffer bug (=== 10 instead of >= 10) deserves a line in the migration plan to fix before porting.

Step 1.1 — Bull queue api-v2 · ApiV2QueueProcessor.execute()

Bull queue api-v2. Defined in apiV2Job.queue.ts and consumed at apiV2Job.processor.ts:44-174. It is the async entry point for agent execution. Enqueues the payload in Redis. Runs with limited concurrency. Delegates to FluxService.apiV2. Updates two status tables. Fires an HTTP callback at the end.
In short — what this step does
  • Async entry point. Any code that needs to execute an agent in the background calls ApiV2Queue.enqueueApiV2Job(model). The payload becomes a Bull job in Redis with timeout: 600s, attempts: 1 (no retry), and a jobId generated by UUID when the caller does not provide one.
  • Consumption with controlled concurrency. The processor reads the AGENT_CONCURRENCY env (default 5) via parseConcurrency. Each Node worker processes up to N jobs simultaneously. If the env is empty or invalid, it falls back to the default.
  • execute() flow. Extracts { jobId, params, webhookUrl, apiV2CallbackFormat }. Resolves processId = params.parentProcessId ?? jobId. Calls markRunning (MCP) and markInProgress (flow_execution_status) if the IDs exist. Invokes fluxService.apiV2({ ...params, parentProcessId, mcpTokenId }). Computes duration. Marks markFinished plus markCompleted or markError based on result.nodeError. Finally fires the HTTP callback (POST with 10s timeout).
  • Two callback formats. apiV2CallbackFormat=true builds a rich payload (executionId, success, outputs, totalTokensUsed, totalCost, timestamp). Otherwise returns the legacy payload { jobId, result }. In the error path, the legacy becomes { jobId, error }.
  • Catch mirrors everything. On exception, the processor computes durationMs. Marks both tables as error with tokens: 0, cost: 0. Fires the callback (new format with success: false or legacy with { jobId, error }). Rethrows the exception. This lets Bull's @OnQueueFailed log to Winston.
  • Output. Returns the result object from fluxService.apiV2. Bull persists it in job.returnvalue. The onFailed handler logs separately with error_type: 'Internal Server Error', status 500, and a stack trace.
Context. This queue is today the backend's only legitimate point for fire-and-forget agent execution. It is called by 3 internal clients. Trigger HTTP endpoints. MCP tool. flowCallerNode or libraryNode nodes in triggerOnly mode. The synchronous apiV2 path (direct controller call) does not go through the queue.

A ApiV2Queue.enqueueApiV2Job(model)
apiV2Job.queue.ts:18-35
async enqueueApiV2Job(model: ApiV2QueueModel): Promise<Job>
Purpose. Wraps the ApiV2QueueModel in a Bull job and sends it to the api-v2 queue on Redis. Serves both external HTTP triggers and nodes executing sub-flows in triggerOnly mode.
In short. The function takes the package (ApiV2QueueModel). Ensures it has a unique label. The jobId comes from the caller or is generated by UUID. Sends it to the queue with clear rules. It has 10 minutes to run. On success, it disappears from the queue in 5 minutes. On failure, it stays for 24h or until 20 failures accumulate, whichever comes first. It does not retry (attempts: 1). Each job is independent. The jobId is also duplicated inside jobData. Not redundant. Lets the processor read the same id from job.data without needing Bull's job.id.

📎 APIV2_QUEUE_NAME and APIV2_JOB_NAME
Constants exported at models/apiV2JobModel.ts:32-33.
APIV2_QUEUE_NAME = 'api-v2'.

Bull separates by queue name and job name. It allows multiple types on the same queue. Here there is only one.
🎯 jobId as dedup key
Bull rejects add() with an already-existing jobId (if still active). Callers that pass an explicit jobId (e.g., MCP passing processId) get natural dedup. Two calls with the same id do not duplicate.
⚠️ attempts: 1 (no retry)
If the worker fails mid-run or the job throws, it does not reprocess. It goes straight to failed. Good for avoiding duplicate side effects (email, webhook). Bad if the error was transient (network blip with LLM provider).

Conscious trade-off. Agents have irreversible side effects (billing, webhook, email).
🔧 removeOn*: housekeeping
removeOnComplete: { age: 300 }. The job leaves Redis 5 minutes after completion. Memory savings.

removeOnFail: { age: 24*3600, count: 20 }. Failures stay 24h or the 20 most recent, whichever expires first. Helps debugging without bloating Redis.
B @Process({ concurrency })
apiV2Job.processor.ts:16-25, 44-47
parseConcurrency(process.env.AGENT_CONCURRENCY) → number // default 5
Purpose. Defines how many simultaneous jobs each worker instance processes. Read at app boot, in the static decorator. Changing the env requires a restart.
In short. This parameter decides how many agents can run simultaneously inside the same Node process. Reads the AGENT_CONCURRENCY env when the app boots. Tries to parse it as an integer. If it fails (empty env, any string, zero, or negative number), falls back to the default 5. The decorator is evaluated once at initialization. Changing the env at runtime does nothing. A restart is required. With 3 backend instances, each processes up to 5 simultaneous jobs. The real ceiling is concurrency multiplied by instances.
B1 parseConcurrency helper
const AGENT_DEFAULT_CONCURRENCY = 5; const parseConcurrency = (raw: string | undefined): number => { if (!raw) return AGENT_DEFAULT_CONCURRENCY; const parsed = Number.parseInt(raw, 10); return Number.isFinite(parsed) && parsed > 0 ? parsed : AGENT_DEFAULT_CONCURRENCY; };

📎 Why env var and not config service?
Concurrency is infra (not business). It has to be read before NestJS wires up DI. A pure env var, evaluated at boot, is the Bull pattern. Changing it requires a process restart.
🎯 Real scale: concurrency × instances
If 3 backend instances are active, each processes up to 5 simultaneous jobs. Total of 15. There is no coordination between them. Bull distributes via Redis (BRPOPLPUSH).
⚠️ Invalid env silently falls back to default
AGENT_CONCURRENCY=abc results in parseInt('abc', 10) = NaN. Number.isFinite(NaN) = false. Applies default 5.

No log, no warning. A typo (wanting 20 and typing wrong) results in running with 5 without notice.

C execute(). Happy-path flow
apiV2Job.processor.ts:48-127
async execute(job: Job<ApiV2QueueModel>) → result
Purpose. Main method. Receives the Bull job. Extracts payload. Orchestrates the call to FluxService.apiV2. Updates status tables. Fires the HTTP callback at the end.
In short. The method unpacks the job (jobId, params, webhookUrl, format flag). Resolves two important identifiers. processId comes from parentProcessId if from a sub-flow. Otherwise from the jobId itself. executionId only comes when the caller wants tracking in the flow_execution_status table. Records the duration timestamp. Does two start markings if the IDs exist. MCP and flow_execution_status are independent. Calls fluxService.apiV2. That is the heavy call that runs Phases 1-4 of the agent. Computes duration at the end. Decides whether it was an error based on the presence of result.nodeError. Propagates status to both tables. Only then fires the webhook. The return value goes to Bull's job.returnvalue.
🔢 execute() steps (happy path)
1 extract { jobId, params, webhookUrl, apiV2CallbackFormat } from job.data next
2 processId = params.parentProcessId ?? jobId next
3 startedAt = Date.now() next
4 if params.mcpTracking → markRunning(processId) → MCP
5 if executionId → markInProgress(executionId) → FES
6 fluxService.apiV2({ ...params, parentProcessId: processId, mcpTokenId }) → Phase 1-4
7 durationMs = Date.now() - startedAt next

9 FES: markError or markCompleted based on result.nodeError → FES
10 if webhookUrl → HTTP POST with new or legacy payload → webhook
11 return result ✓ Bull persists

🎯 processId, jobId, and executionId are distinct
Three distinct IDs coexist.
jobId. Bull id. Dedup key.
processId. Logical execution id. Used by MCP and the run log. Comes from parentProcessId in sub-flows. Otherwise equals jobId.
executionId. Id on the flow_execution_status table. Only exists for trigger executions with opt-in callback.
⚠️ Markings have gated early exit
markRunning only runs if params.mcpTracking.
markInProgress only runs if executionId.

Most executions (internal trigger, fire-and-forget from nodes) write to neither table. They pass straight to apiV2.
🔧 Spread ...params silently ignores executionId
this.fluxService.apiV2({ ...params, ... }) forwards executionId in the argument. apiV2's destructuring (flux.service.ts:2280-2318) does not mention executionId. It stays in the object but is never read. Dead data.
📎 result.nodeError decides error vs success
apiV2 does not throw on node error. It returns result.nodeError: string. If filled, both tables become status error. If null or undefined, they become completed.

Only an uncaught JavaScript exception (network outage, bug) lands in the catch (fn E).
D buildApiV2CallbackPayload(args)
apiV2Job.processor.ts:176-198
private buildApiV2CallbackPayload(args): { executionId, success, flowId, sessionId, totalTokensUsed, totalCost, timestamp, outputs, error }
Purpose. Builds the new (v2 format) payload of the HTTP callback. Only used when apiV2CallbackFormat === true. Otherwise the processor sends the legacy payload { jobId, result } directly.
In short. It is the output envelope for the client that asked for the modern callback. The legacy envelope is raw. It returns the entire result, with everything apiV2 returned. The new one is lean and stable. It takes only the essentials (executionId, flowId, sessionId, total tokens, total cost, ISO timestamp, outputs, error if any) and assembles a flat object. The success flag is derived from !result.nodeError. It is true if there is no error. On error, outputs goes as [] to avoid leaking confusing partial output. Defensive defaults on every numeric field (?? 0). If apiV2 forgot to count something, the payload does not break.

🎯 outputs = [] on error
If result.nodeError is present, outputs becomes []. It is an explicit decision to avoid leaking partial output to the caller. The legacy sends the raw result, so it may have partial output and error together.
🔧 ?? 0 defaults on numeric fields
totalTokensUsed ?? 0 and totalCost ?? 0. If apiV2 did not populate (failed early), the payload still has consistent type. The HTTP client can rely on typeof x === 'number'.
E catch block. Error mirror
apiV2Job.processor.ts:128-173
catch (error) { markFinished('error') · markError · callback(success:false) · throw error; }
Purpose. Handles JavaScript exceptions not caught by apiV2 (network outage, third-party throw, code bug). Marks both tables as error. Fires the callback with success: false. Rethrows so Bull records it in failed.
In short. This block mirrors the happy path with error values. It redoes the same 4 steps (durationMs, MCP markFinished, FES markError, callback), but with hardcoded error values. Status error, tokens 0, cost 0. The error message is extracted with error instanceof Error ? error.message : String(error). Covers both native Error and any throwable value (string, number, object). At the end, throw error hands the exception back to Bull. Bull moves the job to the failed list on Redis and fires the @OnQueueFailed hook. Without the re-throw, Bull would consider it a success and never call the failure handler.

📎 New-format error payload
Different from the happy path (which has outputs, totalTokensUsed, among others), the error payload is smaller. Just { executionId, success:false, error, flowId, timestamp }. A client expecting outputs must check success first.
⚠️ What if the error callback also fails?
lastValueFrom(httpService.post(...)) can throw (timeout, DNS, 5xx). That exception propagates above the catch. It is not caught. The job goes to failed with the callback error message, not the original one.

Bad sequence. MCP and FES were already marked with the original error, but Bull records the callback error. It is a subtle divergence during debug.
⚠️ tokens: 0 and cost: 0 hardcoded
If apiV2 failed mid-run (after already making expensive provider calls), the error rises with tokens: 0, cost: 0. The real billing is invisible on this trail. Requires cross-referencing with provider logs.
🔧 instanceof Error is safe
error instanceof Error ? error.message : String(error). TypeScript accepts any value in catch. Covers throw 'string', throw 42, and throw { foo: 1 } without crash.
F @OnQueueFailed()
apiV2Job.processor.ts:200-212
onFailed(job: Job, err: Error) → void // Winston.error com metadata estruturada
Purpose. Bull hook called when the job goes to failed (because of the throw in E or timeout). Logs to Winston with rich metadata for observability. Outside the synchronous flow of execute().
In short. It is the processor's black box. Runs automatically every time a job ends up in failed. This happens when execute() throws in the catch (E5) or the job blows the 10-minute timeout. It does only one thing. It calls this.logger.error (Winston) with structured metadata. Includes error_type: 'Internal Server Error', status: 500, the user and flow from the payload (with defensive ?., as they may be missing), and the error's stack. It is what shows up in CloudWatch and production logs when an agent fails. It does not write to the MCP and FES tables. That was already done in the catch. Here it is observability only.

@OnQueueFailed() onFailed(job: Job, err: Error) { this.logger.error({ message: `ApiV2QueueProcessor - ERROR While Processing job ${job.data.jobId}`, metadata: { error_type: 'Internal Server Error', status: 500, user: job.data?.params?.user, flow: job.data?.params?.flow, stack: err?.stack, }, }); }
apiV2Job.processor.ts:200-212
🎯 Complementary, not a replacement
F1 does not write to MCP and FES. That is done in the catch (E). F1 exists only for Winston (CloudWatch, Datadog, etc.). It is the structured log for the observability pipeline.
📎 Also fires on Bull timeout
If the job exceeds timeout: 600000, Bull kills the worker and calls @OnQueueFailed. In that case, E's catch does not run. The job was terminated from the outside. F1 logs, but MCP and FES may stay in in_progress forever. It is an orphan.
⚠️ Full user object in the log
job.data?.params?.user. Sends the entire User object into the log. Includes email, id, roles, and possibly PII. Violates the logging rule (do not leak name or email). Should be watched during the worker migration. A good cleanup opportunity.
🔧 error_type and status 500 hardcoded
Internal convention. Every failed job is classified as 'Internal Server Error' with status 500, regardless of the real cause (validation, network, provider). Makes dashboards easier, but loses granularity.
Summary. What comes out of 1.1:
job.returnvalue. The result object from fluxService.apiV2. Persisted by Bull in Redis for 5 minutes after completion.
Table mcp_run_status. Row updated with status, tokens, cost, durationMs, and errorMessage. Only if params.mcpTracking was present.
Table flow_execution_status. Row updated with status, output, tokensUsed, totalCost, durationMs, and finishedAt. Only if executionId was present.
HTTP POST webhook fired (10s timeout) with either legacy payload { jobId, result } or new v2 format. Only if webhookUrl is present.
On failure, the exception is rethrown. Bull marks failed. Winston logs via @OnQueueFailed with stack, user, and flow.
Notes for migration:
The queue still exists today because apiV2 is still synchronous and runs in the backend request. For callers that want fire-and-forget (MCP tool, triggerOnly nodes), the queue is the only available HTTP decoupling. Without a Temporal worker, there is no alternative.
If the Temporal worker takes over execution, the queue can be deleted. Temporal itself is already a durable queue with retry, timeout, and built-in observability. The caller starts using client.workflow.start(...) instead of enqueueApiV2Job.
Points that survive without the queue. The HTTP callback dispatch becomes an activity in the workflow. The markings in mcp_run_status and flow_execution_status become status activities. They can be consolidated into a single table, since today there is duplication. OnQueueFailed becomes the workflow's error handler.
Attempts: 1 does not change. Agents have irreversible side effects. Temporal must be configured with maximumAttempts: 1 on the main activity's retry policy.
Concurrency becomes Temporal worker config (concurrency of taskQueue). No longer an env var read at Nest boot.
Risks of deferring. MCP and FES duplication, dead data in the spread, and PII logging are latent bugs. Worth cleaning up together when rewriting the handler for the worker.

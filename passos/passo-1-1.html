Passo 1.1 — Bull queue api-v2 · ApiV2QueueProcessor.execute()

Bull queue api-v2 definida em apiV2Job.queue.ts e consumida em apiV2Job.processor.ts:44-174. É a porta de entrada assíncrona pra execução de agentes — enfileira o payload no Redis, roda com concorrência limitada, delega ao FluxService.apiV2, atualiza duas tabelas de status e dispara callback HTTP no fim.
Em resumo — o que esse passo faz
  • Porta de entrada assíncrona: qualquer código que precise rodar um agente "em background" chama ApiV2Queue.enqueueApiV2Job(model) — o payload vira um job Bull no Redis com timeout: 600s, attempts: 1 (sem retry) e jobId auto-gerado por UUID caso não venha do chamador.
  • Consumo com concorrência controlada: o processor lê a env AGENT_CONCURRENCY (default 5) via parseConcurrency — cada worker Node processa até N jobs simultâneos. Se a env vier vazia ou inválida, cai no default.
  • Fluxo do execute(): extrai { jobId, params, webhookUrl, apiV2CallbackFormat }, resolve processId = params.parentProcessId ?? jobId, chama markRunning (MCP) e markInProgress (flow_execution_status) se os IDs existirem, invoca fluxService.apiV2({ ...params, parentProcessId, mcpTokenId }), calcula duração, marca markFinished+markCompleted/markError conforme result.nodeError, e finalmente dispara callback HTTP (POST com timeout 10s).
  • Dois formatos de callback: apiV2CallbackFormat=true monta payload rico (executionId, success, outputs, totalTokensUsed, totalCost, timestamp); senão devolve o payload legacy { jobId, result }. No caminho de erro, o legacy vira { jobId, error }.
  • Catch replica tudo: em exceção, o processor calcula durationMs, marca ambas as tabelas como erro com tokens: 0, cost: 0, dispara callback (formato novo com success: false ou legacy com { jobId, error }) e re-lança — pra que o @OnQueueFailed do Bull registre no Winston.
  • Saída: retorna o objeto result do fluxService.apiV2 (o Bull persiste isso em job.returnvalue). Handler onFailed loga separadamente com error_type: 'Internal Server Error', status 500 e stack trace.
Contexto: essa fila é o único ponto legítimo do backend hoje pra rodar agentes de forma fire-and-forget — chamada por 3 clientes internos (endpoints HTTP de trigger, MCP tool, nós flowCallerNode/libraryNode em modo triggerOnly). O caminho síncrono do apiV2 (chamada direta do controller) não passa pela fila.
Cadeia de chamadas em 1.1
AApiV2Queue.enqueueApiV2Job → B@Process({ concurrency }) → Cexecute() — fluxo happy path → DbuildApiV2CallbackPayload → Ecatch — replica de erro → F@OnQueueFailed
Resultado final: job Bull com returnvalue = result do apiV2, tabelas mcp_run_status/flow_execution_status atualizadas e callback HTTP disparado (se webhookUrl).
A ApiV2Queue.enqueueApiV2Job(model)
apiV2Job.queue.ts:18-35
async enqueueApiV2Job(model: ApiV2QueueModel): Promise<Job>
Propósito: Empacota o ApiV2QueueModel num job Bull e joga na fila api-v2 no Redis. Serve tanto pros triggers HTTP externos quanto pros nós que rodam sub-flows em modo triggerOnly.
Em resumo: pense nessa função como o despachante — recebe o pacote (ApiV2QueueModel), garante que ele tem uma etiqueta única (jobId vem do chamador ou é gerado por UUID) e joga no cinturão da fila com regras claras: tem 10 minutos pra rodar, se der certo some da fila em 5 minutos, se der errado fica lá por 24h ou até acumular 20 falhas (o que vier primeiro), e não tenta de novo (attempts: 1). Trade-off consciente: agentes têm side effects irreversíveis (cobrança, webhook, email).
🔧 removeOn* — housekeeping
removeOnComplete: { age: 300 } — job some do Redis 5min após completar (economia de memória).

removeOnFail: { age: 24*3600, count: 20 } — falhas ficam 24h OU as 20 mais recentes (o que expirar primeiro). Ajuda a debugar sem inflar Redis.
B @Process({ concurrency })
apiV2Job.processor.ts:16-25, 44-47
parseConcurrency(process.env.AGENT_CONCURRENCY) → number // default 5
Propósito: Define quantos jobs simultâneos cada instância do worker processa. É lido no boot da app (no decorator estático) — mudar a env exige restart.
Em resumo: essa parte é o porteiro do galpão — decide quantos agentes podem estar rodando ao mesmo tempo dentro do mesmo processo Node. Ele lê a env AGENT_CONCURRENCY logo quando a app sobe, tenta parsear como inteiro, e se der ruim (env vazia, string qualquer, número zero ou negativo) cai no default 5. Detalhe importante: como o decorator é avaliado uma vez na inicialização, trocar a env em runtime não faz nada — precisa reiniciar. E se você roda 3 instâncias do backend, cada uma processa até 5 jobs simultâneos, então o teto real é concorrência × instâncias.
B1 parseConcurrency helper
const AGENT_DEFAULT_CONCURRENCY = 5; const parseConcurrency = (raw: string | undefined): number => { if (!raw) return AGENT_DEFAULT_CONCURRENCY; const parsed = Number.parseInt(raw, 10); return Number.isFinite(parsed) && parsed > 0 ? parsed : AGENT_DEFAULT_CONCURRENCY; };

📎 Por que env var e não config service?
Concorrência é infra (não business), e precisa ser lida antes do NestJS montar o DI. Env var pura, avaliada no boot, é o padrão do Bull. Trocar exige restart do processo.
🎯 Escala real = concorrência × instâncias
Se 3 instâncias do backend estão vivas, cada uma processa até 5 jobs simultâneos ⇒ 15 no total. Não há coordenação entre elas — Bull distribui via Redis (BRPOPLPUSH).
⚠️ Env inválida cai no default silenciosamente
AGENT_CONCURRENCY=abc ⇒ parseInt('abc', 10) = NaN ⇒ Number.isFinite(NaN) = false ⇒ default 5.

Nenhum log, nenhum warning. Se você achou que setou 20 e digitou errado, roda com 5 sem avisar.

C execute() — fluxo happy path
apiV2Job.processor.ts:48-127
async execute(job: Job<ApiV2QueueModel>) → result
Propósito: Método principal — recebe o job Bull, extrai payload, orquestra chamada ao FluxService.apiV2, atualiza tabelas de status e dispara callback HTTP no fim.
Em resumo: essa é a linha de montagem — desempacota o job (jobId, params, webhookUrl, flag de formato), resolve dois identificadores importantes (processId vem do parentProcessId se veio de sub-flow, senão do próprio jobId; executionId vem só quando o chamador quer rastreamento na tabela flow_execution_status), abre timestamp de duração, faz duas marcações de "começou" se os IDs existem (MCP + flow_execution_status são independentes), chama o fluxService.apiV2 — essa é a chamada pesada que roda a Fase 1-4 inteira do agente —, calcula duração no fim, decide se foi erro (existe result.nodeError) e propaga status pras duas tabelas, e só então dispara webhook. O retorno vai pro job.returnvalue do Bull.

2 processId = params.parentProcessId ?? jobId next
3 startedAt = Date.now() next

9 FES: markError ou markCompleted conforme result.nodeError → FES

11 return result ✓ Bull grava

🎯 processId ≠ jobId ≠ executionId
Três IDs distintos convivendo:
• jobId = id do Bull (chave dedup)
• processId = id lógico do run (usado pelo MCP e pelo run-log). Vem de parentProcessId pra sub-flows; senão = jobId.
• executionId = id na tabela flow_execution_status. Só existe pra runs vindos de trigger com callback opt-in.
⚠️ Marcações têm early-exit por gate
markRunning só roda se params.mcpTracking.
markInProgress só roda se executionId.

Isso quer dizer que a maioria dos runs (trigger interno, fire-and-forget dos nós) não escreve em nenhuma das tabelas — passa direto pro apiV2.
🔧 Spread ...params silenciosamente ignora executionId
this.fluxService.apiV2({ ...params, ... }) derrama executionId no argumento, mas a destructuring do apiV2 (flux.service.ts:2280-2318) não menciona executionId — ele fica no objeto mas nunca é lido. Puro dead data.
📎 result.nodeError decide erro vs sucesso
O apiV2 não throw em erro de nó — retorna result.nodeError: string. Se estiver preenchido, ambas as tabelas viram status error. Se estiver null/undefined, viram completed.

Só exceção JS não capturada (queda de rede, bug) cai no catch (fn E).
D buildApiV2CallbackPayload(args)
apiV2Job.processor.ts:176-198
private buildApiV2CallbackPayload(args): { executionId, success, flowId, sessionId, totalTokensUsed, totalCost, timestamp, outputs, error }
Propósito: Monta o payload "novo" (formato v2) do callback HTTP. Só usado quando apiV2CallbackFormat === true. Senão o processor manda o payload legacy { jobId, result } direto.
Em resumo: é o envelope de saída pro cliente que pediu callback moderno. O envelope legacy é cru — devolve o result inteiro, com tudo que o apiV2 retornou. O novo é enxuto e "estável": pega só o essencial (executionId, flowId, sessionId, tokens totais, custo total, timestamp ISO, outputs, erro se houver) e monta um objeto plano. A flag success é derivada — !result.nodeError, ou seja, true se não tem erro. Se teve erro, outputs vai como [] pra não vazar output parcial confuso. E defaults defensivos em todos os campos numéricos (?? 0) — se o apiV2 esqueceu de contabilizar, não quebra o payload.

[] : args.result.outputs ?? [], error: args.result.nodeError ?? null, }

E catch block — replica de erro
apiV2Job.processor.ts:128-173
catch (error) { markFinished('error') · markError · callback(success:false) · throw error; }
Propósito: Trata exceções JS não capturadas pelo apiV2 (queda de rede, throw de terceiros, bug de código). Marca ambas tabelas como erro, dispara callback com success: false, e re-lança pro Bull registrar em failed.
Em resumo: é o plano B espelhado — praticamente refaz os mesmos 4 passos do happy path (durationMs, MCP markFinished, FES markError, callback), mas com valores hard-coded pra erro: status error, tokens 0, cost 0. A mensagem do erro é extraída com error instanceof Error ? error.message : String(error) — cobre tanto Error nativo quanto qualquer coisa jogável (string, número, obj). No fim, throw error devolve a exception pro Bull, pra que ele mova o job pra lista failed no Redis e dispare o hook @OnQueueFailed. Sem esse re-throw, o Bull acharia que deu certo e nunca chamaria o handler de falha.

📎 Payload de erro do formato novo
Diferente do happy path (que tem outputs, totalTokensUsed, etc.), o payload de erro é menor: só { executionId, success:false, error, flowId, timestamp }. Cliente que espera outputs tem que checar success antes.
⚠️ E se o callback de erro também falhar?
lastValueFrom(httpService.post(...)) pode dar throw (timeout, DNS, 5xx). Essa exception propaga pra cima do catch — não é capturada. Resultado: job vai pra failed com a mensagem do erro do callback, não do erro original.

Sequência ruim: MCP/FES já foram marcados com o erro original, mas o Bull registra o erro do callback. Divergência sutil pra debug.
⚠️ tokens: 0 / cost: 0 hardcoded
Se o apiV2 falhou no meio (após já ter feito calls pra provider caras), o erro sobe com tokens: 0, cost: 0. A cobrança real fica invisível nesse rastro — precisa cross-referenciar com logs de provider.
🔧 instanceof Error é seguro
error instanceof Error ? error.message : String(error) — TS aceita anything em catch. Cobre throw 'string', throw 42, throw { foo: 1 } sem crashar.
F @OnQueueFailed()
apiV2Job.processor.ts:200-212
onFailed(job: Job, err: Error) → void // Winston.error com metadata estruturada
Propósito: Hook do Bull chamado quando o job vai pra failed (por causa do throw em E ou timeout). Registra no Winston com metadata rica pra observabilidade — fora do fluxo síncrono do execute().
Em resumo: é a caixa preta do processor. Roda automaticamente sempre que um job termina em failed — seja porque execute() jogou uma exception no catch (E5) ou porque o job estourou o timeout de 10min sem terminar. Ele só faz uma coisa: chama this.logger.error (Winston) com uma metadata bem estruturada — error_type: 'Internal Server Error', status: 500, o user e flow do payload (com ?. defensivo, porque em teoria pode faltar), e o stack do erro. Isso é o que aparece no CloudWatch / logs de produção quando um agente falha. Note que ele não escreve nas tabelas MCP/FES — isso já foi feito no catch. Aqui é só observabilidade.
F1 Winston.error com metadata rica
@OnQueueFailed() onFailed(job: Job, err: Error) { this.logger.error({ message: `ApiV2QueueProcessor - ERROR While Processing job ${job.data.jobId}`, metadata: { error_type: 'Internal Server Error', status: 500, user: job.data?.params?.user, flow: job.data?.params?.flow, stack: err?.stack, }, }); }
apiV2Job.processor.ts:200-212
🎯 Complementar, não substituto
F1 não escreve em MCP/FES — quem faz isso é o catch (E). F1 só existe pro Winston (CloudWatch / Datadog / etc.). É o log estruturado que fica na esteira de observabilidade.
📎 Dispara também em timeout do Bull
Se o job estourar timeout: 600000, o Bull mata o worker e chama @OnQueueFailed — mas nesse caso o catch de E NÃO roda (o job foi morto de fora). Resultado: F1 loga, mas MCP/FES podem ter ficado em in_progress pra sempre. Órfão.
⚠️ user completo no log
job.data?.params?.user — passa o objeto User inteiro pra dentro do log. Inclui email, id, roles, e possivelmente PII. Violação sutil da regra de logging (não vazar nome/email). Ficar de olho quando migrar pro worker — chance ótima de limpar isso.
🔧 error_type + status 500 hard-coded
Convenção interna: todo job falho é classificado como 'Internal Server Error'/500, independente da causa real (validation, network, provider). Facilita dashboards mas perde granularidade.
Resumo — o que sai de 1.1:
• job.returnvalue = o objeto result do fluxService.apiV2 (persistido pelo Bull no Redis por 5min após completar)
• Tabela mcp_run_status: row atualizada com status/tokens/cost/durationMs/errorMessage — só se params.mcpTracking estava presente
• Tabela flow_execution_status: row atualizada com status/output/tokensUsed/totalCost/durationMs/finishedAt — só se executionId estava presente
• Webhook HTTP POST disparado (10s timeout) com payload legacy { jobId, result } ou novo formato v2 — só se webhookUrl presente
• Em falha: exception re-lançada ⇒ Bull marca failed ⇒ Winston loga via @OnQueueFailed com stack + user + flow
Observações para migração:
• Fila continua existindo hoje porque o apiV2 ainda é síncrono e roda no request do backend — pra callers que querem fire-and-forget (MCP tool, nós triggerOnly), a fila é o único desacoplamento HTTP disponível. Sem worker Temporal, sem alternativa.
• Se o worker Temporal absorver a execução, a fila pode ser deletada — o próprio Temporal já é uma fila durável com retry/timeout/observabilidade builtin. Chamador vira client.workflow.start(...) em vez de enqueueApiV2Job.
• Pontos que sobrevivem sem fila: (1) o dispatch de callback HTTP vira uma atividade no workflow; (2) as marcações em mcp_run_status e flow_execution_status viram atividades de status (podem inclusive ser consolidadas numa só tabela, hoje tem duplicação);(3) OnQueueFailed vira o handler de erro do workflow.
• Attempts: 1 não muda: agentes têm side-effects irreversíveis. O Temporal precisa ser configurado com maximumAttempts: 1 na retry policy da atividade principal.
• Concorrência vira config do worker Temporal (taskQueue concurrency), não mais env var lida no boot do Nest.
• Riscos de deixar pra depois: a duplicação MCP/FES + os dead-data no spread + o log de PII são bugs latentes. Vale limpar junto quando reescrever o handler pro worker.

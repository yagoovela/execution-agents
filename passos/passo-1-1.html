Passo 1.1 — Bull queue api-v2 · ApiV2QueueProcessor.execute()

Bull queue api-v2. Definida em apiV2Job.queue.ts e consumida em apiV2Job.processor.ts:44-174. É a porta de entrada assíncrona para a execução de agentes. Enfileira o payload no Redis. Executa com concorrência limitada. Delega ao FluxService.apiV2. Atualiza duas tabelas de status. Dispara callback HTTP no fim.
Em resumo — o que esse passo faz
  • Porta de entrada assíncrona. Qualquer código que precise executar um agente em background chama ApiV2Queue.enqueueApiV2Job(model). O payload vira um job Bull no Redis com timeout: 600s, attempts: 1 (sem retry) e jobId gerado por UUID quando não vem do chamador.
  • Consumo com concorrência controlada. O processor lê a env AGENT_CONCURRENCY (default 5) via parseConcurrency. Cada worker Node processa até N jobs simultâneos. Se a env vier vazia ou inválida, cai no default.
  • Fluxo do execute(). Extrai { jobId, params, webhookUrl, apiV2CallbackFormat }. Resolve processId = params.parentProcessId ?? jobId. Chama markRunning (MCP) e markInProgress (flow_execution_status) se os IDs existirem. Invoca fluxService.apiV2({ ...params, parentProcessId, mcpTokenId }). Calcula duração. Marca markFinished mais markCompleted ou markError conforme result.nodeError. Por fim, dispara callback HTTP (POST com timeout 10s).
  • Dois formatos de callback. apiV2CallbackFormat=true monta payload rico (executionId, success, outputs, totalTokensUsed, totalCost, timestamp). Caso contrário, devolve o payload legacy { jobId, result }. No caminho de erro, o legacy vira { jobId, error }.
  • Catch replica tudo. Em exceção, o processor calcula durationMs. Marca ambas as tabelas como erro com tokens: 0, cost: 0. Dispara callback (formato novo com success: false ou legacy com { jobId, error }). Relança a exceção. Isso permite que o @OnQueueFailed do Bull registre no Winston.
  • Saída. Retorna o objeto result do fluxService.apiV2. O Bull persiste isso em job.returnvalue. O handler onFailed registra separadamente com error_type: 'Internal Server Error', status 500 e stack trace.
Contexto. Essa fila é o único ponto legítimo do backend hoje para executar agentes de forma fire-and-forget. É chamada por 3 clientes internos. Endpoints HTTP de trigger. MCP tool. Nós flowCallerNode ou libraryNode em modo triggerOnly. O caminho síncrono do apiV2 (chamada direta do controller) não passa pela fila.

A ApiV2Queue.enqueueApiV2Job(model)
apiV2Job.queue.ts:18-35

Propósito. Empacota o ApiV2QueueModel num job Bull e envia para a fila api-v2 no Redis. Serve tanto para triggers HTTP externos quanto para nós que executam sub-flows em modo triggerOnly.
Em resumo. A função recebe o pacote (ApiV2QueueModel). Garante que ele tem uma etiqueta única. O jobId vem do chamador ou é gerado por UUID. Envia para a fila com regras claras. Cada job é independente. O jobId também é duplicado dentro do jobData. Não é redundância. Permite que o processor leia o mesmo id em job.data sem precisar do job.id do Bull.

🎯 jobId como chave de dedup
O Bull rejeita add() com jobId já existente (se ainda ativo). Chamadores que passam jobId explícito (por exemplo, MCP passando processId) ganham dedup natural. Duas chamadas com o mesmo id não duplicam.
⚠️ attempts: 1 (sem retry)
Se o worker falhar no meio ou o job der throw, não reprocessa. Vai direto para failed. É bom para evitar side effects duplicados (email, webhook). É ruim se o erro foi transiente (network blip com provider de LLM).

Trade-off consciente. Agentes têm side effects irreversíveis (cobrança, webhook, email).
🔧 removeOn*: housekeeping
removeOnComplete: { age: 300 }. O job some do Redis 5 minutos após completar. Economia de memória.

removeOnFail: { age: 24*3600, count: 20 }. Falhas ficam 24h ou as 20 mais recentes, o que expirar primeiro. Ajuda no debug sem inflar o Redis.
B @Process({ concurrency })
apiV2Job.processor.ts:16-25, 44-47
parseConcurrency(process.env.AGENT_CONCURRENCY) → number // default 5
Propósito. Define quantos jobs simultâneos cada instância do worker processa. É lido no boot da app, no decorator estático. Mudar a env exige restart.
Em resumo. Este parâmetro decide quantos agentes podem executar simultaneamente dentro do mesmo processo Node. Lê a env AGENT_CONCURRENCY quando a app sobe. Tenta parsear como inteiro. Se falhar (env vazia, string qualquer, número zero ou negativo), cai no default 5. O decorator é avaliado uma vez na inicialização. Trocar a env em runtime não faz nada. É necessário reiniciar. Com 3 instâncias do backend, cada uma processa até 5 jobs simultâneos. O teto real é concorrência multiplicado por instâncias.

📎 Por que env var e não config service?
Concorrência é infra (não business). Precisa ser lida antes do NestJS montar o DI. Env var pura, avaliada no boot, é o padrão do Bull. Trocar exige restart do processo.
🎯 Escala real: concorrência × instâncias
Se 3 instâncias do backend estão ativas, cada uma processa até 5 jobs simultâneos. Total de 15. Não há coordenação entre elas. O Bull distribui via Redis (BRPOPLPUSH).
⚠️ Env inválida cai no default silenciosamente
AGENT_CONCURRENCY=abc resulta em parseInt('abc', 10) = NaN. Number.isFinite(NaN) = false. Aplica default 5.

Nenhum log, nenhum warning. Um erro de digitação (querer 20 e digitar errado) resulta em execução com 5 sem aviso.

C execute(). Fluxo happy path
apiV2Job.processor.ts:48-127
async execute(job: Job<ApiV2QueueModel>) → result
Propósito. Método principal. Recebe o job Bull. Extrai payload. Orquestra a chamada ao FluxService.apiV2. Atualiza tabelas de status. Dispara callback HTTP no fim.
Em resumo. O método desempacota o job (jobId, params, webhookUrl, flag de formato). Resolve dois identificadores importantes. processId vem de parentProcessId se veio de sub-flow. Caso contrário, do próprio jobId. executionId vem só quando o chamador quer rastreamento na tabela flow_execution_status. Registra o timestamp de duração. Faz duas marcações de início se os IDs existem. MCP e flow_execution_status são independentes. Chama fluxService.apiV2. Essa é a chamada pesada que executa a Fase 1-4 inteira do agente. Calcula duração no fim. Decide se foi erro pela presença de result.nodeError. Propaga status para as duas tabelas. Só então dispara o webhook. O retorno vai para job.returnvalue do Bull.

🎯 processId, jobId e executionId são distintos
Três IDs distintos convivem.
jobId. Id do Bull. Chave de dedup.
processId. Id lógico da execução. Usado pelo MCP e pelo run log. Vem de parentProcessId em sub-flows. Caso contrário, é igual a jobId.
executionId. Id na tabela flow_execution_status. Só existe em execuções vindas de trigger com callback opt-in.
⚠️ Marcações têm early exit por gate
markRunning só executa se params.mcpTracking.
markInProgress só executa se executionId.

A maioria das execuções (trigger interno, fire-and-forget dos nós) não escreve em nenhuma das tabelas. Passa direto para o apiV2.
🔧 Spread ...params ignora executionId silenciosamente
this.fluxService.apiV2({ ...params, ... }) encaminha executionId no argumento. A destructuring do apiV2 (flux.service.ts:2280-2318) não menciona executionId. Fica no objeto, mas nunca é lido. É dead data.
📎 result.nodeError decide erro versus sucesso
O apiV2 não lança em erro de nó. Retorna result.nodeError: string. Se preenchido, ambas as tabelas viram status error. Se null ou undefined, viram completed.

Só exceção JavaScript não capturada (queda de rede, bug) cai no catch (fn E).
D buildApiV2CallbackPayload(args)
apiV2Job.processor.ts:176-198
private buildApiV2CallbackPayload(args): { executionId, success, flowId, sessionId, totalTokensUsed, totalCost, timestamp, outputs, error }
Propósito. Monta o payload novo (formato v2) do callback HTTP. Só usado quando apiV2CallbackFormat === true. Caso contrário, o processor envia o payload legacy { jobId, result } direto.
Em resumo. É o envelope de saída para o cliente que pediu callback moderno. O envelope legacy é cru. Devolve o result inteiro, com tudo que o apiV2 retornou. O novo é enxuto e estável. Pega só o essencial (executionId, flowId, sessionId, tokens totais, custo total, timestamp ISO, outputs, erro se houver) e monta um objeto plano. A flag success é derivada de !result.nodeError. Vale true se não há erro. Em caso de erro, outputs vai como [] para não vazar saída parcial confusa. Defaults defensivos em todos os campos numéricos (?? 0). Se o apiV2 esqueceu de contabilizar, o payload não quebra.

🎯 outputs = [] quando há erro
Se result.nodeError está presente, outputs vira []. É uma decisão explícita para não vazar saída parcial ao caller. O legacy envia result cru, então pode ter saída parcial e erro juntos.

E catch block. Replica de erro
apiV2Job.processor.ts:128-173
catch (error) { markFinished('error') · markError · callback(success:false) · throw error; }
Propósito. Trata exceções JavaScript não capturadas pelo apiV2 (queda de rede, throw de terceiros, bug de código). Marca ambas as tabelas como erro. Dispara callback com success: false. Relança para o Bull registrar em failed.
Em resumo. Este bloco espelha o happy path com valores de erro. Refaz os mesmos 4 passos (durationMs, MCP markFinished, FES markError, callback), mas com valores hardcoded para erro. Status error, tokens 0, cost 0. A mensagem do erro é extraída com error instanceof Error ? error.message : String(error). Cobre tanto Error nativo quanto qualquer valor lançável (string, número, objeto). No fim, throw error devolve a exceção ao Bull. O Bull move o job para a lista failed no Redis e dispara o hook @OnQueueFailed. Sem o re-throw, o Bull consideraria sucesso e nunca chamaria o handler de falha.

📎 Payload de erro do formato novo
Diferente do happy path (que tem outputs, totalTokensUsed, entre outros), o payload de erro é menor. Só { executionId, success:false, error, flowId, timestamp }. Cliente que espera outputs precisa checar success antes.
⚠️ E se o callback de erro também falhar?
lastValueFrom(httpService.post(...)) pode lançar (timeout, DNS, 5xx). Essa exceção propaga acima do catch. Não é capturada. O job vai para failed com a mensagem do erro do callback, não do erro original.

Sequência ruim. MCP e FES já foram marcados com o erro original, mas o Bull registra o erro do callback. É uma divergência sutil no debug.
⚠️ tokens: 0 e cost: 0 hardcoded
Se o apiV2 falhou no meio (após já ter feito chamadas caras a provedores), o erro sobe com tokens: 0, cost: 0. A cobrança real fica invisível nesse rastro. Requer cross-reference com logs de provider.
🔧 instanceof Error é seguro
error instanceof Error ? error.message : String(error). TypeScript aceita qualquer valor em catch. Cobre throw 'string', throw 42 e throw { foo: 1 } sem crash.
F @OnQueueFailed()
apiV2Job.processor.ts:200-212
onFailed(job: Job, err: Error) → void // Winston.error com metadata estruturada
Propósito. Hook do Bull chamado quando o job vai para failed (por causa do throw em E ou timeout). Registra no Winston com metadata rica para observabilidade. Fora do fluxo síncrono do execute().
Em resumo. É a caixa preta do processor. Executa automaticamente sempre que um job termina em failed. Isso ocorre quando execute() lança uma exceção no catch (E5) ou o job estoura o timeout de 10 minutos. Faz apenas uma coisa. Chama this.logger.error (Winston) com metadata estruturada. Inclui error_type: 'Internal Server Error', status: 500, o user e flow do payload (com ?. defensivo, pois pode faltar) e o stack do erro. É o que aparece no CloudWatch e nos logs de produção quando um agente falha. Não escreve nas tabelas MCP e FES. Isso já foi feito no catch. Aqui é apenas observabilidade.
F1 Winston.error com metadata rica
@OnQueueFailed() onFailed(job: Job, err: Error) { this.logger.error({ message: `ApiV2QueueProcessor - ERROR While Processing job ${job.data.jobId}`, metadata: { error_type: 'Internal Server Error', status: 500, user: job.data?.params?.user, flow: job.data?.params?.flow, stack: err?.stack, }, }); }
apiV2Job.processor.ts:200-212
🎯 Complementar, não substituto
F1 não escreve em MCP e FES. Isso é feito no catch (E). F1 existe apenas para o Winston (CloudWatch, Datadog, etc.). É o log estruturado da esteira de observabilidade.
📎 Dispara também em timeout do Bull
Se o job estoura timeout: 600000, o Bull mata o worker e chama @OnQueueFailed. Nesse caso, o catch de E não executa. O job foi encerrado de fora. F1 registra, mas MCP e FES podem ficar em in_progress para sempre. É um órfão.
⚠️ objeto user completo no log
job.data?.params?.user. Passa o objeto User inteiro para dentro do log. Inclui email, id, roles e possivelmente PII. Viola a regra de logging (não vazar nome ou email). Deve ser observado na migração para o worker. É uma boa oportunidade de limpeza.
🔧 error_type e status 500 hardcoded
Convenção interna. Todo job falho é classificado como 'Internal Server Error' com status 500, independentemente da causa real (validation, network, provider). Facilita dashboards, mas perde granularidade.
Resumo. O que sai de 1.1:
job.returnvalue. O objeto result do fluxService.apiV2. Persistido pelo Bull no Redis por 5 minutos após completar.
Tabela mcp_run_status. Linha atualizada com status, tokens, cost, durationMs e errorMessage. Só se params.mcpTracking estava presente.
Tabela flow_execution_status. Linha atualizada com status, output, tokensUsed, totalCost, durationMs e finishedAt. Só se executionId estava presente.
Webhook HTTP POST disparado (10s timeout) com payload legacy { jobId, result } ou novo formato v2. Só se webhookUrl presente.
Em falha, a exceção é relançada. O Bull marca failed. Winston registra via @OnQueueFailed com stack, user e flow.
Observações para migração:
A fila continua existindo hoje porque o apiV2 ainda é síncrono e executa no request do backend. Para callers que querem fire-and-forget (MCP tool, nós triggerOnly), a fila é o único desacoplamento HTTP disponível. Sem worker Temporal, não há alternativa.
Se o worker Temporal absorver a execução, a fila pode ser deletada. O próprio Temporal já é uma fila durável com retry, timeout e observabilidade builtin. O chamador passa a usar client.workflow.start(...) em vez de enqueueApiV2Job.
Pontos que sobrevivem sem fila. O dispatch de callback HTTP vira uma activity no workflow. As marcações em mcp_run_status e flow_execution_status viram activities de status. Podem ser consolidadas numa só tabela, pois hoje há duplicação. OnQueueFailed vira o handler de erro do workflow.
Attempts: 1 não muda. Agentes têm side effects irreversíveis. O Temporal precisa ser configurado com maximumAttempts: 1 na retry policy da activity principal.
Concorrência vira config do worker Temporal (concurrency de taskQueue). Não mais env var lida no boot do Nest.
Riscos de deixar para depois. A duplicação MCP e FES, o dead data no spread e o log de PII são bugs latentes. Vale limpar em conjunto ao reescrever o handler para o worker.

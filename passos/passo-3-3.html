Step 3.3 — applySubstitutionToObject(node, schema)

Block in flux.service.ts:3280-3284. Engine at node-reference-substitution.service.ts:145-167. Walks recursively through node and replaces every {{...}} with the real value from nodeSubstitutionSchema (built in 2.3, mutated along the loop in 3.6).
In summary — what this step does
  • Fills every {{...}} hole. Takes the raw node (with placeholders like "Write about {{topic}}") and returns processedNode with everything resolved to concrete text. This is the point where cross-node references become real values.
  • Recursive walker with no whitelist. applySubstitutionToObject walks the entire node tree. Strings pass through the regex. Arrays turn into recursive .map. Objects get a new container. Never mutates the original. Returns a parallel cloned tree. That preserves the raw node for retries.
  • Placeholder engine navigates dotted paths. replacePlaceholders runs /{{(.*?)}}/g, splits on . and walks the schema segment by segment. If any node on the path resolves to undefined, it leaves the placeholder literal in the output. Silent fallback, intentional, for optional templates.
  • Every node becomes 3 keys in the schema. stableKey (UUID), refKey (legacy id with dots converted to underscore) and labelKey (human label). All point to the same entry. The user can write {{writer}}, {{6d09d1...}} or the refKey and they all resolve the same. Collisions between labels of different nodes are first-write-wins (footgun).
  • Handlers ignore processedNode in parts. Temporal, voice and mcp use processedNode. Pull/push, condition, nodesBox, arrayNode and fluxBox use raw node and do their own internal substitution. Source of the 57 sync sites scattered across the code.
  • Output. Resolved processedNode (parallel tree), node untouched. 100% synchronous, 100% in-memory. Fat memory: schema × N nodes × strings can go into live megabytes.
Context. This is the point where cross-node references become concrete text. Before: node.data.prompt = "Write about {{topic}}". A applySubstitutionToObject(obj, schema)
node-reference-substitution.service.ts:145-167
applySubstitutionToObject(obj: any, schema: any): any
Purpose. Generic recursive walker. Builds a new tree while walking obj. No field whitelist. Applies to everything that's a string. No pre-cloning, no deep-copy. The return value is the new object assembled level by level.
In summary. It's the draft reviewer. Takes the node's text full of {{...}} ("Write about {{topic}} for {{audience}}") and returns a clean version with all the blanks filled. Instead of walking the text in the traditional way, it recurses through the whole node tree. If it hits a string, calls the substitution engine (fn B). If it's an array, walks each item. If it's an object, creates a new object and reviews field by field. The key point is that it never mutates the original. The node passed as argument stays intact (with its {{...}}). The return value is a parallel cloned tree. That guarantees that, if the handler fails midway, the original node is still available for retries. No whitelist. Applies to every string field, including internal fields like _rawProviderResponse and _attempts. No depth limit. Pathologically it can stack overflow. Real nodes stay in 3-4 levels. This is the heart of the substitution engine. The 57 sync sites the memory mentions ([[project_substitution_engine]]) are variations of this walker. One of the central offenders the worker migration has to rewrite or eliminate via prefetch.
applySubstitutionToObject(obj: any, schema: any): any { if (!obj || !schema) return obj; if (typeof obj === 'string') { return this.replacePlaceholders(obj, schema); } if (Array.isArray(obj)) { return obj.map(item => this.applySubstitutionToObject(item, schema)); } if (typeof obj === 'object') { const result = {}; for (const [key, value] of Object.entries(obj)) { result[key] = this.applySubstitutionToObject(value, schema); } return result; } return obj; // number, boolean, null → unchanged }
↓
🪜 Dispatch by type
1 obj === null/undefined OR schema falsy returns obj (early)
2 typeof obj === 'string' → replacePlaceholders (fn B)
3 Array.isArray(obj) .map(item => recursive)
4 typeof obj === 'object' new {} and Object.entries loop
5 primitive type (number/boolean) returns obj unchanged
🎯 Structural cloning, not in-place
Every object or array returns a new container (const result = {}). The original node is never mutated. The return value is a parallel tree. That guarantees that old previewResponses (read at 3.2) don't leak into processedNode after the output is rewritten.
⚠️ No whitelist, no depth limit
The function applies to every field. If node.data has internal fields like _rawProviderResponse, _attempts, _modelId, they are copied too (and strings inside also pass through the regex).

No maxDepth. A pathologically deep node.data can stack overflow. Flow nodes stay at 3-4 levels.
📎 typeof null === 'object'
The !obj guard (line 146) already catches null. Without it, the typeof obj === 'object' branch would try Object.entries(null) and blow up.
🔧 Call in flux.service
const processedNode = this.nodeReferenceSubstitutionService.applySubstitutionToObject( node, nodeSubstitutionSchema, );
node is the live reference; nodeSubstitutionSchema is the schema mutated by the loop.
B replacePlaceholders(str, schema)
node-reference-substitution.service.ts:5-23
replacePlaceholders(originalString: string, replacementSchema: any): string
Purpose. Core of the engine. Finds {{anything}}, splits on . and walks the schema segment by segment. If at any point the lookup fails, returns the original match (unresolved).
In summary. It's the dictionary called for every word between double braces. Receives a string like "Write about {{textGen1.text}} for client {{currentClient}}". Runs the regex /{{(.*?)}}/g to find every {{...}}. For each one: takes the content (textGen1.text), splits on dot (['textGen1', 'text']) and walks the schema segment by segment. schema['textGen1'], then .text. If any segment returns undefined, aborts and returns the original placeholder literal. {{textGen1.text}} stays in the output without substitution. This is intentional behavior. Allows template prompts with optional placeholders that only resolve if the data exists. Subtle point. If the final value is an object (not string), String.replace coerces to "[object Object]". Almost never what the user wants. That's why step 2.3 (generateSchemaFromNodes) flattens objects to .text/.content/.result before indexing. Another restriction. Substitution is left-to-right, single pass. If a resolved placeholder contains other {{...}}, they stay literal. Not recursive. Simple, predictable. Requires the user to know this restriction.
replacePlaceholders(originalString: string, replacementSchema: any): string { if (!originalString || typeof originalString !== 'string') { return originalString; } const result = originalString.replace(/{{(.*?)}}/g, (match, p1) => { const keys = p1?.split('.'); let value = replacementSchema; for (const key of keys) { value = value[key]; if (value === undefined) { return match; // didn't resolve → keep {{...}} } } return value; }); return result; }
↓
B1 Non-greedy regex: /{{(.*?)}}/g
.*? takes the smallest possible match. For "{{a}} and {{b}}" finds 2 groups, not 1 giant one.
Accepts anything between {{ and }}, including spaces, symbols and dotted paths.
↓
B2 Path navigation a.b.c
keys = p1.split('.'). Loop: value = value[key]. If any segment returns undefined, aborts and returns the original match.

Supports N segments. Common cases:
• {{textGen1}}: 1 segment → the entire node object
• {{textGen1.text}}: 2 segments → only the text field
• {{age.text}}: uses labelKey (fn C)
⚠️ Implicit string coercion
When the final value is an object or array, String.replace calls String(value). Turns into "[object Object]" or "1,2,3". Almost never what the user wants.

That's why generateSchemaFromNodes (step 2.3) already flattens objects to .text/.content/.result before indexing. Avoids this scenario.
💡 Silent fallback
Unresolved placeholder doesn't throw. It just stays in the output as {{wrongName}}. A downstream handler (e.g. LLM) might see it and complain, but the loop keeps going.

It's intentional to allow template prompts with optional placeholders.
🔧 Match order
String.replace with /g regex applies left-to-right, not recursively. A placeholder whose resolved value contains {{...}} is not reprocessed in this pass.
📎 Double typeof guard
Both applySubstitutionToObject and replacePlaceholders check typeof === 'string'. Redundant but defensive. The second check protects replacePlaceholders if called directly (outside the walker).
C Schema: 3 keys per node (contract)
node-reference-substitution.service.ts:82-143
generateSchemaFromNodes(nodes) — indexes each node under stableKey (UUID), refKey (dots→_), labelKey (label without spaces)
Purpose. Context of the schema 3.3 consumes. Every flow node becomes 3 entries in the nodeSubstitutionSchema object. Same entry reference, different keys. That lets the user write {{6d09d1...uuid}}, {{textBox_1714_0_8148}} or {{writer}} and they all resolve to the same place.
In summary. Think of the 3 keys as 3 names the same person answers to. The SSN (stableKey: collision-free UUID), the driver's license nickname (refKey: legacy id with dots swapped for underscore) and the social name (labelKey: whatever the user typed as the node "label", e.g. "My Writer" → "mywriter"). All 3 keys point to the same entry. If the node output updates, all update simultaneously because they're the same reference. This gives the user flexibility. In the editor they can drag a reference (uses the UUID under the hood) or type {{writer}} by hand. Both work. It also lets legacy ids with dots (inherited from old versions) keep resolving. The {{path.field}} parser would split on the wrong dot. Watch out for collisions. If two nodes have the same label, the second one does not overwrite the first. The check labelKey !== stableKey && labelKey !== refKey only handles that within the same node. The labelKey scope across different nodes is first-write-wins. Footgun when someone duplicates a label unnoticed. The basedOnType whitelist (lines 25-80) defines which fields of each type appear in the entry. It's not the walker that filters. It's the indexing that already delivers only the essentials (prompt, text, url, etc.).

⚠️ basedOnType whitelist is INDEXING
basedOnType (lines 25-80) defines which node.data fields are indexed per type. Only listed fields appear in the entry. E.g. textBox only exposes text. apiCaller exposes url, jsonRequestBody, etc.

Careful. The whitelist belongs to the schema generation, not the walker. The walker (fn A) applies to everything. The whitelist only filters what becomes available to be referenced.
🎯 Lookup precedence
None. All 3 keys point to the same entry. If the user writes {{writer}} or {{6d09d1...}}, the result is identical. Key choice is the user's, in the editor.

Collisions (label = another nodeId) are not handled. The if (labelKey && labelKey !== stableKey && labelKey !== refKey) only prevents overwriting itself, not collisions between different nodes.
🔧 Objects flattened during indexing
If node.data.prompt is an object (not string), generateSchemaFromNodes extracts .text → .content → .result in that order. Fallback: JSON.stringify(value). This does not happen in the walker. Only during schema build.
D processedNode (loop variable)
flux.service.ts:3280-3284
const processedNode = this.nodeReferenceSubstitutionService.applySubstitutionToObject(node, nodeSubstitutionSchema);
Purpose. Final consumer of the engine. It's what node handlers (inline or Temporal) receive as already-resolved input. Some handlers use processedNode, others use node. The distinction is not uniform and is one of the footguns of the current code.
In summary. Picture node as the handwritten original document (with annotations, pending references, the draft) and processedNode as the typed-up version, with all blanks filled in and ready to read. The loop hands both to handlers, and then the confusion starts. processNodeViaTemporal, voiceNode, thirdPartyIntegrationNode and mcpNode use processedNode (the clean version). Perfect. But pullDataNode, pushDataNode, conditionNode, nodesBox, arrayNode, fluxBox and libraryNode use raw node. They do their own substitution internally. The code doesn't document who uses what. It's ad-hoc convention you only learn by reading each handler. That's why there are 57 sync sites of substitution. Every handler that ignores processedNode reimplements part of the engine with its own rules. Keeping all those variations in sync is the nightmare of any refactor. Another footgun. Mutating processedNode.data does not affect the myUpdatedNodes array (it's a parallel cloned tree). Mutating node.data does (it's a live ref). Anyone trying to "fix" the output by writing to processedNode will lose the change silently.

🎯 Why processedNode is "pure" but node is "live"
node is the reference into the myUpdatedNodes array. If a handler mutates node.data.text, the next find at 3.2 sees that value. processedNode is a parallel tree. Mutating it does not reflect back into the array.

This is not documented in the code. Common source of bugs when someone tries to "fix" the output by writing into processedNode.data.
🔧 mutatedSchema is the same object
let nodeSubstitutionSchema and let mutatedSchema in apiV2() point to the same schema. Duplicate names from an incomplete refactor. Both are passed to handlers. Reassigning one doesn't affect the other (footgun).
Summary — what leaves 3.3:
• processedNode: new tree with every {{...}} resolved in string fields.
• node remains intact (same ref into the myUpdatedNodes array).
• Unresolved placeholders stay literal in the output ({{wrongName}}).
• 100% synchronous, 100% in-memory, no I/O.
• Time O(size(node.data) × avg-placeholders-per-string).
Migration notes:
• This is the offender for the worker migration (memory [[project_substitution_engine]]). It's 57 sync sites, some explicit (3.3), others hidden in each legacy handler. The worker has no substitution engine. It receives already-resolved input.
• The basedOnType whitelist is hard-coded at node-reference-substitution.service.ts:25-80. Every new type that needs referenceable fields requires editing that list. Prefetch mode and the worker also have parallel lists. Three places to keep in sync.
• The lack of recursive resolution (placeholders inside resolved outputs) is intentional but fragile. Migration can choose: (a) support via a second pass; (b) explicitly forbid; (c) keep current behavior documented.
• processedNode is temporary. It's not persisted anywhere. If a node fails after substitution but before writing, the resolved input is lost. In the Temporal path, the INSERT into node_executions (step T2) writes precisely that resolved input. Superior pattern.
• 3 keys × N nodes × strings inside each. Schema memory grows O(nodes × avg-fields × avg-string-size). In large agents with long LLM responses, the schema holds megabytes of live JSON.
• It is essential and critical. The whole data-propagation model between nodes depends on it. Worker migration needs to design an alternative model (ref prefetch is already an attempt) before touching this code.

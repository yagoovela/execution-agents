Step 3.8 — Per-node error handling (fail-fast)

Block at flux.service.ts:4565-4614 (post-handler detection) and 4635-4723 (catch inside the node try). If the node failed, sets stoppedByNodeFailure=true and does break. The loop stops immediately. Writes node_executions with status FAILED and emits a log via Winston.
In short — what this step does
  • Fail-fast semantics. If any node fails, the whole execution stops at the point of the error. No automatic per-node retry. No "continue on error". No partial success. It is binary: success or error.
  • Two detection paths. The handler handled the error internally and wrote node.data.errorMessage, returning normally. It is detected by the failedNode check in myUpdatedNodes.find(...). Or the handler threw an exception. The catch (nodeRunError) catches it. Both converge on the same destination.
  • Cancellation takes priority over error. Inside the catch, the first check is cancelWatch?.wasAborted(). If it was cancel, it redirects to finishCancelledNode. The UI shows "cancelled" (gray), not "error" (red).
  • Uniform cleanup. extractWorkflowError extracts the exception payload (userMessage, devMessage, category, field, worker's execId when it came from Temporal). clearFailedNodeOutput wipes old output. Rewrites node.data with the error fields. Calls runLogCollector?.endNode with status error. Emits a log via Winston with stack. Only for legacy, calls recordInApiNodeError for UPDATE on node_executions. Temporal already persisted inside the workflow.
  • One variable, big cascade. stoppedByNodeFailure=true does no I/O. Affects roughly 5 points of Phase 4: skip the "unprocessed nodes" warning, status 'Error while running' in flowLogsService, runLogCollector.finalize({status:'error'}), friendly string in 4.5, and return with non-null nodeError.
  • Output. stoppedByNodeFailure=true and loop terminated. Culprit's node.data with all error fields. Row in node_executions UPDATED with status FAILED (legacy). RunLogNode with status='error'. Winston log with stack and metadata.
Context. Flux has fail-fast semantics. If any node fails, the whole execution stops at the point of the error. There is no automatic per-node retry. Temporal has an internal retry policy. If it exits the workflow as an error, the backend does not try again. There is also no "continue on error". Every error is fatal for the execution. Two detection paths. The handler sets node.data.errorMessage but returns normally. It is detected in the failedNode check. Or the handler throws an exception. The catch grabs it, builds the error node.data, and does the same cleanup.

AfailedNode detection (via node.data)
flux.service.ts:4565-4614
const failedNode = myUpdatedNodes.find(n => n.id === node.id && (n.data?.errorMessage || n.data?.errorStatusCode));
Purpose. After the handler returns without throwing, the loop searches the myUpdatedNodes array to see if the current node was marked with an error. Some handlers do not throw. They set node.data.errorMessage and return normally. They let the loop decide whether to abort.
In short. It works like an inspector checking that the node left the shift clean. It is not enough for the handler to return without throwing. Many handlers handle errors internally (fetch failed, provider returned 500, invalid response). Instead of throwing an exception, they prefer to write the info in the node itself (node.data.errorMessage = "API returned 500") and return normally. The UI shows the error on the node card without breaking the execution. The loop needs to know in order to stop. The Flux standard is fail-fast. If a node has an error, the whole execution ends. This failedNode check scans myUpdatedNodes looking for the current node with errorMessage or errorStatusCode. When it finds it, it enters the cascade. Emits a log via Winston with details. Calls recordInApiNodeError only for legacy. Temporal already persisted via activity. Sets stoppedByNodeFailure=true and does break. No continue-on-error and no second attempt. The rest of the agent stays stuck in the scheduler as not executed. Phase 4.1 detects and reports a warning. No retry and no soft-fail. It is a deliberate design decision.

🎯 Two error semantics
Legacy handlers write to node.data.errorMessage and return normally (soft fail). Temporal handlers throw exceptions (hard fail; caught by fn B's catch). Both converge on the same destination: stoppedByNodeFailure=true and break.
⚠️ Fragile field cascade
errorMessage, errorDevMessage, errorCategory, errorField, and errorStatusCode. All set by handlers by convention. No type and no contract. A new handler that forgets to set errorStatusCode is still detected. One of the two is enough. If a handler sets only errorDevMessage without errorMessage, the failedNode check does not detect it. It is a silent failure.
🔧 Only calls recordInApiNodeError for legacy
Temporal nodes already persisted the error inside the workflow (via persistNodeSuccess or an error activity). Calling again here would duplicate. The !isTemporalNode && !isWorkerRoutedIntegration check is the same matrix as the dispatch in 3.5.
Bcatch (nodeRunError) — exception path
flux.service.ts:4635-4723
catch (nodeRunError) { if (cancelWatch?.wasAborted()) { finishCancelledNode(...); break; } /* build error node.data, endNode, recordInApiNodeError, throw or break */ }
Purpose. Path when the handler throws an exception (Temporal fails, HTTP throw, invalid provider). First check: cancellation? If yes, it is the 3.4-cancellation path, not an error. If not, extracts exception details via extractWorkflowError, builds the error node.data, calls endNode and recordInApiNodeError, sets the flag, and does break.
In short. It is plan B. If the handler threw instead of writing to data, this catch grabs it. First action: checks whether the reason was cancellation (cancelWatch?.wasAborted()). If so, it is not a real error. It redirects to finishCancelledNode (step 3.4-cancellation) and exits. If it was a genuine error, it enters cleanup mode. extractWorkflowError extracts the exception payload (user-friendly message, dev message, category, field, worker execId when it came from Temporal). clearFailedNodeOutput wipes the old output. Prevents the UI from showing inconsistent data. Rewrites node.data with all error fields: errorMessage, errorDevMessage, errorCategory, errorField, errorStatusCode, and executionStatus: 'FAILED'. Calls runLogCollector?.endNode. The status becomes 'error' automatically because errorMessage is present. Emits a Winston log with stack. If legacy, calls recordInApiNodeError. In the end, stoppedByNodeFailure=true and break. The finally after the catch runs cancelWatch?.stop() and resets nodeCancelContext. Does timer cleanup to prevent leaks.

🎯 Cancel takes priority over error
If the handler threw AbortError because of cancel, the path becomes cancellation, not error. The if (cancelWatch?.wasAborted()) check comes before any error processing. The client sees "cancelled" (gray), not "error" (red).
📎 extractWorkflowError
Shared utility that knows how to extract error structure from exceptions coming from Temporal. They wrap the original error in a WorkflowFailedError or similar. Also handles regular JS errors. Returns { userMessage, devMessage, category, field, execId }.
⚠️ Double write in endNode
There is a second endNode call at 4549-4562 (no-error path). If the handler fails after some write has happened, there could be two calls. The error path lives inside the catch. It never happens together with the no-error path. The dead code at 4549-4562 (duplication of 4537-4546) is a separate latent bug.
🔧 clearFailedNodeOutput
Private utility that removes old output fields from node.data. Prevents the UI from showing successful output next to the error. An example is a textGenerator that generated partial text before failing.
CrecordInApiNodeError({ ... })
flux.service.ts:4593-4610, 4704-4720
await this.recordInApiNodeError({ execId, nodeId, flowId, type, message, userMessage, errorStack?, errorCategory, errorField, userId, sessionId, ... });
Purpose. Closes the cycle of recordLegacyNodeStart opened in 3.4-D. UPDATE on node_executions setting status='FAILED', errorMessage, errorStack, and timestamps. Only called for legacy nodes. Temporal already persists the error inside the workflow.
In short. Closes the audit trail in node_executions. For each legacy node, step 3.4-D opened a row with status running. Now this function UPDATE's the same row with the final result (failure). Records user message (goes to UI), dev message (goes to Winston), category (input_validation, external_api, permission, and others), field (which input field caused it), and stack trace (only on exception path). It does not recreate. It only updates. That is why the audit trail is uniform across paths. If you query node_executions WHERE flow_id = X AND run_id = Y, you see all executed nodes. It does not matter if they went to the worker or not. All with status COMPLETED, FAILED, or CANCELLED. Called 2 times in the code. At 4593, when failedNode was detected via node.data (soft fail). At 4704, when the handler threw exception (hard fail). Both with the same base fields. The second carries an additional errorStack.

DstoppedByNodeFailure = true; break
flux.service.ts:4612-4613, 4722-4723
stoppedByNodeFailure = true; break;
Purpose. Signal to Phase 4 that the execution ended by failure. Unique flag to distinguish from other cases. Normal termination (all nodes processed). Cancel (stoppedByCancel). Loop behavior (stoppedByLoopBehavior). The break exits the while immediately, without processing anything else.
In short. It is the red flag. It does nothing on its own. It just marks a variable and breaks the loop. Phase 4 reads this flag to decide several paths. Does not emit a "unprocessed nodes" warning. It is expected. All downstream nodes of the error stay pending. flowLogsService.createLog receives logStatus = 'Error while running'. runLogCollector.finalize receives status: 'error'. The friendly message in 4.5 (nodeError) is generated from the first node with errorMessage. The return in 4.9 includes non-null nodeError. The UI uses this field to decide whether to show success or failure. It is a variable. No I/O and no RPC. It has cascading impact on roughly 5 points of Phase 4. It is pure fail-fast. The entire execution stops at the first error. It does not try to continue branches that might complete. An example: if two parallel textGenerators and one fails, the other is not interrupted. It was already running. What stays pending are downstream nodes. No retry, no partial success, and no "run with warnings". It is binary: success or error.

🎯 Three sibling flags
stoppedByCancel, stoppedByLoopBehavior, and stoppedByNodeFailure. Each is set for a different reason. Phase 4 checks combinations to decide the final status.
⚠️ No partial success
If an agent has 10 parallel outputs and 1 fails in the middle of the execution, the other 9 are left without value. Ideally it would be "9 of 10 outputs generated, 1 failed". The current model is binary. Potential feature request.

Notes for migration.
• Fail-fast semantics is architectural. Changing it requires rethinking UX, tables, and return contracts. Can stay as-is during the platform migration.
• The convention of node.data.errorMessage, errorDevMessage, and other fields is not typed. The refactor can formalize a NodeError interface.
• recordInApiNodeError becomes dead code when everything migrates to the worker. Temporal writes directly.
• It is essential. Without robust error handling, the whole execution can run forever or return undefined. Must migrate early.

Passo 3.8 — Tratamento de erro por nó (fail-fast)

Bloco em flux.service.ts:4565-4614 (detecção pós-handler) e 4635-4723 (catch dentro do try do nó). Se o nó falhou, seta stoppedByNodeFailure=true e break — o loop para imediatamente. Grava node_executions com status FAILED e loga Winston.
Em resumo — o que esse passo faz
  • Semântica fail-fast: se qualquer nó falhar, o run inteiro para no ponto do erro. Sem retry automático por nó, sem "continue on error", sem partial success — é binário success/error.
  • Dois caminhos de detecção: (i) o handler tratou o erro internamente e escreveu node.data.errorMessage retornando normal — detectado pelo failedNode check no myUpdatedNodes.find(...); (ii) o handler lançou exception — o catch (nodeRunError) pega. Ambos convergem no mesmo destino.
  • Cancelamento tem prioridade sobre erro: dentro do catch, o primeiro cheque é cancelWatch?.wasAborted() — se foi cancel, redireciona pra finishCancelledNode; a UI mostra "cancelado" (cinza), não "erro" (vermelho).
  • Cleanup uniforme: extractWorkflowError extrai payload da exception (userMessage, devMessage, category, field, execId do worker se veio de Temporal), clearFailedNodeOutput limpa output antigo, reescreve node.data com os campos de erro, chama runLogCollector?.endNode com status error, loga Winston com stack, e — só pra legacy — chama recordInApiNodeError pra UPDATE em node_executions (o Temporal já persistiu dentro do workflow).
  • Uma variável, cascata gigante: stoppedByNodeFailure=true não faz I/O — mas afeta ~5 pontos da Fase 4 (skip warning de nós não processados, status 'Error while running' no flowLogsService, runLogCollector.finalize({status:'error'}), string amigável em 4.5, retorno com nodeError não-null).
  • Saída: stoppedByNodeFailure=true, loop encerrado; node.data do culpado com todos os campos de erro; row em node_executions UPDATED com status FAILED (legacy); RunLogNode com status='error'; Winston log com stack + metadata.
Contexto: Flux tem semântica fail-fast. Se qualquer nó falhar, o run inteiro para no ponto do erro. Não há retry automático por nó (Temporal tem retry policy interno, mas se sair do workflow como erro, o backend não tenta de novo). Também não tem "continue on error" — todo erro é fatal pro run. Dois caminhos de detecção: (i) handler seta node.data.errorMessage mas retorna normal → detectado no failedNode check; (ii) handler lança exception → catch pega, monta node.data de erro e faz mesmo cleanup.

ADetecção do failedNode (via node.data)
flux.service.ts:4565-4614
const failedNode = myUpdatedNodes.find(n => n.id === node.id && (n.data?.errorMessage || n.data?.errorStatusCode));
Propósito: Depois do handler retornar sem lançar, o loop procura no array myUpdatedNodes se o nó atual foi marcado com erro. Alguns handlers não lançam — eles setam node.data.errorMessage e retornam normal, deixando o loop decidir se abortar.
Em resumo: é o fiscal que confere se o nó saiu limpo do turno. Não basta o handler retornar sem lançar — muitos handlers tratam erro internamente (fetch falhou, provider retornou 500, resposta inválida) e em vez de lançar exception, eles preferem escrever a informação no próprio nó (node.data.errorMessage = "API returned 500") e retornar tranquilos. Isso permite que a UI mostre o erro no cartão do nó sem quebrar o run. Só que o loop precisa saber pra parar: o padrão Flux é fail-fast — se um nó tem erro, run inteiro morre. Então esse failedNode check varre myUpdatedNodes procurando o nó atual com errorMessage ou errorStatusCode. Se acha, entra na cascata: loga Winston com detalhes, chama recordInApiNodeError (só pra legacy — Temporal já persistiu via activity), seta stoppedByNodeFailure=true e break. Sem continue-on-error, sem tentativa 2 — o resto do agente fica preso no scheduler como "não executado" (que a Fase 4.1 detecta e reporta warning). Sem retry, sem soft-fail — é decisão de design deliberada.

🎯 Duas semânticas de erro
Handlers legacy: escrevem em node.data.errorMessage e retornam normal (soft fail). Handlers Temporal: lançam exception (hard fail — pega no catch do fn B). Ambos convergem no mesmo destino: stoppedByNodeFailure=true, break.
⚠️ Cascata frágil de campos
errorMessage, errorDevMessage, errorCategory, errorField, errorStatusCode — todos setados por handlers de forma convencional. Sem tipo, sem contrato. Um handler novo que esqueça de setar errorStatusCode ainda é detectado (só precisa de um dos dois). Mas se um handler setar só errorDevMessage sem errorMessage, o failedNode check não detecta — silent failure.
🔧 Só chama recordInApiNodeError pra legacy
Nós Temporal já persistiram o erro dentro do workflow (via persistNodeSuccess ou activity de erro). Chamar de novo aqui duplicaria. O check !isTemporalNode && !isWorkerRoutedIntegration é a mesma matriz do dispatch em 3.5.
Bcatch (nodeRunError) — exception path
flux.service.ts:4635-4723
catch (nodeRunError) { if (cancelWatch?.wasAborted()) { finishCancelledNode(...); break; } /* monta node.data de erro, endNode, recordInApiNodeError, throw ou break */ }
Propósito: Caminho quando handler lança exception (Temporal falha, HTTP throw, provider inválido). Primeiro cheque: cancelamento? Se sim, é caminho do 3.4-cancellation, não erro. Senão: extrai detalhes da exception via extractWorkflowError, monta node.data de erro, chama endNode, recordInApiNodeError, seta flag e break.
Em resumo: é o plano B — se o handler lançou em vez de escrever no data, esse catch pega. Primeira ação: dá uma olhada se o motivo foi cancelamento (cancelWatch?.wasAborted()) — se foi, esse não é erro real, redireciona pro finishCancelledNode (passo 3.4-cancellation) e sai. Se foi erro genuíno, entra em modo cleanup: extractWorkflowError pega o payload da exception (mensagem user-friendly, dev message, categoria, field, execId do worker se veio de Temporal), clearFailedNodeOutput limpa output antigo (pra UI não mostrar dado inconsistente), reescreve node.data com todos os campos de erro (errorMessage, errorDevMessage, errorCategory, errorField, errorStatusCode, executionStatus: 'FAILED'). Aí chama runLogCollector?.endNode (com status='error' automático porque errorMessage tá presente), loga Winston com stack, e se é legacy chama recordInApiNodeError. Final: stoppedByNodeFailure=true e break. O finally depois do catch limpa cancelWatch?.stop() e reseta nodeCancelContext — cleanup de timers pra não vazar.

📎 extractWorkflowError
Utilitário compartilhado que sabe extrair estrutura de erro de exceptions vindas de Temporal (que empacotam o erro original num WorkflowFailedError ou similar). Também trata erros regulares do JS. Devolve { userMessage, devMessage, category, field, execId }.

🔧 clearFailedNodeOutput
Utilitário privado que remove campos de output antigos do node.data — evita que UI mostre saída bem-sucedida ao lado do erro (ex: um textGenerator que gerou texto parcial antes de falhar).

DstoppedByNodeFailure = true; break
flux.service.ts:4612-4613, 4722-4723
stoppedByNodeFailure = true; break;
Propósito: Sinal pra a Fase 4 que o run terminou por falha. Flag única pra distinguir de: (i) término normal (todos os nós processados), (ii) cancel (stoppedByCancel), (iii) loop behavior (stoppedByLoopBehavior). O break sai do while imediatamente, não processando mais nada.
Em resumo: é o sinal vermelho. Não faz nada por si só — apenas marca uma variável e quebra o loop. Mas a Fase 4 lê essa flag pra decidir vários caminhos: (i) não loga warning de "nós não processados" (é esperado — todos os nós downstream do erro ficam pending); (ii) o flowLogsService.createLog recebe logStatus = 'Error while running'; (iii) o runLogCollector.finalize recebe status: 'error'; (iv) a mensagem amigável em 4.5 (nodeError) é gerada a partir do primeiro nó com errorMessage; (v) o retorno em 4.9 inclui nodeError não-null, que a UI usa pra decidir se mostra sucesso ou falha. É uma variável — nada de I/O, nada de RPC — mas tem impacto cascata em ~5 pontos da Fase 4. É fail-fast puro: run inteiro para no primeiro erro, sem tentar continuar branches que talvez pudessem completar (ex: se dois textGenerators paralelos e um falha, o outro não é interrompido — ele estava rodando; o que fica pending são os nós downstream). Sem retry, sem partial success, sem "run com warnings" — só binário success/error.

🎯 Três flags irmãs
stoppedByCancel, stoppedByLoopBehavior, stoppedByNodeFailure — cada uma é setada por um motivo diferente. A Fase 4 checa combinações pra decidir status final.
⚠️ Sem partial success
Se um agente tem 10 outputs paralelos e 1 falha no meio do run, os 9 restantes ficam sem valor. Ideal seria "9 de 10 outputs geraram, 1 falhou" — mas o modelo atual é binário. Feature request potencial.
Resumo — o que sai de 3.8:
• stoppedByNodeFailure=true, loop encerrado
• node.data do nó culpado com todos os campos de erro
• Row em node_executions UPDATED com status='FAILED' (só legacy)
• RunLogNode deste nó com status='error'

Observações para migração:
• Semântica fail-fast é arquitetural — mudar exige repensar UX, tabelas, contracts de retorno. Pode ficar como é na migração de plataforma.
• Convenção de node.data.errorMessage/errorDevMessage/etc. é não tipada — refactor pode formalizar em interface NodeError.
• recordInApiNodeError vira dead code quando tudo migrar pro worker (Temporal grava direto).
• É essencial — sem tratamento de erro robusto, run inteiro pode ficar "eternamente rodando" ou retornar undefined. Deve migrar cedo.

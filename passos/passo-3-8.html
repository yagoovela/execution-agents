Passo 3.8 — Tratamento de erro por nó (fail-fast)

Bloco em flux.service.ts:4565-4614 (detecção pós-handler) e 4635-4723 (catch dentro do try do nó). Se o nó falhou, seta stoppedByNodeFailure=true e faz break. O loop para imediatamente. Grava node_executions com status FAILED e emite log via Winston.
Em resumo — o que esse passo faz
  • Semântica fail-fast. Se qualquer nó falhar, a execução inteira para no ponto do erro. Sem retry automático por nó. Sem "continue on error". Sem partial success. É binário: success ou error.
  • Dois caminhos de detecção. O handler tratou o erro internamente e escreveu node.data.errorMessage, retornando normal. É detectado pelo check failedNode em myUpdatedNodes.find(...). Ou o handler lançou exception. O catch (nodeRunError) pega. Ambos convergem no mesmo destino.
  • Cancelamento tem prioridade sobre erro. Dentro do catch, o primeiro check é cancelWatch?.wasAborted(). Se foi cancel, redireciona para finishCancelledNode. A UI mostra "cancelado" (cinza), não "erro" (vermelho).
  • Cleanup uniforme. extractWorkflowError extrai o payload da exception (userMessage, devMessage, category, field, execId do worker quando veio de Temporal). clearFailedNodeOutput limpa a saída antiga. Reescreve node.data com os campos de erro. Chama runLogCollector?.endNode com status error. Emite log via Winston com stack. Só para legacy, chama recordInApiNodeError para UPDATE em node_executions. O Temporal já persistiu dentro do workflow.
  • Uma variável, cascata grande. stoppedByNodeFailure=true não faz I/O. Afeta aproximadamente 5 pontos da Fase 4: skip do warning de nós não processados, status 'Error while running' no flowLogsService, runLogCollector.finalize({status:'error'}), string amigável em 4.5 e retorno com nodeError não-null.
  • Saída. stoppedByNodeFailure=true e loop encerrado. node.data do culpado com todos os campos de erro. Linha em node_executions UPDATED com status FAILED (legacy). RunLogNode com status='error'. Log Winston com stack e metadata.
Contexto. Flux tem semântica fail-fast. Se qualquer nó falhar, a execução inteira para no ponto do erro. Não há retry automático por nó. O Temporal tem retry policy interno. Se sai do workflow como erro, o backend não tenta de novo. Também não existe "continue on error". Todo erro é fatal para a execução. Dois caminhos de detecção. O handler seta node.data.errorMessage mas retorna normal. É detectado no check failedNode. Ou o handler lança exception. O catch pega, monta node.data de erro e faz o mesmo cleanup.

ADetecção do failedNode (via node.data)
flux.service.ts:4565-4614
const failedNode = myUpdatedNodes.find(n => n.id === node.id && (n.data?.errorMessage || n.data?.errorStatusCode));
Propósito. Depois que o handler retorna sem lançar, o loop procura no array myUpdatedNodes se o nó atual foi marcado com erro. Alguns handlers não lançam. Setam node.data.errorMessage e retornam normal. Deixam o loop decidir se aborta.
Em resumo. Funciona como fiscal que confere se o nó saiu limpo do turno. Não basta o handler retornar sem lançar. Muitos handlers tratam erro internamente (fetch falhou, provider retornou 500, resposta inválida). Em vez de lançar exception, preferem escrever a informação no próprio nó (node.data.errorMessage = "API returned 500") e retornar normal. A UI mostra o erro no cartão do nó sem quebrar a execução. O loop precisa saber para parar. O padrão Flux é fail-fast. Se um nó tem erro, a execução inteira encerra. Esse check failedNode varre myUpdatedNodes procurando o nó atual com errorMessage ou errorStatusCode. Quando acha, entra na cascata. Emite log via Winston com detalhes. Chama recordInApiNodeError só para legacy. Temporal já persistiu via activity. Seta stoppedByNodeFailure=true e faz break. Sem continue-on-error e sem segunda tentativa. O resto do agente fica preso no scheduler como não executado. A Fase 4.1 detecta e reporta warning. Sem retry e sem soft-fail. É decisão de design deliberada.
const failedNode = myUpdatedNodes.find( n => n.id === node.id && (n.data?.errorMessage || n.data?.errorStatusCode) ); if (failedNode) { this.loggerService.error({ message: 'apiV2 node execution failed (fail-fast)', metadata: { /* nodeId, nodeType, flowId, execId, errorCategory... */ }, }); if (!this.isTemporalNode(failedNode.type) && !isWorkerRoutedIntegration(failedNode)) { await this.recordInApiNodeError({ /* ... */ }); } stoppedByNodeFailure = true; break; }

🎯 Duas semânticas de erro
Handlers legacy escrevem em node.data.errorMessage e retornam normal (soft fail). Handlers Temporal lançam exception (hard fail; pega no catch do fn B). Ambos convergem no mesmo destino: stoppedByNodeFailure=true e break.
⚠️ Cascata frágil de campos
errorMessage, errorDevMessage, errorCategory, errorField e errorStatusCode. Todos setados pelos handlers de forma convencional. Sem tipo e sem contrato. Um handler novo que esqueça de setar errorStatusCode ainda é detectado. Basta um dos dois. Se um handler seta só errorDevMessage sem errorMessage, o check failedNode não detecta. É silent failure.
🔧 Só chama recordInApiNodeError para legacy
Nós Temporal já persistiram o erro dentro do workflow (via persistNodeSuccess ou activity de erro). Chamar de novo aqui duplicaria. O check !isTemporalNode && !isWorkerRoutedIntegration é a mesma matriz do dispatch em 3.5.

📎 extractWorkflowError
Utilitário compartilhado que sabe extrair estrutura de erro de exceptions vindas de Temporal. Elas empacotam o erro original em um WorkflowFailedError ou similar. Também trata erros regulares do JS. Devolve { userMessage, devMessage, category, field, execId }.
⚠️ Escrita dupla em endNode
Existe uma segunda chamada endNode em 4549-4562 (path sem erro). Se o handler falhar depois de alguma escrita ter acontecido, poderia haver duas chamadas. O path de erro fica dentro do catch. Nunca acontece junto com o path sem erro. O dead code em 4549-4562 (duplicação de 4537-4546) é bug latente separado.
🔧 clearFailedNodeOutput
Utilitário privado que remove campos de saída antigos do node.data. Evita que a UI mostre saída bem-sucedida ao lado do erro. Um exemplo é o textGenerator que gerou texto parcial antes de falhar.

DstoppedByNodeFailure = true; break
flux.service.ts:4612-4613, 4722-4723
stoppedByNodeFailure = true; break;
Propósito. Sinal para a Fase 4 de que a execução terminou por falha. Flag única para distinguir de outros casos. Término normal (todos os nós processados). Cancel (stoppedByCancel). Loop behavior (stoppedByLoopBehavior). O break sai do while imediatamente, sem processar mais nada.
Em resumo. É o sinal vermelho. Não faz nada por si só. Apenas marca uma variável e quebra o loop. A Fase 4 lê essa flag para decidir vários caminhos. Não emite warning de "nós não processados". É esperado. Todos os nós downstream do erro ficam pending. O flowLogsService.createLog recebe logStatus = 'Error while running'. O runLogCollector.finalize recebe status: 'error'. A mensagem amigável em 4.5 (nodeError) é gerada a partir do primeiro nó com errorMessage. O retorno em 4.9 inclui nodeError não-null. A UI usa esse campo para decidir se mostra sucesso ou falha. É uma variável. Sem I/O e sem RPC. Tem impacto cascata em aproximadamente 5 pontos da Fase 4. É fail-fast puro. A execução inteira para no primeiro erro. Não tenta continuar branches que talvez pudessem completar. Um exemplo: se dois textGenerators paralelos e um falha, o outro não é interrompido. Ele estava rodando. O que fica pending são os nós downstream. Sem retry, sem partial success e sem "run com warnings". É binário: success ou error.

🎯 Três flags irmãs
stoppedByCancel, stoppedByLoopBehavior e stoppedByNodeFailure. Cada uma é setada por um motivo diferente. A Fase 4 checa combinações para decidir o status final.
⚠️ Sem partial success
Se um agente tem 10 outputs paralelos e 1 falha no meio da execução, os 9 restantes ficam sem valor. O ideal seria "9 de 10 outputs geraram, 1 falhou". O modelo atual é binário. Feature request potencial.
Resumo — o que sai de 3.8.
• stoppedByNodeFailure=true e loop encerrado.
• node.data do nó culpado com todos os campos de erro.
• Linha em node_executions UPDATED com status='FAILED' (só legacy).
• RunLogNode deste nó com status='error'.

Observações para migração.
• A semântica fail-fast é arquitetural. Mudar exige repensar UX, tabelas e contracts de retorno. Pode ficar como está na migração de plataforma.
• A convenção de node.data.errorMessage, errorDevMessage e demais campos não é tipada. O refactor pode formalizar em interface NodeError.
• recordInApiNodeError vira dead code quando tudo migrar para o worker. O Temporal grava direto.
• É essencial. Sem tratamento de erro robusto, a execução inteira pode ficar eternamente rodando ou retornar undefined. Deve migrar cedo.

Step 4.1a — Cancelled status publication

Block in flux.service.ts:4805-4825. After the main loop did break because of cancel, this block runs three actions. First, computes which nodes were not executed. Second, writes that result in flow_run_states as the definitive record of the cancellation. Third, emits a WebSocket event for the UI to mark all those nodes as CANCELLED.
In summary — what this step does
  • Simple gate. Only enters if stoppedByCancel === true. The flag is set in the loop when cancelWatch?.wasAborted() returned true (line 4596) or in 3 other detection points (3290, 3877, 4716).
  • Computes the footprint. The function resolveCancelledRunFootprint filters the schedState.nodeIds. Removes those that already completed or died (dead-scheduled). The non-executed remain. Each becomes { nodeId, label, type }. The stoppedAtNodeId is the last node that got to start (lastExecutedNodeId).
  • Persists to the database. The function runCancellationService.markCancelled runs UPDATE flow_run_states SET cancelledAt = now(), stoppedAtNodeId = $2, notExecutedNodeIds = $3::jsonb. On failure, retries up to 3 times with 200ms between them. Doesn't propagate error at the end (definitive fire-and-forget).
  • Emits WebSocket. The function emitCancelledRunStatuses calls notificationsGateway.sendToUser. Sends { runId, flowId, userId, flowVersionHistoryId, nodes: { [nodeId]: { status: 'CANCELLED' } } } in the room_status_updated event. The UI listens to this event and paints the nodes as cancelled.
  • Error differentiation. The row in flow_run_states doesn't hold status cancelled nor error. The discriminator is the presence of cancelledAt. Failed executions have that column null. Cancelled executions have a timestamp. The same UPDATE requires WHERE cancelledAt IS NULL. It's idempotent.

🎯 Why a flag and not a structured return
The loop has multiple exit points (loopBehavior, node error, cancel, natural termination). The flags stoppedByCancel, stoppedByLoopBehavior and stoppedByNodeFailure allow the post-loop code to decide the intent without needing an early return.
⚠️ 4 setting points, 4 places for bugs
If a new exit path is added to the loop without setting stoppedByCancel, the user's cancel turns into natural termination. There's no persistence or WebSocket. The UI is left with pending nodes forever.
🔧 Flag cascade flow
The stoppedByCancel flag takes precedence over stoppedByNodeFailure in resolveRunLogStatus. If cancel was set, the final status is cancelled even if some prior node errored.
B resolveCancelledRunFootprint()

function resolveCancelledRunFootprint(params: { nodeIds; completed; dead; lastExecutedNodeId; nodes }): CancelledRunFootprint
Purpose. Pure function, no I/O. Classifies each node of the execution into two categories. Executed (completed or dead) or not executed (the rest). Returns the footprint to be persisted and emitted. Contains the last node that started (stoppedAtNodeId) and the complete list of nodes that stayed in the queue without running.
In summary. The function receives 5 pieces of info. All scheduled nodes (schedState.nodeIds). Those that ended successfully (schedState.completed). Those marked as dead due to a failed dependency (schedState.dead). The last one that got to start (lastExecutedNodeId). The current node list with their data.label and type. The filter selects those not in completed nor in dead. What's left behind remains. Each node is mapped to { nodeId, label, type }. It's the record the UI and database will keep as "nodes not executed due to cancellation". The stoppedAtNodeId points to the last node that started. It may have completed or been aborted midway. Either way, it was the point where things stopped.

🎯 Three scheduler states
The schedState classifies each node in one of three buckets:
• completed. Ran to the end successfully.
• dead. Won't run because a prior dependency failed. Not cancelled, has no input.
• pending (implicit). The rest, including cancelled.
📎 stoppedAtNodeId semantics
It's the last node that started. It may have completed successfully and cancel happened between it and the next. Or it may have been aborted mid-execution via AbortSignal. The function doesn't distinguish the two cases.
🔧 Pure and tested function
No I/O, no side effect. Receives everything by parameter. Returns an object. Has a dedicated spec (cancelled-run-footprint.spec.ts). Suitable for reuse in the worker.
C runCancellationService.markCancelled()
run-cancellation.service.ts:99-132
async markCancelled(params: { runId; stoppedAtNodeId; notExecutedNodeIds }): Promise<void>
Purpose. Write in flow_run_states the official cancellation moment (cancelledAt = now()) and the context fields (where it stopped, what was left behind). Has retry of 3 attempts with 200ms delay. If all fail, the method returns void without propagating error.
In summary. The row in flow_run_states was created when the user clicked "Cancel". It arrives via requestCancel with INSERT ... ON CONFLICT DO NOTHING. At that moment the row only has runId, flowId, requestedByUserId and requestedAt. Now that the loop has stopped, this method updates the same row and fills in three fields. The cancelledAt is the cancel completion timestamp. The stoppedAtNodeId is the address where it stopped. The notExecutedNodeIds is the JSONB with the list of nodes left behind. The WHERE cancelledAt IS NULL guarantees idempotency. If the method runs twice for the same execution, the second time is a no-op. On error in the UPDATE (deadlock, database down), retries up to 3 times. If all fail, only logs and gives up. The execution doesn't hang because of it.

🎯 Distinguishing cancel from error
The flow_run_states table only exists for cancelled executions. If an execution ended with error without cancel, no row exists. The "errored execution" status is derived from flow_logs. The "cancelled execution" status requires a row in flow_run_states with cancelledAt filled.
⚠️ Fail-open on final retry
If the 3 attempts fail, the method returns without propagating error. The execution proceeds to the WebSocket emit (D) even without the cancellation persisted. It can create inconsistency. The browser sees cancelled nodes, the database never knew.

Only the console.error remains.

D emitCancelledRunStatuses()
flux.service.ts:2154-2189
private emitCancelledRunStatuses({ runId, flowId, userId, flowVersionHistoryId, nodeIds }): void
Purpose. Notify the UI via WebSocket or Socket.io that N nodes ended up with status CANCELLED. Without this emit, the browser doesn't know the execution stopped. Keeps showing the nodes as pending or loading indefinitely, even though the database is already updated.
In summary. The function builds a payload with all the nodes left behind. Each one marked as { status: 'CANCELLED' }. Sends it all in a single WebSocket event via NotificationsGateway.sendToUser. The gateway routes via Socket.io with the formula room_user_{userId}_flow_{flowId}. Only those in that flow's editor, logged in as that user, receive it. The event is room_status_updated. The frontend listens and updates the nodes' UI. If the emit fails because the Socket.io broker is unavailable or the gateway is not ready, there's an outer try/catch that logs with error_type: 'node_status_emit_failed'. If userId or flowId is missing, or if nodeIds comes empty, does a silent early return.

📎 Without flowVersionHistoryId, still works
The payload includes flowVersionHistoryId. The gateway uses only userId and flowId to build the room. If it's null, the emit happens anyway. It's just auxiliary data for the frontend.
⚠️ No delivery confirmation
The Socket.io emit is fire-and-forget. If the client is disconnected (closed the browser, lost network), the event is discarded. There's no retry or queueing. The user only finds out that they cancelled by querying again, via GET on the runlog or a UI reload.
🔧 Contrast with emitNodeStatus
emitNodeStatus (line 2191) sends status per node individually during execution (RUNNING, COMPLETED, FAILED, CANCELLED). emitCancelledRunStatuses is the batch version. A single emit with N nodes at once, at the end.
Summary — what comes out of 4.1a.
• Row in flow_run_states with cancelledAt, stoppedAtNodeId and notExecutedNodeIds filled.
• room_status_updated event emitted on Socket.io. All non-executed nodes marked as CANCELLED.
• The main loop already exited before. This block only documents and communicates.
• If any step fails (retry exhausted or emit crashes), the execution doesn't abort. Proceeds to the normal flow_logs creation.
Notes for migration.
• The resolveCancelledRunFootprint function is pure, no I/O, with a spec. Reusable directly in the worker.
• The runCancellationService.markCancelled function depends on Postgres and the retry. Can be called from inside the worker via injection or become an activity. The retry (3x, 200ms) is reasonable for a Temporal activity with custom retry policy.
• The emitCancelledRunStatuses function requires NotificationsGateway (backend Socket.io). In the worker that gateway doesn't exist. The activity needs to return the payload and the backend calls the emit. As an alternative, use the temporal.controller.ts:90 pattern which already does the relay when the activity ends.
• Order matters. Persist before emit. If reversed, the browser might receive cancelled while the database still doesn't know. The user does a refresh and sees pending.
• Low priority. If the worker runs, cancellation is native via Temporal signal. This path may become dead code after the complete migration.

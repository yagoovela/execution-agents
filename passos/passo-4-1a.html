Passo 4.1a — Publicação de status cancelado

Bloco em flux.service.ts:4805-4825. Depois que o loop principal fez break por causa de cancel, este bloco executa três ações. Primeiro, calcula quais nós não foram executados. Segundo, grava esse resultado em flow_run_states como registro definitivo do cancelamento. Terceiro, emite um evento WebSocket para a UI marcar todos esses nós como CANCELLED.
Em resumo — o que esse passo faz
  • Gate simples. Só entra se stoppedByCancel === true. A flag é definida no loop quando cancelWatch?.wasAborted() devolveu true (linha 4596) ou em outros 3 pontos de detecção (3290, 3877, 4716).
  • Calcula o footprint. A função resolveCancelledRunFootprint filtra os schedState.nodeIds. Remove quem já completou ou morreu (dead-scheduled). Sobram os não executados. Cada um vira { nodeId, label, type }. O stoppedAtNodeId é o último nó que chegou a começar (lastExecutedNodeId).
  • Persiste no banco. A função runCancellationService.markCancelled executa UPDATE flow_run_states SET cancelledAt = now(), stoppedAtNodeId = $2, notExecutedNodeIds = $3::jsonb. Em caso de falha, retenta até 3 vezes com 200ms entre elas. Não propaga erro ao fim (fire-and-forget definitivo).
  • Emite WebSocket. A função emitCancelledRunStatuses chama notificationsGateway.sendToUser. Envia { runId, flowId, userId, flowVersionHistoryId, nodes: { [nodeId]: { status: 'CANCELLED' } } } no evento room_status_updated. A UI escuta esse evento e pinta os nós como cancelado.
  • Diferenciação de erro. A linha em flow_run_states não guarda status cancelled nem error. O discriminador é a presença de cancelledAt. Execuções com erro têm essa coluna nula. Execuções canceladas têm timestamp. O mesmo UPDATE exige WHERE cancelledAt IS NULL. É idempotente.
Cadeia de chamadas em 4.1a
A · gateif (stoppedByCancel) → BresolveCancelledRunFootprint → CrunCancellationService.markCancelled → DemitCancelledRunStatuses
Resultado final. A linha em flow_run_states fica marcada como cancelada. Eventos WebSocket são enviados ao browser marcando os nós não executados como CANCELLED.

🎯 Por que uma flag e não um retorno estruturado
O loop tem múltiplos pontos de saída (loopBehavior, erro de nó, cancel, término natural). As flags stoppedByCancel, stoppedByLoopBehavior e stoppedByNodeFailure permitem ao código pós-loop decidir a intenção sem precisar de return antecipado.
⚠️ 4 pontos de definição, 4 lugares para bug
Se um novo caminho de saída for adicionado ao loop sem definir stoppedByCancel, o cancel do usuário vira término natural. Não há persistência nem WebSocket. A UI fica com nós pendentes para sempre.
🔧 Fluxo em cascata das flags
A flag stoppedByCancel tem precedência sobre stoppedByNodeFailure em resolveRunLogStatus. Se o cancel foi definido, o status final é cancelled mesmo que algum nó anterior tenha errado.
B resolveCancelledRunFootprint()
cancelled-run-footprint.ts:14-36
function resolveCancelledRunFootprint(params: { nodeIds; completed; dead; lastExecutedNodeId; nodes }): CancelledRunFootprint
Propósito. Função pura, sem I/O. Classifica cada nó da execução em duas categorias. Executado (completed ou dead) ou não executado (o resto). Devolve o footprint para ser persistido e emitido. Contém o último nó que começou (stoppedAtNodeId) e a lista completa de nós que ficaram na fila sem rodar.
Em resumo. A função recebe 5 informações. Todos os nós agendados (schedState.nodeIds). Os que terminaram com sucesso (schedState.completed). Os marcados como mortos por dependência falhar (schedState.dead). O último que chegou a começar (lastExecutedNodeId). A lista atual de nós com seus data.label e type. O filtro seleciona quem não está em completed nem em dead. Sobra o que ficou para trás. Cada nó é mapeado para { nodeId, label, type }. É o registro que a UI e o banco vão manter como "nós não executados por cancelamento". O stoppedAtNodeId aponta para o último nó que começou. Ele pode ter completado ou ter sido abortado no meio. De qualquer forma, foi o ponto onde a coisa parou.

🎯 Três estados no scheduler
O schedState classifica cada nó em um de três buckets:
• completed. Rodou até o fim com sucesso.
• dead. Não vai rodar porque uma dependência anterior falhou. Não é cancelado, ficou sem entrada.
• pendente (implícito). O resto, incluindo cancelados.
📎 Semântica do stoppedAtNodeId
É o último nó que começou. Pode ter completado com sucesso e o cancel ter acontecido entre ele e o próximo. Ou pode ter sido abortado no meio da execução via AbortSignal. A função não distingue os dois casos.
🔧 Função pura e testada
Sem I/O, sem side effect. Recebe tudo por parâmetro. Retorna um objeto. Tem spec dedicado (cancelled-run-footprint.spec.ts). Adequada para reuso no worker.
C runCancellationService.markCancelled()
run-cancellation.service.ts:99-132
async markCancelled(params: { runId; stoppedAtNodeId; notExecutedNodeIds }): Promise<void>
Propósito. Gravar em flow_run_states o momento oficial do cancelamento (cancelledAt = now()) e os campos de contexto (onde parou, o que ficou para trás). Tem retry de 3 tentativas com 200ms de delay. Se todas falharem, o método retorna void sem propagar erro.
Em resumo. A linha em flow_run_states foi criada quando o usuário clicou em "Cancelar". Chega via requestCancel com INSERT ... ON CONFLICT DO NOTHING. Nesse momento a linha só tem runId, flowId, requestedByUserId e requestedAt. Agora que o loop parou, este método atualiza a mesma linha e preenche três campos. O cancelledAt é o timestamp de conclusão do cancel. O stoppedAtNodeId é o endereço onde parou. O notExecutedNodeIds é o JSONB com a lista de nós que ficaram para trás. O WHERE cancelledAt IS NULL garante idempotência. Se o método rodar duas vezes para a mesma execução, a segunda vez é no-op. Em caso de erro no UPDATE (deadlock, banco caído), retenta até 3 vezes. Se todas falharem, apenas registra log e desiste. A execução não trava por causa disso.

🎯 Discriminação entre cancel e erro
A tabela flow_run_states só existe para execuções canceladas. Se uma execução terminou com erro sem cancel, não existe linha. O status "execução com erro" é derivado de flow_logs. O status "execução cancelada" exige linha em flow_run_states com cancelledAt preenchido.
⚠️ Fail-open no retry final
Se as 3 tentativas falharem, o método retorna sem propagar erro. A execução segue para o emit de WebSocket (D) mesmo sem o cancelamento persistido. Pode gerar inconsistência. O browser vê nós cancelados, o banco nunca soube.

Fica só o console.error.

D emitCancelledRunStatuses()
flux.service.ts:2154-2189
private emitCancelledRunStatuses({ runId, flowId, userId, flowVersionHistoryId, nodeIds }): void
Propósito. Notificar a UI via WebSocket ou Socket.io de que N nós ficaram com status CANCELLED. Sem esse emit, o browser não sabe que a execução parou. Continua mostrando os nós como pendentes ou em loading indefinidamente, mesmo com o banco já atualizado.
Em resumo. A função monta um payload com todos os nós que ficaram para trás. Cada um marcado como { status: 'CANCELLED' }. Envia tudo num único evento WebSocket via NotificationsGateway.sendToUser. O gateway roteia via Socket.io com a fórmula room_user_{userId}_flow_{flowId}. Apenas quem está no editor daquele flow, logado como aquele usuário, recebe. O evento é room_status_updated. O frontend escuta e atualiza a UI dos nós. Se o emit falhar por broker Socket.io indisponível ou gateway não pronto, há try/catch externo que registra com error_type: 'node_status_emit_failed'. Se userId ou flowId não vier, ou se nodeIds vier vazio, faz early return silencioso.

📎 Sem flowVersionHistoryId, ainda funciona
O payload inclui flowVersionHistoryId. O gateway usa só userId e flowId para montar a sala. Se estiver null, o emit acontece mesmo assim. É apenas dado auxiliar para o frontend.
⚠️ Sem confirmação de entrega
O emit Socket.io é fire-and-forget. Se o cliente estiver desconectado (fechou o browser, perdeu rede), o evento é descartado. Não há retry nem queueing. O usuário só descobre que cancelou consultando de novo, via GET no runlog ou reload da UI.
🔧 Contraste com emitNodeStatus
O emitNodeStatus (linha 2191) envia status por nó individualmente durante a execução (RUNNING, COMPLETED, FAILED, CANCELLED). O emitCancelledRunStatuses é a versão em batch. Um único emit com N nós de uma vez, no fim.
Resumo — o que sai de 4.1a.
• Linha em flow_run_states com cancelledAt, stoppedAtNodeId e notExecutedNodeIds preenchidos.
• Evento room_status_updated emitido no Socket.io. Todos os nós não-executados marcados como CANCELLED.
• O loop principal já saiu antes. Este bloco só documenta e comunica.
• Se qualquer step falhar (retry esgotado ou emit em crash), a execução não aborta. Segue para a criação normal do flow_logs.
Observações para migração.
• A função resolveCancelledRunFootprint é pura, sem I/O, com spec. Reutilizável direto no worker.
• A função runCancellationService.markCancelled depende do Postgres e do retry. Pode ser chamada de dentro do worker via injection ou virar activity. O retry (3x, 200ms) é razoável para activity Temporal com custom retry policy.
• A função emitCancelledRunStatuses exige NotificationsGateway (Socket.io do backend). No worker esse gateway não existe. A activity precisa devolver o payload e o backend chamar o emit. Como alternativa, usar o padrão do temporal.controller.ts:90 que já faz o relay quando a activity termina.
• A ordem importa. Persist antes do emit. Se inverter, o browser pode receber cancelled enquanto o banco ainda não sabe. O usuário faz refresh e vê pendente.
• Prioridade baixa. Se o worker rodar, o cancelamento é nativo via Temporal signal. Esse caminho pode virar código morto depois da migração completa.

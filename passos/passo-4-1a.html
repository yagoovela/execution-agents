Passo 4.1a — Publicação de status cancelado

Bloco em flux.service.ts:4805-4825. Depois que o loop principal breakou por causa de cancel, esse bloco (1) calcula quais nós não foram executados, (2) grava isso em flow_run_states como registro definitivo do cancelamento, e (3) emite um evento WebSocket pra UI marcar todos aqueles nós como CANCELLED.
Em resumo — o que esse passo faz
  • Gate simples: só entra se stoppedByCancel === true — flag setada no loop quando cancelWatch?.wasAborted() voltou true (linha 4596) ou em outros 3 pontos de detecção (3290, 3877, 4716).
  • Calcula footprint: resolveCancelledRunFootprint filtra os schedState.nodeIds tirando quem já completou ou morreu (dead-scheduled). Sobram os não executados — cada um mapeado pra { nodeId, label, type }. O stoppedAtNodeId é o último nó que chegou a começar (lastExecutedNodeId).
  • Persiste no banco: runCancellationService.markCancelled faz UPDATE flow_run_states SET cancelledAt = now(), stoppedAtNodeId = $2, notExecutedNodeIds = $3::jsonb. Se falhar, retenta até 3 vezes com 200ms entre elas — mas não propaga erro no final (fire-and-forget definitivo).
  • Emite WebSocket: emitCancelledRunStatuses chama notificationsGateway.sendToUser, mandando um payload { runId, flowId, userId, flowVersionHistoryId, nodes: { [nodeId]: { status: 'CANCELLED' } } } pro evento room_status_updated. A UI escuta esse evento e pinta os nós de cancelado na hora.
  • Diferenciação de erro: a row em flow_run_states não guarda status "cancelled" nem "error" — o discriminador é a presença de cancelledAt. Runs com erro têm essa coluna nula; runs cancelados têm timestamp. É o mesmo UPDATE que também exige WHERE cancelledAt IS NULL — idempotente.

Resultado final: row flow_run_states marcada como cancelada + eventos WebSocket enviados pro browser marcando nós não executados como CANCELLED.

🎯 Por que uma flag e não um retorno estruturado?
O loop tem múltiplos pontos de saída (loopBehavior, erro de nó, cancel, término natural). Usar flags stoppedByCancel, stoppedByLoopBehavior, stoppedByNodeFailure permite o código pós-loop decidir a intenção sem precisar de return antecipado.
⚠️ 4 pontos de setagem = 4 lugares pra bug
Se um novo caminho de saída for adicionado ao loop sem setar stoppedByCancel, o cancel do usuário vira "run terminou naturalmente" — nenhuma persistência, nenhum WebSocket. UI fica com nós pendentes pra sempre.
🔧 Fluxo em cascata das flags
stoppedByCancel tem precedência sobre stoppedByNodeFailure em resolveRunLogStatus: se o cancel foi setado, o status final é "cancelled" mesmo que algum nó anterior tenha errado.
B resolveCancelledRunFootprint()

function resolveCancelledRunFootprint(params: { nodeIds; completed; dead; lastExecutedNodeId; nodes }): CancelledRunFootprint
Propósito: Função pura (sem I/O). Classifica cada nó do run em uma de duas categorias — executado (completed ou dead) ou não executado (o resto) — e devolve o footprint pra ser persistido e emitido: qual nó foi o último a começar (stoppedAtNodeId) e a lista completa de nós que ficaram na fila sem rodar.
Em resumo: pense nela como uma fotografia final do cemitério. Ela recebe 5 informações: todos os nós que estavam agendados pra rodar (schedState.nodeIds), quais já terminaram com sucesso (schedState.completed), quais foram marcados como mortos por dependência anterior falhar (schedState.dead), qual foi o último que chegou a começar (lastExecutedNodeId) e a lista atual de nós com seus data.label/type. Ela filtra: quem não está em completed e não está em dead — sobra o que ficou pra trás. Cada um é mapeado pra { nodeId, label, type }. Isso vira o que a UI e o banco vão registrar como "nós não executados por cancelamento". O stoppedAtNodeId aponta pro último que começou — ele pode ter completado ou ter sido abortado no meio, mas foi o "ponto onde a coisa parou".

🎯 Três estados no scheduler
O schedState classifica cada nó em uma de três buckets:
• completed — rodou até o fim com sucesso
• dead — não vai rodar porque uma dependência anterior falhou (não é cancelado, é "morto de sede")
• pendente (implícito) — o resto, incluindo cancelados
📎 stoppedAtNodeId semântica
É o último nó que começou — pode ter completado com sucesso e o cancel foi entre ele e o próximo, ou pode ter sido abortado no meio da execução (via AbortSignal). Não distingue os dois casos.
🔧 Função pura e testada
Sem I/O, sem side effect. Recebe tudo por parâmetro, retorna um objeto. Tem spec dedicado (cancelled-run-footprint.spec.ts). Ideal pra reuso no worker.
C runCancellationService.markCancelled()
run-cancellation.service.ts:99-132
async markCancelled(params: { runId; stoppedAtNodeId; notExecutedNodeIds }): Promise<void>
Propósito: Gravar em flow_run_states o momento oficial do cancelamento (cancelledAt = now()) mais os campos de contexto (onde parou, o que ficou pra trás). Tem retry policy de 3 tentativas com 200ms de delay — se todas falharem, o método volta void sem propagar erro.
Em resumo: pense nele como o cartório que registra o divórcio. A row em flow_run_states foi criada quando o usuário clicou em "Cancelar" (via requestCancel, INSERT com ON CONFLICT DO NOTHING). Nesse momento ela só tem runId, flowId, requestedByUserId, requestedAt. Agora que o loop de fato parou, esse método atualiza a mesma row preenchendo três campos: cancelledAt (o timestamp de conclusão do cancel), stoppedAtNodeId (o "endereço" onde parou) e notExecutedNodeIds (JSONB com a lista de nós que ficaram pra trás). O WHERE cancelledAt IS NULL garante idempotência: se por algum motivo esse método rodar duas vezes pro mesmo run, a segunda vez é no-op. Se der erro no UPDATE (deadlock, banco caído), retenta até 3 vezes; se todas falharem, apenas loga e desiste. O run não trava por causa disso.

🎯 Discriminação cancel vs. erro
A tabela flow_run_states só existe pra runs cancelados. Se um run terminou com erro (mas não cancelado), não há row. O status "run com erro" é derivado de flow_logs. O status "run cancelado" precisa da row em flow_run_states com cancelledAt preenchido.
⚠️ Fail-open no retry final
Se as 3 tentativas falharem, o método retorna sem lançar. O run segue pro emit de WebSocket (D) mesmo sem o cancelamento ter sido persistido. Isso pode gerar inconsistência: browser vê nós cancelados, banco nunca soube.

Fica só o console.error.

D emitCancelledRunStatuses()
flux.service.ts:2154-2189
private emitCancelledRunStatuses({ runId, flowId, userId, flowVersionHistoryId, nodeIds }): void
Propósito: Notificar a UI (via WebSocket/Socket.io) que N nós ficaram em status CANCELLED. Sem esse emit, o browser não sabe que o run parou e continua mostrando os nós como pendentes ou "loading" pra sempre — mesmo que o banco já esteja atualizado.
Em resumo: pense nele como um anúncio no alto-falante pra UI. Ele monta um payload com todos os nós que ficaram pra trás — cada um marcado como { status: 'CANCELLED' } — e joga tudo num único evento WebSocket via NotificationsGateway.sendToUser. O gateway rotea via Socket.io usando a fórmula room_user_{userId}_flow_{flowId} — só quem está no editor daquele flow, logado como aquele user, recebe. O evento é 'room_status_updated' — o frontend escuta e atualiza a UI dos nós. Se por algum motivo o emit falhar (broker Socket.io down, gateway não pronto), há um try/catch externo que loga com error_type: 'node_status_emit_failed'. Se userId ou flowId não vier, ou se nodeIds vier vazio, faz early return silencioso.

📎 Sem flowVersionHistoryId, ainda funciona
O payload inclui flowVersionHistoryId, mas o gateway usa só userId + flowId pra montar a sala. Se estiver null, o emit acontece mesmo assim (é apenas dado auxiliar pro frontend).
⚠️ Sem confirmação de entrega
Emit Socket.io é fire-and-forget. Se o cliente estiver desconectado (fechou o browser, perdeu net), o evento é jogado fora. Não há retry, não há queueing. O usuário só descobre que cancelou olhando de novo (via GET no runlog ou reload da UI).
🔧 Contraste com emitNodeStatus
emitNodeStatus (linha 2191) manda status por nó individualmente durante o run (RUNNING, COMPLETED, FAILED, CANCELLED). emitCancelledRunStatuses é uma versão em batch — um único emit com N nós de uma vez, no fim.
Resumo — o que sai de 4.1a:
• Row em flow_run_states com cancelledAt, stoppedAtNodeId, notExecutedNodeIds preenchidos
• Evento 'room_status_updated' emitido no Socket.io — todos os nós não-executados marcados como CANCELLED
• Loop principal já saiu antes; esse bloco só documenta e comunica
• Se qualquer step falhar (retry esgotado ou emit crash), o run não aborta — segue pra criação do flow_logs normal
Observações para migração:
• resolveCancelledRunFootprint é função pura, sem I/O, com spec — reutilizável direto no worker.
• runCancellationService.markCancelled depende do Postgres + retry — pode ser chamada de dentro do worker via injection ou virar activity. O retry (3x, 200ms) é razoável pra activity Temporal com custom retry policy.
• emitCancelledRunStatuses exige NotificationsGateway (Socket.io do backend). No worker isso não existe — a activity precisa devolver o payload e o backend chamar o emit. Ou usar o padrão do temporal.controller.ts:90 que já faz o relay quando a activity termina.
• Ordem importa: persist antes de emit. Se inverter, o browser pode receber "cancelled" enquanto o banco ainda não sabe — usuário refresh e vê "pendente".
• Prioridade: baixa. Se o worker rodar, ele já tem cancelamento nativo via Temporal signal. Esse código path pode virar dead code depois da migração completa.

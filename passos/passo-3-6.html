Passo 3.6 — updateSchemaWithNodeOutput()

Bloco em node-reference-substitution.service.ts:169-216. Chamadas em flux.service.ts:3389, 3485, 3624, 3670, 4331. Quando um handler termina, a saída passa a fazer parte do schema. Os próximos nós enxergam esses valores como {{nodeLabel.text}}, {{nodeLabel.url}}, entre outros.
Em resumo — o que esse passo faz
  • É a outra ponta da substitution engine. Em 3.3 alguém lê o schema para resolver {{...}}. Aqui em 3.6 escreve-se nele. Sem esse passo, cada nó ficaria isolado. Seria impossível referenciar a saída de um nó anterior.
  • Aceita string ou objeto como saída. Quando veio string simples, grava duas vezes, em .text e .result. Isso preserva compatibilidade com placeholders antigos. Quando veio objeto, distribui em até 5 campos opcionais: text, content, result, url e audioUrl. Cada campo só é escrito quando o handler o forneceu.
  • Preserva os campos de entrada existentes. A entry do nó não é reescrita. O { ...schema[stableKey] ?? {} } mantém prompt, url e formula indexados em 2.3. Só sobrescreve os campos de saída. Assim {{writer.prompt}} continua funcionando depois que o nó termina.
  • 3 chaves apontam para a mesma entry. São stableKey (UUID), refKey (dots convertidos em underscores) e labelKey (label humano em lowercase). Atualizar uma reflete nas 3 automaticamente. Segue simetria explícita com o build inicial em 2.3.
  • 3 mecanismos convivendo. Só 5 dos aproximadamente 17 handlers legacy chamam essa função de forma explícita. Handlers Temporal atualizam via retorno do processNodeViaTemporal. Outros (conditionNode, arrayNode, nodesBox) usam a closure onMutateSchema. A inconsistência dificulta o refactor.
  • Saída. A variável nodeSubstitutionSchema é reatribuída com um novo objeto. O objeto vem de um spread do anterior. Do próximo applySubstitutionToObject em diante, placeholders desse nó já resolvem para a saída atual.

updateSchemaWithNodeOutput(schema: any, nodeId: string, nodeLabel: string, output: any): any
Propósito. Recebe a saída do handler que acabou de rodar (string ou objeto). Escreve os campos apropriados na entry do nó no schema. Retorna um novo schema (spread do anterior). Não muta in-place.
Em resumo. Se 3.3 é o revisor que lê e resolve {{...}}, este é o redator que atualiza o dicionário depois que o nó termina. Pega a saída do handler. A saída pode ser uma string simples como "Hello world" ou um objeto complexo como { text, url, content }. Abre a entry desse nó no schema e escreve os campos que couberem. Quando veio string, escreve em .text e .result. Quando veio objeto, extrai .text, .content, .result, .url e .audioUrl conforme presentes. Não substitui a entry inteira. Preserva os campos existentes (entrada, prompt). Só acrescenta ou atualiza os de saída. As 3 chaves (stableKey, refKey e labelKey) apontam para o mesmo objeto. Atualizar uma atualiza as 3 automaticamente. O próximo nó que ler {{writer.text}}, {{6d09d1...uuid.text}} ou {{textBox_1714_0_8148.text}} enxerga exatamente o mesmo valor. O { ...schema } na linha 182 clona o container antes de qualquer mutação. O schema anterior permanece imutável. Se alguém guardou referência, a mudança não vaza.

🎯 Por que preservar a entry existente
O entry = updatedSchema[stableKey] ?? {} preserva os campos de entrada (prompt, url, formula e outros). Esses campos foram indexados em 2.3 pelo generateSchemaFromNodes. Só sobrescreve os campos de saída. Assim, referências como {{writer.prompt}} continuam funcionando depois que o nó termina.
📎 shallow clone, não deep
{ ...schema } clona só o container. As entries individuais permanecem como referências compartilhadas. As 3 chaves apontam para a mesma entry. É intencional. Escrever em uma chave reflete nas 3.
🔧 typeof null === 'object'
A guarda output !== null na linha 188 evita cair no ramo de objeto quando o valor é null. Sem ela, null.text geraria TypeError.

Propósito. Decide quais campos escrever com base no formato da saída. String simples vira .text e .result, para compatibilidade com placeholders legacy. Objeto expande em vários campos condicionais.
Em resumo. Funciona como uma caixa de encomenda. O handler não sabe onde o próximo nó vai procurar o valor. Alguns usam {{writer.text}}. Outros escreveram templates antigos com {{writer.result}}. Um handler de imagem gera {{img.url}}. A função aceita a encomenda em qualquer formato e distribui nos 5 campos possíveis. Quando veio uma string pura, escreve nos dois campos .text e .result. Cobre 2 estilos de placeholder ao mesmo tempo. Quando veio um objeto, cada campo .text, .content, .result, .url e .audioUrl é opcional. Só é escrito quando está definido na saída. Um handler de LLM manda { text }. Um de imagem manda { url }. Um de áudio manda { audioUrl, text }. Nunca vaza dados de outros nós. Cada handler é responsável por retornar apenas o que produziu. A ausência de campo não zera valor existente. Mantém o que já estava.

⚠️ Sem validação de tipos
entry.text = output.text aceita qualquer valor: string, number, array ou function. Se um handler com bug passar output.text = { foo: 1 }, esse objeto vira "[object Object]" quando um placeholder tentar interpolar. A coerção acontece via String no replacePlaceholders.
🔧 Ausência não é null
O check output.text !== undefined permite sobrescrever explicitamente com null ou string vazia. Só undefined significa "não mexer".

O caller reatribui: nodeSubstitutionSchema = this.node...updateSchemaWithNodeOutput(...). Do próximo applySubstitutionToObject em diante, todo placeholder resolve com a saída atualizada.
⚠️ Colisão de labelKey
Se dois nós têm o mesmo label ("Writer"), o segundo update reescreve a mesma chave. Cada nó ainda tem as suas próprias 3 chaves. O primeiro nó continua com schema[stableKey1] e schema[refKey1] apontando para a entry original. Só schema['writer'] (label compartilhada) foi sobrescrita. O comportamento é sutil. Não é "última vence" nem "primeira vence". Depende da chave que o placeholder usa.
🎯 Simetria com generateSchemaFromNodes
Mesma lógica de replace(/\./g, '_'). Mesmo toLowerCase().replace(/\s/g, ''). Garante que o build inicial e o update pós-execução usam exatamente as mesmas chaves. Nenhuma referência é perdida entre 2.3 e 3.6.
🔧 refKey e labelKey podem colidir
Se o label é do tipo "6d09d1a3_...", pode colidir com o refKey. O último check garante que labelKey só é atribuído quando é realmente distinto. Evita duas escritas na mesma chave.

Resumo — o que sai de 3.6.
• nodeSubstitutionSchema reatribuído com a saída do nó que terminou (novo objeto, spread do anterior).
• As 3 chaves do nó (stableKey, refKey, labelKey) apontam para a mesma entry atualizada.
• 100% síncrono, in-memory.
• Só 5 handlers legacy chamam de forma explícita. Temporal usa retorno. Outros usam onMutateSchema.
Observações para migração.
• É o segundo maior ofensor da substitution engine, junto com o passo 3.3. São 57 sync sites que precisam funcionar em coerência. A migração para o worker requer que todos os call-sites usem um único mecanismo. Ou tudo via retorno de activity, ou via API centralizada.
• A entry compartilhada entre 3 chaves é otimização de memória. Em qualquer refactor com paralelismo, vira problema de race. Precisará ser convertida em 3 escritas independentes ou lock por nodeId.
• A escrita dupla em .text e .result (ramo string) existe para backward compat. Um sistema novo pode escolher só um dos campos e forçar migração de placeholders.
• A whitelist implícita de 5 campos (text, content, result, url, audioUrl) está hardcoded. Se um novo tipo de node produzir videoUrl, é preciso adicionar aqui e no generateSchemaFromNodes em paralelo.
• É essencial. Sem esse passo, o loop não funciona. Deve migrar junto com 3.3.

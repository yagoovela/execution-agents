Step 3.6 — updateSchemaWithNodeOutput()

Block at node-reference-substitution.service.ts:169-216. Calls at flux.service.ts:3389, 3485, 3624, 3670, 4331. When a handler finishes, its output becomes part of the schema. The next nodes see those values as {{nodeLabel.text}}, {{nodeLabel.url}}, and so on.
In short — what this step does
  • It is the other end of the substitution engine. In 3.3 someone reads the schema to resolve {{...}}. Here in 3.6 it is written to. Without this step, each node would be isolated. It would be impossible to reference the output of a previous node.
  • Accepts string or object as output. When a plain string arrived, it writes twice, into .text and .result. This preserves compatibility with old placeholders. When an object arrived, it distributes into up to 5 optional fields: text, content, result, url and audioUrl. Each field is only written when the handler provided it.
  • Preserves the existing input fields. The node entry is not rewritten. The { ...schema[stableKey] ?? {} } keeps prompt, url, and formula indexed in 2.3. It only overwrites the output fields. This way {{writer.prompt}} keeps working after the node finishes.
  • 3 keys point to the same entry. They are stableKey (UUID), refKey (dots converted to underscores) and labelKey (human label in lowercase). Updating one reflects across all 3 automatically. Follows an explicit symmetry with the initial build in 2.3.
  • 3 mechanisms coexisting. Only 5 of the roughly 17 legacy handlers call this function explicitly. Temporal handlers update via the return of processNodeViaTemporal. Others (conditionNode, arrayNode, nodesBox) use the onMutateSchema closure. The inconsistency makes refactoring harder.
  • Output. The nodeSubstitutionSchema variable is reassigned with a new object. The object comes from a spread of the previous one. From the next applySubstitutionToObject onwards, placeholders for this node already resolve to the current output.

updateSchemaWithNodeOutput(schema: any, nodeId: string, nodeLabel: string, output: any): any
Purpose. Receives the output of the handler that just ran (string or object). Writes the appropriate fields into the node entry in the schema. Returns a new schema (spread of the previous one). Does not mutate in-place.
In short. If 3.3 is the reviewer that reads and resolves {{...}}, this is the writer that updates the dictionary after the node finishes. It takes the handler output. The output may be a plain string like "Hello world" or a complex object like { text, url, content }. It opens that node's entry in the schema and writes whichever fields fit. When a string arrived, it writes into .text and .result. When an object arrived, it extracts .text, .content, .result, .url and .audioUrl as present. It does not replace the whole entry. It preserves the existing fields (input, prompt). It only adds or updates the output ones. The 3 keys (stableKey, refKey and labelKey) point to the same object. Updating one updates all 3 automatically. The next node that reads {{writer.text}}, {{6d09d1...uuid.text}} or {{textBox_1714_0_8148.text}} sees exactly the same value. The { ...schema } on line 182 clones the container before any mutation. The previous schema stays immutable. If someone kept a reference, the change does not leak.

A1 Guard: no nodeId, no-op

🎯 Why preserve the existing entry
The entry = updatedSchema[stableKey] ?? {} preserves the input fields (prompt, url, formula, and others). Those fields were indexed in 2.3 by generateSchemaFromNodes. Only the output fields are overwritten. This way, references like {{writer.prompt}} keep working after the node finishes.
📎 shallow clone, not deep
{ ...schema } only clones the container. Individual entries remain shared references. The 3 keys point to the same entry. It is intentional. Writing to one key reflects on all 3.
🔧 typeof null === 'object'
The output !== null guard on line 188 avoids falling into the object branch when the value is null. Without it, null.text would throw a TypeError.
BDispatch by output type
service.ts:185-204
if (typeof output === 'string') → text+result · if (object) → text/content/result/url/audioUrl (optional)
Purpose. Decides which fields to write based on the output format. A plain string becomes .text and .result, for compatibility with legacy placeholders. An object expands into several conditional fields.
In short. It works like a package box. The handler does not know where the next node will look for the value. Some use {{writer.text}}. Others wrote old templates with {{writer.result}}. An image handler produces {{img.url}}. The function accepts the package in any format and distributes it into the 5 possible fields. When a pure string arrived, it writes into both .text and .result. It covers 2 placeholder styles at once. When an object arrived, each of .text, .content, .result, .url and .audioUrl is optional. It is only written when defined in the output. An LLM handler sends { text }. An image handler sends { url }. An audio handler sends { audioUrl, text }. It never leaks data from other nodes. Each handler is responsible for returning only what it produced. Missing fields do not zero out an existing value. They keep what was already there.

CRewrite on the 3 keys
service.ts:206-213
updatedSchema[stableKey] = entry; if (refKey ≠ stableKey) updatedSchema[refKey] = entry; if (labelKey && ≠ both) updatedSchema[labelKey] = entry;
Purpose. Ensures the 3 access keys (UUID, normalized refKey, human labelKey) point to the same updated entry. Since entry is a reference, writing to one key already reflects on the others. Even so, the explicit assign guarantees idempotency even when the entry was swapped.
In short. It ensures the 3 access names (SSN, ID, nickname) point to the same updated folder. The schema was shallow-cloned on line 182. The updatedSchema has a copy of the container. It still references the old entries. By doing updatedSchema[stableKey] = entry, it forces the assignment to that new entry. The entry came from schema[stableKey] ?? {}. If it existed, it is the same. If not, it is a new object. Then it does the same for refKey and labelKey when they are different. The guard avoids unnecessary overwrite when the node has no dots in the id or a human label. It is idempotent. Running it twice with the same args changes nothing. There is symmetry with the initial build in 2.3. Same indexing logic. Same guards. The entry is a shared reference. If a placeholder resolved {{writer.text}} after this update and another node in the agent updates the same writer, the second update affects the reading of the first. Today it does not happen. In any future parallelism, this would be a bug.
updatedSchema[stableKey] = entry; const refKey = stableKey.replace(/\./g, '_'); if (refKey !== stableKey) { updatedSchema[refKey] = entry; // dots → underscores } if (labelKey && labelKey !== stableKey && labelKey !== refKey) { updatedSchema[labelKey] = entry; // alias humano } return updatedSchema;

C1 Return as a new schema
The caller reassigns: nodeSubstitutionSchema = this.node...updateSchemaWithNodeOutput(...). From the next applySubstitutionToObject onwards, every placeholder resolves with the updated output.
⚠️ labelKey collision
If two nodes have the same label ("Writer"), the second update rewrites the same key. Each node still has its own 3 keys. The first node keeps schema[stableKey1] and schema[refKey1] pointing to the original entry. Only schema['writer'] (shared label) was overwritten. The behavior is subtle. It is neither "last wins" nor "first wins". It depends on the key the placeholder uses.
🎯 Symmetry with generateSchemaFromNodes
Same replace(/\./g, '_') logic. Same toLowerCase().replace(/\s/g, ''). Ensures the initial build and the post-execution update use exactly the same keys. No reference is lost between 2.3 and 3.6.
🔧 refKey and labelKey may collide
If the label is like "6d09d1a3_...", it can collide with the refKey. The last check ensures labelKey is only assigned when it is really distinct. Avoids two writes to the same key.
DCall sites (5 handlers)

nodeSubstitutionSchema = this.nodeReferenceSubstitutionService.updateSchemaWithNodeOutput(schema, node.id, node.data?.label, newTexts[last]?.text)
Purpose. The 5 points in the loop where the function is called. Not in every handler. Only in those that produce legacy output that needs to appear in the schema. Temporal handlers (worker) update via the return of processNodeViaTemporal. They do not go through here.
In short. Only 5 of the roughly 17 legacy handlers call this function explicitly: voiceBoxNode (3389), thirdPartyIntegration/mcpNode (3485), imageGenerator (3624), audioReaderNode (3670, in a comment) and arrayNode after closing iteration (4331). The other handlers either do not produce substitutable output (conditionNode, arrayNode before closing) or do their own manipulation via the onMutateSchema callback. Temporal handlers (commandTextNode, scripting, apiCaller, and others) update the schema through the envelope return (result.nodeSubstitutionSchema). The worker receives the input already resolved. The updated schema returns as part of the result. This pattern inconsistency (some call explicit, others via callback, others via return) is one of the reasons that make the substitution engine refactor complex. To migrate, all the roughly 57 sync sites mentioned in memory must be tracked. The argument newTexts[newTexts.length - 1]?.text follows a pattern. Handlers collect multiple texts (history). Only the last one becomes the visible output for the next node.

🎯 Temporal handlers use return, not direct call
processNodeViaTemporal returns { myUpdatedNodes, myTexts, nodeSubstitutionSchema }. The loop reassigns directly (lines 3336-3338, 3361-3363 and others). It does not call updateSchemaWithNodeOutput here. The worker already did the equivalent logic inside.
Effect: 2 output propagation patterns, hard to keep in sync.
🔧 onMutateSchema for exotic cases
conditionNode, arrayNode during iteration, and nodesBox use onMutateSchema. It is a callback closure that mutates the schema in the apiV2 scope. Third pattern for propagating output. In total, 3 mechanisms do the same thing.
Summary — what comes out of 3.6.
• nodeSubstitutionSchema reassigned with the output of the node that finished (new object, spread of the previous one).
• The 3 node keys (stableKey, refKey, labelKey) point to the same updated entry.
• 100% synchronous, in-memory.
• Only 5 legacy handlers call explicitly. Temporal uses return. Others use onMutateSchema.
Notes for migration.
• It is the second biggest offender of the substitution engine, together with step 3.3. There are 57 sync sites that must work coherently. Migrating to the worker requires all call-sites to use a single mechanism. Either all via activity return, or via centralized API.
• The entry shared across 3 keys is a memory optimization. In any parallel refactor, it becomes a race condition. It will need to be converted into 3 independent writes or a per-nodeId lock.
• The double write into .text and .result (string branch) exists for backward compat. A new system can pick just one field and force placeholder migration.
• The implicit whitelist of 5 fields (text, content, result, url, audioUrl) is hardcoded. If a new node type produces videoUrl, it must be added here and in generateSchemaFromNodes in parallel.
• It is essential. Without this step, the loop does not work. Must migrate together with 3.3.

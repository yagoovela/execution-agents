Step 1.8 — Input resolution (varInputNode) + extraction/OCR

Block in flux.service.ts:2772-3134. It's the phase where the HTTP request (body.variableInputs/body.dataInput) becomes data on the canvas's varInputNodes. If the input is a file or link and isExtraction=true, calls ExtractionService with one of the three OCR providers. Finishes propagating the result via addConnectToNodes() to the connected nodes. Runs before the scheduler. The main loop already starts with varInputNode.data populated.
In short — what this step does
  • Translates the HTTP request into canvas nodes. The API receives a variableInputs[] list (or the dataInput string shortcut). It must distribute each value onto the correct varInputNode, identified by inputId. Without this, the agent would start running with empty varInputNodes.
  • dataInput shortcut. If the client sent only dataInput as a string (without variableInputs), it grabs the first varInputNode in the flow and injects the text there. It's the simple mode for agents with a single input. It's the main use case for Chatbot/simple public API.
  • Three paths per varInput. First. isExtraction=true with links/files calls OCR and concatenates text. Second. isExtraction=false with links/files only does S3 upload without OCR and stores the URL. Third. Without files, it builds minimal data with just text. Also handles inputFileUrl for types that are not varInputNode (custom file nodes).
  • OCR with provider choice. extractionService.extractTextFromLink() accepts 3 providers. mistral_ocr (default), mistral_vision, google_ocr. Each varInput picks one via typeOCR. It's per-node, not per-flow. If it fails, it returns a friendly error message in place of the text and continues. Doesn't kill the execution.
  • Mandatory S3 upload for base64. Files arrive as base64 in the request. awsService.uploadFile() generates an S3 URL before OCR. Large files become S3 traffic even if OCR fails afterwards.
  • Propagates via edges before the loop. addConnectToNodes() takes the resolved data from the varInputNode and writes it into the nodes connected via edges. Text goes as text. Files as uploadedFiles. The main loop (Phase 3) already sees the inputs in the right place.
  • Persistence. persistInputNodeData() writes the resolved data to the database. It becomes visible in the editor and in the execution history. One write per varInput. In agents with many inputs, it's non-trivial sequential I/O.
  • Silent cost. This step can be the most expensive one in Phase 1 depending on the input. A 30-page PDF with Mistral OCR blocks the execution for seconds. There's no specific telemetry to measure it.
Context — why this phase exists. The agent canvas was designed assuming varInputNode.data.text and uploadedFiles are already ready when execution starts. The HTTP request doesn't know about nodes. It only knows inputId. This step is the adapter. It takes the API payload and rewrites the canvas in memory. The Phase 3 loop finds everything already resolved. It's also where any binary file (PDF, image, audio) becomes text for the LLM to consume. It's the main entry point for unstructured data.

🎯 isExtraction tri-state

C Sub-branch: isExtraction === true → OCR
flux.service.ts:2838-2953
for (const link of links) { texts = await extractionService.extractTextFromLink({ fileSrc, fileMimetype, flowId, user, typeOCR }); ... }
Purpose. When isExtraction=true, each link and each base64 file becomes text via ExtractionService. Each base64 file uploads to S3 first. Extracted text is concatenated with \n\n between sources and saved in data.extractText.
In short. This is the workshop where a PDF becomes text for the LLM to read. Two paths. First. External links enter OCR directly by URL. Second. Base64 files upload to S3 first (OCR needs an accessible URL) and then enter OCR. Text from all sources is concatenated with a double line break between them. That's what the LLM reads as the "user's file". If any extraction fails, it puts a friendly error message in place of the text ("Unable to extract text from this file...") and continues. The execution doesn't die. The LLM just receives less context. OCR providers are chosen per node via typeOCR. Mistral OCR (default, general text). Mistral Vision (complex images). Google OCR (documents).

⚠️ Hidden cost
OCR is synchronous and expensive. An agent with 3 large PDFs spends 30 to 60s before the first node runs. Doesn't appear in node logs. Only in total execution time. Zero latency telemetry per provider.
🔧 Silent fallback on error
Try/catch on each individual link or file. The failure becomes an error string in extractText. The execution is not aborted. The LLM receives "Unable to extract text from this file..." in place of the real content. Good resilience. Bad for debugging. The client believes they passed the file. The LLM perceives the file as empty or broken.
🎯 fileUrls vs links
fileUrls stores S3 URLs of uploaded base64 files. Together with original links, forms uploadedFiles = [...links, ...fileUrls]. Loses the original difference between "user file" and "external link". The downstream node sees everything as URL.

⚠️ Misleading name. extractText is not extracted text
In path D, extractText stores a list of URLs concatenated with \n\n. It's not OCR text. A downstream node expecting "file text" receives URLs. Silent bug when the schema doesn't distinguish.
🎯 Typical use
Multimodal LLMs (Claude, GPT-4V, Gemini) that receive the image URL directly and read the binary. The intermediate OCR only gets in the way. Also. Archival pipelines. The agent just forwards the file to another system.
🔧 Cascading overwrite
D1 builds data. D4 overwrites completely if nothing came in. The chain is. isExtraction=true → data (C). Then isExtraction=false → data (D). Then no files → data (D4). Only the last match wins. Order matters.

📎 Why propagate via edges before the loop?
Design decision. Instead of the varInputNode being executed like any other node (Phase 3) and writing to the schema, it's pre-resolved here to save one pass through the scheduler. Consequence. The varInputNode doesn't appear in the Phase 3.5 dispatch. The [[project_node_field_taxonomy]] calls this "static config resolved in Phase 1".
⚠️ N sequential DB round-trips
Each varInput generates an UPDATE on flows_nodes. Agent with 10 varInputs generates 10 sequential calls. It's not Promise.all. In form-based agents (varInputs per field), this setup can dominate Phase 1 latency.
🔧 Relation with nodeSubstitutionSchema
The onMutateSchema callback in addConnectToNodes already populates the substitution schema. When step 2.3 generates the official schema, the varInputs are already there. It's a pre-seed of the schema.

↻ Re-execution in sub-flows (nodesBox / libraryNode / fluxBox)
flux.service.ts:5464-5533, 5819+
// Inside the nodesBox/libraryNode/fluxBox handler, when a sub-flow is called: the same varInputNode+OCR mechanism runs again.
Purpose. When the agent calls another agent (via nodesBox, libraryNode or fluxBox), the sub-flow has its own varInputNodes. They need to be resolved again, using callerData instead of body.variableInputs.
In short. Step 1.8 runs at the top level. When a node calls another agent (sub-flow), all of this happens again. But the input data doesn't come from the HTTP request. It comes from the parent node. The block reads callerData.textData[varNodeId], callerData.fileLinkData[varNodeId] and also legacy fields like ${varNodeId}Text and ${varNodeId}FileLink. Runs replacePlaceholders to resolve {{...}} inside the texts. It's where sub-flow inputs are sub-substituted with parent data. Then builds an equivalent variableInputs[] and sends it to the sub-flow's apiV2(). The sub-flow executes 1.8 again. Critical consequence. Each nesting level pays the OCR cost again if the file is re-extracted. There's no cache between executions. Same PDF, same execution: two OCRs when called from two sub-flows.

⚠️ Multiplicative OCR cost
No extraction cache between calls. If the same PDF passes through 3 sub-flows in the same execution, 3 OCRs. Latency scales linearly with sub-flow depth multiplied by the number of files.
🎯 replacePlaceholders on inputText
Unlike the top level, which only receives plain text from the request, the sub-flow's inputText may contain {{outputOfPreviousNode}}. replacePlaceholders resolves these placeholders before sending to apiV2. It's the bridge between the substitution engine (Phases 2.3 and 3.3) and the input phase.

Relates to step 2.3 (schema) and step 3.3 (substitution).
🔧 Legacy keys in callerData
Accepts two conventions. New. callerData.textData[nodeId]. Legacy. callerData[${nodeId}Text]. The legacy is dead-weight. Only exists to avoid breaking flows saved with the old schema.
Summary — what comes out of 1.8.
• Mutated newFlows. Each varInputNode with data = { text, uploadedFiles, isExtraction, extractText }.
• Nodes connected via edges also receive data (pre-substituted).
• nodeSubstitutionSchema pre-populated via onMutateSchema callback.
• flows_nodes.data written to the database. One UPDATE per varInput.
• I/O. Zero to N OCR calls (per links and files). Zero to N S3 uploads (per files). N UPDATEs in the database.
• Consumed in. Phase 2.3 (schema already pre-populated) and Phase 3 (downstream nodes receive resolved data).
Migration notes.
• OCR could become a Temporal activity. Today it's synchronous and blocks the backend. A dedicated workflow (extractInputActivity) frees the backend while OCR runs. Big win for agents with multiple files.
• Extraction cache. The same file (same URL, same hash) could reuse extractText. Especially relevant for sub-flows (function G). Today it's pure rework.
• N sequential UPDATEs. persistInputNodeData per varInput could become Promise.all or a batched UPDATE.
• Confusing extractText name. In isExtraction=false, it stores URLs, not extracted text. Renaming to extractedContent or splitting into two fields would help.
• Zero telemetry. Nothing is logged about OCR duration, file size or chosen provider. Diagnosing Phase 1 latency without instrumentation is infeasible.

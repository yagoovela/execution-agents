Passo 1.8 — Resolução de inputs (varInputNode) + extração/OCR

Bloco em flux.service.ts:2772-3134. É a fase onde o request HTTP (body.variableInputs/body.dataInput) vira data nos varInputNodes do canvas. Se o input for arquivo/link e isExtraction=true, chama o ExtractionService com um dos três providers OCR. Termina propagando o resultado via addConnectToNodes() pros nós conectados. Roda antes do scheduler — o loop principal já começa com varInputNode.data populado.
Em resumo — o que esse passo faz
  • Traduz o request HTTP em nós do canvas: a API recebe uma lista variableInputs[] (ou um atalho dataInput string) e precisa espalhar cada valor no varInputNode certo, identificado por inputId. Sem isso, o agente começaria a rodar com os varInputNodes vazios.
  • Atalho dataInput: se o cliente mandou só dataInput como string (sem variableInputs), pega o primeiro varInputNode do flow e injeta o texto ali. É o "modo fácil" pra agentes com um único input — o principal caso de uso em Chatbot/API pública simples.
  • Três caminhos por varInput: (a) isExtraction=true com links/files → chama OCR e concatena texto; (b) isExtraction=false com links/files → só upload S3 sem OCR (armazena URL); (c) sem arquivos → data mínima só com texto. Também trata inputFileUrl pra tipos não-varInputNode (nós de arquivo custom).
  • OCR com escolha de provider: extractionService.extractTextFromLink() aceita 3 providers: mistral_ocr (default), mistral_vision, google_ocr. Cada varInput pode escolher via typeOCR — é por nó, não por flow. Se falhar, retorna uma mensagem de erro amigável no lugar do texto e continua (não derruba o run).
  • Upload S3 obrigatório pra base64: arquivos vêm como base64 no request; awsService.uploadFile() gera uma URL S3 antes do OCR. Isso significa que arquivos grandes viram tráfego S3 mesmo se o OCR falhar depois.
  • Propaga via arestas antes do loop: addConnectToNodes() pega o data resolvido do varInputNode e escreve nos nós conectados (via edges) — texto vai como text, arquivos como uploadedFiles. O loop principal (Fase 3) já vê os inputs no lugar certo.
  • Persistência: persistInputNodeData() grava o data resolvido no banco pra ficar visível no editor e no histórico de execução. Uma escrita por varInput — em agentes com muitos inputs é I/O sequencial não-trivial.
  • Custo silencioso: esse passo pode ser o mais caro da Fase 1 dependendo do input — PDF de 30 páginas com OCR Mistral bloqueia o run por segundos. Não tem telemetria específica pra medir isso.
Contexto — por que essa fase existe: O canvas do agente foi desenhado assumindo que varInputNode.data.text / uploadedFiles já estão prontos quando a execução começa. O request HTTP não sabe nada de nós — só de inputId. Esse passo é o adaptador: pega o payload da API e reescreve o canvas em memória pra que o loop de Fase 3 encontre tudo já resolvido. É também onde qualquer arquivo binário (PDF, imagem, áudio) vira texto pro LLM consumir — logo, é o principal ponto de entrada de dados não-estruturados.

C Sub-branch: isExtraction === true → OCR
flux.service.ts:2838-2953

Propósito: Quando isExtraction=true, cada link e cada file base64 vira texto via ExtractionService. Cada file base64 sobe pra S3 primeiro. O texto extraído é concatenado com \n\n entre fontes e salvo em data.extractText.
Em resumo: essa é a oficina onde PDF vira texto pro LLM ler. Dois caminhos: (1) links externos entram direto no OCR pela URL; (2) files base64 primeiro sobem pra S3 (o OCR precisa de URL acessível), depois entram no OCR. O texto de todas as fontes é concatenado com quebra dupla entre eles — é o que o LLM vai ler como "arquivo do usuário". Se qualquer extração falhar, coloca uma mensagem de erro amigável no lugar do texto ("Unable to extract text from this file...") e continua — o run não morre, o LLM só recebe menos contexto. Providers OCR são escolhidos por nó via typeOCR: Mistral OCR (default, textos gerais), Mistral Vision (imagens complexas), Google OCR (documentos).

🔧 Fallback silencioso em erro
Try/catch em cada link/file individual — falha vira string de erro no extractText. O run não é abortado, o LLM só recebe "Unable to extract text from this file..." no lugar do conteúdo real. Bom pra resiliência, ruim pra debug: cliente acha que passou o arquivo, LLM acha que o arquivo tá vazio/quebrado.
🎯 fileUrls vs links
fileUrls guarda URLs S3 dos files base64 uploaded. Junto com links originais, forma uploadedFiles = [...links, ...fileUrls]. Perde a diferença original entre "arquivo do usuário" e "link externo" — nó downstream vê tudo como URL.

📎 Por que propagar via arestas ANTES do loop?
Design decision: em vez do varInputNode ser executado como qualquer outro nó (Fase 3) e escrever no schema, ele é pré-resolvido aqui pra economizar uma passada no scheduler. Consequência: varInputNode não aparece no dispatch da Fase 3.5 — [[project_node_field_taxonomy]] chama isso de "static config resolvido em Fase 1".
⚠️ N round-trips DB sequenciais
Cada varInput = 1 UPDATE em flows_nodes. Agente com 10 varInputs = 10 chamadas sequenciais. Não é Promise.all. Em agentes formulário-based (varInputs por campo), esse setup pode dominar a latência de Fase 1.
🔧 Relação com nodeSubstitutionSchema
O callback onMutateSchema em addConnectToNodes já popula o schema de substituição — quando passo 2.3 for gerar o schema oficial, os varInputs já estão lá. É um "pre-seed" do schema.

🎯 replacePlaceholders no inputText
Diferente do top-level (que só recebe texto puro do request), aqui o inputText do sub-flow pode conter {{outputDoNoAnterior}} — e o replacePlaceholders resolve esses placeholders antes de enviar pro apiV2. É a ponte entre a substitution engine (Fase 2.3+3.3) e a fase de input.

🔧 Chaves legadas em callerData
Aceita duas convenções: nova (callerData.textData[nodeId]) e legada (callerData[${nodeId}Text]). O legado é dead-weight — só existe pra não quebrar flows salvos com o schema antigo.
Resumo — o que sai de 1.8:
• newFlows mutado: cada varInputNode com data = { text, uploadedFiles, isExtraction, extractText }
• Nós conectados via arestas também recebem data (pré-substituído)
• nodeSubstitutionSchema pré-populado via callback onMutateSchema
• flows_nodes.data gravado no banco (1 UPDATE por varInput)
• I/O: 0-N chamadas OCR (por links+files) + 0-N uploads S3 (por files) + N UPDATEs banco

Observações para migração:
• OCR pode virar handler Temporal: hoje é síncrono e cega o backend. Um workflow dedicado (extractInputActivity) libera o backend enquanto o OCR corre. Ganho grande em agentes com múltiplos arquivos.
• Cache de extração: mesmo arquivo (mesma URL, mesmo hash) pode reusar extractText. Especialmente relevante pra sub-flows (função G) — hoje é rework puro.
• N UPDATEs sequenciais: persistInputNodeData por varInput pode virar Promise.all ou um UPDATE batched.
• Nome extractText confuso: em isExtraction=false guarda URLs, não texto extraído. Renomear pra extractedContent ou split em dois campos ajudaria.
• Telemetria zero: nada é logado sobre duração de OCR, tamanho de arquivo, provider escolhido. Impossível diagnosticar latência de Fase 1 sem instrumentar.

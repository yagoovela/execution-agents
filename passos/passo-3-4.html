Passo 3.4 — runLogCollector.startNode() + chargeContext.enterWith()

Bloco em flux.service.ts:3263-3316. Duas coisas em paralelo. (1) Abre um RunLogNode hierárquico no coletor para rastrear a execução. (2) Entra em contexto de cobrança via AsyncLocalStorage. Assim qualquer serviço chamado abaixo consegue cobrar tokens e custo no nó certo sem receber execId e nodeId por argumento.
Em resumo — o que esse passo faz
  • Coloca o crachá invisível de cobrança. chargeContext.enterWith({ execId, nodeId }) injeta esses ids na AsyncLocalStorage. Qualquer await abaixo (LLM, HTTP, DB) consegue ler o contexto sem receber por argumento. É o mecanismo central de bilhetagem por nó.
  • Abre a pasta do nó no log hierárquico. runLogCollector.startNode(...) cria um RunLogNode novo com status in_progress, ofusca segredos (apiKey, Authorization) e empurra no nodesBucket. Esse bucket é um ponteiro que muda por contexto (root, library, loop, sub-flow) e produz hierarquia sem esforço.
  • Sub-run anchors delegam o log. fluxBox e libraryNode pulam o startNode (genericRunLogNode = null). O handler deles cria um subRun aninhado próprio com toda a hierarquia interna. Evita registro duplicado na timeline.
  • Trace uniforme via recordLegacyNodeStart. Para nós que não vão pelo Temporal, insere linha com status running em node_executions. Garante que a tabela de audit trail cubra os dois paths (inline e worker). Vira dead code quanto mais tipos migram.
  • Debounce nas gravações. spaceRunLogsService.scheduleUpsert agrupa rajadas de flushRoot num único UPSERT (setTimeout keyed por processId). Sem isso, uma execução com 100 nós faria 200+ writes. No fim da execução, flushNow força o write final.
  • Saída. chargeContext ativa, genericRunLogNode vivo no coletor (ou null para anchors), 1 INSERT em node_executions para legacy, 1 UPSERT debounced em space_run_logs. Cross-cutting. Não executa o nó, prepara observabilidade e billing.
Contexto. Este passo é cross-cutting. Não faz parte da lógica de execução do nó em si. Prepara observabilidade e bilhetagem antes do handler rodar. Também aqui é feito o recordLegacyNodeStart para nós que não vão pelo Temporal (INSERT em node_executions com status running). Garante audit trail uniforme entre paths.

Em resumo. É o crachá invisível que o funcionário coloca antes de começar a trabalhar. Quem precisar saber "quem está fazendo esse trabalho agora?" só olha para o crachá. Ninguém precisa perguntar. Tecnicamente é AsyncLocalStorage, recurso nativo do Node.js que carrega dados através de async chains sem poluir assinaturas de função. Antes do handler rodar, o loop chama chargeContext.enterWith({ execId, nodeId }). Pronto. Todo await feito dentro daquele contexto (chamada de LLM, HTTP externo, query TypeORM) enxerga esses valores via chargeContext.getStore(). Isso é essencial para billing. Quando o AnthropicService ou o OpenAIService vai cobrar tokens, nem sabe que está rodando dentro de um agente. Só chama updateTokens(delta). O ProductService lê o contexto, extrai execId e nodeId e insere em token_transactions com metadata correta. Sem ALS, cada método provider precisaria receber esses ids por argumento explícito. Como esses serviços são compartilhados com rotas API públicas, isso poluiria a assinatura toda. Ponto de fragilidade. enterWith não é auto-limpo. Se algum callback assíncrono escapar do try do nó, continua vendo o contexto antigo. Não acontece em prática (o try engloba tudo). É o tipo de coisa que quebra silenciosamente se o refactor não for cuidadoso.

🎯 Por que AsyncLocalStorage e não parâmetro?
Passar execId e nodeId por argumento em toda chamada de LLM, HTTP ou DB seria assinatura poluída. Provider services (Anthropic, OpenAI, etc.) são compartilhados por rotas API e por execução de agente. Não podem ter esse contexto na assinatura.

ALS resolve. Contexto lexical num async chain sem envenenar interfaces.
⚠️ enterWith não é "escopado"
Diferente de .run(store, fn), o enterWith não é auto-limpo quando o try termina. Se o próximo nó também chamar .enterWith, o valor é sobrescrito. Ok para este uso. Se algum callback assíncrono escapar do try (não deveria acontecer), continua vendo o contexto antigo.
🔧 nodeCancelContext usa o mesmo pattern
Logo abaixo, linha 3268: nodeCancelContext.enterWith(cancelWatch.entry). Também ALS. Também injeta contexto para que interceptors de fetch e axios possam abortar. Ver detalhamento do Cancellation check.
📎 Sub-runs (fluxBox, libraryNode) reentram
Quando um nó container dispara um sub-flow, o loop nested faz seu próprio enterWith com o novo nodeId dos nós de dentro. Ao voltar para o parent, o contexto do parent precisa ser restaurado. Hoje isso é feito pela cadeia async natural (o parent segue seu próprio async context).

C RunLogCollector.startNode(params)
space_run_logs/run-log-collector.ts:319-335
startNode(params: StartNodeParams): RunLogNode | null
Propósito. Cria um RunLogNode novo, ofusca segredos de settings e input, faz push no bucket ativo (nodesBucket, que aponta para rootDoc.nodes ou para parentNode.innerSteps se dentro de um loop ou library) e dispara flush para o banco.
Em resumo. É o escrivão que abre uma pasta para o nó atual na "árvore da execução". Cada agente executando tem um RunLogDocument raiz. É um JSON com todos os nós que rodaram, seus tempos, tokens, custos, aninhamento (sub-runs, loops). O escrivão preenche a capa da pasta agora (timestamp de início, tipo, label, entrada já resolvida, status in_progress). Ofusca credenciais sensíveis (redactSecrets troca apiKey, Authorization, password por [REDACTED]) e empurra para a pilha ativa. O ponto central é o nodesBucket. É um ponteiro que muda conforme o contexto. Se está na execução raiz, aponta para rootDoc.nodes. Se está dentro de um libraryNode, aponta para innerSteps daquele parent. Se está numa iteração de arrayNode, também aponta para innerSteps. Se é um sub-flow (fluxBox), aponta para um documento novo. Só trocar o ponteiro faz o mesmo startNode gerar hierarquia certa em qualquer contexto. Depois do push, chama flushRoot, que dispara spaceRunLogsService.scheduleUpsert. O log vai para o banco de forma debounced, sem hammering. Se a execução crashar antes de endNode, esse registro fica com status='in_progress' para sempre. Indicador visual de execução interrompida.

🎯 Por que trace uniforme?
Analytics, replay, debug. Todos querem uma tabela única de execuções. Se só nós Temporal aparecessem, um agente com mix de textGenerator (Temporal) e conditionNode (inline) teria histórico "furado".

Também é o que permite à UI de execution log mostrar todos os passos numa timeline consistente.
📎 Quem escreve o "finish" desses rows?
recordInApiNodeError (linha 3303, 4593-4720) escreve o resultado de nós legacy. Grava status='FAILED' ou 'COMPLETED', outputData e errorMessage. Não é o worker (path Temporal usa persistNodeSuccess).
⚠️ Async não-espera é tentador
O await aqui atrasa o dispatch. Em nós rápidos (condition, math) esse INSERT vira ~5-10ms de latência por nó. Não é elegível para remover porque o UPDATE seguinte precisa dessa linha existir.
🔧 Diferença para o path Temporal
No path Temporal, o INSERT em node_executions é feito por createNodeExecution dentro de processNodeViaTemporal (passo T2). É feito com metadata.workflowId populado. Aqui (legacy) o INSERT é sem workflow. Indica execução inline no próprio processo do backend.
E spaceRunLogsService.scheduleUpsert (autoflush)
space_run_logs/space_run_logs.service.ts:92-120
scheduleUpsert(params: { spaceId; rootFlowId; doc: RunLogDocument }): void
Propósito. Callback registrado no runLogCollector. Cada flushRoot (disparado por startNode, endNode, finalize) agenda um UPSERT debounced em space_run_logs. Sem debounce, uma execução com 100 nós faria 200+ writes. Com debounce, agrupa mudanças recentes num único write.
Em resumo. É o timer da secretária, que evita reimprimir a mesma pilha de papel 200 vezes. O coletor quer gravar rápido no banco para a UI ver a timeline atualizada em quase-tempo-real. Cada startNode e endNode disparando UPSERT direto faria uma rajada absurda de writes numa execução com muitos nós. A solução. Cada chamada de flushRoot vira scheduleUpsert(doc). Faz setTimeout(FLUSH_DEBOUNCE_MS) e guarda o timer num Map por processId. Se outra chamada chegar antes do timer disparar, cancela a anterior e reinicia. Só grava quando fica quieto por N ms. Rajadas de mudança viram 1 write. Padrão simples de debounce. No fim da execução (passo 4.4), runLogCollector.finalize() chama spaceRunLogsService.flushNow(processId). Força write imediato. Garante que o registro final está no banco antes do backend responder. O risco. Se o backend crashar entre o último flush e o finalize, o batch em andamento se perde. O log fica congelado no penúltimo estado, com nós ainda em in_progress. É otimização, não correção. Se remover, semântica não muda, só o custo aumenta. Pode ser adiado no plano de migração.
E1 Debounce map keyed by processId
this.pendingFlushes: Map<processId, { timer, spaceId, rootFlowId, doc }>. Cada chamada:
1. Faz clear no timer anterior (se existir)
2. setTimeout(FLUSH_DEBOUNCE_MS, () => upsert(doc))
3. Guarda o novo timer no map

Efeito. Só grava se ficar quieto por N ms. Rajadas de atualização (start e end de vários nós) viram 1 write.

E2 UPSERT com JSONB completo

🎯 flushNow em 4.4
No fim da execução (Fase 4, passo 4.4), runLogCollector.finalize() chama spaceRunLogsService.flushNow(processId). Cancela debounce e força write imediato. Garante que o registro final está no banco antes do backend retornar.
⚠️ Se a execução crashar, debounce perde
Se o backend crashar entre startNode e finalize, o último batch de mudanças (que ainda estava no timer) some. Fica registrado em space_run_logs só o estado do último flush efetivo.

Em prática significa. Crash log pode ficar com nó em in_progress mesmo depois de terminar. Não é reconstitutível sem replay.
🔧 Uma linha por processId
space_run_logs tem PK processId. A execução inteira vira uma única linha com JSONB gigante. UI de timeline lê essa linha inteira. Escalar para execuções muito grandes vai virar problema de tamanho de linha e query time.
Resumo — o que sai de 3.4:
• chargeContext.getStore() agora retorna { execId, nodeId } para qualquer serviço assíncrono chamado abaixo.
• genericRunLogNode: RunLogNode com status='in_progress' vivo no coletor (null para fluxBox e libraryNode).
• space_run_logs ganhou um flush agendado (debounced) refletindo o novo nó.
• node_executions ganhou uma linha com entrada resolvida para nós legacy (não vale para Temporal).
• 1 INSERT (só para legacy), 1 UPSERT debounced.
Observações para migração:
• chargeContext depende de single-process. No worker, o handler roda em outro processo ou máquina e não vê a ALS do backend. O worker cobra via HTTP /worker/charge-tokens (W7) passando execId e nodeId explícitos. Padrão superior que o backend pode adotar também.
• RunLogCollector hierárquico com innerSteps e subRun é parte essencial da UX (timeline aninhada). Migração precisa preservar. Como o coletor vive no processo do backend, a migração para o worker envolve serializar RunLogNode para o backend agregar. Ou expor um serviço centralizado.
• O redactSecrets é o único ponto onde credenciais são ofuscadas antes de log. Qualquer refactor precisa manter esse hook. Vazar em space_run_logs é evento de segurança.
• Debounce de scheduleUpsert é otimização, não correção. Se remover, a semântica não muda, só o custo. Pode ficar de fora do MVP da migração.
• recordLegacyNodeStart só existe para manter parity com Temporal. Quando tudo for para o worker, essa função vira dead code. Bom sinal do progresso da migração.
• É essencial e cross-cutting. Deve ser tratado como subsistema no plano de migração, não como parte do handler de nó individual.

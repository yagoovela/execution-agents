Step 3.4 — runLogCollector.startNode() + chargeContext.enterWith()

Block in flux.service.ts:3263-3316. Two things in parallel. (1) Opens a hierarchical RunLogNode in the collector to trace execution. (2) Enters the charging context via AsyncLocalStorage. That way any service called below can charge tokens and cost to the right node without receiving execId and nodeId as arguments.
In summary — what this step does
  • Puts on the invisible charging badge. chargeContext.enterWith({ execId, nodeId }) injects those ids into the AsyncLocalStorage. Any await below (LLM, HTTP, DB) can read the context without receiving it as argument. It's the central per-node billing mechanism.
  • Opens the node's folder in the hierarchical log. runLogCollector.startNode(...) creates a new RunLogNode with status in_progress, redacts secrets (apiKey, Authorization) and pushes onto nodesBucket. That bucket is a pointer that shifts per context (root, library, loop, sub-flow) and produces hierarchy effortlessly.
  • Sub-run anchors delegate the log. fluxBox and libraryNode skip startNode (genericRunLogNode = null). Their handler creates its own nested subRun with the full internal hierarchy. Avoids duplicated entries in the timeline.
  • Uniform trace via recordLegacyNodeStart. For nodes that don't go through Temporal, inserts a running-status row in node_executions. Ensures the audit trail table covers both paths (inline and worker). Becomes dead code as more types migrate.
  • Debounced writes. spaceRunLogsService.scheduleUpsert groups bursts of flushRoot into a single UPSERT (setTimeout keyed by processId). Without it, a run with 100 nodes would do 200+ writes. At the end, flushNow forces the final write.
  • Output. chargeContext active, genericRunLogNode live in the collector (or null for anchors), 1 INSERT in node_executions for legacy, 1 debounced UPSERT in space_run_logs. Cross-cutting. Doesn't run the node, just sets up observability and billing.
Context. This step is cross-cutting. It's not part of the node's execution logic itself. It sets up observability and billing before the handler runs. This is also where recordLegacyNodeStart happens for nodes that don't go through Temporal (INSERT in node_executions with running status). Ensures a uniform audit trail across paths.

A chargeContext.enterWith({ execId, nodeId })
product/charge-context.ts:1-8 · flux.service.ts:3263-3266
chargeContext = new AsyncLocalStorage<ChargeContext>() · interface ChargeContext { execId?: string; nodeId?: string; }
Purpose. Injects { execId, nodeId } into Node.js's async context. Any async call made inside the try below (LLM, HTTP, DB) that invokes chargeContext.getStore() gets these values without having to pass them by argument. It's the central per-node billing mechanism.
In summary. It's the invisible badge the employee puts on before starting work. Anyone who needs to know "who's doing this work right now?" just looks at the badge. Nobody has to ask. Technically it's AsyncLocalStorage, a Node.js native feature that carries data through async chains without polluting function signatures. Before the handler runs, the loop calls chargeContext.enterWith({ execId, nodeId }). Done. Every await inside that context (LLM call, external HTTP, TypeORM query) sees those values via chargeContext.getStore(). This is essential for billing. When AnthropicService or OpenAIService goes to charge tokens, it doesn't even know it's running inside an agent. It just calls updateTokens(delta). ProductService reads the context, extracts execId and nodeId and inserts into token_transactions with correct metadata. Without ALS, each provider method would have to receive those ids by explicit argument. Since these services are shared with public API routes, that would pollute the entire signature. Fragility point. enterWith is not auto-cleaning. If some async callback escapes the node's try block, it keeps seeing the old context. Doesn't happen in practice (the try covers everything). The kind of thing that breaks silently if the refactor isn't careful.

🎯 Why AsyncLocalStorage and not a parameter?
Passing execId and nodeId by argument on every LLM, HTTP or DB call would pollute the signature. Provider services (Anthropic, OpenAI, etc.) are shared between API routes and agent execution. They can't carry that context in the signature.

ALS solves it. Lexical context in an async chain without poisoning interfaces.
⚠️ enterWith is not "scoped"
Unlike .run(store, fn), enterWith is not auto-cleaned when the try ends. If the next node also calls .enterWith, the value is overwritten. Fine for this use. If some async callback escapes the try (shouldn't happen), it keeps seeing the old context.
🔧 nodeCancelContext uses the same pattern
Right below, line 3268: nodeCancelContext.enterWith(cancelWatch.entry). Also ALS. Also injects context so fetch and axios interceptors can abort. See Cancellation check detail.
📎 Sub-runs (fluxBox, libraryNode) re-enter
When a container node fires a sub-flow, the nested loop does its own enterWith with the new nodeId of the internal nodes. When returning to the parent, the parent's context needs to be restored. Today that's done by the natural async chain (the parent follows its own async context).
B isSubRunAnchorNode = (fluxBox | libraryNode)
flux.service.ts:3286-3295
const isSubRunAnchorNode = node.type === 'fluxBox' || node.type === 'libraryNode';
Purpose. Decides whether the collector should create a "flat" RunLogNode or skip. Container nodes (fluxBox, libraryNode) delegate log creation to their handler. That one calls startFlowCallerSubRun or startLibrarySubRun and creates its own nested document with the full internal hierarchy.
In summary. It's a filter to avoid duplicate logging. fluxBox and libraryNode are container nodes. They don't do work themselves. They fire another whole agent internally. If the collector created a simple RunLogNode here (the container) and then those types' handler created a full subRun with the child agent's whole hierarchy, the UI timeline would show two entries for the same container: one shallow, one deep. Confusing. Solution. For those types, the collector skips (genericRunLogNode = null) and delegates log creation to the handler itself. Via startFlowCallerSubRun, the handler builds a nested RunLogDocument with all the sub-flow's internal nodes. Side effect of the null. Step 3.9 (endNode) is also skipped. The handler is responsible for finalizing its own sub-log. It's the only place in the loop with "hardcoded knowledge" about those two specific types. Ideally would be a flag on the node type metadata, not an inline comparison. Small refactor but symbolic of the migration direction.

C RunLogCollector.startNode(params)
space_run_logs/run-log-collector.ts:319-335
startNode(params: StartNodeParams): RunLogNode | null
Propósito. Cria um RunLogNode novo, ofusca segredos de settings e input, faz push no bucket ativo (nodesBucket, que aponta para rootDoc.nodes ou para parentNode.innerSteps se dentro de um loop ou library) e dispara flush para o banco.
Em resumo. É o escrivão que abre uma pasta para o nó atual na "árvore da execução". Cada agente executando tem um RunLogDocument raiz. É um JSON com todos os nós que rodaram, seus tempos, tokens, custos, aninhamento (sub-runs, loops). O escrivão preenche a capa da pasta agora (timestamp de início, tipo, label, entrada já resolvida, status in_progress). Ofusca credenciais sensíveis (redactSecrets troca apiKey, Authorization, password por [REDACTED]) e empurra para a pilha ativa. O ponto central é o nodesBucket. É um ponteiro que muda conforme o contexto. Se está na execução raiz, aponta para rootDoc.nodes. Se está dentro de um libraryNode, aponta para innerSteps daquele parent. Se está numa iteração de arrayNode, também aponta para innerSteps. Se é um sub-flow (fluxBox), aponta para um documento novo. Só trocar o ponteiro faz o mesmo startNode gerar hierarquia certa em qualquer contexto. Depois do push, chama flushRoot, que dispara spaceRunLogsService.scheduleUpsert. O log vai para o banco de forma debounced, sem hammering. Se a execução crashar antes de endNode, esse registro fica com status='in_progress' para sempre. Indicador visual de execução interrompida.

Propósito. Grava linha em node_executions com status running apenas para nós que não vão pelo Temporal (isTemporalNode=false) e não são worker-routed integrations. Por quê? Trace uniforme. node_executions vira o audit trail canônico de todos os nós, independente do path.

🎯 Por que trace uniforme?
Analytics, replay, debug. Todos querem uma tabela única de execuções. Se só nós Temporal aparecessem, um agente com mix de textGenerator (Temporal) e conditionNode (inline) teria histórico "furado".

Também é o que permite à UI de execution log mostrar todos os passos numa timeline consistente.
📎 Quem escreve o "finish" desses rows?
recordInApiNodeError (linha 3303, 4593-4720) escreve o resultado de nós legacy. Grava status='FAILED' ou 'COMPLETED', outputData e errorMessage. Não é o worker (path Temporal usa persistNodeSuccess).
⚠️ Async não-espera é tentador
O await aqui atrasa o dispatch. Em nós rápidos (condition, math) esse INSERT vira ~5-10ms de latência por nó. Não é elegível para remover porque o UPDATE seguinte precisa dessa linha existir.
🔧 Diferença para o path Temporal
No path Temporal, o INSERT em node_executions é feito por createNodeExecution dentro de processNodeViaTemporal (passo T2). É feito com metadata.workflowId populado. Aqui (legacy) o INSERT é sem workflow. Indica execução inline no próprio processo do backend.
E spaceRunLogsService.scheduleUpsert (autoflush)
space_run_logs/space_run_logs.service.ts:92-120
scheduleUpsert(params: { spaceId; rootFlowId; doc: RunLogDocument }): void
Propósito. Callback registrado no runLogCollector. Cada flushRoot (disparado por startNode, endNode, finalize) agenda um UPSERT debounced em space_run_logs. Sem debounce, uma execução com 100 nós faria 200+ writes. Com debounce, agrupa mudanças recentes num único write.
Em resumo. É o timer da secretária, que evita reimprimir a mesma pilha de papel 200 vezes. O coletor quer gravar rápido no banco para a UI ver a timeline atualizada em quase-tempo-real. Cada startNode e endNode disparando UPSERT direto faria uma rajada absurda de writes numa execução com muitos nós. A solução. Cada chamada de flushRoot vira scheduleUpsert(doc). Faz setTimeout(FLUSH_DEBOUNCE_MS) e guarda o timer num Map por processId. Se outra chamada chegar antes do timer disparar, cancela a anterior e reinicia. Só grava quando fica quieto por N ms. Rajadas de mudança viram 1 write. Padrão simples de debounce. No fim da execução (passo 4.4), runLogCollector.finalize() chama spaceRunLogsService.flushNow(processId). Força write imediato. Garante que o registro final está no banco antes do backend responder. O risco. Se o backend crashar entre o último flush e o finalize, o batch em andamento se perde. O log fica congelado no penúltimo estado, com nós ainda em in_progress. É otimização, não correção. Se remover, semântica não muda, só o custo aumenta. Pode ser adiado no plano de migração.
E1 Debounce map keyed by processId
this.pendingFlushes: Map<processId, { timer, spaceId, rootFlowId, doc }>. Cada chamada:
1. Faz clear no timer anterior (se existir)
2. setTimeout(FLUSH_DEBOUNCE_MS, () => upsert(doc))
3. Guarda o novo timer no map

Efeito. Só grava se ficar quieto por N ms. Rajadas de atualização (start e end de vários nós) viram 1 write.

🎯 flushNow em 4.4
No fim da execução (Fase 4, passo 4.4), runLogCollector.finalize() chama spaceRunLogsService.flushNow(processId). Cancela debounce e força write imediato. Garante que o registro final está no banco antes do backend retornar.
⚠️ Se a execução crashar, debounce perde
Se o backend crashar entre startNode e finalize, o último batch de mudanças (que ainda estava no timer) some. Fica registrado em space_run_logs só o estado do último flush efetivo.

Em prática significa. Crash log pode ficar com nó em in_progress mesmo depois de terminar. Não é reconstitutível sem replay.
🔧 Uma linha por processId
space_run_logs tem PK processId. A execução inteira vira uma única linha com JSONB gigante. UI de timeline lê essa linha inteira. Escalar para execuções muito grandes vai virar problema de tamanho de linha e query time.
Resumo — o que sai de 3.4:
• chargeContext.getStore() agora retorna { execId, nodeId } para qualquer serviço assíncrono chamado abaixo.
• genericRunLogNode: RunLogNode com status='in_progress' vivo no coletor (null para fluxBox e libraryNode).
• space_run_logs ganhou um flush agendado (debounced) refletindo o novo nó.
• node_executions ganhou uma linha com entrada resolvida para nós legacy (não vale para Temporal).
• 1 INSERT (só para legacy), 1 UPSERT debounced.
Observações para migração:
• chargeContext depende de single-process. No worker, o handler roda em outro processo ou máquina e não vê a ALS do backend. O worker cobra via HTTP /worker/charge-tokens (W7) passando execId e nodeId explícitos. Padrão superior que o backend pode adotar também.
• RunLogCollector hierárquico com innerSteps e subRun é parte essencial da UX (timeline aninhada). Migração precisa preservar. Como o coletor vive no processo do backend, a migração para o worker envolve serializar RunLogNode para o backend agregar. Ou expor um serviço centralizado.
• O redactSecrets é o único ponto onde credenciais são ofuscadas antes de log. Qualquer refactor precisa manter esse hook. Vazar em space_run_logs é evento de segurança.
• Debounce de scheduleUpsert é otimização, não correção. Se remover, a semântica não muda, só o custo. Pode ficar de fora do MVP da migração.
• recordLegacyNodeStart só existe para manter parity com Temporal. Quando tudo for para o worker, essa função vira dead code. Bom sinal do progresso da migração.
• É essencial e cross-cutting. Deve ser tratado como subsistema no plano de migração, não como parte do handler de nó individual.

Step 2.2a — Cancellation setup before the loop

Block at flux.service.ts:3239-3249. Before the main loop starts, the backend decides whether to arm the Cancel button for this execution. It goes through three independent gates (run type, global feature flag and cancel key resolution). If all match, each node in the loop gets its own AbortSignal when it runs.
In summary — what this step does
  • Decides whether to arm cancellation. shouldWatchCancellation only turns on the watch when runType is canvas (manual execution from the editor) or when it is a nested sub-run (called by fluxBox/libraryNode). Cronjobs, webhooks, MCP and other automatic triggers cannot be cancelled.
  • Resolves the execution key for cancellation. resolveCancelRunKey returns parentRunId if one was passed (sub-run), otherwise the own runLogProcessId. This ensures that cancelling the parent run propagates to nested children without requiring those children to know their own cancel ID.
  • Checks global feature flag. featureFlagsService.isEnabled(NODE_CANCEL_IN_FLIGHT_FLAG) reads the feature_flags table. It is a single-row kill switch (key node_cancel_in_flight). Global. No user or space scope. Query error returns false (fail-closed).
  • No AbortController here yet. At this point it only computes the three booleans (cancelWatchEnabled, cancelRunKey, inFlightEnabled). The real AbortController and the polling timer are only born inside the loop, at line 3304-3314, per node, via startNodeCancelWatch.
  • Output. Three variables ready in the apiV2() scope. cancelWatchEnabled, cancelRunKey, inFlightEnabled. The loop calls shouldStartNodeCancelWatch({ watchEnabled, inFlightEnabled }) per iteration to decide whether to create the node's watch.
⚠️ Careful with the 3 gates. If any of the three fails (runType not cancellable, feature flag off, or some bug in resolveCancelRunKey returning empty string, which does not happen today), the watch does not arm. The user can click cancel 20 times. The row in flow_run_states is created but the loop never reads it. Execution proceeds silently to the end as if nothing was requested.

A shouldWatchCancellation()
run-cancellation.service.ts:19-24
function shouldWatchCancellation(params: { runType: string | null | undefined; isNestedRun: boolean }): boolean
Purpose. First gate. Decides whether the execution is of a type the user can cancel. Returns true only for cancellable editor executions or nested sub-runs. For any other execution (webhook, cronjob, MCP, batch, etc.), returns false. No watch is armed afterwards.
In summary. This gate is the doorman of the Cancel button. It checks two conditions. First. Was the execution fired from the editor (canvas)? If yes, there is a button. The user can click. Second. Is it a sub-run nested inside another execution? If yes, the parent is already canvas, so cancellation has to reach the child too. If both answers are "no" (cronjob, webhook, MCP, public API call, email, etc.), the doorman closes the door. The cancel button does not exist for this execution type. Makes sense. A cronjob has no UI during execution.

🎯 Why only canvas?
It is the only execution type with a visible UI while running. Only there is a clickable Cancel button. Cronjobs, webhooks and MCP run server-side without active UI.

A cronjob that calls another flow via flow-caller-node propagates the parent execution to the child. But the parent is not canvas. Nothing in that chain is cancellable.
📎 Nested run inherits cancellability
A fluxBox executed inside a canvas run becomes a sub-run. In it, isNestedRunLog = true. The watch arms in the child too.

Essential for cancel to propagate. The parent reads the same row in flow_run_states via the cancelRunKey resolved in B.
⚠️ Closed list, not configurable
CANCELLABLE_RUN_TYPES is a hardcoded constant in the file. Adding chatbot or batch as cancellable requires code change and deploy. There is no per-type feature flag.
B resolveCancelRunKey()
cancel-run-key.ts:1-7
function resolveCancelRunKey(params: { runLogProcessId: string; parentRunId: string | null }): string
Purpose. Defines which ID is used to read the cancellation intent from the database. In a root run, it is the runLogProcessId itself. In a sub-run, it is the parentRunId. When the user cancels the parent run, the nested child is also interrupted, without explicit communication between them.
In summary. This mechanism makes every node, even inside sub-runs nested 3 levels deep, look at the same row in flow_run_states. The root run's row. When the user clicks Cancel in the editor, a single row is created with the parent run's ID. Nested children have no rows of their own. They query the parent's. If each sub-run created its own row, cancel would have to be propagated manually. Not here. Parentage is resolved up front and everyone reads from the same place.
B1 Formula
return params.parentRunId || params.runLogProcessId;
One line only. If parentRunId exists (not null, not empty), use it. Otherwise, fall back to runLogProcessId. No transformation, no namespace, no prefix.

B2 How the value is used
In startNodeCancelWatch({ runId: cancelRunKey, ... }), the timer calls runCancellationService.isCancelRequested(cancelRunKey). The function runs SELECT ... FROM flow_run_states WHERE runId = $1 AND deletedAt IS NULL. The root run and all nested ones use the same runId value.
flux.service.ts:3308-3313
📎 Not Redis, it's Postgres
Although the name suggests a pub/sub key, no Redis is involved. Cancel is stored as a row in flow_run_states (Postgres) and read by polling every 2s (CANCEL_POLL_MS at node-cancel-watch.ts:3).

The name "key" refers to "logical key of the run", not to "Redis key".
🔧 parentCancelRunKey also exists
The parentCancelRunKey parameter arrives at apiV2() when a fluxBox or libraryNode calls another flow. Even in deep chains (canvas → fluxBox → nested fluxBox), the key stays as the root canvas one.

See call. parentRunId: parentCancelRunKey ?? null at flux.service.ts:3245.
⚠️ No namespace. Collision risk
The key is a raw UUID (from runLogProcessId). Two system features could theoretically collide if they used the same UUIDs in other contexts. In practice, UUIDs are unique. There is no prefix (run:, cancel:, etc.). The table is dedicated to runs, so it works. In Redis this would be bad practice.
C featureFlagsService.isEnabled(NODE_CANCEL_IN_FLIGHT_FLAG)
feature-flags.service.ts:15-26
async isEnabled(key: string): Promise<boolean>
Purpose. Global kill switch. Reads the feature_flags table looking for the 'node_cancel_in_flight' key. If the row exists and enabled === true, in-flight cancel (interrupt LLM streaming, HTTP calls, etc.) is on. Any other situation, including query error, returns false (fail-closed).
In summary. It is a global breaker. If a bug starts interrupting executions by mistake in production, an admin flips this breaker in the database. Nobody can cancel in-flight anymore. Worst case is cancel only working between nodes (after a node naturally ends), not during. Handy for debugging without needing a deploy. The key is global. Not per user, space or tenant. It applies to the whole platform. If the database read fails for any reason, behavior is to turn off for safety instead of assuming it is on. Classic fail-closed policy.

🎯 Global scope. Not user, not space
The feature_flags table only has key and enabled. No userId, spaceId or companyId. It is a whole-platform flag. Turning it on/off affects every user in every space at the same time.
⚠️ Silent fail-closed
If the query throws (DB down, timeout, etc.), the catch logs a console.error and returns false. The execution does not know the check failed. It only notices that in-flight cancel is not armed.

Effect. In a DB outage, all in-flight cancels silently stop working.

D startNodeCancelWatch() inside the loop
node-cancel-watch.ts:63-93
function startNodeCancelWatch(params: { runId; nodeId; isCancelRequested; pollMs? }): NodeCancelWatch
Purpose. Creates (per node, inside the main loop) a new AbortController and a setInterval. Every 2s asks runCancellationService.isCancelRequested(runId) whether the user clicked cancel. If yes, calls controller.abort(). This propagates the AbortSignal to the node's handler (Anthropic, OpenAI, HTTP, MCP, etc.). This is the only place that actually arms in-flight cancel.
In summary. A watchman that shows up at the start of each node's execution, if step 2.2a authorized. Sets up an AbortController (the abort button) and starts a stopwatch that, every 2 seconds, asks "did they cancel this execution?". If the answer is "yes", calls abort(). The AbortSignal is propagated to any ongoing async call (call to Claude/OpenAI, HTTP fetch, MCP call). The provider's SDK, on receiving the abort, cancels the stream. Prevents spending tokens on a response nobody will see. When the node ends (naturally or aborted), the watchman leaves. stop() clears the timer. Armed per node, not per execution. Each node gets a new AbortController.

D4 Who publishes the cancellation
Not Redis pub/sub. When the user clicks cancel, the backend calls runCancellationService.requestCancel({ runId, flowId, userId }). The function runs INSERT INTO flow_run_states ... ON CONFLICT DO NOTHING. The startNodeCancelWatch timer finds out via polling SELECT.
run-cancellation.service.ts:42-60
🎯 Polling, not pub/sub
CANCEL_POLL_MS = 2000 (2 seconds). Each active node queries flow_run_states every 2s. There is an in-memory cache for 1.5s (CANCEL_CHECK_TTL_MS) to reduce load in executions with many parallel nodes.

Cancel latency. User clicks. Up to 2s for the node to see. abort() propagates to the libs. The SDK handles it.
📎 Error names accepted as abort
ABORT_ERROR_NAMES. 'AbortError', 'CanceledError', 'McpError', 'APIUserAbortError'. If a provider (Anthropic SDK, axios, MCP client) throws an error with one of these names, it is interpreted as abort, not as a failure.

See node-cancel-watch.ts:7-12, 34-46.
⚠️ Timer without stop. Potential memory leak
If the main loop breaks for any reason before cancelWatch.stop() in the finally, the setInterval keeps running indefinitely in that process. Current code correctly calls stop() in the finally. Any future refactor must keep this. Orphan timer is a classic bug with setInterval.
🔧 wasAborted() is synchronous
cancelWatch.wasAborted() returns controller.signal.aborted. Synchronous flag read. After the node's handler runs, the loop uses this value to decide whether to set stoppedByCancel = true and break (line 4583-4598).
Summary — what 2.2a outputs.
• cancelWatchEnabled. Boolean. true if runType is canvas or nested run.
• cancelRunKey. String. parentCancelRunKey if provided, otherwise the runLogProcessId itself.
• inFlightEnabled. Boolean. Global feature flag node_cancel_in_flight.
• No AbortController created yet. Only the three variables. The controller is born later, per node, at line 3308.
Migration notes.
• Resolving the three gates is pure business logic. Replicable in the worker. It only needs runType, isNestedRun, parentRunId and access to the feature flag.
• Today the DB polling (2s) and the setInterval live in the backend process. In the worker (Temporal), the idiomatic pattern is to use Temporal signals instead of polling. More efficient. No 2s query per active node.
• The AsyncLocalStorage (nodeCancelContext) that carries the AbortSignal to child functions does not work the same in the worker. Temporal activities run in their own context. Alternatives. Pass the signal explicitly or use Temporal's Context.current().cancellationSignal.
• The feature flag node_cancel_in_flight can be reused in the worker. Same key, same read via Postgres. No need to migrate the table.
• Executions on the worker inherit cancellation for free via Temporal's mechanism. No need to duplicate the flow_run_states logic. Incremental migration requires the two systems coexisting. Inline backend uses polling. Worker uses signal.

Passo 2.2a — Setup de cancellation antes do loop

Bloco em flux.service.ts:3239-3249. Antes do loop principal iniciar, o backend decide se vai armar o botão de "Cancelar" pra esse run — passa por 3 gates independentes (tipo do run, feature flag global e resolução da chave de cancelamento). Se tudo bate, cada nó do loop vai ganhar um AbortSignal próprio quando executar.
Em resumo — o que esse passo faz
  • Decide se vale armar cancelamento: shouldWatchCancellation só liga o watch se o runType for canvas (execução manual pelo editor) ou se for um sub-run aninhado (chamado por fluxBox/libraryNode). Cronjobs, webhooks, MCP e outros disparos automáticos não podem ser cancelados.
  • Resolve a chave do run pra cancelamento: resolveCancelRunKey devolve o parentRunId se veio um (sub-run), senão o próprio runLogProcessId. Isso garante que cancelar o run pai propaga pros filhos aninhados sem esses filhos precisarem saber seu próprio ID de cancelamento.
  • Confere feature flag global: featureFlagsService.isEnabled(NODE_CANCEL_IN_FLIGHT_FLAG) lê a tabela feature_flags. É um kill switch single-row (chave node_cancel_in_flight) — global, sem escopo de user/space. Se der erro na query, retorna false (fail-closed).
  • Nada de AbortController aqui ainda: nesse ponto só calcula os 3 booleans (cancelWatchEnabled, cancelRunKey, inFlightEnabled). O AbortController real e o timer de polling só nascem dentro do loop, na linha 3304-3314, por nó, via startNodeCancelWatch.
  • Saída: 3 variáveis prontas no escopo do apiV2(): cancelWatchEnabled, cancelRunKey, inFlightEnabled. O loop consulta shouldStartNodeCancelWatch({ watchEnabled, inFlightEnabled }) por iteração pra decidir se cria o watch daquele nó.
⚠️ Cuidado com os 3 gates: se qualquer um dos três falhar (runType não cancelável, feature flag desligada, ou algum bug em resolveCancelRunKey retornando string vazia — o que hoje não acontece), o watch simplesmente não arma. O usuário pode clicar em cancelar 20 vezes, a linha em flow_run_states é criada, mas o loop nunca a lê — o run vai silenciosamente até o fim como se nada tivesse sido pedido.

A shouldWatchCancellation()
run-cancellation.service.ts:19-24
function shouldWatchCancellation(params: { runType: string | null | undefined; isNestedRun: boolean }): boolean
Propósito: Primeiro gate. Decide se esse run é do tipo que pode ser cancelado pelo usuário. Retorna true só pra runs cancelláveis do editor ou pra sub-runs aninhados; pra qualquer outro run (webhook, cronjob, MCP, batch, etc.) volta false e nenhum watch é armado depois.
Em resumo: pense nele como o porteiro do botão de Cancelar. Antes de qualquer coisa, ele pergunta duas coisas: (1) o run foi disparado pelo editor (canvas)? Se sim, tem botão, o usuário pode clicar. (2) É um sub-run aninhado dentro de outro run? Se sim, o pai já é canvas, então o cancelamento tem que descer pra ele também. Se ambas respostas forem "não" — ou seja, é um cronjob, webhook, MCP, chamada de API pública, email, etc. — o porteiro fecha a porta e o botão de cancelar não existe pra esse tipo de execução. Fica óbvio: você não cancela um cronjob no meio do run porque nem tem UI pra isso.

🎯 Por que só canvas?
É o único tipo de run que tem UI visível pro usuário enquanto executa — só ali existe botão de "Cancelar" clicável. Cronjobs, webhooks e MCP rodam server-side sem UI ativa.

Ainda assim, um cronjob que chame outro flow via flow-caller-node propaga o run pai pro filho — mas o pai não é canvas, então nada é cancelável nessa cadeia.
📎 Nested run herda cancellability
Um fluxBox executado dentro de um canvas run vira sub-run. Nele, isNestedRunLog = true, então o watch arma no filho também.

Isso é essencial pro cancel propagar — o pai lê a mesma flow_run_states row (via cancelRunKey resolvido em B).
⚠️ Lista fechada, não configurável
CANCELLABLE_RUN_TYPES é uma constante hardcoded no arquivo. Pra adicionar chatbot ou batch como canceláveis, tem que mudar código e deploy — não tem feature flag por tipo.
B resolveCancelRunKey()
cancel-run-key.ts:1-7
function resolveCancelRunKey(params: { runLogProcessId: string; parentRunId: string | null }): string
Propósito: Define qual ID vai ser usado pra ler a intenção de cancelamento no banco. Em um run raiz, é o próprio runLogProcessId. Em um sub-run, é o parentRunId — assim quando o usuário cancela o run pai, o filho aninhado também é interrompido, sem precisar de comunicação explícita entre eles.
Em resumo: pense nele como um sistema de "chamar todo mundo pelo apelido do chefe". Cada nó, mesmo dentro de sub-runs aninhados 3 níveis de profundidade, olha pra mesma linha na tabela flow_run_states — a linha do run raiz. Assim, quando o usuário clica em "Cancelar" no editor, uma única row é criada com o ID do run pai. Os filhos aninhados não têm rows próprias — eles olham a do pai. Se você mandasse cada sub-run criar sua própria row, aí sim precisaria propagar cancel manualmente. Aqui não: o parentesco é resolvido logo no início e todos leem do mesmo lugar.

flux.service.ts:3308-3313
📎 Não é Redis, é Postgres
Apesar do nome sugerir chave de pub/sub, não tem Redis envolvido. O cancel é armazenado como row em flow_run_states (Postgres) e lido por polling a cada 2s (CANCEL_POLL_MS em node-cancel-watch.ts:3).

O nome "key" vem de "chave lógica do run", não de "chave Redis".
🔧 parentCancelRunKey também existe
O parâmetro parentCancelRunKey chega no apiV2() quando um fluxBox/libraryNode chama outro flow. Assim, mesmo em cadeias profundas (canvas → fluxBox → fluxBox aninhado), a chave continua sendo a do canvas raiz.

Ver call: parentRunId: parentCancelRunKey ?? null em flux.service.ts:3245.
⚠️ Sem namespace = risco de colisão
Como a chave é UUID cru (do runLogProcessId), duas features do sistema poderiam teoricamente colidir se usassem UUIDs iguais em outros contextos. Na prática, UUIDs são únicos, mas não há prefixo (run:, cancel:, etc.) — a tabela é dedicada a runs, então tudo bem, mas em Redis isso seria má prática.
C featureFlagsService.isEnabled(NODE_CANCEL_IN_FLIGHT_FLAG)
feature-flags.service.ts:15-26
async isEnabled(key: string): Promise<boolean>
Propósito: Kill switch global. Lê a tabela feature_flags procurando a chave 'node_cancel_in_flight'. Se a row existir e enabled === true, o cancel em pleno voo (interromper LLM streaming, HTTP calls, etc.) fica ligado. Qualquer outra situação — incluindo erro na query — devolve false (fail-closed).
Em resumo: pense nela como um disjuntor global na parede. Se um bug começar a matar runs por engano em produção, um admin desliga esse disjuntor no banco e ninguém mais consegue cancelar em pleno voo — o worst case é o cancel só funcionar entre nós (após um nó terminar naturalmente), não durante. Isso é útil pra debugar sem precisar de deploy. A chave é global, não por user, space ou tenant — vale pra plataforma inteira. Se falhar a leitura do banco por qualquer motivo, o comportamento é desligar por segurança em vez de assumir ligado — política de fail-closed clássica.

🎯 Escopo global — nem user, nem space
A tabela feature_flags só tem key + enabled — não tem userId, spaceId ou companyId. É uma flag da plataforma inteira. Se ligar/desligar afeta todos os users em todos os spaces simultaneamente.
⚠️ Fail-closed silencioso
Se a query lançar (banco fora, timeout, etc.), o catch loga um console.error e devolve false. O run não sabe que a checagem falhou — só vê que o inflight cancel não está armado.

Efeito: em uma pane de banco, todos os cancels em pleno voo silenciosamente param de funcionar.
🔧 Diferença: watch vs. inflight cancel
cancelWatchEnabled (A) → dá pra observar intenção de cancelar em algum ponto?
inFlightEnabled (C) → dá pra abortar durante o nó via AbortSignal?

Precisa dos dois true pra shouldStartNodeCancelWatch retornar true e criar o AbortController.
D startNodeCancelWatch() dentro do loop
node-cancel-watch.ts:63-93
function startNodeCancelWatch(params: { runId; nodeId; isCancelRequested; pollMs? }): NodeCancelWatch
Propósito: Cria — por nó, dentro do loop principal — um AbortController novo e um setInterval que a cada 2s pergunta pra runCancellationService.isCancelRequested(runId) se o usuário clicou cancelar. Se sim, chama controller.abort(), que propaga o AbortSignal pro node handler (Anthropic, OpenAI, HTTP, MCP, etc.). É o único ponto que efetivamente arma o cancel em pleno voo.
Em resumo: pense nele como um vigia com um walkie-talkie que aparece no início da execução de cada nó, se o passo 2.2a autorizou. Ele monta um AbortController (o botão vermelho) e liga um cronômetro que a cada 2 segundos pergunta "já cancelaram esse run?". Se a resposta vier "sim", ele aperta o botão vermelho — o abort() é propagado via AbortSignal pra qualquer chamada assíncrona que esteja rodando (chamada pro Claude/OpenAI, fetch HTTP, MCP call). O SDK do provider ao receber o abort cancela a stream, evitando gastar tokens em resposta que ninguém vai ver. Quando o nó termina (naturalmente ou abortado), o vigia sai (stop() limpa o timer). É armado por nó, não por run — cada nó ganha um AbortController fresh.

D4 Quem "publica" o cancelamento
Não é Redis pub/sub: quando o usuário clica em cancelar, o backend chama runCancellationService.requestCancel({ runId, flowId, userId }) — que faz INSERT INTO flow_run_states ... ON CONFLICT DO NOTHING. O timer de startNodeCancelWatch descobre isso via polling do SELECT.
run-cancellation.service.ts:42-60
🎯 Polling, não pub/sub
CANCEL_POLL_MS = 2000 (2 segundos). Cada nó ativo faz 1 query por 2s no flow_run_states. Existe cache in-memory por 1.5s (CANCEL_CHECK_TTL_MS) pra reduzir load em runs com muitos nós paralelos.

Latência do cancel: usuário clica → até 2s pro nó ver → abort() propaga pra libs → SDK trata.
📎 Names de erros aceitos como abort
ABORT_ERROR_NAMES: 'AbortError', 'CanceledError', 'McpError', 'APIUserAbortError'. Se um provider (Anthropic SDK, axios, MCP client) lança erro com um desses nomes, é interpretado como abort — não como falha.

Ver node-cancel-watch.ts:7-12, 34-46.
⚠️ Timer não parado = memory leak potencial
Se o loop principal breakar por qualquer motivo antes do cancelWatch.stop() no finally, o setInterval continua rodando pra sempre naquele process. O código atual chama stop() corretamente em finally, mas qualquer refactor futuro precisa manter isso — timer órfão é bug clássico com setInterval.
🔧 wasAborted() é sync
cancelWatch.wasAborted() retorna controller.signal.aborted — leitura síncrona da flag. Depois do handler do nó rodar, o loop usa isso pra decidir se seta stoppedByCancel = true e break (linha 4583-4598).
Resumo — o que sai de 2.2a:
• cancelWatchEnabled = boolean (true se runType canvas OU nested run)
• cancelRunKey = string (parentCancelRunKey se veio, senão o próprio runLogProcessId)
• inFlightEnabled = boolean (feature flag global node_cancel_in_flight)
• Nenhum AbortController criado ainda — só as 3 variáveis. O controller nasce depois, por nó, na linha 3308.
Observações para migração:
• A resolução dos 3 gates é business logic pura — replicável no worker, precisa apenas de runType, isNestedRun, parentRunId e acesso à feature flag.
• Hoje o polling do banco (2s) e o setInterval vivem no processo do backend. No worker (Temporal), o padrão idiomático seria usar signals do Temporal em vez de polling — bem mais eficiente, sem query a cada 2s por nó ativo.
• O AsyncLocalStorage (nodeCancelContext) que carrega o AbortSignal pra funções filhas não funciona igual no worker: activities do Temporal rodam em contexto próprio. A alternativa é passar o signal explicitamente ou usar o Context.current().cancellationSignal do Temporal.
• Feature flag node_cancel_in_flight pode ser reaproveitada no worker — mesma chave, mesma leitura via Postgres. Não precisa migrar a tabela.
• Runs no worker herdam cancelamento gratuitamente via mecanismo do Temporal — não precisa duplicar a lógica de flow_run_states. Mas migração incremental precisa dos dois sistemas coexistindo (backend inline usa polling, worker usa signal).

Passo 2.2a — Setup de cancellation antes do loop

Bloco em flux.service.ts:3239-3249. Antes do loop principal iniciar, o backend decide se arma o botão de Cancelar para a execução. Passa por três gates independentes (tipo da execução, feature flag global e resolução da chave de cancelamento). Se tudo bate, cada nó do loop ganha um AbortSignal próprio quando executar.
Em resumo — o que esse passo faz
  • Decide se vale armar cancelamento. shouldWatchCancellation só liga o watch quando runType é canvas (execução manual pelo editor) ou quando é sub-run aninhado (chamado por fluxBox/libraryNode). Cronjobs, webhooks, MCP e outros disparos automáticos não podem ser cancelados.
  • Resolve a chave da execução para cancelamento. resolveCancelRunKey devolve o parentRunId se veio um (sub-run), senão o próprio runLogProcessId. Isso garante que cancelar o run pai propaga para os filhos aninhados sem exigir que esses filhos conheçam o próprio ID de cancelamento.
  • Verifica feature flag global. featureFlagsService.isEnabled(NODE_CANCEL_IN_FLIGHT_FLAG) lê a tabela feature_flags. É um kill switch single-row (chave node_cancel_in_flight). Global. Sem escopo de user ou space. Erro na query retorna false (fail-closed).
  • Nada de AbortController aqui ainda. Neste ponto só calcula os três booleans (cancelWatchEnabled, cancelRunKey, inFlightEnabled). O AbortController real e o timer de polling só nascem dentro do loop, na linha 3304-3314, por nó, via startNodeCancelWatch.
  • Saída. Três variáveis prontas no escopo do apiV2(). cancelWatchEnabled, cancelRunKey, inFlightEnabled. O loop consulta shouldStartNodeCancelWatch({ watchEnabled, inFlightEnabled }) por iteração para decidir se cria o watch do nó.
⚠️ Cuidado com os 3 gates. Se qualquer um dos três falhar (runType não cancelável, feature flag desligada, ou algum bug em resolveCancelRunKey retornando string vazia, o que hoje não acontece), o watch não arma. O usuário pode clicar em cancelar 20 vezes. A linha em flow_run_states é criada, mas o loop nunca a lê. A execução prossegue em silêncio até o fim como se nada tivesse sido solicitado.

A shouldWatchCancellation()
run-cancellation.service.ts:19-24
function shouldWatchCancellation(params: { runType: string | null | undefined; isNestedRun: boolean }): boolean
Propósito. Primeiro gate. Decide se a execução é do tipo que pode ser cancelada pelo usuário. Retorna true só para execuções canceláveis do editor ou para sub-runs aninhados. Para qualquer outra execução (webhook, cronjob, MCP, batch, etc.), retorna false. Nenhum watch é armado depois.
Em resumo. Este gate é o porteiro do botão Cancelar. Verifica duas condições. Primeira. A execução foi disparada pelo editor (canvas)? Se sim, existe botão. O usuário pode clicar. Segunda. É sub-run aninhado dentro de outra execução? Se sim, o pai já é canvas, então o cancelamento tem que descer para o filho. Se ambas as respostas são "não" (cronjob, webhook, MCP, chamada de API pública, email, etc.), o porteiro fecha a porta. O botão de cancelar não existe para este tipo de execução. Faz sentido. Um cronjob não tem UI durante a execução.

🎯 Por que só canvas?
É o único tipo de execução com UI visível para o usuário enquanto roda. Só ali existe botão de Cancelar clicável. Cronjobs, webhooks e MCP rodam server-side sem UI ativa.

Um cronjob que chame outro flow via flow-caller-node propaga a execução pai para o filho. Mas o pai não é canvas. Nada é cancelável nessa cadeia.
📎 Nested run herda cancellability
Um fluxBox executado dentro de um canvas run vira sub-run. Nele, isNestedRunLog = true. O watch arma no filho também.

É essencial para o cancel propagar. O pai lê a mesma linha em flow_run_states via cancelRunKey resolvido em B.
⚠️ Lista fechada, não configurável
CANCELLABLE_RUN_TYPES é constante hardcoded no arquivo. Adicionar chatbot ou batch como canceláveis exige mudança de código e deploy. Não há feature flag por tipo.
B resolveCancelRunKey()
cancel-run-key.ts:1-7
function resolveCancelRunKey(params: { runLogProcessId: string; parentRunId: string | null }): string
Propósito. Define qual ID é usado para ler a intenção de cancelamento no banco. Em um run raiz, é o próprio runLogProcessId. Em um sub-run, é o parentRunId. Quando o usuário cancela o run pai, o filho aninhado também é interrompido, sem comunicação explícita entre eles.
Em resumo. Este mecanismo faz cada nó, mesmo dentro de sub-runs aninhados a 3 níveis de profundidade, olhar para a mesma linha em flow_run_states. A linha do run raiz. Quando o usuário clica em Cancelar no editor, uma única linha é criada com o ID do run pai. Os filhos aninhados não têm linhas próprias. Consultam a do pai. Se cada sub-run criasse a própria linha, seria necessário propagar cancel manualmente. Aqui não. O parentesco é resolvido no início e todos leem do mesmo lugar.

flux.service.ts:3308-3313
📎 Não é Redis, é Postgres
Apesar do nome sugerir chave de pub/sub, não há Redis envolvido. O cancel é armazenado como linha em flow_run_states (Postgres) e lido por polling a cada 2s (CANCEL_POLL_MS em node-cancel-watch.ts:3).

O nome "key" refere-se a "chave lógica do run", não a "chave Redis".
🔧 parentCancelRunKey também existe
O parâmetro parentCancelRunKey chega no apiV2() quando um fluxBox ou libraryNode chama outro flow. Mesmo em cadeias profundas (canvas → fluxBox → fluxBox aninhado), a chave continua sendo a do canvas raiz.

Ver call. parentRunId: parentCancelRunKey ?? null em flux.service.ts:3245.
⚠️ Sem namespace. Risco de colisão
A chave é UUID cru (do runLogProcessId). Duas features do sistema poderiam teoricamente colidir se usassem UUIDs iguais em outros contextos. Na prática, UUIDs são únicos. Não há prefixo (run:, cancel:, etc.). A tabela é dedicada a runs, então funciona. Em Redis isso seria má prática.
C featureFlagsService.isEnabled(NODE_CANCEL_IN_FLIGHT_FLAG)
feature-flags.service.ts:15-26
async isEnabled(key: string): Promise<boolean>
Propósito. Kill switch global. Lê a tabela feature_flags procurando a chave 'node_cancel_in_flight'. Se a linha existir e enabled === true, o cancel em pleno voo (interromper LLM streaming, HTTP calls, etc.) fica ligado. Qualquer outra situação, incluindo erro na query, devolve false (fail-closed).
Em resumo. É um disjuntor global. Se um bug começar a interromper execuções por engano em produção, um admin desliga esse disjuntor no banco. Ninguém mais consegue cancelar em pleno voo. O pior caso é o cancel só funcionar entre nós (após um nó terminar naturalmente), não durante. Útil para debugar sem precisar de deploy. A chave é global. Não é por user, space ou tenant. Vale para a plataforma inteira. Se falhar a leitura do banco por qualquer motivo, o comportamento é desligar por segurança em vez de assumir ligado. Política de fail-closed clássica.

🎯 Escopo global. Nem user, nem space
A tabela feature_flags tem apenas key e enabled. Não tem userId, spaceId ou companyId. É uma flag da plataforma inteira. Ligar/desligar afeta todos os usuários em todos os spaces simultaneamente.
⚠️ Fail-closed silencioso
Se a query lançar (banco fora, timeout, etc.), o catch loga um console.error e devolve false. A execução não sabe que a checagem falhou. Só percebe que o inflight cancel não está armado.

Efeito. Em uma pane de banco, todos os cancels em pleno voo silenciosamente param de funcionar.
🔧 Diferença. watch vs. inflight cancel
cancelWatchEnabled (A). Dá para observar intenção de cancelar em algum ponto?
inFlightEnabled (C). Dá para abortar durante o nó via AbortSignal?

Precisa dos dois iguais a true para shouldStartNodeCancelWatch retornar true e criar o AbortController.
D startNodeCancelWatch() dentro do loop
node-cancel-watch.ts:63-93
function startNodeCancelWatch(params: { runId; nodeId; isCancelRequested; pollMs? }): NodeCancelWatch
Propósito. Cria (por nó, dentro do loop principal) um AbortController novo e um setInterval. A cada 2s pergunta a runCancellationService.isCancelRequested(runId) se o usuário clicou em cancelar. Se sim, chama controller.abort(). Isso propaga o AbortSignal para o handler do nó (Anthropic, OpenAI, HTTP, MCP, etc.). É o único ponto que efetivamente arma o cancel em pleno voo.
Em resumo. É um vigia que aparece no início da execução de cada nó, se o passo 2.2a autorizou. Monta um AbortController (o botão de aborto) e liga um cronômetro que, a cada 2 segundos, pergunta "já cancelaram esta execução?". Se a resposta é "sim", chama abort(). O AbortSignal é propagado para qualquer chamada assíncrona em andamento (chamada para Claude/OpenAI, fetch HTTP, MCP call). O SDK do provider, ao receber o abort, cancela a stream. Evita gastar tokens em resposta que ninguém verá. Quando o nó termina (naturalmente ou abortado), o vigia sai. stop() limpa o timer. Armado por nó, não por execução. Cada nó ganha um AbortController novo.

D4 Quem publica o cancelamento
Não é Redis pub/sub. Quando o usuário clica em cancelar, o backend chama runCancellationService.requestCancel({ runId, flowId, userId }). A função executa INSERT INTO flow_run_states ... ON CONFLICT DO NOTHING. O timer de startNodeCancelWatch descobre isso via polling do SELECT.
run-cancellation.service.ts:42-60
🎯 Polling, não pub/sub
CANCEL_POLL_MS = 2000 (2 segundos). Cada nó ativo faz uma query a cada 2s no flow_run_states. Existe cache in-memory por 1.5s (CANCEL_CHECK_TTL_MS) para reduzir load em execuções com muitos nós paralelos.

Latência do cancel. Usuário clica. Até 2s para o nó ver. abort() propaga para as libs. O SDK trata.
📎 Nomes de erros aceitos como abort
ABORT_ERROR_NAMES. 'AbortError', 'CanceledError', 'McpError', 'APIUserAbortError'. Se um provider (Anthropic SDK, axios, MCP client) lança erro com um desses nomes, é interpretado como abort, não como falha.

Ver node-cancel-watch.ts:7-12, 34-46.
⚠️ Timer sem parada. Memory leak potencial
Se o loop principal executar break por qualquer motivo antes do cancelWatch.stop() no finally, o setInterval continua rodando indefinidamente naquele processo. O código atual chama stop() corretamente no finally. Qualquer refactor futuro precisa manter isso. Timer órfão é bug clássico com setInterval.
🔧 wasAborted() é síncrono
cancelWatch.wasAborted() retorna controller.signal.aborted. Leitura síncrona da flag. Após o handler do nó rodar, o loop usa esse valor para decidir se ativa stoppedByCancel = true e faz break (linha 4583-4598).
Resumo — o que sai de 2.2a.
• cancelWatchEnabled. Boolean. true se runType é canvas ou nested run.
• cancelRunKey. String. parentCancelRunKey se veio, senão o próprio runLogProcessId.
• inFlightEnabled. Boolean. Feature flag global node_cancel_in_flight.
• Nenhum AbortController criado ainda. Só as três variáveis. O controller nasce depois, por nó, na linha 3308.
Observações para migração.
• A resolução dos três gates é business logic pura. Replicável no worker. Precisa apenas de runType, isNestedRun, parentRunId e acesso à feature flag.
• Hoje o polling do banco (2s) e o setInterval vivem no processo do backend. No worker (Temporal), o padrão idiomático é usar signals do Temporal em vez de polling. Mais eficiente. Sem query a cada 2s por nó ativo.
• O AsyncLocalStorage (nodeCancelContext) que carrega o AbortSignal para funções filhas não funciona igual no worker. Activities do Temporal rodam em contexto próprio. Alternativas. Passar o signal explicitamente ou usar Context.current().cancellationSignal do Temporal.
• A feature flag node_cancel_in_flight pode ser reaproveitada no worker. Mesma chave, mesma leitura via Postgres. Não precisa migrar a tabela.
• Execuções no worker herdam cancelamento gratuitamente via mecanismo do Temporal. Não precisa duplicar a lógica de flow_run_states. A migração incremental exige os dois sistemas coexistindo. Backend inline usa polling. Worker usa signal.

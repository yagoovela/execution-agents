Step 5.3 — Chatbot socket cleanup + forgetRun

Block at flux.service.ts:5393-5397. Last line executed. It's the finally of the main try/catch. deletes the entry from the chatbotSocketByRun Map and calls runCancellationService.forgetRun. In-memory cleanup to avoid leaks.
In short — what this step does
  • finally block. Always runs. Last thing executed on any path (success, error, cancel, rethrow). Cleans up in-memory Maps that aren't persisted. Without this cleanup, each execution would keep accumulating entries. The process would leak memory over time.
  • Closes the chatbot socket "book". If the execution populated chatbotSocketByRun in 3.10 (chatbot with socketId), the finally deletes that key. The if (socketId) guard avoids a needless call for other run_types that don't populate the Map.
  • Clears the runCancellationService cache. Calls forgetRun(runLogProcessId). Belt-and-suspenders. The cache has a 1500ms TTL and would clean itself. Explicit cleanup reduces the immediate footprint during high-frequency execution spikes.
  • Zero I/O, zero external side effect. Both are Map.delete. O(1). No network. No DB. Pure Node process housekeeping.
  • Output. Nothing externally visible. Just freed memory. If the execution went through 5.1 (error), the finally runs before the throw actually propagates. Cleanup guaranteed even on crash.
Context. The finally runs on any path: success, error, cancel, rethrow. Ensures in-memory Maps (not persisted) are cleaned at the end of the execution. Without this cleanup, each execution would keep accumulating entries. Chronic memory leak.

⚠️ Memory leak if it doesn't run
If some bug prevented the finally from executing (JS won't allow it; finally always runs, except on catastrophic process crash), the Map grows. In a long-running process with thousands of executions per hour, it becomes a problem.
🎯 Delete O(1)
Map.delete is constant time. No performance trade-off.

Migration notes:
• Trivial to maintain. Two cleanup lines. If the worker takes over the loop, it needs its own analogous cleanup.

• Doesn't block migration. Can stay as-is while the worker migrates other steps.

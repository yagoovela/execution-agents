Step 1.0a — Pre-everything initial setup

Block at flux.service.ts:2319-2337. The first 19 lines of apiV2(). They run before any query, guard, or try/catch. Stabilizes sessionId. Creates the billing counters. Resolves the canonical runLogProcessId. Wires the socket→execution lookup for the chatbot.
In short — what this step does
  • Normalizes the sessionId. A defensive ?.trim(). Strings with spaces, undefined, or null become an empty string. This matters later. The condition sessionId === '' carries special semantics. Step 1.5 uses 'default' when the flow has fluxObject.chat.
  • Initializes the counters. Declares totalTokensUsed and totalCost as zero. Creates the closure onUpdateTokens(t, c) that adds to those counters. That callback is passed downstream. It is the only way billing can find this execution's counters.
  • Decides the execution ID. A cascade over 4 sources in the order execId → injectedRunLogCollector.processId → parentProcessId → uuid(). It is the process number used as key across every service. It shows up in WebSocket, space run logs, and cancellation feature flags.
  • Registers the chatbot socket. If socketId came in, runs chatbotSocketByRun.set(runLogProcessId, socketId) on a class-level Map. This lets the worker return events to the correct browser even when the handoff is async. Cleanup only happens in step 5.3, inside the finally block.
  • Sets isNestedRunLog. Boolean flag derived from !!injectedRunLogCollector. Distinguishes a root execution, which writes its own SpaceRunLog, from a nested execution called by another flow. The nested execution must append to the parent's collector instead of writing on its own.
Context. These 19 lines do no I/O. They throw no exceptions. They have no try/catch. It is pure in-memory setup. The goal is to hand the following phases a stable, immutable context (counters, IDs, refs) before any operation that can fail.

B Counters + onUpdateTokens closure
flux.service.ts:2321-2327
let totalTokensUsed = 0;
let totalCost = 0;
const onUpdateTokens = (tokensUsed, cost) => { totalTokensUsed += tokensUsed; totalCost += cost; };
Purpose. Creates the execution's billing accumulators. Mutable counters (let) and a closure that increments them. It is the only mechanism through which AI providers, worker node executions, and sub-flows can add tokens and cost to the execution's totals.
In short. Two counters start at zero. They grow as nodes run and consume AI. Anyone who needs to add does not get a reference to the numbers. JavaScript does not pass number by reference. They get the onUpdateTokens closure. It is a tiny function that knows where the counters live and does the increment. That pattern enables distributed billing. The worker runs an LLM, calls onUpdateTokens(t, c), and the totals on the backend grow with no round-trip. At the end, the totals feed flowLogsService.createLog (step 4.3) and SpaceRunLog.finalize (step 4.4).

Both are let. Both zero. The closure captures by scope reference. Every += mutates the parent-scope variable.

B3 Callback consumers

🎯 Why a closure and not an object?
A { tokens, cost } passed by reference would have the same effect. The callback hides the structure. The consumer only knows how to call the function with (t, c). It is simple isolation that does not leak internal details.
📎 Final destination of the totals
totalTokensUsed and totalCost become spent_tokens and cost on the FlowLog (flux.service.ts:4873-4874). And become totalTokens and totalCost on the SpaceRunLog (flux.service.ts:4895-4896).
⚠️ No lock, but sequential in practice
The main loop runs nodes sequentially. No race. If nodes were ever run in parallel (concurrent branches), += is not atomic. Two nearly-simultaneous callbacks could lose a write.
🔧 Identical pattern in 1.5
Same technique as onMutateObjectCallerData (step 1.5-E) and onMutateSchema. The closure captures a let variable and allows outside mutation without passing an object reference.
C runLogProcessId cascade (4 sources)
flux.service.ts:2329-2330
const runLogProcessId = execId ?? injectedRunLogCollector?.processId ?? parentProcessId ?? uuid();
Purpose. Picks the canonical execution ID. This ID shows up in WebSocket, SpaceRunLog, cancel FeatureFlags, prefetch, and cross-run cache. The cascade has 4 levels. Whoever already has an ID (external execId, injected collector, parent) reuses it. Otherwise, generates a new UUID.
In short. Every execution needs a protocol number. The order matters a lot. First, if execId came from outside (a scheduled execution or a Temporal workflow that already named the run), that value wins. Second, if the execution is nested with an injectedRunLogCollector already in use, it inherits the collector's processId. That way the parent's SpaceRunLog gathers everything together. Third, if parentProcessId came in (flow-caller-node chaining executions), it reuses that value. Fourth and last, if nothing came in, the backend generates a new uuid(). The resulting ID is the key across every downstream component: chatbotSocketByRun, runCancellationService, the Mongo run log, and the dashboard. Swapping the order breaks parent-child correlation for flow-caller.
🪜 Resolution cascade (first non-null wins)
1 execId present (Temporal or scheduled execution) use execId
2 injectedRunLogCollector?.processId present (nested execution with parent collector) use collector.processId
3 parentProcessId present (flow-caller-node) use parentProcessId
4 none of the above new uuid()

🎯 Why 4 sources?
Each source covers a different scenario.
execId. The caller already has an ID (Temporal replay-safe).
injectedRunLogCollector.processId. A nested execution should become an entry inside the parent's log.
parentProcessId. Legacy pre-collector path. Still used by flow-caller.
uuid(). Top-level execution with no pre-defined value.
📎 execId versus runLogProcessId
When execId is filled in, runLogProcessId === execId. In every other case, they differ. Many downstream places treat runLogProcessId as the effective execId.
⚠️ Nullish coalescing (??), not falsy
Uses ??, not ||. An empty string '' would pass as present through ??, but would be discarded by ||. Since every value here is a UUID when present, the difference does not matter in practice.
🔧 uuid() from the 'uuid' module
import { v4 as uuid } from 'uuid' (v4 random). Returns a string like 'a1b2c3d4-...'. Practical collision is zero.
D chatbotSocketByRun.set (gated)
flux.service.ts:2331-2333
if (socketId) { this.chatbotSocketByRun.set(runLogProcessId, socketId); }
Purpose. Registers the runLogProcessId → socketId mapping on an instance Map. This lets any code that knows the runId (for example executeNodeViaTemporal) find the browser socket. The socket receives progressive events (streaming, node-started, cancel).
In short. It works as the chatbot's address book. Before any node runs, the backend notes that that runId is being followed by that socket. Without this note, Temporal handlers run in async context without knowing who originated the call. They would not be able to send events back to the user's screen. The if (socketId) gate matters. Only the chatbot sends socketId. API, webhook, or cronjob executions pass undefined and nothing is registered. Cleanup does not happen here. It happens in apiV2's finally block (step 5.3, lines 5427-5429). If an execution fails before reaching finally, the entry leaks into the Map. It is a slow leak that piles up over days.

⚠️ Leak on failure before finally
If anything between line 2333 and the finally throws an exception that escapes the main try/catch (rare but possible), the Map ends up with an orphan entry. An example is a throw before the try.

In practice it has never happened. Everything relevant sits inside the try. It is a risk if some refactor moves the setup before the try.
📎 Why a Map and not Redis?
The socket handshake is local. The client talks to that specific pod via WebSocket. Sockets do not migrate between pods. The local Map is enough and avoids a round-trip.
🔧 socketId format
Opaque string from the gateway (Socket.io). It is Socket.io's internal format. The backend only proxies it to locate the connected client.
E isNestedRunLog flag
flux.service.ts:2337
const isNestedRunLog = !!injectedRunLogCollector;
Purpose. Marks whether this execution is a sub-execution called by another flow (flow-caller-node) that arrived with an active parent RunLogCollector. Instead of flushing its own SpaceRunLog, the nested execution should append nodes to the injected collector. The parent will do the flush.
In short. When an execution is the child of another (flow-caller-node fires a sub-flow), the parent passes its RunLogCollector in injectedRunLogCollector. This flag simplifies the decision at several points. If isNestedRunLog is true, the child execution should skip several operations that only make sense for a root execution. It should skip assertOwnerCanRunFlow (the parent already checked the billing gate), the SpaceRunLog gate log (the parent already recorded it), and the flushNow of the Mongo document (the parent will flush at the end). The flag is used in 5 places. 2409 (assertOwner gate). 2415 (log gate). 3241 (feed for cancel-watch). 4900 (skip flushNow success). 5351 (skip flushNow error). It is a classic derived boolean. Compute once, use often.
E1 Boolean derivation
!! is a coercion to pure boolean. null and undefined become false. Any object becomes true.

🎯 Semantics of "nested"
"Nested" here means called with a pre-existing collector. It is not the same as having a parent. A flow can have parentProcessId without an injected collector (legacy path). The flush gate uses this specific flag.
📎 Combined with parentProcessId
At L3241, cancel-watch uses the union isNestedRunLog || Boolean(parentProcessId). cancel-watch treats both scenarios as sub-run. A sub-run does not install its own watcher. It inherits from the parent.
⚠️ Skipping assertOwnerCanRunFlow
If a sub-flow escapes the parent's billing check (due to a bug in whoever injects the collector), the flag lets it through unchecked. It relies on the parent having already checked. Integration tests should cover this implicit contract.

Defined in src/app-api/space_run_logs/run-log-collector.ts. Has a readonly processId and methods appendNode, finalize, among others. It is the buffer that gathers nodes throughout the execution.

Notes for migration:
The whole step is pure setup. It is trivially replicable on the worker.
The runLogProcessId cascade is business-critical. Any worker must preserve exactly this order. Otherwise sub-executions lose correlation with the parent.
The chatbotSocketByRun Map does not go to the worker. Sockets are local to the backend pod. On the worker, streaming would have to leave via callback or API to the backend. The backend would proxy to the socket.
onUpdateTokens is apiV2's most critical closure pattern. It does not migrate 1-to-1 to the worker. On the worker, each activity would need to write tokens into a table. The backend reads at the end. That is already the pattern of tokenTransactionService.sumChargesByExecution (see flux.service.ts:696).
isNestedRunLog depends on the collector being injected. On the worker, that becomes a start-args parameter.
It is essential and trivial. It is the migration's lowest risk. It only requires the discipline to keep the same cascade.

Passo 1.0a — Setup inicial pré-tudo

Bloco em flux.service.ts:2319-2337. As primeiras 19 linhas do apiV2(). Executadas antes de qualquer query, guard ou try/catch. Estabiliza sessionId. Cria os contadores de billing. Resolve o runLogProcessId canônico. Conecta o lookup socket→execução para o chatbot.
Em resumo — o que esse passo faz
  • Normaliza o sessionId. Um ?.trim() defensivo. String com espaços, undefined ou null viram string vazia. Isso importa depois. A condição sessionId === '' tem semântica especial. O passo 1.5 usa 'default' quando o flow tem fluxObject.chat.
  • Inicializa os contadores. Declara totalTokensUsed e totalCost como zero. Cria o closure onUpdateTokens(t, c) que soma nesses contadores. Esse callback é passado adiante. É a única forma de o billing encontrar os contadores dessa execução.
  • Decide o ID da execução. Cascata em 4 fontes na ordem execId → injectedRunLogCollector.processId → parentProcessId → uuid(). É o número de processo usado como chave em todos os serviços. Aparece em WebSocket, run logs de space e feature flags de cancelamento.
  • Registra o socket do chatbot. Se veio socketId, executa chatbotSocketByRun.set(runLogProcessId, socketId) num Map da classe. Isso permite que o worker devolva eventos ao browser correto mesmo quando o handoff é assíncrono. A limpeza ocorre apenas no passo 5.3, no bloco finally.
  • Define isNestedRunLog. Flag booleana derivada de !!injectedRunLogCollector. Diferencia uma execução raiz, que grava o próprio SpaceRunLog, de uma execução aninhada chamada por outro flow. A execução aninhada deve anexar ao coletor do pai em vez de gravar sozinha.
Contexto. Essas 19 linhas não fazem I/O. Não lançam exceção. Não têm try/catch. É puro setup em memória. O objetivo é dar às fases seguintes um contexto estável e imutável (contadores, IDs, refs) antes de qualquer operação que possa falhar.
Cadeia de setup em 1.0a

Resultado final. Estado inicial imutável. Inclui sessionId, contadores mais o closure, runLogProcessId, o lookup de socket e a flag isNestedRunLog.
A Trim defensivo do sessionId
flux.service.ts:2319
const sessionId = untrimmedSessionId?.trim() || '';
Propósito. Normaliza o sessionId recebido do controller. Espaços em branco, undefined, null e string vazia. Todos viram ''. A convenção define que sessionId vazio equivale a sem sessão. Essa linha garante que todos os passos leem o mesmo valor.
Em resumo. Este bloco funciona como um filtro de entrada. O parâmetro cru chega com nome longo (untrimmedSessionId). O nome deixa claro que o valor ainda não está pronto para uso. A linha faz o encaixe seguro. Se veio texto, remove as bordas. Se veio null ou undefined, o optional chaining pula e o || '' aplica o default. A partir desta linha, o restante do código lê sessionId sem se preocupar com whitespace, null-check ou tipo. O valor é sempre string. O caso ' '.trim() === '' também vira vazio. Whitespace-only é tratado como "sem sessão", não como sessão nomeada " ".

B Contadores + closure onUpdateTokens
flux.service.ts:2321-2327
let totalTokensUsed = 0;
let totalCost = 0;
const onUpdateTokens = (tokensUsed, cost) => { totalTokensUsed += tokensUsed; totalCost += cost; };
Propósito. Cria os acumuladores de billing da execução. Contadores mutáveis (let) e um closure que os incrementa. É o único mecanismo pelo qual provedores de AI, execuções de node no worker e sub-flows conseguem acumular tokens e custos no total da execução.
Em resumo. Dois contadores começam em zero. Somam conforme os nós executam e consomem AI. Quem precisa somar não recebe referência aos números. JavaScript não passa number por referência. Recebe o closure onUpdateTokens. É uma função pequena que sabe onde os contadores moram e faz o incremento. Esse padrão viabiliza o billing distribuído. O worker executa um LLM, chama onUpdateTokens(t, c) e os totais no backend crescem sem round-trip. No final, os totais alimentam flowLogsService.createLog (passo 4.3) e SpaceRunLog.finalize (passo 4.4).
B1 Declarações mutáveis
Ambos let. Ambos zero. O closure captura por referência de escopo. Cada += muta a variável do escopo pai.

🎯 Por que closure e não objeto?
Um { tokens, cost } passado por referência teria o mesmo efeito. O callback esconde a estrutura. O consumidor só sabe chamar a função com (t, c). É isolamento simples que não vaza detalhes internos.
📎 Destino final dos totais
totalTokensUsed e totalCost viram spent_tokens e cost no FlowLog (flux.service.ts:4873-4874). E viram totalTokens e totalCost no SpaceRunLog (flux.service.ts:4895-4896).
⚠️ Sem lock, mas sequencial na prática
O loop principal executa nós sequencialmente. Não há race. Se um dia executar nós em paralelo (branches concorrentes), += não é atômico. Dois callbacks quase simultâneos podem perder um write.
🔧 Padrão idêntico em 1.5
Mesma técnica de onMutateObjectCallerData (passo 1.5-E) e onMutateSchema. O closure captura variável let e permite mutação de fora sem passar referência de objeto.
C Cascata do runLogProcessId (4 fontes)
flux.service.ts:2329-2330
const runLogProcessId = execId ?? injectedRunLogCollector?.processId ?? parentProcessId ?? uuid();
Propósito. Elege o ID canônico da execução. Esse ID aparece em WebSocket, SpaceRunLog, FeatureFlags de cancel, prefetch e cross-run cache. A cascata tem 4 níveis. Quem já tem ID (execId externo, coletor injetado, parent) reutiliza. Caso contrário, gera UUID novo.
Em resumo. Toda execução precisa de um número de protocolo. A ordem importa muito. Primeiro, se veio execId de fora (uma execução programada ou um Temporal workflow que já batizou a execução), respeita esse valor. Segundo, se a execução é aninhada com um injectedRunLogCollector já em uso, herda o processId dele. Assim o SpaceRunLog do pai coleta tudo junto. Terceiro, se veio parentProcessId (flow-caller-node encadeando execuções), reusa esse valor. Quarto e último, se nada veio, o backend gera um uuid() novo. O ID resultante é a chave de todos os componentes seguintes: chatbotSocketByRun, runCancellationService, o run log no Mongo e o dashboard. Trocar a ordem quebra correlação entre pai e filho em flow-caller.
🪜 Cascata de resolução (primeiro não nulo ganha)
1 execId presente (Temporal ou execução programada) usa execId
2 injectedRunLogCollector?.processId presente (execução aninhada com collector do pai) usa collector.processId
3 parentProcessId presente (flow-caller-node) usa parentProcessId
4 nenhum dos anteriores uuid() novo

🎯 Por que 4 fontes?
Cada fonte cobre um cenário diferente.
execId. Quem chamou já tem ID (Temporal replay-safe).
injectedRunLogCollector.processId. Execução aninhada deve virar entrada dentro do log do pai.
parentProcessId. Caminho legacy pré-collector. Ainda usa flow-caller.
uuid(). Execução top-level sem valor pré-definido.
📎 execId versus runLogProcessId
Quando execId vem preenchido, runLogProcessId === execId. Nos outros casos, são desiguais. Vários locais downstream tratam runLogProcessId como o execId de fato.
⚠️ Nullish coalescing (??), não falsy
Usa ??, não ||. String vazia '' passaria como presente pelo ??, mas seria descartada por ||. Como todos os valores aqui são UUIDs quando presentes, a diferença não importa na prática.
🔧 uuid() a partir do módulo 'uuid'
import { v4 as uuid } from 'uuid' (v4 random). Retorna string do tipo 'a1b2c3d4-...'. Colisão prática é zero.
D chatbotSocketByRun.set (com gate)
flux.service.ts:2331-2333
if (socketId) { this.chatbotSocketByRun.set(runLogProcessId, socketId); }
Propósito. Registra a associação runLogProcessId → socketId num Map de instância. Isso permite que qualquer código que sabe o runId (por exemplo executeNodeViaTemporal) descubra o socket do browser. O socket recebe eventos progressivos (streaming, node-started, cancel).
Em resumo. Funciona como o livro de endereços do chatbot. Antes de qualquer node executar, o backend anota que aquele runId está sendo acompanhado por aquele socket. Sem essa anotação, os handlers do Temporal rodam em contexto assíncrono sem saber quem originou a chamada. Não conseguiriam enviar eventos de volta à tela do usuário. O gate if (socketId) importa. Só o chatbot manda socketId. Execuções via API, webhook ou cronjob passam undefined e nada é registrado. A limpeza não acontece aqui. Ocorre no bloco finally do apiV2 (passo 5.3, linha 5427-5429). Se uma execução falhar antes de chegar no finally, a entrada vaza no Map. É um leak lento acumulado ao longo de dias.

⚠️ Leak em falha antes do finally
Se algo entre a linha 2333 e o finally lançar uma exceção que escape do try/catch principal (raro mas possível), o Map fica com entrada órfã. Um exemplo é um throw antes do try.

📎 Por que Map e não Redis?
O socket handshake é local. O cliente conversa com esse pod específico via WebSocket. Sockets não migram entre pods. O Map local basta e evita round-trip.
🔧 Formato do socketId
String opaca vinda do gateway (Socket.io). É o formato interno do Socket.io. O backend só faz proxy dela para localizar o cliente conectado.
E isNestedRunLog flag
flux.service.ts:2337
const isNestedRunLog = !!injectedRunLogCollector;
Propósito. Marca se esta execução é uma sub-execução chamada por outro flow (flow-caller-node) que já veio com um RunLogCollector ativo do pai. Em vez de fazer flush do próprio SpaceRunLog, a execução aninhada deve anexar nós no coletor injetado. O pai fará o flush.
Em resumo. Quando uma execução é filha de outra (flow-caller-node dispara um sub-flow), o pai passa seu RunLogCollector em injectedRunLogCollector. Essa flag simplifica a decisão em vários pontos. Se isNestedRunLog for true, a execução filha deve pular várias operações que só fazem sentido para uma execução raiz. Deve pular assertOwnerCanRunFlow (o billing gate já foi checado pelo pai), o log de gate do SpaceRunLog (pai já registrou) e o flushNow do documento no Mongo (o pai fará o flush no final). A flag é usada em 5 lugares. 2409 (gate assertOwner). 2415 (gate log). 3241 (feed para cancel-watch). 4900 (skip flushNow success). 5351 (skip flushNow error). É um boolean derivativo clássico. Computa uma vez, usa muito.
E1 Derivação booleana
!! é coerção para boolean puro. null e undefined viram false. Qualquer objeto vira true.

🎯 Semântica de "nested"
"Nested" aqui significa chamado com um coletor pré-existente. Não é o mesmo que ter parent. Um flow pode ter parentProcessId sem coletor injetado (caminho legacy). O gate de flush usa essa flag específica.
📎 Combinado com parentProcessId
Em L3241, o cancel-watch usa a união isNestedRunLog || Boolean(parentProcessId). O cancel-watch trata os dois cenários como sub-run. A sub-run não instala o próprio watcher. Herda do pai.
⚠️ Skip do assertOwnerCanRunFlow
Se um sub-flow escapar do billing check do pai (por bug em quem injeta o collector), a flag deixa passar direto sem checar. Depende de o pai já ter checado. Testes de integração devem cobrir esse contrato implícito.
🔧 Classe RunLogCollector
Definida em src/app-api/space_run_logs/run-log-collector.ts. Tem processId readonly e métodos appendNode, finalize, entre outros. É o buffer que junta nós ao longo da execução.

Observações para migração:
Todo o passo é puro setup. É trivialmente replicável no worker.
A cascata do runLogProcessId é business-critical. Qualquer worker precisa preservar exatamente essa ordem. Caso contrário, sub-execuções perdem correlação com o pai.
O chatbotSocketByRun Map não vai para o worker. Sockets são locais ao pod do backend. No worker, o streaming teria que sair via callback ou API para o backend. O backend faria o proxy para o socket.
onUpdateTokens é o padrão de closure mais crítico do apiV2. Não migra 1 para 1 para o worker. No worker, cada activity teria que gravar tokens numa tabela. O backend lê no final. Esse já é o padrão de tokenTransactionService.sumChargesByExecution (ver flux.service.ts:696).
isNestedRunLog depende de o collector ser injetado. No worker, isso vira parâmetro de start-args.
É essencial e trivial. É o menor risco da migração. Requer apenas disciplina para manter a mesma cascata.

Passo 1.1b — Chamadores internos da fila (fire-and-forget)

Dois nós dentro do próprio flux.service.ts — flowCallerNode (linhas 5593-5660) e libraryNode (linhas 5960-6026) — podem disparar a fila do 1.1 em vez de rodar o sub-flow inline. É controlado pela flag executionMode do caller: 'triggerOnly' vai pra fila, 'returnAfterFlow' (default) roda síncrono.
Em resumo — o que esse passo faz
  • Uma flag no nó decide o caminho: callerData.executionMode (ou libraryCallerData.executionMode pro library-node). Default 'returnAfterFlow' — roda o sub-flow inline. Quando o usuário marca 'triggerOnly', o nó só dispara e segue em frente sem esperar resultado.
  • Fire-and-forget de verdade: a chamada this.apiV2Queue.enqueueApiV2Job(...) não é await-ed — vai .catch(...) só pra logar. O nó considera o disparo bem-sucedido no exato momento em que o Redis aceitou o job. O resultado do sub-flow nunca volta pra esse run.
  • Nó marca próprio estado como "enqueued": depois do disparo, addConnectToNodes atualiza o nó com { triggerStatus: 'enqueued', triggerMessage, lastTriggeredAt }. O usuário vê "enfileirado" no editor — não vê output porque não teve.
  • runType prefixado indica origem: 'flow-caller-node (trigger-only) - flowId: X' ou 'library-node (trigger-only) - flowId: X'. O runType do trigger-only não é o mesmo do síncrono — dá pra filtrar em logs qual caminho o run veio.
  • Caminho síncrono é distinto: quando executionMode !== 'triggerOnly', o nó não passa pela fila — chama this.apiV2(...) direto (via nodeCancelContext.run), passando parentProcessId, parentCancelRunKey e injectedRunLogCollector. Isso mantém o run como um só, com run-log unificado e cancelamento propagado.
  • Assimetria library vs flow-caller: o libraryNode passa billingFlowId no payload (cobrança direcionada); o flowCallerNode não.
Contexto: esses dois nós são os únicos pontos dentro do próprio motor de execução (Fase 3) que voltam a chamar a fila — todos os outros disparos externos vêm de endpoints REST ou MCP. É recursão indireta: o run pai passa por apiV2, dentro dele o handler de flowCallerNode chama a fila api-v2 de novo, que roda outro apiV2 completo (o filho).

A gate executionMode === 'triggerOnly'
flux.service.ts:5574 · 5593 · 5957 · 5960
const executionMode = callerData?.executionMode || 'returnAfterFlow';
Propósito: Decide, dentro do handler de cada nó, se vai enfileirar (trigger-only, fire-and-forget) ou rodar inline (síncrono, com output incorporado no pai). Default é síncrono.
Em resumo: essa parte é o seletor de trilho. Antes de sair chamando qualquer coisa, o handler lê a configuração que o usuário colocou no nó: callerData.executionMode pro flow-caller ou libraryCallerData.executionMode pro library. Se veio a string 'triggerOnly', o handler segue pro trilho da fila (fire-and-forget). Se veio qualquer outra coisa (ou nada), cai no default 'returnAfterFlow' e roda inline. Os defaults são idênticos nos dois nós; a diferença é só qual objeto tem a config. Note que não tem enum — é comparação de string. Se alguém digitar 'trigger_only' ou 'triggeronly', cai no default e vira síncrono sem avisar — bug latente do frontend precisar mandar exatamente 'triggerOnly'.

🎯 Default seguro

⚠️ String literal sem enum

'returnAfterFlow' — espera o sub-flow, usa output no pai

Propósito: Dispara execução assíncrona do sub-flow chamado pelo flowCallerNode. O run atual não espera; o nó é marcado como enqueued e o handler retorna imediatamente.
Em resumo: essa parte é o disparador do flowCaller. ⚠️ O .catch() só loga — falha invisível pro usuário
Se o Redis estiver fora ou o Bull rejeitar o add (ex.: duplicate jobId ativo), o .catch() escreve um log e a promise morre. O nó vira triggerStatus: 'enqueued' mesmo se o enfileiramento falhou — porque o marcaStatus roda antes do .catch resolver. Usuário vê "enfileirado" mesmo quando não foi.

Sequência real: enqueue(...) começa (retorna Promise), depois addConnectToNodes roda sync marcando enqueued, depois o handler retorna, e só então — em outra tick do event loop — a Promise resolve/reject.
📎 Sem parentProcessId no payload
Diferente do caminho síncrono (fn D), a chamada fire-and-forget não passa parentProcessId. O run filho vira um "run raiz" — não é conectado ao run pai no run-log. Rastreabilidade de árvore quebra aqui.
🎯 runType como marcador
`flow-caller-node (trigger-only) - flowId: X` — string livre, sem enum. Consumido por dashboards e queries de log. Se mudar o texto, alertas quebram.
🔧 body enviado ao filho
{ variableInputs, webhook, spaceId } — variableInputs tem { inputId, inputText, links, files, isExtraction, typeOCR }. É o payload de entrada do filho — vai virar body no apiV2 dele.
C libraryNode — fire-and-forget
flux.service.ts:5960-6004
this.apiV2Queue.enqueueApiV2Job({ params: {..., billingFlowId} }).catch(...)
Propósito: Igual a (B), mas pro libraryNode — que roda flows da biblioteca (mesa) do usuário. Diferença crítica: passa billingFlowId pra separar cobrança do flow instalado vs flow original.
Em resumo: essa é a versão biblioteca do disparador. O padrão é praticamente idêntico ao do flow-caller: enqueue(...).catch(logger), marca o nó como enqueued, retorna. A grande diferença está numa linha só: o payload inclui billingFlowId: billingFlowIdForExecution. Isso resolve um problema específico de biblioteca — quando um usuário instala um flow público da biblioteca, cada execução tem dois flowIds envolvidos: o flowId real que vai rodar (a cópia do usuário) e o billingFlowId que aponta pro flow original (pra cobrança/attribuição correta). O flow-caller não tem essa complexidade porque só chama flows do próprio workspace. O runType também é diferente: 'library-node (trigger-only)' — dá pra separar em logs quantos disparos vieram de biblioteca vs quantos vieram de flow-caller normal.

🎯 billingFlowId — flow original vs cópia
Quando um user instala um flow da biblioteca (marketplace), a cópia dele ganha um novo id (flowId). Mas pra cobrança/analytics, é útil apontar pro flow "de origem" (billingFlowId). Isso permite: (1) autor original recebe créditos de execução; (2) analytics agregam por flow público, não por cópia.

Passado até o apiV2 filho, que usa na lógica de billing.
📎 triggerMessage prefixado
Library flow ${id} enqueued for execution — texto diferente do flow-caller (Flow ${id} enqueued). Ajuda o usuário no editor a distinguir de onde veio o disparo.
⚠️ Mesmo bug do .catch() silencioso
Igual ao flow-caller: se enfileirar falhar, log rola mas o nó vira enqueued. UI mente pro usuário. Aqui é ainda pior porque bibliotecas costumam ser usadas em cascata — se 10 library-nodes disparam num run e Redis cair no meio, 5 podem falhar sem sinal visual.

D caminho síncrono — nodeCancelContext.run(() => this.apiV2(...)) contraste
flux.service.ts:5645-5660 (flow-caller) · 6010-6026 (library)
await nodeCancelContext.run(undefined, () => this.apiV2({ ...body, parentProcessId, parentCancelRunKey, injectedRunLogCollector }))
Propósito: Rodar o sub-flow dentro do mesmo processo, preservando run-log unificado, cancelamento propagado e output incorporado no nó pai. É o default quando executionMode !== 'triggerOnly'.
Em resumo: aqui é a face oposta do trigger-only — tudo unificado, um run só. O handler abre um AsyncLocalStorage (nodeCancelContext.run(undefined, () => ...)) pra isolar contexto de cancelamento e chama this.apiV2(...) com await. Passa 3 coisas que o trigger-only não passa: parentProcessId (pra ligar o run filho ao pai no run-log), parentCancelRunKey (pra que cancelar o pai cancele o filho automaticamente) e injectedRunLogCollector (pra que o run-log do filho apareça como sub-run dentro do pai, não como run raiz separado). O resultado (nestedFlowResult) é usado logo depois — se falhou, marca erro no nó; se deu certo, incorpora outputs no nó pai. É o modo de execução caro mas rico: paga o custo de esperar, ganha rastreabilidade completa e cancelamento em cascata.

🎯 3 coisas que só o síncrono passa
1. parentProcessId — run-log conecta filho ao pai como sub-run
2. parentCancelRunKey — cancelamento propaga do pai pro filho automaticamente
3. injectedRunLogCollector — startFlowCallerSubRun/startLibrarySubRun abre um coletor filho aninhado no coletor do pai

Sem isso, o filho seria um run raiz órfão.
📎 runType SEM sufixo
'flow-caller-node - flowId: X' (sem (trigger-only)). Facilita filtrar em logs: WHERE runType LIKE '%(trigger-only)%' pega só os fire-and-forget.
⚠️ nodeCancelContext.run(undefined, ...) — isolamento intencional
undefined como primeiro arg do AsyncLocalStorage.run zera qualquer contexto de cancelamento herdado — o filho começa "limpo". O cancelamento vem via parentCancelRunKey, não via herança de AsyncLocalStorage.

Resumo — o que sai de 1.1b:
• Trigger-only: novo job na fila api-v2 (com runType prefixado), nó pai atualizado com triggerStatus: 'enqueued' + triggerMessage + lastTriggeredAt, run atual continua sem esperar
• Síncrono: sub-run completo executado dentro do run pai, com run-log aninhado (startFlowCallerSubRun/startLibrarySubRun), cancelamento em cascata, output incorporado no nó pai via nestedFlowResult.message
• Assimetria: só libraryNode passa billingFlowId — flowCallerNode não
• Falha silenciosa possível no trigger-only: .catch() loga mas o nó continua marcado como enqueued
Observações para migração:
• Trigger-only e síncrono precisam ser migrados juntos. Se o worker Temporal absorver a execução mas o backend ainda chama this.apiV2(...) no caminho síncrono, todas as flags parentProcessId/parentCancelRunKey/injectedRunLogCollector deixam de existir — o worker isola cada nó, não compartilha esse contexto.
• Solução natural: quando o pai roda no Temporal, chamar sub-flow vira await workflow.executeChildWorkflow(subAgentWorkflow, ...) — que já é await-able (síncrono do ponto de vista lógico) e tem cancelamento em cascata builtin. Trigger-only vira await workflow.startChild(subAgentWorkflow, { parentClosePolicy: ABANDON }).
• Rastreabilidade: Temporal tem workflow-id relationship (parent/child) que substitui parentProcessId. Run-log aninhado (startFlowCallerSubRun) precisa ser reescrito pra usar as APIs do Temporal ou continuar no Postgres com a mesma estrutura.
• Bug do .catch() silencioso: corrigir junto — no Temporal, o start de child workflow pode falhar (workflow existe? task queue tá saudável?). Precisa propagar status real pro nó em vez de assumir 'enqueued'.
• billingFlowId continua fazendo sentido no worker — passa como argumento do workflow. Nenhum impacto arquitetural.
• Cuidado com AsyncLocalStorage: nodeCancelContext.run(undefined, ...) é padrão específico do fluxo síncrono atual. No worker Temporal, cancelamento é via CancellationScope — modelo diferente. Não tentar portar 1:1.

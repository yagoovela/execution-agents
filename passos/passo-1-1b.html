Step 1.1b — Internal queue callers (fire-and-forget)

Two nodes inside flux.service.ts itself. flowCallerNode (lines 5593-5660) and libraryNode (lines 5960-6026). Can fire the 1.1 queue instead of executing the sub-flow inline. Controlled by the caller's executionMode flag. 'triggerOnly' goes to the queue. 'returnAfterFlow' (default) executes synchronously.
In summary — what this step does
  • A flag on the node decides the path. callerData.executionMode, or libraryCallerData.executionMode for the library-node. Default 'returnAfterFlow'. Executes the sub-flow inline. When the user selects 'triggerOnly', the node just fires and moves on without waiting for a result.
  • True fire-and-forget. The this.apiV2Queue.enqueueApiV2Job(...) call is not awaited. It uses .catch(...) only to log. The node considers the dispatch successful the moment Redis accepts the job. The sub-flow result never comes back to this execution.
  • Node marks its own state as "enqueued". After the dispatch, addConnectToNodes updates the node with { triggerStatus: 'enqueued', triggerMessage, lastTriggeredAt }. The user sees "enqueued" in the editor. No output shown because there wasn't one.
  • Prefixed runType indicates origin. 'flow-caller-node (trigger-only) - flowId: X' or 'library-node (trigger-only) - flowId: X'. The trigger-only runType is not the same as the synchronous one. Allows filtering logs by path.
  • Synchronous path is distinct. When executionMode !== 'triggerOnly', the node doesn't go through the queue. It calls this.apiV2(...) directly via nodeCancelContext.run. Passes parentProcessId, parentCancelRunKey and injectedRunLogCollector. Keeps the execution as one. With unified run log and propagated cancellation.
  • Library versus flow-caller asymmetry. The libraryNode passes billingFlowId in the payload (targeted billing). The flowCallerNode does not.
Context. These two nodes are the only points inside the execution engine itself (Phase 3) that call back into the queue. All other external dispatches come from REST or MCP endpoints. It's indirect recursion. The parent execution goes through apiV2. Inside it, the flowCallerNode handler calls the api-v2 queue again. This runs another full apiV2 (the child).

A gate executionMode === 'triggerOnly'
flux.service.ts:5574 · 5593 · 5957 · 5960
const executionMode = callerData?.executionMode || 'returnAfterFlow';
Purpose. Decides, inside each node's handler, whether to enqueue (trigger-only, fire-and-forget) or execute inline (synchronous, with output incorporated into the parent). The default is synchronous.
In summary. Before calling anything, the handler reads the config the user set on the node. callerData.executionMode for the flow-caller. libraryCallerData.executionMode for the library. If the string 'triggerOnly' came through, it follows the queue rail (fire-and-forget). If anything else came (or nothing), it falls into the default 'returnAfterFlow' and executes inline. Defaults are identical on both nodes. The only difference is which object holds the config. There's no enum. It's a string comparison. If someone types 'trigger_only' or 'triggeronly', it silently falls to the default and becomes synchronous. It's a latent bug. The frontend must send exactly 'triggerOnly'.

🎯 Safe default
|| 'returnAfterFlow'. If the config came undefined, null or an empty string, the default applies. Preserves backward compatibility. Flows saved before the flag existed continue executing synchronously.
⚠️ String literal without enum
Exact comparison with 'triggerOnly'. There's no validation, TypeScript type or enum protecting it. If a refactor renames it to 'fireAndForget', all old flows with 'triggerOnly' silently become synchronous.
🔧 Option names in the UI
'triggerOnly'. Fire and forget.
'returnAfterFlow'. Waits for the sub-flow and uses the output in the parent.

There's no third value in the current code. If one appears, it falls to the default.

this.apiV2Queue.enqueueApiV2Job({ params: {...} }).catch(error => logger.error(...))
Purpose. Dispatches asynchronous execution of the sub-flow called by flowCallerNode. The current execution does not wait. The node is marked as enqueued and the handler returns immediately.
In summary. The handler builds the body with variableInputs, webhook and spaceId. Builds params with the selected flow, user, session and counters. Calls enqueueApiV2Job without await. Intentional. The pattern is .enqueue(...).catch(...). If enqueuing fails (Redis down, Bull stuck), the .catch just logs the error and the promise dies. The parent node moves on as if everything went well. The runType sent to the queue is 'flow-caller-node (trigger-only) - flowId: X'. Enables tracking execution origin in logs. After dispatch, the handler updates the node in the schema with triggerStatus: 'enqueued', a descriptive message and the timestamp. The editor shows the status to the user.

⚠️ The .catch() only logs. Failure invisible to the user
If Redis is down or Bull rejects the add (e.g., duplicate active jobId), .catch() writes a log and the promise dies. The node ends up with triggerStatus: 'enqueued' even when the enqueuing failed. The status marking runs before .catch resolves. The user sees "enqueued" even when it wasn't.

Real sequence. enqueue(...) starts (returns Promise). Then, addConnectToNodes runs synchronously marking enqueued. The handler returns. Only then, on another event loop tick, does the Promise resolve or reject.
📎 No parentProcessId in the payload
Unlike the synchronous path (fn D), the fire-and-forget call does not pass parentProcessId. The child execution becomes a root execution. It is not connected to the parent execution in the run log. Tree traceability breaks here.
🎯 runType as a marker
`flow-caller-node (trigger-only) - flowId: X`. Free string, no enum. Consumed by dashboards and log queries. If the text changes, alerts break.
🔧 body sent to the child
{ variableInputs, webhook, spaceId }. variableInputs has { inputId, inputText, links, files, isExtraction, typeOCR }. It's the child's input payload. Becomes body in its apiV2.
C libraryNode. fire-and-forget
flux.service.ts:5960-6004
this.apiV2Queue.enqueueApiV2Job({ params: {..., billingFlowId} }).catch(...)
Purpose. Same as (B), but for libraryNode. Executes flows from the user's library. Critical difference. Passes billingFlowId to separate billing of the installed flow versus the original flow.
In summary. It's the library version of the dispatcher. The pattern is practically identical to the flow-caller's. enqueue(...).catch(logger). Marks the node as enqueued and returns. The big difference is in a single line. The payload includes billingFlowId: billingFlowIdForExecution. Solves a library-specific problem. When a user installs a public flow from the library, each execution involves two flowIds. The actual flowId that will execute (the user's copy) and the billingFlowId pointing to the original flow (for correct billing and attribution). The flow-caller doesn't have this complexity. It only calls flows from its own workspace. The runType is also different. 'library-node (trigger-only)'. Allows separating in logs how many dispatches came from library and how many came from normal flow-caller.

🎯 billingFlowId. Original flow versus copy
When a user installs a flow from the library (marketplace), the copy receives a new id (flowId). For billing and analytics, it's useful to point to the source flow (billingFlowId). Enables two effects. The original author receives execution credits. Analytics aggregate by public flow, not by copy.

Passed through to the child apiV2, which uses it in the billing logic.
📎 Prefixed triggerMessage
Library flow ${id} enqueued for execution. Different text from flow-caller (Flow ${id} enqueued). Helps the user in the editor distinguish the origin of the dispatch.
⚠️ Same silent .catch() bug
Same as flow-caller. If enqueuing fails, the log is recorded, but the node becomes enqueued. The UI lies to the user. It's even worse here. Libraries are usually used in cascade. If 10 library-nodes fire in one execution and Redis drops in the middle, 5 can fail without visual signal.
🔧 buildClearedLibraryOutputs
There's a subtle difference in the synchronous library error path (fn D, contrast). It uses buildClearedLibraryOutputs(staleLibraryNode?.data) to clear previous outputs. Not applicable in trigger-only because there was never output to clear.
D synchronous path. nodeCancelContext.run(() => this.apiV2(...)) contrast
flux.service.ts:5645-5660 (flow-caller) · 6010-6026 (library)
await nodeCancelContext.run(undefined, () => this.apiV2({ ...body, parentProcessId, parentCancelRunKey, injectedRunLogCollector }))
Purpose. Execute the sub-flow within the same process. Preserves unified run log, propagated cancellation and output incorporated into the parent node. Default when executionMode !== 'triggerOnly'.
In summary. This is the opposite face of trigger-only. Everything unified. A single execution. The handler opens an AsyncLocalStorage (nodeCancelContext.run(undefined, () => ...)) to isolate cancellation context and calls this.apiV2(...) with await. Passes 3 things trigger-only doesn't. parentProcessId to link the child execution to the parent in the run log. parentCancelRunKey so that cancelling the parent automatically cancels the child. injectedRunLogCollector so that the child's run log appears as a sub-run inside the parent, not as a separate root execution. The result (nestedFlowResult) is used right after. If it failed, marks error on the node. If it succeeded, incorporates outputs into the parent node. It's the expensive but rich execution mode. Pays the cost of waiting. Gains complete traceability and cascade cancellation.

🎯 3 things only the synchronous passes
1. parentProcessId. The run log connects the child execution to the parent as a sub-run.
2. parentCancelRunKey. Cancellation propagates from parent to child automatically.
3. injectedRunLogCollector. startFlowCallerSubRun and startLibrarySubRun open a child collector nested inside the parent's collector.

Without this, the child would be an orphan root execution.
📎 runType without suffix
'flow-caller-node - flowId: X' (without (trigger-only)). Makes log filtering easier. WHERE runType LIKE '%(trigger-only)%' catches only the fire-and-forget.
⚠️ nodeCancelContext.run(undefined, ...). Intentional isolation
undefined as the first argument to AsyncLocalStorage.run zeroes out any inherited cancellation context. The child starts clean. Cancellation comes via parentCancelRunKey, not via AsyncLocalStorage inheritance.

Summary. What comes out of 1.1b:
Trigger-only. New job on the api-v2 queue (with prefixed runType). Parent node updated with triggerStatus: 'enqueued' plus triggerMessage and lastTriggeredAt. The current execution continues without waiting.
Synchronous. Full sub-run executed inside the parent execution, with nested run log (startFlowCallerSubRun or startLibrarySubRun). Cascade cancellation. Output incorporated into the parent node via nestedFlowResult.message.
Asymmetry. Only libraryNode passes billingFlowId. flowCallerNode does not.
Possible silent failure in trigger-only. .catch() logs, but the node remains marked as enqueued.
Migration notes:
Trigger-only and synchronous need to be migrated together. If the Temporal worker absorbs the execution, but the backend still calls this.apiV2(...) on the synchronous path, all the parentProcessId, parentCancelRunKey and injectedRunLogCollector flags cease to exist. The worker isolates each node. It doesn't share that context.
Natural solution. When the parent runs in Temporal, calling a sub-flow becomes await workflow.executeChildWorkflow(subAgentWorkflow, ...). It's already await-able (logically synchronous) and has built-in cascade cancellation. Trigger-only becomes await workflow.startChild(subAgentWorkflow, { parentClosePolicy: ABANDON }).
Traceability. Temporal has a workflow-id relationship (parent/child) that replaces parentProcessId. The nested run log (startFlowCallerSubRun) needs to be rewritten to use Temporal APIs or continue in Postgres with the same structure.
Silent .catch() bug. Fix together. In Temporal, starting a child workflow can fail (does the workflow exist? is the task queue healthy?). Real status must be propagated to the node instead of assuming enqueued.
billingFlowId still makes sense in the worker. It's passed as a workflow argument. No architectural impact.
Careful with AsyncLocalStorage. nodeCancelContext.run(undefined, ...) is a specific pattern of the current synchronous flow. In the Temporal worker, cancellation is via CancellationScope. It's a different model. Don't try to port 1-to-1.

Passo 1.1b — Chamadores internos da fila (fire-and-forget)

Dois nós dentro do próprio flux.service.ts. flowCallerNode (linhas 5593-5660) e libraryNode (linhas 5960-6026). Podem disparar a fila do 1.1 em vez de executar o sub-flow inline. É controlado pela flag executionMode do caller. 'triggerOnly' vai para a fila. 'returnAfterFlow' (default) executa síncrono.
Em resumo — o que esse passo faz
  • Uma flag no nó decide o caminho. callerData.executionMode, ou libraryCallerData.executionMode para o library-node. Default 'returnAfterFlow'. Executa o sub-flow inline. Quando o usuário marca 'triggerOnly', o nó só dispara e segue em frente sem aguardar resultado.
  • Fire-and-forget de fato. A chamada this.apiV2Queue.enqueueApiV2Job(...) não é aguardada. Usa .catch(...) só para registrar log. O nó considera o disparo bem-sucedido no momento em que o Redis aceitou o job. O resultado do sub-flow nunca volta para essa execução.
  • Nó marca o próprio estado como "enqueued". Depois do disparo, addConnectToNodes atualiza o nó com { triggerStatus: 'enqueued', triggerMessage, lastTriggeredAt }. O usuário vê "enfileirado" no editor. Não vê output porque não houve.
  • runType prefixado indica origem. 'flow-caller-node (trigger-only) - flowId: X' ou 'library-node (trigger-only) - flowId: X'. O runType do trigger-only não é o mesmo do síncrono. Permite filtrar em logs por caminho.
  • Caminho síncrono é distinto. Quando executionMode !== 'triggerOnly', o nó não passa pela fila. Chama this.apiV2(...) direto via nodeCancelContext.run. Passa parentProcessId, parentCancelRunKey e injectedRunLogCollector. Mantém a execução como um só. Com run log unificado e cancelamento propagado.
  • Assimetria library versus flow-caller. O libraryNode passa billingFlowId no payload (cobrança direcionada). O flowCallerNode não passa.
Contexto. Esses dois nós são os únicos pontos dentro do próprio motor de execução (Fase 3) que voltam a chamar a fila. Todos os outros disparos externos vêm de endpoints REST ou MCP. É recursão indireta. A execução pai passa por apiV2. Dentro dele, o handler de flowCallerNode chama a fila api-v2 de novo. Isso executa outro apiV2 completo (o filho).

A gate executionMode === 'triggerOnly'
flux.service.ts:5574 · 5593 · 5957 · 5960
const executionMode = callerData?.executionMode || 'returnAfterFlow';
Propósito. Decide, dentro do handler de cada nó, se vai enfileirar (trigger-only, fire-and-forget) ou executar inline (síncrono, com output incorporado no pai). O default é síncrono.
Em resumo. Antes de chamar qualquer coisa, o handler lê a configuração que o usuário colocou no nó. callerData.executionMode para o flow-caller. libraryCallerData.executionMode para o library. Se veio a string 'triggerOnly', segue para o trilho da fila (fire-and-forget). Se veio qualquer outra coisa (ou nada), cai no default 'returnAfterFlow' e executa inline. Os defaults são idênticos nos dois nós. A diferença é só qual objeto tem a config. Não há enum. É comparação de string. Se alguém digitar 'trigger_only' ou 'triggeronly', cai no default e vira síncrono sem aviso. É um bug latente. O frontend precisa enviar exatamente 'triggerOnly'.

🎯 Default seguro

⚠️ String literal sem enum
Comparação exata com 'triggerOnly'. Não há validação, tipo TypeScript ou enum protegendo. Se um refactor renomear para 'fireAndForget', todos os flows antigos com 'triggerOnly' viram síncrono silenciosamente.
🔧 Nomes das opções na UI
'triggerOnly'. Dispara e esquece.
'returnAfterFlow'. Aguarda o sub-flow e usa o output no pai.

Não há um terceiro valor no código atual. Se aparecer, cai no default.
B flowCallerNode. fire-and-forget
flux.service.ts:5593-5636

Propósito. Dispara execução assíncrona do sub-flow chamado pelo flowCallerNode. A execução atual não aguarda. O nó é marcado como enqueued e o handler retorna imediatamente.
Em resumo. O handler monta o body com variableInputs, webhook e spaceId. Monta o params com o flow selecionado, user, session e contadores. Chama enqueueApiV2Job sem await. É intencional. Depois do disparo, o handler atualiza o nó no schema com triggerStatus: 'enqueued', uma mensagem descritiva e o timestamp. O editor exibe o status ao usuário.

⚠️ O .catch() só registra log. Falha invisível ao usuário
Se o Redis está fora ou o Bull rejeita o add (por exemplo, jobId duplicado ativo), o .catch() escreve um log e a promise morre. O nó fica com triggerStatus: 'enqueued' mesmo quando o enfileiramento falhou. A marcação de status roda antes do .catch resolver. O usuário vê "enfileirado" mesmo quando não foi.

Sequência real. enqueue(...) começa (retorna Promise). Em seguida, addConnectToNodes executa síncrono marcando enqueued. O handler retorna. Só então, em outra tick do event loop, a Promise resolve ou rejeita.
📎 Sem parentProcessId no payload
Diferente do caminho síncrono (fn D), a chamada fire-and-forget não passa parentProcessId. A execução filha vira uma execução raiz. Não é conectada à execução pai no run log. A rastreabilidade em árvore quebra aqui.
🎯 runType como marcador
`flow-caller-node (trigger-only) - flowId: X`. String livre, sem enum. Consumida por dashboards e queries de log. Se mudar o texto, alertas quebram.
🔧 body enviado ao filho
{ variableInputs, webhook, spaceId }. variableInputs tem { inputId, inputText, links, files, isExtraction, typeOCR }. É o payload de entrada do filho. Vira body no apiV2 dele.
C libraryNode. fire-and-forget
flux.service.ts:5960-6004
this.apiV2Queue.enqueueApiV2Job({ params: {..., billingFlowId} }).catch(...)
Propósito. Igual a (B), mas para o libraryNode. Executa flows da biblioteca do usuário. Diferença crítica. Passa billingFlowId para separar a cobrança do flow instalado versus o flow original.
Em resumo. É a versão biblioteca do disparador. O padrão é praticamente idêntico ao do flow-caller. enqueue(...).catch(logger). Marca o nó como enqueued e retorna. A grande diferença está numa linha só. O payload inclui billingFlowId: billingFlowIdForExecution. Resolve um problema específico de biblioteca. Quando um usuário instala um flow público da biblioteca, cada execução tem dois flowIds envolvidos. O flowId real que vai executar (a cópia do usuário) e o billingFlowId que aponta ao flow original (para cobrança e atribuição corretas). O flow-caller não tem essa complexidade. Só chama flows do próprio workspace. O runType também é diferente. 'library-node (trigger-only)'. Permite separar em logs quantos disparos vieram de biblioteca e quantos vieram de flow-caller normal.

D caminho síncrono. nodeCancelContext.run(() => this.apiV2(...)) contraste
flux.service.ts:5645-5660 (flow-caller) · 6010-6026 (library)
await nodeCancelContext.run(undefined, () => this.apiV2({ ...body, parentProcessId, parentCancelRunKey, injectedRunLogCollector }))
Propósito. Executar o sub-flow dentro do mesmo processo. Preserva run log unificado, cancelamento propagado e output incorporado no nó pai. É o default quando executionMode !== 'triggerOnly'.
Em resumo. Aqui é a face oposta do trigger-only. Tudo unificado. Uma execução só. O handler abre um AsyncLocalStorage (nodeCancelContext.run(undefined, () => ...)) para isolar contexto de cancelamento e chama this.apiV2(...) com await. Passa 3 coisas que o trigger-only não passa. parentProcessId para ligar a execução filha ao pai no run log. parentCancelRunKey para que cancelar o pai cancele o filho automaticamente. injectedRunLogCollector para que o run log do filho apareça como sub-run dentro do pai, e não como execução raiz separada. O resultado (nestedFlowResult) é usado logo depois. Se falhou, marca erro no nó. Se deu certo, incorpora outputs no nó pai. É o modo de execução caro, mas rico. Paga o custo de aguardar. Ganha rastreabilidade completa e cancelamento em cascata.

🎯 3 coisas que só o síncrono passa
1. parentProcessId. O run log conecta a execução filha à pai como sub-run.
2. parentCancelRunKey. O cancelamento propaga do pai para o filho automaticamente.
3. injectedRunLogCollector. startFlowCallerSubRun e startLibrarySubRun abrem um coletor filho aninhado no coletor do pai.

Sem isso, o filho seria uma execução raiz órfã.
📎 runType sem sufixo
'flow-caller-node - flowId: X' (sem (trigger-only)). Facilita filtrar em logs. WHERE runType LIKE '%(trigger-only)%' pega só os fire-and-forget.
⚠️ nodeCancelContext.run(undefined, ...). Isolamento intencional
undefined como primeiro argumento do AsyncLocalStorage.run zera qualquer contexto de cancelamento herdado. O filho começa limpo. O cancelamento vem via parentCancelRunKey, não via herança de AsyncLocalStorage.

Resumo. O que sai de 1.1b:
Trigger-only. Novo job na fila api-v2 (com runType prefixado). Nó pai atualizado com triggerStatus: 'enqueued' mais triggerMessage e lastTriggeredAt. A execução atual continua sem esperar.
Síncrono. Sub-run completo executado dentro da execução pai, com run log aninhado (startFlowCallerSubRun ou startLibrarySubRun). Cancelamento em cascata. Output incorporado no nó pai via nestedFlowResult.message.
Assimetria. Só o libraryNode passa billingFlowId. O flowCallerNode não passa.
Falha silenciosa possível no trigger-only. O .catch() registra log, mas o nó continua marcado como enqueued.
Observações para migração:
Trigger-only e síncrono precisam ser migrados juntos. Se o worker Temporal absorver a execução, mas o backend ainda chama this.apiV2(...) no caminho síncrono, todas as flags parentProcessId, parentCancelRunKey e injectedRunLogCollector deixam de existir. O worker isola cada nó. Não compartilha esse contexto.
Solução natural. Quando o pai executa no Temporal, chamar sub-flow vira await workflow.executeChildWorkflow(subAgentWorkflow, ...). Já é await-able (síncrono do ponto de vista lógico) e tem cancelamento em cascata builtin. Trigger-only vira await workflow.startChild(subAgentWorkflow, { parentClosePolicy: ABANDON }).
Rastreabilidade. O Temporal tem workflow-id relationship (parent/child) que substitui parentProcessId. O run log aninhado (startFlowCallerSubRun) precisa ser reescrito para usar as APIs do Temporal ou continuar no Postgres com a mesma estrutura.
Bug do .catch() silencioso. Corrigir em conjunto. No Temporal, o start de child workflow pode falhar (o workflow existe? a task queue está saudável?). Precisa propagar status real ao nó em vez de assumir enqueued.
billingFlowId continua fazendo sentido no worker. É passado como argumento do workflow. Nenhum impacto arquitetural.
Cuidado com AsyncLocalStorage. nodeCancelContext.run(undefined, ...) é um padrão específico do fluxo síncrono atual. No worker Temporal, cancelamento é via CancellationScope. É um modelo diferente. Não tentar portar 1 para 1.

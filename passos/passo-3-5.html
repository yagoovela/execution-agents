Passo 3.5 — Dispatch: Temporal vs Inline

Bloco em flux.service.ts:3299-4438 (grande if em cascata por node.type). Decide se o nó vai executar via processNodeViaTemporal() (worker Temporal) ou via handler inline no próprio backend. A decisão é uma cascata de checks por tipo/provider, sem tabela de rotas.
Em resumo — o que esse passo faz
  • Escolhe entre 2 caminhos por nó: ou o nó vai pro worker Temporal (processo separado, isolado) ou fica inline no próprio backend. Não há tabela nem registry — a decisão é uma cascata de ifs hardcoded por tipo (e por provider, no caso de integrações).
  • Lista VIP hardcoded no worker: isTemporalNode tem 6 tipos fixos (commandTextNode, scripting, apiCaller, mathFunction, counterNode, outputController). Se o tipo bate, sobe pro Temporal e nada mais é discutido.
  • Migração provider-a-provider pra integrações: isWorkerRoutedIntegration olha o provider do nó (stripe, slack, notion, zapier, hubspot só pull...) e roteia pro worker só se o provider estiver no Set MIGRATED_INTEGRATION_PROVIDERS. Permite migrar 1 provider por semana sem quebrar os outros.
  • Todo mundo migrado passa pelo mesmo envelope: processNodeViaTemporal resolve arrays de referência, abre row em node_executions, starta o workflow com id determinístico, bloqueia esperando resultado (síncrono!), agrega charges via sumChargesByExecution e devolve o envelope pro loop. Sem paralelismo entre irmãos.
  • ~17 handlers legacy inline pra tudo que não foi: cascata gigante de if (node.type === 'X') { await this.handlerX(...) } em ~1000 linhas do FluxService.apiV2 — desde imageGenerator, webSearch, voiceBoxNode até orquestradores estruturais (arrayNode, conditionNode, nodesBox, fluxBox) que dependem de state compartilhado com o loop.
  • Saída: nó executado por um dos 2 caminhos (ou nem — tipos passivos tipo comment/label/GLOBAL_STARTER pulam); myUpdatedNodes, myTexts e nodeSubstitutionSchema refletem output — pipeline pronto pra 3.6 (updateSchemaWithNodeOutput).
Contexto: este é o heart da execução híbrida. Cada nó cai em uma das 3 rotas: (1) Temporal — worker isolado (blocking wait no backend); (2) Inline legacy — handler no próprio backend; (3) Sem handler — tipos passivos (comment, label, group, GLOBAL_STARTER). O critério de roteamento é isTemporalNode(type) || isWorkerRoutedIntegration(processedNode). Tudo o mais cai em inline (memória [[project_execution_architecture]]).
Cadeia de decisão em 3.5
AisTemporalNode(type) → BisWorkerRoutedIntegration(node) → CisIntegrationExecutableNodeType → DprocessNodeViaTemporal (envelope) → EHandlers inline (dispatch fallback)
Resultado: nó terminou de executar de um dos dois lados. myUpdatedNodes, myTexts, nodeSubstitutionSchema foram atualizados (pra ambos os paths — mas por caminhos diferentes). O loop cai em 3.6 updateSchemaWithNodeOutput.

private isTemporalNode(type: string): boolean
Propósito: Whitelist hardcoded dos node types que por padrão vão pro worker Temporal. Não considera provider — o tipo já implica worker. É a rota "canônica" migrada.
Em resumo: é a lista VIP do worker. Um array literal com 6 nomes: commandTextNode, scripting, apiCaller, mathFunction, counterNode, outputController. Se o tipo do nó tá nessa lista, ele vai pro Temporal. Fim. Sem tabela de config, sem env var, sem registro no banco — é código hardcoded que exige deploy pra mudar. Esses 6 são os "puros" — sem estado compartilhado com o loop, sem objectCallerData, sem onMutateSchema, sem dependência do scheduler. Foram os primeiros migrados justamente por causa disso. O commandTextNode (LLM) foi o primeiro-primeiro, porque justifica o overhead de start-workflow-wait-result com a duração natural de segundos que uma chamada de LLM tem. Se você adicionar um novo tipo pro worker, precisa editar duas listas: essa aqui (pra o backend saber que deve rotear) e o switch em process-single-node.workflow.ts:78 (pra o worker saber como executar). Sincronizar duas listas é frágil — se você esquecer o worker, chega no default: throw "Node type X not supported". Sem fallback, sem retry, sem retorno inline. Fail-hard. Todos os 6 tipos VIP acabam chamando uma única função no backend (processNodeViaTemporal) — o dispatch por tipo real acontece dentro do worker.

B isWorkerRoutedIntegration(node)
shared/integration/integration-executable-node.ts:39-43
export function isWorkerRoutedIntegration(node: ThirdPartyIntegrationNodeLike | undefined): boolean
Propósito: Roteamento dependente de provider. Um mesmo type='thirdPartyIntegration' pode ir pro worker (se provider ∈ whitelist) ou ficar inline (se não). Permite migração gradual, provider por provider, sem quebrar quem ainda não migrou.
Em resumo: é a mesma ideia da lista VIP (fn A), mas por provider dentro de um tipo. Todo thirdPartyIntegration é o mesmo tipo pro backend, mas o provider (stripe, slack, notion, salesforce, klaviyo, shopify...) diz o que ele faz de fato. Migrar todos os providers de uma vez pro worker seria arriscado — cada um tem SDK próprio, autenticação própria, quirks próprios. A solução: um Set<string> com os providers migrados (MIGRATED_INTEGRATION_PROVIDERS — hoje tem stripe, wordpress, slack, notion, zapier, hubspot só pra pull). Cada semana pode entrar um novo — sem quebrar os outros. Se o provider tá no Set, roteia pro worker; se não, cai pro handler inline no backend. Um detalhe fino: recebe processedNode (não node), porque o provider poderia vir via {{...}} de outro nó (raro mas possível) — sem substitution prévia, provider dinâmico não bateria com o Set. Também tem granularidade máxima: hubspot só pull — o pull tá no worker, mas push/update ainda ficam inline. Essa granularidade fina (provider + operation) vive dentro do switch do worker, não expressa por essa função. Bom template pra isTemporalNode — que ainda é hardcoded no service.

🎯 Por que dispatch por provider é bom
Deixa migrar 1 provider por vez sem quebrar os outros. Ex: enquanto Salesforce ainda tá inline, Slack já pode ir pro worker. Se algo quebrar, é isolado por provider.

Mesmo tipo (thirdPartyIntegration) chega no worker com contract genérico — o worker resolve o provider internamente.
⚠️ Recebe processedNode, não node
isWorkerRoutedIntegration(processedNode). Isso é importante porque um provider dinâmico via {{...}} só resolve depois do passo 3.3. Sem substitution, provider viria como string com placeholder e não bateria com o Set.

Na prática, provider dinâmico é raro — mas o pattern é defensivo.
🔧 hubspot só pull
No worker, o handler de hubspot tem só pull — push/update ainda são inline. É a granularidade máxima do sistema: por (provider, operation). Não expressa nesta função — vive no switch do worker.
C isIntegrationExecutableNodeType(type)

export function isIntegrationExecutableNodeType(nodeType): nodeType is IntegrationExecutableProviderNodeType
Propósito: Type guard TS. Retorna true pra thirdPartyIntegration ou mcpNode — tipos que têm a semântica de "chama integração externa" mas cuja decisão de worker vs inline depende de isWorkerRoutedIntegration. É usado depois do dispatch pra roteear pro handler inline correto quando o provider não migrou.
Em resumo: pensa nas 3 funções assim: isTemporalNode pergunta "esse tipo está VIP?", isWorkerRoutedIntegration pergunta "esse tipo + provider está VIP?", e essa aqui pergunta só "esse é um tipo que fala com integração externa, independente de estar migrado ou não?" — retorna true pra thirdPartyIntegration ou mcpNode. É usada logo depois do isWorkerRoutedIntegration, como um else if: "ok, esse é um nó de integração mas o provider não tá migrado — pra qual handler inline eu chamo?". Aí escolhe entre thirdPartyIntegrationNode ou mcpNode (linhas 3456, 3468). Ela é secundária, complementar — o principal roteamento é o dupla worker/inline. Ela existe pra dar a granularidade do fallback correto: sem ela, o dispatcher inline não saberia qual handler chamar entre os dois. Também é o único desses 3 checks com syntax de type guard TS (: nodeType is IntegrationExecutableProviderNodeType) — depois do check, o TS narrow o tipo, permitindo o destructuring sem cast. Puro açúcar de compile-time, mas melhora legibilidade.

D processNodeViaTemporal(args)
flux.service.ts:639-738
private async processNodeViaTemporal({ node, processedNode, userId, sessionId, runId, flowId, flowVersionHistoryId, myUpdatedNodes, myTexts, nodeSubstitutionSchema, edges, onMutateSchema, objectCallerData, onUpdateTokens, ... })
Propósito: Envelope único de todas as chamadas ao worker. Faz o INSERT node_executions com input resolvido (T2), starta o workflow com workflowId determinístico (T3), bloqueia esperando resultado (T4), agrega charges via sumChargesByExecution (T6), atualiza myUpdatedNodes/myTexts/schema. Retorna esse envelope pro loop.
Em resumo: é o escritório central que despacha trabalho pro worker Temporal. Não importa se é scripting, commandTextNode, apiCaller ou qualquer outro tipo VIP — todos passam por esse mesmo envelope. Ele faz o pipeline: resolve arrays de referência (promptData/contentData) numa passada extra pra garantir que o worker receba input 100% resolvido; abre uma row em node_executions com execId=uuid() e workflowId determinístico (node-process-${nodeId}-${execId} — mesmo id em retry = idempotente); starta o workflow no Temporal server; e aí vem o ponto sensível arquitetural: backend fica travado esperando via handle.result(). É síncrono. Não tem paralelismo entre irmãos, mesmo que o scheduler tenha 3 nós prontos ao mesmo tempo. O worker escala verticalmente handlers (pode ter várias máquinas rodando o mesmo tipo em paralelo, mas o backend orquestra 1 nó por vez). Depois do worker retornar, faz SELECT em node_executions.outputData (se veio como {__claimRef}, resolve GET no S3), agrega token_transactions gravados pelo worker via sumChargesByExecution, e retorna um envelope { myUpdatedNodes, myTexts, nodeSubstitutionSchema } pra o loop reatribuir. Se algo der throw no worker, sobe direto pro try do loop e vira erro fatal do nó (passo 3.8). Não tem fallback pra inline — worker offline ou bug no handler = run inteiro bloqueado.

🎯 Blocking wait = síncrono
Cada nó Temporal custa ~150-500ms de overhead (start + wait) além do próprio trabalho. Mesmo agentes puramente Temporal-eligible perdem paralelismo — o worker poderia fazer batch, mas o backend orquestra 1 por vez.

Nesse modelo, worker é escala vertical de handlers, não paralelismo horizontal.
⚠️ Erros do worker propagam como throw
Se handle.result() lançar (workflow falhou), o throw sobe pro try do loop (3.8 — tratamento de erro por nó) que marca errorMessage/errorStatusCode no node.data e potencialmente stoppedByNodeFailure=true.

Path Temporal não tem fallback pra inline — se worker está com bug, o run inteiro fica bloqueado.
🔧 processNodeViaTemporal é chamado múltiplas vezes
No dispatch, cada tipo Temporal (scripting, commandTextNode, apiCaller, mathFunction, counter, outputController) chama processNodeViaTemporal com o mesmo shape de args. É o único hook — o worker é que faz o switch por tipo internamente (processSingleNode.workflow.ts:78).
📎 objectCallerData e onMutateSchema no path Temporal
São passados como args, mas apenas os valores atuais. O worker não pode mutar de volta — quando retorna, o backend confia no result.nodeSubstitutionSchema (worker atualiza baseado nas suas próprias regras). O padrão de closure mutation do path inline não existe aqui.
E Handlers inline (fallback dispatch)
flux.service.ts:3299-4438
Cascata de ~17 if (node.type === '...') { await this.someHandler({...}) }
Propósito: Path legacy — nós que ainda não foram migrados pro worker rodam direto no backend. Cada tipo tem seu handler dedicado no próprio FluxService (métodos privados/públicos que fazem SQL, chamam APIs externas, gravam flows_nodes.data). Padrão que causa problema de perf de FE em agentes grandes.
Em resumo: é o armário do "ainda não migrei". Se o nó não é VIP nem worker-routed, cai numa cascata gigante de if (node.type === 'X') { await this.handlerX(...) } que ocupa mais de 1000 linhas dentro de FluxService.apiV2. São ~17 branches: voiceBoxNode, imageGenerator, pullData/pushData (Google Sheets), webSearch/webCrawling, conditionNode, nodesBox, arrayNode (loop!), fluxBox/libraryNode (sub-flows), reportBuilder, audioReaderNode, commandContentNode, e mais. Cada um roda inline no processo do backend — faz chamada à API externa (ElevenLabs, Ideogram, FAL, SerpAPI...), grava flows_nodes.data com previewResponses/contentData/text gordos. Aí recordInApiNodeError fecha a row de node_executions aberta em 3.4-D. Tem 2 grupos: (1) leaf handlers — fazem trabalho simples e podem migrar pro worker em algum momento (imageGenerator, webSearch, etc.); (2) orquestradores estruturais — arrayNode, conditionNode, nodesBox, fluxBox, libraryNode — dependem de state compartilhado com o loop principal (schedState, objectCallerData, runLogCollector, closures como onMutateSchema). Esses são o boss final da migração: exigem refactor arquitetural do próprio orquestrador, não portação de handler. Também tem tipos passivos que nem caem em nenhum if: varInputNode, GLOBAL_STARTER, comment, label, group — servem só como fonte de dado ou visual, sem execução ativa.

⚠️ 17 branches sem factory
É um switch gigante em ifs empilhados dentro de FluxService.apiV2. Cada tipo novo adiciona mais uma branch. Sem registry, sem visitor pattern — pura cascata que ocupa ~1000 linhas.

Split em métodos privados é o que salva legibilidade — mas a orquestração aqui é acoplada demais pra refactor incremental.
🎯 Fallback esperado
Tipos como conditionNode, arrayNode, nodesBox, fluxBox não devem migrar tão cedo — dependem de state compartilhado com o loop (schedState, objectCallerData, runLogCollector). Migração dessas cabeças de dispatch é um refactor arquitetural, não portação de handler.

Nesse sentido, o path inline é permanente enquanto essas dependências existirem.
🔧 Tipos sem handler
varInputNode, GLOBAL_STARTER, GLOBAL_OUTPUTS, comment, label, group — não caem em nenhum if. O loop faz o schema update em 3.6 (o input já está no data desses tipos) e prossegue.

São nós "passivos" — presença no DAG mas sem execução ativa. Ex: varInputNode só serve como fonte de dado pra referências {{...}}.
Resumo — o que sai de 3.5:
• Nó rodou por um dos caminhos: Temporal (com processNodeViaTemporal em envelope síncrono) OU inline (handler direto em FluxService) OU no-op (tipos passivos)
• myUpdatedNodes, myTexts, nodeSubstitutionSchema refletem output do handler
• Path Temporal grava node_executions.outputData; path inline grava flows_nodes.data (gordo) + node_executions (row de trace)
• Loop prossegue pra 3.6 (updateSchemaWithNodeOutput) — deixa output visível pros próximos nós
Observações para migração:
• Estado atual: 2 caminhos híbridos pra evitar big-bang. Cada tipo migra individualmente conforme o worker ganha suporte. Nenhum fallback backend↔worker: se worker não tem handler, é erro fatal (throw "Node type X not supported").
• Ordem de migração recomendada: (1) providers de integração 1 por 1 via MIGRATED_INTEGRATION_PROVIDERS; (2) tipos leaf (imageGenerator, webSearch, webCrawling, pullData/pushData) — não dependem de state do loop; (3) o boss final: arrayNode, conditionNode, nodesBox, fluxBox, libraryNode — exigem refactor do próprio loop (buildSchedulerState + state pattern do worker).
• O blocking wait em processNodeViaTemporal é arquitetural. Mesmo depois de migrar tudo, se o backend continuar orquestrando, o "loop 1 nó por vez" persiste. Paralelismo real exige migrar o próprio orquestrador pro worker (via processAgent workflow — hoje um stub comentado).
• isTemporalNode hoje é hardcode. Convertê-lo num registry (config file ou tabela) permitiria toggle por env sem deploy. Melhoria fácil de tocar durante a migração.
• isWorkerRoutedIntegration já é config-friendly (Set exportável). Bom template pra isTemporalNode.
• É o coração da migração — todas as decisões arquiteturais da migração passam por aqui. Cada checkbox do plano de migração afeta essas 3 funções + o switch do worker. Documentar em detalhe é pré-requisito de qualquer refactor.

Step 3.5 — Dispatch: Temporal vs Inline

Block in flux.service.ts:3299-4438 (large cascading if by node.type). Decides whether the node will execute via processNodeViaTemporal() (Temporal worker) or via inline handler in the backend itself. The decision is a cascade of checks by type and provider, without a routing table.
In short — what this step does
  • Picks between 2 paths per node. The node either goes to the Temporal worker (separate, isolated process) or stays inline in the backend itself. There is no table or registry. The decision is a cascade of ifs hardcoded by type (and by provider, in the case of integrations).
  • VIP list hardcoded into the worker. isTemporalNode has 6 fixed types (commandTextNode, scripting, apiCaller, mathFunction, counterNode, outputController). If the type matches, it goes up to Temporal and nothing else is discussed.
  • Provider-by-provider migration for integrations. isWorkerRoutedIntegration looks at the node's provider (stripe, slack, notion, zapier, hubspot pull only...) and routes to the worker only if the provider is in the MIGRATED_INTEGRATION_PROVIDERS Set. Allows migrating 1 provider per week without breaking the others.
  • Everyone migrated goes through the same envelope. processNodeViaTemporal resolves reference arrays, opens a row in node_executions, fires the workflow with a deterministic id, blocks waiting for the result (synchronous!), aggregates charges via sumChargesByExecution and returns the envelope to the loop. No parallelism between siblings.
  • ~17 legacy inline handlers for everything that hasn't been migrated. Giant cascade of if (node.type === 'X') { await this.handlerX(...) } in ~1000 lines of FluxService.apiV2. From imageGenerator, webSearch, voiceBoxNode to structural orchestrators (arrayNode, conditionNode, nodesBox, fluxBox) that depend on state shared with the loop.
  • Output. Node executed by one of the 2 paths (or neither: passive types like comment, label, GLOBAL_STARTER skip). myUpdatedNodes, myTexts and nodeSubstitutionSchema reflect the output. Pipeline ready for 3.6 (updateSchemaWithNodeOutput).
Context. This is the heart of hybrid execution. Every node falls into one of 3 routes.
(1) Temporal: isolated worker (blocking wait in the backend).
(2) Legacy inline: handler in the backend itself.
(3) No handler: passive types (comment, label, group, GLOBAL_STARTER).
The routing criterion is isTemporalNode(type) || isWorkerRoutedIntegration(processedNode). Everything else falls into inline (memory [[project_execution_architecture]]).
Decision chain in 3.5
AisTemporalNode(type) → BisWorkerRoutedIntegration(node) → CisIntegrationExecutableNodeType → DprocessNodeViaTemporal (envelope) → EInline handlers (dispatch fallback)
Result. The node finished executing on one of the two sides. myUpdatedNodes, myTexts and nodeSubstitutionSchema were updated (for both paths, through different routes). The loop falls into 3.6 updateSchemaWithNodeOutput.
A isTemporalNode(type)
flux.service.ts:740-749
private isTemporalNode(type: string): boolean
Purpose. Hardcoded whitelist of node types that by default go to the Temporal worker. Provider is not considered. The type alone implies worker. This is the canonical migrated route.
In short. It's the worker's VIP list. A literal array with 6 names: commandTextNode, scripting, apiCaller, mathFunction, counterNode, outputController. If the node's type is on this list, it goes to Temporal. End of story. No config table, no env var, no DB record. It's hardcoded code that requires a deploy to change. These 6 are the "pure" ones. No shared state with the loop, no objectCallerData, no onMutateSchema, no dependency on the scheduler. They were the first migrated because of this. commandTextNode (LLM) was the very first. It justifies the overhead of start-workflow-wait-result with the naturally seconds-long duration of an LLM call. If a new type joins the worker, two lists need to be edited. This one (so the backend knows to route it) and the switch in process-single-node.workflow.ts:78 (so the worker knows how to execute it). Keeping two lists in sync is fragile. If you forget the worker, you hit the default: throw "Node type X not supported". No fallback, no retry, no inline return. Fail-hard. All 6 VIP types end up calling a single function in the backend (processNodeViaTemporal). The actual per-type dispatch happens inside the worker.

B isWorkerRoutedIntegration(node)
shared/integration/integration-executable-node.ts:39-43
export function isWorkerRoutedIntegration(node: ThirdPartyIntegrationNodeLike | undefined): boolean
Purpose. Provider-dependent routing. The same type='thirdPartyIntegration' can go to the worker (if provider ∈ whitelist) or stay inline (if not). Enables gradual migration, provider by provider, without breaking those not yet migrated.
In short. Same idea as the VIP list (fn A), but per provider within a type. Every thirdPartyIntegration is the same type to the backend. The provider (stripe, slack, notion, salesforce, klaviyo, shopify...) says what it actually does. Migrating all providers to the worker at once would be risky. Each has its own SDK, its own auth, its own quirks. The solution. A Set<string> with the migrated providers (MIGRATED_INTEGRATION_PROVIDERS). Today it has stripe, wordpress, slack, notion, zapier, hubspot pull only. A new one can join each week. Without breaking the others. If the provider is in the Set, it routes to the worker. If not, it falls to the inline handler in the backend. A subtle detail. It receives processedNode (not node). The provider could come via {{...}} from another node (rare but possible). Without prior substitution, a dynamic provider wouldn't match the Set. It also has maximum granularity. hubspot pull only. Pull is on the worker, but push and update are still inline. This fine-grained granularity (provider + operation) lives inside the worker switch. It's not expressed by this function. Good template for isTemporalNode, which is still hardcoded in the service.

🎯 Why provider-based dispatch is good
Allows migrating 1 provider at a time without breaking the others. E.g., while Salesforce is still inline, Slack can already go to the worker. If something breaks, it's isolated per provider.

Same type (thirdPartyIntegration) reaches the worker with a generic contract. The worker resolves the provider internally.

In practice, dynamic provider is rare. The pattern is defensive.
🔧 hubspot pull only
On the worker, the hubspot handler has only pull. push and update are still inline. It's the system's maximum granularity: per (provider, operation). Not expressed in this function. Lives in the worker switch.

export function isIntegrationExecutableNodeType(nodeType): nodeType is IntegrationExecutableProviderNodeType
Purpose. TS type guard. Returns true for thirdPartyIntegration or mcpNode. These are types that have the "calls external integration" semantics, but whose worker-vs-inline decision depends on isWorkerRoutedIntegration. Used after dispatch to route to the correct inline handler when the provider hasn't been migrated.
In short. Think of the 3 functions like this. isTemporalNode asks "is this type VIP?". isWorkerRoutedIntegration asks "is this type + provider VIP?". And this one only asks "is this a type that talks to an external integration, regardless of migration?". Returns true for thirdPartyIntegration or mcpNode. It's used right after isWorkerRoutedIntegration, as an else if. "OK, this is an integration node but the provider hasn't been migrated. Which inline handler do I call?" Chooses between thirdPartyIntegrationNode or mcpNode (lines 3456, 3468). It's secondary, complementary. The main routing is the worker-vs-inline pair. It exists to give the correct fallback granularity. Without it, the inline dispatcher wouldn't know which of the two handlers to call. It's also the only of these 3 checks with TS type guard syntax (: nodeType is IntegrationExecutableProviderNodeType). After the check, TS narrows the type, allowing destructuring without casts. Pure compile-time sugar. Improves readability.

D processNodeViaTemporal(args)
flux.service.ts:639-738
private async processNodeViaTemporal({ node, processedNode, userId, sessionId, runId, flowId, flowVersionHistoryId, myUpdatedNodes, myTexts, nodeSubstitutionSchema, edges, onMutateSchema, objectCallerData, onUpdateTokens, ... })
Purpose. Single envelope for all worker calls. Does the INSERT node_executions with resolved input (T2), fires the workflow with deterministic workflowId (T3), blocks waiting for the result (T4), aggregates charges via sumChargesByExecution (T6), updates myUpdatedNodes, myTexts and schema. Returns this envelope to the loop.
In short. It's the central office that dispatches work to the Temporal worker. It doesn't matter if it's scripting, commandTextNode, apiCaller or any other VIP type. All go through the same envelope. The pipeline. Resolves reference arrays (promptData, contentData) in an extra pass to ensure the worker receives 100% resolved input. Opens a row in node_executions with execId=uuid() and deterministic workflowId (node-process-${nodeId}-${execId}. Same id on retry = idempotent). Fires the workflow on the Temporal server. Then comes the architecturally sensitive point. Backend stays blocked waiting via handle.result(). It's synchronous. No parallelism between siblings, even if the scheduler has 3 ready nodes at the same time. The worker scales handlers vertically (can have multiple machines running the same type in parallel, but the backend orchestrates 1 node at a time). After the worker returns, does SELECT on node_executions.outputData. If it came as {__claimRef}, resolves GET on S3. Aggregates token_transactions recorded by the worker via sumChargesByExecution. Returns an envelope { myUpdatedNodes, myTexts, nodeSubstitutionSchema } for the loop to reassign. If something throws on the worker, it bubbles up directly to the loop's try and becomes a fatal node error (step 3.8). No fallback to inline. Worker offline or bug in the handler equals entire execution blocked.

🎯 Blocking wait = synchronous
Each Temporal node costs ~150-500ms of overhead (start + wait) beyond the work itself. Even purely Temporal-eligible agents lose parallelism. The worker could batch, but the backend orchestrates 1 at a time.

In this model, the worker is vertical scaling of handlers, not horizontal parallelism.
⚠️ Worker errors propagate as throw
If handle.result() throws (workflow failed), the throw bubbles up to the loop's try (3.8, per-node error handling). Marks errorMessage and errorStatusCode on node.data and potentially stoppedByNodeFailure=true.

The Temporal path has no fallback to inline. If the worker is buggy, the entire execution is blocked.
🔧 processNodeViaTemporal is called multiple times
In dispatch, each Temporal type (scripting, commandTextNode, apiCaller, mathFunction, counter, outputController) calls processNodeViaTemporal with the same args shape. It's the only hook. The worker is what does the per-type switch internally (processSingleNode.workflow.ts:78).
📎 objectCallerData and onMutateSchema in the Temporal path
They are passed as args, but only the current values. The worker cannot mutate them back. When it returns, the backend trusts the result.nodeSubstitutionSchema (worker updates based on its own rules). The closure mutation pattern from the inline path doesn't exist here.
E Inline handlers (fallback dispatch)
flux.service.ts:3299-4438
Cascade of ~17 if (node.type === '...') { await this.someHandler({...}) }
Purpose. Legacy path. Nodes that haven't been migrated to the worker yet run directly on the backend. Each type has its own dedicated handler within FluxService (private or public methods that do SQL, call external APIs, write to flows_nodes.data). Pattern that causes FE perf problems in large agents.
In short. It's the "not migrated yet" closet. If the node is neither VIP nor worker-routed, it falls into a giant cascade of if (node.type === 'X') { await this.handlerX(...) } that takes up more than 1000 lines inside FluxService.apiV2. There are ~17 branches: voiceBoxNode, imageGenerator, pullData and pushData (Google Sheets), webSearch and webCrawling, conditionNode, nodesBox, arrayNode (loop), fluxBox and libraryNode (sub-flows), reportBuilder, audioReaderNode, commandContentNode, and more. Each runs inline in the backend process. Calls external API (ElevenLabs, Ideogram, FAL, SerpAPI...) and writes flows_nodes.data with fat previewResponses, contentData and text. Then recordInApiNodeError closes the node_executions row opened in 3.4-D. There are 2 groups.
(1) leaf handlers: do simple work and may migrate to the worker at some point (imageGenerator, webSearch, etc.).
(2) Structural orchestrators: arrayNode, conditionNode, nodesBox, fluxBox, libraryNode. Depend on state shared with the main loop (schedState, objectCallerData, runLogCollector, closures like onMutateSchema). These are the final boss of the migration. Require architectural refactor of the orchestrator itself, not just handler porting.
There are also passive types that don't fall into any if: varInputNode, GLOBAL_STARTER, comment, label, group. They only serve as data sources or visuals, with no active execution.

⚠️ 17 branches without a factory
It's a giant switch of stacked ifs inside FluxService.apiV2. Each new type adds another branch. No registry, no visitor pattern. Pure cascade that takes up ~1000 lines.

Splitting into private methods is what saves readability. The orchestration here is too coupled for incremental refactor.
🎯 Expected fallback
Types like conditionNode, arrayNode, nodesBox, fluxBox should not migrate any time soon. They depend on state shared with the loop (schedState, objectCallerData, runLogCollector). Migrating these dispatch heads is architectural refactor, not handler porting.

In that sense, the inline path is permanent for as long as those dependencies exist.
🔧 Types without handler
varInputNode, GLOBAL_STARTER, GLOBAL_OUTPUTS, comment, label, group. They don't fall into any if. The loop does the schema update in 3.6 (input is already in these types' data) and proceeds.

They are "passive" nodes. Present in the DAG but with no active execution. E.g., varInputNode only serves as a data source for {{...}} references.
Summary — what comes out of 3.5:
• The node ran via one of the paths: Temporal (with processNodeViaTemporal in a synchronous envelope), inline (direct handler in FluxService), or no-op (passive types).
• myUpdatedNodes, myTexts and nodeSubstitutionSchema reflect the handler output.
• Temporal path writes to node_executions.outputData. Inline path writes to flows_nodes.data (fat) and node_executions (trace row).
• Loop proceeds to 3.6 (updateSchemaWithNodeOutput). Makes the output visible to the next nodes.
Migration notes:
• Current state: 2 hybrid paths to avoid a big-bang. Each type migrates individually as the worker gains support. No backend ↔ worker fallback. If the worker has no handler, it's a fatal error (throw "Node type X not supported").
• Recommended migration order. (1) Integration providers 1 by 1 via MIGRATED_INTEGRATION_PROVIDERS. (2) Leaf types (imageGenerator, webSearch, webCrawling, pullData, pushData). They don't depend on loop state. (3) The final boss: arrayNode, conditionNode, nodesBox, fluxBox, libraryNode. They require refactoring the loop itself (buildSchedulerState plus worker state pattern).
• The blocking wait in processNodeViaTemporal is architectural. Even after migrating everything, if the backend keeps orchestrating, the "loop 1 node at a time" persists. Real parallelism requires migrating the orchestrator itself to the worker (via the processAgent workflow, currently a commented-out stub).
• isTemporalNode is hardcoded today. Converting it to a registry (config file or table) would allow env-based toggling without a deploy. Easy improvement to do during the migration.
• isWorkerRoutedIntegration is already config-friendly (exportable Set). Good template for isTemporalNode.
• It's the heart of the migration. All architectural decisions of the migration go through here. Every checkbox of the migration plan affects these 3 functions and the worker switch. Documenting in detail is a prerequisite for any refactor.

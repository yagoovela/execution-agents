Passo 5.2 — mcpRunStatusService.markFinished

Bloco em apiV2Job.processor.ts:58-67 (caminho de sucesso) e 80-88 (caminho de erro). Não vive no FluxService.apiV2. Vive no processor da fila Bull. Só roda quando o request veio pelo endpoint MCP e o job foi enfileirado via Bull.
Em resumo — o que esse passo faz
  • Tracking dedicado do MCP. Esse passo não vive no FluxService. Vive no processor do Bull. É opt-in via flag mcpTracking. Se a execução não veio pelo endpoint MCP, tudo aqui é pulado. Serve para dashboards específicos: latência, error rate, tokens por token MCP.
  • Pareamento markRunning / markFinished. Na entrada do job, o processor grava a linha em mcp_run_status com status: 'in_progress' e startedAt=NOW(). No fim, atualiza com o resultado. Fecha o par do começo ao fim do lifecycle.
  • Success path. Deriva o status de nodeError. Quando o apiV2() retorna sem lançar, o processor lê result.nodeError. Se null, o status vira 'completed'. Se string, o status vira 'error' (nó falhou, mas a execução terminou). Grava totalTokensUsed, totalCost, durationMs e errorMessage.
  • Error path. Tokens e cost zerados. Se o apiV2() lançou (5.1), o catch do processor marca status: 'error' com tokens: 0, cost: 0. Limitação atual. O processor não tem acesso ao acumulador da execução. Crash catastrófico fica subcontado em analytics de custo. Depois, faz throw error para o Bull marcar o job como failed.
  • Saída. 1 UPDATE em mcp_run_status, só quando vem via MCP. Grava status final, tokens, cost, duração e erro. O cleanup do MCP fica separado de execution_logs. Não polui queries dos outros run_types.
Contexto. MCP (Model Context Protocol) é uma layer separada. Permite outros LLMs chamarem o Flux como tool. Cada chamada MCP dispara um job Bull. Esse tracking permite analytics de "quantas execuções de MCP rodaram", latência e error rate por token MCP. Fora do main path do FluxService. Vive no processor.

Propósito. Antes de chamar fluxService.apiV2(), se a flag mcpTracking=true veio no payload, o processor marca a execução como em execução em mcp_run_status. INSERT (ou UPDATE se a linha existe) com status='in_progress' e startedAt=NOW().
Em resumo. O passo 1.1 do diagrama menciona markRunning. O pareamento markRunning/markFinished caracteriza esse subsistema. Fica separado do restante do audit trail. Serve para dashboards específicos do MCP: "quantas execuções do mcpToken X estão rodando agora, quantas terminaram, latência média". A tabela mcp_run_status é dedicada. Não é execution_logs. Motivação. MCP é uma layer de API pública com contrato próprio: tokens de MCP e rate limiting por MCP client. Tracking granular ajuda a gerir essa layer.

INSERT/UPDATE mcp_run_status
Linha com { id: processId, status: 'in_progress', startedAt: NOW() }. Sinaliza para o dashboard de MCP que existe execução em curso.
🎯 Flag mcpTracking
Chega no request quando o endpoint é específico de MCP. Se é false ou ausente, o tracking MCP inteiro é pulado. Outros run_types não pagam esse custo.
BmarkFinished (success path)
apiV2Job.processor.ts:58-67
await this.mcpRunStatusService.markFinished({ id: processId, status: result.nodeError ? 'error' : 'completed', tokens: result.totalTokensUsed, cost: result.totalCost, durationMs: Date.now() - startedAt, errorMessage: result.nodeError ?? null })
Propósito. Depois de o fluxService.apiV2() retornar (sem throw), fecha o tracking. Status vale 'error' se nodeError está presente no retorno. Caso contrário, vale 'completed'. Grava tokens totais, cost total, duração em ms e errorMessage.
Em resumo. Pareamento com markRunning. Quando o apiV2() retorna sem crash, o processor pega o result. O result traz nodeError, totalTokensUsed e totalCost. O processor faz UPDATE na linha de mcp_run_status. O status é derivado de result.nodeError. Se é null, status vira 'completed' (sucesso limpo). Se é string, status vira 'error' (algum nó falhou, mas a execução terminou sem crash top-level; o catch da Fase 4 em 3.8 fez fail-fast). durationMs é Date.now() - startedAt. O startedAt foi marcado pelo processor no início. Preciso para dashboards de latência. errorMessage é o próprio nodeError (a string amigável do 4.5). Permite ao MCP client mostrar a UI apropriada. UPDATE via TypeORM.
// apiV2Job.processor.ts:58 if (params.mcpTracking) { await this.mcpRunStatusService.markFinished({ id: processId, status: result.nodeError ? 'error' : 'completed', tokens: result.totalTokensUsed, cost: result.totalCost, durationMs: Date.now() - startedAt, errorMessage: result.nodeError ?? null, }); }
🎯 3 estados possíveis
Status: 'pending' (nunca setado explicitamente; default do INSERT), 'in_progress' (markRunning), 'completed' ou 'error' (markFinished). Cancel não tem status próprio aqui. Cancel de MCP é raro ou inexistente.
📎 nodeError vs. crash
Se o agente falhou por bug de handler (fail-fast em 3.8), nodeError é string, mas o apiV2 retornou normalmente. Se o agente crashou de forma catastrófica (5.1), o apiV2 lançou. Nesse caso, o fluxo vai para o fn C.
CmarkFinished (error path)
apiV2Job.processor.ts:80-88
catch (error) { if (params.mcpTracking) { await mcpRunStatusService.markFinished({ id: processId, status: 'error', tokens: 0, cost: 0, durationMs, errorMessage: error.message }); } throw error; }
Propósito. Se o fluxService.apiV2() lançou (não retornou), o processor pega no catch. Marca mcp_run_status com status='error', tokens=0, cost=0 (o processor não tem acesso ao acumulador) e errorMessage=error.message. Faz re-throw para o Bull marcar o job como failed.
Em resumo. Paralelo do fn B, mas em catch. Diferença crítica. Aqui o processor não tem acesso a totalTokensUsed nem totalCost. O result nunca foi retornado. Passa 0 para ambos. Limitação do design atual. Em teoria, o backend poderia expor essas variáveis via chargeContext ou outro padrão para o processor recuperar. Hoje, execução com crash catastrófico não é billed. Boa notícia para o user, que não paga pelo crash. Ruim para analytics de custo real. errorMessage é a mensagem crua da exception. Depois, o código faz throw error. Sem isso, o Bull acharia que o job foi OK e não trataria como erro.
// apiV2Job.processor.ts:80 } catch (error) { if (params.mcpTracking) { await this.mcpRunStatusService.markFinished({ id: processId, status: 'error', tokens: 0, // não tem acesso ao acumulador cost: 0, durationMs: Date.now() - startedAt, errorMessage: error.message, }); } throw error; // Bull marca job failed }
⚠️ tokens/cost zerados em crash
Se o agente crashou no meio, tokens e cost já cobrados no banco (token_transactions) NÃO aparecem em mcp_run_status. O dashboard "custo por token MCP" fica com subcontagem.
🎯 Re-throw para o Bull
Sem throw error, o Bull acharia que o job foi OK (returned nothing). O erro precisa propagar para a lógica de retry funcionar.
DTabela mcp_run_status
mcp/entities/mcp-run-status.entity.ts
@Entity('mcp_run_status') class McpRunStatus { id: string PK; status: 'pending' | 'in_progress' | 'completed' | 'error'; tokens: number; cost: number; durationMs: number; errorMessage: string; startedAt, endedAt: Date; }
Propósito. Tabela dedicada para MCP tracking. Uma linha por processId (job Bull). Analytics: SUM de tokens por mcpTokenId, percentis de latência, error rate. Separada de execution_logs para não poluir queries de execuções não MCP com filtros.
Em resumo. Tabela pequena e focada. Uma linha equivale a uma execução MCP. A chave é o processId (o mesmo do runLogProcessId). Permite JOIN com execution_logs, space_run_logs e node_executions. Colunas específicas de MCP tracking. status como enum-like (string com valores restritos). durationMs para latência. errorMessage para debug. Sem flowId nem userId. É possível fazer JOIN via processId quando preciso. O dashboard "meus MCP calls" filtra por userId via join.
🪜 Ciclo de status
1Job enqueued (markRunning)'in_progress'
2apiV2 retornou OK (result.nodeError null)'completed'
3apiV2 retornou com nodeError'error'
4apiV2 lançou exception'error' (tokens=0, cost=0)
🎯 Por que ficar separado de execution_logs
MCP tracking é opt-in pela flag mcpTracking. Manter em tabela separada evita coluna nullable em execution_logs. Também evita poluição de queries de outros run_types.
Resumo — o que sai de 5.2:
• 1 UPDATE em mcp_run_status, só quando vem via MCP.
• Linha completa: status final, tokens, cost (0 em crash), duração e erro.
• Roda antes de o throw propagar no error path. Cleanup garantido.
Observações para migração:
• MCP tracking é opcional e isolado. Só afeta endpoints MCP. A migração pode ficar para depois.
• Zerar tokens e cost em crash é dívida. Um refactor pode expor essas variáveis via chargeContext ou callback para o processor ler.
• Tabela dedicada é bom padrão. Evita "tabela deusa" em execution_logs. Manter.
• Não bloqueia migração de agentes normais.

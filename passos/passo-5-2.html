Step 5.2 — mcpRunStatusService.markFinished

Block at apiV2Job.processor.ts:58-67 (success path) and 80-88 (error path). Doesn't live in FluxService.apiV2. Lives in the Bull queue processor. Only runs when the request came through the MCP endpoint and the job was queued via Bull.
In short — what this step does
  • Dedicated MCP tracking. This step doesn't live in FluxService. It lives in the Bull processor. Opt-in via mcpTracking flag. If the execution didn't come through the MCP endpoint, everything here is skipped. Serves specific dashboards: latency, error rate, tokens per MCP token.
  • markRunning / markFinished pairing. On job entry, the processor writes a row into mcp_run_status with status: 'in_progress' and startedAt=NOW(). At the end, updates with the result. Closes the pair from start to end of the lifecycle.
  • Success path. Derives status from nodeError. When apiV2() returns without throwing, the processor reads result.nodeError. If null, status becomes 'completed'. If a string, status becomes 'error' (node failed, but the execution finished). Writes totalTokensUsed, totalCost, durationMs, and errorMessage.
  • Error path. Tokens and cost zeroed. If apiV2() threw (5.1), the processor catch marks status: 'error' with tokens: 0, cost: 0. Current limitation. The processor has no access to the execution accumulator. Catastrophic crash is undercounted in cost analytics. Then does throw error so Bull marks the job as failed.
  • Output. 1 UPDATE on mcp_run_status, only for MCP-originated executions. Writes final status, tokens, cost, duration, and error. MCP cleanup stays separate from execution_logs. Doesn't pollute queries of other run_types.
Context. MCP (Model Context Protocol) is a separate layer. Lets other LLMs call Flux as a tool. Each MCP call fires a Bull job. This tracking enables analytics for "how many MCP executions ran", latency and error rate per MCP token. Outside the FluxService main path. Lives in the processor.

await this.mcpRunStatusService.markFinished({ id: processId, status: result.nodeError ? 'error' : 'completed', tokens: result.totalTokensUsed, cost: result.totalCost, durationMs: Date.now() - startedAt, errorMessage: result.nodeError ?? null })
Purpose. After fluxService.apiV2() returns (without throwing), closes the tracking. Status is 'error' if nodeError is present in the return value. Otherwise, 'completed'. Writes total tokens, total cost, duration in ms, and errorMessage.
In short. Pairing with markRunning. When apiV2() returns without crashing, the processor takes the result. The result carries nodeError, totalTokensUsed, and totalCost. The processor does an UPDATE on the mcp_run_status row. Status is derived from result.nodeError. If null, status becomes 'completed' (clean success). If string, status becomes 'error' (some node failed, but the execution finished without a top-level crash; the Phase 4 catch in 3.8 did fail-fast). durationMs is Date.now() - startedAt. startedAt was marked by the processor at the start. Precise for latency dashboards. errorMessage is nodeError itself (the user-friendly string from 4.5). Lets the MCP client show the appropriate UI. UPDATE via TypeORM.

🎯 3 possible states
Status: 'pending' (never explicitly set; INSERT default), 'in_progress' (markRunning), 'completed' or 'error' (markFinished). Cancel has no own status here. MCP cancel is rare or nonexistent.
📎 nodeError vs. crash
If the agent failed via a handler bug (fail-fast in 3.8), nodeError is a string, but apiV2 returned normally. If the agent crashed catastrophically (5.1), apiV2 threw. In that case, flow goes to fn C.
CmarkFinished (error path)
apiV2Job.processor.ts:80-88
catch (error) { if (params.mcpTracking) { await mcpRunStatusService.markFinished({ id: processId, status: 'error', tokens: 0, cost: 0, durationMs, errorMessage: error.message }); } throw error; }
Purpose. If fluxService.apiV2() threw (didn't return), the processor catches it. Marks mcp_run_status with status='error', tokens=0, cost=0 (the processor has no access to the accumulator), and errorMessage=error.message. Rethrows so Bull marks the job as failed.
In short. Parallel to fn B, but in catch. Critical difference. Here the processor has no access to totalTokensUsed nor totalCost. The result was never returned. Passes 0 for both. Current design limitation. In theory, the backend could expose these variables via chargeContext or another pattern for the processor to retrieve. Today, catastrophic-crash executions aren't billed. Good news for the user, who doesn't pay for the crash. Bad for real cost analytics. errorMessage is the raw exception message. Then the code does throw error. Without it, Bull would think the job was OK and wouldn't treat it as an error.
// apiV2Job.processor.ts:80 } catch (error) { if (params.mcpTracking) { await this.mcpRunStatusService.markFinished({ id: processId, status: 'error', tokens: 0, // no access to accumulator cost: 0, durationMs: Date.now() - startedAt, errorMessage: error.message, }); } throw error; // Bull marks job failed }
⚠️ tokens/cost zeroed on crash
If the agent crashed midway, tokens and cost already charged in the DB (token_transactions) do NOT appear in mcp_run_status. The "cost per MCP token" dashboard is undercounted.
🎯 Rethrow to Bull
Without throw error, Bull would think the job was OK (returned nothing). The error needs to propagate for the retry logic to work.
Dmcp_run_status table
mcp/entities/mcp-run-status.entity.ts
@Entity('mcp_run_status') class McpRunStatus { id: string PK; status: 'pending' | 'in_progress' | 'completed' | 'error'; tokens: number; cost: number; durationMs: number; errorMessage: string; startedAt, endedAt: Date; }
Purpose. Dedicated table for MCP tracking. One row per processId (Bull job). Analytics: SUM of tokens per mcpTokenId, latency percentiles, error rate. Separate from execution_logs so it doesn't pollute queries for non-MCP executions with filters.
In short. Small, focused table. One row equals one MCP execution. The key is processId (same as runLogProcessId). Allows JOINs with execution_logs, space_run_logs, and node_executions. MCP-tracking-specific columns. status as enum-like (string with restricted values). durationMs for latency. errorMessage for debug. No flowId nor userId. You can JOIN via processId when needed. The "my MCP calls" dashboard filters by userId via join.
🪜 Status cycle
1Job enqueued (markRunning)'in_progress'
2apiV2 returned OK (result.nodeError null)'completed'
3apiV2 returned with nodeError'error'
4apiV2 threw exception'error' (tokens=0, cost=0)
🎯 Why kept separate from execution_logs
MCP tracking is opt-in via the mcpTracking flag. Keeping it in a separate table avoids a nullable column in execution_logs. Also avoids polluting queries for other run_types.
Summary — what leaves 5.2:
• 1 UPDATE on mcp_run_status, only for MCP-originated executions.
• Full row: final status, tokens, cost (0 on crash), duration, and error.
• Runs before the throw propagates on the error path. Guaranteed cleanup.
Migration notes:
• MCP tracking is optional and isolated. Only affects MCP endpoints. Migration can wait.
• Zeroing tokens and cost on crash is debt. A refactor can expose these variables via chargeContext or a callback for the processor to read.
• Dedicated table is a good pattern. Avoids "god table" in execution_logs. Keep it.
• Doesn't block normal agent migration.

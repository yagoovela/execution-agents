Step 3.11 — DAG advance

Block in flux.service.ts:3566-3571 (conditionNode), 4013 (comment on arrayNode) and 4730-4732 (loop fallback). Closes the current node in the scheduler. Calls markCompleted for normal types or completeCondition for conditions. Then nextReady returns the next id or null.
In summary — what this step does
  • Counterpart of 3.1. If 3.1 is "next please" (nextReady), this is "that one is done". Closes the current node in the scheduler. Propagates the resolution to successors. Requests the next id. The loop cycles until nextReady returns null.
  • handledAdvance flag. Signals whether the handler already closed its own advance. In today's only case (conditionNode), the handler calls completeCondition and sets the flag to true. Otherwise, the loop falls into the markCompleted fallback. Implicit and fragile pattern. No type contract forces a new handler to remember the flag.
  • markCompleted is the common path. Marks the node as completed. Resolves all forward deps as alive (predWasDead=false). Successor that hits resolvedPreds === totalPreds becomes ready. Idempotent. Detailed in 3.1.
  • completeCondition is the special path. For conditionNode, must kill non-taken branches. Receives the takenHandle ('outputHandle-0' and similar) via resolveConditionHandle(condNode). Iterates conditionEdges[conditionId]. Propagates alive to those that match. Propagates dead to those that don't. Without this logic, non-taken branches would wait for input that never arrives. It's an eternal deadlock.
  • arrayNode uses markCompleted, not completeCondition. The diagram's comment on 4013 says arrayNode also calls completeCondition. This is inaccurate. When the arrayNode finishes iterating (line 4346), it closes via normal markCompleted.
  • Output. <code>schedState.completed</code> gained the current node's id. <code>state.ready</code> may have gained 0 to N new ids (successors that unlocked). Non-taken condition branches became <code>dead</code>. <code>scheduledId</code> was reassigned with the next id or null. Null means end of execution, and Phase 4 begins.
Context. Opposite end of 3.1. If 3.1 is "next please", 3.11 is "that one is done". The distinction between markCompleted and completeCondition is essential. Without this logic, non-taken condition branches would remain pending forever, waiting for input that never arrives.

AhandledAdvance flag
flux.service.ts:3242 (declara), 3572 (seta), 4730-4732 (usa)
let handledAdvance = false; ... if (!handledAdvance) { markCompleted(schedState, id); } scheduledId = nextReady(schedState);
Purpose. Flag that signals whether the handler already called markCompleted or completeCondition. If so, the loop does not call markCompleted again at the end. Thus, special handlers (condition, arrayNode when finishing) control their own advance. The rest depend on the default fallback.
In summary. It's a "I already handled this" flag. Some node types, mainly conditionNode, need special logic to advance the DAG. Instead of just marking completed, they also need to kill non-taken branches via completeCondition. The loop does not know this distinction directly. Each handler sets handledAdvance = true when it decides to close its own advance. At the end of the try (line 4730-4732), the loop checks. If handledAdvance is false, it calls default markCompleted. If true, it respects what the handler did. Simple, but fragile. If a new handler forgets to set the flag and does its own advance (calling completeCondition, for example), the loop calls markCompleted on top. It's idempotent. Has early-return on state.completed.has(id). Does not break. If there are other advance variants in the future, care is needed. Poorly documented pattern. Only noticeable by reading the entire dispatch.

BmarkCompleted(schedState, id)
scheduler.ts:352-357 · call site flux.service.ts:4731
export function markCompleted(state: SchedulerState, id: string): void
Purpose. Closes the node by marking it as completed. Resolves the dependency of all forwardDeps as alive. It's the default fallback for all types that don't need special branching logic.
In summary. It's the common path. The handler finished the normal node. Now it releases the successors. Already detailed in depth in step 3.1 (fn C, markCompleted). Here is the place where it is called. At the end of the try when handledAdvance is false. Receives no handle or taken info. Just resolves all forward deps as alive (non-dead). If the current node has 3 successors, the 3 receive resolvedPreds++. Those that hit totalPreds become ready. Idempotent. Calling twice is safe.
export function markCompleted(state: SchedulerState, id: string): void { if (state.completed.has(id)) return; // idempotente state.completed.add(id); for (const next of state.forwardDeps.get(id) ?? []) { resolvePred(state, id, next, false); // predWasDead=false (viva) } }

Purpose. Specialisation for decision nodes (conditionNode). Kills non-taken branches via resolvePred(..., predWasDead=true). Receives the taken handle as a string of type 'outputHandle-0'. Edges that match propagate alive. Those that don't match propagate dead.
In summary. Special path for conditionNode. The internal logic has been detailed in step 3.1 (fn D, completeCondition). Here we see who calls. The conditionNode dispatch in flux.service.ts:3540-3573. ⚠️ resolveConditionHandle can return null
If the condition could not decide (bug, all handles resolved false), resolveConditionHandle can return null. Passes null to completeCondition. All edges become dead. Equivalent effect to DEAD_HANDLE.
🔧 stoppedByLoopBehavior
Special case in the condition handler. If idxCondition < -1 (loop finished iteration), sets stoppedByLoopBehavior=true and calls normal markCompleted, instead of completeCondition. Signals to Phase 4 that execution ended because the loop reached the end, not by error.

Purpose. Last line of the while body. Requests the next id from the scheduler. If it returns non-null, the while continues to the next iteration. If null, exits. Phase 4 begins.
In summary. It's the turn's closing. After everything that happened in the node (fetch, substitution, log, dispatch, handler, endNode, error check, advance), the last thing is a question: is anyone else ready? nextReady returns the next id or null. If id, the while goes back to the top. The cancellation check runs again. The whole cycle repeats. If null, exits. Phase 4 begins with unprocessedNodeIds = [...] and all the cleanup. It's the same nextReady as 3.1. Not a variant. Completes the loop symmetrically.

Migration observations.
• The pure scheduler is portable. The handledAdvance flag pattern is fragile. The refactor can formalise in a contract: "handler returns { advance: 'default' | { condition: handle } | { skip: reason } }".
• completeCondition with literal handle names ('outputHandle-0') is typo-sensitive. Validate handles at build or use typed constants.
• It's essential. Without this logic, execution stalls. The migration must preserve the semantics of dead branches.

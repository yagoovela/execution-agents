Passo 3.11 — Avanço do DAG

Bloco em flux.service.ts:3566-3571 (conditionNode), 4013 (comentário sobre arrayNode) e 4730-4732 (fallback do loop). Fecha o nó atual no scheduler. Chama markCompleted para tipos normais ou completeCondition para conditions. Depois, nextReady devolve o próximo id ou null.
Em resumo — o que esse passo faz
  • Contraponto do 3.1. Se lá é "próximo por favor" (nextReady), aqui é "esse já foi". Fecha o nó atual no scheduler. Propaga a resolução aos sucessores. Requisita o próximo id. O loop se recicla até nextReady devolver null.
  • Flag handledAdvance. Sinaliza se o próprio handler já fechou seu avanço. No único caso hoje (conditionNode), o handler chama completeCondition e seta a flag em true. Caso contrário, o loop cai no fallback markCompleted. Padrão implícito e frágil. Sem contract de tipo que force handler novo a lembrar da flag.
  • markCompleted é o caminho comum. Marca o nó como completed. Resolve todos os forward deps como vivos (predWasDead=false). Sucessor que bater resolvedPreds === totalPreds vira ready. Idempotente. Detalhado no 3.1.
  • completeCondition é o caminho especial. Para conditionNode, precisa matar branches não tomadas. Recebe o takenHandle ('outputHandle-0' e similares) via resolveConditionHandle(condNode). Itera conditionEdges[conditionId]. Propaga viva para quem bate. Propaga morta para quem não bate. Sem essa lógica, branches não tomadas ficariam esperando entrada que nunca chega. É trava eterna.
  • arrayNode usa markCompleted, não completeCondition. O comentário do diagrama sobre 4013 diz que arrayNode também chama completeCondition. Isso não é preciso. Quando o arrayNode termina de iterar (linha 4346), fecha via markCompleted normal.
  • Saída. schedState.completed ganhou o id do nó atual. state.ready pode ter ganhado de 0 a N novos ids (sucessores que destravaram). Branches não tomadas de condition viraram dead. scheduledId foi reatribuído com o próximo id ou null. Null significa fim da execução, e a Fase 4 começa.
Contexto. Ponta contrária do 3.1. Se 3.1 é "próximo por favor", 3.11 é "esse já foi". A distinção entre markCompleted e completeCondition é essencial. Sem essa lógica, branches não tomadas do condition ficariam pendentes eternamente, esperando entrada que nunca chega.

Propósito. Flag que sinaliza se o próprio handler já chamou markCompleted ou completeCondition. Se sim, o loop não chama markCompleted de novo no final. Assim, handlers especiais (condition, arrayNode quando encerra) controlam o próprio avanço. O resto depende do fallback padrão.
Em resumo. É um flag de "já cuidei disso". Alguns tipos de nó, principalmente conditionNode, precisam de lógica especial para avançar o DAG. Em vez de só marcar completed, precisam também matar branches não tomadas via completeCondition. O loop não conhece essa distinção diretamente. Cada handler seta handledAdvance = true quando decide fechar o próprio avanço. No final do try (linha 4730-4732), o loop checa. Se handledAdvance é false, chama markCompleted padrão. Se true, respeita o que o handler fez. Simples, mas frágil. Se um handler novo esquecer de setar a flag e fizer avanço próprio (chamando completeCondition, por exemplo), o loop chama markCompleted em cima. É idempotente. Tem early-return em state.completed.has(id). Não quebra. Se houver outras variantes de avanço no futuro, é preciso cuidado. Padrão pouco documentado. Só se percebe lendo o dispatch inteiro.

Propósito. Fecha o nó marcando-o como completed. Resolve viva a dependência de todos os forwardDeps. É o fallback padrão para todos os tipos que não precisam de lógica especial de branching.
Em resumo. É o caminho comum. O handler terminou o nó normal. Agora libera os sucessores. Já foi detalhado em profundidade no passo 3.1 (fn C, markCompleted). Aqui está o local em que é chamado. No fim do try quando handledAdvance é false. Não recebe handle nem taken info. Apenas resolve todos os forward deps como vivos (não-dead). Se o nó atual tem 3 sucessores, os 3 recebem resolvedPreds++. Os que baterem com totalPreds viram ready. Idempotente. Chamar 2 vezes é seguro.
export function markCompleted(state: SchedulerState, id: string): void { if (state.completed.has(id)) return; // idempotente state.completed.add(id); for (const next of state.forwardDeps.get(id) ?? []) { resolvePred(state, id, next, false); // predWasDead=false (viva) } }

Propósito. Especialização para nós de decisão (conditionNode). Mata branches não tomadas via resolvePred(..., predWasDead=true). Recebe o handle tomado como string do tipo 'outputHandle-0'. Arestas que combinam propagam viva. As que não combinam propagam morte.
Em resumo. Caminho especial para conditionNode. A lógica interna já foi detalhada no passo 3.1 (fn D, completeCondition). Aqui vemos quem chama. Se o condition não conseguiu decidir (bug, todos os handles resolveram falso), resolveConditionHandle pode devolver null. Passa null para completeCondition. Todas as arestas viram dead. É efeito equivalente ao DEAD_HANDLE.

Caso especial no handler de condition. Se idxCondition < -1 (loop terminou a iteração), seta stoppedByLoopBehavior=true e chama markCompleted normal, em vez de completeCondition. Sinaliza para a Fase 4 que a execução terminou porque o loop chegou ao fim, e não por erro.

Observações para migração.
• O scheduler puro é portável. O padrão da flag handledAdvance é frágil. O refactor pode formalizar em um contract: "handler retorna { advance: 'default' | { condition: handle } | { skip: reason } }".
• completeCondition com nomes literais de handle ('outputHandle-0') é sensível a typo. Validar handles no build ou usar constantes tipadas.
• É essencial. Sem essa lógica, a execução trava. A migração deve preservar a semântica de branches mortos.

Passo 1.5a — stripStaleErrorState + montagem de edges

Bloco em flux.service.ts:2513-2520. Higieniza os nodes da execução anterior. Remove o error-state acumulado (errorMessage, errorStatusCode, hasExecutionError). Reduz cada edge a apenas os 5 campos que o scheduler realmente lê. A implementação de stripStaleErrorState está em flux.service.ts:444-459.
Em resumo — o que esse passo faz
  • Limpa restos de erros anteriores em cada node. Se a execução anterior falhou e deixou errorMessage, errorStatusCode ou hasExecutionError gravados no node.data (via persistNodeSuccess na fase 4), esta função remove. Evita que o coletor de erros do passo 4.2 confunda erro antigo com erro da execução atual.
  • Cai um nível de profundidade adicional. Se node.data.text é objeto (não string), também limpa errorMessage e errorStatusCode lá dentro. Cobre o caso do commandContentNode, que grava erros dentro de data.text.errorMessage.
  • Retorna um array novo (imutável). Nada é mutado in-place. .map(node => ...) devolve nodes novos com data spread. É crítico. As versões originais no banco não devem ser modificadas até que persistNodeSuccess escreva de novo.
  • Reduz cada edge ao shape mínimo. Pega só { id, source, sourceHandle, target, targetHandle }. Descarta data, type, coordenadas e style. Tudo que o frontend usa, mas o scheduler não precisa. Reduz footprint em memória quando o loop principal iterar centenas de vezes lendo edges.
  • Downstream. O array retornado é atribuído a const nodes = .... Vira let updatedFlows = [...nodes] na linha 2523. A partir daqui, esse é o array canônico da execução inteira. Os edges viram source of truth para o scheduler encontrar next nodes.
Contexto. Essa higienização evita um bug clássico. Sem o strip, o coletor de erros da fase 4 (filtro nodesWithError) pegaria também nodes que falharam numa execução passada mas executaram OK agora. Marcaria a execução atual como falha por erro.

A stripStaleErrorState(nodes)
flux.service.ts:2513 (call) + 444-459 (impl)
private stripStaleErrorState(nodes: any[]): any[]
Propósito. Remove o error state acumulado gravado no data de cada node em execuções anteriores. Se a execução passada gravou errorMessage, errorStatusCode ou hasExecutionError via persistNodeSuccess, esta função limpa antes da execução nova começar.
Em resumo. Cada node no banco pode ter herdado sujeira de execuções passadas. Se um apiCaller falhou ontem, o error message ficou salvo em data.errorMessage. A função percorre a lista, tira uma cópia de cada data, apaga as chaves errorMessage, errorStatusCode e hasExecutionError. Ainda desce um nível. Se data.text é objeto (não string), limpa lá dentro também. O commandContentNode historicamente aninhava erros em data.text.errorMessage. Retorna sempre um array novo. Nunca muta o original. Preserva o que veio do banco. Sem essa passada, o filtro nodesWithError na fase 4 sinalizaria falso positivo. Nodes que executaram OK, mas tinham erro de execução passada marcado, seriam contados como erros desta execução.

private stripStaleErrorState(nodes: any[]): any[] { return nodes.map(node => { if (!node?.data) return node; const cleanData = { ...node.data }; delete cleanData.errorMessage; delete cleanData.errorStatusCode; delete cleanData.hasExecutionError; if (cleanData.text && typeof cleanData.text === 'object') { const cleanText = { ...cleanData.text }; delete cleanText.errorMessage; delete cleanText.errorStatusCode; cleanData.text = cleanText; } return { ...node, data: cleanData }; }); }

🎯 Por que 2 níveis?
commandContentNode guarda todo o resultado em data.text como objeto ({ result, errorMessage, ... }). Outros nodes usam data.text como string. O typeof === 'object' distingue os dois. Só desce quando é objeto.
📎 Onde esses campos são gravados
persistNodeSuccess (worker e backend) grava esses 3 campos no data do node quando o node falha durante execução. Ficam persistidos no Postgres até a próxima execução, quando esta função limpa.
⚠️ Só 3 chaves. Não é exhaustive
Se algum node type grava erro em outra chave (por exemplo, data.errorCode ou data.stackTrace), esta função não pega. Precisa ser mantida sincronizada com o que o persistNodeSuccess grava.
🔧 Imutabilidade via spread
{ ...node, data: cleanData }. O spread cria referências novas em ambos os níveis. O original em getFlow.nodes continua intacto. É importante se algo mais adiante quiser inspecionar o pré-strip.
B Montagem enxuta de edges
flux.service.ts:2514-2520
const edges = getFlow.edges.map(edge => ({ id, source, sourceHandle, target, targetHandle }))
Propósito. Reduz cada edge do banco a apenas os 5 campos que o scheduler realmente lê ao decidir a rota entre nós. Descarta metadata visual (type, data, animações, style, position). Só o frontend usa esses campos.
Em resumo. As edges no banco carregam campos que só interessam para desenhar o grafo. type, data, animações, estilo, cor de handle. É toda bagagem visual. O scheduler precisa apenas de source, target e o handle de cada lado para decidir o próximo node. A linha faz um .map() que pega só as 5 chaves relevantes. Efeitos. Menos memória. Se um flow tem 500 edges com data pesado, corta significativamente. Menos superfície de atenção. Quem lê o loop principal não pergunta se edge.data é usada. Imutabilidade forte. Quem quiser mutar o edge cria um novo com apenas esses 5 campos. Trade-off. Se algum dia o scheduler precisar de outro campo do edge (por exemplo, edge.type para diferenciar edges condicionais), precisa ser adicionado aqui explicitamente.

🎯 Onde edges é lido depois
edges.find(e => e.source.includes('flow-global-starter')). L2560 (localiza o starter).
Scheduler e prefetch. Decidem next node por match de source, target e handles.
Nada em runtime lê data, type ou style do edge.
📎 Ordem no map
A ordem no literal {...} é id, source, sourceHandle, target, targetHandle. Reflete o que aparece na visualização (aresta indo de source a target).
⚠️ Perda silenciosa de campos
Se o schema de edges ganhar um campo novo (por exemplo, edge.condition para branch semantics), esse map não vai propagar. É um bug fácil de esconder.
🔧 Não é deep-clone
Cada string é copiada por valor (primitivas JavaScript). Se um campo virar objeto, o spread aqui pegaria por referência. Nesse caso, mutar edge.X mutaria o banco também.
C Uso downstream. Como isso previne bugs na fase 4
flux.service.ts:4854 (nodesWithError filter)
// Coletor de erros da fase 4: nodesWithError = myUpdatedNodes.filter(n => n.data.errorMessage)
Propósito. Deixar claro por que o strip é necessário. Na fase 4, o coletor de erros lê node.data.errorMessage para montar nodesWithError. Se o erro antigo estivesse acumulado no data, marcaria falso positivo.
Em resumo. A fase 4 do apiV2 (encerramento) faz um filtro simples. Quais nodes têm errorMessage? Usa a resposta para decidir se a execução inteira foi sucesso ou erro. Se stripStaleErrorState não executasse, o cenário seria o seguinte. Execução 1 falha num apiCaller e grava errorMessage. Execução 2 começa. Esse mesmo apiCaller nem é executado (talvez porque o flow tomou uma branch diferente). Na fase 4, o coletor vê a mensagem de erro antiga ainda presente e conclui que a execução falhou. Resultado. Métricas erradas, notificação errada, flow log com status errado. O strip prévio garante que os nodes começam limpos. O único jeito de aparecer errorMessage ali é a execução atual ter falhado nele.

Efeito cumulativo do strip
Com stripStaleErrorState. O único errorMessage que sobrevive até a fase 4 é o que esta execução gravou. Sem ele. Falsos positivos e logs corrompidos por execuções passadas.
🎯 O contrato implícito
Se um node tem errorMessage depois do loop, é porque falhou nesta execução. Esse contrato só vale se algum strip executou antes. Se em algum refactor esse strip sumir, o contrato quebra silenciosamente.
📎 Passo 1.5b versus 1.5a
1.5a limpa erros de execuções passadas. 1.5b (mesmo bloco, linhas 2525-2558) limpa output de execuções passadas para nodes com clearOnExecution ligado. São higienizações distintas com propósitos distintos.
⚠️ getFlow.nodes ainda com error state
getFlow.nodes (o original do banco) continua com o error state. Se algum código futuro ler direto de getFlow.nodes em vez de nodes, pega o valor sujo.
🔧 Alternativa não usada
Poderia ser feito UPDATE no banco antes da execução começar (limpar via SQL). Não é feito. Em vez disso, mantém o estado no banco (útil para debug post-mortem) e limpa em memória para esta execução.
Resumo. O que sai de 1.5a:
const nodes. Cópia enxuta e limpa dos nodes, sem error state acumulado.
const edges. Cópia enxuta com apenas 5 campos por edge.
Alocações. N mais M objetos novos (N nodes, M edges). Todos rasos.
Zero I/O. Puro compute em memória.
Contrato preservado. Qualquer errorMessage no data depois deste ponto vem desta execução.
Observações para migração:
stripStaleErrorState é função pura. Replicável 1 para 1 no worker sem esforço.
Se a migração passar a limpar error state no banco antes da execução (via UPDATE), esse método pode até sumir. Cuidado. Perde a granularidade de "limpo em memória sem alterar o Postgres até o próximo persist".
O shape enxuto de edges é uma otimização de memória e um contrato implícito com o scheduler. Se o worker executa o scheduler, precisa herdar essa restrição. Ou os start-args do workflow enviam edges já enxutas.
Prioridade média. Não é blocker. É preciso preservar o contrato implícito da fase 4 (só errorMessage desta execução sobrevive).
Atenção. Se a lista de chaves acumuladas crescer (por exemplo, adicionar errorCode), atualizar tanto stripStaleErrorState quanto o coletor da fase 4 para manter a consistência.

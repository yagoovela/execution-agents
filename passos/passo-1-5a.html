Step 1.5a — stripStaleErrorState + edge assembly

Block in flux.service.ts:2513-2520. Sanitizes the nodes from the previous execution. Removes accumulated error state (errorMessage, errorStatusCode, hasExecutionError). Reduces each edge to only the 5 fields the scheduler actually reads. The stripStaleErrorState implementation is at flux.service.ts:444-459.
In summary — what this step does
  • Cleans leftovers of previous errors on each node. If the previous execution failed and left errorMessage, errorStatusCode or hasExecutionError written to node.data (via persistNodeSuccess in phase 4), this function removes them. Prevents the error collector in step 4.2 from confusing old error with current execution error.
  • Descends one extra level. If node.data.text is an object (not a string), also clears errorMessage and errorStatusCode in there. Covers the commandContentNode case, which writes errors inside data.text.errorMessage.
  • Returns a fresh array (immutable). Nothing is mutated in-place. .map(node => ...) returns new nodes with spread data. Critical. The original versions in the database must not be modified until persistNodeSuccess writes again.
  • Reduces each edge to the minimal shape. Keeps only { id, source, sourceHandle, target, targetHandle }. Drops data, type, coordinates and style. Everything the frontend uses, but the scheduler doesn't need. Reduces memory footprint when the main loop iterates hundreds of times reading edges.
  • Downstream. The returned array is assigned to const nodes = .... Becomes let updatedFlows = [...nodes] on line 2523. From here on, this is the canonical array for the entire execution. The edges become source of truth for the scheduler to find next nodes.
Context. This sanitization prevents a classic bug. Without the strip, the phase 4 error collector (the nodesWithError filter) would also pick nodes that failed in a past execution but ran OK now. It would mark the current execution as a failure.

A stripStaleErrorState(nodes)
flux.service.ts:2513 (call) + 444-459 (impl)
private stripStaleErrorState(nodes: any[]): any[]
Purpose. Removes accumulated error state written to each node's data in previous executions. If the past execution wrote errorMessage, errorStatusCode or hasExecutionError via persistNodeSuccess, this function cleans them before the new execution starts.
In summary. Each node in the database may have inherited dirt from past executions. If an apiCaller failed yesterday, the error message stayed in data.errorMessage. The function walks the list, takes a copy of each data, deletes the errorMessage, errorStatusCode and hasExecutionError keys. Descends one more level. If data.text is an object, cleans in there too. commandContentNode historically nested errors under data.text.errorMessage. Always returns a new array. Never mutates the original. Preserves what came from the database. Without this pass, the nodesWithError filter in phase 4 would raise a false positive. Nodes that executed OK, but had a past error marked, would be counted as errors of this execution.

getFlow.nodes comes from the database via flowService.getFlowWithNodesAndEdges (step 1.2). The returned array is the canonical input for the execution loop. Becomes updatedFlows on the next line.

private stripStaleErrorState(nodes: any[]): any[] { return nodes.map(node => { if (!node?.data) return node; const cleanData = { ...node.data }; delete cleanData.errorMessage; delete cleanData.errorStatusCode; delete cleanData.hasExecutionError; if (cleanData.text && typeof cleanData.text === 'object') { const cleanText = { ...cleanData.text }; delete cleanText.errorMessage; delete cleanText.errorStatusCode; cleanData.text = cleanText; } return { ...node, data: cleanData }; }); }

🧹 Keys removed
1 data.errorMessage delete

4b data.text.errorStatusCode (if text is object) delete
🎯 Why 2 levels?
commandContentNode stores the whole result in data.text as an object ({ result, errorMessage, ... }). Other nodes use data.text as a string. The typeof === 'object' distinguishes the two. Only descends when it's an object.
📎 Where these fields are written
persistNodeSuccess (worker and backend) writes these 3 fields to the node's data when the node fails during execution. They stay persisted in Postgres until the next execution, when this function cleans them.
⚠️ Only 3 keys. Not exhaustive
If some node type writes error to another key (e.g. data.errorCode or data.stackTrace), this function won't catch it. Needs to stay in sync with what persistNodeSuccess writes.
🔧 Immutability via spread
{ ...node, data: cleanData }. The spread creates new references at both levels. The original in getFlow.nodes stays intact. Important if something downstream wants to inspect the pre-strip.
B Lean edge assembly
flux.service.ts:2514-2520
const edges = getFlow.edges.map(edge => ({ id, source, sourceHandle, target, targetHandle }))
Purpose. Reduces each database edge to just the 5 fields the scheduler actually reads when deciding the route between nodes. Drops visual metadata (type, data, animations, style, position). Only the frontend uses these fields.
In summary. Edges in the database carry fields that only matter for drawing the graph. type, data, animations, style, handle color. It's all visual baggage. The scheduler only needs source, target and the handle on each side to decide the next node. The line does a .map() that keeps only the 5 relevant keys. Effects. Less memory. If a flow has 500 edges with heavy data, it cuts significantly. Less attention surface. Whoever reads the main loop doesn't ask if edge.data is used. Strong immutability. Whoever wants to mutate an edge creates a new one with only these 5 fields. Trade-off. If the scheduler ever needs another edge field (e.g. edge.type to distinguish conditional edges), it must be added here explicitly.

📎 Order in the map
Order in the {...} literal is id, source, sourceHandle, target, targetHandle. Reflects what shows up on the diagram (edge going from source to target).
⚠️ Silent field loss
If the edges schema gains a new field (e.g. edge.condition for branch semantics), this map won't propagate it. It's an easy bug to hide.
🔧 Not a deep-clone
Each string is copied by value (JavaScript primitives). If a field turns into an object, the spread here would take it by reference. In that case, mutating edge.X would mutate the DB too.
C Downstream use. How this prevents bugs in phase 4
flux.service.ts:4854 (nodesWithError filter)
// Phase 4 error collector: nodesWithError = myUpdatedNodes.filter(n => n.data.errorMessage)
Purpose. Makes clear why the strip is needed. In phase 4, the error collector reads node.data.errorMessage to build nodesWithError. If the old error remained in data, it would trigger a false positive.
In summary. Phase 4 of apiV2 (finalization) runs a simple filter. Which nodes have errorMessage? Uses the answer to decide whether the whole execution was success or error. If stripStaleErrorState didn't run, the scenario would be as follows. Execution 1 fails on an apiCaller and writes errorMessage. Execution 2 begins. That same apiCaller isn't even executed (maybe because the flow took a different branch). At phase 4, the collector sees the old error still present and concludes the execution failed. Result. Wrong metrics, wrong notification, flow log with wrong status. The prior strip ensures nodes start clean. The only way errorMessage can appear there is the current execution having failed on it.

Cumulative effect of the strip
With stripStaleErrorState. The only errorMessage that survives to phase 4 is what this execution wrote. Without it. False positives and logs corrupted by past executions.
🎯 The implicit contract
If a node has errorMessage after the loop, it's because it failed in this execution. This contract only holds if some strip ran before. If a refactor removes this strip, the contract breaks silently.
📎 Step 1.5b vs 1.5a
1.5a cleans past-execution errors. 1.5b (same block, lines 2525-2558) cleans past-execution output for nodes with clearOnExecution on. They are distinct sanitizations with distinct purposes.
⚠️ getFlow.nodes still with error state
getFlow.nodes (the DB original) still carries the error state. If any future code reads directly from getFlow.nodes instead of nodes, it gets the dirty value.
🔧 Alternative not used
Could be done via UPDATE in the DB before execution starts (clean via SQL). Not done. Instead, keeps the state in the database (useful for post-mortem debug) and cleans in memory for this execution.

Observações para migração:
stripStaleErrorState é função pura. Replicável 1 para 1 no worker sem esforço.
Se a migração passar a limpar error state no banco antes da execução (via UPDATE), esse método pode até sumir. Cuidado. Perde a granularidade de "limpo em memória sem alterar o Postgres até o próximo persist".
O shape enxuto de edges é uma otimização de memória e um contrato implícito com o scheduler. Se o worker executa o scheduler, precisa herdar essa restrição. Ou os start-args do workflow enviam edges já enxutas.
Prioridade média. Não é blocker. É preciso preservar o contrato implícito da fase 4 (só errorMessage desta execução sobrevive).
Atenção. Se a lista de chaves acumuladas crescer (por exemplo, adicionar errorCode), atualizar tanto stripStaleErrorState quanto o coletor da fase 4 para manter a consistência.

Passo 1.5a — stripStaleErrorState + montagem de edges

Bloco em flux.service.ts:2513-2520. Higieniza os nodes do run anterior removendo error-state gruda (errorMessage, errorStatusCode, hasExecutionError) e reduz cada edge a apenas os 5 campos que o scheduler realmente lê. Impl de stripStaleErrorState em flux.service.ts:444-459.
Em resumo — o que esse passo faz
  • Limpa restos de erros anteriores em cada node: se o run anterior falhou e deixou errorMessage, errorStatusCode ou hasExecutionError gravados no node.data (via persistNodeSuccess na fase 4), essa função remove — evita que o coletor de erros do passo 4.2 confunda erro velho com erro novo do run atual.
  • Cai um nível de profundidade a mais: se node.data.text for objeto (não string), também limpa errorMessage/errorStatusCode lá dentro. Isso pega o caso do commandContentNode que grava erros dentro de data.text.errorMessage.
  • Retorna um array novo (imutável): nada é mutado in-place — .map(node => ...) devolve nodes novos com data spread. Isso é crítico porque as versões originais no banco não devem ser mexidas até que persistNodeSuccess escreva de novo.
  • Enxuga cada edge pro shape mínimo: pega só { id, source, sourceHandle, target, targetHandle }. Descarta data, type, coordenadas, style — tudo que o frontend usa mas o scheduler não precisa. Reduz footprint em memória quando o loop principal iterar centenas de vezes lendo edges.
  • Downstream: o array retornado é atribuído a const nodes = ..., que vira let updatedFlows = [...nodes] na linha 2523 — a partir daqui, esse é o array canônico do run inteiro. Os edges viram source of truth pra scheduler encontrar next nodes.
Contexto: essa higienização evita um bug clássico — sem o strip, o coletor de erros da fase 4 (nodesWithError filter) pegaria também nodes que falharam num run passado mas rodaram OK agora, marcando o run atual como falho erroneamente.

A stripStaleErrorState(nodes)
flux.service.ts:2513 (call) + 444-459 (impl)
private stripStaleErrorState(nodes: any[]): any[]
Propósito: Remove error state gruda gravado no data de cada node em runs anteriores. Se o run passado gravou errorMessage, errorStatusCode ou hasExecutionError via persistNodeSuccess, essa função limpa antes do run novo começar.
Em resumo: é o zelador que passa antes do run começar. Cada node no banco pode ter herdado sujeira de execuções passadas — se um apiCaller falhou ontem, o error message ficou salvo em data.errorMessage. Essa função corre a lista, tira uma cópia de cada data, apaga as chaves errorMessage, errorStatusCode, hasExecutionError e ainda desce um nível — se data.text for objeto (não string), limpa lá dentro também, porque commandContentNode historicamente aninhava erros em data.text.errorMessage. Retorna sempre um array novo — nunca muta o original — pra preservar o que veio do banco. Sem essa passada, o filtro nodesWithError na fase 4 sinalizaria falso positivo: nodes que rodaram OK mas tinham error de run passado marcado seriam contados como "erros deste run".

private stripStaleErrorState(nodes: any[]): any[] { return nodes.map(node => { if (!node?.data) return node; const cleanData = { ...node.data }; delete cleanData.errorMessage; delete cleanData.errorStatusCode; delete cleanData.hasExecutionError; if (cleanData.text && typeof cleanData.text === 'object') { const cleanText = { ...cleanData.text }; delete cleanText.errorMessage; delete cleanText.errorStatusCode; cleanData.text = cleanText; } return { ...node, data: cleanData }; }); }

🎯 Por que 2 níveis?
commandContentNode guarda todo o resultado em data.text como objeto ({ result, errorMessage, ...}). Outros nodes usam data.text como string. O typeof === 'object' distingue os dois e só desce quando é objeto.
📎 Onde esses campos são gravados
persistNodeSuccess (worker + backend) grava esses 3 campos no data do node quando node falha durante execução. Ficam persistidos no Postgres até o próximo run, quando essa função limpa.
⚠️ Só 3 chaves — não é exhaustive
Se algum node type gravar erro em outra chave (ex.: data.errorCode, data.stackTrace), essa função não pega. Precisa manter sincronizado com o que persistNodeSuccess grava.
🔧 Imutabilidade via spread
{ ...node, data: cleanData } — spread cria referências novas em ambos níveis. O original em getFlow.nodes continua intacto (importante se algo mais adiante quiser inspecionar o pré-strip).
B Montagem enxuta de edges
flux.service.ts:2514-2520
const edges = getFlow.edges.map(edge => ({ id, source, sourceHandle, target, targetHandle }))
Propósito: Reduz cada edge do banco a só os 5 campos que o scheduler realmente lê ao decidir "de onde pra onde ir". Descarta metadata visual (type, data, animações, style, position) que só o frontend usa.
Em resumo: as edges no banco carregam um monte de coisa que só interessa pra desenhar o grafo — type, data, animações, estilo, cor de handle, tudo bagagem visual. O scheduler precisa apenas de "quem é o source, quem é o target, qual handle de cada lado" pra decidir o próximo node. Essa linha faz um .map() que pega só as 5 chaves relevantes. Efeito: (1) menos memória — se um flow tem 500 edges com data pesado, isso corta pesadamente; (2) menos superfície de atenção — quem lê o loop principal não fica se perguntando "hmm, essa edge.data aqui é usada?"; (3) imutabilidade forte — quem quiser mutar o edge tem que criar um novo com só esses 5 campos. Trade-off: se algum dia o scheduler precisar de outro campo do edge (ex.: edge.type pra diferenciar edges "condicionais" das normais), tem que ser adicionado aqui explicitamente.

📎 Ordem no map
A ordem no {...} literal é: id, source, sourceHandle, target, targetHandle — reflete o que aparece na visualização (aresta indo de source→target).
⚠️ Perda silenciosa de campos
Se o schema de edges ganhar um campo novo (ex.: edge.condition pra branch semantics), esse map não vai propagar. Bug fácil de esconder.
🔧 Não é deep-clone
Cada string é copiada por valor (JS primitives). Mas se algum dia um campo virasse objeto, o spread aqui pegaria por referência — nesse caso, mutar edge.X mutaria o banco também.
C Uso downstream — como isso previne bugs na fase 4
flux.service.ts:4854 (nodesWithError filter)
// Coletor de erros da fase 4: nodesWithError = myUpdatedNodes.filter(n => n.data.errorMessage)
Propósito: Deixar claro por que o strip é necessário. Na fase 4, o coletor de erros lê node.data.errorMessage pra montar nodesWithError — se error velho estivesse gruda no data, marcaria falso positivo.
Em resumo: a fase 4 do apiV2 (encerramento) faz um filtro simples: "quais nodes têm errorMessage?" — e usa a resposta pra decidir se o run inteiro foi sucesso ou erro. Se stripStaleErrorState não rodasse, o cenário seria: run 1 falhou num apiCaller, gravou errorMessage. Run 2 começa, esse mesmo apiCaller nem é executado (talvez porque o flow rodou uma branch diferente). Na fase 4, o coletor vê o error message velho ainda ali e conclui "esse run falhou". Resultado: métricas erradas, notificação errada, flow log com status errado. O strip prévio garante que os nodes começam limpos, então o único jeito de aparecer errorMessage lá é o run atual ter falhado nele.

Efeito cumulativo do strip
Com stripStaleErrorState: o único errorMessage que sobrevive até a fase 4 é o que este run gravou. Sem ele: falsos positivos e logs corrompidos por runs passados.
🎯 O contract implícito
"Se um node tem errorMessage depois do loop, é porque falhou neste run" — esse contract só vale se algum strip rodou antes. Se em algum refactor esse strip sumir, o contract quebra silenciosamente.
📎 Passo 1.5b vs 1.5a
1.5a limpa erros de runs passados. 1.5b (mesmo bloco, linhas 2525-2558) limpa output de runs passados pra nodes com clearOnExecution ligado. São higienizações distintas com propósitos distintos.
⚠️ getFlow.nodes ainda com error state
getFlow.nodes (o original do banco) continua com o error state. Se algum código futuro ler direto de getFlow.nodes em vez de nodes, pega o sujo.
🔧 Alternativa não-usada
Poderia ter feito UPDATE no banco antes do run começar (limpar via SQL). Não é feito — em vez disso, mantém o estado no banco (útil pra debug post-mortem) e limpa em memória pra este run.
Resumo — o que sai de 1.5a:
• const nodes — cópia enxuta e limpa dos nodes (sem error state gruda)
• const edges — cópia enxuta com só 5 campos por edge
• Alocações: N + M objetos novos (N nodes, M edges) — todos rasos
• Zero I/O — puro compute em memória
• Contract preservado: quaisquer errorMessage no data depois desse ponto vem deste run
Observações para migração:
• stripStaleErrorState é função pura — replicável 1:1 no worker sem esforço.
• Se a migração passar a limpar error state no banco antes do run (via UPDATE), esse método pode até sumir. Mas cuidado: perde a granularidade de "limpo em memória sem alterar o Postgres até o próximo persist".
• O shape enxuto de edges é uma otimização de memória e um contract implícito com o scheduler. Se o worker rodar o scheduler, precisa herdar essa restrição — ou o start-args do workflow envia edges já enxutas.
• Prioridade média: não é blocker, mas é preciso preservar o "contract implícito" da fase 4 (só errorMessage deste run sobrevive).
• Watch out: se a lista de chaves erradas crescer (ex.: adicionar errorCode), atualizar ambos stripStaleErrorState e o coletor da fase 4 pra continuar consistente.

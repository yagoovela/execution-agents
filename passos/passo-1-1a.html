Passo 1.1a — Serviços auxiliares acionados pela fila

Bloco em apiV2Job.processor.ts:38-42 (injects), :63-108 (start/mid) e :133-152 (catch). O processor grava rastreamento em duas tabelas independentes. mcp_run_status via McpRunStatusService. E flow_execution_status via FlowExecutionStatusService. Cada uma é opcional. É ativada por gate diferente no payload.
Em resumo — o que esse passo faz
  • Dois rastreadores independentes convivem. O processor injeta McpRunStatusService e FlowExecutionStatusService. Cada um escreve numa tabela própria com colunas parecidas mas separadas. Nenhum dos dois é obrigatório. Ambos têm gate.
  • Gate MCP. Só grava em mcp_run_status se params.mcpTracking veio preenchido no payload. É um objeto com { workspaceId, agentId, tokenId }. Só acontece quando a execução foi disparada via MCP tool.
  • Gate FES. Só grava em flow_execution_status se params.executionId veio no payload. Esse ID é criado por endpoints HTTP de trigger que oferecem callback opt-in. O cliente cria o registro antes de enfileirar.
  • Marcações em pares. Antes do apiV2, markRunning (MCP) e markInProgress (FES). Depois do apiV2, markFinished (MCP) com status completed ou error, e markCompleted ou markError (FES). Ambos recebem durationMs, tokens e cost.
  • Catch replica tudo. Em exceção, ambas as marcações finais executam de novo com status: 'error', tokens 0, cost 0 e a mensagem do erro. Nada é deixado em in_progress.
  • Consumo. MCP é lida pela API do MCP (endpoints de status e run history da tool). FES é lida por endpoints REST que fazem polling do status de execuções trigadas. O cliente consulta pelo executionId.
Contexto. Essas duas tabelas foram criadas em épocas diferentes para necessidades parecidas. MCP surgiu para atender a ferramenta MCP (agente conversando com Claude, etc.). FES surgiu para callbacks REST v2 (webhooks confiáveis). Elas não se conversam. Se a mesma execução precisar dos dois, o processor escreve nos dois lugares.
Cadeia de chamadas em 1.1a
A · gate MCPmarkRunning(processId) → BmarkFinished({status, tokens, cost, durationMs, error}) → C · gate FESmarkInProgress(id) → DmarkCompleted / markError
Resultado final. 0, 1 ou 2 linhas atualizadas em tabelas diferentes conforme os gates. Colunas tokens, cost e durationMs só ficam corretas no happy path. No catch vão zeradas.

Propósito. Marca a linha do MCP como in_progress. Sinaliza que o job Bull saiu de pending (criada pelo endpoint MCP) e entrou em execução. Só executa se params.mcpTracking veio preenchido no payload.
Em resumo. Quando a execução começa via MCP, existe uma linha em mcp_run_status com status pending. Foi criada pelo endpoint que chamou a tool. Se o processId não bate com nada, o UPDATE some silenciosamente. Se a execução veio de outro caminho que não é MCP (por exemplo, trigger interno de flowCallerNode), esse método não é chamado. A tabela MCP é ignorada.

🎯 Extract type. Status restrito
status: Extract<McpRunStatusValue, 'completed' | 'error'>. O TypeScript impede passar pending ou in_progress para o markFinished. É segurança de tipo para evitar corromper a máquina de estado.
⚠️ Catch zera métricas reais
Se o apiV2 lançou exceção depois de fazer chamadas caras a provedores (Anthropic, OpenAI), os tokens e cost reais ficam invisíveis nessa tabela. Ficam em 0. A contabilidade fica bugada. Para billing preciso, é necessário cruzar com outras fontes (logs de provider, run log).
📎 Diferença em relação a markCancelled
Existe também markCancelled(id) (mcp-run-status.service.ts:66-71). Grava { status: 'error', errorMessage: 'Run cancelled' } sem tocar em tokens e cost. Usado por endpoint de cancel. Não é chamado pelo processor aqui.
🔧 Timestamps automáticos
updatedAt é atualizado sozinho via @UpdateDateColumn. O createdAt foi atribuído em createPending. Não há finishedAt explícito. O timestamp de fim é implicitamente o updatedAt da última mudança.
C FlowExecutionStatusService.markInProgress(executionId) condicional
flow-execution-status.service.ts:28-33
async markInProgress(id: string): Promise<void> // status='in_progress', startedAt=NOW()
Propósito. Marca a linha em flow_execution_status como in_progress e grava o timestamp de início. É o análogo de markRunning para o rastreamento REST v2, independente do MCP.
Em resumo. Se a execução veio de um endpoint REST v2 que oferece callback opt-in, o endpoint criou uma linha pending em flow_execution_status antes de enfileirar (via create) e passou o executionId no payload. Aqui o processor confere. Se o executionId existe, chama markInProgress. Essa chamada faz o UPDATE trocando o status para in_progress e populando startedAt com new Date(). A diferença importante em relação ao markRunning do MCP é o timestamp explícito. FES tem startedAt e finishedAt explícitos. MCP não tem (só o updatedAt automático). Consequência. No FES, dá para calcular a duração diretamente pelas colunas. No MCP, só via o campo durationMs que o processor calcula em memória.

🔧 startedAt versus createdAt
createdAt. Momento em que a linha foi criada em pending. Geralmente milissegundos antes do enqueue.
startedAt. Momento em que o job saiu de pending para in_progress (aqui). A diferença mede o tempo em fila.
D FlowExecutionStatusService.markCompleted / markError
flow-execution-status.service.ts:35-74
async markCompleted({ id, output, tokensUsed, totalCost, durationMs })
async markError({ id, errorMessage, tokensUsed, totalCost, durationMs })
Propósito. Fecham a linha do FES com resultado. markCompleted grava o output completo em jsonb e limpa o errorMessage. markError grava só a mensagem de erro. Ambos atribuem finishedAt: new Date().
Em resumo. Essa dupla é o fechamento da linha FES. O processor decide qual chamar olhando result.nodeError. Se veio preenchido, markError. Caso contrário, markCompleted. A diferença essencial entre os dois. markCompleted salva o result inteiro no campo output (jsonb). Permite que consultas futuras recuperem o payload de resposta. markError guarda só a string do erro. Os dois zeram tokens e cost separadamente quando o processor entrega 0 (no catch). Assim como no MCP, o finishedAt é o momento do UPDATE, não o fim real do apiV2, que teria sido milissegundos antes. Fica bem próximo, mas não é o mesmo timestamp.

🎯 output em jsonb
output é jsonb nullable. Recebe o objeto result inteiro do apiV2. Inclui outputs[], totalTokensUsed, totalCost e potencialmente muito mais, dependendo da execução. Pode crescer bastante em execuções grandes.

O cliente REST que fizer GET no status vai ver tudo.
⚠️ markError não limpa output
Diferente de markCompleted (que limpa errorMessage: null), o markError não zera o campo output. Se por algum motivo a linha já tinha um output de tentativa anterior, ele permanece. É baixo risco por attempts: 1, mas latente.
📎 finishedAt é o timestamp do UPDATE
Não é o momento exato em que o apiV2 retornou. É o UPDATE em si. A diferença é mínima (o UPDATE roda logo depois). Se o markCompleted travar (lock, connection pool), finishedAt mostra o tempo do UPDATE, não do fim da execução.
🔧 Nullish coalescing defensivo
result.totalTokensUsed ?? 0 e result.totalCost ?? 0. Se o apiV2 não populou (retornou undefined), o UPDATE ainda tem valores numéricos válidos. A coluna é float default 0. Preserva o tipo.
Resumo. O que sai de 1.1a:
0, 1 ou 2 linhas atualizadas em tabelas independentes. mcp_run_status se há mcpTracking. flow_execution_status se há executionId. Uma mesma execução pode escrever em zero, uma ou nas duas.
Sequência em cada tabela. pending (criada por quem enfileirou), in_progress (aqui, antes do apiV2) e completed ou error (aqui, depois do apiV2 ou no catch).
Métricas. tokens, cost e durationMs corretos no happy path. Zeram no catch mesmo se o apiV2 já consumiu tokens caros antes do throw.
flow_execution_status tem startedAt e finishedAt explícitos e persiste o output em jsonb. mcp_run_status não tem.
Observações para migração:
Duplicidade de rastreamento é o maior débito técnico aqui. Duas tabelas independentes, com colunas parecidas (tokens, cost, durationMs, status), gates separados e sem foreign key entre elas. Se o worker Temporal absorver a execução, é o momento ideal para consolidar numa flow_execution_status unificada. Um campo mcpRunId nullable pode preservar a granularidade MCP.
Se ficarem separadas, ambas viram activities Temporal. markInProgressActivity, markCompletedActivity e markErrorActivity. Vantagem. O Temporal garante que a activity executa pelo menos uma vez (retry configurável). Corrige o problema atual em que a linha nunca sai de in_progress quando o job estoura o timeout do Bull.
Ordem importa. Hoje o processor faz markRunning antes de markInProgress. Se migrar, convém manter (algum código de status usa ordem cronológica). No Temporal, fica await activity(mcp); await activity(fes).
Riscos de deixar para depois. O tokens: 0 e cost: 0 no catch é um bug real de contabilidade. Se uma execução gastou $10 em tokens e falhou no final, o billing perde essa cobrança. Vale corrigir em conjunto. result?.totalTokensUsed ?? tokensAcumuladosPorNodesJaExecutados.
Se um serviço equivalente ao FlowExecutionStatusService precisar ser criado ou renomeado no worker, o arquivo src/app-api/flux/flow-execution-status.service.ts é a fonte canônica atual. Mover para src/shared/ ou src/services/ antes da migração para ser consumível pelo worker.

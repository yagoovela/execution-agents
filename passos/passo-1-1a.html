Passo 1.1a — Serviços auxiliares acionados pela fila

Bloco em apiV2Job.processor.ts:38-42 (injects) + :63-108 (start/mid) + :133-152 (catch). O processor grava rastreamento em duas tabelas independentes: mcp_run_status (via McpRunStatusService) e flow_execution_status (via FlowExecutionStatusService). Cada uma é opcional e ativada por gate diferente no payload.
Em resumo — o que esse passo faz
  • Dois rastreadores independentes convivendo: o processor injeta McpRunStatusService E FlowExecutionStatusService — cada um escreve numa tabela própria, com colunas parecidas mas separadas. Nenhum dos dois é obrigatório; ambos têm gate.
  • Gate MCP: só grava em mcp_run_status se params.mcpTracking veio preenchido no payload — objeto com { workspaceId, agentId, tokenId }. Isso só acontece quando o run foi disparado via MCP tool.
  • Gate FES: só grava em flow_execution_status se params.executionId veio no payload. Esse ID é criado por endpoints HTTP de trigger que oferecem callback opt-in (o cliente cria o registro antes de enfileirar).
  • Marcações em pares: antes do apiV2 ⇒ markRunning (MCP) + markInProgress (FES). Depois do apiV2 ⇒ markFinished (MCP) com status completed/error + markCompleted/markError (FES). Ambos recebem durationMs, tokens e cost.
  • Catch replica tudo: em exception, ambas as marcações finais rodam de novo com status: 'error', tokens 0, cost 0, e a mensagem do erro. Nada é deixado em in_progress.
  • Consumo: MCP é lida pela API do MCP (endpoints de status/run history da tool). FES é lida por endpoints REST que polling do status de execuções trigadas — cliente consulta pelo executionId.
Contexto: essas duas tabelas foram criadas em épocas diferentes pra necessidades parecidas. MCP surgiu pra atender a ferramenta MCP (agente conversando com Claude/etc.); FES surgiu pra callbacks REST v2 (webhooks confiáveis). Elas não se conversam — se o mesmo run precisar dos dois, o processor escreve nos dois lugares.
Cadeia de chamadas em 1.1a
A · gate MCPmarkRunning(processId) → BmarkFinished({status, tokens, cost, durationMs, error}) → C · gate FESmarkInProgress(id) → DmarkCompleted / markError
Resultado final: 0, 1 ou 2 rows atualizadas em tabelas diferentes conforme os gates. Colunas tokens/cost/durationMs só ficam corretas no happy path — no catch vão zeradas.
A McpRunStatusService.markRunning(processId) condicional
mcp-run-status.service.ts:38-40
async markRunning(id: string): Promise<void> // UPDATE mcp_run_status SET status='in_progress' WHERE id=$1
Propósito: Marca a row do MCP como in_progress — sinaliza que o job Bull saiu da pending (criada pelo endpoint MCP) e entrou em execução. Só executa se params.mcpTracking veio preenchido no payload.
Em resumo: pense nele como um vigia da linha de produção. Quando o run começa via MCP, existe uma row lá em mcp_run_status com status pending (criada pelo endpoint que chamou a tool). O processor entra em ação, vê que o payload tem mcpTracking, e sacode aquela row: "opa, agora está rodando de verdade". É uma única query UPDATE — nenhuma checagem de existência, nenhum retorno. Se o processId não bater com nada, o UPDATE some silenciosamente. E note o gate: se o run veio de outro caminho que não é MCP (ex.: um trigger interno de flowCallerNode), esse método nem é chamado — a tabela MCP ignora.

Propósito: Fecha a row do MCP com resultado — status completed ou error + métricas totais. Chamado no happy path (com valores reais) e no catch (com zeros).
Em resumo: é o fechamento da linha de produção pra MCP. Recebe 6 campos e faz uma única query UPDATE populando todos: status, tokens, cost, durationMs, errorMessage. ⚠️ Catch zera métricas reais

📎 Diferença vs markCancelled

🔧 Timestamps automáticos
updatedAt é atualizado sozinho via @UpdateDateColumn. O createdAt foi setado no createPending. Não tem finishedAt explícito — o timestamp de fim é implicitamente o updatedAt da última mudança.
C FlowExecutionStatusService.markInProgress(executionId) condicional
flow-execution-status.service.ts:28-33
async markInProgress(id: string): Promise<void> // status='in_progress', startedAt=NOW()
Propósito: Marca a row em flow_execution_status como in_progress e grava o timestamp de início. É o análogo do markRunning pro rastreamento REST v2 (independente do MCP).
Em resumo: é o equivalente do vigia, mas pra outra tabela. Se o run veio de um endpoint REST v2 que oferece callback opt-in, o endpoint criou uma row pending em flow_execution_status antes de enfileirar (via create), e passou o executionId no payload. Aqui o processor confere: se o executionId existe, chama markInProgress — que faz o UPDATE trocando status pra in_progress e populando startedAt com new Date(). Essa diferença é importante em relação ao markRunning do MCP: FES tem startedAt/finishedAt explícitos, MCP não tem (só o updatedAt automático). Consequência: no FES, dá pra calcular a duração diretamente pelas colunas; no MCP, só via o campo durationMs que o processor calcula em memória.

D FlowExecutionStatusService.markCompleted / markError
flow-execution-status.service.ts:35-74
async markCompleted({ id, output, tokensUsed, totalCost, durationMs })
async markError({ id, errorMessage, tokensUsed, totalCost, durationMs })
Propósito: Fecham a row do FES com resultado. markCompleted grava o output completo em jsonb e limpa o errorMessage; markError grava só a mensagem de erro. Ambos setam finishedAt: new Date().
Em resumo: essa dupla é o ponteiro final da linha FES. O processor decide qual chamar olhando result.nodeError: se veio preenchido, markError; senão, markCompleted. A diferença essencial entre os dois: markCompleted salva o result inteiro no campo output (jsonb) — permite consultas futuras recuperarem o payload de resposta —, enquanto markError guarda só a string do erro. E os dois zeram tokens/cost separadamente quando o processor entrega 0 (no catch). Assim como no MCP, o finishedAt é o momento do UPDATE — não do fim real do apiV2, que teria sido milissegundos antes. Fica bem próximo, mas não é o mesmo timestamp.

🎯 output no jsonb
output é jsonb nullable — recebe o objeto result inteiro do apiV2. Isso inclui outputs[], totalTokensUsed, totalCost, e potencialmente muito mais dependendo do run. Pode crescer bastante em runs grandes.

Cliente REST que fizer GET no status vai ver isso tudo.
⚠️ markError NÃO limpa output
Diferente do markCompleted (que limpa errorMessage: null), o markError não zera o campo output. Se por algum motivo a row já tinha um output de tentativa anterior, ele fica. Baixo risco porque attempts: 1, mas latente.
📎 finishedAt = timestamp do UPDATE
Não é o momento exato em que o apiV2 retornou — é o UPDATE em si. A diferença é minúscula (o UPDATE roda logo depois), mas se o markCompleted travar (lock, connection pool), finishedAt mostra o tempo do UPDATE, não do fim de execução.
🔧 Nullish coalescing defensivo
result.totalTokensUsed ?? 0 e result.totalCost ?? 0 — se o apiV2 não populou (retornou undefined), o UPDATE ainda tem valores numéricos válidos. Coluna é float default 0, então preserva o tipo.
Resumo — o que sai de 1.1a:
• 0, 1 ou 2 rows atualizadas em tabelas independentes: mcp_run_status se mcpTracking, flow_execution_status se executionId. Um mesmo run pode escrever em zero, um ou nos dois.
• Sequência em cada tabela: pending (criada por quem enfileirou) → in_progress (aqui, antes do apiV2) → completed/error (aqui, depois do apiV2 ou no catch).
• Métricas: tokens / cost / durationMs corretas no happy path; zeradas no catch (mesmo se apiV2 já consumiu tokens caros antes do throw).
• flow_execution_status tem startedAt/finishedAt explícitos e persiste o output em jsonb — mcp_run_status não.
Observações para migração:
• Duplicidade de rastreamento é o maior débito técnico aqui. Duas tabelas independentes, com colunas parecidas (tokens/cost/durationMs/status), gates separados, sem foreign key entre elas. Se o worker Temporal absorver a execução, é a hora ideal pra consolidar numa flow_execution_status unificada (com um campo mcpRunId nullable, se ainda precisar da granularidade MCP).
• Se ficarem separadas, ambas viram atividades Temporal: markInProgressActivity, markCompletedActivity, markErrorActivity. Vantagem: Temporal garante que a atividade roda ao menos uma vez (retry configurável), corrigindo o problema atual de "row nunca sai de in_progress" quando o job estoura timeout do Bull.
• Ordem importa: hoje o processor faz markRunning ANTES de markInProgress. Se migrar, é bom manter (algum código de status usa ordem cronológica). No Temporal fica await activity(mcp); await activity(fes).
• Riscos de deixar pra depois: o tokens: 0 / cost: 0 no catch é um bug de contabilidade real — se um run gastou $10 em tokens e crashou no final, o billing perde essa cobrança. Vale corrigir junto: result?.totalTokensUsed ?? tokensAcumuladosPorNodesJaExecutados.
• Se um serviço equivalente à FlowExecutionStatusService precisar ser criado ou renomeado no worker, o arquivo src/app-api/flux/flow-execution-status.service.ts é a fonte canônica atual — mover pra src/shared/ ou src/services/ antes da migração pra ser consumível pelo worker.

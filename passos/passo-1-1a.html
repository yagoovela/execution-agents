Step 1.1a — Auxiliary services triggered by the queue

Block at apiV2Job.processor.ts:38-42 (injects), :63-108 (start/mid), and :133-152 (catch). The processor writes tracking to two independent tables. mcp_run_status via McpRunStatusService. And flow_execution_status via FlowExecutionStatusService. Each one is optional. Enabled by a different payload gate.
In short — what this step does
  • Two independent trackers coexist. The processor injects McpRunStatusService and FlowExecutionStatusService. Each one writes to its own table with similar but separate columns. Neither is mandatory. Both are gated.
  • MCP gate. Only writes to mcp_run_status if params.mcpTracking is present in the payload. It is an object with { workspaceId, agentId, tokenId }. Only happens when the execution was fired via the MCP tool.
  • FES gate. Only writes to flow_execution_status if params.executionId is in the payload. This ID is created by trigger HTTP endpoints that offer opt-in callback. The client creates the record before enqueueing.
  • Paired markings. Before apiV2, markRunning (MCP) and markInProgress (FES). After apiV2, markFinished (MCP) with status completed or error, and markCompleted or markError (FES). Both receive durationMs, tokens, and cost.
  • Catch mirrors everything. On exception, both final markings run again with status: 'error', tokens 0, cost 0, and the error message. Nothing is left in in_progress.
  • Consumption. MCP is read by the MCP API (status and run history tool endpoints). FES is read by REST endpoints polling the status of triggered executions. The client queries by executionId.
Context. These two tables were created at different times for similar needs. MCP came up to serve the MCP tool (agent talking to Claude, etc.). FES came up for REST v2 callbacks (reliable webhooks). They do not talk to each other. If the same execution needs both, the processor writes to both places.
Call chain in 1.1a
A · MCP gatemarkRunning(processId) → BmarkFinished({status, tokens, cost, durationMs, error}) → C · FES gatemarkInProgress(id) → DmarkCompleted / markError
Final result. 0, 1, or 2 rows updated in different tables depending on the gates. tokens, cost, and durationMs columns are only correct on the happy path. On the catch they go as zero.
A McpRunStatusService.markRunning(processId) conditional
mcp-run-status.service.ts:38-40
async markRunning(id: string): Promise<void> // UPDATE mcp_run_status SET status='in_progress' WHERE id=$1
Purpose. Marks the MCP row as in_progress. Signals that the Bull job left pending (created by the MCP endpoint) and started running. Only runs if params.mcpTracking is present in the payload.
In short. When execution begins via MCP, a row already exists in mcp_run_status with pending status. It was created by the endpoint that called the tool. The processor sees the payload has mcpTracking and updates the row to the new state. It is a single UPDATE query. No existence check. No return. If the processId does not match anything, the UPDATE vanishes silently. If the execution came from another path that is not MCP (for example, internal flowCallerNode trigger), this method is not called. The MCP table is ignored.

B McpRunStatusService.markFinished({ id, status, tokens, cost, durationMs, errorMessage })
mcp-run-status.service.ts:42-60
async markFinished(params: { id, status: 'completed' | 'error', tokens, cost, durationMs, errorMessage }): Promise<void>
Purpose. Closes the MCP row with the result. Writes status completed or error, plus the total metrics. Called on the happy path (with real values) and on the catch (with zeros).
In short. Closes the MCP row. Takes 6 fields and does a single UPDATE query populating all of them: status, tokens, cost, durationMs, and errorMessage. The status type is restricted. Only 'completed' or 'error', via Extract<McpRunStatusValue, ...>. It is impossible to mark as in_progress here by mistake. On the happy path, the processor computes real numbers (result.totalTokensUsed, result.totalCost, Date.now() - startedAt). On the catch, values are hardcoded to 0. The query does not assign updatedAt manually. TypeORM handles that via @UpdateDateColumn. Like markRunning, if the id does not exist, the UPDATE disappears without a log.

🎯 Extract type. Restricted status
status: Extract<McpRunStatusValue, 'completed' | 'error'>. TypeScript prevents passing pending or in_progress to markFinished. Type safety to avoid corrupting the state machine.
⚠️ Catch zeros real metrics
If apiV2 threw after making expensive provider calls (Anthropic, OpenAI), the real tokens and cost stay invisible in this table. They stay at 0. Accounting is broken. For accurate billing, you must cross-reference with other sources (provider logs, run log).
📎 Difference vs markCancelled
There is also markCancelled(id) (mcp-run-status.service.ts:66-71). Writes { status: 'error', errorMessage: 'Run cancelled' } without touching tokens and cost. Used by the cancel endpoint. Not called by the processor here.
🔧 Automatic timestamps
updatedAt is updated on its own via @UpdateDateColumn. createdAt was assigned in createPending. There is no explicit finishedAt. The end timestamp is implicitly updatedAt of the last change.
C FlowExecutionStatusService.markInProgress(executionId) conditional
flow-execution-status.service.ts:28-33
async markInProgress(id: string): Promise<void> // status='in_progress', startedAt=NOW()
Purpose. Marks the row in flow_execution_status as in_progress and writes the start timestamp. It is the analog of markRunning for REST v2 tracking, independent from MCP.
In short. If the execution came from a REST v2 endpoint offering opt-in callback, the endpoint created a pending row in flow_execution_status before enqueueing (via create) and passed executionId in the payload. Here the processor checks. If executionId exists, it calls markInProgress. This call does the UPDATE switching the status to in_progress and populating startedAt with new Date(). The important difference from MCP's markRunning is the explicit timestamp. FES has explicit startedAt and finishedAt. MCP does not (only the automatic updatedAt). Consequence. On FES, you can compute duration directly from the columns. On MCP, only via the durationMs field the processor computes in memory.

⚠️ Row must exist beforehand
Like MCP, update({ id }) disappears if the row is missing. The endpoint that enqueues creates it (via create({ id, flowId, userId, callbackUrl })). If the client enqueues without creating first, all this tracking is lost.
🔧 startedAt versus createdAt
createdAt. Moment the row was created as pending. Usually milliseconds before enqueue.
startedAt. Moment the job left pending for in_progress (here). The difference measures time in queue.
D FlowExecutionStatusService.markCompleted / markError
flow-execution-status.service.ts:35-74
async markCompleted({ id, output, tokensUsed, totalCost, durationMs })
async markError({ id, errorMessage, tokensUsed, totalCost, durationMs })
Purpose. Close the FES row with the result. markCompleted writes the full output as jsonb and clears errorMessage. markError writes only the error message. Both assign finishedAt: new Date().
In short. This pair closes the FES row. The processor decides which to call by looking at result.nodeError. If filled, markError. Otherwise, markCompleted. The essential difference between the two. markCompleted saves the entire result in the output field (jsonb). Allows future queries to retrieve the response payload. markError keeps only the error string. Both separately zero out tokens and cost when the processor sends 0 (on the catch). Just like MCP, finishedAt is the UPDATE moment, not the actual end of apiV2, which was milliseconds earlier. Very close, but not the same timestamp.

🎯 output em jsonb
output é jsonb nullable. Recebe o objeto result inteiro do apiV2. Inclui outputs[], totalTokensUsed, totalCost e potencialmente muito mais, dependendo da execução. Pode crescer bastante em execuções grandes.

O cliente REST que fizer GET no status vai ver tudo.
⚠️ markError não limpa output
Diferente de markCompleted (que limpa errorMessage: null), o markError não zera o campo output. Se por algum motivo a linha já tinha um output de tentativa anterior, ele permanece. É baixo risco por attempts: 1, mas latente.
📎 finishedAt é o timestamp do UPDATE
Não é o momento exato em que o apiV2 retornou. É o UPDATE em si. A diferença é mínima (o UPDATE roda logo depois). Se o markCompleted travar (lock, connection pool), finishedAt mostra o tempo do UPDATE, não do fim da execução.
🔧 Nullish coalescing defensivo
result.totalTokensUsed ?? 0 e result.totalCost ?? 0. Se o apiV2 não populou (retornou undefined), o UPDATE ainda tem valores numéricos válidos. A coluna é float default 0. Preserva o tipo.
Resumo. O que sai de 1.1a:
0, 1 ou 2 linhas atualizadas em tabelas independentes. mcp_run_status se há mcpTracking. flow_execution_status se há executionId. Uma mesma execução pode escrever em zero, uma ou nas duas.
Sequência em cada tabela. pending (criada por quem enfileirou), in_progress (aqui, antes do apiV2) e completed ou error (aqui, depois do apiV2 ou no catch).
Métricas. tokens, cost e durationMs corretos no happy path. Zeram no catch mesmo se o apiV2 já consumiu tokens caros antes do throw.
flow_execution_status tem startedAt e finishedAt explícitos e persiste o output em jsonb. mcp_run_status não tem.
Observações para migração:
Duplicidade de rastreamento é o maior débito técnico aqui. Duas tabelas independentes, com colunas parecidas (tokens, cost, durationMs, status), gates separados e sem foreign key entre elas. Se o worker Temporal absorver a execução, é o momento ideal para consolidar numa flow_execution_status unificada. Um campo mcpRunId nullable pode preservar a granularidade MCP.
Se ficarem separadas, ambas viram activities Temporal. markInProgressActivity, markCompletedActivity e markErrorActivity. Vantagem. O Temporal garante que a activity executa pelo menos uma vez (retry configurável). Corrige o problema atual em que a linha nunca sai de in_progress quando o job estoura o timeout do Bull.
Ordem importa. Hoje o processor faz markRunning antes de markInProgress. Se migrar, convém manter (algum código de status usa ordem cronológica). No Temporal, fica await activity(mcp); await activity(fes).
Riscos de deixar para depois. O tokens: 0 e cost: 0 no catch é um bug real de contabilidade. Se uma execução gastou $10 em tokens e falhou no final, o billing perde essa cobrança. Vale corrigir em conjunto. result?.totalTokensUsed ?? tokensAcumuladosPorNodesJaExecutados.
Se um serviço equivalente ao FlowExecutionStatusService precisar ser criado ou renomeado no worker, o arquivo src/app-api/flux/flow-execution-status.service.ts é a fonte canônica atual. Mover para src/shared/ ou src/services/ antes da migração para ser consumível pelo worker.

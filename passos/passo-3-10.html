Step 3.10 — WebSocket notification

Block at flux.service.ts:2288 (socket map setup). emitNodeStatus at several points (around 1837 and 2158). Final return at 5293-5307. Notifies the client in real time via NotificationsGateway (Socket.io) about per-node status.
In short — what this step does
  • Tells the client in real time. During execution, each per-node status change ('RUNNING' becomes 'COMPLETED', 'FAILED', or 'CANCELLED') is emitted via WebSocket. Allows the editor to paint the node card's border yellow, green, or red as the execution progresses.
  • Internal chatbot socket registry. A Map<runLogProcessId, socketId> kept in FluxService. Populated only when the request came with socketId (endpoints like /flux/chatbot-api-socket). At the end of the execution, the finally deletes the entry to avoid memory leaks.
  • emitNodeStatus is the announcer. Thin wrapper on top of NotificationsGateway.sendToUser. Payload is map by nodeId: { execId, flowId, userId, nodes: { [nodeId]: { status, userMessage } } }. It is ephemeral. Only valid while the socket is connected. Refresh loses the state. The state is rehydrated via HTTP and persisted RunLogNode.
  • Gateway works like a postman by userId. The NotificationsGateway keeps a Map<userId, socket[]> internally. On emit, it iterates all connections of that user. Multi-device: laptop and phone see updates simultaneously. No Redis adapter on Socket.io. Blocker for horizontal scaling. Acceptable today on single-node prod.
  • Final return at 5293-5307. { message[], nodeError, totalTokensUsed, totalCost }. Each outputObjectNode becomes a message item via arrayDataToText to concatenate textData. The actual chatbot socket handling lives in the controller. Not here. No intermediate streaming in apiV2. Token-by-token streaming from LLM is the worker's responsibility, via Redis pub/sub during commandTextNode.
  • Output. Incremental per-node emissions throughout the execution and a consolidated response object on return. Fire-and-forget. If the socket drops, the message is lost. The client reconnects and fetches state via HTTP. It is UX-only. The execution completes even if the socket is not working.
Context. Not every notification is done at this specific step. The diagram places 3.10 as "sends iteration and finalResult" on the final return. emitNodeStatus is called at several points during execution to update the UI in real time. The editor client (canvas) subscribes to the socket. It sees the per-node status changing as the execution progresses.

AchatbotSocketByRun (Map interna)
flux.service.ts:356 (declaração), 2288 (populate)
private readonly chatbotSocketByRun = new Map<string, string>() // runLogProcessId → socketId
Propósito. Map estático interno do FluxService que relaciona runLogProcessId a socketId. Popula só quando veio socketId no request (endpoints de chatbot). Usado quando é preciso enviar mensagem específica ao socket que iniciou a execução.
Em resumo. Esse Map é uma agenda que o serviço mantém aberta no processo do backend. Alguns endpoints (como o /flux/chatbot-api-socket) vêm com socketId. O cliente do chatbot mandou o request e ficou esperando resposta no mesmo socket persistente. O backend precisa saber, no meio da execução, para qual socket devolver cada pedaço da resposta. Salva na agenda: chatbotSocketByRun.set(runLogProcessId, socketId). Durante a execução, emitNodeStatus e outros pontos consultam essa agenda via runLogProcessId para descobrir qual socket avisar. No fim (passo 5.3), o finally chama this.chatbotSocketByRun.delete(runLogProcessId). Faz cleanup para não vazar memória. É uma agenda por processo do Node.js. Não é distribuída. Se o backend está em N pods e o socket foi aberto no pod 1, mas a execução está no pod 2, essa agenda não ajuda. O socket não é acessível cross-process. Em prod hoje, com um processo por pod, funciona. O Bull enfileira o job no mesmo pod onde o socket ficou. Ou o cenário não usa chatbot com múltiplos pods. Refactor futuro tem que resolver isso via Redis pub/sub ou similar.
// flux.service.ts:356 private readonly chatbotSocketByRun = new Map<string, string>(); // flux.service.ts:2287-2289 (dentro do apiV2) if (socketId) { this.chatbotSocketByRun.set(runLogProcessId, socketId); }
🎯 Só quando veio socketId
Endpoints como /flux/api-v2 não passam socketId. Não populam. O /flux/chatbot-api-socket passa. Isso permite que emissões por nó cheguem só onde faz sentido. O usuário de chatbot vê o streaming.
⚠️ Não é distribuído
Map local no processo. Se o backend escalar horizontalmente sem sticky sessions, o socket aberto no pod A e a execução rodando no pod B não conseguem se comunicar. Trade-off aceitável em single-node prod. Blocker em multi-pod.
BemitNodeStatus (per-node)
flux.service.ts:2146-2182
private emitNodeStatus({ execId, flowId, userId, nodeId, status, userMessage }): void
Propósito. Chamado em vários pontos da execução para emitir o status atual do nó via WebSocket. Wrapper fino sobre NotificationsGateway.sendToUser. Formato: { execId, flowId, userId, nodes: { [nodeId]: { status, userMessage } } }. O cliente ouvinte atualiza o cartão visual do nó em tempo real.
Em resumo. É o locutor da execução. Anuncia o status por nó a quem está ouvindo do outro lado do socket. O formato do payload é map por nodeId. O mesmo evento pode carregar update de múltiplos nós. Na prática, essa função sempre emite 1 por vez. Chamado em pontos específicos. Quando recordLegacyNodeStart abre uma linha em node_executions, status='RUNNING'. Quando o handler termina, status='COMPLETED' ou 'FAILED'. Em cancelamento, status='CANCELLED' (via emitCancelledRunStatuses). No final da execução inteira, via retorno. O cliente do editor tem listener. Recebe update para o nó X com status Y. Muda a borda visual para amarelo, verde ou vermelho. É assim que a UI mostra progresso realtime. Diferente do RunLogNode, que é persistido para histórico, essa emissão é efêmera. Só vale enquanto o socket está conectado. O refresh perde tudo.
private emitNodeStatus({ execId, flowId, userId, nodeId, status, userMessage }) { this.notificationsGateway.sendToUser({ execId, flowId, userId, nodes: { [nodeId]: { status, userMessage } }, }); }
🎯 Status literais
Strings: 'RUNNING', 'COMPLETED', 'FAILED' e 'CANCELLED'. Sem enum. String literal espalhada em vários pontos. O cliente confia na convenção.
📎 userMessage opcional
Quando presente, o cliente pode mostrar tooltip com detalhe. Por exemplo, mensagem de erro amigável em FAILED, ou quantidade de itens em COMPLETED de arrayNode.
🔧 forwardRef para evitar dependência circular
Injetado com @Inject(forwardRef(() => NotificationsGateway)) em flux.service.ts:410. O NotificationsGateway depende do FluxService para resolver algumas queries. Evita dependência circular.
CNotificationsGateway.sendToUser
gateway/notifications.gateway.ts (Socket.io)
sendToUser(payload: { execId, flowId, userId, nodes: Record<nodeId, { status, userMessage }> }): void
Propósito. Gateway NestJS com Socket.io. Emite evento específico para o userId. Mantém internamente um Map<userId, socket[]>. Quando sendToUser é chamado, itera todas as conexões daquele user e emite o payload via WebSocket.
Em resumo. É o carteiro que sabe para qual endereço enviar cada carta. O NotificationsGateway mantém uma tabela interna de userId para sockets ativos. O cliente fez subscribe ao abrir o editor. Quando o backend chama sendToUser({ userId, ... payload }), busca todas as conexões daquele user e executa socket.emit('flowUpdate', payload) em cada uma. Permite múltiplos dispositivos. Se o usuário abriu o editor no laptop e no celular, ambos veem updates simultâneos. Aqui não há Redis pub/sub direto para WebSocket. O Redis do sistema é usado para Bull queue e dedup de e-mail, mas não para pub/sub de eventos WS. É trade-off. Simples e rápido. Se o backend escalar em N pods sem sticky, um user pode estar conectado no pod 1 e a execução rodar no pod 2. O carteiro não sabe entregar. A solução clássica seria Redis Adapter do Socket.io. Não está em uso hoje.
C1 Socket.io emit por userId
O payload vai para todas as conexões daquele userId. O cliente fez subscribe ao abrir o editor. Recebe cada update por nó em tempo real. Payload leve (aproximadamente 200 bytes por nó).

⚠️ Sem Redis adapter
Socket.io não está configurado com Redis adapter no setup atual. Escalar horizontalmente sem sticky rompe o modelo.
🎯 Fire-and-forget
Emit não espera confirmação. Se o socket cair ou estiver lento, a mensagem se perde. O cliente precisaria reconectar e buscar o estado atual via HTTP.
DReturn final { message, nodeError, totalTokensUsed, totalCost }
flux.service.ts:5293-5307
return { message: outputNodes.map(...), nodeError, totalTokensUsed, totalCost };
Propósito. É o "3.10 do diagrama" no sentido de retornar o resultado consolidado ao caller. Não é WebSocket direto. O caller (endpoint HTTP) recebe esse objeto e devolve ao cliente. Se o request veio de chatbot com socket, o retorno é emitido no socket pelo controller do endpoint, não aqui.
Em resumo. A linha 5293 é o último ato do apiV2. Constrói o objeto de resposta. Contém message[], que mapeia cada outputObjectNode em { timestamp, text, outputId }. Contém nodeError, string amigável construída em 4.5. É null quando é sucesso. Contém totalTokensUsed e totalCost. Esse retorno é recebido pelo controller do endpoint após toda a execução terminar. O controller devolve ao cliente HTTP como JSON. No caso de chatbot com socket, emite pelo socket antes de fechar. O comentário na linha 5292 diz "This is the response to the user by websocket". A intenção era enviar via socket. O código apenas faz return. O socket handling real fica no controller ou no consumer (Bull processor). Sem cronograma de streaming aqui. O message vai tudo de uma vez no final. O streaming intermediário (por token de LLM) é responsabilidade do handler do worker, via Redis pub/sub durante a execução do commandTextNode. Fica fora do escopo desse return.
return { message: getOutputsObjectNodes.map(node => ({ timestamp: newChatTimestamp, text: node?.data?.textData?.length > 0 ? arrayDataToText(node.data?.textData) : (node.data?.text ?? ''), outputId: node.id, })), nodeError, // null se sucesso, string amigável se erro totalTokensUsed, totalCost, };
🎯 arrayDataToText
Utilitário que concatena textos de textData: [{text, id}...] em uma única string. Suporta o modelo de saída composta de várias referências resolvidas.
📎 Um message por outputObjectNode
Se o agente tem 3 outputObjectNode, retorna array de 3 messages. O cliente decide qual mostrar. Ou todas.
Resumo — o que sai de 3.10.
• Emissões incrementais por nó via emitNodeStatus ao longo da execução (RUNNING vira COMPLETED ou FAILED).
• Retorno consolidado no final: { message[], nodeError, totalTokensUsed, totalCost }.
• Se veio socketId, o chatbot socket recebe payload via socket handling do controller do endpoint.
Observações para migração.
• Socket local (não distribuído) é blocker para escala horizontal. Precisa Redis adapter do Socket.io ou similar antes de migrar.
• Status strings não tipadas ('RUNNING', 'COMPLETED', 'FAILED', 'CANCELLED') deveriam virar enum tipado.
• O path Temporal já tem streaming próprio via Redis pub/sub. O refactor pode unificar em vez de manter 2 mecanismos.
• Não é crítico para a correção da execução. Mesmo sem socket funcionar, a execução completa. É UX-only. Pode ficar para depois no plano de migração.

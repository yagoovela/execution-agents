Step 3.5b — publishInApiNodeOutput + persistSmallMemoryEntries

Block in flux.service.ts:4562-4581. After a node's handler finished and the result is in myUpdatedNodes, this block is the inline equivalent of W7-W9 in the worker. Propagates the output to the connected nodes (via schema and edges) and persists the fluxObject entries (Small Memory) in the database. Only runs if the node is not Temporal and not an integration routed to the worker.
In short — what this step does
  • "Is this my problem?" gate. !isTemporalNode(node.type) && !isWorkerRoutedIntegration(processedNode). If the node is already processed by the worker (7 Temporal types or 9 migrated integration providers), the worker runs W8 and W9 there. Skip. Only enters here when the inline backend is the owner.
  • Propagates output downstream. publishInApiNodeOutput delegates to addConnectToNodes (in folw/contants.ts). This one rewrites the nodes array by running modifyData for each edge source. Downstream nodes receive the output of the node that just ran, reflected in their data. It also calls onMutateSchema(nodeSchema(nodes)), updating the global schema.
  • Reassign, not mutation. myUpdatedNodes = this.publishInApiNodeOutput({...}). The method returns a new array (via [...nds] and .map) and the loop reassigns the reference. Follows the same closure-mutation pattern as 1.5 (onMutateObjectCallerData).
  • Persists Small Memory. persistSmallMemoryEntries scans the edges looking for which targets are connected via targetHandle === 'inputAdd' to the source node. For each fluxObject (which is the SMALL_MEMORY_TYPE), it runs UPDATE flows_nodes SET data = ... with entries and userSessionsChat.
  • No size filter. Despite the name "SmallMemory", there is no size validation here. "Small" refers to the node type. The fluxObject was renamed to "Small Memory" in the UI. It is not a byte cap. It persists everything that is in memoryNode.data.entries.
Context. This pair (publishInApiNodeOutput plus persistSmallMemoryEntries) is the "I'm not Temporal, so I have to do it myself". In the worker, W7-W9 already handle this for migrated nodes. Here, the inline backend has to replicate it manually to keep compatibility while the migration to Temporal continues incrementally.

Purpose. Avoid double execution. If the node has already been run by the Temporal worker (or is going to be routed there), the worker already did W7-W9. Published output and persisted memory. Running here again would corrupt the state (double-persist, edges reprocessed twice).
In short. Think of a recycling guard at the door. "Has this node already gone to the back (Temporal) to do its job? Then don't even try to reprocess here." Checks two groups.
(1) Temporal types: 7 hardcoded types (commandTextNode, scripting, apiCaller, mathFunction, counterNode, outputController, mcpNode). For those, the entire worker takes over.
(2) Integrations routed to the worker: providers listed in MIGRATED_INTEGRATION_PROVIDERS (Stripe, WordPress, Slack, Notion, Zapier, HubSpot, Supabase, Pinecone, MCP).
If the node falls into either of the two, the inline backend does not re-publish or persist. The worker already did.

📎 Why two separate tests?
isTemporalNode tests the node type. isWorkerRoutedIntegration tests the integration provider (same type, depends on data.provider).

A thirdPartyIntegration node with provider=stripe goes to the worker. The same type with provider=airtable does not. Only the second test can tell them apart.

private publishInApiNodeOutput({ nodeId, nodes, edges, onMutateSchema, objectCallerData }): any[]
Purpose. Marks the node as finished in the myUpdatedNodes array and propagates its data to the nodes connected via edges. Delegates to addConnectToNodes. The return value is reassigned to myUpdatedNodes. This ensures that the next node in the loop already sees the updated state.
In short. Think of a mailman who announces the result. After the node finished, its result is stored in myUpdatedNodes, still in "mine" format. This method does three things.
(1) Finds the finished node in the array.
(2) Passes the whole list to addConnectToNodes. It scans all edges and, for each node that receives a connection from that finished node, injects its data into the appropriate fields via modifyData. That way, when the next node in the loop is read, it already has the right inputs.
(3) As a bonus, it recomputes the global schema via nodeSchema(nodes) and passes it to onMutateSchema. Same closure-mutation pattern as 1.5.

C persistSmallMemoryEntries()
flux.service.ts:759-799
private async persistSmallMemoryEntries({ sourceNodeId, nodes, edges, flowId, flowVersionHistoryId }): Promise<void>
Purpose. Persist in the database the entries that the node that just ran wrote to a fluxObject (Small Memory) connected to it. Without this, the value written during execution exists only in memory and vanishes when the process restarts. This is the writeback to flows_nodes.data.
In short. Think of saving the draft to disk. During execution, when a node (for example, an LLM or outputController) writes something to a Small Memory connected via the inputAdd handle, that stays only in myUpdatedNodes. Process memory. If the backend crashes mid-execution, the data is lost. This method is the answer. As soon as the node has finished, it scans the edges looking for any Small Memory connected as an inputAdd target of that node. Takes the entries and userSessionsChat fields from the memory node. Runs UPDATE flows_nodes SET data = ... on that specific row. Misleading name. Despite "small memory", there is no size filter. "Small" is the product name in the UI (node of type fluxObject), not a limit.

⚠️ "Small" does not exist as a cap
Despite the name, there is no size limit at persist time. If entries has 10 MB of JSON, the 10 MB go to Postgres. The name comes from the UI ("Small Memory" node). It is not a technical constraint.

See the constant in small-memory.ts:1: SMALL_MEMORY_TYPE = 'fluxObject'.
📎 Magic handle: inputAdd
SMALL_MEMORY_INPUT_HANDLE = 'inputAdd'. A specific handle string. Only edges with that targetHandle trigger persist. Other fluxObject handles (read, session switch) do not persist.

Tacit rule. "Whoever writes to memory connects on inputAdd."
🔧 Silent persist failure
persistNodeDataToLiveRow has an internal try/catch. If the UPDATE fails (deadlock, constraint, database down), it logs error_type: 'live_node_persist_failed' and the method returns void. Execution does not abort.

Effect. During a database outage, all Small Memory persistences fail silently. The user only finds out on the next execution.
Summary — what comes out of 3.5b:
• myUpdatedNodes = new array with the finished node and downstream edges updated via modifyData.
• Global schema recomputed and propagated via onMutateSchema.
• fluxObject rows connected via inputAdd persisted to flows_nodes.data (or flow_version_history_nodes).
• One UPDATE per connected Small Memory. No batching, no parallelism (for ... of loop with await).
Notes for migration:
• This pair is the inline equivalent of W7-W9 from the worker. Migrating a new node type to Temporal takes three steps. (1) Add it to isTemporalNode. (2) Ensure W7-W9 in the worker call the same logic. (3) The gate in this step will automatically skip the new node, avoiding double-persist.
• publishInApiNodeOutput mutates an array via [...nds] and .map. It does not mutate myUpdatedNodes in-place. It preserves references for the closure-mutation pattern (same style as 1.5).
• persistSmallMemoryEntries is fire-and-forget. It has await, but the error is swallowed in the internal try/catch of persistNodeDataToLiveRow. In the worker, the ideal would be an activity with a retry policy.
• Magic handle ('inputAdd') and magic type ('fluxObject') are in constants in a dedicated file (flux/small-memory.ts). Easy to reuse in the worker.
• Medium-high priority in the migration. As long as the inline backend exists, this pair has to keep working. Each new migrated type removes clients from this code path.

Passo 3.5b — publishInApiNodeOutput + persistSmallMemoryEntries

Bloco em flux.service.ts:4562-4581. Depois que o handler de um nó terminou e o resultado está em myUpdatedNodes, este bloco é o equivalente inline de W7-W9 do worker. Propaga a saída para os nós conectados (via schema e edges) e persiste as entries de fluxObject (Small Memory) no banco. Só roda se o nó não for Temporal e não for integração roteada para o worker.
Em resumo — o que esse passo faz
  • Gate de "isso é meu problema?". !isTemporalNode(node.type) && !isWorkerRoutedIntegration(processedNode). Se o nó já é processado pelo worker (7 tipos Temporal ou 9 providers de integração migrados), o worker faz W8 e W9 lá. Pular. Só entra aqui quando o backend inline é o responsável.
  • Propaga saída para downstream. publishInApiNodeOutput delega para addConnectToNodes (em folw/contants.ts). Este reescreve o array de nodes rodando modifyData para cada source de edge. Os nós à jusante recebem a saída do nó que acabou de rodar, refletida no data deles. Também chama onMutateSchema(nodeSchema(nodes)), atualizando o schema global.
  • Reassign, não mutação. myUpdatedNodes = this.publishInApiNodeOutput({...}). O método retorna um novo array (via [...nds] e .map) e o loop reatribui a referência. Segue o mesmo padrão de closure mutation de 1.5 (onMutateObjectCallerData).
  • Persiste Small Memory. persistSmallMemoryEntries varre os edges procurando quais targets estão ligados via targetHandle === 'inputAdd' ao nó de origem. Para cada fluxObject (que é o SMALL_MEMORY_TYPE), faz UPDATE flows_nodes SET data = ... com entries e userSessionsChat.
  • Sem filtro por tamanho. Apesar do nome "SmallMemory", não há validação de tamanho aqui. "Small" refere-se ao tipo de nó. O fluxObject foi renomeado para "Small Memory" na UI. Não é um cap de bytes. Persiste tudo que estiver em memoryNode.data.entries.
Contexto. Este par (publishInApiNodeOutput mais persistSmallMemoryEntries) é o "eu não sou Temporal, então tenho que fazer eu mesmo". No worker, W7-W9 já cuidam disso para os nós migrados. Aqui, o backend inline precisa replicar manualmente para manter compatibilidade, enquanto a migração para o Temporal continua incremental.

Propósito. Evitar dupla execução. Se o nó já foi rodado pelo worker Temporal (ou vai ser roteado para lá), o worker já fez W7-W9. Publicou saída e persistiu memória. Rodar aqui de novo corromperia o state (double-persist, edges reprocessadas duas vezes).

B publishInApiNodeOutput()
flux.service.ts:729-754
private publishInApiNodeOutput({ nodeId, nodes, edges, onMutateSchema, objectCallerData }): any[]
Propósito. Marca o nó como finalizado no array myUpdatedNodes e propaga o data dele para os nós conectados via edges. Delega para addConnectToNodes. O retorno é reatribuído a myUpdatedNodes. Isso garante que o próximo nó do loop já veja o estado atualizado.
Em resumo. Pense num carteiro que anuncia o resultado. Depois que o nó terminou, o resultado dele está guardado em myUpdatedNodes, ainda em formato "meu". Este método faz três coisas.
(1) Acha o nó finalizado no array.
(2) Passa a lista inteira para addConnectToNodes. Este varre todas as edges e, para cada nó que recebe conexão desse nó finalizado, injeta o data dele nos campos apropriados via modifyData. Assim, quando o próximo nó do loop for lido, já tem as entradas corretas.
(3) Como bônus, recalcula o schema global via nodeSchema(nodes) e joga no onMutateSchema. Mesmo padrão de closure mutation que 1.5.

Para cada source presente no array, chama modifyData(nodes, id, newEdges, objectCallerData, nodeData?.id, 'execute'). Propaga saída para os nós à jusante conectados àquele source. 🎯 changeType: 'execute'
modifyData tem múltiplos modos ('execute', 'default', etc.). Em 'execute', propaga saída resultante da execução do nó. Em 'default' (usado no fim da execução, linha 4943), é reset e limpeza.
📎 objectCallerData vai junto
modifyData precisa da lista atual de objetos personalizados (do passo 1.5) porque nós como nodesBox podem ler valores de objetos ao construir entrada dos nós filhos.
⚠️ Não emite WebSocket aqui
Apesar do nome "publish", não há emit de WebSocket neste método. O status do nó no frontend é emitido em outros pontos (via notificationsGateway.sendToUser em emitNodeStatus, emitCancelledRunStatuses, etc.). "Publish" aqui significa "publicar saída no grafo local, propagar via edges".
C persistSmallMemoryEntries()
flux.service.ts:759-799
private async persistSmallMemoryEntries({ sourceNodeId, nodes, edges, flowId, flowVersionHistoryId }): Promise<void>
Propósito. Persistir no banco as entries que o nó que acabou de rodar escreveu num fluxObject (Small Memory) conectado a ele. Sem isso, o valor gravado durante a execução existe só em memória e some quando o processo reinicia. É o writeback para flows_nodes.data.
Em resumo. Pense em gravar o rascunho no HD. Durante a execução, quando um nó (por exemplo, um LLM ou outputController) grava algo numa Small Memory conectada via handle inputAdd, isso fica só em myUpdatedNodes. Memória do processo. Se o backend cair no meio da execução, o dado se perde. Este método é a resposta. Assim que o nó terminou, varre os edges procurando qualquer Small Memory conectada como target de inputAdd a esse nó. Pega os campos entries e userSessionsChat do nó de memória. Faz UPDATE flows_nodes SET data = ... naquela linha específica. Nome enganoso. Apesar de "small memory", não tem filtro de tamanho. O "small" é o nome do produto na UI (nó do tipo fluxObject), não um limite.

⚠️ "Small" não existe como cap
Apesar do nome, não há limite de tamanho na hora de persistir. Se entries tem 10 MB de JSON, os 10 MB vão para o Postgres. O nome vem da UI ("Small Memory" node). Não é uma constraint técnica.

Ver constante em small-memory.ts:1: SMALL_MEMORY_TYPE = 'fluxObject'.
📎 Handle mágico: inputAdd
SMALL_MEMORY_INPUT_HANDLE = 'inputAdd'. String handle específico. Só edges com esse targetHandle disparam persist. Outros handles do fluxObject (leitura, session switch) não persistem.

Regra tácita. "Quem escreve na memória se conecta em inputAdd."
🔧 Persist falha silenciosa
persistNodeDataToLiveRow tem try/catch interno. Se o UPDATE falhar (deadlock, constraint, banco fora), loga error_type: 'live_node_persist_failed' e o método volta void. A execução não aborta.

Efeito. Em pane de banco, todas as persistências de Small Memory fracassam silenciosamente. O usuário só descobre na próxima execução.
Resumo — o que sai de 3.5b:
• myUpdatedNodes = novo array com o nó finalizado e edges downstream atualizadas via modifyData.
• Schema global recalculado e propagado via onMutateSchema.
• Linhas de fluxObject conectadas via inputAdd persistidas em flows_nodes.data (ou flow_version_history_nodes).
• Um UPDATE por Small Memory conectada. Sem batching, sem paralelismo (loop for ... of com await).
Observações para migração:
• Este par é o equivalente inline de W7-W9 do worker. Migrar um novo tipo de nó para o Temporal significa três passos. (1) Adicionar em isTemporalNode. (2) Garantir que W7-W9 no worker chamam a mesma lógica. (3) O gate deste passo automaticamente vai pular para o nó novo, evitando double-persist.
• publishInApiNodeOutput muta um array via [...nds] e .map. Não muta myUpdatedNodes in-place. Preserva referências para o padrão de closure mutation (mesmo estilo do 1.5).
• persistSmallMemoryEntries é fire-and-forget. Tem await, mas o erro é engolido no try/catch interno de persistNodeDataToLiveRow. No worker, ideal seria activity com retry policy.
• Handle mágico ('inputAdd') e tipo mágico ('fluxObject') estão em constantes num arquivo dedicado (flux/small-memory.ts). Fácil de reaproveitar no worker.
• Prioridade média-alta na migração. Enquanto o backend inline existir, este par tem que continuar funcionando. Cada tipo novo migrado remove clientes desse code path.

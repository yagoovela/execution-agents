Step 2.1 — buildSchedulerState (DAG scheduler)

Block at scheduler.ts:152-293 (planOrder: 412-425). Builds the DAG scheduler state that drives the main loop. Classifies edges into control, condition, data and global. Computes reachability from the starter. Removes backedges (cycles). Builds predecessor counters. Returns the initial queue of ready nodes (ready).
In summary — what this step does
  • Labels every edge on the canvas. Walks all connections between nodes and applies a label (global, control, condition, data). The label decides whether the edge blocks execution.
  • Finds out which nodes take part in the execution. Starting from the starter, computes the Set of reachable nodes. Anything not in it stays idle throughout the run, even if it is drawn on the canvas.
  • Removes cycles from the graph. A DFS with coloring (white, gray, black) identifies backedges (typical of arrayNode that loops back to the start) and ignores them. Prevents predecessor counters from getting stuck.
  • Builds the control panel for the loop. For each node, computes how many predecessors exist in total and how many are gates (control and condition). Initializes counters at zero. Fills ready[] only with in-degree 0 nodes.
  • Output. A mutable 12-field SchedulerState. Contains ready, forwardDeps, conditionEdges, counters and empty sets for completed, dead, scheduled. The Phase 3 loop consumes this data. Pure CPU. Zero I/O. Complexity O(V+E).
Context. This is the core of the execution algorithm. The whole Phase 3 loop depends on the SchedulerState produced here. The functions nextReady(), markCompleted(), markDead() and completeCondition() operate on the structures built in 2.1. It is pure code, no I/O and no async. Deterministic. About 140 lines. Trivial to cover with unit tests.
Operation chain in 2.1
AclassifyEdge → Breachable + pullProviders/Consumers → CfindBackEdges (DFS) → DBuilds preds + gating + ready → EplanOrder (debug)
Final result. SchedulerState with 12 fields consumed by the loop. ready[], forwardDeps, conditionEdges, preds and gating counters, sets of completed, dead and scheduled.
A classifyEdge()
scheduler.ts:46-57
function classifyEdge(edge, starterSourceId): 'control' | 'condition' | 'data' | 'global'
Purpose. Categorizes each edge into one of 4 classes. The classification determines how the scheduler treats the dependency. control and condition gate execution. data passes a value but does not block by itself. global does not count as a dependency.
In summary. This function is the edge registrar. It takes each line that links one node to another on the canvas and puts a label on it. Looking at the source handle, it picks one of four options. global (comes from the starter, does not block). control (explicit flow, respects order). condition (output of if/switch, can kill the branch if the test fails). data (just delivers a value). A cascade of 5 checks. First match wins. The label tells the rest of the scheduler whether the edge blocks execution.

isDependencyEdge = control || condition || data

scheduler.ts:59-65
🎯 Semantics of the 4 classes
global. Starter and globals. They do not block anyone. Every execution begins from them.
control. Explicit flow (outputFlow edge). "Only run after this one."
condition. Output of conditionNode. Can mark a branch as dead.
data. Value edge. Precedence dependency. Does not force order in the DAG if already resolved.
🔧 Hardcoded handles
GLOBAL_HANDLE = 'a'. CONTROL_HANDLE = 'outputFlow'. Regex outputHandle-[01] (bool if/else). Regex conditionHandle-[TF]\d+ (switch). If the front creates a handle whose name falls outside these patterns, it accidentally lands on data or global.
⚠️ Silent fallback to global
An edge without sourceHandle and without targetHandle goes to global. If a bug on the front creates an edge like that between two business nodes, the scheduler does not block execution. Can cause a race in Phase 3.
B reachableFrom + pullDataProviders + pullSinkConsumers
scheduler.ts:113-220
// BFS from the starter, then expands via data-providers and data-sinks until fixed point
Purpose. Finds out which nodes run in the execution. Only nodes reachable from flow-global-starter via control/condition edges enter the base. Then pulls in data providers (nodes whose output feeds a reachable node) and data sinks (output or varInput consumers). Repeats until fixed point.
In summary. This step is the gatekeeper that decides who takes part in the execution. It starts from the starter node and walks control and condition edges to build a first group of admitted nodes. Then it makes a pass pulling in whoever feeds these nodes with data (the providers). Then another pulling in whoever receives their results (sinks like outputController and varInputNode). Runs to fixed point. Repeats until nothing changes. What's left is a Set called reachable. Anyone outside it does not even exist to the loop. Even drawn on the canvas, the node stays idle throughout the run. This is what prevents executing a disconnected apiCaller just because it sits on the canvas.

🎯 Why 2 phases?
Phase 1 is the full expansion. Brings in everything that feeds business nodes, even side-effects like apiCaller. Phase 2 fixes overshoot. If an output-sink became reachable and needs more providers, it only pulls when they are not side-effects. Prevents firing apiCaller just to populate an output.
📎 SIDE_EFFECT_TYPES
apiCaller, mcpNode, thirdPartyIntegration, pushData, hubSpotCRM, fileSave. Closed set at scheduler.ts:29-36. Adding a new type here changes reachability semantics. Careful.
📎 DATA_SINK_TYPES
outputController, outputObjectNode, varInputNode. Only these three are pulled by the "consumer reachable if produced by reachable" rule. scheduler.ts:23-27.
🔧 orchAdj vs dataAdj
Two separate adjacency lists. orchAdj only has control and condition. Used in the initial BFS. dataAdj and reverseDataAdj only have data. Used in the expansion. Classic bug is mixing the two.
C findBackEdges()
scheduler.ts:130-150
function findBackEdges(roots, adj: depAdj): Set<`${src}->${tgt}`>
Purpose. Classic DFS with coloring (0 = white/unvisited, 1 = gray/on-stack, 2 = black/done) to detect backedges in the dependency graph. Backedges are ignored when building forwardDeps and preds. Without this, cycles would freeze nextReady. Predecessors would never reach zero.
In summary. The graph might have an arrayNode that loops back to the start to iterate. That is a cycle. A cycle in a DAG is poison for the scheduler. The predecessor counter never reaches zero. nextReady never finds the node ready. The loop hangs. This function is the janitor. It walks the graph with three-color marking. White: not visited. Gray: currently inside. Black: already left. Whenever it hits an arrow pointing to someone still gray (the same arrow that climbs back up the stack), it marks the edge as a backedge. These backedges go into a Set and are ignored when dependencies are built. The array's logical loop becomes the problem of the arrayNode handler in Phase 3, not the scheduler.

⚠️ Recursive DFS. Stack overflow risk
A flow with over 5000 nodes chained in series can blow up Node's call stack. Not a real case today. No production flow comes close. Latent limitation. Migrating to iterative DFS with an explicit stack removes the risk.
🎯 Why ignore the backedge?
If A → B → A forms a cycle, one of the nodes has in-degree ≥ 1 forever. nextReady never finds the node ready. Removing the backedge from the dep graph lets the main loop run A, then B (which now has in-degree 0). The logical loop becomes the responsibility of the arrayNode handler in Phase 3.
🔧 Key ${node}->${next}
String literal, not a tuple. Direct concat. If some nodeId contains the substring ->, it causes a collision. Since IDs are UUIDs on the front, it is safe in practice.
D Builds forwardDeps + preds + gating + ready[]
scheduler.ts:232-292
return { nodeIds, forwardDeps, conditionEdges, totalPreds, resolvedPreds, deadPreds, gatingPairs, totalGating..., ready: [], completed: Set(), dead: Set(), scheduled: Set() }
Purpose. Materializes the final state that the loop will mutate. Each node has 6 counters (total, resolved, dead combined with preds and gating) that markCompleted, markDead and completeCondition increment in O(1) during execution. ready[] starts with in-degree 0 nodes.
In summary. This function is the builder of the control panel used by the execution loop from start to finish. Edge by edge, it fills maps. For each node: how many total predecessors exist, how many of them are gates (control and condition, the ones that can kill the node), what the outgoing edges are for later propagation, and which conditionNode outputs must be remembered when the if resolves. At the end, it initializes zeroed resolved and dead counters for each node. Builds the initial ready[] with only nodes that have no predecessors. Those run first. From here on, each markCompleted, markDead or completeCondition just increments counters in O(1) and moves nodes into ready as they get freed.

🎯 Why 2 counts (preds vs gating)?
preds. All deps (control, condition and data). Only when all are resolved does the node go to ready.

gating. Subset (only control and condition). If all remaining gates are dead, the node also dies and does not run.

Data edges count toward order but do not kill the node on their own.
📎 conditionEdges stores all condition edges by source
Used by completeCondition(schedState, id, takenHandle) to decide which branch turns dead when a conditionNode resolves. See scheduler.ts:366-389.
🔧 Pre-allocated empty sets
completed, dead and scheduled start empty. The loop populates them on the fly. scheduled prevents re-queueing the same id when nextReady is called after it has already served.
⚠️ All structures are Map or Set
Fast in memory. Not directly serializable to Redis/Postgres. If one day the scheduler needs to survive a backend crash, it needs a custom serializer.
E planOrder()
scheduler.ts:412-425
function planOrder(nodes, edges, starterSourceId): string[] // linear topological order
Purpose. Runs the scheduler dry. Calls buildSchedulerState and loops nextReady → markCompleted until empty, without executing handlers. Returns the order in which nodes would run. Used to populate allNodesIds in flux.service for debug/UI.
In summary. It is a rehearsal of the agent with no one on stage. Calls everything D built and simulates the loop. Takes the next ready node. Marks it complete (without actually running, without burning a token, without calling any API). Takes the next one. And so on until finished. The result is an ordered list of IDs in the sequence they would run. Used in allNodesIds for debug, previews and some asserts. Careful. The function never calls completeCondition nor markDead. The rehearsal assumes every branch is taken. The list is the maximal scenario, not necessarily what will happen in a real execution with conditions.
export function planOrder(nodes, edges, starterSourceId): string[] { const state = buildSchedulerState(nodes, edges, starterSourceId); const order = []; let id; while ((id = nextReady(state)) !== null) { order.push(id); markCompleted(state, id); } return order; }

⚠️ Does not consider conditions
planOrder only calls markCompleted. Never completeCondition or markDead. Assumes every branch is taken. The generated order is the maximal hypothesis, not what will run in a real execution with conditions.
🎯 Cost
Basically double the build's work. Calls buildSchedulerState again and does a topological pass. Runs on every execution. Could be cached by (flowId, version), since it is deterministic from nodes and edges alone. Today it is not.
🔧 buildSchedulerState is called twice per execution
Once here for schedState (flux.service.ts:3136) and once inside planOrder for allNodesIds. Could reuse the same state, but that requires markCompleted to be non-destructive. It is not.
Summary — what 2.1 outputs.
• schedState: SchedulerState. Mutable. Consumed by the Phase 3 loop.
• allNodesIds: string[]. Topological order for debug/UI.
• Zero I/O. Pure CPU. Complexity ~O(V+E) in most cases.
• Nodes outside reachable are invisible to execution. Never executed.
Migration notes.
• Essential and pure code. Lowest migration risk. Can become a shared library between backend and worker without semantic change.
• The worker does not need to run the scheduler today. Each activity is an isolated node. If one day the worker orchestrates sub-DAGs, the same module works.
• Caching buildSchedulerState by (flowId, versionId) removes one run per execution. Trivial cost today. Grows linearly with the number of nodes.
• Formalize the public interface (export only buildSchedulerState, nextReady, markCompleted, markDead and completeCondition) before any refactor. Today it is easy to import an internal helper by accident.
• Add typing on top of handles. The regex outputHandle-[01] and conditionHandle-[TF]\d+ are magic strings. A typed enum on the front generating these handles would be safer.

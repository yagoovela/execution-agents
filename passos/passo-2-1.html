Passo 2.1 — buildSchedulerState (DAG scheduler)

Bloco em scheduler.ts:152-293 (planOrder: 412-425). Constrói o estado do scheduler DAG que rege o loop principal. Classifica arestas em control, condition, data e global. Calcula alcançabilidade a partir do starter. Remove backedges (ciclos). Monta contadores de predecessores. Devolve a fila inicial de nós prontos (ready).
Em resumo — o que esse passo faz
  • Etiqueta cada aresta do canvas. Passa por todas as ligações entre nós e coloca um rótulo (global, control, condition, data). O rótulo indica se a aresta bloqueia execução.
  • Descobre quais nós entram na execução. A partir do starter, calcula o Set de nós reachable. Quem não estiver nele fica ocioso durante toda a execução, mesmo desenhado no canvas.
  • Remove ciclos do grafo. Um DFS com coloring (branco, cinza, preto) identifica as backedges (típico de arrayNode que volta ao início) e as ignora. Evita travar os contadores de predecessores.
  • Monta o painel de controle do loop. Para cada nó, calcula quantos predecessores existem no total e quantos são gates (control e condition). Inicializa contadores em zero. Popula o ready[] só com nós de in-degree 0.
  • Saída. Um SchedulerState mutável de 12 campos. Contém ready, forwardDeps, conditionEdges, contadores e sets vazios de completed, dead, scheduled. O loop da Fase 3 consome esses dados. Puro CPU. Zero I/O. Complexidade O(V+E).
Contexto. Este é o núcleo do algoritmo de execução. Todo o loop da Fase 3 depende do SchedulerState que sai daqui. As funções nextReady(), markCompleted(), markDead() e completeCondition() operam nas estruturas montadas em 2.1. É código puro, sem I/O e sem async. Determinístico. Cerca de 140 linhas. Trivial de cobrir com unit tests.
Cadeia de operações em 2.1

A classifyEdge()
scheduler.ts:46-57
function classifyEdge(edge, starterSourceId): 'control' | 'condition' | 'data' | 'global'
Propósito. Categoriza cada aresta em uma de 4 classes. A classificação determina como o scheduler trata a dependência. control e condition gateiam execução. data passa valor mas não bloqueia por si só. global não conta como dependência.
Em resumo. Esta função é o cadastrador das arestas. Pega cada linha que liga um nó a outro no canvas e coloca uma etiqueta. Ao olhar o handle de saída, decide entre quatro opções. global (vem do starter, não bloqueia). control (fluxo explícito, respeita a ordem). condition (saída de if/switch, pode matar o branch se o teste der errado). data (só entrega um valor). Cascata de 5 checks. O primeiro que bate ganha. O rótulo diz ao resto do scheduler se a aresta bloqueia execução.
🪜 Cascata de classificação
1 source === starterSourceId || handle = 'a' global
2 handle = 'outputFlow' control
3 handle bate em /outputHandle-[01]/ ou /conditionHandle-[TF]\d+/ condition
4 tem targetHandle data
5 nenhum global (fallback)
↓
isDependencyEdge = control || condition || data
Só arestas global são ignoradas no cálculo de dependência. As demais entram no grafo de precedência.
scheduler.ts:59-65
🎯 Semântica das 4 classes
global. Starter e globals. Não bloqueiam ninguém. Toda execução começa por eles.
control. Fluxo explícito (aresta outputFlow). "Só rode depois deste."
condition. Saída de conditionNode. Pode marcar branch como dead.
data. Aresta de valor. Dependência de precedência. Não força ordem no DAG se já resolvido.
🔧 Handles hardcoded
GLOBAL_HANDLE = 'a'. CONTROL_HANDLE = 'outputFlow'. Regex outputHandle-[01] (bool if/else). Regex conditionHandle-[TF]\d+ (switch). Se o front cria um handle com nome fora desses padrões, cai em data ou global por acidente.
⚠️ Fallback silencioso para global
Aresta sem sourceHandle e sem targetHandle vai para global. Se um bug no front criar aresta assim entre dois nós de negócio, o scheduler não bloqueia a execução. Pode causar race na Fase 3.
B reachableFrom + pullDataProviders + pullSinkConsumers
scheduler.ts:113-220
// BFS a partir do starter, depois expande por data-providers e data-sinks até fixed point
Propósito. Descobre quais nós rodam na execução. Só nós alcançáveis a partir do flow-global-starter via arestas control/condition entram na base. Depois puxa data providers (nós cujo output alimenta um nó alcançável) e data sinks (output ou varInput consumers). Repete até fixed point.
Em resumo. Esta etapa é o vigia que decide quem participa da execução. Parte do nó starter e percorre as arestas de control e condition para montar um primeiro grupo de nós admitidos. Depois faz uma passada puxando quem alimenta esses nós com dados (os providers). Depois outra puxando quem recebe resultado deles (os sinks como outputController e varInputNode). Roda em fixed point. Repete até nada mudar. Sobra um Set chamado reachable. Quem não está nele nem existe para o loop. Mesmo desenhado no canvas, o nó fica ocioso durante toda a execução. É o que evita executar um apiCaller desconectado só por estar no canvas.

🎯 Por que 2 fases?
Fase 1 é a expansão completa. Traz tudo que alimenta os nós de negócio, mesmo side-effects como apiCaller. Fase 2 corrige overshoot. Se um output-sink virou alcançável e precisa de mais providers, só puxa quando não é side-effect. Evita disparar apiCaller só para popular um output.
📎 SIDE_EFFECT_TYPES
apiCaller, mcpNode, thirdPartyIntegration, pushData, hubSpotCRM, fileSave. Set fechado em scheduler.ts:29-36. Adicionar type novo aqui muda a semântica de alcançabilidade. Cuidado.
📎 DATA_SINK_TYPES
outputController, outputObjectNode, varInputNode. Só esses três são puxados pela regra "consumer alcançável se produzido por alcançável". scheduler.ts:23-27.
🔧 orchAdj vs dataAdj
Duas listas de adjacência separadas. orchAdj só tem control e condition. Usada na BFS inicial. dataAdj e reverseDataAdj só têm data. Usadas na expansão. Bug clássico é misturar as duas.
C findBackEdges()
scheduler.ts:130-150
function findBackEdges(roots, adj: depAdj): Set<`${src}->${tgt}`>
Propósito. DFS clássico com coloring (0 = white/unvisited, 1 = gray/on-stack, 2 = black/done) para detectar backedges no grafo de dependência. Backedges são ignoradas na montagem de forwardDeps e preds. Sem isso, ciclos travariam nextReady. Nunca zeraria predecessores.
Em resumo. O grafo pode ter um arrayNode que volta ao início para iterar. Isso é um ciclo. Ciclo em DAG é veneno para o scheduler. O contador de predecessores nunca chega a zero. O nextReady nunca acha o nó pronto. O loop trava. Esta função é o faxineiro. Passeia pelo grafo com marcação de três cores. Branco: não visitei. Cinza: estou dentro. Preto: já saí. Sempre que topa com uma seta apontando para alguém ainda cinza (a mesma seta sobe pela pilha), marca a aresta como backedge. Essas backedges ficam em um Set e são ignoradas na montagem das dependências. O loop lógico do array vira problema do handler de arrayNode na Fase 3, não do scheduler.

⚠️ DFS recursivo. Risco de stack overflow
Flow com mais de 5000 nós encadeados em série pode estourar o call stack do Node. Não é caso real hoje. Nenhum flow em produção chega perto. Limitação latente. Migrar para DFS iterativo com stack explícito elimina o risco.
🎯 Por que ignorar backedge?
Se A → B → A forma um ciclo, um dos nós tem in-degree ≥ 1 para sempre. O nextReady nunca acha o nó pronto. Ao remover o backedge do grafo de deps, o loop principal consegue rodar A, depois B (que agora tem in-degree 0). O loop lógico vira responsabilidade do handler de arrayNode na Fase 3.
🔧 Chave ${node}->${next}
String literal, não tupla. Concat direto. Se algum nodeId contiver a substring ->, gera colisão. Como IDs são UUIDs no front, é seguro na prática.
D Monta forwardDeps + preds + gating + ready[]
scheduler.ts:232-292
return { nodeIds, forwardDeps, conditionEdges, totalPreds, resolvedPreds, deadPreds, gatingPairs, totalGating..., ready: [], completed: Set(), dead: Set(), scheduled: Set() }
Propósito. Materializa o estado final que o loop vai mutar. Cada nó tem 6 contadores (total, resolved, dead combinados com preds e gating) que markCompleted, markDead e completeCondition incrementam em O(1) durante a execução. O ready[] começa com nós de in-degree 0.
Em resumo. Esta função é o montador do painel de controle usado pelo loop de execução do início ao fim. Aresta por aresta, preenche mapas. Para cada nó, quantos predecessores totais existem, quantos deles são gates (control e condition, os que podem matar o nó), quais são as arestas de saída para propagar depois, e quais saídas de conditionNode devem ser lembradas para quando o if resolver. No fim, inicializa contadores zerados de resolved e dead para cada nó. Monta o ready[] inicial só com os nós sem predecessor. Esses rodam primeiro. Daqui em diante, cada markCompleted, markDead ou completeCondition só incrementa contadores em O(1) e move nós para o ready conforme se liberam.

Passa por cada aresta uma vez. Se é condition, guarda em conditionEdges[source] para o completeCondition resolver depois. Se é dep e não backedge, preenche forward, preds e (se control ou condition) gating.

🎯 Por que 2 contagens (preds vs gating)?
preds. Todas as deps (control, condition e data). Só quando todas estão resolvidas o nó vai para ready.

gating. Subset (só control e condition). Se todos os gates restantes estão mortos, o nó também morre e não roda.

Data edges contam para a ordem, mas não matam o nó sozinhas.
📎 conditionEdges guarda todas as arestas de condition por source
Usado pelo completeCondition(schedState, id, takenHandle) para decidir qual branch vira dead quando um conditionNode resolve. Ver scheduler.ts:366-389.
🔧 Sets vazios pré-alocados
completed, dead e scheduled começam vazios. O loop popula on-the-fly. scheduled evita reenfileirar o mesmo id quando o nextReady é chamado após já ter servido.
⚠️ Todas as estruturas são Map ou Set
Rápido em memória. Não são serializáveis para Redis/Postgres diretamente. Se um dia o scheduler precisar sobreviver a um crash do backend, precisa de serializer custom.
E planOrder()
scheduler.ts:412-425
function planOrder(nodes, edges, starterSourceId): string[] // ordem topológica linear
Propósito. Roda o scheduler a seco. Chama buildSchedulerState e o loop nextReady → markCompleted até esvaziar, sem executar handlers. Devolve a ordem em que os nós iriam rodar. Usado para popular allNodesIds no flux.service para debug/UI.
Em resumo. É um ensaio do agente sem ninguém no palco. Chama tudo o que a D montou e simula o loop. Pega o próximo nó pronto. Marca como completo (sem executar de verdade, sem gastar token, sem chamar API). Pega o próximo. E assim por diante até acabar. O resultado é a lista ordenada dos IDs na sequência em que iriam rodar. Usada em allNodesIds para debug, previews e alguns asserts. Atenção. A função nunca chama completeCondition nem markDead. O ensaio assume que todos os branches são tomados. A lista é o cenário máximo, não necessariamente o que vai acontecer em uma execução real com condições.
export function planOrder(nodes, edges, starterSourceId): string[] { const state = buildSchedulerState(nodes, edges, starterSourceId); const order = []; let id; while ((id = nextReady(state)) !== null) { order.push(id); markCompleted(state, id); } return order; }

⚠️ Não considera conditions
planOrder só chama markCompleted. Nunca completeCondition ou markDead. Assume que todo branch é tomado. A ordem gerada é a hipótese máxima, não o que vai rodar em uma execução real com condições.

Basicamente o dobro do trabalho do build. Chama buildSchedulerState de novo e faz uma passada topológica. Executado a cada execução. Poderia ser cacheado por (flowId, version), já que é determinístico só a partir de nodes e edges. Hoje não é.

Uma vez aqui para schedState (flux.service.ts:3136) e outra dentro de planOrder para allNodesIds. Poderia reusar o mesmo state, mas exige que markCompleted seja não destrutivo. Não é.
Resumo — o que sai de 2.1.
• schedState: SchedulerState. Mutável. Consumido pelo loop da Fase 3.
• allNodesIds: string[]. Ordem topológica para debug/UI.
• Zero I/O. Puro CPU. Complexidade ~O(V+E) na maioria dos casos.
• Nós fora do reachable ficam invisíveis para a execução. Nunca executados.
Observações para migração.
• Essencial e código puro. Menor risco de migrar. Pode virar biblioteca compartilhada entre backend e worker sem mudança semântica.
• O worker não precisa rodar scheduler hoje. Cada activity é um nó isolado. Se um dia o worker orquestrar sub-DAGs, o mesmo módulo funciona.
• Cachear buildSchedulerState por (flowId, versionId) elimina uma rodada por execução. Custo trivial hoje. Cresce linear com o número de nós.
• Formalize a interface pública (só exporte buildSchedulerState, nextReady, markCompleted, markDead e completeCondition) antes de qualquer refactor. Hoje é fácil alguém importar um helper interno sem querer.
• Adicionar tipagem em cima de handles. As regex outputHandle-[01] e conditionHandle-[TF]\d+ são strings mágicas. Um enum tipado no front que gera esses handles seria mais seguro.

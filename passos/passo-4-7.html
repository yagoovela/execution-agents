Step 4.7 — Emails + HTTP Callbacks

Big block at flux.service.ts:4907-5196. Main loop per outputObjectNode (4917-5163). Double Redis dedup (5030-5075). Consolidated request callback (5164-5196). Sends emails via Gmail, Microsoft, or SendGrid. POSTs per-node callbacks. POSTs the consolidated callback at the end.
In short — what this step does
  • Prepares the "package" for each output. Per outputObjectNode, resolves emails, subject, text and urls in two formats: plain string or *Data array. Extracts URLs from varInputNode.uploadedFiles. Downloads each attachment via axios.get sequentially as a Buffer.
  • Guards against duplicate sends. Before sending, does two SET NXs in Redis. One per runId, TTL 24h, avoids re-sending on Bull retry. Another per sha256 hash of the content, TTL 90s, avoids spam on burst-triggered executions.
  • Dispatches through 1 of 3 providers. If the node has useFromPersonalGmail, sends from the user's own Gmail via OAuth. If it has useFromMicrosoft, sends via Outlook OAuth. Otherwise, falls back to the SendGrid default. SendGrid receives attachments as Buffer, unlike the others that accept a URL.
  • Per-output webhook. If the node has a configured callbackUrl, does POST { text } with a 10s timeout and no retry. If that URL matches requestCallbackUrl (fn E) exactly, the code skips. Avoids calling twice.
  • Consolidated request callback. At the end, if the request carried a callbackUrl, fires a POST in fire-and-forget mode. Rich payload: { success, error, flowId, sessionId, totalTokensUsed, totalCost, outputs[] }. Doesn't block the return.
  • Output. N emails sent. N per-node webhooks. 1 consolidated callback, all optional. Webhook and callback errors are logged without crashing. Email send error propagates.
Context. Longest step of Phase 4. Three groups. Group 1: per output, sends email to recipients with Redis dedup, when applicable. Group 2: per output, POSTs a webhook, when applicable. Group 3: consolidated callback at the request level, when applicable. Each group has its own logic. Dedup for duplicate emails. Consolidated callback dedup when it matches the per-node callback. 10s timeout on callbacks.

ACollect emails, urls, attachments
flux.service.ts:4917-5007
Per outputObjectNode: aggregates types ['emails', 'subject', 'text', 'urls']; extracts URLs from textData/uploadedFiles; downloads attachments via axios; assembles files[]
Purpose. Prepares data before sending. Collects emails from the emails string (comma-separated) or from emailsData (array of refs). Collects attachment URLs from urlsData, or from uploadedFiles on upstream varInputNodes. Downloads each URL as a Buffer to attach to the email.
In short. Heavy prep work before sending. The output node has fields like emails, subject, text, urls. Each can arrive in two formats: plain string (comma-separated) or array (emailsData, subjectData, urlsData) resolved from {{...}} references at the end of execution. The loop does the merge. If emailsData exists, joins everything with a comma. Otherwise, uses raw emails. URLs need more care. Can come from three sources. Source 1: explicit value in node.data.urls. Source 2: resolved from urlsData with refs to varInputNode.uploadedFiles (files the user attached in the chat). Source 3: URLs in plain text within other fields, captured by the regex /https?:\/\/[^\s]+/gi. For each valid URL, runs axios.get(url, { responseType: 'arraybuffer' }) to download as a Buffer. The Buffer becomes an email attachment. Download errors are logged and don't block the send. A missing file is acceptable. A problematic file doesn't block. There's plenty of merge and parse logic. Reflects that outputObjectNode accumulates responsibilities. It can be display. It can fire an email. It can do a callback.

BDouble Redis dedup (24h + 90s)
flux.service.ts:5030-5076
emailDedupeKey = `email-sent:${flowId}:${nodeId}:${runId}` (24h NX) · emailContentDedupeKey = `email-content:${flowId}:${nodeId}:${sha256(emails+subject+text)}` (90s NX)
Purpose. Avoids duplicate emails on two dimensions. Dimension 1: same runId, TTL 24h. If this execution already sent the email via accidental retry, skips. Dimension 2: same content, TTL 90s. If it ran twice in a short window with the same recipients, subject, and body, skips. Both use Redis SET NX.
In short. Defense in depth against accidental spam. The Bull queue and retry policies can re-execute the same run twice (retry on transient error). That would email the client twice. Dedup 1: key by runId. If the execution already sent it, SET NX fails (the key exists) and skips. TTL 24h. More than enough time for any retry. Dedup 2: key by content hash. If in a 90s window the same email is sent for N reasons (different executions), skips. Covers agent bugs that fire emails in a fast loop. Both use SET key value EX ttl NX. Atomic Redis command. Returns null if the key already exists. firstSend === null means duplicate, skip. Log duplicate send suppressed helps debugging. If both pass, the code moves on to dispatch. Classic Redis dedup use case. Simple and effective.
// Dedup 1: per runId (24h) const emailDedupeKey = `email-sent:${flowId}:${node?.id}:${runLogProcessId}`; const firstSend = await this.redisClient.set( emailDedupeKey, '1', 'EX', EMAIL_DEDUPE_TTL_SECONDS, 'NX', ); if (firstSend === null) return { success: false, message: 'Duplicate send suppressed' }; // Dedup 2: per content hash (90s) const emailContentHash = createHash('sha256') .update(`${[...emailsArray].sort().join(',')}|${emailSubject}|${emailText}`).digest('hex'); const emailContentDedupeKey = `email-content:${flowId}:${node?.id}:${emailContentHash}`; // same SET NX ...
🎯 emailsArray sorted
[...emailsArray].sort(). Ensures the same recipient list (same people in different order) produces the same hash. Important for dedup to work.
⚠️ 24h TTL is long
If the user edits the agent and re-executes with the same config within 24h, the runId dedup won't catch it. The runId is unique. If the same execution is retried by Bull, the dedup works. Good retry coverage. Doesn't cover intentional resends.
CEmail dispatch (3 providers)
flux.service.ts:5077-5125
if (useFromPersonalGmail) mailService.sendGmailEmail(...); else if (useFromMicrosoft) microsoftMailService.sendMail(...); else mailService.sendMail(...) /* SendGrid default */;
Purpose. Dispatch across 3 providers based on node flags. Provider 1: personal Gmail (user's own OAuth). Calls sendGmailEmail passing user.email as the sender. Provider 2: Microsoft (Outlook OAuth). Calls microsoftMailService.sendMail. Provider 3: SendGrid default. Calls mailService.sendMail. Each has a specific signature and configuration.
In short. Three paths with similar props. If node.data.useFromPersonalGmail=true, the email is sent from the user's own Gmail via a connected OAuth token. Personalized because the email comes from a personal address. If useFromMicrosoft=true, the same pattern applies to Microsoft and Outlook. With no flag, the default is SendGrid via mailService.sendMail. All accept: recipients (array), subject, HTML body (with template htmlBody(user, node) or raw), plain text via htmlToPlainText, and attachments. Attachments go as Buffer[] on SendGrid and as URLs on Gmail and Microsoft.

DWebhook per-node (fire-and-log)
flux.service.ts:5128-5161
nodeCallbackUrl = data.callbackUrlInputData?.[0]?.text || data.callbackUrl || data.webhookUrl; if (nodeCallbackUrl && !isDuplicateOfRequestCallback) { await axios.post(url, { text }, { timeout: 10000 }); }
Purpose. After the email, if the output has a callbackUrl configured, does a POST with { text }. Dedup against requestCallbackUrl. If the node's callback is the same as the consolidated one, skips. Avoids 2 POSTs to the same endpoint. 10s timeout. No retry.
In short. Per-output webhook. The outputObjectNode may have a callback URL configured in the editor. When execution ends, does a simple POST with { text }. Just the output text, no rich payload. 10s timeout. No retry. Failure is only logged. Dedup against requestCallbackUrl (the consolidated request callback, fn E). If the user set the same URL on both, avoids calling twice. Compares trimmedNodeCallbackUrl.toLowerCase() === normalizedRequestCallbackUrl. Case-insensitive comparison. Field precedence: callbackUrlInputData[0].text (resolved from {{...}}) > callbackUrl (plain string) > webhookUrl (legacy alias).
const nodeCallbackUrl = node?.data?.callbackUrlInputData?.[0]?.text || node?.data?.callbackUrl || node?.data?.webhookUrl; if (trimmedNodeCallbackUrl && !isDuplicateOfRequestCallback) { try { await axios.post(trimmedNodeCallbackUrl, { text: extractOutputText(node) }, { headers: { 'Content-Type': 'application/json' }, timeout: 10000, }); } catch (error) { /* log webhook_error, no throw */ } }
🎯 Minimalist payload
Just { text }. Doesn't include tokens, cost, or error info. The per-output callback is for "here's this output's result". Lets you plug a Zapier in easily.
⚠️ No retry
A failure means permanent delivery failure. Could become a reliability issue. Ideal would be retry plus dead-letter queue.
EConsolidated request callback
flux.service.ts:5164-5196
if (requestCallbackUrl) { axios.post(url, { success, error, flowId, sessionId, totalTokensUsed, totalCost, outputs: [{ outputId, text }] }, { timeout: 10000 }).catch(logError);
Purpose. After all per-node callbacks, does a consolidated POST to the request's callbackUrl. That URL is a client parameter when starting the execution. Rich payload: success or error, all outputs, costs. It's fire-and-forget (.catch(log) with no await). Doesn't block the execution return.
In short. Callback at the whole-request level. Unlike the per-node callback (fn D), here there's only one and it carries a complete payload. Includes success (based on whether nodeError is null or not), flowId, sessionId, total tokens and cost, and outputs[] with { outputId, text } for each outputObjectNode. Serves external systems monitoring executions. Examples: internal dashboard, billing system, larger orchestrator that calls Flux via API. Fire-and-forget. axios.post().catch(log), no await. So the apiV2() return doesn't wait for that POST. If the POST takes 5s, the HTTP client gets a response in about 200ms. The callback fires in the background. Makes sense. The endpoint client already asked for an async callback. The timeout still exists (10s), but it's on axios, not the backend.
if (requestCallbackUrl) { const consolidatedPayload = { success: !nodeError, error: nodeError ? 'Flow execution failed' : null, flowId, sessionId: sessionId || null, totalTokensUsed, totalCost, timestamp: new Date().toISOString(), outputs: nodeError ? [] : getOutputsObjectNodes.map(node => ({ outputId: node.id, text: extractOutputText(node), })), }; axios.post(requestCallbackUrl, consolidatedPayload, { /* ... */ }) .catch(error => { /* log webhook_error */ }); }
🎯 Empty outputs on error
If nodeError exists, the outputs field is empty. The client sees "error and no outputs". Clear signal. On success, all outputs go in.
⚠️ No retry
Same as fn D. A failure loses the delivery. Ideal endpoints: (a) idempotency on the callback receiver; (b) exponential backoff plus DLQ on the sender.
Summary — what leaves 4.7:
• N emails sent (via Gmail, Outlook or SendGrid) with double Redis dedup.
• N POST webhooks per output.
• 1 consolidated callback, if the request carried a callbackUrl.
• Individual failures are logged and don't cause crashes. Email error throws.
Migration notes:
• Huge block (about 300 lines). Main candidate to extract into an OutputDeliveryService or similar.
• Serial attachment download is a bottleneck. Worth parallelizing.
• Redis dedup is a good pattern. Keep it.
• Lack of retry is debt. Consider Bull's retry policy for failing webhooks and emails.
• Consolidated callback in fire-and-forget mode is OK for async. On the dev side, a /runs/:id/callback-status endpoint would be better to check whether the callback arrived.

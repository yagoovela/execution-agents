Passo 4.7 — Emails + Callbacks HTTP

Bloco grande em flux.service.ts:4907-5196. Loop principal por outputObjectNode (4917-5163). Dedup Redis duplo (5030-5075). Callback consolidado do request (5164-5196). Envia emails via Gmail, Microsoft ou SendGrid. Faz POST de callbacks por nó. Faz POST do callback consolidado no fim.
Em resumo — o que esse passo faz
  • Prepara o "pacote" de cada output. Por outputObjectNode, resolve emails, subject, text e urls em dois formatos: string direta ou array *Data. Extrai URLs de varInputNode.uploadedFiles. Baixa cada anexo via axios.get em série como Buffer.
  • Blinda contra envio duplicado. Antes de mandar, faz dois SET NX no Redis. Um por runId, com TTL de 24h, evita reenvio em retry do Bull. Outro por hash sha256 do conteúdo, com TTL de 90s, evita spam em execuções disparadas em rajada.
  • Despacha em 1 de 3 providers. Se o nó tem useFromPersonalGmail, sai do Gmail do próprio user via OAuth. Se tem useFromMicrosoft, sai por Outlook OAuth. Caso contrário, cai no default SendGrid. O SendGrid recebe anexos como Buffer, ao contrário dos outros que aceitam URL.
  • Webhook por output. Se o nó tem callbackUrl configurada, faz POST { text } com timeout de 10s e sem retry. Se essa URL bate exatamente com o requestCallbackUrl (fn E), o código pula. Assim não chama 2 vezes.
  • Callback consolidado do request. No fim, se o request trouxe callbackUrl, dispara um POST em modo fire-and-forget. Payload rico: { success, error, flowId, sessionId, totalTokensUsed, totalCost, outputs[] }. Não bloqueia o retorno.
  • Saída. N emails enviados. N webhooks por nó. 1 callback consolidado, todos opcionais. Erros de webhook e callback são logados sem crash. Erro de envio de email propaga.
Contexto. Passo mais longo da Fase 4. Três grupos. Grupo 1: por output, envia email para destinatários com dedup Redis, quando aplicável. Grupo 2: por output, faz POST de webhook, quando aplicável. Grupo 3: callback consolidado no nível do request, quando aplicável. Cada grupo tem lógica própria. Dedup para emails duplicados. Deduplicação de callback consolidado quando coincide com callback por nó. Timeout de 10s nos callbacks.

⚠️ Download sequencial, N por vez
Baixa anexos em série (for). Um email com 5 anexos de 10MB significa 50MB × RTT. Segundos de latência antes de enviar. Seria possível paralelizar com Promise.all.
📎 uploadedFiles do varInputNode
O usuário sobe um arquivo no chat ou form. O arquivo entra em varInputNode.uploadedFiles. Aqui o valor é resolvido para URL do S3 e baixado para anexar.
🔧 Regex de URL
/https?:\/\/[^\s]+/gi. Captura tudo depois de http(s):// até um whitespace. Simples e funcional para URLs comuns. Pode incluir caracteres finais indesejados (vírgula, parênteses).
BRedis dedup duplo (24h + 90s)
flux.service.ts:5030-5076
emailDedupeKey = `email-sent:${flowId}:${nodeId}:${runId}` (24h NX) · emailContentDedupeKey = `email-content:${flowId}:${nodeId}:${sha256(emails+subject+text)}` (90s NX)
Propósito. Evita duplicação de emails em duas dimensões. Dimensão 1: mesmo runId, TTL de 24h. Se esta execução já enviou o email por retry acidental, pula. Dimensão 2: mesmo conteúdo, TTL de 90s. Se rodou 2 vezes em janela curta com os mesmos destinatários, subject e texto, pula. Ambas usam Redis SET NX.
Em resumo. Defesa em profundidade contra spam acidental. A fila Bull e as políticas de retry podem re-executar a mesma execução duas vezes (retry por erro transiente). Isso emailaria o cliente duas vezes. Dedup 1: chave por runId. Se a execução já enviou, o SET NX falha (a chave existe) e pula. TTL de 24h. Tempo mais que suficiente para qualquer retry. Dedup 2: chave por hash do conteúdo. Se em janela de 90s o mesmo email é enviado por N causas (execuções diferentes), pula. Cobre bug de agente que dispara email em loop rápido. Ambas usam SET key value EX ttl NX. Comando Redis atômico. Retorna null se a chave já existe. firstSend === null significa duplicata, pula. Log duplicate send suppressed ajuda no debug. Se ambos passam, o código segue para o dispatch. Caso de uso clássico de dedup com Redis. Simples e efetivo.
// Dedup 1: por runId (24h) const emailDedupeKey = `email-sent:${flowId}:${node?.id}:${runLogProcessId}`; const firstSend = await this.redisClient.set( emailDedupeKey, '1', 'EX', EMAIL_DEDUPE_TTL_SECONDS, 'NX', ); if (firstSend === null) return { success: false, message: 'Duplicate send suppressed' }; // Dedup 2: por content hash (90s) const emailContentHash = createHash('sha256') .update(`${[...emailsArray].sort().join(',')}|${emailSubject}|${emailText}`).digest('hex'); const emailContentDedupeKey = `email-content:${flowId}:${node?.id}:${emailContentHash}`; // mesma SET NX ...
🎯 emailsArray ordenado
[...emailsArray].sort(). Garante que a mesma lista de destinatários (mesmas pessoas em ordem diferente) produz o mesmo hash. Importante para o dedup funcionar.
⚠️ TTL de 24h é longo
Se o usuário editar o agente e reexecutar com a mesma configuração em 24h, o dedup por runId não pega. O runId é único. Se a mesma execução for retentada pelo Bull, o dedup funciona. Boa cobertura para retry. Não cobre reenvio intencional.
CEmail dispatch (3 providers)
flux.service.ts:5077-5125
if (useFromPersonalGmail) mailService.sendGmailEmail(...); else if (useFromMicrosoft) microsoftMailService.sendMail(...); else mailService.sendMail(...) /* SendGrid default */;
Propósito. Dispatch entre 3 providers com base em flags do nó. Provider 1: Gmail pessoal (OAuth do próprio user). Chama sendGmailEmail passando user.email como remetente. Provider 2: Microsoft (Outlook OAuth). Chama microsoftMailService.sendMail. Provider 3: SendGrid default. Chama mailService.sendMail. Cada um tem assinatura e configuração específicas.
Em resumo. Três caminhos com props semelhantes. Se node.data.useFromPersonalGmail=true, o email sai do Gmail do próprio user via OAuth token conectado. Personaliza porque o email vem do endereço pessoal. Se useFromMicrosoft=true, o mesmo padrão vale para Microsoft e Outlook. Sem nenhuma flag, o default é SendGrid via mailService.sendMail. Todos aceitam: destinatários (array), subject, corpo HTML (com template htmlBody(user, node) ou raw), texto puro via htmlToPlainText, e anexos. Anexos vão como Buffer[] no SendGrid e como URLs no Gmail e Microsoft.

⚠️ Erro faz throw
Se o envio falha em qualquer provider, o código faz throw new Error(...). O erro propaga para o caller. Aborta o restante da Fase 4 (webhook desse nó, callback consolidado) porque está dentro do Promise.all. O ideal seria isolar.

🎯 Payload minimalista
Só { text }. Não inclui tokens, cost ou informação de erro. O callback por output serve para "aqui está o resultado deste output". Permite conectar um Zapier de forma simples.
⚠️ Sem retry
Uma falha significa falha permanente para essa entrega. Pode virar problema de confiabilidade. O ideal seria retry mais dead-letter queue.
ECallback consolidado do request
flux.service.ts:5164-5196
if (requestCallbackUrl) { axios.post(url, { success, error, flowId, sessionId, totalTokensUsed, totalCost, outputs: [{ outputId, text }] }, { timeout: 10000 }).catch(logError);
Propósito. Depois de todos os callbacks por nó, faz um POST consolidado à callbackUrl do request. Essa URL é parâmetro do cliente ao iniciar a execução. Payload rico: sucesso ou erro, todos os outputs, custos. É fire-and-forget (.catch(log) sem await). Não bloqueia o retorno da execução.
Em resumo. Callback no nível do request inteiro. Diferente do callback por nó (fn D), aqui é um só e traz payload completo. Inclui success (com base em nodeError ser null ou não), flowId, sessionId, tokens e cost totais, e outputs[] com { outputId, text } de cada outputObjectNode. Serve para sistemas externos monitorarem execuções. Exemplos: dashboard interno, sistema de billing, orquestrador maior que chama Flux via API. Fire-and-forget. axios.post().catch(log), sem await. Assim, o retorno do apiV2() não espera esse POST. Se o POST demora 5s, o cliente HTTP recebe resposta em cerca de 200ms. O callback dispara em segundo plano. Faz sentido. O cliente do endpoint já pediu callback assíncrono. O timeout ainda existe (10s), mas é do axios, não do backend.

🎯 outputs vazio em caso de erro
Se existe nodeError, o campo outputs vai vazio. O cliente vê "erro e sem outputs". Sinal claro. Em sucesso, todos os outputs entram.
⚠️ Sem retry
Como o fn D. Uma falha perde a entrega. Endpoints ideais: (a) idempotência no receiver do callback; (b) exponential backoff mais DLQ no sender.
Resumo — o que sai de 4.7:
• N emails enviados (via Gmail, Outlook ou SendGrid) com dedup Redis duplo.
• N webhooks POST por output.
• 1 callback consolidado, se o request trouxe callbackUrl.
• Falhas individuais são logadas e não causam crash. Erro de email faz throw.
Observações para migração:
• Bloco gigante (cerca de 300 linhas). Candidato principal para extrair num OutputDeliveryService ou similar.
• Download de anexos em série é gargalo. Vale paralelizar.
• O dedup Redis é bom padrão. Manter.
• A ausência de retry é dívida. Considerar política de retry do Bull para webhooks e emails que falhem.
• Callback consolidado em modo fire-and-forget está OK para async. Do lado do dev, seria melhor um endpoint /runs/:id/callback-status para saber se o callback chegou.

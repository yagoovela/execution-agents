Passo 4.7 — Emails + Callbacks HTTP

Bloco grande em flux.service.ts:4907-5196. Loop principal por outputObjectNode (4917-5163), dedup Redis duplo (5030-5075), callback consolidado do request (5164-5196). Envia emails via Gmail/Microsoft/SendGrid, POST callbacks por-nó, POST callback consolidado no fim.
Em resumo — o que esse passo faz
  • Prepara o "pacote" de cada output: por outputObjectNode, resolve emails/subject/text/urls em 2 formatos (string direta ou *Data array), extrai URLs de varInputNode.uploadedFiles e baixa cada anexo via axios.get em série como Buffer.
  • Blinda contra envio duplicado: antes de mandar, dois SET NX no Redis — um por runId (24h, evita reenvio em retry do Bull) e outro por hash sha256 do conteúdo (90s, evita spam em runs disparados em rajada).
  • Despacha em 1 de 3 providers: se o node tem useFromPersonalGmail, sai do Gmail do próprio user via OAuth; se useFromMicrosoft, vai por Outlook OAuth; senão cai no default SendGrid (que recebe attachments como Buffer, ao contrário dos outros que aceitam URL).
  • Webhook por output: se o node tem callbackUrl configurada, faz POST { text } com timeout de 10s e sem retry. Se essa URL bate exatamente com o requestCallbackUrl (fn E), skipa pra não chamar 2×.
  • Callback consolidado do request: no fim, se o request trouxe callbackUrl, dispara fire-and-forget um POST rico com { success, error, flowId, sessionId, totalTokensUsed, totalCost, outputs[] } — não bloqueia o retorno.
  • Saída: N emails enviados, N webhooks per-node, 1 callback consolidado (opcionais); erros de webhook/callback são logados sem crashar, mas erro de envio de email propaga.
Contexto: passo mais longo da Fase 4. Tem 3 grupos: (i) por output, opcionalmente envia email pra recipients (com dedup Redis); (ii) por output, opcionalmente faz POST webhook; (iii) request-level callback consolidado (opcional). Cada um tem lógica própria — dedup pra emails duplicados, deduplicação de callback consolidado se coincidir com callback por-nó, timeout de 10s em callbacks.

BRedis dedup duplo (24h + 90s)
flux.service.ts:5030-5076
emailDedupeKey = `email-sent:${flowId}:${nodeId}:${runId}` (24h NX) · emailContentDedupeKey = `email-content:${flowId}:${nodeId}:${sha256(emails+subject+text)}` (90s NX)
Propósito: Evita duplicação de emails em 2 dimensões: (i) mesmo run ID (24h TTL) — se este run já enviou este email por retry acidental, skip; (ii) mesmo conteúdo (90s TTL) — se rodou 2 vezes em janela curta com mesmo destinatários/subject/texto, skip. Ambos via Redis SET NX (only-if-not-exists).
Em resumo: defesa em profundidade contra spam acidental. Bull queue e retry policies podem re-executar o mesmo run 2× (retry por erro transient), o que emailaria o cliente 2×. Dedup #1: chave por runId — se este run já enviou, `SET NX` falha (key existe), skip. TTL 24h (tempo mais que suficiente pra qualquer retry). Dedup #2: chave por hash do conteúdo — se em janela de 90s o mesmo email é enviado por N causas (diferentes runs), skip. Cobre bug de agente que dispara email em loop rápido. Ambos usam SET key value EX ttl NX — comando Redis atomic que retorna null se já existe. firstSend === null = duplicata, skip. Log de "duplicate send suppressed" pra debug. Se ambos passam, prossegue pra dispatch. Isso é caso de uso clássico de dedup Redis — simples e efetivo.

🎯 Sorted emailsArray
[...emailsArray].sort() — garante mesma lista de recipients (mesma pessoas em ordem diferente) hash igual. Importante pra dedup funcionar.
⚠️ 24h TTL é longo
Se usuário editar o agente e re-executar com mesma config em 24h, o dedup por runId nem pega (runId é único). Mas se o mesmo run for retentado por Bull, dedup funciona. Boa cobertura pra retry, não pra "resubmit intencional".

ECallback consolidado do request
flux.service.ts:5164-5196
if (requestCallbackUrl) { axios.post(url, { success, error, flowId, sessionId, totalTokensUsed, totalCost, outputs: [{ outputId, text }] }, { timeout: 10000 }).catch(logError);
Propósito: Após todos os per-node callbacks, faz um POST consolidado ao callbackUrl do request (parâmetro passado pelo cliente ao iniciar o run). Payload rico: sucesso/erro, todos os outputs, custos. É fire-and-forget (.catch(log) sem await), não bloqueia o retorno do run.
Em resumo: callback nível do request inteiro. Diferente do per-node (fn D), esse é um só e traz payload completo: success (baseado em nodeError null ou não), flowId, sessionId, tokens/cost totais, e outputs[] com { outputId, text } de cada outputObjectNode. Serve pra sistemas externos monitorar runs — ex: dashboard interno, sistema de billing, orquestrador maior chamando Flux via API. Fire-and-forget: axios.post().catch(log) — sem await. Assim, o retorno do apiV2() não espera esse POST. Se demorar 5s, o cliente HTTP recebe resposta em ~200ms e o callback vai dispatched em segundo plano. Sensato — cliente do endpoint já pediu callback assíncrono. Timeout ainda existe (10s) mas é do axios, não do backend.

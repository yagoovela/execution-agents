AnodesWithError filter
flux.service.ts:4780-4782
const nodesWithError = myUpdatedNodes.filter(node => node.data?.errorMessage || node.data?.errorStatusCode);
Purpose. Scans myUpdatedNodes looking for nodes marked with error. Simple filter, no I/O. Not every errored node caused fail-fast. In edge cases, multiple nodes may have written errorMessage and the loop stopped for another reason, like cancel.
In summary. It's the census of errored nodes. Walks through all the agent's nodes. Groups those that have errorMessage or errorStatusCode defined. In execution with fail-fast (the most common), there's only 1 node in that list. It's the one responsible for stopping everything. In more complex edge cases (cancel after multiple nodes had already written soft-fail without breaking the loop, or scheduler bugs), there may be more. Regardless of quantity, the next step (4.3) uses only the first to assemble log and message. The list contains candidates. The choice is first-fit.
const nodesWithError = myUpdatedNodes.filter( node => node.data?.errorMessage || node.data?.errorStatusCode, );
🎯 OR between 2 fields
Selects the node when either of the 2 fields is populated. Some handlers define only errorStatusCode (HTTP code). Others, only errorMessage.
⚠️ Falsy check
The || discards '', 0 and null. If a handler defines errorMessage: '' by bug, that node doesn't enter the list, even though it's technically errored.

CresolveRunLogStatus (pure helper)
node-cancel-outcome.ts:1-8 · call at 4790-4793
export function resolveRunLogStatus(params: { hasNodeError: boolean; stoppedByCancel: boolean }): string
Purpose. Pure function that decides the execution's status string. Error while running if there's an error. Cancelled if it was cancelled. Successfully ran otherwise. Order of precedence matters. Error beats cancel.
In summary. Pure string decision, no I/O, no side effect. If there's an error on any node, it wins everything. Status Error while running. Even if it was also cancelled midway, the error is prioritized. If there was no error and it was cancelled, status Cancelled. Otherwise, success: Successfully ran. The strings are free-form, not enum. Go to the status column of execution_logs. A bit fragile because they're strings (typo breaks query), but functional.
export function resolveRunLogStatus(params: { hasNodeError: boolean; stoppedByCancel: boolean; }): string { if (params.hasNodeError) return 'Error while running'; if (params.stoppedByCancel) return 'Cancelled'; return 'Successfully ran'; }
🎯 Precedence: error, cancel, success
Not accidental. Cancel while running OK generates Cancelled. Cancel while there was an error generates Error while running. The dev wants to see the real error, not the cancel that came after.
⚠️ No flow_truncated status
If an orphan node remained without stop flags (bug in 4.1), the status is still Successfully ran. There's no hasNodeError. Subtle inconsistency. The Winston log says truncated, but execution_logs shows success.

Notes for migration.
• Pure, no I/O. Trivial to move anywhere. Can become a shared utility between backend and worker.
• The status strings deserve to become a typed enum (RunLogStatus.Error | Cancelled | Success).
• Picking [0] arbitrarily can become a bug if someday agents have multiple parallel outputs with failures.
• Doesn't block migration. Can stay as is. Incremental refactor.

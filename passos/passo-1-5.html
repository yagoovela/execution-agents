Step 1.5 — Custom objects loading

Block in flux.service.ts:2439-2462. Resolves the objects owner (space, companyUser or user) and loads the UserObject entries for that owner. Objects are user-defined JSON structures. The nodesBox node reads them and, in some cases, writes them during execution.
In summary — what this step does
  • Determines who owns the object set. Cascade with 3 mutually exclusive options. If the flow is in a space, the objects belong to the space (collaborative). Otherwise, if the user has selectedCompanyId, checks the CompanyUser relation in the database. Otherwise, falls back to the personal objects of the user.
  • Loads all objects of that owner. getObjectsByOwner builds a dynamic WHERE clause (space_id, company_user_id or user_id) and runs SELECT * FROM user_objects without pagination. If the owner comes in empty, the WHERE becomes {}. It's a footgun that returns everything from everyone.
  • Translates entity to DTO. toJsonArray is a pure mapper that renames objectId to id, drops ownership columns and timestamps, and returns FluxObject[] in the flat shape the frontend and nodesBox expect.
  • Sets up the mutation mechanism. Creates the onMutateObjectCallerData closure that lets the nodesBox handler rewrite the list during execution. Changes made by one node become visible to the next. It's reference reassignment (let), not in-place mutation.
  • Output. objectCallerData equal to FluxObject[], ready to be read by nodesBox handlers in Phase 3. Plus the onMutateObjectCallerData callback that keeps this list synchronized across nodes throughout execution.
Context. Custom objects are named data structures (key-value plus sessions) that the user defines in the editor. The nodesBox node uses them as storage. They are loaded once here and are referenced through mutable objectCallerData throughout the loop.

A Resolve ObjectOwner (3 fallbacks)
flux.service.ts:2439-2454
let objectOwner: ObjectOwner; // { userId? } | { companyUserId? } | { spaceId? }
Purpose. Decides which scope the custom objects come from. Space (shared), companyUser (private within a company) or user (private personal). Cascade over 3 exclusive cases.
In summary. The function answers a single question: who owns the custom object set? Tests in order. First, if the flow lives inside a space, the objects belong to that space (shared with the team). Second, if there's no space but the user is logged into a company, queries the database to confirm this relation. If found, the objects belong to the companyUser. Otherwise, falls to personal. Third, if neither space nor selected company came in, the objects belong to the user itself. The result is an object { spaceId }, { companyUserId } or { userId }, mutually exclusive. The next steps use it to filter exactly one subset in the database.

2a found companyUser { companyUserId }
2b not found { userId }

🎯 3 object ownership modes
1. Space. Object shared among all members of the space (collaboration).

2. CompanyUser. Private within a company. The user belongs to that company, but the object isn't public in the space.

3. User. Private, tied only to the user (personal use, outside any company).
📎 Precedence. Why space first?
If the flow is in a space, it makes sense to use that space's objects (collaborative context). Only falls to companyUser or user when the flow isn't in any space.

Note. selectedCompanyId is the user's active workspace. The same company can have multiple users, each with their own objects.
🔧 How it's used in buildWhereClause
Later in (C), buildWhereClause translates this ObjectOwner to the right column of the user_objects table.
spaceId. WHERE space_id = X.
companyUserId. WHERE company_user_id = X.
userId. WHERE user_id = X.

Three different columns in the same table. Only one is populated per row.

Purpose. Loads all UserObject entries for that owner. Delegates all WHERE logic to the private buildWhereClause helper.
In summary. After (A) and (B) decide the owner, this function actually loads the objects. Receives the ObjectOwner. Passes it to the buildWhereClause helper, which translates into which database column to filter (space_id, company_user_id or user_id). Runs SELECT * on user_objects. D objectsService.toJsonArray()

toJsonArray(objects: UserObject[]): FluxObject[]
Purpose. Pure mapper. Converts the UserObject entity (which has objectId, separate owner columns, etc) to the FluxObject DTO that the frontend and nodesBox expect. Uses id instead of objectId and omits ownership columns.
In summary. A pure function, no I/O. Just swaps the structure. The entities coming from (C) carry fields the frontend doesn't need to see. The real database PK, owner columns, TypeORM timestamps. Here they get remapped into a leaner shape. id (which is actually objectId), name, text, sessions, etc. After this step, consumers of the list (nodesBox itself and the frontend) work with FluxObject[]. No risk of leaking internal DB details or the real PK.

E onMutateObjectCallerData (callback)
flux.service.ts:2460-2462
const onMutateObjectCallerData = (data) => { objectCallerData = data; };
Purpose. Closure that lets nodesBox mutate the object list during agent execution. Without this mutable reference, changes made by a node would not propagate to subsequent nodes in the same execution.
In summary. This callback sits between nodes. When a nodesBox alters an object mid-execution (writes new text, switches the active session, adds a row), the callback receives the new version of the list and reassigns the objectCallerData variable in the parent scope. So the next node that reads the list already sees the updated state. It's a classic mutation closure. Instead of mutating the array in place, replaces the entire reference with the new array the handler returned. Follows the same pattern as onMutateSchema and onUpdateTokens. It's the main friction point for a worker migration. On the worker, nodes don't share this memory. They would have to round-trip back to the backend on every mutation.

E2 Passed as argument to the nodesBox handler
When the main loop (Phase 3) dispatches a nodesBox-type node, it passes objectCallerData (current value) and onMutateObjectCallerData (mutation callback). The handler calls the callback if the object was changed, propagating to the next iteration.

See flux.service.ts:3575-3599, 4146-4174 (nodesBox handler).
🎯 Closure mutation pattern
It's the same pattern used by onMutateSchema right below (line 2465-2467) and by onUpdateTokens in Phase 3. Keeps the source of truth in apiV2()'s scope and lets child services update it without passing an object reference.
⚠️ Potential race condition
If two nodesBox nodes run in parallel, the last callback wins. Doesn't happen in the legacy loop today. In a parallelism refactor, it will surface.

On the worker it would be worse. The worker doesn't share this closure. The mutation would be lost.
🔧 Reassignment, not array mutation
The callback replaces the reference (objectCallerData = data) instead of mutating the array in-place (objectCallerData.push(...)).

Intentional. The nodesBox handler returns a new array with the changes already applied.
Summary. What comes out of 1.5:
objectOwner. ObjectOwner (space, companyUser or user, mutually exclusive).
objectCallerData. FluxObject[]. List of objects for that owner, in the flat format expected by the frontend.
onMutateObjectCallerData. Callback the loop passes to the nodesBox handler to rewrite the list during execution.
No heavy I/O. 1 (rarely 2) SELECTs, no pagination, no cache.
Notes for migration:
The ObjectOwner resolution cascade (A) is pure business logic. Replicable anywhere. Needs flow.folder.spaces.id and user.selectedCompanyId as input.
The buildWhereClause footgun returning {} when the owner is empty is a warning for any new implementation. Always ensure at least userId before calling.
If the worker needs the objects, it should receive the array ready at workflow start or run the query itself. In that case, it loses the closure mutation pattern. The worker can't later change the backend's in-memory array.
onMutateObjectCallerData is the biggest hurdle for the migration. nodesBox mutating objectCallerData during execution is shared state across nodes. On the worker, each node runs isolated. Any mutation would have to go via an API call back to the backend. That costs a round-trip per nodesBox node.
Without refactor effort, 1.5 can stay on the backend even after the migration. It's fast and the result is passed in the workflow start-args.

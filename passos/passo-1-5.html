Passo 1.5 — Carregamento de objetos personalizados

Bloco em flux.service.ts:2439-2462. Resolve quem é o dono dos objetos (space, companyUser ou user) e carrega os UserObject daquele owner. Objetos são JSONs personalizados. O node nodesBox lê e, em alguns casos, escreve durante a execução.
Em resumo — o que esse passo faz
  • Descobre de quem é o conjunto de objetos. Cascata em 3 opções mutuamente exclusivas. Se o flow está num space, os objetos são do space (colaborativo). Caso contrário, se o usuário tem selectedCompanyId, confere no banco a relação CompanyUser. Caso contrário, fallback para os objetos pessoais do próprio user.
  • Carrega todos os objetos daquele dono. getObjectsByOwner monta um WHERE clause dinâmico (space_id, company_user_id ou user_id) e faz SELECT * FROM user_objects sem paginação. Se o owner vier vazio, o WHERE vira {}. É um footgun que traz tudo de todos.
  • Traduz entidade para DTO. toJsonArray é um mapper puro que renomeia objectId para id, descarta colunas de ownership e timestamps, e devolve FluxObject[] no shape flat que o frontend e o nodesBox esperam.
  • Configura o mecanismo de mutação. Cria o closure onMutateObjectCallerData que permite ao handler do nodesBox reescrever a lista durante a execução. Mudanças feitas por um nó ficam visíveis para o próximo. É reatribuição de referência (let), não mutação in-place.
  • Saída. objectCallerData igual a FluxObject[], pronto para ser lido pelos handlers de nodesBox na Fase 3. Mais o callback onMutateObjectCallerData que mantém essa lista sincronizada entre nós ao longo da execução.
Contexto. Objetos personalizados são estruturas de dados nomeadas (chave-valor mais sessions) que o usuário define no editor. O nó nodesBox os usa como storage. São carregados uma única vez aqui e passam a referenciar objectCallerData mutável ao longo do loop.

A Resolve ObjectOwner (3 fallbacks)
flux.service.ts:2439-2454
let objectOwner: ObjectOwner; // { userId? } | { companyUserId? } | { spaceId? }
Propósito. Decide de qual escopo os objetos personalizados vêm. Space (compartilhado), companyUser (privado dentro de uma company) ou user (privado pessoal). Cascata em 3 casos exclusivos.
Em resumo. A função responde a uma pergunta. De quem é o conjunto de objetos personalizados? Testa em ordem. Primeiro, se o flow vive dentro de um space, os objetos são do space (compartilhados com o time). Segundo, se não há space mas o usuário está logado numa company, consulta o banco para confirmar essa relação. Se acha, os objetos são do companyUser. Caso contrário, cai para o pessoal. Terceiro, se não veio nem space nem company selecionada, os objetos são do próprio user. O resultado é um objeto { spaceId }, { companyUserId } ou { userId }, mutuamente exclusivo. Os próximos passos o usam para filtrar exatamente um subconjunto no banco.

2a achou companyUser { companyUserId }

ObjectOwner é um union type mutually-exclusive
interface ObjectOwner { userId?: string; companyUserId?: string; spaceId?: string; }

🎯 3 modos de ownership de objetos
1. Space. Objeto compartilhado entre todos os membros do space (colaboração).

2. CompanyUser. Privado dentro de uma company. O usuário pertence a essa company, mas o objeto não é público no space.

3. User. Privado, atrelado apenas ao usuário (uso pessoal, fora de qualquer company).
📎 Precedência. Por que space primeiro?
Se o flow está em um space, faz sentido usar os objetos daquele space (contexto colaborativo). Só cai para companyUser ou user se o flow não está em space nenhum.

Nota. selectedCompanyId é o workspace ativo do usuário. A mesma company pode ter múltiplos usuários, cada um com os próprios objetos.
🔧 Como é usado no buildWhereClause
Depois em (C), buildWhereClause traduz esse ObjectOwner na coluna correta da tabela user_objects.
spaceId. WHERE space_id = X.
companyUserId. WHERE company_user_id = X.
userId. WHERE user_id = X.

São 3 colunas diferentes na mesma tabela. Só uma é populada por linha.

C objectsService.getObjectsByOwner()
objects.service.ts:21-24
async getObjectsByOwner(owner: ObjectOwner): Promise<UserObject[]>
Propósito. Carrega todos os UserObject daquele owner. Delega toda a lógica de WHERE ao helper privado buildWhereClause.
Em resumo. Depois de (A) e (B) decidirem o dono, esta função efetivamente carrega os objetos. Recebe o ObjectOwner. Passa ao helper buildWhereClause, que traduz em qual coluna do banco filtrar (space_id, company_user_id ou user_id). Executa SELECT * em user_objects. O retorno é um array de entidades UserObject. Todos os objetos daquele dono. Cuidado embutido. Se por algum motivo o owner vier vazio, o WHERE vira {} e o banco devolve todos os objetos de todos os usuários. É um footgun clássico. Um bug em (A) pode causar leak.

⚠️ Fallback {} do buildWhereClause
Se por algum motivo o objectOwner fica vazio (todos os campos undefined), o WHERE clause vira {}. No TypeORM, isso significa "trazer todas as linhas".

Na prática, (A) sempre popula ao menos userId. É um footgun latente. Um bug em (A) que zere o owner faria leak de objetos de todos os usuários.

D objectsService.toJsonArray()

Propósito. Mapper puro. Converte a entidade UserObject (que tem objectId, colunas de owner separadas, etc.) para o DTO FluxObject que o frontend e o nodesBox esperam. Usa id no lugar de objectId e omite colunas de ownership.

🔧 objectId versus id
UserObject.id. PK do banco (UUID gerado pelo TypeORM).
UserObject.objectId. ID lógico usado no frontend. O mesmo objeto pode ter várias linhas por owner, mas o mesmo objectId.

O DTO expõe objectId como id. O frontend nunca vê a PK real do banco.
🔧 Diferença UserObject para FluxObject
Ficam de fora.
userId, companyUserId e spaceId. Colunas de ownership não são expostas.
createdAt e updatedAt. Timestamps do banco.
A PK id. Só a chave lógica objectId vai para o frontend.
E onMutateObjectCallerData (callback)
flux.service.ts:2460-2462
const onMutateObjectCallerData = (data) => { objectCallerData = data; };
Propósito. Closure que permite ao nodesBox mutar a lista de objetos durante a execução do agente. Sem essa referência mutável, mudanças feitas pelo nó não se propagariam para os próximos nós da mesma execução.
Em resumo. Este callback fica entre os nós. Quando um nodesBox altera algum objeto no meio da execução (grava um novo texto, muda a session ativa, adiciona uma linha), o callback recebe a nova versão da lista e reatribui a variável objectCallerData no escopo pai. Assim, o próximo nó que lê a lista já vê o estado atualizado. É uma closure clássica de mutação. Em vez de mutar o array no lugar, substitui a referência inteira pelo novo array que o handler devolveu. Segue o mesmo padrão de onMutateSchema e onUpdateTokens. É o principal ponto de atrito para uma migração ao worker. No worker, os nós não compartilham essa memória. Teriam que fazer round-trip pelo backend a cada mutação.

let objectCallerData = this.objectsService.toJsonArray(...) em (D). Variável let, não const.

O callback recebe novo data e reatribui a variável do escopo pai. Padrão de mutação via closure.

E2 Passado como argumento ao handler de nodesBox
Quando o loop principal (Fase 3) despacha um nó do tipo nodesBox, passa objectCallerData (valor atual) e onMutateObjectCallerData (callback para mutação). O handler chama o callback se o objeto foi alterado, propagando à próxima iteração.

Ver flux.service.ts:3575-3599, 4146-4174 (handler do nodesBox).
🎯 Padrão de closure mutation
É o mesmo padrão usado por onMutateSchema logo abaixo (linha 2465-2467) e por onUpdateTokens em Fase 3. Mantém a fonte da verdade no escopo do apiV2() e permite que serviços filhos atualizem sem passar referência de objeto.
⚠️ Race condition potencial
Se dois nós nodesBox executam em paralelo, a última chamada do callback ganha. Não acontece no loop legacy hoje. Em um refactor de paralelismo, virá à tona.

No worker seria pior. O worker não compartilha essa closure. A mutação seria perdida.
🔧 Reatribuição, não mutação de array
O callback substitui a referência (objectCallerData = data) em vez de mutar o array in-place (objectCallerData.push(...)).

É intencional. O handler do nodesBox retorna um novo array já com as mudanças aplicadas.
Resumo. O que sai de 1.5:
objectOwner. ObjectOwner (space, companyUser ou user, mutuamente exclusivos).
objectCallerData. FluxObject[]. Lista dos objetos daquele owner, no formato flat esperado pelo frontend.
onMutateObjectCallerData. Callback que o loop passa ao handler do nodesBox para reescrever a lista durante a execução.
Nenhum I/O pesado. 1 (raras vezes 2) SELECTs, sem paginação, sem cache.
Observações para migração:
A cascata de resolução do ObjectOwner (A) é business logic pura. Replicável em qualquer lugar. Precisa do flow.folder.spaces.id e do user.selectedCompanyId como input.
O footgun do buildWhereClause retornando {} quando o owner é vazio é um alerta para qualquer implementação nova. Sempre garantir pelo menos userId antes de chamar.
Se o worker precisar dos objetos, deve receber o array já preparado no start do workflow ou fazer a query lá. Nesse caso, perde o padrão de closure mutation. O worker não pode alterar o array in-memory do backend depois.
onMutateObjectCallerData é a maior dificuldade para a migração. O nodesBox mutando objectCallerData durante a execução é state compartilhado entre nós. No worker, cada nó executa isolado. Qualquer mutação teria que ir via chamada de API ao backend. Custa round-trip por nó de nodesBox.
Sem esforço de refactor, 1.5 pode continuar no backend mesmo depois da migração. É rápido e o resultado é passado nos start-args do workflow.

Passo 3.1 — nextReady(schedState)

Bloco em flux.service.ts:3227 (condição do while) e scheduler.ts:295-308 (função). O scheduler devolve o próximo nó pronto para executar. O critério é in-degree zero nas arestas ativas, respeitando branches mortos por completeCondition.
Em resumo — o que esse passo faz
  • Chama o próximo da fila. O loop principal pergunta nextReady(state) e recebe o id do próximo nó pronto. Usa shift() FIFO na fila ready, sem prioridade nem justiça.
  • Descarta ids repetidos ou mortos. Antes de entregar um id, confere 3 listas: dead (branch podado), completed (já rodou) e scheduled (deduplicação de duplicatas na fila). Ignora silenciosamente qualquer id que caia numa delas.
  • Painel de controle é o SchedulerState. Struct in-memory com Sets e Maps que guarda todo o DAG da execução. Inclui nós, dependências, contadores de predecessores (normais e gating) e arestas condicionais. É portável em TypeScript puro. É frágil: se o backend cai, some inteiro.
  • Feedback loop via markCompleted e completeCondition. Quando um nó termina, o "secretário" resolve dependências dos vizinhos. Empurra para ready quem ficou com 0 pendências. Para bifurcações, o "juiz" mata os handles não-tomados. Inclui o sentinel DEAD_HANDLE em caso de erro fatal.
  • Saída. scheduledId é o próximo nodeId para a Fase 3 processar. Recebe null quando a fila esvaziou e o loop passa para a Fase 4. Zero I/O, 100% in-memory.
Contexto. Esta é a condição de parada do loop principal da Fase 3. Enquanto nextReady retornar um id, o backend processa mais um nó. Quando devolve null, o loop termina e passa para a Fase 4 (finalização). Toda a lógica de DAG scheduling vive no SchedulerState mutável, construído no passo 2.1. Isso inclui resolver dependências, marcar branches mortos e propagar condições.
Cadeia de chamadas em 3.1
AnextReady(state) → BSchedulerState (contrato) → CmarkCompleted (feedback loop) → DcompleteCondition (branches mortos)
Resultado. A variável local scheduledId recebe o próximo nodeId ou null. O nó é marcado como scheduled no state (deduplicação) antes de sair da função.
A nextReady(state)
scheduler.ts:295-308
export function nextReady(state: SchedulerState): string | null
Propósito. Chama shift() na fila FIFO state.ready até achar o primeiro nó que não está em dead, completed ou scheduled. Retorna esse id e o marca como scheduled para não voltar. Retorna null se a fila esvaziou.
Em resumo. Pense como um guichê de senha de banco. Existe uma fila de gente pronta para ser atendida (ready). O guichê chama o próximo da fila. Antes de mandar para a frente, confere 3 listas. Já foi atendido hoje (completed)? Foi cancelado (dead)? Já foi chamado por outro guichê (scheduled)? Se cair em qualquer uma dessas listas, descarta a senha e chama a próxima. Sem reclamar, sem log. Se a fila esvaziou, retorna null. O "banco fechou" e o loop principal encerra. É FIFO puro, sem prioridade nem justiça. A ordem de chegada é a ordem de execução. E o guichê nunca chama o mesmo nome duas vezes. Ao devolver um id, adiciona no set scheduled. Assim, se o mesmo id aparecer duplicado na fila (dois predecessores resolvem em cascata), o segundo shift pula silenciosamente.
export function nextReady(state: SchedulerState): string | null { while (state.ready.length > 0) { const id = state.ready.shift()!; // FIFO if (state.dead.has(id)) continue; if (state.completed.has(id)) continue; if (state.scheduled.has(id)) continue; state.scheduled.add(id); // deduplicação return id; } return null; }
↓
🪜 Cascata por candidato saído da fila
1 está em dead? pula (branch podado)
2 está em completed? pula (nó já rodou)
3 está em scheduled? pula (deduplicação)
4 nenhum dos acima adiciona em scheduled e retorna id
5 fila esvaziou retorna null (fim do loop)
🎯 Por que shift() e não priority queue?
É FIFO puro. A ordem que os nós entraram em ready é a ordem que executam. O buildSchedulerState inicializa a fila com os nós de in-degree zero. Cada markCompleted pode empurrar novos quando o último predecessor resolve. O efeito prático é uma BFS topológica. O scheduler não promete essa ordem.
📎 A fila pode ter entradas duplicadas
Um mesmo nó pode receber push duas vezes. Isso ocorre quando dois predecessores resolvem em sequência próxima antes do primeiro nextReady retirá-lo. O set scheduled descarta as duplicatas no segundo shift.
⚠️ Sem priority, sem fairness
Não há garantia de quando um nó específico vai rodar em relação a outros também prontos. Para qualquer refactor que precise controlar ordem (SLA, timeout por nó, retry policy), a estrutura atual não expõe hooks. Exige alterar o SchedulerState.
🔧 O que o loop faz depois do return
Recebe o id em scheduledId e entra no corpo do while em flux.service.ts:3229. Isso dispara a checagem de cancelamento (3229-3239), a busca de node em myUpdatedNodes (3241) e a cadeia dos passos 3.2 até 3.11.
B SchedulerState (contrato)
scheduler.ts:96-111
interface SchedulerState { nodeIds; forwardDeps; ready; completed; dead; scheduled; totalPreds; resolvedPreds; deadPreds; gatingPairs; totalGatingPreds; resolvedGatingPreds; deadGatingPreds; conditionEdges; }
Propósito. Estado mutável in-memory do DAG scheduler. Todo o loop da Fase 3 opera sobre esse struct. nextReady lê 3 sets. markCompleted resolve predecessores dos vizinhos. completeCondition mata branches não-tomadas.
Em resumo. É o painel de controle do agente. Imagine uma sala com um quadro branco enorme onde tudo da execução está desenhado. Quais nós existem, quem depende de quem, quantos predecessores cada um ainda espera, quem já rodou, quem morreu em branch podado, quem está na fila. Nada disso vive no banco durante a execução. É tudo Sets e Maps no heap do backend. É o "cérebro" que fica aberto enquanto o agente executa. Todas as funções (nextReady, markCompleted, completeCondition, resolvePred) apenas leem e escrevem nesse quadro. Por causa disso, o scheduler é portável (TypeScript puro, sem Nest, DB ou Redis). Também é frágil. Se o processo do backend cai no meio, o quadro some inteiro. Não há checkpoint nem crash recovery. É esse trade-off que a migração para o Temporal resolve. Move o "quadro" para o próprio WorkflowHistory do Temporal, que persiste tudo automaticamente.

🎯 Por que 3 sets separados?
completed: terminou com sucesso ou erro tratado.
dead: nunca vai rodar (branch podado).
scheduled: já entregue por nextReady, aguardando o markCompleted.

Um nó nunca está em mais de um set ao mesmo tempo. Isso permite o continue em cascata em O(1).
📎 dead ≠ completed
Em Fase 4, o warning "nós não-processados" (4.1) compara todos os nodeIds com a união completed ∪ dead. Se sobrar alguém, houve bug de scheduling.
🔧 gatingPairs
Set<string> com strings "src→dst" representando arestas control ou condition. Detecta quando todos os caminhos gating para um nó morreram. Nesse caso o nó vai para o set dead, não para ready, mesmo com resolvedPreds === totalPreds.
C markCompleted(state, id)
scheduler.ts:352-357
export function markCompleted(state: SchedulerState, id: string): void
Propósito. Fecha o loop de nextReady. Depois que um nó terminou, esta função marca o nó como completed e itera os forwardDeps (quem dependia dele) chamando resolvePred. Cada vizinho tem seu resolvedPreds incrementado. Se bate com totalPreds, entra em ready.
Em resumo. É o secretário do guichê. Quando alguém termina o atendimento e sai, ele passa em cada mesa que dependia dessa pessoa e coloca um "check" no formulário. Exemplo. O nó B esperava entrada do A. Quando A termina, o secretário vai na "ficha" do B e escreve "ok, A já resolveu, falta só o C". Se essa foi a última pendência do B (todos os predecessores resolveram), o secretário empurra B para a fila do guichê (ready). É a única forma de nós novos entrarem em ready depois da inicialização. Um "check" pode ser dead ou vivo. Se A morreu numa branch podada, o secretário ainda "resolve" a dependência do B, mas marca essa resolução como fantasma. Se todos os predecessores gating do B forem fantasmas, B também vira dead e nunca vai para ready. É idempotente. Se por bug o mesmo id chegar duas vezes, o secretário identifica pelo state.completed.has(id) e ignora. Nada de dupla contagem.
export function markCompleted(state: SchedulerState, id: string): void { if (state.completed.has(id)) return; // idempotente state.completed.add(id); for (const next of state.forwardDeps.get(id) ?? []) resolvePred(state, id, next, false); // predWasDead=false }
↓
↳ resolvePred(state, source, target, predWasDead) — scheduler.ts:310-350
Incrementa resolvedPreds[target]. Se predWasDead=true, também incrementa deadPreds[target].
Regras:
• Se todos os gating predecessors do target morreram → state.dead.add(target).
• Se resolvedPreds[target] === totalPreds[target] e não é dead → state.ready.push(target).
• Se target já é dead ou completed → no-op (idempotente).
scheduler.ts:310-350
🎯 Quem chama markCompleted?
É o passo 3.11 do diagrama. Depois de um nó rodar (via Temporal ou inline), o loop chama:
• markCompleted(schedState, id) para nós normais
• completeCondition(schedState, id, handle) para nós de decisão (pode setar branches como dead)
📎 Idempotência
O early-return em state.completed.has(id) permite chamar markCompleted várias vezes com o mesmo id sem quebrar contadores. É uma proteção. Em condições especiais (arrayNode iterando o body, retries) pode chegar duas vezes no mesmo id.
🔧 Predecessores dead são "resolvidos"
resolvePred incrementa resolvedPreds independente de predWasDead. A ideia é simples. Um branch morto ainda "resolve" a dependência. Não empurra dado, mas também não está pendente. Se sobrar dado suficiente por outras arestas, o nó ainda pode rodar.
D completeCondition(state, id, takenHandle)
scheduler.ts:366-389
export function completeCondition(state: SchedulerState, conditionId: string, takenHandle: string | null): void
Propósito. Versão especializada de markCompleted para nós de decisão (conditionNode etc.). Marca o nó como completed e propaga "dead" para todas as arestas condition saindo desse nó por handles não-tomadas. As arestas do handle tomado propagam normalmente.
Em resumo. É o juiz de uma bifurcação. Quando um conditionNode avalia "se x > 10 vai por A, senão vai por B", o juiz precisa fechar oficialmente a rota que não foi escolhida. Sem isso, nós desse lado ficariam eternamente esperando entrada que nunca chega. Ele recebe o takenHandle (ex.: 'outputHandle-0') e percorre todas as arestas condition saindo do nó. Para as arestas que combinam com o handle tomado, faz a "resolução viva" (nó destino recebe entrada normal). Para as outras, marca como predWasDead=true. O secretário do próximo nó registra "essa dependência morreu, não vai vir dado". Se todos os caminhos gating de um nó a jusante morrerem, esse nó também vira dead. Cascata de morte propagando para baixo. Existe também um sentinela especial chamado DEAD_HANDLE. Quando um nó de decisão falha antes de decidir (bug, timeout, throw), o loop chama completeCondition(id, DEAD_HANDLE). Todos os handles são considerados não-tomados. Isso mata o subgrafo inteiro e evita que sucessores rodem com dados undefined. Único perigo. O nome do handle é literal string. Um typo ('outputHandle-0' versus 'outputHandel-0') faz o juiz matar a rota errada silenciosamente.

🎯 Onde DEAD_HANDLE aparece
Sentinel usado pelo passo 3.8 (tratamento de erro por nó). Se um nó falhar antes de decidir uma branch, o loop chama completeCondition(schedState, id, DEAD_HANDLE) para matar todos os caminhos possíveis. Isso evita que sucessores rodem com entrada undefined.
📎 Diferença de markCompleted
markCompleted é agnóstico. Assume que todas as arestas saindo do nó eram "vivas". completeCondition precisa distinguir handle tomado versus não-tomado. Por isso lê conditionEdges (populado em buildSchedulerState).
⚠️ Handle name matters
O takenHandle vem literal do return do handler do condition ('outputHandle-0', 'outputHandle-1', 'conditionHandle-T0', etc.). Qualquer typo no handler faz o scheduler comparar contra a string errada e matar branches viáveis. Não há validação. Footgun clássico.
🔧 Onde isso é usado no loop
Chamado em flux.service.ts:3566-3571 (handler do conditionNode), 4013 (handler do arrayNode para encerrar iteração) e 4004-4006 (após erro fatal). É o passo 3.11 do diagrama para tipos que decidem branches.
Resumo — o que sai de 3.1:
• scheduledId: string | null. Id do próximo nó pronto ou null.
• Efeito colateral. Se retornou id, o state teve scheduled.add(id).
• Se retornou null, o loop da Fase 3 termina e o backend cai na Fase 4 (finalização).
• Nenhum I/O. 100% in-memory (Sets e Maps).
Observações para migração:
• O scheduler é puro TypeScript sem dependência de Nest, DB ou Redis. É portável para o worker sem refactor pesado.
• É stateful in-memory. Todo o SchedulerState vive no heap do backend enquanto o agente executa. Para rodar isso no worker (Temporal workflow), o state teria que ser serializável ou reconstituído a cada activity call.
• A deduplicação via scheduled depende de execução single-threaded. Se o worker executar irmãos em paralelo, dois nextReady concorrentes podem devolver ids diferentes. Dois markCompleted concorrentes atualizando o mesmo resolvedPreds exigem lock.
• completeCondition mais DEAD_HANDLE é o mecanismo central de branching. Qualquer reimplementação precisa preservar a semântica. Especial atenção para conditionNode, arrayNode (iteração), fail-fast em erros e o warning da Fase 4.1.
• É essencial. O loop inteiro colapsa sem ele. Deve entrar cedo no plano de migração, com o scheduler como uma das primeiras responsabilidades do worker (ou de um serviço dedicado consumido tanto por backend quanto worker).

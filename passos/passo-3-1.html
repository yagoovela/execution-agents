Step 3.1 — nextReady(schedState)

Block in flux.service.ts:3227 (the while condition) and scheduler.ts:295-308 (the function). The scheduler returns the next node ready to execute. The criterion is in-degree zero over active edges, respecting branches killed by completeCondition.
In summary — what this step does
  • Calls the next in the queue. The main loop asks nextReady(state) and gets back the id of the next ready node. Uses FIFO shift() on the ready queue, no priority, no fairness.
  • Discards repeated or dead ids. Before returning an id, checks 3 lists: dead (pruned branch), completed (already ran), and scheduled (dedupe against queue duplicates). Silently ignores any id that falls in one of them.
  • Control panel is the SchedulerState. An in-memory struct with Sets and Maps that holds the whole execution DAG. Includes nodes, dependencies, predecessor counters (normal and gating) and conditional edges. It's portable (pure TypeScript). It's fragile: if the backend crashes, it disappears entirely.
  • Feedback loop via markCompleted and completeCondition. When a node finishes, the "secretary" resolves the neighbors' dependencies. Pushes to ready anyone left with 0 pending. For branching, the "judge" kills the untaken handles. Includes the DEAD_HANDLE sentinel in case of fatal error.
  • Output. scheduledId is the next nodeId for Phase 3 to process. Gets null when the queue empties and the loop moves to Phase 4. Zero I/O, 100% in-memory.
Context. This is the stop condition of Phase 3's main loop. As long as nextReady returns an id, the backend processes one more node. When it returns null, the loop ends and moves to Phase 4 (finalization). All DAG scheduling logic lives in the mutable SchedulerState, built in step 2.1. That includes resolving dependencies, marking dead branches and propagating conditions.

A nextReady(state)
scheduler.ts:295-308
export function nextReady(state: SchedulerState): string | null
Purpose. Calls shift() on the FIFO queue state.ready until it finds the first node that is not in dead, completed or scheduled. Returns that id and marks it as scheduled so it doesn't come back. Returns null if the queue is empty.
In summary. Think of it as a bank ticket counter. There's a queue of people ready to be served (ready). The counter calls the next in line. Before sending them forward, it checks 3 lists. Already served today (completed)? Cancelled (dead)? Already called by another counter (scheduled)? If they fall into any of those, discards the ticket and calls the next one. No complaints, no log. If the queue is empty, returns null. The "bank closed" and the main loop ends. It's pure FIFO, no priority, no fairness. Arrival order is execution order. And the counter never calls the same name twice. When returning an id, it adds it to the scheduled set. So, if the same id appears duplicated in the queue (two predecessors resolve in cascade), the second shift skips it silently.
export function nextReady(state: SchedulerState): string | null { while (state.ready.length > 0) { const id = state.ready.shift()!; // FIFO if (state.dead.has(id)) continue; if (state.completed.has(id)) continue; if (state.scheduled.has(id)) continue; state.scheduled.add(id); // deduplicação return id; } return null; }
↓
🪜 Cascade per candidate popped from the queue
1 in dead? skip (pruned branch)
2 in completed? skip (node already ran)
3 in scheduled? skip (dedupe)
4 none of the above add to scheduled and return id
5 queue empty return null (loop ends)
🎯 Why shift() and not a priority queue?
It's pure FIFO. The order nodes entered ready is the order they execute. buildSchedulerState initializes the queue with in-degree-zero nodes. Each markCompleted can push new ones when the last predecessor resolves. The practical effect is a topological BFS. The scheduler does not promise that order.
📎 The queue can hold duplicate entries
The same node can be pushed twice. This happens when two predecessors resolve close in sequence before the first nextReady pops it. The scheduled set discards the duplicates on the second shift.
⚠️ No priority, no fairness
There is no guarantee about when a specific node will run relative to others that are also ready. Any refactor that needs to control order (SLA, per-node timeout, retry policy) will find that the current structure exposes no hooks. It requires changing the SchedulerState.
🔧 What the loop does after the return
Receives the id in scheduledId and enters the while body at flux.service.ts:3229. That triggers the cancellation check (3229-3239), the node lookup in myUpdatedNodes (3241) and the chain of steps 3.2 through 3.11.
B SchedulerState (contract)
scheduler.ts:96-111
interface SchedulerState { nodeIds; forwardDeps; ready; completed; dead; scheduled; totalPreds; resolvedPreds; deadPreds; gatingPairs; totalGatingPreds; resolvedGatingPreds; deadGatingPreds; conditionEdges; }
Purpose. Mutable in-memory state of the DAG scheduler. The entire Phase 3 loop operates on this struct. nextReady reads 3 sets. markCompleted resolves the neighbors' predecessors. completeCondition kills untaken branches.
In summary. This is the agent's control panel. Picture a room with a huge whiteboard on which the whole execution is drawn. What nodes exist, who depends on whom, how many predecessors each one still waits for, who already ran, who died on a pruned branch, who's in the queue. None of this lives in the database during execution. It's all Sets and Maps on the backend heap. It's the "brain" that stays open while the agent runs. Every function (nextReady, markCompleted, completeCondition, resolvePred) only reads and writes on that board. Because of this, the scheduler is portable (pure TypeScript, no Nest, DB or Redis). It's also fragile. If the backend process crashes mid-flight, the whole board disappears. There is no checkpoint or crash recovery. That's the trade-off the Temporal migration solves. It moves the "board" into Temporal's own WorkflowHistory, which persists everything automatically.

🎯 Why 3 separate sets?
completed: finished successfully or with a handled error.
dead: will never run (pruned branch).
scheduled: already handed out by nextReady, waiting for markCompleted.

A node is never in more than one set at a time. This makes the cascade of continue checks O(1).
📎 dead ≠ completed
In Phase 4, the "unprocessed nodes" warning (4.1) compares every nodeIds with the union completed ∪ dead. If anyone's left over, there was a scheduling bug.
🔧 gatingPairs
Set<string> of strings "src→dst" representing control or condition edges. Detects when every gating path into a node has died. In that case the node goes to the dead set, not to ready, even with resolvedPreds === totalPreds.
C markCompleted(state, id)
scheduler.ts:352-357
export function markCompleted(state: SchedulerState, id: string): void
Purpose. Closes the nextReady loop. After a node finishes, this function marks it as completed and iterates over forwardDeps (whoever depended on it) calling resolvePred. Each neighbor has its resolvedPreds incremented. If it matches totalPreds, it enters ready.
In summary. This is the counter's secretary. When someone finishes being served and leaves, they walk past every desk that depended on that person and put a "check" on the form. Example. Node B was waiting on input from A. When A finishes, the secretary goes to B's "file" and writes "ok, A resolved, only C left". If that was B's last pending item (all predecessors resolved), the secretary pushes B onto the counter queue (ready). That is the only way new nodes enter ready after initialization. A "check" can be dead or live. If A died on a pruned branch, the secretary still "resolves" B's dependency, but marks that resolution as a ghost. If all of B's gating predecessors are ghosts, B also becomes dead and never goes to ready. It's idempotent. If, due to a bug, the same id shows up twice, the secretary spots it through state.completed.has(id) and ignores it. No double counting.
export function markCompleted(state: SchedulerState, id: string): void { if (state.completed.has(id)) return; // idempotente state.completed.add(id); for (const next of state.forwardDeps.get(id) ?? []) resolvePred(state, id, next, false); // predWasDead=false }

↳ resolvePred(state, source, target, predWasDead) — scheduler.ts:310-350
Increments resolvedPreds[target]. If predWasDead=true, also increments deadPreds[target].
Rules:
• If all of target's gating predecessors died → state.dead.add(target).
• If resolvedPreds[target] === totalPreds[target] and it's not dead → state.ready.push(target).
• If target is already dead or completed → no-op (idempotent).
scheduler.ts:310-350
🎯 Who calls markCompleted?
It's step 3.11 in the diagram. After a node runs (via Temporal or inline), the loop calls:
• markCompleted(schedState, id) for normal nodes
• completeCondition(schedState, id, handle) for decision nodes (can set branches as dead)
📎 Idempotency
The early-return on state.completed.has(id) lets you call markCompleted several times with the same id without breaking counters. It's a safeguard. In special conditions (arrayNode iterating its body, retries) the same id can arrive twice.
🔧 Dead predecessors are "resolved"
resolvePred increments resolvedPreds regardless of predWasDead. The idea is simple. A dead branch still "resolves" the dependency. It doesn't push data, but it isn't pending either. If enough data comes through other edges, the node can still run.
D completeCondition(state, id, takenHandle)
scheduler.ts:366-389
export function completeCondition(state: SchedulerState, conditionId: string, takenHandle: string | null): void
Purpose. Specialized version of markCompleted for decision nodes (conditionNode etc.). Marks the node as completed and propagates "dead" to every condition edge leaving the node through untaken handles. The edges of the taken handle propagate normally.
In summary. This is the judge of a fork. When a conditionNode evaluates "if x > 10 go A, else go B", the judge has to officially close the route that was not picked. Without that, nodes on that side would wait forever for input that never arrives. It receives the takenHandle (e.g. 'outputHandle-0') and walks every condition edge leaving the node. For edges matching the taken handle, it does a "live resolve" (target node receives normal input). For the others, it marks predWasDead=true. The next node's secretary records "that dependency died, no data coming". If every gating path into a downstream node dies, that node also becomes dead. Cascading death propagating downward. There is also a special sentinel called DEAD_HANDLE. When a decision node fails before deciding (bug, timeout, throw), the loop calls completeCondition(id, DEAD_HANDLE). All handles are treated as untaken. That kills the whole subgraph and prevents successors from running with undefined data. Only danger. The handle name is a literal string. A typo ('outputHandle-0' vs 'outputHandel-0') makes the judge silently kill the wrong route.

🎯 Where DEAD_HANDLE appears
Sentinel used by step 3.8 (per-node error handling). If a node fails before deciding a branch, the loop calls completeCondition(schedState, id, DEAD_HANDLE) to kill every possible path. That prevents successors from running with undefined input.
📎 Difference from markCompleted
markCompleted is agnostic. It assumes every edge leaving the node was "live". completeCondition has to distinguish taken vs untaken handle. That's why it reads conditionEdges (populated in buildSchedulerState).
⚠️ Handle name matters
The takenHandle comes literal from the condition handler's return ('outputHandle-0', 'outputHandle-1', 'conditionHandle-T0', etc.). Any typo in the handler makes the scheduler compare against the wrong string and kill viable branches. There is no validation. Classic footgun.

• If it returned null, the Phase 3 loop ends and the backend falls into Phase 4 (finalization).
• No I/O. 100% in-memory (Sets and Maps).
Migration notes:
• The scheduler is pure TypeScript with no dependency on Nest, DB or Redis. It is portable to the worker without heavy refactor.
• It is stateful in-memory. The whole SchedulerState lives on the backend heap while the agent runs. To run this in the worker (Temporal workflow), the state would have to be serializable or reconstituted on each activity call.
• The dedupe via scheduled relies on single-threaded execution. If the worker runs siblings in parallel, two concurrent nextReady may return different ids. Two concurrent markCompleted updating the same resolvedPreds require a lock.
• completeCondition plus DEAD_HANDLE is the central branching mechanism. Any reimplementation must preserve the semantics. Pay special attention to conditionNode, arrayNode (iteration), fail-fast on errors and the Phase 4.1 warning.
• It is essential. The whole loop collapses without it. Should enter the migration plan early, with the scheduler being one of the first responsibilities of the worker (or of a dedicated service consumed by both backend and worker).

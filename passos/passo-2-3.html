Passo 2.3 — generateSchemaFromNodes (schema de substituição)

Bloco em node-reference-substitution.service.ts:82-143. Constrói o mapa de substituição in-memory que resolve placeholders {{...}} em tempo de execução. Cada nó vira até três chaves no mapa. UUID puro. UUID normalizado (pontos viram underscores). Label lowercase. Todas apontam para a mesma entry, compartilhada por referência.
Em resumo — o que esse passo faz
  • Monta a agenda de referências do agente. Constrói um único mapa in-memory que responde a "quando o prompt escreve {{persona}}, o que significa?". Sem esse mapa, nenhum placeholder resolve.
  • Filtra por whitelist hand-maintained. Só publica campos listados em basedOnType. Um tipo de nó novo com campo referenciável precisa ser adicionado manualmente à lista. Sem isso, o placeholder falha silenciosamente.
  • Normaliza tudo para string. Se o campo é objeto, tenta value.text ?? value.content ?? value.result em ordem. Cai em JSON.stringify como fallback. É onde a RAM cresce se um result é grande (2MB fica inteiro no schema).
  • Indexa cada nó sob 3 chaves apontando para a mesma entry. UUID puro, UUID com . trocado por _, e label lowercase sem espaço. O usuário pode escrever {{Persona Model}}, {{a1b2_c3d4}} ou o UUID cru. Todos resolvem para o mesmo valor. Colisão de label sobrescreve silenciosamente.
  • Roda uma vez no início da execução. Depois disso o schema é mutado in-place por updateSchemaWithNodeOutput a cada nó completado. Nunca regenerado. A memória [[project_substitution_engine]] avisa que existem 57 sync sites tocando esse schema no FluxService.
  • Saída. nodeSubstitutionSchema: { [key]: { [field]: string } }. Pronto para ser consumido por applySubstitutionToObject em cada iteração do loop. Zero I/O. Puro CPU. Complexidade O(N × F).
Contexto. Este é o motor de referência. Permite que um nó escreva {{model_1}} ou {{Persona Model}} no prompt e receba o output do nó upstream substituído. A memória [[project_substitution_engine]] avisa que o engine tem 57 sync sites em FluxService lendo e mutando o schema. Não é regex simples. Envolve resolução de field-paths e aliases humanos.

Propósito. Define quais campos de node.data valem a pena publicar no schema, por tipo de nó. Nó não listado é ignorado. Campo não listado (mesmo existindo em data) não vira substituível.
Em resumo. Esta whitelist é o cadastro do sistema de referência. É uma lista escrita à mão indicando "para cada tipo de nó, estes são os campos que podem ser referenciados via {{placeholder}}". Se o campo não está listado, existe em memória mas ninguém consegue referenciar. Por isso, criar um novo tipo de nó e esquecer de atualizar esta lista gera bug silencioso. O placeholder não resolve. C Extração de value (flatten de object)
node-reference-substitution.service.ts:105-127
for (const field of relevantFields) { let value = node.data[field]; if (object) value = value.text ?? value.content ?? value.result ?? JSON.stringify(value); entry[field] = value; }
Propósito. Normaliza o valor para que seja sempre string. Se node.data[field] é objeto (comum em outputs), tenta extrair text, content ou result. Se nada bate, cai em JSON.stringify. Se é undefined, não cria a chave.
Em resumo. Esta parte é o tradutor. Garante que tudo que vai para o schema saia como texto, porque no fim o {{placeholder}} é injetado dentro de um prompt de LLM, e prompt é string. Se o campo já é primitivo (string, number, boolean), passa direto. Se é objeto, tenta em ordem. Primeiro text, depois content, depois result. Se nenhum bate, serializa o objeto inteiro como JSON. Se o campo é undefined, não cria a entrada. A precedência text > content > result é silenciosa e frágil. Se um handler grava os dois, text ganha. Mudar essa precedência em refactor pode quebrar coisas sem aviso. Também é aqui que a memória cresce. Um único result de 2MB fica inteiro no schema e é replicado em cada substituição.
🪜 Cascata de coerção
1 node.data[field] === undefined skip (não adiciona)
2 value é primitivo grava direto
3a objeto com value.text entry[field] = value.text
3b senão, com value.content entry[field] = value.content
3c senão, com value.result entry[field] = value.result
3d fallback JSON.stringify(value)
↓
Resultado. entry[field]: string | number | boolean
Nunca objeto. Sempre coerced. Permite que String.replace funcione direto no applySubstitutionToObject.
⚠️ Precedência text > content > result
Se o objeto tem text e content setados (raro mas acontece), text ganha. Se um handler grava {text: 'x', content: {...json_grande...}}, o placeholder {{node}} resolve para 'x', não para o JSON.

Se essa precedência mudar em um refactor, quebra silenciosamente handlers que dependem dela.
🎯 JSON.stringify fallback
Quando o objeto não tem nenhum dos 3 campos padrão, vira JSON serializado. Exemplo. modelSettings em commandTextNode. O prompt final tem uma string JSON literal. Não é elegante, mas funciona para o LLM ler.
🔧 Grande contribuidor de RAM
content e result podem ser payloads grandes (respostas de LLM, resultados SQL). Se um único nó tem result de 2MB, o schema carrega esses 2MB e todo {{node}} substituído replica isso na string final. Ver [[project_jsonb_fat_fields]] para o pattern relacionado.
D 3-key indexing (stable/ref/label)
node-reference-substitution.service.ts:129-140
schema[stableKey] = entry; schema[refKey] = entry; schema[labelKey] = entry; // 3 keys, MESMA referência
Propósito. Aceita três formatos diferentes de placeholder para o mesmo nó. UUID puro, UUID normalizado e label humano. Todos apontam para a mesma referência. Atualização em uma delas reflete nas outras.
Em resumo. Esta etapa é o cartório que registra o mesmo nó sob três nomes diferentes, todos apontando para o mesmo endereço. O nó vai para o arquivo. Primeiro. Sob o UUID puro (a1b2-...). Segundo. Sob o UUID com pontos trocados por underscore (o ponto em placeholder é usado como field access {{x.y}}). Terceiro. Sob o label humano lowercase sem espaço (personamodel). Os três slots guardam a mesma referência ao objeto entry. Quando o output é atualizado depois, uma única mutação reflete nas três chaves automaticamente. Permite ao usuário escrever {{Persona Model}}, {{a1b2_c3d4_...}} ou o UUID cru no template. Todos resolvem para o mesmo valor. Cuidado. Se dois nós têm o mesmo label, o segundo sobrescreve o primeiro no slot do label. O {{persona}} vira ambíguo silenciosamente.
schema[stableKey] = entry; // UUID puro: schema['a1b2-...'] const refKey = stableKey.replace(/\./g, '_'); if (refKey !== stableKey) { schema[refKey] = entry; // UUID normalizado: schema['a1b2___'] } if (labelKey && labelKey !== stableKey && labelKey !== refKey) { schema[labelKey] = entry; // label lowercase: schema['personamodel'] }
↓
D1 stableKey = node.id
UUID puro do nó. Sempre presente (skip acima se ausente).
↓
D2 refKey = id.replace(/\./g, '_')
Normaliza pontos (não permitidos em placeholder path {{x.y}}. Colidiria com field access). Só entra no schema se difere do stableKey.
↓
D3 labelKey (opcional)
Só se o label do nó existe e não colide com as outras duas chaves. Permite ao usuário escrever {{Persona Model}} no prompt. O replacer busca schema.personamodel após normalizar.
⚠️ Colisão de labels
Dois nós com o mesmo label. O último ganha no schema. {{persona}} vira ambíguo. O front deveria proibir labels duplicados. Sem essa proteção, um é ignorado silenciosamente.
🎯 Compartilhamento de referência
As três chaves apontam para o mesmo objeto entry. É intencional. O updateSchemaWithNodeOutput só precisa mutar via uma chave. As outras duas refletem automaticamente.
🔧 Placeholder syntax suportada
{{<key>.<field>}} ou {{<key>}} (só a chave, resolve para o fallback do primeiro campo). O replacePlaceholders (linhas 5-22) faz split por . e navega o objeto.
E Ciclo de vida do schema no run
flux.service.ts:3149, 3281, 3389+ · node-reference-substitution.service.ts:145-216
// 1x generate (aqui) → N× applySubstitutionToObject + updateSchemaWithNodeOutput (loop) → onMutateSchema (callback pra reatribuição)
Propósito. Mostra como o schema criado aqui é consumido e mutado ao longo da execução. Não é regenerado. É atualizado ao vivo. Cada nó completado enriquece o schema com seu output.
Em resumo. Se as etapas anteriores construíram a agenda de referências, esta é o carteiro que leva e traz essa agenda durante toda a execução. O ciclo por nó vira. Primeiro. Antes do handler rodar, chama applySubstitutionToObject, que substitui todos os {{...}} pelos valores do schema. Segundo. O handler executa em cima do nó já preenchido e produz um output. Terceiro. Esse output é gravado de volta no schema via updateSchemaWithNodeOutput para ficar disponível para os nós seguintes. Quarto. Como o schema é reatribuído (novo objeto raiz via spread), o callback onMutateSchema sinaliza "use esta nova referência agora". A memória [[project_substitution_engine]] alerta que existem 57 lugares no FluxService tocando esse ciclo. Qualquer refactor do engine precisa mexer em todos ao mesmo tempo. Não dá para fazer troca cirúrgica.

⚠️ 57 sync sites (ver memória)

🎯 Por que spread em updateSchemaWithNodeOutput?
const updatedSchema = { ...schema } cria novo objeto raiz, mas as entries permanecem compartilhadas. Mutação pontual não invalida referências antigas. Reatribuição invalida. Por isso existe o callback onMutateSchema.

Método na linha 241-267 do service que faz o mesmo ciclo (generate → apply → execute → update). Não é usado pela Fase 3 (que faz manualmente), mas está exportado. Possível dead code ou usado por endpoint alternativo.
Resumo — o que sai de 2.3.
• nodeSubstitutionSchema: { [key]: { [field]: string } }. Mapa in-memory pronto para applySubstitutionToObject.
• De 1 a 3 chaves por nó (UUID puro, UUID normalizado, label lowercase).
• Valores coerced para string (via text ?? content ?? result ?? JSON.stringify).
• Zero I/O. Puro CPU. Complexidade O(N × F), com F em torno de 4 campos por tipo.
Observações para migração.
• Ver memória [[project_substitution_engine]]. 57 sync sites em FluxService. Refactor exige tocar em todos simultaneamente.
• O worker não tem esse engine. Recebe cada nó já pré-substituído. Aplica applySubstitutionToObject antes do handoff. Migração para o worker preserva essa boundary.
• A basedOnType é hand-maintained (igual ao MCP schema catalog). Ao adicionar novo tipo de nó com campo referenciável, tem que atualizar. Sem CI check. Bug silencioso.
• O flattening de result, content e text carrega payloads grandes para a memória. Não é seguro apenas preview-truncar (ver [[project_node_field_taxonomy]]). O placeholder pode precisar do valor completo.
• Alternativa de longo prazo. Index-only schema. O schema guarda só {nodeId, field}. O resolver busca o valor real sob demanda. Elimina duplicação em memória. Complica cache.
• O processFlowWithSubstitution (linhas 241-267) parece dead code. Validar antes de qualquer limpeza.

Step 2.3 — generateSchemaFromNodes (substitution schema)

Block at node-reference-substitution.service.ts:82-143. Builds the in-memory substitution map that resolves {{...}} placeholders at execution time. Each node becomes up to three keys in the map. Raw UUID. Normalized UUID (dots become underscores). Lowercase label. All point to the same entry, shared by reference.
In summary — what this step does
  • Builds the agent's reference directory. Builds a single in-memory map that answers "when the prompt writes {{persona}}, what does it mean?". Without this map, no placeholder resolves.
  • Filters by hand-maintained whitelist. Only publishes fields listed in basedOnType. A new node type with a referenceable field must be added manually to the list. Without that, the placeholder fails silently.
  • Normalizes everything to string. If the field is an object, tries value.text ?? value.content ?? value.result in order. Falls back to JSON.stringify. This is where RAM grows if a result is big (2MB lands whole in the schema).
  • Indexes each node under 3 keys pointing to the same entry. Raw UUID, UUID with . swapped by _, and lowercase label with no spaces. The user can write {{Persona Model}}, {{a1b2_c3d4}} or the raw UUID. All resolve to the same value. Label collision silently overwrites.
  • Runs once at the start of the execution. After that the schema is mutated in-place by updateSchemaWithNodeOutput on every completed node. Never regenerated. Memory [[project_substitution_engine]] warns that there are 57 sync sites touching this schema in FluxService.
  • Output. nodeSubstitutionSchema: { [key]: { [field]: string } }. Ready to be consumed by applySubstitutionToObject on every loop iteration. Zero I/O. Pure CPU. Complexity O(N × F).
Context. This is the reference engine. Lets a node write {{model_1}} or {{Persona Model}} in the prompt and receive the upstream node's output substituted in. Memory [[project_substitution_engine]] warns that the engine has 57 sync sites in FluxService reading and mutating the schema. It is not a simple regex. It involves field-path resolution and human aliases.

A basedOnType (static whitelist)
node-reference-substitution.service.ts:25-80
private readonly basedOnType: Record<nodeType, string[]>
Purpose. Defines which node.data fields are worth publishing to the schema, by node type. An unlisted node is ignored. An unlisted field (even if it exists in data) does not become substitutable.
In summary. This whitelist is the registry of the reference system. A hand-written list saying "for each node type, these are the fields that can be referenced via {{placeholder}}". A commandTextNode, for example, exposes prompt, persona, content, text. A sqlQuerier exposes host, query, etc. If the node type does not appear in the registry, it is ignored without a log. If the field is not listed, it exists in memory but no one can reference it. Because of this, creating a new node type and forgetting to update this list produces a silent bug. The placeholder does not resolve. No warning.

C Value extraction (object flatten)
node-reference-substitution.service.ts:105-127
for (const field of relevantFields) { let value = node.data[field]; if (object) value = value.text ?? value.content ?? value.result ?? JSON.stringify(value); entry[field] = value; }
Purpose. Normalizes the value so it is always a string. If node.data[field] is an object (common in outputs), tries to extract text, content or result. If nothing matches, falls back to JSON.stringify. If it is undefined, does not create the key.
In summary. This part is the translator. Ensures everything going into the schema comes out as text, because in the end {{placeholder}} is injected inside an LLM prompt, and a prompt is a string. If the field is already primitive (string, number, boolean), passes through. If it is an object, tries in order. First text, then content, then result. If none match, serializes the whole object as JSON. If the field is undefined, does not create the entry. The text > content > result precedence is silent and fragile. If a handler writes both, text wins. Changing this precedence in a refactor can break things without warning. This is also where memory grows. A single 2MB result lands whole in the schema and is replicated in every substitution.
🪜 Coercion cascade
1 node.data[field] === undefined skip (does not add)
2 value is primitive write directly
3a object with value.text entry[field] = value.text
3b otherwise, with value.content entry[field] = value.content
3c otherwise, with value.result entry[field] = value.result
3d fallback JSON.stringify(value)
↓
Result. entry[field]: string | number | boolean
Never an object. Always coerced. Lets String.replace work directly in applySubstitutionToObject.
⚠️ Precedence text > content > result
If the object has both text and content set (rare but happens), text wins. If a handler writes {text: 'x', content: {...big_json...}}, the {{node}} placeholder resolves to 'x', not to the JSON.

If this precedence changes in a refactor, it silently breaks handlers that rely on it.
🎯 JSON.stringify fallback
When the object has none of the 3 default fields, it becomes serialized JSON. Example. modelSettings in commandTextNode. The final prompt has a literal JSON string. Not elegant, but works for the LLM to read.
🔧 Big RAM contributor
content and result can be big payloads (LLM responses, SQL results). If a single node has a 2MB result, the schema carries those 2MB and every substituted {{node}} replicates it in the final string. See [[project_jsonb_fat_fields]] for the related pattern.
D 3-key indexing (stable/ref/label)
node-reference-substitution.service.ts:129-140
schema[stableKey] = entry; schema[refKey] = entry; schema[labelKey] = entry; // 3 keys, SAME reference
Purpose. Accepts three different placeholder formats for the same node. Raw UUID, normalized UUID and human label. All point to the same reference. An update in one of them reflects in the others.
In summary. This step is the registry that files the same node under three different names, all pointing to the same address. The node goes to the file. First. Under the raw UUID (a1b2-...). Second. Under the UUID with dots swapped by underscore (a dot in placeholders is used as field access {{x.y}}). Third. Under the human lowercase label with no spaces (personamodel). The three slots store the same reference to the entry object. When the output is updated later, a single mutation reflects in all three keys automatically. Lets the user write {{Persona Model}}, {{a1b2_c3d4_...}} or the raw UUID in the template. All resolve to the same value. Careful. If two nodes have the same label, the second overwrites the first in the label slot. {{persona}} becomes silently ambiguous.
schema[stableKey] = entry; // raw UUID: schema['a1b2-...'] const refKey = stableKey.replace(/\./g, '_'); if (refKey !== stableKey) { schema[refKey] = entry; // normalized UUID: schema['a1b2___'] } if (labelKey && labelKey !== stableKey && labelKey !== refKey) { schema[labelKey] = entry; // lowercase label: schema['personamodel'] }
↓
D1 stableKey = node.id
Raw UUID of the node. Always present (skipped above if missing).
↓
D2 refKey = id.replace(/\./g, '_')
Normalizes dots (not allowed in placeholder path {{x.y}}. Would collide with field access). Only enters the schema if different from stableKey.
↓
D3 labelKey (optional)
Only if the node's label exists and does not collide with the other two keys. Lets the user write {{Persona Model}} in the prompt. The replacer looks up schema.personamodel after normalizing.
⚠️ Label collision
Two nodes with the same label. The last wins in the schema. {{persona}} becomes ambiguous. The front should forbid duplicate labels. Without that protection, one is silently ignored.
🎯 Reference sharing
The three keys point to the same entry object. Intentional. updateSchemaWithNodeOutput only needs to mutate via one key. The other two reflect automatically.
🔧 Supported placeholder syntax
{{<key>.<field>}} or {{<key>}} (only the key, resolves to the first field's fallback). replacePlaceholders (lines 5-22) splits by . and navigates the object.
E Schema lifecycle in the run
flux.service.ts:3149, 3281, 3389+ · node-reference-substitution.service.ts:145-216
// 1x generate (here) → N× applySubstitutionToObject + updateSchemaWithNodeOutput (loop) → onMutateSchema (reassignment callback)
Purpose. Shows how the schema created here is consumed and mutated throughout execution. It is not regenerated. It is updated live. Each completed node enriches the schema with its output.
In summary. If the previous steps built the reference directory, this one is the courier that carries it back and forth throughout the execution. The per-node cycle goes. First. Before the handler runs, calls applySubstitutionToObject, which replaces all {{...}} with schema values. Second. The handler runs on the already-filled node and produces an output. Third. That output is written back into the schema via updateSchemaWithNodeOutput so it is available for the next nodes. Fourth. Because the schema is reassigned (new root object via spread), the onMutateSchema callback signals "use this new reference now". Memory [[project_substitution_engine]] warns that there are 57 sites in FluxService touching this cycle. Any engine refactor needs to touch all of them at once. No surgical swap possible.

🎯 Why spread in updateSchemaWithNodeOutput?
const updatedSchema = { ...schema } creates a new root object, but the entries remain shared. Punctual mutation does not invalidate old references. Reassignment does. That is why the onMutateSchema callback exists.

Migration notes.
• See memory [[project_substitution_engine]]. 57 sync sites in FluxService. Refactor requires touching all simultaneously.
• The worker does not have this engine. It receives each node already pre-substituted. Applies applySubstitutionToObject before the handoff. Migration to the worker preserves this boundary.
• basedOnType is hand-maintained (same as the MCP schema catalog). Adding a new node type with a referenceable field requires updating it. No CI check. Silent bug.
• Flattening result, content and text carries big payloads into memory. It is not safe to just preview-truncate (see [[project_node_field_taxonomy]]). The placeholder may need the full value.
• Long-term alternative. Index-only schema. The schema stores only {nodeId, field}. The resolver fetches the real value on demand. Eliminates in-memory duplication. Complicates cache.
• processFlowWithSubstitution (lines 241-267) looks like dead code. Validate before any cleanup.

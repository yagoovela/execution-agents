Step 1.6 — Chat context loading

Block in flux.service.ts:2485-2618. Determines the active chat session. Loads that session's history for each fluxObject in chat mode. Injects those entries and selectedSession into the in-memory node.data of fluxObject and nodesBox. Only runs when there is a sessionId (from the request or the 'default' fallback).
In short — what this step does
  • Decides whether this execution has a conversation. Checks the request's sessionId. If missing and the flow has some fluxObject with chat=true, applies the 'default' fallback. Without any of that, it produces an empty string and the whole step is skipped. Batch/api flows without chat pay no cost.
  • Loads history from the new table. For each fluxObject in chat/session mode, runs a SELECT on session_state_entries. The filter uses (flowId, nodeId, sessionKey, ownerUserId). The loop is sequential, one await per node. The result goes into a temporary local Map.
  • Merge into fluxObject via immutable spread. Injects entries, userSessionsChat and selectedChat into node.data. Rebuilds the old shape that the loop handlers already know how to read. Elects a single spokesperson. Only the first fluxObject with chat=true keeps the flag on. The others become silent storage.
  • Merge into nodesBox, simpler. For every nodesBox in the flow, sets selectedSession = sessionIdForChat and upserts into the data.sessions array. Does not read the new table. Its storage still lives in the legacy JSONB. Migration is partial. fluxObject has migrated. nodesBox has not yet.
  • Output. updatedFlows is an array of nodes with hydrated fluxObject and nodesBox pointing to the correct session. It lives in memory ready for the main loop (Phase 3). The temporary Map is discarded.
Context. A recent migration moved chat history and object sessions. They no longer live in mutable JSONB (flows_nodes.data.userSessionsChat, flow_objects.sessions). They moved to the session_state_entries table, append-only, isolated by ownerUserId. This step is the hydrator. It reads those rows and rebuilds the old shape inside updatedFlows in memory. The main loop handlers (Phase 3) keep working without a rewrite.

A sessionIdForChat resolution + gate
flux.service.ts:2485-2495
const sessionIdForChat = sessionId || (hasFluxObjectChat ? 'default' : '');
Purpose. Decides whether the execution has an associated chat session. If sessionId came in the request, uses that value. Otherwise, when some fluxObject declares chat=true, applies the 'default' fallback. An empty string skips the whole block (no chat).
In short. This step is the chat's door guard. Before firing any query, it decides whether the execution has an ongoing conversation. It answers three questions in order. First. Did the request bring a sessionId? If yes, use that value. Second. If not, does the flow have any node marked as interactive chat? If yes, enters the 'default' session. Third. None of the above? Returns an empty string and the whole block is skipped. That includes history queries and merges into the nodes. The step also locates the first fluxObject with chat=true. Downstream, only one node can be responsible for the chat. The rest become silent storage.

🎯 Why 'default'?
It is the DEFAULT_SESSION_KEY exposed in session-state.service.ts:32. If the flow has chat but the client did not pass sessionId, all executions share the 'default' session. History is single and global for that node, isolated by ownerUserId.
⚠️ Collision on 'default'
Two concurrent executions from the same user without sessionId will both read and write on the 'default' session. appendEntries is append-only. The history becomes an interleaved concatenation of the two conversations. There is no corruption, the append is safe. It is semantically confusing.
🔧 chat vs sessionEnabled
fluxObject has two flags.
• chat === true. Interpreted as interactive chat (user/assistant messages).
• sessionEnabled === true. Persists turn by turn, without chat UI.

The gate's detection (hasFluxObjectChat) considers only chat === true. If all fluxObject nodes only have sessionEnabled, the gate does not open with 'default'. An explicit sessionId is required.
B Loop 1: fetch chatEntriesByNodeId
flux.service.ts:2496-2515
for (const chatNode of updatedFlows) { if (fluxObject && (chat || sessionEnabled)) chatEntriesByNodeId.set(id, await readContents(...)) }
Purpose. For each fluxObject in chat or session mode, fetches all entries persisted in session_state_entries for the (flowId, nodeId, sessionKey, ownerUserId) combination. Populates a Map<nodeId, content[]>. The map is consumed by the merge loop (C).
In short. The backend plays the mailman. For each fluxObject participating in chat or session, it queries the new session_state_entries table. Passes the address (flowId, nodeId, sessionKey, ownerUserId). Collects all messages ordered by seq. The result goes into a local Map. The key is the node id. The value is the message array. This map only serves as a draft for the next step. After the merge, it is discarded. The loop is sequential. Each await waits for the previous one. Flows with many chat nodes stack up serial SELECTs at the beginning of the execution.

⚠️ Sequential N+1 (not Promise.all)
It is a for...of with an internal await. Each readContents waits for the previous one. A flow with 5 fluxObject in chat generates 5 sequential SELECTs at the start of every execution.

The real impact is low. The query is indexed and each returns few rows. Conversion to Promise.all(...) is trivial if needed.

🔧 buildNodeScopeId
String concatenation. `${flowId}:${nodeId}`. ownerUserId does not enter the scopeId. It goes into the WHERE separately. Allows indexing by (flow, node) and filtering by owner afterwards.

Consequence. If ownerUserId is undefined (bug in user?.id), the query brings all entries in that scope from all users. The WHERE does not even include the column. Footgun to watch for.
C Loop 2: merge into fluxObject
flux.service.ts:2517-2578
updatedFlows = updatedFlows.map(node => { if (fluxObject && isChatMode) return { ...node, data: { ...data, entries, userSessionsChat, ... } } })
Purpose. Injects the entries read from session_state_entries inside the in-memory node.data of each fluxObject. Rebuilds the old shape (entries, userSessionsChat, selectedChat). Only one node per execution ends with chat=true. The other fluxObject with chat=true end up with chat=false.
In short. This step is the translator. The history coming from the new table needs to be plugged into node.data in the old format that the loop handlers already know how to read (entries, userSessionsChat, selectedChat). For each fluxObject in chat/session mode, the merge decides the fit. If that session already existed in the old array, replace its entries with those from the new table. There is a fallback to the old JSONB when the new storage is empty. If the session did not exist, create a new entry. The step also elects a single spokesperson. The first node with chat=true keeps being the interactive chat owner. The others get demoted to storage. This avoids fighting over user input. Everything is done via immutable spread. The original object from getFlow is not modified.

🎯 Why does only 1 fluxObject end up with chat=true?
Interactive chat (with UI and socket message routing) only makes sense for one node. The other fluxObject with chat=true become session storage. They end up with sessionEnabled=true and chat=false.

This avoids two nodes competing for user input.
⚠️ Dangerous fallback: uses entries from JSONB
If storedEntries.length === 0 but findUserSession exists, the merge keeps the old JSONB entries (findUserSession.entries). Does not become an empty array.

This is a remnant of the old model, prior to the migration to session_state_entries. A flow with residual data in userSessionsChat JSONB keeps seeing that legacy history indefinitely. It only changes when someone writes into the new storage.
🔧 Shape of userSessionsChat[i]
{ id: string, name: string, entries: Record<string,any>[] }

The newly created item has name equal to 'Primary' when sessionIdForChat === 'default'. Otherwise, it uses sessionIdForChat itself.
🔧 Immutable mutation
Everything goes through spread (...node, ...data, [...userSessionsChat, new]). updatedFlows becomes a new reference on each map. The old sub-references are not touched. No risk of leaking mutation to the original getFlow.nodes.
D Loop 2: merge into nodesBox

Purpose. Every nodesBox receives sessionIdForChat as selectedSession. Upserts into data.sessions[]. Unlike fluxObject, there is no read of session_state_entries here. Only the selectedSession pointer is adjusted.
In short. If fluxObject had a translator, nodesBox has a simple registrar. For every nodesBox in the flow (without filtering by chat/session), points a cursor called selectedSession to the current session id. If that drawer does not yet exist in the data.sessions array, creates an empty one (content: []). Nothing else. No SELECT. No read from the new table. The nodesBox storage still lives inside the fat JSONB of flows_nodes.data. Migration to session_state_entries is still pending. Beware of naming. Here the list is called content. In fluxObject it is called entries. Same idea. Different schemas.

🎯 Why update every nodesBox?
nodesBox is object storage (key-value with sessions). Any node in the flow can read or write. When sessionIdForChat changes, every nodesBox needs to point to the same session. The storage written by one node must be the same read by another within the same execution.
⚠️ content: [], not entries: []
The shape of nodesBox.sessions[i] has content. fluxObject.userSessionsChat[i] has entries. Don't confuse them. They are different schemas by design. They carry the same idea of a list of items recorded in the session.
⚠️ Does not read from session_state_entries
Unlike fluxObject, which hydrates via readContents, nodesBox does not read the table. It only uses the in-memory array from data.sessions. The new storage (session_state_entries) only covers fluxObject. If the nodesBox handler depends on the old content, it reads JSONB. Migration incomplete.

See objects.service.ts and handler in flux.service.ts:3575 (nodesBox handler) to confirm how the append happens.
🔧 selectedSession = pointer
Works as a cursor into the array. The nodesBox handler runs sessions.find(s => s.id === selectedSession) to know where to write and read during execution.
Summary — what leaves 1.6.
• sessionIdForChat. String with the resolved chat session ('', 'default', or the request's sessionId).
• updatedFlows. Array of nodes with hydrated fluxObject (entries, userSessionsChat, selectedChat, chat, sessionEnabled) and nodesBox pointing to the correct selectedSession.
• A local Map<nodeId, content[]> (chatEntriesByNodeId) discarded after the merge.
• I/O. One SELECT on session_state_entries per fluxObject in chat/session mode, sequential.
Migration notes.
• Essential only when the flow has chat/session. The gate in (A) allows skipping the whole block. Batch/api flows without chat pay no cost.
• This step has already been partially migrated. fluxObject.entries now comes from session_state_entries. nodesBox.sessions[i].content still lives in the flows_nodes.data JSONB. Migrating nodesBox to session_state_entries (scopeType 'object') is the natural next step. Eliminates the fat JSONB ([[project_jsonb_fat_fields]]).
• The worker does not need to perform this setup. It can receive the updatedFlows already hydrated in the workflow's start-args. Alternative: only receive sessionIdForChat and ownerUserId and perform the read remotely inside a specific handler when history is needed.
• The sequential N+1 (B) is trivial to turn into Promise.all. Can fit into any optimization sprint. Does not block the migration.
• Critical footgun. If ownerUserId is undefined, the WHERE in readEntries omits the column. It leaks entries from other users. Harden this before any refactor.
• The old entries fallback (C, warn aside) needs to be removed at some point. Today it keeps residual JSONB data indefinitely.

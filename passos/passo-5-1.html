Passo 5.1 — Catch top-level

Bloco em flux.service.ts:5309-5392. Catch que envolve todo o corpo do apiV2(). Finaliza o RunLog com status='error'. Cria FlowLog de erro. Loga via Winston com hint contextual. Re-lança o erro para o caller.
Em resumo — o que esse passo faz
  • Rede de segurança do apiV2. Catch top-level que envolve o corpo inteiro do método. Se algo não tratado lançar (bug, banco caindo, code path esquecido), esse bloco é o último a rodar. Garante audit trail mesmo em cenário catastrófico.
  • Finaliza o RunLog em modo desastre. Mesma cadeia da Fase 4.4 (finalize + flushNow). Aqui com status: 'error' e errorMessage da exception. Um try/catch aninhado protege contra erro do erro. Se o próprio flush falha, o código apenas loga sem duplo-throw.
  • Log estruturado com hint contextual. Winston recebe errorName, errorMessage, errorStack e contexto da execução. Se a mensagem é 'nodes is not iterable' (bug conhecido), anexa sugestão diagnóstica direcionando o dev para os handlers suspeitos. Base de conhecimento embutida no código.
  • Grava execution_log de erro (com guard). Mesma createLog da 4.3, agora com status: 'Error while running'. Guard: se a exception é NotFoundException com "flow not found", o código não grava. Sem flowId válido, não há FK para respeitar.
  • Saída. throw error re-lança a exception original. Tipo e stack são preservados. O controller HTTP devolve 500. O Bull marca o job como failed. O finally do 5.3 ainda roda antes da propagação efetiva.
Contexto. Última linha de defesa contra qualquer exception não tratada no apiV2. Diferente do catch por nó (3.8), que só quebra o loop e segue para a Fase 4. Aqui trata-se de bug ou erro sistêmico. Falha em setup, banco fora do ar, code path não esperado. Garante audit trail mesmo em cenário catastrófico.

Quando você conhece bem os bugs comuns, otimiza para a próxima ocorrência.

⚠️ Regex de detecção
/flow not found/i.test(msg). Depende da mensagem literal. Se outro código do sistema lançar NotFoundException("Flow could not be found"), o teste não bate. Frágil. Uma classe específica (FlowNotFoundException extends NotFoundException) seria melhor.
Dthrow error
flux.service.ts:5392
throw error;
Propósito. Re-lança a exception original para o caller. O controller do endpoint (ou o processor do Bull) recebe e devolve HTTP 500, ou marca o job como failed no Bull. Fica evidente que a execução falhou de forma fatal. Não retornou objeto de resposta.
Em resumo. Última linha do catch. Depois de todo o cleanup (finalize, log, createLog), o código re-lança a exception original. Simples. Motivo. O caller precisa saber que falhou. Se apiV2 retornasse null ou algo similar, o controller ou processor não distinguiria "sucesso com resposta vazia" de "crash fatal". Com throw, o caller HTTP recebe erro. O controller do endpoint cai no exception handler global do Nest. Devolve HTTP 500. O processor do Bull vê a exception e marca o job como failed. Sinalização clara. O código preserva a exception original. Não faz wrap em new Error. Quem pega tem stack completo e tipo original. É a coisa certa em quase todos os casos.
throw error;

Propagação
Controller do endpoint (HTTP): cai no exception handler global do Nest. Processor do Bull: marca o job como failed. O mcpRunStatusService (5.2) chama markFinished antes de o erro propagar.
🎯 O finally roda antes do throw efetivo
Semântica do JS. throw dentro do catch ainda passa pelo finally antes de propagar. É o que garante que o 5.3 (delete chatbotSocketByRun) roda mesmo em erro.
📎 Sem wrapping
Tipo e stack originais são preservados. Boa prática. Melhor para debug.
Resumo — o que sai de 5.1:

Observações para migração:
• Essencial e cross-cutting. Cobertura de erros catastróficos é obrigatória.
• Try/catch aninhados dentro do catch principal (defesa contra erro do erro) é bom padrão. Manter.
• Hint contextual ('nodes is not iterable') é dívida baixa. Cresce conforme mais bugs conhecidos aparecerem.
• NotFoundException + regex é frágil. Um tipo específico é melhor.
• Migração para o worker. O worker terá seu próprio catch. O backend continua como orquestrador principal e precisa dessa rede de segurança.

Step 2.4 — RunLogCollector setup (plumbing)

Block in flux.service.ts:2290-2293 (init) and 3810-3818 (startLoopBody inside arrayNode). Unlike 1.4, which creates the collector via createRoot(), 2.4 is the cross-cutting plumbing. Describes how the collector flows through sub-runs (fluxBox/libraryNode) and loop iterations (arrayNode).
In summary — what this step does
  • Decides whether to open a new document or continue an existing one. If an injectedRunLogCollector came from the parent (sub-run via fluxBox/libraryNode), reuse it. Otherwise, leave null for now and delegate creation to 1.4. The isNestedRunLog flag gates three behaviors throughout execution.
  • Creates the root collector if it's top-level and the space records logs. createRoot({...}) builds a RunLogDocument in memory and plugs flushFn into spaceRunLogsService.scheduleUpsert. If any condition fails, runLogCollector = null. The ?. pattern at all call-sites allows operating in silent mode without branches.
  • Opens a RunLogNode on each loop iteration. startNode({ nodeId, nodeType, label, settings }) records the post-substitution input and returns a handle used later in endNode. Anchor nodes (fluxBox/libraryNode) skip this generic startNode. Their handler builds the correct structure.
  • Specializes the collector inside loops (startLoopBody). When execution encounters an arrayNode, it creates a sub-collector whose nodesBucket points to parentNode.innerSteps. The N iterations become nested children of the loop in the UI, not loose siblings.
  • Attaches sub-documents when fluxBox/libraryNode call another flow. startFlowCallerSubRun creates a complete subDoc: RunLogDocument and places it in the parent node's subRun field. Inherits spaceId and orgId from the ancestor. Shares flushFn. Everything writes to the same physical root document with a layered structure.
  • Output. runLogCollector: RunLogCollector | null ready for Phase 3 handlers. A RunLogNode tree is built in memory at each event and flushed via scheduleUpsert. The entire observability layer depends on this plumbing.
Context. The RunLogCollector is the backbone of execution observability. It captures a hierarchical tree of RunLogNodes per execution. At top-level, it's created in 1.4 via createRoot(). In sub-runs (agent calling another agent), it's injected as a parameter. Inside loops, it's specialized via startLoopBody. This step maps the three modes.

A Init pattern (injected vs null)
flux.service.ts:2290-2293
let runLogCollector: RunLogCollector | null = injectedRunLogCollector ?? null; const isNestedRunLog = !!injectedRunLogCollector;
Purpose. Detects whether this apiV2() is a top-level execution or a sub-run called by another agent (fluxBox/libraryNode). Sub-runs receive the parent's collector as a parameter (injectedRunLogCollector). Logs go to the parent's root document, without creating a new one.
In summary. This function is the reception desk of the execution registry. When a new execution arrives, it checks whether it's a new client (top-level) or the continuation of a record opened above (sub-run). If one agent called another (via fluxBox or libraryNode), the parent already handed over the collector at the door. The function takes that collector and keeps writing to it. It sets isNestedRunLog=true to tell the rest of the flow that someone is already handling this. If no one came, it leaves runLogCollector = null for now and delegates creation to step 1.4.

A2 Callers that inject

🎯 Why pass the collector instead of creating anew?
An agent that calls three sub-agents creates three sub-documents (via startFlowCallerSubRun). All live inside the same root document. The UI shows the hierarchy. If each sub-run created its own doc, the tree would be lost.
⚠️ Injected can be null even for sub-run
If the parent didn't have logging enabled (outside of space, or space without loggingEnabled), the parent has runLogCollector = null. Passes null to the child. The child doesn't log. Sub-run only logs if the parent was logging.

D startLoopBody (arrayNode iterations)
flux.service.ts:3810-3818 · run-log-collector.ts:252-275
const loopRunLogNode = runLogCollector?.startNode({...}); const loopRunLogCollector = runLogCollector?.startLoopBody(loopRunLogNode) ?? runLogCollector;
Purpose. When the main loop encounters an arrayNode, it creates a special RunLogNode for the loop and returns a sub-collector whose entries go into innerSteps of that node. Each body iteration is recorded as a child of the loop, not as a sibling.
In summary. This step opens an organized sub-structure inside the diary. When execution encounters an arrayNode, it does two things. First. Opens a parent node in the log saying "I will run N iterations". Second. Delivers a specialized collector (the loopRunLogCollector) that, instead of noting at the level above, stacks everything inside that parent node's innerSteps. Thus the UI shows the loop as expandable ("click here to see the 50 iterations of this arrayNode"), instead of dumping everything into a flat list. If the parent is disabled, it falls back and uses the normal collector. Doesn't break.

🎯 Why sub-collector and not sub-node?
It would be possible to record each iteration as a sibling in the root doc. But the RunLogNode.innerSteps schema allows displaying the UI as a tree. Expand arrayNode. See iterations. Each iteration has its nodes. Much more readable than a flat list with 200 entries.
⚠️ Iterations without index distinction
All iterations append to innerSteps. There's no iterationIndex field. Opening 3 iterations of 5 nodes each shows 15 sequential entries. The order preserves execution order, but requires manual counting.
🔧 startLibrarySubRun
Same thing, but kind='library'. Used by the libraryNode handler. Semantically identical to loopBody. Only the label changes.
E startFlowCallerSubRun (fluxBox anchor)
run-log-collector.ts:277-317 · flux.service.ts:4350 (fluxBox)
const sub = runLogCollector?.startFlowCallerSubRun(parentNode, { flowId, flowName, input });
Purpose. When a fluxBox calls another flow, it creates a nested subDoc (not innerSteps. A whole document). The parent node gets subRun instead of innerSteps. The UI shows "this node executed this entire sub-flow".
In summary. If the loop opened a sub-tab, this step attaches a whole document inside the main document. When a fluxBox node calls another complete agent, this function builds a new subDoc (with rootFlowId, rootFlowName, nodes: [], etc.) and places it in the parent node's subRun field. The UI shows a breadcrumb like "Agent A → Agent B → node X" instead of mixing everything at the same level. The processId stays the same (it's the same physical execution). spaceId and orgId are inherited from the ancestor (even if the sub-flow is from another space). Everything keeps flushing to the same physical root document in the database. Just structured in layers.

🎯 subRun vs innerSteps
innerSteps. Child nodes of the same flow (loops, internal sub-tasks). Shares flowId and flowName.

subRun. Called another flow. Has its own rootFlowId and rootFlowName. The UI shows a breadcrumb ("Agent A → Agent B → node X").
⚠️ Field inheritance from ancestor
subDoc.spaceId = ancestor.spaceId. Sub-run always inherits. If the sub-flow is in a different space than the parent, logs go to the parent's org and space. May not be semantically desired, but keeps the tree consistent.
🔧 SubKind enum
'library' | 'flowCaller' | 'loopBody'. Three sub-collector categories. Each with slightly different semantics. flowCaller creates subRun/subDoc. The other two use innerSteps.
Summary — what comes out of 2.4.
• runLogCollector: RunLogCollector | null. Ready for Phase 3 handlers.
• isNestedRunLog: boolean. Flag consumed at three gates throughout execution.
• ?. pattern at all call-sites. Optional logging without branches.
• RunLogNode tree built in memory during execution. Flushed via scheduleUpsert.
Migration notes.
• This is the observability layer. Not essential for execution (the loop works with a null collector). Critical for debugging, UI and billing.
• The worker has no collector. It emits events via notifyStatusActivity (Redis pub/sub) and writes to execution_logs. The backend consumes these events and reconstructs the tree in the root doc.
• Sub-runs (fluxBox/libraryNode) only work synchronously today. They pass the collector by parameter. If sub-runs ever become async (worker), the collector must serialize via processId and emit events.
• startLoopBody and startLibrarySubRun return another instance. Be careful about who uses which in Phase 3. Classic bug. Using runLogCollector instead of loopRunLogCollector inside the loop makes iterations become siblings of the loop, not children.
• Flushing on every event can become a bottleneck in large executions. Debounce or batch in scheduleUpsert helps.
• Ideally, RunLogCollector is stateless per call. Receives an event and emits to a sink (Redis, DB, nothing). Today it keeps the tree in memory. Replicating that in the worker is complicated.

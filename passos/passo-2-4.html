Passo 2.4 — Setup do RunLogCollector (plumbing)

Bloco em flux.service.ts:2290-2293 (init) e 3810-3818 (startLoopBody dentro do arrayNode). Diferente do 1.4, que cria o collector via createRoot(), o 2.4 é o plumbing cross-cutting. Descreve como o collector flui através de sub-runs (fluxBox/libraryNode) e iterações de loop (arrayNode).
Em resumo — o que esse passo faz
  • Decide se abre um documento novo ou continua um existente. Se veio um injectedRunLogCollector do parent (sub-run via fluxBox/libraryNode), reusa. Senão, deixa null por enquanto e delega a criação para o 1.4. A flag isNestedRunLog gateia três comportamentos ao longo da execução.
  • Cria o collector root se for top-level e o space registra logs. createRoot({...}) monta um RunLogDocument em memória e pluga o flushFn no spaceRunLogsService.scheduleUpsert. Se qualquer condição falhar, runLogCollector = null. O padrão ?. em todos os call-sites permite operar em modo silencioso sem branches.
  • Abre um RunLogNode a cada iteração do loop. startNode({ nodeId, nodeType, label, settings }) registra o input pós-substituição e devolve um handle usado depois no endNode. Anchor nodes (fluxBox/libraryNode) pulam esse startNode genérico. O handler deles monta a estrutura correta.
  • Especializa o collector dentro de loops (startLoopBody). Quando a execução encontra um arrayNode, cria um sub-collector cujo nodesBucket aponta para parentNode.innerSteps. As N iterações viram filhos aninhados do loop no UI, não siblings soltos.
  • Anexa sub-documentos quando fluxBox/libraryNode chamam outro flow. startFlowCallerSubRun cria um subDoc: RunLogDocument completo e coloca no campo subRun do parent node. Herda spaceId e orgId do ancestor. Compartilha o flushFn. Tudo grava no mesmo documento raiz físico com estrutura em camadas.
  • Saída. runLogCollector: RunLogCollector | null pronto para os handlers da Fase 3. Uma árvore RunLogNode é montada em memória a cada evento e flushada via scheduleUpsert. O observability inteiro depende desse plumbing.
Contexto. O RunLogCollector é a espinha dorsal do observability da execução. Captura árvore hierárquica de RunLogNodes por execução. Em top-level, é criado em 1.4 via createRoot(). Em sub-runs (agente que chama outro agente), é injetado como parâmetro. Dentro de loops, é especializado via startLoopBody. Este passo mapeia os três modos.
Padrões de plumbing em 2.4
AInit pattern (injected ?? null) → BcreateRoot fallback (1.4) → CstartNode por iteração → DstartLoopBody (arrayNode) → EstartSubRun (fluxBox/library)
Resultado final. Uma árvore de RunLogNodes montada em memória (via innerSteps e subRun). Serializada em run_log_documents pelo spaceRunLogsService.
A Init pattern (injected vs null)
flux.service.ts:2290-2293
let runLogCollector: RunLogCollector | null = injectedRunLogCollector ?? null; const isNestedRunLog = !!injectedRunLogCollector;
Propósito. Detecta se este apiV2() é execução top-level ou sub-run chamada por outro agente (fluxBox/libraryNode). Sub-runs recebem o collector do pai como parâmetro (injectedRunLogCollector). Os logs vão para o documento raiz do pai, sem criar documento novo.
Em resumo. Esta função é a recepção do cartório de execução. Ao chegar uma nova execução, verifica se é cliente novo (top-level) ou continuação de um registro aberto acima (sub-run). Se um agente chamou outro (via fluxBox ou libraryNode), o pai já entregou o collector na porta. A função pega esse collector e continua escrevendo nele. Marca isNestedRunLog=true para avisar o resto do fluxo que já tem alguém cuidando disso. Se não veio ninguém, deixa runLogCollector = null por enquanto e delega a criação para o passo 1.4.

A2 Chamadores que injetam

🎯 Por que passar collector e não criar de novo?
Um agente que chama três sub-agents cria três sub-documentos (via startFlowCallerSubRun). Todos vivem dentro do mesmo documento raiz. A UI mostra a hierarquia. Se cada sub-run criasse doc próprio, perderia a árvore.
⚠️ Injected pode ser null mesmo para sub-run
Se o parent não tinha logging habilitado (fora de space, ou space sem loggingEnabled), o parent tem runLogCollector = null. Passa null para o filho. O filho não loga. Sub-run só loga se o parent logava.

B createRoot fallback (delegado ao 1.4)

Propósito. Se é top-level e o space tem loggingEnabled, cria o collector root. Se não, runLogCollector continua null e todos os runLogCollector?.startNode(...) viram no-ops via optional chain.
Em resumo. Esta etapa é a abertura oficial do documento de execução. Só ocorre se três condições passam. Primeira. É execução top-level. Segunda. O space tem logging ligado. Terceira. Tem dono do space definido. Se tudo passa, chama createRoot(), que monta um RunLogDocument zerado em memória e devolve o collector já plugado no scheduleUpsert para persistir no banco. Se falha, runLogCollector fica null. O resto do código usa runLogCollector?.startNode(...) com optional chain. Tudo continua rodando normalmente, só que sem gravar log. É um modo silencioso que dispensa if em cada chamada.

🎯 Ciclo de vida por nó

⚠️ Flush a cada evento
Toda startNode, endNode, startLoopBody, etc. chama flushRoot(). Isso dispara scheduleUpsert. Não faz UPSERT direto. Agenda. Um flow de 200 nós gera mais de 400 agendamentos. Vale conferir se o schedule tem debounce (provavelmente sim).
🔧 settings é o node.data pós-substituição
Já com {{...}} resolvidos. É o snapshot do que o handler vai receber. Útil para debugging. Mostra o input real, não o template.
D startLoopBody (arrayNode iterations)
flux.service.ts:3810-3818 · run-log-collector.ts:252-275
const loopRunLogNode = runLogCollector?.startNode({...}); const loopRunLogCollector = runLogCollector?.startLoopBody(loopRunLogNode) ?? runLogCollector;
Propósito. Quando o loop principal encontra um arrayNode, cria um RunLogNode especial para o loop e devolve um sub-collector cujas entries vão em innerSteps desse nó. Cada iteração do body é registrada como filho do loop, não como sibling.
Em resumo. Esta etapa abre uma sub-estrutura organizada dentro do diário. Quando a execução encontra um arrayNode, faz duas coisas. Primeiro. Abre um nó pai no log dizendo "vou rodar N iterações". Segundo. Entrega um collector especializado (o loopRunLogCollector) que, em vez de anotar no nível de cima, empilha tudo dentro do innerSteps desse nó pai. Assim a UI mostra o loop expansível ("clique aqui para ver as 50 iterações deste arrayNode"), em vez de despejar tudo em uma lista plana. Se o parent está desabilitado, cai no fallback e usa o collector normal. Não quebra.

🎯 Por que sub-collector e não sub-node?
Seria possível gravar cada iteração como sibling no doc raiz. Mas o schema de RunLogNode.innerSteps permite exibir a UI como árvore. Expande arrayNode. Vê iterações. Cada iteração tem seus nós. Muito mais legível que uma lista plana com 200 entries.
⚠️ Iterações sem distinção por índice
Todas as iterações fazem append em innerSteps. Não há campo iterationIndex. Ao abrir 3 iterações de 5 nós cada, vê 15 entries seguidas. A ordem preserva a ordem de execução, mas exige contar manualmente.
🔧 startLibrarySubRun
Mesma coisa, mas kind='library'. Usado pelo handler de libraryNode. Semanticamente idêntico ao loopBody. Só muda o rótulo.
E startFlowCallerSubRun (fluxBox anchor)
run-log-collector.ts:277-317 · flux.service.ts:4350 (fluxBox)
const sub = runLogCollector?.startFlowCallerSubRun(parentNode, { flowId, flowName, input });
Propósito. Quando um fluxBox chama outro flow, cria um subDoc aninhado (não innerSteps. Um documento inteiro). O parent node ganha subRun em vez de innerSteps. A UI mostra "este nó executou este sub-flow inteiro".
Em resumo. Se o loop abria uma sub-aba, esta etapa anexa um documento inteiro dentro do documento principal. Quando um nó fluxBox chama outro agente completo, esta função monta um subDoc novo (com rootFlowId, rootFlowName, nodes: [], etc.) e o coloca no campo subRun do nó pai. A UI mostra breadcrumb como "Agente A → Agente B → nó X" em vez de misturar tudo no mesmo nível. O processId permanece o mesmo (é a mesma execução física). spaceId e orgId são herdados do ancestor (mesmo que o sub-flow seja de outro space). Tudo continua flushando para o mesmo documento raiz físico no banco. Só que estruturado em camadas.

🎯 subRun vs innerSteps
innerSteps. Nós filhos do mesmo flow (loops, sub-tasks internas). Compartilha flowId e flowName.

subRun. Chamou outro flow. Tem rootFlowId e rootFlowName próprios. A UI mostra breadcrumb ("Agente A → Agente B → nó X").
⚠️ Herança de campos do ancestor
subDoc.spaceId = ancestor.spaceId. Sub-run sempre herda. Se o sub-flow está em space diferente do parent, os logs vão para org e space do parent. Pode não ser semanticamente desejado, mas mantém a árvore consistente.
🔧 SubKind enum
'library' | 'flowCaller' | 'loopBody'. Três categorias de sub-collector. Cada uma com semântica ligeiramente diferente. flowCaller cria subRun/subDoc. As outras duas usam innerSteps.
Resumo — o que sai de 2.4.
• runLogCollector: RunLogCollector | null. Pronto para os handlers da Fase 3.
• isNestedRunLog: boolean. Flag consumida em três gates ao longo da execução.
• Padrão ?. em todos os call-sites. Logging opcional sem branches.
• Árvore RunLogNode montada em memória durante a execução. Flushada via scheduleUpsert.
Observações para migração.
• Este é o observability layer. Não é essencial para a execução (o loop funciona com collector null). Crítico para debugging, UI e billing.
• O worker não tem collector. Emite eventos via notifyStatusActivity (Redis pub/sub) e escreve em execution_logs. O backend consome esses eventos e reconstrói a árvore no doc raiz.
• Sub-runs (fluxBox/libraryNode) só funcionam síncronos hoje. Passam collector por parâmetro. Se um dia sub-runs virarem async (worker), o collector precisa serializar via processId e emitir eventos.
• startLoopBody e startLibrarySubRun retornam outra instância. Atenção com quem usa qual na Fase 3. Bug clássico. Usar runLogCollector em vez de loopRunLogCollector dentro do loop faz iterações virarem siblings do loop, não filhos.
• Flush a cada evento pode virar gargalo em execuções grandes. Debounce ou batch no scheduleUpsert ajuda.
• Idealmente, RunLogCollector é stateless por chamada. Recebe evento e emite para sink (Redis, DB, nada). Hoje mantém árvore em memória. Replicar isso no worker é complicado.

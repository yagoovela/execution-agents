Step 1.3 — Flow loading + permissions

4 sequential calls in flux.service.ts:2338-2367. Each one is detailed below with its own sub-flow and helper services.
In summary — what this step does
  • Loads the agent's blueprint. Queries the database to get the flow with all nodes, edges and relations (owner, folder, company, library), already in the format React Flow understands.
  • Decides which snapshot of the agent will run. If the request asked for a specific version, uses it. Otherwise, falls back to the published version or the live working copy. Ensures execution is reproducible even if someone edits the agent midway.
  • Checks if the user can trigger it. Validates whether whoever hit "run" has permission on this flow (owner, active company member, public template, etc). If not, throws HTTP 403 immediately.
  • For top-level runs, validates the account owner. Blocks if the owner is on an expired plan (Vault or read-only). Internal sub-flows skip this gate — it was already checked above.
  • Output. A complete Flow object in memory. Authorization and billing already validated. Ready for the pipeline to continue without worrying about access.

B flowService.resolveExecutionHistoryId()

async resolveExecutionHistoryId(flow: Flow, requestedVersionId?: string, requestedHistoryId?: string): Promise<string | null>
Purpose. Decides which snapshot of nodes and edges the execution will read from. flow_version_history_id (frozen version) or null (live working copy). It's called twice. Once inside (A). Once explicitly by apiV2() to persist flowVersionHistoryId in the context.
In summary. The function answers a single question. Which snapshot of the agent will the execution start from. Tests alternatives in order. If the flow has no version control enabled, runs the current working version. If a specific history came in the request, uses that. If a versionId came in, looks up the corresponding history. If the flow has a version flagged as deployed (the production one), uses it as fallback. Otherwise, also runs the live version. This ensures execution is reproducible. Even if someone edits the agent five minutes later, whoever was already running continues to see exactly the snapshot it started with.

Purpose. Billing gate. Checks if the flow's owner (not the caller) has an active plan that allows agent execution. Blocks flows whose owner is on the Vault (read-only) plan.
Called only if !isNestedRunLog. Not applied to flows called internally via fluxBox or libraryNode.
In summary. If (C) is the user's gatekeeper, this function is the billing ruler for the agent's owner. Answers the question: does the account holder for this flow have an active plan for running agents? Figures out who the billable admin of the flow is. If it's inside a company, it's the company admin. Otherwise, the creator themself. Queries that admin's active plan. If the plan is Vault type (read-only, typical of expired subscription), blocks execution with 403 even if the caller has permission. Only runs at the top level of execution. If this flow is already a sub-flow called by another (via fluxBox or libraryNode), skips the check. The owner's billing was already validated above.

🔧 Owner resolution order (selectFlowAdmin)
1. Prioritizes the space company admin if the flow is in a space.
2. Falls back to companyUser company admin if the flow is a companyUser one.
3. Otherwise, returns the direct creator user of the flow.

Billing and charges always fall on the company admin, not the actual owner of the flow in multi-tenant environments.

Notes for migration:
The 3 loading queries (flow, nodes and edges) happen on the backend before any dispatch decision. If the worker is going to orchestrate, it will need this same triad. Either receives everything serialized at the start of the workflow or redoes the queries there.
The permission layer (C plus D) is 100% relational (users, company_user, user_product, folder.spaces). Replicating it on the worker means exposing these schemas or keeping the gate on the backend before starting the workflow.
The selectFlowAdmin cascade is sensitive to changes in company structure. Any multi-tenancy refactor will affect the billing gate.

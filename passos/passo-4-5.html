Passo 4.5 — Preparação de erro amigável

Bloco em flux.service.ts:4881-4884. Uma única expressão monta a string nodeError. A string é user-facing e traz o nome do nó e a mensagem original. Vai para o retorno em 4.9. O cliente lê essa string para exibir o modal de erro.
Em resumo — o que esse passo faz
  • Localiza o nó culpado. currentFlux.find(node => node.data?.errorMessage). Usa find, que para no primeiro match. Roda sobre currentFlux. currentFlux é myUpdatedNodes após addConnectToNodes.
  • Monta a string user-facing. "Execution failed at node \"Escritor\" — Rate limit exceeded. Check the execution logs for details (timestamp: 2026-08-20T14:23:15.123Z).". Três informações em uma linha: onde, o que e quando.
  • Fallback para o id quando não há label. label || id. Se o dev do agente nomeou o nó ("Escritor"), o nome aparece formatado. Caso contrário, aparece o UUID cru.
  • O timestamp é o momento atual, não o do erro. new Date().toISOString() gera o momento em que a string é montada. Não representa quando o erro aconteceu. É uma falha de UX pequena.
  • Saída. nodeError guarda a string amigável em caso de erro. Guarda null em caso de sucesso. Vai para o retorno em 4.9. O cliente checa if (nodeError) para decidir se abre o modal de erro.
Contexto. Passo pequeno, porém relevante para a UX. Se a execução falhar, o cliente precisa saber onde e por quê. Essa string aparece para o usuário. Não é log nem analytics. Também traz timestamp. O cliente consegue cruzar essa string com os logs quando abre um ticket.

BTemplate string do nodeError
flux.service.ts:4882-4884
const nodeError = nodeWithError ? `Execution failed at node "${label || id}" — ${errorMessage}. Check the execution logs for details (timestamp: ${ISO}).` : null;
Propósito. Monta a string user-friendly com três partes. Parte 1: label do nó culpado. Faz fallback para o id quando o label está ausente. Parte 2: mensagem de erro do handler. Parte 3: timestamp ISO para cruzar com os logs. Sem erro, o valor é null.
Em resumo. É o relatório final para o cliente. Formato: "Execution failed at node \"Escritor\" — Rate limit exceeded. Check the execution logs for details (timestamp: 2026-08-20T14:23:15.123Z).". Três informações densas em uma linha. Onde: label do nó, ou id quando o label falta. Dizer "Escritor" é mais amigável que "6d09d1a3-...". O que: mensagem que o handler escreveu. Geralmente algo curto, tipo "API returned 503" ou "Invalid credentials". Quando: timestamp ISO em UTC. O cliente vê o UTC estranho. Trata-se de problema conhecido. O frontend converte para local timezone. Em caso de sucesso, nodeError = null. O retorno traz esse campo. O cliente checa if (nodeError) para decidir se mostra o modal de erro. O timestamp é gerado no momento em que a string é montada. Não representa quando o erro aconteceu, o que seria mais preciso.
const nodeError = nodeWithError ? `Execution failed at node "${nodeWithError.data?.label || nodeWithError.id}" — ${nodeWithError.data.errorMessage as string}. Check the execution logs for details (timestamp: ${new Date().toISOString()}).` : null;
🎯 Fallback do label para o id
label || id. Se o usuário nomeou o nó ("Escritor"), o código usa esse nome. Caso contrário, usa o UUID cru. Melhora a UX quando o dev do agente nomeou todos os nós.
⚠️ Timestamp do momento atual, não do erro
new Date().toISOString() retorna o momento em que a string é montada. Não representa quando o erro aconteceu. Para debug preciso, o cliente prefere o timestamp real do erro. Esse valor existe em execution_logs.updated_at ou node_executions.updated_at. Não é usado aqui. É uma falha de UX.
🔧 String livre, sem estrutura
O cliente faz parse por regex ou substring quando precisa extrair o nome do nó ou o timestamp. A string não é JSON. Se o formato mudar, o parse do cliente quebra. Contrato implícito.
Resumo — o que sai de 4.5:
• nodeError: string amigável em caso de erro. null em caso de sucesso.
• Vai para o retorno em 4.9 como parte do { message, nodeError, ... }.
• O callback consolidado em 4.7 usa esse valor para decidir sucesso ou erro da execução.
Observações para migração:
• A string livre é dívida técnica leve. Poderia virar erro estruturado { nodeId, nodeLabel, message, timestamp }.
• O timestamp do momento atual em vez do momento do erro é bug de UX pequeno. Vale corrigir cedo.
• Não bloqueia migração. Pode ficar como está. Refactor incremental depois.

Passo 4.5 — Preparação de erro amigável

Bloco em flux.service.ts:4881-4884. Uma única expressão que monta a string nodeError — user-facing, com nome do nó e mensagem original. Vai pro retorno em 4.9 e é lido pelo cliente pra exibir modal de erro.
Em resumo — o que esse passo faz
  • Acha o culpado (de novo): currentFlux.find(node => node.data?.errorMessage) — usa find (para no primeiro match), e sobre currentFlux (que é myUpdatedNodes pós-addConnectToNodes).
  • Monta a string user-facing: "Execution failed at node \"Escritor\" — Rate limit exceeded. Check the execution logs for details (timestamp: 2026-08-20T14:23:15.123Z).". Três coisas em uma linha: onde, o que e quando.
  • Fallback pro id se não tem label: label || id — se o dev do agente nomeou o nó ("Escritor"), aparece bonito; senão UUID cru.
  • Timestamp é "agora", não do erro: new Date().toISOString() gera o momento de montar a string — não quando o erro realmente aconteceu. Miss de UX pequeno.
  • Saída: nodeError = string amigável em caso de erro, null em caso de sucesso. Vai pro retorno em 4.9 — cliente checa if (nodeError) pra decidir se abre modal de erro.
Contexto: passo pequeno, mas importante pra UX. Se o run falhar, o cliente precisa saber onde e por quê. Essa string é o que aparece pro usuário — não é log, não é analytics. Cabe também timestamp pra o cliente conseguir cross-reference com logs se abrir ticket.

BTemplate string do nodeError
flux.service.ts:4882-4884
const nodeError = nodeWithError ? `Execution failed at node "${label || id}" — ${errorMessage}. Check the execution logs for details (timestamp: ${ISO}).` : null;
Propósito: Monta string user-friendly com 3 pedaços: (i) label do nó culpado (fallback pro id se não tem label), (ii) mensagem de erro do handler, (iii) timestamp ISO pra cross-reference com logs. Se sem erro, é null.
Em resumo: é o relatório final pro cliente. Formato: "Execution failed at node \"Escritor\" — Rate limit exceeded. Check the execution logs for details (timestamp: 2026-08-20T14:23:15.123Z).". Três informações densas em uma linha: onde (label do nó, ou id se label ausente — mais amigável dizer "Escritor" que "6d09d1a3-..."), o que (mensagem que o handler escreveu — geralmente algo curto e amigável, tipo "API returned 503" ou "Invalid credentials"), e quando (timestamp ISO em UTC — o cliente vê UTC estranho mas isso é problema conhecido; converte pra local timezone só no frontend). Se run foi sucesso, nodeError = null — o retorno tem esse campo mas o cliente checa if (nodeError) pra decidir se mostra modal de erro. Timestamp gerado agora na hora de montar a string — não é o tempo em que o erro aconteceu (que seria mais preciso).
const nodeError = nodeWithError ? `Execution failed at node "${nodeWithError.data?.label || nodeWithError.id}" — ${nodeWithError.data.errorMessage as string}. Check the execution logs for details (timestamp: ${new Date().toISOString()}).` : null;
🎯 Label fallback pro id
label || id — se o usuário nomeou o nó ("Escritor"), usa. Senão o UUID cru. Melhor UX quando o dev do agente nomeou tudo direitinho.
⚠️ Timestamp de "agora" não do erro
O new Date().toISOString() é o momento de montar a string, não quando o erro aconteceu. Pra debug preciso, o cliente prefere o timestamp do erro real — que existe em execution_logs.updated_at ou node_executions.updated_at, mas não é usado aqui. Miss de UX.
🔧 String livre, sem estrutura
Cliente parseia por regex ou substring se precisa extrair o nome do nó ou o timestamp. Não é JSON — se algum dia mudar formato, quebra parseamento cliente. Contratual implícito.
Resumo — o que sai de 4.5:
• nodeError: string amigável se erro, ou null se sucesso
• Vai pro retorno em 4.9 como parte do { message, nodeError, ... }
• Usado pelo callback consolidado em 4.7 pra decidir sucesso/erro do run
Observações para migração:
• String livre é dívida técnica leve — poderia virar structured error { nodeId, nodeLabel, message, timestamp }.
• Timestamp de "agora" vs "quando o erro aconteceu" é bug de UX pequeno — corrigir cedo.
• Não bloqueia migração — pode ficar tal como é. Refactor incremental depois.

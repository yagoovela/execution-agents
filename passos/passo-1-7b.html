Passo 1.7b — clearRunOutputForSeed + clearObjects

Bloco em flux.service.ts:2814-2825. Duas passadas finais de limpeza antes do loop começar. Primeira. clearRunOutputForSeed é a segunda passada de reset por node type. Também zera refs resolvidas em promptData, contentData e textData. Segunda. clearObjects reseta os objetos personalizados (nomes antigos de fluxObject) que participam via nodesBox. Termina com o snapshot newFlows = [...updatedFlows].
Em resumo — o que esse passo faz
  • Segunda passada de reset via clearRunOutputForSeed. Passa em todos os nós, não só os com clearOnExecution. Executa clearStaleNodeOutput. Limpa outputObjectNode.text. Zera text em qualquer ref dentro dos arrays promptData, contentData, textData. É redundante com o 1.7a para types com clearOnExecution. É necessário para types que não têm essa flag mas precisam de output limpo.
  • clearObjects processa nodesBox para objetos personalizados. Percorre os nós procurando type === 'nodesBox'. Para cada um, acha o UserObject selecionado via data.selectedId na lista objectCallerData, carregada em 1.5. Decide quais itens de text resetar via clearOnExecution por item. Recria sessions se necessário.
  • onMutateObjectCallerData no fim. Após todo o processamento, chama o callback do closure de 1.5 (onMutateObjectCallerData(myObjects)) que reatribui objectCallerData no escopo pai. Funciona como flush da mutação.
  • let newFlows = [...updatedFlows] é snapshot raso. Última linha do bloco. Cria um array novo via spread, mas com referências para os mesmos nós. Quem escreve em updatedFlows ou newFlows depois tem o próprio array. Os nós ficam compartilhados.
  • Sem session sync no clearObjects. Diferente do 1.5b, que chamava sessionStateService.clear, o clearObjects só append de entries. Não deleta. Usa sessionStateService.appendEntries quando o nó tem sessionEnabled. Semântica muito diferente do clear do fluxObject.
Contexto. Esta é a última etapa antes de sair da Fase 1 (setup). Após essas duas chamadas e o spread, o loop principal (Fase 3) começa. É a última chance de deixar tudo limpo. Evita leak de estado entre execuções.

🎯 nodesBox. Não confundir com fluxObject
O nodesBox é o nó que lê e escreve um objeto personalizado. O objeto em si é FluxObject (na variável objectCallerData). nodesBox.data.selectedId aponta para o id do objeto que ele controla.
⚠️ appendEntries em vez de clear
Diferente do 1.5b, que fez DELETE, aqui só faz APPEND. O session state cresce a cada execução. Nunca é limpo. Rodar 1000 vezes gera 1000 linhas por object e session. A manutenção fica com sistema externo (cleanup jobs).

D let newFlows = [...updatedFlows] · snapshot raso
flux.service.ts:2825
let newFlows = [...updatedFlows];
Propósito. Cria um segundo array (newFlows) com as mesmas referências de nós que updatedFlows. A partir daqui, os dois arrays podem divergir. Escritas em updatedFlows[i] = ... ou newFlows[i] = ... só afetam o próprio array.
Em resumo. O spread cria um array novo. As referências para os nós dentro são as mesmas. É snapshot estrutural, não profundo. Prática. Se o loop principal (Fase 3) fizer newFlows[i] = { ...newFlows[i], data: { ...} }, cria um nó novo e substitui só em newFlows. O updatedFlows[i] continua apontando para o antigo. Se o loop mutar in-place (newFlows[i].data.x = 'y'), a mutação aparece em updatedFlows[i] também. Mesma referência de objeto. Convenção do apiV2. Quase todos os writes usam spread para criar nó novo. Na prática, os dois arrays divergem sem afetar um ao outro. Por que dois arrays? Historicamente, updatedFlows é o snapshot pré-loop e newFlows é o current durante o loop. Alguns caminhos consultam updatedFlows para conhecer o estado inicial (exemplo: comparar current com initial).

Writes em nós sempre usam spread ({ ...node, data: ... }). Nunca mutação in-place. Assim updatedFlows preserva o estado inicial enquanto newFlows evolui.
📎 let (não const)
let newFlows porque pode ser reatribuído inteiro, não só mutado. Alguns caminhos reatribuem via .map ou substituindo por outro array.
⚠️ Spread não é deep clone
Quem espera isolamento profundo entre updatedFlows e newFlows vai se surpreender. node.data é o mesmo objeto. Mutação in-place vaza.
🔧 Onde newFlows é usado depois
É o array vivo da Fase 3. Passado para o prefetch, o scheduler e os handlers. O updatedFlows pode ser descartado depois (garbage), mas continua referenciado em várias funções auxiliares.
Resumo — o que sai de 1.7b.
• updatedFlows passou pela segunda passada de clearRunOutputForSeed (todos os nós, sem gate).
• objectCallerData reatribuído. Objetos com nodesBox associados têm text resetado por item e sessions atualizadas.

Observações para migração.
• clearRunOutputForSeed e clearStaleNodeOutput são funções puras em node-output-reset.ts. Trivialmente migráveis para o worker.
• O clearObjects é grande (149 linhas) e depende de três coisas. Primeira. objectCallerData passado do 1.5. Segunda. sessionStateService (Postgres). Terceira. O closure onMutateObjectCallerData. Migrar exige repensar a linkage do closure. No worker, cada activity está isolada. Cada mutação de objectCallerData precisaria de round-trip para o backend. Alternativa. O worker mantém o array na memória local do workflow.
• appendEntries (não clear) significa que o session state cresce indefinidamente. Se a lógica for migrada, herde o comportamento. Não transforme em DELETE. Isso quebra a semântica de história das sessions.
• A duplicação de resets (1.7a inline e 1.7b via helper) é tech debt ativa. Consolide em um único caminho antes de migrar.
• newFlows = [...updatedFlows] é convenção. No worker, dá para passar o array direto sem clone se garantir que activities não mutam in-place. O pattern seguro é replicar.
• Prioridade. O clearRunOutputForSeed é fácil e essencial. Evita leak de refs antigas no prompt builder. O clearObjects é mais complexo. Pode ir por último. Se ficar no backend, exige que o worker chame o backend quando nodesBox muta.

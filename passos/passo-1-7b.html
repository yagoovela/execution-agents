Step 1.7b — clearRunOutputForSeed + clearObjects

Block in flux.service.ts:2814-2825. Two final cleanup passes before the loop starts. First. clearRunOutputForSeed is the second reset pass by node type. Also zeroes resolved refs in promptData, contentData and textData. Second. clearObjects resets the custom objects (old fluxObject names) that participate via nodesBox. Ends with the snapshot newFlows = [...updatedFlows].
In short — what this step does
  • Second reset pass via clearRunOutputForSeed. Runs on all nodes, not just those with clearOnExecution. Runs clearStaleNodeOutput. Clears outputObjectNode.text. Zeroes text on any ref inside the promptData, contentData, textData arrays. Redundant with 1.7a for types with clearOnExecution. Necessary for types that don't have that flag but need clean output.
  • clearObjects processes nodesBox for custom objects. Loops through nodes searching for type === 'nodesBox'. For each, finds the UserObject selected via data.selectedId in the objectCallerData list, loaded in 1.5. Decides which text items to reset via per-item clearOnExecution. Recreates sessions if needed.
  • onMutateObjectCallerData at the end. After all processing, calls the 1.5 closure callback (onMutateObjectCallerData(myObjects)) that reassigns objectCallerData in the parent scope. Works as a mutation flush.
  • let newFlows = [...updatedFlows] is a shallow snapshot. Last line of the block. Creates a new array via spread, but with references to the same nodes. Whoever writes to updatedFlows or newFlows afterwards has their own array. The nodes remain shared.
  • No session sync in clearObjects. Unlike 1.5b, which called sessionStateService.clear, clearObjects only appends entries. Does not delete. Uses sessionStateService.appendEntries when the node has sessionEnabled. Very different semantics from the fluxObject clear.
Context. This is the last stage before leaving Phase 1 (setup). After these two calls and the spread, the main loop (Phase 3) starts. It is the last chance to leave everything clean. Prevents state leak between executions.

A clearRunOutputForSeed(node)
node-output-reset.ts:173-192 (impl) + flux.service.ts:2814 (call)
export function clearRunOutputForSeed<T>(node: T): T
Purpose. Second reset pass. Calls clearStaleNodeOutput, which handles the 7 types listed in 1.7a. Additionally zeroes text: '' on any ref-object inside promptData, contentData and textData. Exists to cover cases the 1.7a clearOnExecution gate does not cover.
In short. After the extensive 1.7a .map that already reset everything with clearOnExecution, this function passes again on every node. Difference. Does not depend on the clearOnExecution gate. Always handles. First it calls clearStaleNodeOutput, which is the clean and correct version of the 1.7a inline logic. Resets text, canceled, response, errorMessage, errorStatusCode and jsonRequestBody for the same 7 types. Then does an extra pass. If it is outputObjectNode, forces data.text = ''. Redundant with 1.7a A, but acceptable. The most relevant point. Iterates the 3 arrays promptData, contentData and textData. They are arrays of resolved references, used by the prompt builder to hold snapshots of upstream node values. Zeroes text: '' on each ref. This prevents the prompt builder from reading old text from refs cached in the node. This second pass is necessary because clearOnExecution is opt-in per node. Without it, a node without the flag would keep old refs.

🎯 No clearOnExecution gate
clearStaleNodeOutput does not test clearOnExecution. Always runs the reset if the type is in the list. Safe to call on every node.
📎 Refs in promptData/contentData/textData
These arrays hold resolved snapshots of upstream values. Example. A commandTextNode has promptData: [{id, name, text: 'resolved value'}, ...]. The clear zeroes only text. Keeps id and name.
⚠️ Duplication with 1.7a
For the 7 types with clearOnExecution, 1.7a already reset them. Now clearStaleNodeOutput resets them again. Idempotent. Does not break, but it is wasteful. A refactor should consolidate everything into a single pass.

Second pass gain. Catches nodes without clearOnExecution that still need clean output for the prompt builder seed.

B this.clearObjects({ ... })
flux.service.ts:2816-2823 (call) + 9411-9559 (impl)
async clearObjects({ objectCallerData, nodes, onMutateObjectCallerData, spaceId, user, sessionId })
Purpose. Resets the custom objects loaded in 1.5. Loops through nodes searching for type === 'nodesBox'. Finds the associated object via data.selectedId. Decides which text items to reset via {itemId}clearOnExecution flags. Recreates and updates the object's sessions.
In short. After resetting the nodes themselves, this function resets the custom objects. They are named data structures (like "Small Memory") that nodesBox reads from and writes to. The function is long (149 lines). Step by step. First. Starts with myObjects = [...objectCallerData]. Shallow copy of the array loaded in 1.5. If empty, returns early. Second. Loop through nodes searching for nodesBox. For each, finds the selected object via data.selectedId. If not found (deleted in the editor), runs continue. Third. If sessionEnabled, creates or updates the default session when it does not exist (backfill). Then populates selectedObject.text with the content of the selected session. Alternative. If the session does not exist, creates a new one with all text zeroed. Fourth. Filters uniqueTextElements by id. Applies the per-item clear (key {itemId}clearOnExecution in nd.data). Builds findItem. Fifth. Updates selectedObject.sessions with findItem on the active session. Sixth. Replaces the object in myObjects. Seventh. If session is on, calls sessionStateService.appendEntries. Not clear, only append. Writes the snapshot as a new entry in the session state. Eighth. After the loop, calls onMutateObjectCallerData(myObjects). Observation. The function aggregates instead of fully clearing. Always rewrites the entire sessions with the new findItem. Never deletes rows from the session state. Unlike 1.5b, which ran sessionStateService.clear.

🎯 nodesBox. Do not confuse with fluxObject
nodesBox is the node that reads from and writes to a custom object. The object itself is FluxObject (in the objectCallerData variable). nodesBox.data.selectedId points to the id of the object it controls.
⚠️ appendEntries instead of clear
Unlike 1.5b, which did DELETE, here it only does APPEND. Session state grows with every execution. Never cleared. Running 1000 times generates 1000 rows per object and session. Maintenance is left to an external system (cleanup jobs).
⚠️ Dynamic keys. Footgun
nd.data[item.id + 'clearOnExecution']. Key built by concat. If item.id has unexpected characters, it builds an invalid key. No validation.
🔧 Default session backfill
L9442-9461. If the default session does not exist but sessionEnabled is on, creates one with the current content before processing. Lazy migration from the old format to the new one.

D let newFlows = [...updatedFlows] · snapshot raso
flux.service.ts:2825
let newFlows = [...updatedFlows];
Propósito. Cria um segundo array (newFlows) com as mesmas referências de nós que updatedFlows. A partir daqui, os dois arrays podem divergir. Escritas em updatedFlows[i] = ... ou newFlows[i] = ... só afetam o próprio array.
Em resumo. O spread cria um array novo. As referências para os nós dentro são as mesmas. É snapshot estrutural, não profundo. Prática. Se o loop principal (Fase 3) fizer newFlows[i] = { ...newFlows[i], data: { ...} }, cria um nó novo e substitui só em newFlows. O updatedFlows[i] continua apontando para o antigo. Se o loop mutar in-place (newFlows[i].data.x = 'y'), a mutação aparece em updatedFlows[i] também. Mesma referência de objeto. Convenção do apiV2. Quase todos os writes usam spread para criar nó novo. Na prática, os dois arrays divergem sem afetar um ao outro. Por que dois arrays? Historicamente, updatedFlows é o snapshot pré-loop e newFlows é o current durante o loop. Alguns caminhos consultam updatedFlows para conhecer o estado inicial (exemplo: comparar current com initial).

Writes em nós sempre usam spread ({ ...node, data: ... }). Nunca mutação in-place. Assim updatedFlows preserva o estado inicial enquanto newFlows evolui.
📎 let (não const)
let newFlows porque pode ser reatribuído inteiro, não só mutado. Alguns caminhos reatribuem via .map ou substituindo por outro array.
⚠️ Spread não é deep clone
Quem espera isolamento profundo entre updatedFlows e newFlows vai se surpreender. node.data é o mesmo objeto. Mutação in-place vaza.
🔧 Onde newFlows é usado depois
É o array vivo da Fase 3. Passado para o prefetch, o scheduler e os handlers. O updatedFlows pode ser descartado depois (garbage), mas continua referenciado em várias funções auxiliares.
Resumo — o que sai de 1.7b.
• updatedFlows passou pela segunda passada de clearRunOutputForSeed (todos os nós, sem gate).
• objectCallerData reatribuído. Objetos com nodesBox associados têm text resetado por item e sessions atualizadas.
• Session state (Postgres). Novas entries appendadas via appendEntries. Não deleta. Cresce.
• newFlows criado como snapshot raso. Array novo, mesmas refs.
• A Fase 1 termina. O próximo passo é a Fase 2 (dispatch).
Observações para migração.
• clearRunOutputForSeed e clearStaleNodeOutput são funções puras em node-output-reset.ts. Trivialmente migráveis para o worker.
• O clearObjects é grande (149 linhas) e depende de três coisas. Primeira. objectCallerData passado do 1.5. Segunda. sessionStateService (Postgres). Terceira. O closure onMutateObjectCallerData. Migrar exige repensar a linkage do closure. No worker, cada activity está isolada. Cada mutação de objectCallerData precisaria de round-trip para o backend. Alternativa. O worker mantém o array na memória local do workflow.
• appendEntries (não clear) significa que o session state cresce indefinidamente. Se a lógica for migrada, herde o comportamento. Não transforme em DELETE. Isso quebra a semântica de história das sessions.
• A duplicação de resets (1.7a inline e 1.7b via helper) é tech debt ativa. Consolide em um único caminho antes de migrar.
• newFlows = [...updatedFlows] é convenção. No worker, dá para passar o array direto sem clone se garantir que activities não mutam in-place. O pattern seguro é replicar.
• Prioridade. O clearRunOutputForSeed é fácil e essencial. Evita leak de refs antigas no prompt builder. O clearObjects é mais complexo. Pode ir por último. Se ficar no backend, exige que o worker chame o backend quando nodesBox muta.

Passo 1.7b — clearRunOutputForSeed + clearObjects

Bloco em flux.service.ts:2814-2825. Duas passadas finais de limpeza antes do loop começar: (1) clearRunOutputForSeed — segunda passada de reset por node type + zerar refs resolvidas em promptData/contentData/textData; (2) clearObjects — reset dos objetos personalizados (fluxObject nomes velhos) que participam via nodesBox. Termina com snapshot newFlows = [...updatedFlows].
Em resumo — o que esse passo faz
  • Segunda pasada de reset via clearRunOutputForSeed: passa em todos os nodes (não só os com clearOnExecution) e roda clearStaleNodeOutput + limpa outputObjectNode.text + zera text em qualquer ref dentro dos arrays promptData, contentData, textData. Isso é redundante com 1.7a pra tipos com clearOnExecution, mas necessário pra tipos que não têm essa flag mas mesmo assim precisam de output limpo.
  • clearObjects processa nodesBox pra objetos personalizados: percorre os nodes procurando type === 'nodesBox'. Pra cada um, acha o UserObject selecionado (via data.selectedId) na lista objectCallerData (carregada em 1.5), decide quais itens de text resetar (via clearOnExecution por item) e re-cria sessions se necessário.
  • onMutateObjectCallerData no fim: depois de todo o processing, chama o callback do closure de 1.5 (onMutateObjectCallerData(myObjects)) que reatribui objectCallerData no escopo pai. É como o "flush" da mutação.
  • let newFlows = [...updatedFlows] — snapshot raso: última linha do bloco. Cria um array novo (spread) mas referências pros mesmos nodes. Quem escreve em updatedFlows ou newFlows depois, cada um tem seu próprio array mas nodes compartilhados.
  • Sem session sync no clearObjects: diferente do 1.5b que chamava sessionStateService.clear, o clearObjects só appenda entries (não deleta) — usa sessionStateService.appendEntries se o node tem sessionEnabled. Semântica muito diferente do fluxObject clear.
Contexto: essa é a última etapa antes de sair da Fase 1 (setup). Depois desses dois calls + o spread, o loop principal (Fase 3) começa. É a última chance de deixar tudo "limpo" pra evitar leakage de estado entre runs.

export function clearRunOutputForSeed<T>(node: T): T
Propósito: Segunda pasada de reset — chama clearStaleNodeOutput (que trata os 7 types listados no 1.7a) e adicionalmente zera text: '' em qualquer ref-object dentro de promptData, contentData, textData. Existe pra pegar casos que o gate clearOnExecution do 1.7a não cobre.
Em resumo: depois do .map gigantesco do 1.7a que já resetou tudo com clearOnExecution, essa função passa de novo em todo mundo. A diferença: não depende do gate clearOnExecution — trata sempre. Primeiro chama clearStaleNodeOutput, que é a versão limpa (e correta) da lógica inline do 1.7a — resetando text, canceled, response, errorMessage, errorStatusCode e jsonRequestBody pros mesmos 7 types. Depois faz uma passada extra: se outputObjectNode, força data.text = '' (redundante com 1.7a A mas ok). E o mais interessante: itera os 3 arrays promptData, contentData, textData — que são arrays de referências resolvidas (usado pelo prompt builder pra guardar snapshots de valores de nodes upstream) — e zera text: '' em cada ref. Isso previne prompt builder ler texto velho de refs "cacheadas" no node. Curiosidade: essa segunda pasada é necessária porque o clearOnExecution é opt-in por node — sem essa, um node sem a flag manteria refs velhas.

🎯 nodesBox — não confundir com fluxObject
nodesBox é o node que lê/escreve um objeto personalizado. O objeto em si é FluxObject (na variável objectCallerData). nodesBox.data.selectedId aponta pro id do objeto que ele controla.

C onMutateObjectCallerData(myObjects) — flush do closure
flux.service.ts:9558 + 2504-2506 (closure def)
onMutateObjectCallerData(myObjects); // callback do closure de 1.5-E
Propósito: Depois de processar todos os nodes no clearObjects, chama uma única vez o callback pra reatribuir objectCallerData no escopo do apiV2. É o "commit" da mutação — sem essa chamada, myObjects ficaria só no escopo do clearObjects.
Em resumo: lembra do closure criado em 1.5-E (onMutateObjectCallerData = data => { objectCallerData = data; })? Aqui é onde ele é chamado pela primeira vez. Como clearObjects trabalha numa cópia local (myObjects), o array original em apiV2 ainda estava com o estado pré-limpeza. Essa linha é o "flush" — passa a lista atualizada pro closure, que reatribui a variável no escopo pai. A partir daqui, quem ler objectCallerData no apiV2 vê a nova versão (com os objetos com text resetado por item + sessions atualizadas). É crítico porque o closure permite bidirectional flow: qualquer nodesBox chamado dentro do loop principal (Fase 3) pode também chamar onMutateObjectCallerData pra propagar suas mudanças pra frente.

D let newFlows = [...updatedFlows] — snapshot raso
flux.service.ts:2825
let newFlows = [...updatedFlows];
Propósito: Cria um segundo array (newFlows) contendo as mesmas referências de nodes que updatedFlows. A partir daqui, os dois arrays podem divergir — quem faz updatedFlows[i] = ... ou newFlows[i] = ... só afeta o próprio array.
Em resumo: spread cria um array novo, mas as referências pros nodes dentro são as mesmas. É um snapshot estrutural, não profundo. Prática: se o loop principal (Fase 3) fizer newFlows[i] = { ...newFlows[i], data: { ...} }, cria um node novo e substitui só em newFlows — updatedFlows[i] continua apontando pro antigo. Se o loop mutar in place (newFlows[i].data.x = 'y'), a mutação aparece em updatedFlows[i] também (mesma referência de objeto). Convenção do apiV2: quase todos os writes usam spread pra criar node novo, então na prática os dois arrays divergem sem afetar um ao outro. Por que dois arrays? Historicamente, updatedFlows é o "snapshot pré-loop" e newFlows é o "current" durante o loop. Alguns caminhos consultam updatedFlows pra saber o estado inicial (ex.: comparar current com initial).

🎯 Convenção do apiV2
Writes em nodes sempre usam spread ({ ...node, data: ... }), nunca mutação in-place. Assim updatedFlows preserva o estado inicial enquanto newFlows evolui.
📎 let (não const)
let newFlows porque pode ser reatribuído inteiro (não só mutado). Alguns caminhos reatribuem via .map ou substituindo por outro array.
⚠️ Spread não é deep clone
Quem esperar isolamento profundo entre updatedFlows e newFlows vai se surpreender: node.data é o mesmo objeto. Mutação in-place vaza.
🔧 Onde newFlows é usado depois
É o "array vivo" da Fase 3 — passado pro prefetch, pro scheduler, pros handlers. updatedFlows pode até ser deletado depois (garbage), mas continua referenciado em várias funções auxiliares.
Resumo — o que sai de 1.7b:
• updatedFlows passou pela segunda pasada de clearRunOutputForSeed (todos os nodes, sem gate)
• objectCallerData reatribuído — objetos com nodesBox associados têm text resetado por item + sessions atualizadas
• Session state (Postgres): novas entries appendadas via appendEntries (não deleta — cresce)
• newFlows criado como snapshot raso — array novo, refs iguais
• Depois disso, Fase 1 termina — próximo passo é a Fase 2 (dispatch)
Observações para migração:
• clearRunOutputForSeed + clearStaleNodeOutput são funções puras em node-output-reset.ts — trivialmente migráveis pro worker.
• clearObjects é grande (149 linhas) e depende de: (a) objectCallerData passado do 1.5, (b) sessionStateService (Postgres), (c) onMutateObjectCallerData closure. Migrar exige repensar a linkage do closure — no worker, cada activity está isolada, então cada mutação de objectCallerData teria que ir via round-trip pro backend, ou o worker precisa manter o array na memória local do workflow.
• appendEntries (não clear!) significa que session state cresce indefinidamente. Se essa lógica for migrada, herdar o comportamento — não transformar em DELETE, senão quebra semântica de "história" das sessions.
• A duplicação de resets (1.7a inline + 1.7b via helper) é tech debt viva. Consolidar em um único caminho antes de migrar.
• newFlows = [...updatedFlows] é convenção — no worker, pode passar array direto sem clone se guaranteed que activities não mutam in-place. Mas o pattern seguro é replicar.
• Prioridade: clearRunOutputForSeed é fácil e essencial (evita leak de refs velhas no prompt builder). clearObjects é mais complexo — pode ir por último, mas se ficar no backend, exige que o worker chame o backend quando nodesBox mutar.

Step 1.4 — Per-space log setup

Conditional block in flux.service.ts:2371-2437. Starts the hierarchical log collector (RunLogCollector) and writes the first row to space_run_logs. Only runs when the space has logging enabled.
In summary — what this step does
  • Decides whether the execution generates a log. Checks four conditions:
    • is a top-level execution (not a sub-flow);
    • the space has logging enabled;
    • runType is neither manual nor chatbot;
    • the flow belongs to a space.
    If any condition fails, the whole step is skipped. The execution proceeds without a record.
  • Freezes the token price. Queries the active plan of the flow's owner. Writes the current fluxTokenPrice into the log document. Same pattern as e-commerce, which saves the unit price in order_item. On error, the value falls back to 0 and execution continues.
  • Builds the root collector. Creates the RunLogCollector in memory as root. Fills the initial metadata:
    • processId;
    • flow;
    • space;
    • org;
    • triggerer;
    • input with secrets redacted;
    • metrics initialized to zero.
    The node tree is appended throughout execution. When logging is disabled, a no-op version is returned. Call-sites don't need any if.
  • Writes the initial row to the database. Writes a row to space_run_logs with status in_progress. The row starts practically empty. This write ensures the execution shows in the dashboard even when the process dies mid-way (OOM, deploy). A later cron marks the execution as error.
  • Wires up the debounced flush. Registers the scheduleUpsert callback with a 2s debounce. Each change to the doc (startNode, endNode, sub-run, finalize) schedules a write. Each schedule resets the timer. The pattern groups N events into roughly 1 write per 2s of activity.
  • Output. The runLogCollector variable is ready for propagation. The initial row in space_run_logs is written. When the gate fails, runLogCollector receives undefined. Phase 3 call-sites use optional chaining.
Context. This step is cross-cutting (observability). It is not essential for the agent execution. When the gate fails, execution continues normally. There is simply no trace in the space_run_logs table.

🎯 Why these 3 conditions?
1. !isNestedRunLog. Avoids duplicate log. When a flow calls another via fluxBox, the log already comes from the root as a nested subRun.

2. loggingEnabled + runType. Respects the space's preference. Ignores interactive modes (manual, chatbot) that pollute the log without value.

3. spaceOwnerId. Without a defined space there's nowhere to persist. The table is indexed by spaceId.

🎯 Why do the initial upsert right in 1.4?
If the execution dies mid-way (SIGKILL, OOM, deploy), the row already exists as in_progress. Without this initial upsert, the execution would disappear if the process died before the first flush.

A later cron job (markStuckRunsAsError) marks orphan executions as error.

E spaceRunLogsService.scheduleUpsert() flush callback
space_run_logs.service.ts:92-120
scheduleUpsert(params: { spaceId, rootFlowId, doc: RunLogDocument }): void
Purpose. Wrapper with a 2-second debounce over upsertRun. It is not called directly in step 1.4. It's configured in (C) as the flush callback. Every change to the collector triggers this flush. Typical changes: startNode, endNode, finalize, sub-runs.
In summary. The function groups writes. Whenever the collector signals a change, the database write doesn't happen immediately. It waits 2 seconds to accumulate new changes. Each new change in that window resets the timer. An execution with 50 nodes firing rapid events becomes roughly 1 write per 2s of activity instead of 50 consecutive writes. The cost is the risk of losing up to 2s of progress when the process dies between two debounces. The initial upsertRun from step 1.4 mitigates this risk. It ensures the row already exists. To avoid loss at finalization, the final step calls the flushNow() variant. flushNow bypasses the debounce and writes immediately.

⏱️ Why a 2s debounce?
An agent may have dozens of nodes firing startNode and endNode in seconds. Without debounce it would be more than 50 writes per execution.

With debounce, the pattern becomes roughly 1 write per 2s of activity. Plus one final write via flushNow at finalization.
⚠️ Trade-off: loss on crash
If the process dies between two debounces, the last 2s of progress are lost. Only the previous snapshot is persisted. That's why the initial upsertRun in step 1.4 matters. It ensures the row exists.

Finalization (Phase 4) calls flushNow() without debounce. It cancels the pending flush and writes immediately.
🔧 pendingFlushes
Map<processId, { timer, spaceId, rootFlowId, doc }>

Holds scheduled writes in memory. If the process dies, the map dies with it.
🔧 OnModuleDestroy
The service implements OnModuleDestroy to flush all pending writes during NestJS graceful shutdown. Doesn't help in a forced crash.
Summary — what comes out of 1.4 when the gate passes:
  • runLogCollector instantiated as root. Contains rootDoc in memory and flushFn wired to scheduleUpsert.
  • An initial row in space_run_logs with status = 'in_progress' and empty node tree.
  • From here on, each startNode, endNode, subRun and finalize mutates the doc and schedules a debounced write.
  • The resolved fluxTokenPrice stays frozen in the doc. Does not change during execution.
  • If the gate fails, runLogCollector receives undefined. Phase 3 call-sites use if (runLogCollector) ... or optional chaining.
Notes for migration:
  • This block is cross-cutting. It must happen before the main loop. That way steps 3.4 (startNode), 3.9 (endNode) and 4.4 (finalize) already have the collector ready.
  • RunLogCollector is an in-memory structure. Follows the same pattern as nodeSubstitutionSchema: mutates throughout the loop. If orchestration lives on the worker, the worker keeps its own tree or does partial updates via API back to the backend.
  • The 2s debounce is per process. If orchestration splits between backend and worker, each has its own pendingFlushes. Writeback may run concurrently.
  • Nothing here is essential for execution correctness. It's observability. Can be migrated last in the plan.

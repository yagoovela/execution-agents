Passo 1.4 — Setup de log por espaço

Bloco condicional em flux.service.ts:2371-2437. Inicia o coletor hierárquico de logs (RunLogCollector) e grava a primeira linha em space_run_logs. Executa apenas quando o space tem logging habilitado.
Em resumo — o que esse passo faz
  • Decide se a execução gera log. Verifica quatro condições:
    • é execução de topo (não é sub-fluxo);
    • o space tem logging habilitado;
    • o runType não é manual nem chatbot;
    • o flow pertence a um space.
    Se qualquer condição falhar, o passo inteiro é descartado. A execução prossegue sem registro.
  • Congela o preço do token. Consulta o plano ativo do dono do flow. Grava o fluxTokenPrice atual no documento do log. Segue o mesmo padrão de e-commerce, que salva o preço unitário em order_item. Em caso de erro, o valor cai para 0 e a execução prossegue.
  • Monta o coletor raiz. Cria em memória o RunLogCollector como raiz. Preenche a metadata inicial:
    • processId;
    • flow;
    • space;
    • org;
    • responsável pelo disparo;
    • entrada com segredos ofuscados;
    • métricas zeradas.
    A árvore de nós é anexada ao longo da execução. Quando o logging está desativado, devolve uma versão no-op. Os call-sites não precisam de if.
  • Grava a linha inicial no banco. Escreve uma linha em space_run_logs com status in_progress. A linha nasce praticamente vazia. Esse write garante que a execução aparece no dashboard mesmo quando o processo morre no meio (OOM, deploy). Um cron posterior marca a execução como erro.
  • Conecta o flush debounced. Registra o callback scheduleUpsert com debounce de 2s. Cada mudança no doc (startNode, endNode, sub-run, finalize) agenda um write. Cada agendamento reseta o timer. O padrão agrupa N eventos em cerca de 1 write a cada 2s de atividade.
  • Saída. A variável runLogCollector fica pronta para propagação. A linha inicial em space_run_logs fica gravada. Quando o gate falha, runLogCollector recebe undefined. Os call-sites da Fase 3 usam optional chaining.
Contexto. Este passo é cross-cutting (observabilidade). Não é essencial para a execução do agente. Quando o gate falha, a execução continua normalmente. Apenas não há trace na tabela space_run_logs.

🎯 Por que essas 3 condições?
1. !isNestedRunLog. Evita log duplicado. Quando um flow chama outro via fluxBox, o log já vem da raiz como subRun aninhado.

2. loggingEnabled + runType. Respeita a preferência do space. Ignora modos interativos (manual, chatbot) que poluem o log sem valor.

3. spaceOwnerId. Sem space definido não há onde persistir. A tabela é indexada por spaceId.

🎯 Por que fazer o upsert inicial já em 1.4?
Se a execução falhar no meio (SIGKILL, OOM, deploy), a linha já existe em in_progress. Sem esse upsert inicial, a execução desapareceria quando o processo morresse antes do primeiro flush.

Um cron job posterior (markStuckRunsAsError) marca execuções órfãs como erro.
📊 Colunas indexáveis vs blob

Essas colunas alimentam queries de listagem e filtro. O doc inteiro fica em logData JSONB. Só é carregado quando o usuário abre a execução individual.

E spaceRunLogsService.scheduleUpsert() callback do flush
space_run_logs.service.ts:92-120
scheduleUpsert(params: { spaceId, rootFlowId, doc: RunLogDocument }): void
Propósito. Wrapper com debounce de 2 segundos sobre upsertRun. Não é chamado diretamente no passo 1.4. Está configurado em (C) como callback flush. Cada mudança no coletor chama esse flush. Mudanças típicas: startNode, endNode, finalize, sub-runs.
Em resumo. A função agrupa writes. Sempre que o coletor sinaliza uma mudança, o write no banco não acontece na hora. Ele aguarda 2 segundos para acumular novas mudanças. Cada mudança nova nesse intervalo reseta o timer. Uma execução com 50 nós disparando eventos rápidos vira cerca de 1 write a cada 2s de atividade em vez de 50 writes consecutivos. O custo é o risco de perder até 2s de progresso quando o processo morre entre dois debounces. O upsertRun inicial do passo 1.4 mitiga esse risco. Garante que a linha já existe. Para evitar a perda na finalização, o passo final chama a variante flushNow(). flushNow dispensa o debounce e escreve imediatamente.

⏱️ Por que debounce de 2s?
Um agente pode ter dezenas de nós disparando startNode e endNode em segundos. Sem debounce seriam mais de 50 writes por execução.

Com debounce, o padrão vira cerca de 1 write a cada 2s de atividade. Mais um write final via flushNow na finalização.
⚠️ Trade-off: perda em crash
Se o processo morrer entre dois debounces, os últimos 2s de progresso se perdem. Apenas o snapshot anterior fica gravado. Por isso o upsertRun inicial do passo 1.4 é importante. Ele garante que a linha existe.

A finalização (Fase 4) chama flushNow() sem debounce. Cancela o pending flush e escreve imediatamente.
🔧 pendingFlushes
Map<processId, { timer, spaceId, rootFlowId, doc }>

Mantém os writes agendados em memória. Se o processo morrer, o mapa desaparece com ele.
🔧 OnModuleDestroy
O serviço implementa OnModuleDestroy para dar flush em todos os pending durante o encerramento graceful do NestJS. Não ajuda em crash forçado.
Resumo — o que sai de 1.4 quando o gate passa:
  • runLogCollector instanciado como raiz. Contém rootDoc em memória e flushFn conectado ao scheduleUpsert.
  • Uma linha inicial em space_run_logs com status = 'in_progress' e árvore de nós vazia.
  • A partir daqui, cada startNode, endNode, subRun e finalize muta o doc e agenda um write debounced.
  • O fluxTokenPrice resolvido fica congelado no doc. Não muda durante a execução.
  • Se o gate falhar, runLogCollector recebe undefined. Os call-sites da Fase 3 usam if (runLogCollector) ... ou optional chaining.
Observações para migração:
  • Este bloco é cross-cutting. Precisa acontecer antes do loop principal. Assim os passos 3.4 (startNode), 3.9 (endNode) e 4.4 (finalize) já têm o coletor pronto.
  • O RunLogCollector é uma estrutura in-memory. Segue o mesmo padrão do nodeSubstitutionSchema: muta ao longo do loop. Se a orquestração for no worker, o worker mantém a própria árvore ou faz update parcial via API para o backend.
  • O debounce de 2s é por processo. Se a orquestração se divide entre backend e worker, cada um tem o próprio pendingFlushes. O writeback pode ficar concorrente.
  • Nada aqui é essencial para a correção da execução. É observabilidade. Pode ser migrado por último no plano.

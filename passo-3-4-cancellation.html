Cancellation check — feature flag NODE_CANCEL_IN_FLIGHT

Bloco espalhado em flux.service.ts:3184-3194 (setup), 3229-3239 (check entre nós), 3251-3269 (start watch por nó) e 4516-4530 (finish quando abortado). Sistema que permite o usuário cancelar um run em execução — hoje só habilitado pra runType='canvas'.
Contexto: este é o único passo do diagrama novo pós-doc — não existia na versão original documentada. Foi adicionado depois pra atender o botão "cancelar" no editor. Funciona em dois níveis: (1) checagem entre nós (sempre que watchEnabled=true); (2) checagem durante o nó via AbortSignal em fetch/axios (só quando feature flag NODE_CANCEL_IN_FLIGHT_FLAG está ligada).
Cadeia do sistema de cancellation
AshouldWatchCancellation + runKey → BisCancelRequested (check entre nós) → CstartNodeCancelWatch (in-flight) → DnodeCancelContext (AbortSignal) → EfinishCancelledNode
Resultado quando cancelado: stoppedByCancel=true, break do loop, nó fica com executionStatus='CANCELLED' em node_executions, WebSocket avisa o cliente. Sem cancel: prossegue normalmente pro passo 3.5.
A shouldWatchCancellation + resolveCancelRunKey
executions_logs/run-cancellation.service.ts:19-24 · flux/cancel-run-key.ts:1-6
cancelWatchEnabled = shouldWatchCancellation({ runType, isNestedRun }) · cancelRunKey = resolveCancelRunKey({ runLogProcessId, parentRunId })
Propósito: Setup uma vez por run, antes do while começar. Decide se o run é elegível pra watchar cancelamento e qual chave usar pra consultar o status (parentRunId em runs aninhados, processId próprio caso contrário).
Em resumo: é o porteiro que responde três perguntas antes do run começar: (1) "esse tipo de run permite cancelar?" — só canvas (do editor) permite; API, chatbot, form, batch, webhook não. É intencional: request-response síncrono não faz sentido cancelar do lado servidor sem o cliente pedir. (2) "esse é um sub-run herdando de um pai?" — se sim, herda watch do pai. Cancelar o pai propaga pra todos os filhos. (3) "qual chave usar pra consultar cancelamento?" — se é nested, usa o id do root (todos os filhos consultam a mesma chave e cancelam juntos). Se é top-level, usa o próprio processId. Depois vem a segunda camada: mesmo com watch habilitado, só se a feature flag NODE_CANCEL_IN_FLIGHT_FLAG tiver ligada é que o cancel durante a execução do nó funciona (polling + AbortSignal). Sem a flag, só checa cancel entre nós — um LLM streaming a resposta continua até terminar, mesmo se o usuário clicou "cancelar". A flag tá desligada em produção hoje, o que sugere: (a) o sistema é novo e ainda não passou em bateria de testes em larga escala, ou (b) o custo de rodar 60 setIntervals paralelos em runs grandes ainda tá sendo avaliado.

🎯 Por que só canvas cancela?
Runs de API (runType='api') tem semântica "request-response" — o cliente já está esperando síncrono. Cancelar do lado servidor sem cliente pedir seria confuso.

Já canvas é execução no editor: o usuário clica "cancelar" e espera parada real.
📎 Nested herda watch
Um fluxBox/libraryNode chama apiV2 recursivamente pro sub-flow. Como isNestedRun=true, o watch é habilitado no filho também. Assim, cancelar o pai propaga: filho consulta a mesma cancelRunKey (pai) e vê o cancel request.
🔧 Feature flag stringly-typed
'node_cancel_in_flight' como string literal em NODE_CANCEL_IN_FLIGHT_FLAG. Rollout gradual — dá pra ativar por espaço/user via featureFlagsService. Setup padrão: OFF em produção (hoje).
B runCancellationService.isCancelRequested(runId)
executions_logs/run-cancellation.service.ts:62-79 · flux.service.ts:3229-3239
async isCancelRequested(runId: string): Promise<boolean> · check no topo do while
Propósito: Checagem entre nós — no início de cada iteração do while, consulta se algum cliente pediu cancel. Se sim, seta stoppedByCancel=true e break. Não interrompe nó em execução — só evita começar o próximo.
Em resumo: é um vigia no batente da porta do próximo nó. Antes de deixar cada nó entrar em execução, o vigia dá uma olhada na "lista de cancelamento" (tabela flow_run_states). Se o runId do agente atual tá lá, ele fecha a porta: stoppedByCancel = true e break — o nó nem começa a rodar. É deliberadamente polido: não interrompe nada em execução, só previne o próximo. Se o usuário clicou "cancelar" enquanto um textGenerator tá streaming, esse vigia só age depois que o streaming terminar. Pra interromper mid-execution precisa do watch in-flight (fn C). Como não vale a pena consultar Postgres a cada 100ms num run com 100 nós rápidos, o service tem um cache in-memory com TTL de 1500ms — se você consultou faz menos de 1.5s, retorna o resultado do cache sem hit no banco. O usuário pode ter até 1.5s de atraso entre clicar "cancelar" e ver efeito, mas isso é indistinguível de latência normal de UI. Se cancel é confirmado, o cleanup vai pra Fase 4 normal (não vira erro), o run termina com status cancelado, e o cliente vê a mensagem apropriada.

🎯 Cache TTL=1500ms
Evita hammer no Postgres em runs longos com muitos nós. Trade-off: pode demorar até 1.5s pro cancel ser observado. Aceitável pra UX de "cancelar" — o usuário não nota diferença entre 200ms e 1500ms.
⚠️ Cancel entre nós ≠ abort do nó atual
Se um textGenerator está streaming resposta e o usuário clica cancelar durante o streaming, esta checagem não interrompe — só evita começar o próximo nó. Pra interromper mid-execution, precisa do watch in-flight (fn C) + fetch/axios interceptors (fn D).
🔧 Como o cancel é setado
POST /executions_logs/runs/:runId/cancel chama executionsLogsService.requestRunCancellation(user, runId) que:
• Valida permissões e status (só canvas, run must be running)
• Chama runCancellationService.requestCancel({ runId, flowId, userId })
• INSERT em flow_run_states
• interruptStepsInFlight(runId) pra abort imediato
C startNodeCancelWatch({ runId, nodeId, isCancelRequested })
flux/node-cancel-watch.ts:56-93 · flux.service.ts:3251-3261
shouldStartNodeCancelWatch({ watchEnabled, inFlightEnabled }) ? startNodeCancelWatch({...}) : null
Propósito: Se ambos watchEnabled e inFlightEnabled forem true, cria um watcher POR NÓ que faz polling a cada 2s (CANCEL_POLL_MS=2000) pra isCancelRequested. Quando detectar cancel, chama controller.abort() no AbortController que foi entregue via cancelWatch.entry.
Em resumo: se o vigia da porta (fn B) é passivo, esse é o vigia dentro da sala. Durante o nó rodar, esse watcher fica batendo no relógio a cada 2 segundos perguntando "e agora, cancelaram?". Quando a resposta é sim, ele puxa a corda do sino — controller.abort() — e um AbortSignal vai correndo por todos os fetch/axios em andamento dentro daquele nó, fazendo cada um levantar AbortError. É como um alarme cooperativo: as chamadas HTTP escolhem respeitar o signal (padrão web moderno). O watcher devolve 3 coisas pro loop: entry (o AbortSignal + metadata pra ser injetado na ALS nodeCancelContext), wasAborted() (função que o loop chama depois pra saber se rolou abort), e stop() (pra limpar o setInterval quando o nó termina — sem isso, timers vazam). Ponto crítico de perf: um agente com 100 nós tem 100 setIntervals rodando ao mesmo tempo, cada um consultando Postgres (com cache 1.5s ainda dá ~66 queries/segundo). É por isso que a feature flag tá OFF em prod hoje. Solução real e definitiva vai vir com Temporal — WorkflowHandle.cancel() nativo, sem polling, sem timer, sem custo constante.
// flux/node-cancel-watch.ts:56-93 — resumo export function shouldStartNodeCancelWatch(params) { return params.watchEnabled && params.inFlightEnabled; } export function startNodeCancelWatch(params) { const controller = new AbortController(); let aborted = false; const timer = setInterval(async () => { if (await params.isCancelRequested(params.runId)) { aborted = true; controller.abort(); clearInterval(timer); } }, CANCEL_POLL_MS); return { entry: { signal: controller.signal, runId, nodeId }, wasAborted: () => aborted, stop: () => clearInterval(timer), }; }

⚠️ setInterval por nó = memory footprint
Se um agente tem 100 nós, isso é 100 setIntervals de 2s executando em paralelo. Cada um chama isCancelRequested — que tem cache de 1500ms, então mesmo assim vira 66 queries/segundo no Postgres.

Talvez seja um dos motivos da feature flag estar OFF em prod hoje.
🎯 Watch é PER-NODE, não per-run
Cada iteração do while cria um novo watcher com um novo AbortController. Isso porque cada nó tem seu próprio async chain e precisa do próprio AbortSignal pra interceptors de fetch/axios.
🔧 CANCEL_POLL_MS
Constante em node-cancel-watch.ts. Valor 2000ms — customizável via param pollMs do startNodeCancelWatch. Backend hardcoda 2s no call site.
D nodeCancelContext (AsyncLocalStorage<AbortSignal>)
flux/node-cancel-watch.ts:19-21 · node-cancel-fetch.ts:17-35 · node-cancel-interceptor.ts:21-30
export const nodeCancelContext = new AsyncLocalStorage<NodeCancelEntry | undefined>()
Propósito: Mesmo pattern de chargeContext: ALS que carrega o AbortSignal do nó atual. Wrappers globais de fetch e axios leem essa ALS e injetam o signal em toda chamada HTTP feita pelo handler do nó — cooperativa via AbortController.
Em resumo: se o chargeContext é um crachá invisível de "quem tá cobrando", o nodeCancelContext é um crachá invisível de "quem tem alarme de cancelamento". Mesmo mecânica: AsyncLocalStorage injetada antes do handler rodar. A diferença é quem consome: em vez de service de billing, são interceptors globais de fetch e axios — funções que envolvem window.fetch e o instance do axios pra que, antes de cada request HTTP feito pelo handler, elas leem o signal da ALS e o injetam no init.signal da chamada. Fetch e axios nativos respeitam AbortSignal — se aborta, levanta AbortError. Elegância: o handler nem precisa saber que existe cancel. Ele chama fetch('https://api.openai.com/...') normalmente e, se o watch abortou, esse fetch levanta AbortError como se fosse timeout. O try do loop pega isso em if (cancelWatch?.wasAborted()) e chama finishCancelledNode. Fragilidade: é cooperativa. Se o handler fizer SQL síncrono pesado ou cálculo em memória sem I/O, o abort não interrompe nada — só a próxima chamada HTTP. Não é preemptivo. Também: em sub-runs, o loop faz nodeCancelContext.run(undefined, ...) pra desligar o contexto do parent — se algo escapar dessa scope, um handler pode ver undefined e o abort silencia.

↳ Consumo: node-cancel-interceptor.ts:21-30 (axios interceptor)

🎯 Cooperativa, não hard-kill
AbortSignal sinaliza. Fetch/axios respeitam e levantam AbortError. Mas se um handler fizer SQL query direto ou cálculo síncrono pesado, o abort não interrompe — só a próxima chamada HTTP.

Não é preemptivo. É o que Node.js single-threaded pode oferecer sem worker_threads.
⚠️ Nested resets pra undefined
Em runs aninhados, o loop faz nodeCancelContext.run(undefined, ...) em algumas call sites (flux.service.ts:5612, 5977). Isso é intencional — sub-run tem seu próprio watcher. Mas se algo escapar dessa scope, um handler pode ver undefined e desligar o abort. Fragilidade que precisa de teste.

E finishCancelledNode({ ... })
flux.service.ts:2056-2107 · call site 4516-4530
await this.finishCancelledNode({ execId, node, flowId, myUpdatedNodes, schedState, userId, runType, elapsedMs, abortObserved, inFlightEnabled });
Propósito: Cleanup e persistência do estado cancelado. Chamado depois do handler retornar (após AbortError). Limpa erros que possam ter sido setados pelo abort, marca executionStatus='CANCELLED' no node_executions, dispara WebSocket avisando o cliente, e marca no scheduler pra parar o loop.
Em resumo: é o encerrador que faz o cleanup depois que o alarme tocou. Quando o watch aborta e o fetch/axios levanta AbortError, o handler retorna deixando o nó num estado meio confuso — pode ter escrito errorMessage no node.data ("network error"), pode ter output parcial, pode ter deixado sujeira. Essa função vem depois pra limpar: (1) zera os campos de erro — cancel não é erro pra UX, tem que ser tratado como estado próprio (cinza, não vermelho); (2) UPDATE em node_executions setando executionStatus='CANCELLED' e cancelledAt=NOW() — audit trail preciso; (3) dispara WebSocket pra o cliente atualizar a UI em tempo real ("esse nó foi cancelado"); (4) marca o nó no scheduler pra Fase 4 não achar como "não processado"; (5) seta stoppedByCancel = true e break — sai do while imediatamente. A Fase 4 então fecha o run com status "cancelado limpo", não com erro. Também guarda métricas: elapsedMs (quanto o nó rodou antes de ser cancelado) e abortObserved (se o cancel foi observado pelo in-flight ou só entre nós) — servem pra telemetria e pra medir a eficácia do sistema em produção. Só quebra o loop desse nível — se é sub-run, o parent precisa também detectar o cancel na sua próxima iteração.
// flux.service.ts:4516-4530 — call site if (cancelWatch?.wasAborted()) { await this.finishCancelledNode({ execId: runLogProcessId, node, flowId, myUpdatedNodes, schedState, userId: user.id, runType, elapsedMs: Date.now() - nodeStartedAtMs, abortObserved: Boolean(cancelWatch?.wasAborted()), inFlightEnabled, }); stoppedByCancel = true; break; }
↓
🪜 finishCancelledNode faz
1 Limpa errorMessage / errorStatusCode em node.data nulls out — cancel não é erro
2 recordLegacyNodeCancelled(...) UPDATE node_executions SET executionStatus='CANCELLED', cancelledAt=NOW()
3 emitNodeStatus (WebSocket) notifica cliente com status cancelado
4 Marca no scheduler completed/dead pra Fase 4 não achar como pending
5 stoppedByCancel = true; break sai do while imediatamente
🎯 Cancel ≠ erro
Um nó cancelado não vira nó com errorMessage. A Fase 4.5 (preparação de erro amigável) NÃO deve reportar "execution failed at node X" quando o motivo foi cancel. Por isso finishCancelledNode explicitamente limpa os campos de erro antes de persistir.

UI diferencia visualmente: cancelado = cinza / grayed out, erro = vermelho.
📎 elapsedMs vai pra telemetria
elapsedMs = Date.now() - nodeStartedAtMs — usa o timer marcado em 3.2. Vai pro log de cancelamento pra métricas ("quanto tempo o nó rodou antes de ser cancelado").
⚠️ Só quebra o loop deste nível
Se este é um sub-run (nested), o break só sai do while do sub-run. O caller (fluxBox handler no parent) recebe o retorno e precisa lidar com o cancel também. Hoje o parent ainda checa isCancelRequested na sua próxima iteração e cancela também.
🔧 abortObserved param
Diferencia cancel observado pelo watch in-flight (fetch/axios levantou AbortError) vs cancel só detectado entre nós. Vai pra telemetria — mede a eficácia do in-flight.
Resumo — o que sai do Cancellation check:
• Caminho feliz (sem cancel): 100% no-op, passa direto pro passo 3.5
• Cancel entre nós detectado: stoppedByCancel=true, break, sem executar nó
• Cancel durante nó: AbortError propaga, handler retorna, finishCancelledNode registra em node_executions, WebSocket, break
• Fase 4 depois vê: stoppedByCancel não vira erro fatal; run termina "cancelado" limpo
Observações para migração:
• Sistema é novo — foi adicionado depois do doc original. Ainda tem partes marcadas com feature flag OFF (NODE_CANCEL_IN_FLIGHT_FLAG). Pode não estar totalmente estável pra produção — validar antes de migrar.
• Base do cancel (via Postgres poll + WebSocket + status column) é portável. Mas nodeCancelContext é ALS — não funciona quando o handler roda no worker (outro processo). O worker teria que ter seu próprio mecanismo (Temporal já suporta workflow cancel nativamente via WorkflowHandle.cancel()).
• Ideal na migração: alinhar cancel do backend com cancel nativo do Temporal. Backend chama handle.cancel() quando isCancelRequested=true, worker respeita via Context.current().cancelled. Muito mais robusto que polling + AbortSignal.
• Setinterval por nó (60 nós = 60 timers × 500ms cada, hoje 2s) é fonte de CPU/BD. Se ficar ligado por padrão sem otimização, vira ofensor de perf.
• É cross-cutting e opt-in. Pode ficar pra depois no plano de migração — a migração pro Temporal por si só dá cancel semântica quase de graça via workflowHandle.cancel(). Priorizar isso depois do worker migrar.
• Cache de 1500ms + poll de 2000ms tem race condition latente: pode ter até 3.5s de delay entre o clique e o cancel efetivo. Aceitável mas documentar.

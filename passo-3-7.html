Passo 3.7 — Contabilidade token/custo por nó

Bloco em flux.service.ts:2280-2283 (closure), 3248-3249 (snapshot antes), 3296-3297 (2ª leitura), 4537-4546 (delta no endNode). Sem tabela, sem service — pura aritmética em variáveis globais do run + closure de mutação.
Em resumo — o que esse passo faz
  • Contabiliza gasto de tokens e custo por nó: pura aritmética em cima de variáveis globais do run (totalTokensUsed, totalCost). Sem service, sem tabela — só duas variáveis vivendo no escopo do apiV2().
  • Closure onUpdateTokens pra path legacy: uma "caixinha de troco" passada como arg pros handlers legacy (LLM, imagem, áudio, embedding); cada handler grita onUpdateTokens(delta, cost) e a closure soma nos acumuladores. Funciona porque Node.js é single-threaded — sem lock, sem race.
  • Delta por nó via snapshot antes/depois: no início do try do nó, guarda genericTokensBefore = totalTokensUsed; depois do handler, calcula delta = valor atual − snapshot. O delta vai pro RunLogNode em 3.9. Robusto enquanto não há paralelismo entre nós.
  • AsyncLocalStorage pra propagação implícita: chargeContext injeta { execId, nodeId } na ALS antes do handler; quando o ProductService.updateTokens (compartilhado com API pública) insere row em token_transactions, ele consulta a ALS pra saber a qual nó atribuir a cobrança.
  • Path Temporal usa HTTP + SUM no banco: handlers no worker não podem tocar a closure (outro processo); então cobram via /worker/charge-tokens, e o backend, no retorno de processNodeViaTemporal, chama sumChargesByExecution(execId, nodeId) pra agregar do banco e somar em totalTokensUsed. Overhead per-node de HTTP+SQL, mas garante consistência entre paths.
  • Saída: totalTokensUsed/totalCost refletindo consumo pós-nó; delta atribuído ao RunLogNode; row em token_transactions gravada como audit trail; dois mecanismos convergindo numa única fonte de verdade em memória.
Contexto: billing é cross-cutting (memória [[project_execution_architecture]]). O total do run vive em totalTokensUsed/totalCost — mutados por callback quando chamadas de LLM/API/embedding cobram tokens. Já o delta por nó é calculado por diferença antes/depois. Duas fontes possíveis: (i) handlers legacy chamam onUpdateTokens(delta, cost) direto; (ii) handlers Temporal cobram via HTTP /worker/charge-tokens e depois sumChargesByExecution(execId, nodeId) agrega do banco.

AonUpdateTokens (closure)
flux.service.ts:2280-2283
const onUpdateTokens = (tokensUsed: number, cost: number) => { totalTokensUsed += tokensUsed; totalCost += cost; };
Propósito: Callback closure criado no início de apiV2(). Passado por argumento pra todos os handlers legacy que fazem cobrança (LLM, embedding, etc.). Cada handler chama onUpdateTokens(delta, cost) após cada operação cobrada — a closure muta as variáveis do escopo pai.
Em resumo: pensa nele como uma caixinha de troco que fica em cima da mesa do apiV2(). Toda vez que um handler gasta tokens (chamou o LLM, gerou embedding, transcreveu áudio), ele grita "gastei 300 tokens, 0.002 dolar!" chamando onUpdateTokens(300, 0.002). A closure aceita e soma nos acumuladores globais do run. Como é closure (função definida no escopo do apiV2 acessando as variáveis totalTokensUsed e totalCost), mutar dentro da função mexe direto nas variáveis do run — sem passar por service, sem I/O, sem consistência distribuída. É simples, síncrono, e funciona porque tudo mora no mesmo processo. Cada handler recebe essa referência via arg (não via injeção) — é padrão dependency injection funcional. Handlers Temporal não chamam essa closure; eles cobram por HTTP direto no /worker/charge-tokens, e o backend depois lê via sumChargesByExecution (fn D). Sem worker, sem HTTP, sem lock — mas também sem paralelismo real.
let totalTokensUsed = 0; let totalCost = 0; const onUpdateTokens = (tokensUsed: number, cost: number) => { totalTokensUsed += tokensUsed; totalCost += cost; };
↓
A1 Passado a handlers legacy
Handlers como voiceNode, imageGeneratorNode, webSearchNode, audioReaderNode, commandContentNode recebem onUpdateTokens como arg — chamam durante execução. Dispatch em flux.service.ts:3380, 3615, 3706, 3722, 3712.
🎯 Sem lock, single-threaded funciona
Como Node.js é single-threaded no event loop, mutar totalTokensUsed += x nunca vai dar race — não existem 2 handlers rodando em paralelo de verdade. Só um await tá suspenso por vez. Em qualquer refactor que introduza paralelismo real (worker_threads, cluster), essa closure precisa virar operação atômica.
⚠️ Sem idempotência
Se um handler chamar onUpdateTokens 2× por engano (retry, bug), soma 2×. Não há dedup. Diferente do token_transactions do Temporal path, que pelo menos tem PK.
🔧 Fecha sobre 2 variáveis
A closure captura totalTokensUsed e totalCost por referência (é let, não const — mas mesmo com const, closure lê o valor atual da variável, não snapshot). Reatribuição fora afeta a leitura.
BSnapshot before/after do nó
flux.service.ts:3248-3249, 3296-3297, 4537-4546
genericTokensBefore = totalTokensUsed; ... [handler roda] ... delta = totalTokensUsed - genericTokensBefore;
Propósito: Pattern universal pra atribuir cobrança ao nó certo — no início do try do nó (linha 3248 e 3296 pra segurança dupla), snapshot dos acumuladores globais. Depois do handler terminar, delta = valor atual - snapshot. Vai pro endNode em 3.9.
Em resumo: é a régua antes/depois. O total do run tá subindo o tempo todo (cada handler cobra, cada iteração). Pra saber quanto foi desse nó específico, marca-se o total antes do nó começar (genericTokensBefore) e o total depois (totalTokensUsed) — a diferença é o gasto atribuível. Simples e robusto enquanto não há paralelismo entre nós. Se 2 nós rodassem em paralelo, os deltas se cruzariam — não teria como saber quem gastou o quê só pela diferença. Por que o snapshot aparece 2× (3248 e 3296)? Segurança dupla: a linha 3248 é depois do try { abrir; a 3296 é dentro do bloco onde o RunLog está sendo criado — reset explícito pra garantir que qualquer cobrança do runLogCollector.startNode (não deveria acontecer mas...) não vaze pro delta do nó. Um tanto paranóico mas defensivo. E o delta final é escrito no RunLogNode em 3.9 (endNode), com tokens: totalTokensUsed - genericTokensBefore. Assim a UI de timeline mostra tokens/custo por nó, não só o total do run.
// linha 3248-3249 let genericTokensBefore = totalTokensUsed; let genericCostBefore = totalCost; // linha 3296-3297: reset após startNode genericTokensBefore = totalTokensUsed; genericCostBefore = totalCost; // [... handler roda ...] // linha 4539-4540: cálculo do delta em endNode tokens: totalTokensUsed - genericTokensBefore, cost: totalCost - genericCostBefore,
🎯 Por que 2 snapshots?
Linha 3248 é durante inicialização de vars. Linha 3296-3297 é depois do startNode, garantindo reset — se o startNode/redactSecrets ativou algum path que cobrasse tokens (improvável mas defensivo), fica fora do delta do nó.
⚠️ Delta pode ficar negativo?
Não em código normal — totalTokensUsed só cresce. Mas se alguém decidir "compensar" (subtrair tokens em caso de erro), o delta pode ficar negativo. O endNode passa cru pra RunLogNode, que persiste o número — futuramente pode virar bug se alguém somar sem checar sinal.
🔧 Snapshot em cópia por valor
Numbers em JS são valores, não referências. genericTokensBefore = totalTokensUsed copia o número — mudar totalTokensUsed depois não afeta o snapshot.
CchargeContext (AsyncLocalStorage)
product/charge-context.ts:1-8 · product.service.ts:1013-1015
chargeContext = new AsyncLocalStorage<{ execId, nodeId }>() · getStore() lido em updateTokens
Propósito: Faz a ponte entre "quem está cobrando" (services de provider genéricos) e "onde persistir" (execId + nodeId do run atual). Injetado em 3.4 antes do handler; lido pelo ProductService.updateTokens quando insere row em token_transactions.
Em resumo: se você olhar só o onUpdateTokens do fn A, parece que a cobrança só vive na memória do backend. Mas na verdade, quando um handler chama anthropicService.chat(...), esse service internamente também chama productService.updateTokens(delta, cost) — que insere row em token_transactions no Postgres. E aí vem o problema: o ProductService é compartilhado com rotas API públicas — como ele sabe que essa cobrança pertence a este agente, a este nó? Resposta: via chargeContext.getStore(). O 3.4 injetou { execId, nodeId } na AsyncLocalStorage antes do handler começar; quando o ProductService lê a ALS, pega esses ids e escreve na coluna metadata da row. Assim, duas cobranças acontecem em paralelo: (i) onUpdateTokens soma no total do run em memória; (ii) ProductService insere row com identificação por-nó no banco. A memória vira o retorno síncrono do run (Fase 4 pega); o banco vira audit trail e fonte pra sumChargesByExecution depois (fn D).
↳ ProductService.updateTokens — product.service.ts:1013-1015
const chargeCtx = chargeContext.getStore(); // ALS lookup execId = execId ?? chargeCtx?.execId ?? null; nodeId = nodeId ?? chargeCtx?.nodeId ?? null; // INSERT INTO token_transactions ({ execId, nodeId, tokens, cost, ... })
🎯 Fallback para arg explícito
execId = execId ?? chargeCtx?.execId — se o caller passou explícito, respeita. Só usa ALS como fallback. Permite outros callers (API pública) não precisar do contexto.
📎 Duas fontes de verdade
Memória (totalTokensUsed) e banco (token_transactions) podem divergir — se onUpdateTokens é chamado mas o INSERT do ProductService falha, memória tem valor mas banco não. Não há reconciliação automática — mas em prática, se ProductService falha, o request de LLM falharia antes.
DsumChargesByExecution (path Temporal)
flux.service.ts:709-716 · tokenTransactionService
const { tokens, cost } = await tokenTransactionService.sumChargesByExecution(execId, nodeId)
Propósito: Handlers Temporal cobram via HTTP /worker/charge-tokens no worker (não têm acesso ao onUpdateTokens closure). Após workflow terminar, o backend agrega esses charges do banco por {execId, nodeId} e soma no totalTokensUsed/totalCost do run.
Em resumo: handlers no worker não podem chamar a closure — outro processo, outra memória, outra vida. A solução: cada activity que cobra tokens chama HTTP /worker/charge-tokens passando { execId, nodeId, tokens, cost }. O endpoint no backend insere row em token_transactions. Aí, quando processNodeViaTemporal retorna, o backend chama tokenTransactionService.sumChargesByExecution(execId, nodeId) — SELECT SUM(tokens), SUM(cost) FROM token_transactions WHERE exec_id = $1 AND node_id = $2. O resultado é somado direto em totalTokensUsed/totalCost. Efeito: dois caminhos de propagação de billing, mas uma única fonte de verdade final no fim (a soma em memória do backend). Elegante mas com custo de round-trip: HTTP + SQL por nó Temporal. Em runs grandes com muitos nós migrados, é overhead considerável — mas garante consistência entre paths.

D2 Backend agrega ao retornar

🎯 Idempotente por design
Se o worker retentar uma activity de cobrança, o INSERT em token_transactions pode duplicar — mas se a activity chargeTokens tem PK única, é seguro. Verificar se existe unique constraint em (execId, nodeId, iterationIndex) ou similar.
⚠️ Overhead per node
HTTP call + SQL SUM por nó Temporal. Numa agente com 50 nós migrados, é 100 round-trips extras (charge + sum). Poderia ser batched — hoje é um-a-um.
🔧 Ambos os paths somam no mesmo lugar
Path legacy: onUpdateTokens muta memória direto. Path Temporal: sumChargesByExecution lê do banco e soma na memória. Depois de 3.7 rodar (ou equivalente para Temporal), totalTokensUsed reflete os dois caminhos.
Resumo — o que sai de 3.7:
• totalTokensUsed/totalCost refletem consumo pós-execução do nó
• Delta atribuído ao RunLogNode em 3.9 (tokens/cost)
• Row em token_transactions gravada (via ProductService ou HTTP worker)
• 2 mecanismos: closure legacy + AsyncLocalStorage/HTTP Temporal
Observações para migração:
• A closure onUpdateTokens vira obsoleta quando tudo estiver no worker — todo mundo cobra via HTTP /worker/charge-tokens. É bom sinal: menos código, menos padrões concorrentes.
• chargeContext ALS também some — o worker sempre passa execId/nodeId explícitos por API.
• O snapshot before/after continua útil como pattern — mas se worker paralelizar, precisa de dedup por PK em token_transactions, não subtração de acumuladores.
• É cross-cutting e essencial pra billing. Deve ser migrado junto com o loop principal, com contract HTTP claro entre worker e backend.

Passo 4.2 — Coleta de nós com erro

Bloco em flux.service.ts:4780-4799. Filtra myUpdatedNodes por nós com errorMessage/errorStatusCode. Extrai primeira mensagem pra logErrorMessage e primeiro status pra logErrorStatusCode. Também resolve logStatus via helper puro resolveRunLogStatus.
Contexto: passo curto e puro — sem I/O, sem side effects. Só monta variáveis que os passos 4.3 e 4.4 vão consumir. É onde o status final do run se cristaliza: 'Successfully ran' vs 'Error while running' vs 'Cancelled'.
AnodesWithError filter
flux.service.ts:4780-4782
const nodesWithError = myUpdatedNodes.filter(node => node.data?.errorMessage || node.data?.errorStatusCode);
Propósito: Varre todo myUpdatedNodes procurando nós marcados com erro. Simples filter — sem I/O. Nem todo nó com erro necessariamente causou fail-fast — em edge cases, múltiplos nós podem ter escrito errorMessage e o loop parou por outro motivo (ex: cancel).
Em resumo: é o censo de vítimas — passeia por todos os nós do agente e junta os que tem errorMessage ou errorStatusCode setado. Em run com fail-fast (o mais comum), tem só 1 nó nessa lista — o culpado que parou tudo. Em edge cases mais complexos (cancel após múltiplos nós já terem escrito soft-fail sem quebrar o loop, ou bugs de scheduler), pode ter mais. Independente da quantidade, o próximo passo (4.3) só usa o primeiro pra montar log e mensagem — dá pra chamar essa lista de "possíveis" e escolhe o first-fit.
const nodesWithError = myUpdatedNodes.filter( node => node.data?.errorMessage || node.data?.errorStatusCode, );
🎯 OR entre 2 campos
Pega nó se qualquer um dos 2 estiver populado. Alguns handlers setam só errorStatusCode (código HTTP), outros só errorMessage.
⚠️ Falsy check
|| descarta '', 0, null. Se um handler setar errorMessage: '' por bug, esse nó não entra na lista mesmo sendo "com erro" tecnicamente.
BPrimeira mensagem + status code
flux.service.ts:4794-4799
const logErrorMessage = nodesWithError.length > 0 ? nodesWithError[0].data.errorMessage : null; · const logErrorStatusCode = ... : null;
Propósito: Pega [0] — o primeiro do array. Não escolhe "o mais grave" nem "o primeiro no tempo" — literalmente ordem do array (que reflete ordem de definição no flow). Usado por 4.3 pro flowLogsService.createLog.
Em resumo: se tem 1 nó com erro, é ele. Se tem múltiplos, é o primeiro que aparecer em myUpdatedNodes. Não é "primeiro cronologicamente" — a ordem do array reflete ordem de criação no editor, não execução. Em prática, com fail-fast, só tem 1 mesmo — não vira problema. Se algum dia tiver múltiplos por causa de partial execution ou branches paralelos, escolher o primeiro por index é decisão arbitrária que talvez não seja a melhor UX. Mas é o que tá em uso hoje.
const logErrorMessage = nodesWithError.length > 0 ? nodesWithError[0].data.errorMessage : null; const logErrorStatusCode = nodesWithError.length > 0 ? nodesWithError[0].data.errorStatusCode : null;
📎 Sem erro = null
Se lista vazia, ambas as vars ficam null. Passadas assim pra flowLogsService.createLog em 4.3 — o service aceita null e persiste como NULL no Postgres.
CresolveRunLogStatus (helper puro)
node-cancel-outcome.ts:1-8 · call em 4790-4793
export function resolveRunLogStatus(params: { hasNodeError: boolean; stoppedByCancel: boolean }): string
Propósito: Função pura que decide status string do run: 'Error while running' se tem erro, 'Cancelled' se cancelado, 'Successfully ran' senão. Ordem de precedência matters — erro vence cancel.
Em resumo: pura decisão de string — sem I/O, sem side effect. Se tem erro em qualquer nó, vence tudo: status='Error while running' (mesmo que também tenha sido cancelado no meio, o erro é priorizado). Senão, se foi cancelado, status='Cancelled'. Senão, sucesso: 'Successfully ran'. Strings livres, não enum — usadas depois na coluna status de execution_logs. Um pouco fragile por serem strings (typo quebra query), mas funcional.
export function resolveRunLogStatus(params: { hasNodeError: boolean; stoppedByCancel: boolean; }): string { if (params.hasNodeError) return 'Error while running'; if (params.stoppedByCancel) return 'Cancelled'; return 'Successfully ran'; }
🎯 Precedência: erro > cancel > sucesso
Não é acidental — reflete: cancel enquanto rodava OK = cancel; cancel enquanto tinha erro = erro (o dev quer saber do erro real, não do cancel que veio depois).
⚠️ Sem 'flow_truncated' status
Se sobrou nó órfão sem stop flags (bug em 4.1), o status ainda é 'Successfully ran' — porque não tem hasNodeError. Inconsistência sutil: log Winston diz "truncado" mas execution_logs mostra sucesso.
Resumo — o que sai de 4.2:
• nodesWithError — array (pode ser vazio)
• logErrorMessage, logErrorStatusCode — null ou string do primeiro nó com erro
• logStatus — 'Error while running' | 'Cancelled' | 'Successfully ran'
• Prontas pra Fase 4.3 e 4.4 consumir
Observações para migração:
• Puro, sem I/O — trivial de mover pra qualquer lugar. Pode virar utility compartilhado entre backend e worker.
• Strings de status merecem virar enum tipado (RunLogStatus.Error | Cancelled | Success).
• Escolher [0] arbitrariamente pode virar bug se algum dia agentes tiverem múltiplos outputs paralelos com falhas.
• Não bloqueia migração — pode ficar tal como está e refactor incremental.

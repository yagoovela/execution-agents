Passo 5.1 — Catch top-level

Bloco em flux.service.ts:5309-5392. Catch envolvendo todo o corpo do apiV2(). Finaliza RunLog com status='error', cria FlowLog de erro, loga Winston com hint contextual, e re-throw o erro pro caller.
Em resumo — o que esse passo faz
  • Rede de segurança do apiV2: catch top-level que envolve o corpo inteiro do método. Se qualquer coisa não-tratada lançar (bug, DB caindo, code path esquecido), esse bloco é o último a rodar — garante audit trail mesmo em cenário catastrófico.
  • Finaliza o RunLog em modo desastre: mesma cadeia da Fase 4.4 (finalize + flushNow), mas com status: 'error' e errorMessage da exception. Try/catch aninhado protege contra erro-do-erro — se o próprio flush falhar, só loga sem duplo-throw.
  • Log estruturado com hint contextual: Winston recebe errorName, errorMessage, errorStack e contexto do run. Se a mensagem for 'nodes is not iterable' (bug conhecido), anexa uma sugestão diagnóstica direcionando o dev pros handlers suspeitos — knowledge base embutida no código.
  • Grava execution_log de erro (com guard): mesma createLog da 4.3, agora com status: 'Error while running'. Guard: se a exception é NotFoundException com "flow not found", não escreve — sem flowId válido não tem FK pra respeitar.
  • Saída: throw error re-lança a exception original (tipo e stack preservados) pro caller — controller HTTP devolve 500, Bull marca job failed. O finally do 5.3 ainda roda antes da propagação efetiva.
Contexto: última linha de defesa contra qualquer exception não-tratada no apiV2. Diferente do catch por nó (3.8) que só quebra o loop e continua Fase 4, aqui é bug/erro sistêmico — falha em setup, DB down, code path não-esperado. Garante audit trail mesmo em cenário catastrófico.

Isso é knowledge base embutido no código — reflete debugs anteriores que a equipe já teve. Se aparecer em prod, dev vê o hint e sabe onde procurar antes mesmo de abrir stack trace. Padrão elegante — quando você conhece bem os bugs comuns, otimiza pra próxima ocorrência.

⚠️ Regex de detecção

Dthrow error
flux.service.ts:5392
throw error;
Propósito: Re-lança a exception original pro caller. Endpoint controller (ou Bull processor) recebe e devolve HTTP 500 (ou marca job como failed no Bull). Fica evidente que o run falhou fatal — não retornou objeto de resposta.
Em resumo: última linha do catch. Depois de todo o cleanup (finalize, log, createLog), re-lança a exception original. Simples. Isso pra que? Caller precisa saber que falhou. Se apiV2 tivesse return null ou similar, o controller/processor não saberia distinguir "sucesso com resposta vazia" de "crash fatal". Com throw, o caller HTTP recebe erro (endpoint controller vai pro exception handler global do Nest, devolve HTTP 500). Bull processor vê exception, marca job como failed. Tudo bem sinalizado. Note que preserva a exception original — não wrappa em new Error. Assim, quem pegar tem stack completo e tipo original. É a coisa certa em quase todos os casos.

Observações para migração:
• Essencial e cross-cutting — cobertura de erros catastróficos é obrigatória.
• Try/catch aninhados dentro do catch principal (defesa contra erro-do-erro) é bom pattern — manter.
• Hint contextual ('nodes is not iterable') é dívida-baixa: crescer conforme mais bugs conhecidos aparecerem.
• NotFoundException+ regex é frágil — melhor tipo específico.
• Migração pro worker: worker vai ter seu próprio catch — mas backend continua sendo o orquestrador principal e precisa desse safety net.

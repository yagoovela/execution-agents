A nextReady(state)
scheduler.ts:295-308
export function nextReady(state: SchedulerState): string | null
Propósito: Dá shift() na fila FIFO state.ready até achar o primeiro nó que não está em dead, completed ou scheduled. Retorna esse id (e marca como scheduled pra não voltar) ou null se a fila secou.
Em resumo: pense como um guichê de senha de banco. Tem uma fila de gente pronta pra ser atendida (ready). O guichê chama o próximo da fila, mas antes de mandar ele pra frente confere 3 listas: já foi atendido hoje? (completed) foi cancelado? (dead) ou já foi chamado por outro guichê? (scheduled). Se cair em qualquer uma dessas listas, descarta a senha e chama a próxima — sem ficar reclamando, sem log. Se a fila secou, retorna null — o "banco fechou" e o loop principal encerra. É FIFO puro, sem prioridade, sem justiça — a ordem de chegada é a ordem de execução. E o guichê nunca chama o mesmo nome duas vezes: ao devolver um id, ele adiciona no set scheduled como um "sim, esse já saiu daqui" — assim, se o mesmo id aparecer duplicado na fila (o que acontece quando dois predecessores resolvem em cascata), o segundo shift silenciosamente pula.
export function nextReady(state: SchedulerState): string | null { while (state.ready.length > 0) { const id = state.ready.shift()!; // FIFO if (state.dead.has(id)) continue; if (state.completed.has(id)) continue; if (state.scheduled.has(id)) continue; state.scheduled.add(id); // deduplicação return id; } return null; }
↓
🪜 Cascata por candidato saído da fila
1 está em dead? skip (branch podado)
2 está em completed? skip (nó já rodou)
3 está em scheduled? skip (dedupe)
4 nenhum dos acima add em scheduled + return id
5 fila esvaziou return null (fim do loop)
🎯 Por que shift() e não priority queue?
É FIFO puro. A ordem que os nós entraram em ready é a ordem que executam. Como buildSchedulerState inicializa a fila com os nós de in-degree zero e depois cada markCompleted pode empurrar novos (quando o último predecessor resolve), o efeito prático é uma BFS topológica — mas o scheduler não promete essa ordem.
📎 A fila pode ter entradas duplicadas
Um mesmo nó pode ser push-ado 2× se dois predecessores resolvem em sequência muito próxima antes do primeiro nextReady tirá-lo. O set scheduled serve exatamente pra descartar as duplicatas no segundo shift.
⚠️ Sem priority, sem fairness
Não há garantia de quando um nó específico vai rodar em relação a outros também prontos. Pra qualquer refactor que precise controlar ordem (SLA, timeout por nó, retry policy), a estrutura atual não expõe hooks — precisa mexer no SchedulerState.
🔧 O que o loop faz depois do return
Recebe o id em scheduledId, entra no corpo do while em flux.service.ts:3229 — o que engatilha a checagem de cancelamento (3229-3239), a busca de node em myUpdatedNodes (3241) e a cadeia dos passos 3.2 → 3.11.
B SchedulerState (contrato)
scheduler.ts:96-111
interface SchedulerState { nodeIds; forwardDeps; ready; completed; dead; scheduled; totalPreds; resolvedPreds; deadPreds; gatingPairs; totalGatingPreds; resolvedGatingPreds; deadGatingPreds; conditionEdges; }
Propósito: Estado mutável in-memory do DAG scheduler. Todo o loop da Fase 3 opera sobre esse struct — nextReady lê 3 sets, markCompleted resolve predecessores dos vizinhos, completeCondition mata branches não-tomadas.
Em resumo: é o painel de controle do agente. Imagina uma sala com um quadro branco enorme onde tudo do run tá desenhado — quais nós existem, quem depende de quem, quantos predecessores cada um ainda tá esperando, quem já rodou, quem morreu em uma branch podada, quem tá na fila. Nada disso vive no banco durante o run: é tudo Sets e Maps em heap do backend. É o "cérebro" que fica aberto enquanto o agente executa, e todas as funções — nextReady, markCompleted, completeCondition, resolvePred — não fazem nada além de ler e escrever nesse quadro. Por causa disso, o scheduler é portável (é TypeScript puro, sem Nest/DB/Redis), mas também é frágil: se o processo do backend cair no meio, o quadro some inteiro — não tem checkpoint, não tem crash recovery. É esse trade-off que a migração pro Temporal quer resolver: mover o "quadro" pra o próprio WorkflowHistory do Temporal, que persiste tudo automaticamente.

🎯 Por que 3 sets separados?
completed = terminou com sucesso ou erro tratado.
dead = nunca vai rodar (branch podado).
scheduled = já entregue por nextReady, aguardando o markCompleted.

Um nó nunca está em mais de um set ao mesmo tempo. Isso permite o continue em cascata em O(1).
📎 dead ≠ completed
Em Fase 4, o warning "nós não-processados" (4.1) compara todos os nodeIds com a união completed ∪ dead. Se sobrar alguém, foi bug de scheduling.
🔧 gatingPairs
Set<string> com strings "src→dst" representando arestas control ou condition. Usado pra saber quando todos os caminhos gating pra um nó morreram — nesse caso o nó vai pro set dead, não pro ready, mesmo com resolvedPreds === totalPreds.
C markCompleted(state, id)
scheduler.ts:352-357
export function markCompleted(state: SchedulerState, id: string): void
Propósito: Fecha o loop de nextReady. Depois que um nó terminou, esta função marca ele como completed e itera os forwardDeps (quem dependia dele) chamando resolvePred. Cada vizinho tem seu resolvedPreds incrementado — se bater com totalPreds, entra em ready.
Em resumo: é o secretário do guichê — quando alguém termina o atendimento e sai, ele passa em cada mesa que dependia dessa pessoa e coloca um "check" no formulário. Ex: se o nó B esperava input do A, quando A termina, o secretário vai na "ficha" do B e escreve "ok, A já resolveu, falta só o C". Se essa foi a última pendência do B (todos os predecessores dele resolveram), o secretário empurra B pra fila do guichê (ready) — pronto pra ser atendido. É a única forma de nós novos entrarem em ready depois da inicialização. Detalhe importante: um "check" pode ser dead ou vivo — se A morreu numa branch podada, o secretário ainda "resolve" a dependência do B, mas marca essa resolução como fantasma. Se todos os predecessores gating do B forem fantasmas, B também vira dead e nunca vai pro ready. E é idempotente: se por bug o mesmo id chegar 2×, o secretário identifica pelo state.completed.has(id) e ignora — nada de dupla contagem.
export function markCompleted(state: SchedulerState, id: string): void { if (state.completed.has(id)) return; // idempotente state.completed.add(id); for (const next of state.forwardDeps.get(id) ?? []) resolvePred(state, id, next, false); // predWasDead=false }

↳ resolvePred(state, source, target, predWasDead) — scheduler.ts:310-350
Incrementa resolvedPreds[target] e, se predWasDead=true, também deadPreds[target].
Regras:
• Se todos os gating predecessors do target morreram → state.dead.add(target).
• Se resolvedPreds[target] === totalPreds[target] e não é dead → state.ready.push(target).
• Se target já é dead ou completed → no-op (idempotente).
scheduler.ts:310-350
🎯 Quem chama markCompleted?
É o passo 3.11 do diagrama. Depois de um nó rodar (via Temporal ou inline), o loop chama:
• markCompleted(schedState, id) pra nós normais
• completeCondition(schedState, id, handle) pra nós de decisão (que pode setar branches como dead)
📎 Idempotência
O early-return em state.completed.has(id) permite chamar markCompleted várias vezes com o mesmo id sem quebrar contadores. É uma proteção — em condições especiais (arrayNode iterando o body, retries) pode chegar 2× no mesmo id.
🔧 Predecessores dead são "resolvidos"
resolvePred incrementa resolvedPreds independente de predWasDead. A ideia é: um branch morto ainda "resolve" a dependência (ele não vai empurrar dado, mas também não está pendente). Se sobrar dado suficiente por outras arestas, o nó ainda pode rodar.
D completeCondition(state, id, takenHandle)
scheduler.ts:366-389
export function completeCondition(state: SchedulerState, conditionId: string, takenHandle: string | null): void
Propósito: Versão especializada de markCompleted pra nós de decisão (conditionNode etc.). Marca o nó como completed e propaga "dead" pra todas as arestas condition saindo desse nó por handles não-tomadas. As arestas do handle tomado propagam normalmente.
Em resumo: é o juiz de uma bifurcação. Quando um conditionNode avalia "se x > 10 vai por A, senão vai por B", o juiz precisa fechar oficialmente a rota que não foi escolhida — senão nós desse lado ficariam eternamente esperando input que nunca chega. Ele recebe o takenHandle (ex: 'outputHandle-0') e percorre todas as arestas condition saindo do nó: pras que combinam com o handle tomado, faz a "resolução viva" (nó destino recebe input normal); pras outras, marca como predWasDead=true — o secretário do próximo nó registra "essa dependência morreu, não vai vir dado". Se todos os caminhos gating de um nó a jusante morrerem, esse nó também vira dead — cascata de morte propagando pra baixo. Existe também um sentinela especial chamado DEAD_HANDLE: quando um nó de decisão falha antes de decidir (bug, timeout, throw), o loop chama completeCondition(id, DEAD_HANDLE) — todos os handles são considerados não-tomados, matando o subgrafo inteiro pra evitar que sucessores rodem com dados undefined. Único perigo: o nome do handle é literal string — um typo ('outputHandle-0' vs 'outputHandel-0') faz o juiz matar a rota errada silenciosamente.

🎯 Onde DEAD_HANDLE aparece
Sentinel usado pelo passo 3.8 (tratamento de erro por nó): se um nó falhar antes de decidir uma branch, o loop chama completeCondition(schedState, id, DEAD_HANDLE) pra matar todos os caminhos possíveis, evitando que sucessores rodem com input undefined.
📎 Diferença de markCompleted
markCompleted é agnóstico — assume que todas as arestas saindo do nó eram "vivas". completeCondition precisa distinguir handle tomado × não-tomado, e por isso lê conditionEdges (populado em buildSchedulerState).
⚠️ Handle name matters
O takenHandle vem literal do return do handler do condition ('outputHandle-0', 'outputHandle-1', 'conditionHandle-T0', etc.). Qualquer typo no handler faz o scheduler comparar contra a string errada e matar branches viáveis. Não há validação — footgun clássico.
🔧 Onde isso é usado no loop
Chamado em flux.service.ts:3566-3571 (handler do conditionNode), 4013 (handler do arrayNode pra encerrar iteração), 4004-4006 (após erro fatal). É o passo 3.11 do diagrama pra tipos que decidem branches.
Resumo — o que sai de 3.1:
• scheduledId: string | null — id do próximo nó pronto ou null
• Efeito colateral: se retornou id, o state teve scheduled.add(id)
• Se retornou null, o loop da Fase 3 termina e o backend cai na Fase 4 (finalização)
• Nenhum I/O: 100% in-memory (Sets e Maps)
Observações para migração:
• O scheduler é puro TypeScript sem dependência de Nest/DB/Redis — portável pro worker sem refactor pesado. Mas...
• ...ele é stateful in-memory. Todo o SchedulerState vive no heap do backend enquanto o agente executa. Pra rodar isso no worker (Temporal workflow), o state teria que ser serializable ou reconstituído a cada activity call.
• A dedupe via scheduled depende de execução single-threaded. Se o worker executar irmãos em paralelo, dois nextReady concorrentes podem devolver ids diferentes; mas dois markCompleted concorrentes atualizando o mesmo resolvedPreds precisam de lock.
• completeCondition + DEAD_HANDLE é o mecanismo central de branching — qualquer reimplementação precisa preservar semanticamente. Especial atenção pra conditionNode, arrayNode (iteração), fail-fast em erros e o warning de Fase 4.1.
• É essencial — o loop inteiro colapsa sem ele. Deve ir pro plano de migração cedo, com o scheduler como uma das primeiras responsabilidades do worker (ou de um serviço dedicado consumido tanto por backend quanto worker).

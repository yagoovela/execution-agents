Passo 3.6 — updateSchemaWithNodeOutput()

Bloco em node-reference-substitution.service.ts:169-216 · chamadas em flux.service.ts:3389, 3485, 3624, 3670, 4331. Após um handler terminar, o output vira parte do schema — visível pros próximos nós como {{nodeLabel.text}}, {{nodeLabel.url}}, etc.
Contexto: essa é a outra ponta da substitution engine (memória [[project_substitution_engine]]). Em 3.3 applySubstitutionToObject LÊ o schema; aqui em 3.6 se ESCREVE nele. Sem esse passo, cada nó ficaria isolado — impossível referenciar output de nó anterior. É o "ponto de sincronização" entre handlers.

AupdateSchemaWithNodeOutput(schema, nodeId, label, output)
node-reference-substitution.service.ts:169-216
updateSchemaWithNodeOutput(schema: any, nodeId: string, nodeLabel: string, output: any): any
Propósito: Recebe output do handler que acabou de rodar (string ou objeto) e escreve os campos apropriados na entry do nó no schema. Retorna novo schema (spread do anterior) — não muta in-place.
Em resumo: se 3.3 é o revisor que lê e resolve {{...}}, essa é a redatora que atualiza o dicionário depois que o nó terminou. Pega o output do handler (pode ser uma string simples como "Hello world" ou um objeto complexo como { text, url, content }), abre a entry desse nó no schema e escreve os campos que caberem — se veio string vira .text e .result; se veio objeto, extrai .text, .content, .result, .url, .audioUrl conforme presentes. Não substitui a entry inteira — preserva os campos existentes (input, prompt) e só acrescenta/atualiza os de saída. E aqui vem o pulo do gato: como as 3 chaves (stableKey/refKey/labelKey) da entry apontam pra mesmo objeto, atualizar uma atualiza as 3 automaticamente. O próximo nó que ler {{writer.text}}, {{6d09d1...uuid.text}} ou {{textBox_1714_0_8148.text}} vê exatamente o mesmo valor. E o { ...schema } na linha 182 clona o container antes de mexer — o schema anterior fica imutável (se alguém guardou referência, não vaza mudança).
updateSchemaWithNodeOutput(schema, nodeId, nodeLabel, output) { const stableKey = nodeId; if (!stableKey) return schema; const labelKey = (nodeLabel || '').toLowerCase().replace(/\s/g, ''); const updatedSchema = { ...schema }; // clona shallow const entry = updatedSchema[stableKey] ?? {}; // preserva existente if (typeof output === 'string') { entry.text = output; entry.result = output; } else if (typeof output === 'object' && output !== null) { // copia .text / .content / .result / .url / .audioUrl (se existirem) } ... }

A1 Guard: sem nodeId, no-op
Se !stableKey, retorna schema inalterado. Defensivo — nunca deveria acontecer em prática porque o loop só chama isso depois de encontrar um node válido.

🎯 Por que preservar entry existente
O entry = updatedSchema[stableKey] ?? {} preserva os campos de input (prompt, url, formula, etc.) que foram indexados em 2.3 pelo generateSchemaFromNodes. Só sobrescreve os campos de output. Assim, referências como {{writer.prompt}} continuam funcionando depois que o nó terminou.
📎 shallow clone, não deep
{ ...schema } clona só o container. As entries individuais ainda são referências partilhadas (as 3 chaves apontam pra mesma). É intencional — assim escrever numa chave reflete nas 3.
🔧 typeof null === 'object'
O guard output !== null na linha 188 evita cair no ramo de objeto com null. Sem ele, null.text daria TypeError.
BDispatch por tipo de output
service.ts:185-204
if (typeof output === 'string') → text+result · if (object) → text/content/result/url/audioUrl (opcionais)
Propósito: Decide quais campos escrever baseado no formato do output. String simples vira ambos .text e .result (pra compat com placeholders legacy); objeto expande em vários campos condicionais.
Em resumo: pensa nisso como uma caixa de encomenda — o handler não sabe (e não deve saber) exatamente onde o próximo nó vai procurar o valor. Alguns usam {{writer.text}}, outros escreveram templates antigos com {{writer.result}}, um handler de imagem vai gerar {{img.url}}. A função aceita a encomenda em qualquer formato e distribui nos 5 slots possíveis. Se veio uma string pura, dupla escrita em .text e .result — cobre 2 estilos de placeholder simultaneamente. Se veio um objeto, cada campo .text/.content/.result/.url/.audioUrl é opcional — só é escrito se estiver definido no output. Um handler de LLM manda { text }; um de imagem manda { url }; um de áudio manda { audioUrl, text }. Nunca vaza dados de outros nós — cada handler é responsável por retornar só o que ele produziu. E ausência de campo não zera valor existente — mantém o que já estava.

entry.text = output; entry.result = output; — dupla escrita. Cobre placeholders {{X.text}} e {{X.result}} ao mesmo tempo. Usado pra outputs de mathFunction, textBox, etc.

⚠️ Sem validação de tipos
entry.text = output.text aceita qualquer coisa — string, number, array, function. Se um handler bugado passar output.text = { foo: 1 }, esse objeto vai virar "[object Object]" quando um placeholder tentar interpolar (via String coerção no replacePlaceholders).

O check output.text !== undefined permite explicitamente sobrescrever com null ou '' (string vazia). Só undefined significa "não mexer".
CReescrita nas 3 chaves
service.ts:206-213
updatedSchema[stableKey] = entry; if (refKey ≠ stableKey) updatedSchema[refKey] = entry; if (labelKey && ≠ ambos) updatedSchema[labelKey] = entry;
Propósito: Garante que as 3 chaves de acesso (UUID, refKey normalizado, labelKey humano) apontem pra mesma entry atualizada. Como entry é referência, escrever uma chave já reflete nas outras — mas fazer o assign explícito garante idempotência mesmo se a entry foi trocada.
Em resumo: é o momento de garantir que os 3 nomes que a pessoa atende (CPF, RG, apelido) apontem pra mesma pasta atualizada. Como o schema foi shallow cloned na linha 182, o updatedSchema tem uma cópia do container mas ainda tá referenciando as entries antigas. Ao fazer updatedSchema[stableKey] = entry, força a atribuição pra essa nova entry (que veio de schema[stableKey] ?? {} — se existia, é a mesma; se não, é objeto novo). Depois faz o mesmo pra refKey e labelKey se forem diferentes — o guard evita sobrescrita desnecessária quando o nó não tem dots no id ou label humano. É idempotente: rodar 2× com mesmos args não muda nada. É simetria com o build inicial em 2.3 — mesma lógica de indexação, mesmos guards. E é referência partilhada: se um placeholder resolveu {{writer.text}} depois desse update, e outro nó do agente atualizar o mesmo writer (não acontece hoje, mas em qualquer paralelismo futuro seria bug), o segundo update afeta a leitura do primeiro — mutação compartilhada.
updatedSchema[stableKey] = entry; const refKey = stableKey.replace(/\./g, '_'); if (refKey !== stableKey) { updatedSchema[refKey] = entry; // dots → underscores } if (labelKey && labelKey !== stableKey && labelKey !== refKey) { updatedSchema[labelKey] = entry; // alias humano } return updatedSchema;

C1 Retorno = novo schema
O caller reatribui: nodeSubstitutionSchema = this.node...updateSchemaWithNodeOutput(...). Do próximo applySubstitutionToObject em diante, todo placeholder resolve com o output atualizado.
⚠️ Colisão de labelKey
Se dois nós têm o mesmo label ("Writer") — o segundo update reescreveria a mesma chave, mas nas suas próprias 3 chaves. O primeiro nó ainda tem schema[stableKey1] e schema[refKey1] apontando pra sua entry original — só schema['writer'] (label compartilhada) foi sobrescrita. Comportamento sutil: nem "última wins" nem "primeira wins" — depende de qual chave o placeholder usa.
🎯 Símetria com generateSchemaFromNodes
Mesma lógica de replace(/\./g, '_') e mesmo toLowerCase().replace(/\s/g, ''). É a garantia de que build inicial e update pós-execução usam exatamente as mesmas chaves — nenhuma referência "some" entre 2.3 e 3.6.
🔧 refKey e labelKey podem colidir
Se o label for tipo "6d09d1a3_...", ele pode colidir com o refKey. O último check garante que labelKey só é atribuído se for realmente distinto — evita 2 escritas na mesma chave.

Resumo — o que sai de 3.6:
• nodeSubstitutionSchema reatribuído com output do nó que terminou (novo objeto, spread do anterior)
• As 3 chaves do nó (stableKey/refKey/labelKey) apontam pra mesma entry atualizada
• 100% síncrono, in-memory
• Só 5 handlers legacy chamam explicitamente; Temporal usa retorno; outros usam onMutateSchema
Observações para migração:
• É o segundo maior ofensor da substitution engine (junto com o passo 3.3). São 57 sync sites que precisam funcionar em coerência. Migração pro worker requer que TODOS os call sites usem um único mecanismo — ou tudo via retorno de activity, ou via API centralizada.
• A entry compartilhada entre 3 chaves é uma otimização de memória — em qualquer refactor com paralelismo, vira problema de race. Precisará ser convertida em 3 escritas independentes ou lock por nodeId.
• A dupla escrita em .text e .result (ramo string) é backward compat. Um sistema novo pode escolher um só e forçar migração de placeholders.
• A whitelist implícita de 5 campos (text/content/result/url/audioUrl) é hardcoded — se um novo tipo de node produzir videoUrl, precisa adicionar aqui e no generateSchemaFromNodes em paralelo.
• É essencial — sem esse passo o loop não funciona. Deve migrar junto com 3.3.

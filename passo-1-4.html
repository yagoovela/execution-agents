Ainda faz um console.log com a decisão pra facilitar debug do tipo "cadê minha run que não apareceu?".

🎯 Por que essas 3 condições?
1. !isNestedRunLog — evita duplicar log. Se um flow chama outro via fluxBox, o log já vem do top-level como subRun aninhado.

2. loggingEnabled + runType — respeita a preferência do space E ignora modos "interativos" (manual/chatbot) onde o log costuma poluir sem valor.

3. spaceOwnerId — sem space definido não tem onde persistir (a tabela é indexada por spaceId).

C RunLogCollector.createRoot()
run-log-collector.ts:200-246 (chamada em flux.service.ts:2393-2417)
static createRoot(init: CollectorInit): RunLogCollector
Propósito: Factory que cria o coletor root de logs — o objeto in-memory que acumula toda a árvore de execução (nós, sub-runs, loops) e sabe fazer flush pra tabela space_run_logs. Guarda a referência do doc e do callback flush pra uso posterior.
Em resumo: imagine um caderno de campo que vai andando junto com a execução, anotando cada nó que roda, quanto durou e quanto custou. Essa função é a que abre a primeira página desse caderno: cria o objeto em memória com toda a metadata da run (id do processo, nome do flow, space, org, preço do token, quem disparou, input já com secrets ofuscados) e deixa métricas zeradas prontas pra serem acumuladas ao longo da execução. Também plugga um "botão de flush" (o callback) que vai ser puxado a cada mudança pra persistir no banco. Detalhe importante: se o logging estiver desligado, ela devolve uma versão no-op (métodos vazios) — assim o resto do código chama startNode/endNode sem precisar de if em todo lugar.

D spaceRunLogsService.upsertRun()
space_run_logs.service.ts:65-90
async upsertRun(params: { processId, spaceId, rootFlowId, logData: RunLogDocument }): Promise<SpaceRunLog>
Propósito: Escreve (ou atualiza) a row em space_run_logs. No passo 1.4 é chamada uma vez com o doc vazio (só metadata) para gravar a run em estado in_progress. Depois é chamada de novo assincronamente via debounce em scheduleUpsert a cada mudança.
Em resumo: essa é a gravadora do caderno de logs no banco. No 1.4, ela é chamada logo de cara pra plantar uma "bandeirinha" no Postgres: cria uma row em space_run_logs com status in_progress, praticamente vazia, só pra registrar que essa execução começou. Isso é uma proteção — se o processo morrer no meio (deploy, OOM, kill), pelo menos a run não some do dashboard: fica marcada como "começou mas não terminou" e outro job depois carimba como erro. Ela usa o processId como chave, então funciona como upsert: cada chamada seguinte (via debounce) vai sobrescrever a mesma linha com o snapshot atualizado do doc. Como logging não pode derrubar agente, o call-site envolve tudo em try/catch — se falhar, só loga um aviso e segue a vida.

🎯 Por que fazer o upsert inicial já em 1.4?
Se a execução crashar no meio (SIGKILL, OOM, deploy no meio da run...), pelo menos a row já existe em in_progress. Sem esse upsert inicial, se o processo morre antes do primeiro flush, a run desaparece.

Depois um cron job (markStuckRunsAsError) marca runs órfãs como erro.
📊 Colunas indexáveis vs blob
A entity tem colunas indexáveis extraídas do doc (spaceId, rootFlowId, runType, status, startedAt, endedAt, durationMs, totalTokens, totalCost) usadas em queries de listagem/filtro.

O doc inteiro fica em logData JSONB — carregado só quando abrir a run individual.

E spaceRunLogsService.scheduleUpsert() callback do flush
space_run_logs.service.ts:92-120
scheduleUpsert(params: { spaceId, rootFlowId, doc: RunLogDocument }): void
Propósito: Wrapper com debounce de 2 segundos em cima de upsertRun. Não é chamado diretamente em 1.4 — é configurado em (C) como flush callback. Cada vez que o coletor muda algo (startNode, endNode, finalize, sub-runs), ele chama esse flush.
Em resumo: pense num funcionário meio preguiçoso, mas esperto. Toda vez que o coletor grita "ei, teve mudança!", em vez de correr no banco na hora, ele fala "calma, vou esperar 2 segundos pra ver se vem mais coisa". Se vier outra mudança nesse meio-tempo, ele reseta o cronômetro — assim, uma execução com 50 nós disparando eventos rápidos vira ~1 write a cada 2s de atividade em vez de 50 writes seguidos. O preço a pagar é o risco de perder até ~2s de progresso se o processo morrer entre dois debounces (mas a bandeirinha inicial de D já garante que a row existe). Pra evitar essa perda no fim, a finalização chama uma variante flushNow() que dispensa o debounce e grava na hora.

⏱️ Por que debounce de 2s?
Um agente pode ter dezenas de nós disparando startNode/endNode em segundos. Sem debounce seriam 50+ writes por run.

Com debounce, agrupamos em ~1 write por 2s de atividade + um write final via flushNow na finalização.
⚠️ Trade-off: perda em crash
Se o processo morrer entre dois debounces, os últimos ~2s de progresso se perdem — só o snapshot anterior fica gravado. Por isso o upsertRun inicial em 1.4 é importante: garante a row existe.

A finalização (Fase 4) chama flushNow() (sem debounce) — cancela o pending flush e escreve na hora.
🔧 pendingFlushes
Map<processId, { timer, spaceId, rootFlowId, doc }>

Guarda in-memory os writes agendados. Se processo morrer, esse mapa some com ele.
🔧 OnModuleDestroy
O service implementa OnModuleDestroy pra dar flush em todos os pending durante shutdown gracioso do NestJS. Não ajuda em crash forçado.
Resumo — o que sai de 1.4 (quando o gate passa):
• runLogCollector instanciado como root, com rootDoc em memória e flushFn conectado ao scheduleUpsert
• Uma row inicial em space_run_logs com status = 'in_progress' e árvore de nós vazia
• A partir daqui, cada startNode/endNode/subRun/finalize vai mutar o doc e agendar um write debounced
• O fluxTokenPrice resolvido fica congelado no doc — não muda mais durante a run
• Se o gate não passar: runLogCollector = undefined, todos os call-sites em Fase 3 ficam checando if (runLogCollector) ... ou usando optional chaining
Observações para migração:
• Este bloco é cross-cutting — precisa acontecer antes do loop principal para que os passos 3.4 (startNode), 3.9 (endNode) e 4.4 (finalize) tenham o coletor pronto.
• O RunLogCollector é uma estrutura in-memory com o mesmo padrão do nodeSubstitutionSchema: mutado ao longo do loop. Se orquestrar no worker, ou o worker mantém sua própria árvore, ou faz update parcial via API pro backend.
• O debounce de 2s é por processo — se dividir orquestração entre backend e worker, cada um teria seu próprio pendingFlushes e o writeback pode ficar concorrente.
• Nada aqui é essencial pra correção da execução (é observabilidade) — pode ser migrado por último no plano.

Passo 3.2 — Busca do nó + previewResponses cache

Bloco em flux.service.ts:3240-3278. Recupera o objeto node completo (com data mutada por passos anteriores) do array myUpdatedNodes, marca o id como processado e prepara o cache local responses (últimas 10 preview responses).
Em resumo — o que esse passo faz
  • Abre a pasta viva do funcionário: o scheduler entregou só um id em 3.1 — agora myUpdatedNodes.find devolve o node inteiro, como referência viva do array, com todas as mutações que handlers anteriores já fizeram (schema, contentData, previewResponses).
  • Skip silencioso se sumiu: se o find não achar (bug latente sem repro), o loop não crasha — if (node) { ... } engole o caso e pula pra próxima iteração. Custo é O(n) por nó — em agentes com 1000+ nós vira quadrático.
  • Carimba o ponto e tira foto dos contadores: processedNodeIds.add(id) vira audit trail pra Fase 4.1; genericTokensBefore/genericCostBefore guardam snapshot dos acumuladores globais pra calcular o delta desse nó depois em 3.9; nodeStartedAtMs marca o timer pra durationMs.
  • Clona o carrossel de preview responses: lê node.data.previewResponses pra um array local com até 10 itens (ring buffer com bug === 10 em vez de >= 10). Só handlers legacy usam esse cache — path Temporal persiste em node_executions.
  • Saída: node (ref viva), responses (array local), snapshots de tokens/cost e timer de duração — tudo pronto pro dispatch em 3.5. Zero I/O.
Contexto: o scheduler devolveu só um id em 3.1. Agora precisamos do node inteiro — inclusive campos data que já foram atualizados por nós anteriores neste mesmo run (ex: schema mutado, contentData preenchido). Essa referência é viva: mutar node.data aqui reflete no array pai (é o mesmo objeto), o que várias handlers dependem depois.

A myUpdatedNodes.find(node => node.id === id)
flux.service.ts:3241
const node = myUpdatedNodes.find(node => node.id === id);
Propósito: Busca linear pelo id no array myUpdatedNodes. Devolve referência — não cópia. Qualquer mutação em node.data nas etapas seguintes atinge o mesmo objeto que o próximo find vai encontrar.
Em resumo: é o arquivo vivo do run. O scheduler te deu só uma etiqueta (id), mas você precisa da pasta inteira do funcionário — com todos os documentos que outros nós já mexeram nele: schema atualizado, contentData preenchido, previewResponses acumulados. O find abre essa pasta no arquivo compartilhado (myUpdatedNodes) e te entrega a pasta original, não uma fotocópia. Isso significa que qualquer coisa que você riscar ou escrever nela vai aparecer pro próximo cara que abrir a mesma pasta. É o que permite handlers escreverem node.data.text = 'resposta do LLM' e o próximo nó já ver essa saída. Detalhe importante: se o find não achar (algum handler removeu o nó do array mas o scheduler ainda tem esse id na fila — bug latente sem repro conhecido), o loop não crasha — apenas pula pra próxima iteração com um if (node) { ... } silencioso. E outra coisa: é O(n) — em agentes com 1000+ nós, essa busca linear a cada iteração vai virar quadrática. Barato hoje, ofensor amanhã.
A1 Array de nós mutáveis do run
myUpdatedNodes foi inicializado no início do apiV2() a partir de newFlows (nós carregados em 1.3) e é reatribuído por vários handlers ao longo do loop:
• handlers Temporal: myUpdatedNodes = result.myUpdatedNodes (novo array)
• handlers inline: myUpdatedNodes = [...nodes]
• arrayNode: reescreve durante iteração

Por que isso aconteceria? Se um handler removeu um id do array mas o scheduler ainda tem esse id em ready (bug latente, sem repro conhecido).
flux.service.ts:3244
⚠️ Custo O(n) por nó
Array.find é linear no tamanho de myUpdatedNodes. Em agentes com 100+ nós, isso é 100 iterações internas × 100 nós no loop = 10.000 comparações — barato hoje, mas escalar pra 1.000+ nós vira O(n²).

Um Map<id, node> resolveria em O(1), mas exigiria manutenção sempre que myUpdatedNodes é reatribuído.
🎯 Reatribuição vs mutação
Alguns handlers reatribuem myUpdatedNodes (novo array). Outros mutam campos in-place em node.data. As duas coisas convivem — pra saber qual precisa ler o handler específico. Consistência não é garantida.
🔧 Silent skip quando node = undefined
O guard if (node) engole o caso sem log. Se o scheduler agendou um id que não existe mais em myUpdatedNodes, o loop apenas prossegue pro próximo — sem marcar como completed nem dead. Isso pode causar warning na Fase 4 (nós não-processados) mas sem crash.
B processedNodeIds.add + snapshot de tokens/cost
flux.service.ts:3245-3250
processedNodeIds.add(id); lastExecutedNodeId = id; genericTokensBefore = totalTokensUsed; genericCostBefore = totalCost; nodeStartedAtMs = Date.now();
Propósito: Registra pra usos posteriores: (i) que este id foi visto pelo loop (usado no aviso de Fase 4.1 sobre nós não-processados), (ii) snapshot de quantos tokens/custo já foram gastos antes deste nó — o delta é atribuído ao nó em 3.7 e 3.9.
Em resumo: é o carimbo de entrada do funcionário no ponto. Antes do trabalho começar, o sistema anota 4 coisas: (1) "esse cara passou por aqui hoje" (processedNodeIds) — vira audit trail pra Fase 4 detectar nós que ficaram órfãos; (2) "esse foi o último a entrar" (lastExecutedNodeId) — pro caso do run explodir, o catch top-level saber onde parou; (3) snapshot do total de tokens/custo já gastos no run inteiro até esse momento — pra depois do nó rodar, o passo 3.9 fazer a subtração totalTokensUsed - genericTokensBefore e saber exatamente quantos tokens esse nó específico consumiu; (4) marca o timestamp de início pra calcular durationMs. Nada disso executa o nó — é só preparação de contadores. O ponto sutil é o snapshot: os acumuladores totalTokensUsed/totalCost são globais do run, atualizados via callback onUpdateTokens durante streaming de LLM. A única forma de saber "quanto foi só desse nó" é fazer esse snapshot antes-depois — pattern simples mas essencial pro billing por nó.

nodeStartedAtMs é usado no branch de cancelamento (linha 4525: elapsedMs: Date.now() - nodeStartedAtMs) e no durationMs do RunLogNode. Marcar aqui garante que o timer captura toda a preparação do nó (substitution, RunLog, dispatch), não só a execução propriamente.
📎 lastExecutedNodeId
Usado pelo catch top-level (5.1) pra reportar onde parou quando algo explode. Também aparece em logs de webhook de erro. É uma string, atualizada a cada iteração — se o run crasha no meio de um nó, esse campo aponta pra ele.
🔧 genericRunLogNode = null
Inicializado como null. Vai ser preenchido em 3.4 exceto pra fluxBox/libraryNode (sub-run anchors — o coletor cria um documento aninhado em vez de um nó simples). Depois, 3.9 só chama endNode se genericRunLogNode ficou não-nulo.
C previewResponses (leitura do cache in-JSONB)
flux.service.ts:3270-3274
let responses = []; if (node?.data?.previewResponses?.length) { responses = [...node?.data?.previewResponses]; }
Propósito: Copia (spread) as respostas de preview já persistidas em flows_nodes.data pra um array local. Handlers de nós que produzem preview (voiceBoxNode, imageGenerator, audioReaderNode, etc.) usam esse array como base pra montar o próximo item do histórico.
Em resumo: é o carrossel de últimas fotos do nó — pense num painel na UI que mostra "veja as últimas 10 respostas que esse nó gerou". Esses históricos vivem dentro do JSONB de flows_nodes.data.previewResponses, e o loop clona esse array pro escopo local no início de cada execução. Handlers que produzem preview (TTS, imagem, áudio, HTML) recebem esse array como argumento, adicionam o novo item no fim, e no passo 3.6/L4 gravam de volta no banco. Se já tiver 10 itens, o mais antigo é descartado (shift) pra manter o carrossel no tamanho — mas a checagem é === 10, não >= 10, então se por bug o array chegou com 11+ ele só remove um e a próxima persistência já enche demais. Bug latente. O ponto crítico pra migração: previewResponses é o principal ofensor de perf de FE em agentes grandes. Cada item pode carregar texto longo, imagem base64, contentData inteiro — × 10 versões por nó × 100 nós = 1000 blobs vivos no JSONB. Handlers migrados pro worker (textGenerator, scripting, etc.) já não recebem esse array — persistem em node_executions.outputData, que é o padrão desejado.

C1 Passado por args para handlers
O array responses é passado a handlers como voiceBoxNode, audioReaderNode, commandContentNode, imageGenerator. Cada um push-a o novo item e grava node.data.previewResponses = responses na saída — persistido em flows_nodes.data no passo 3.6/L4.
flux.service.ts:3372, 3651, 6972, 7911
⚠️ Ring buffer só cuida de len === 10
O check é if (responses.length === 10). Se por algum bug o array chegou com 11+ itens (ex: dois handlers escreveram em ordem estranha), o shift acontece uma vez só, permanecendo com 10 ou mais na próxima persistência.

Não é robusto. Deveria ser while (responses.length >= 10).
🎯 Por que 10?
Limite arbitrário pra evitar que flows_nodes.data cresça indefinidamente por nó com histórico de reruns manuais. É o "carrossel de últimas respostas" que aparece na UI do canvas — permite o usuário navegar entre execuções recentes sem persistir tudo em node_executions.
⚠️ Origem do JSONB gordo
previewResponses é o campo campeão de RAM/perf pesada em flows_nodes.data. Cada item pode ter texto longo, image base64, contentData completo. Manter 10 versões por nó × 100 nós = 1000 blobs vivos no JSONB. É o motivo de agentes grandes terem FE travando ao abrir o canvas.
🔧 Path Temporal não usa isso
Handlers migrados pro worker (textGenerator, scripting, etc.) não recebem o array responses. O worker persiste output em node_executions.outputData — não replica em flows_nodes.data.previewResponses. Só o path inline (legacy) mantém esse cache.
Resumo — o que sai de 3.2:
• node — referência viva do array myUpdatedNodes (mutável)
• processedNodeIds ganhou 1 entrada (audit trail)
• lastExecutedNodeId = id do nó atual
• genericTokensBefore / genericCostBefore — snapshot pra calcular delta em 3.7
• nodeStartedAtMs — timer pra durationMs e telemetria de cancelamento
• responses — array local com até 10 preview responses (só usado pelo path inline)
• Nenhum I/O: 100% in-memory
Observações para migração:
• myUpdatedNodes.find é acoplado ao modelo "backend é orquestrador único". No worker, cada activity recebe o node por payload; sem array vivo, sem find.
• previewResponses precisa sair de flows_nodes.data. É o principal ofensor de perf de FE (memória [[project_jsonb_fat_fields]]). Migração vai levá-lo pra node_executions, o que já é o padrão do path Temporal.
• O snapshot de tokens/cost via variável local do loop não sobrevive num modelo onde cada nó é uma activity isolada — o worker cobra individualmente via HTTP /worker/charge-tokens (passo W7), e o backend agrega depois via sumChargesByExecution (T6).
• Bookkeeping (processedNodeIds, lastExecutedNodeId) hoje é usado em Fase 4/5 pra warnings e diagnóstico. No worker, essa informação pode vir do próprio WorkflowHistory do Temporal (mais confiável). É essencial mas simples de reimplementar.
• O bug do ring buffer (=== 10 em vez de >= 10) merece uma linha no plano de migração pra corrigir antes de portar.

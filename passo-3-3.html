Passo 3.3 — applySubstitutionToObject(node, schema)

Bloco em flux.service.ts:3280-3284 · engine em node-reference-substitution.service.ts:145-167. Percorre recursivamente o node e substitui todo {{...}} pelo valor real do nodeSubstitutionSchema (montado em 2.3, mutado ao longo do loop em 3.6).
Em resumo — o que esse passo faz
  • Preenche todos os buracos {{...}}: pega o node cru (com placeholders tipo "Escreva sobre {{tema}}") e devolve processedNode com tudo resolvido em texto concreto. É o ponto onde referências entre nós viram valores reais.
  • Walker recursivo sem whitelist: applySubstitutionToObject desce a árvore inteira do node — strings passam pelo regex, arrays viram .map recursivo, objetos ganham container novo. Nunca muta o original — retorna uma árvore paralela clonada, o que preserva o node cru pra retry.
  • Motor de placeholder navega paths com ponto: replacePlaceholders roda /{{(.*?)}}/g, splita por ., e vai andando no schema segmento a segmento. Se qualquer nó do path resolve undefined, deixa o placeholder literal no output — fallback silencioso intencional pra templates opcionais.
  • Cada nó vira 3 chaves no schema: stableKey (UUID), refKey (id legacy com dots→underscore) e labelKey (label humano). Todas apontam pra mesma entry — o usuário pode escrever {{writer}}, {{6d09d1...}} ou o refKey e todos resolvem igual. Colisões entre labels de nós diferentes são first-write-wins (footgun).
  • Handlers ignoram processedNode em partes: Temporal, voice, mcp usam processedNode; pull/push, condition, nodesBox, arrayNode, fluxBox usam node cru e fazem substitution interna própria — origem dos 57 sync sites espalhados pelo código.
  • Saída: processedNode resolvido (árvore paralela), node intocado. 100% síncrono, 100% in-memory — mas com memória gorda: schema × N nós × strings pode virar megabytes vivos.
Contexto: este é o ponto onde referências entre nós viram texto concreto. Antes: node.data.prompt = "Escreva sobre {{tema}}". Depois: processedNode.data.prompt = "Escreva sobre inteligência artificial". A função é síncrona e sem I/O — toda a resolução vem do schema in-memory (memória [[project_substitution_engine]]).

Resultado: processedNode — objeto novo com mesma estrutura de node, mas todo campo string teve seus placeholders resolvidos. O node original permanece intacto (não muta).
A applySubstitutionToObject(obj, schema)
node-reference-substitution.service.ts:145-167
applySubstitutionToObject(obj: any, schema: any): any
Propósito: Walker recursivo genérico. Cria uma nova árvore percorrendo obj. Sem whitelist de campos — aplica em tudo que for string. Sem clonagem prévia, sem deep-copy — o retorno é o próprio novo objeto montado nível-por-nível.
Em resumo: é o revisor de rascunho — pega o texto do nó cheio de {{...}} ("Escreva sobre {{tema}} para {{publico}}") e devolve uma versão limpa, com todos os buracos preenchidos. Só que ao invés de percorrer o texto de forma tradicional, ele desce recursivo pela árvore inteira do node: se topa com string, chama o motor de substitution (fn B); se é array, percorre cada item; se é objeto, cria um novo objeto e revisa campo por campo. O importante é que nunca muta o original — o node que veio como argumento continua intacto (com seus {{...}}), e o retorno é uma árvore paralela clonada. Isso é o que garante que se o handler falhar no meio, o node original ainda tá disponível pra retry. Não tem whitelist — aplica em todo campo string, inclusive coisas internas como _rawProviderResponse, _attempts. Não tem limite de profundidade — patologicamente pode dar stack overflow, mas nós reais ficam em 3-4 níveis. Este é o coração da substitution engine: os 57 sync sites que a memória menciona ([[project_substitution_engine]]) são todos variações desse walker, um dos ofensores centrais que a migração pro worker precisa reescrever ou eliminar via prefetch.
applySubstitutionToObject(obj: any, schema: any): any { if (!obj || !schema) return obj; if (typeof obj === 'string') { return this.replacePlaceholders(obj, schema); } if (Array.isArray(obj)) { return obj.map(item => this.applySubstitutionToObject(item, schema)); } if (typeof obj === 'object') { const result = {}; for (const [key, value] of Object.entries(obj)) { result[key] = this.applySubstitutionToObject(value, schema); } return result; } return obj; // number, boolean, null → inalterado }
↓
🪜 Dispatch por tipo
1 obj === null/undefined OU schema falsy return obj (early)
2 typeof obj === 'string' → replacePlaceholders (fn B)
3 Array.isArray(obj) .map(item => recursiva)
4 typeof obj === 'object' novo {} + Object.entries loop
5 tipo primitivo (number/boolean) return obj inalterado
🎯 Clonagem estrutural, não in-place
Cada objeto/array retorna um novo container (const result = {}). O node original nunca é mutado — o retorno é uma árvore paralela. Isso é o que garante que previewResponses antigos (lidos em 3.2) não vazem pra processedNode depois de a saída ser reescrita.
⚠️ Sem whitelist, sem limite de profundidade
A função aplica em todos os campos. Se node.data tem campos internos tipo _rawProviderResponse, _attempts, _modelId, eles também são copiados (e strings dentro também passam pelo regex).

Sem maxDepth. Um node.data patologicamente profundo pode dar stack overflow, mas nós de flow ficam em 3-4 níveis.
📎 typeof null === 'object'
O guard !obj (linha 146) já pega null. Se não fosse ele, o ramo do typeof obj === 'object' tentaria Object.entries(null) e explodiria.

B replacePlaceholders(str, schema)
node-reference-substitution.service.ts:5-23
replacePlaceholders(originalString: string, replacementSchema: any): string
Propósito: Núcleo da engine — encontra {{qualquer.coisa}}, faz split por ., navega o schema segmento por segmento. Se em qualquer ponto o lookup falha, devolve o match original (não resolvido).
Em resumo: é o dicionário chamado pra cada palavra entre chaves duplas. Recebe uma string como "Escreva sobre {{textGen1.text}} pro cliente {{clienteAtual}}", roda um regex /{{(.*?)}}/g pra achar todos os {{...}}, e pra cada um: pega o conteúdo (textGen1.text), splita por ponto (['textGen1', 'text']), e vai navegando o schema segmento a segmento — schema['textGen1'], depois .text. Se qualquer segmento retornar undefined, aborta e devolve o placeholder original literal ({{textGen1.text}} fica no output, sem substituir). Isso é comportamento intencional: permite prompts template com placeholders opcionais que só se resolvem se o dado existir. Ponto sutil: se o valor final for um objeto (não string), o String.replace coage pra "[object Object]" — quase nunca é o que o usuário quer. Por isso o passo 2.3 (generateSchemaFromNodes) achata objetos pra .text/.content/.result antes de indexar. E outra: a substituição é de esquerda pra direita, uma passada só — se um placeholder resolvido conter outros {{...}}, eles ficam literais (não é recursivo). Simples, previsível, mas exige que o usuário conheça essa restrição.
replacePlaceholders(originalString: string, replacementSchema: any): string { if (!originalString || typeof originalString !== 'string') { return originalString; } const result = originalString.replace(/{{(.*?)}}/g, (match, p1) => { const keys = p1?.split('.'); let value = replacementSchema; for (const key of keys) { value = value[key]; if (value === undefined) { return match; // não resolveu → mantém {{...}} } } return value; }); return result; }
↓
B1 Regex non-greedy: /{{(.*?)}}/g
.*? pega o menor match possível — pra "{{a}} e {{b}}" ele acha 2 grupos, não 1 gigante.
Aceita qualquer conteúdo entre {{ e }}, inclusive espaços, símbolos e paths com dots.
↓
B2 Navegação por path a.b.c
keys = p1.split('.'). Loop: value = value[key]. Se qualquer segmento retorna undefined, aborta e retorna o match original.

Suporta N segmentos. Casos comuns:
• {{textGen1}} — 1 segmento → objeto inteiro do nó
• {{textGen1.text}} — 2 segmentos → só o campo text
• {{age.text}} — usa labelKey (fn C)
⚠️ Coerção implícita string
Quando o value final é um objeto/array, o String.replace chama String(value) — vira "[object Object]" ou "1,2,3". Isso quase nunca é o que o usuário quer.

É por isso que generateSchemaFromNodes (passo 2.3) já achata objetos pra .text/.content/.result antes de indexar — pra evitar esse cenário.
💡 Fallback silencioso
Placeholder não resolvido não lança erro — apenas fica no output como {{nomeErrado}}. Handler downstream (ex: LLM) pode ver isso e reclamar, mas o loop segue.

É comportamento intencional pra permitir prompts template com placeholders opcionais.
🔧 Ordem de match
String.replace com regex /g aplica da esquerda pra direita, não recursivamente. Um placeholder cujo valor resolvido contém {{...}} não é re-processado nesta passada.
📎 typeof guard duplo
Tanto applySubstitutionToObject quanto replacePlaceholders checam typeof === 'string'. Redundante mas defensivo — a segunda checagem protege se replacePlaceholders é chamada direto (fora do walker).
C Schema: 3 chaves por nó (contrato)
node-reference-substitution.service.ts:82-143
generateSchemaFromNodes(nodes) — indexa cada nó sob stableKey (UUID), refKey (dots→_), labelKey (label sem espaços)
Propósito: Contexto do schema que 3.3 consome. Cada nó do flow vira 3 entradas no objeto nodeSubstitutionSchema — mesma referência de entry, chaves diferentes. Isso permite que o usuário escreva {{6d09d1...uuid}}, {{textBox_1714_0_8148}} ou {{writer}} e todos resolvam pro mesmo lugar.
Em resumo: pensa nas 3 chaves como 3 nomes que a mesma pessoa atende: o CPF (stableKey — UUID collision-free), o apelido do RG (refKey — id legacy com dots trocados por underscore) e o nome social (labelKey — o que o usuário digitou como "label" do nó, tipo "My Writer" → "mywriter"). Todas as 3 chaves apontam pra mesma entry — se o output do nó atualizar, atualiza pra todas simultaneamente porque é a mesma referência. Isso é o que dá flexibilidade pro usuário: no editor ele pode arrastar uma referência (usa o UUID por baixo dos panos) ou digitar {{writer}} na mão — os dois funcionam. Também é o que permite ids legacy com dots (herança de versões antigas) continuarem resolvendo — porque o parser de {{path.field}} splitaria no dot errado. Cuidado com colisões: se dois nós têm o mesmo label, o segundo não sobrescreve o primeiro (o check labelKey !== stableKey && labelKey !== refKey só cuida disso dentro do mesmo nó), mas o escopo do labelKey de nós diferentes é first-write-wins — footgun quando alguém duplica um label sem perceber. A whitelist basedOnType (linhas 25-80) define quais campos de cada tipo aparecem na entry — não é o walker que filtra, é o indexing que já entrega só o essencial (prompt, text, url, etc.).

⚠️ Whitelist basedOnType é INDEXING
basedOnType (linhas 25-80) define quais campos do node.data são indexados por tipo. Só campos listados aparecem no entry — ex: textBox só expõe text; apiCaller expõe url/jsonRequestBody/etc.

Mas ATENÇÃO: a whitelist é da geração do schema, não do walker. O walker (fn A) aplica em tudo. A whitelist só filtra o que fica disponível pra ser referenciado.
🎯 Precedência de lookup
Não existe. Todas as 3 chaves apontam pra mesma entry. Se o usuário escrever {{writer}} ou {{6d09d1...}}, o resultado é idêntico. A "escolha" da chave é do usuário no editor.

Colisões (label = outro nodeId) não são tratadas — o if (labelKey && labelKey !== stableKey && labelKey !== refKey) só evita sobrescrever a si mesmo, não colisões entre nós diferentes.
🔧 Objetos achatados no indexing
Se node.data.prompt é um objeto (não string), generateSchemaFromNodes extrai .text → .content → .result nessa ordem. Fallback: JSON.stringify(value). Isso não acontece no walker — só no schema build.
D processedNode (variável do loop)
flux.service.ts:3280-3284
const processedNode = this.nodeReferenceSubstitutionService.applySubstitutionToObject(node, nodeSubstitutionSchema);
Propósito: Consumidor final da engine. É o que os handlers de nó (inline ou Temporal) recebem como input já resolvido. Alguns handlers usam processedNode, outros usam node — a distinção não é uniforme e é um dos footguns do código atual.
Em resumo: imagina que node é o original manuscrito do documento (com anotações, referências pendentes, o rascunho) e processedNode é a versão datilografada, com todos os buracos preenchidos e pronta pra ser lida. O loop entrega os dois pros handlers, e aí começa a confusão: processNodeViaTemporal, voiceNode, thirdPartyIntegrationNode, mcpNode usam processedNode (a versão limpa) — perfeito. Mas pullDataNode, pushDataNode, conditionNode, nodesBox, arrayNode, fluxBox, libraryNode usam node cru — fazem sua própria substitution internamente. Não tá documentado no código quem usa o quê; é convenção ad-hoc que só se aprende lendo cada handler. É por isso que existem 57 sync sites de substitution: cada handler que ignora processedNode reimplementa parte da engine com regras próprias, e sincronizar todas essas variações é o pesadelo de qualquer refactor. Outro footgun: mutar processedNode.data não afeta o array myUpdatedNodes (é árvore paralela clonada) — mutar node.data afeta (é ref viva). Quem tentar "corrigir" o output escrevendo em processedNode vai perder a mudança silenciosamente.

⚠️ Handlers que ignoram processedNode
pullDataNode, pushDataNode, conditionNode, arrayNode, nodesBox, fluxBox, libraryNode recebem node cru. Eles fazem sua própria resolução (via schema: mutatedSchema ou reimplementação parcial).

Resultado: a substituição é feita 57 sync sites, alguns explícitos como este 3.3, outros escondidos dentro dos handlers.
🎯 Por que processedNode é "puro" mas node é "vivo"
node é a referência do array myUpdatedNodes — se um handler mutar node.data.text, o próximo find em 3.2 pega esse valor. processedNode é uma árvore paralela — mutá-la não reflete de volta no array.

Isso não é documentado no código. É fonte comum de bugs quando alguém tenta "corrigir" o output escrevendo em processedNode.data.
🔧 mutatedSchema é o mesmo objeto
let nodeSubstitutionSchema e let mutatedSchema em apiV2() apontam pro mesmo schema — nomes duplicados por refactor incompleto. Ambos são passados aos handlers. Reatribuir um não afeta o outro (footgun).
Resumo — o que sai de 3.3:
• processedNode — árvore nova com todo {{...}} resolvido em campos string
• node permanece intacto (mesma ref do array myUpdatedNodes)
• Placeholders não resolvidos ficam literais no output ({{nomeErrado}})
• 100% síncrono, 100% in-memory, sem I/O
• Tempo O(size(node.data) × avg-placeholders-per-string)
Observações para migração:
• Este é o ofensor da migração pro worker (memória [[project_substitution_engine]]). São 57 sync sites, alguns explícitos (3.3), outros escondidos em cada handler legacy. O worker não tem engine de substitution — recebe input já resolvido.
• A whitelist basedOnType é hard-coded em node-reference-substitution.service.ts:25-80. Cada tipo novo que precisar de campos referenciáveis exige editar essa lista. Prefetch mode e worker também têm listas paralelas — três lugares pra manter sincronizados.
• A ausência de resolução recursiva (placeholders dentro de outputs resolvidos) é intencional mas frágil. Migração pode escolher: (a) suportar via 2ª passada, (b) proibir explicitamente, (c) manter o comportamento atual documentado.
• processedNode é temporário — não persistido em lugar nenhum. Se um nó falhar após substitution mas antes de gravar, o input resolvido é perdido. No path Temporal, o INSERT em node_executions (passo T2) grava justamente esse input resolvido — pattern superior.
• 3 chaves × N nós × strings dentro de cada = memória do schema cresce O(nodes × avg-fields × avg-string-size). Em agentes grandes com respostas de LLM longas, o schema fica com megabytes de JSON vivos.
• É essencial e crítico — todo o modelo de propagação de dados entre nós depende disso. Migração pro worker precisa desenhar um modelo alternativo (prefetch por refs já é uma tentativa) antes de tocar nesse código.

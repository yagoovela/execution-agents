Companion — the plan as tasks

Companion to arquitetura-v2.html · it does not replace the design, it maps what has to exist around it
The v2 draws the destination: bootstrap in Temporal, an immutable DAG, a parallel wave loop, lanes for the special nodes, cancellation by signal and retry by policy. This document does not argue with that design — it takes it as correct and answers a different question: what has to be in place before phase 3 can be switched on without breaking anything, and in what order that is delivered. Every item carries its task and the wave it ships in. Where the v2 already resolves something, it is marked as such.

PHASE 1 — Reception and scheduling
detail →
The v2 draws the endpoints and the queueing. What it does not draw is who is entitled to create a run.
▸the v2 already resolves it
What the v2 already resolves
The three response modes of /flux/api-v2 and the split between a full agent and a single node. /flux/api-v2 became asynchronous in production on 24 August, which is already half of this phase.
⚠missing, or blocking
Three of the four entry points do not authenticate
/flux/api-v2-webhook is @Public() and its where matches any flow, public or private. The email trigger authorises a private flow on a forgeable From header, with no DKIM, and a public flow not at all — with the sender controlling the prompt. And none of the four is rate limited.

⚠missing, or blocking
Every scheduled trigger counts once per replica
Fourteen crons with no leader election, user schedules in NestJS's in-process registry, and a POP3 poll every ten seconds. Adding the second backend replica multiplies all three. Temporal Schedules solves the second by construction and is not in use.

⚠missing, or blocking
The batch has no phase here at all
/flux/batch-process calls processBatch without await: a sequential for of complete runs, detached inside the API process, that dies silently on a deploy. It is the largest multiplier of every missing ceiling.
B7wave 5
+the plan builds it
A ceiling on concurrent runs per tenant
Today @Process with no concurrency option serialises one run per replica — accidental protection that phase 3 removes deliberately.

PHASE 2 — Workflow bootstrap inside Temporal
detail →
Snapshot, immutable DAG, OutputStore. This is where the plan has least to add and most to confirm — the design is right.
▸the v2 already resolves it
The immutable DAG already exists as pure code
The builder the v2 describes is scheduler.ts: no injection, no database, already the single source of ordering truth and already consumed by the engine and by the MCP write service. It does not need rebuilding — it needs moving.
B2wave 4
+the plan builds it
The OutputStore key must name one execution
(execId, nodeId) names a node within a run, not an execution of it. Inside a loop the same node runs several times, there is no unique constraint, persistNodeSuccess updates every matching row and fetchNodeRow takes rows[0] with no ORDER BY.
B1wave 4
▸the v2 already resolves it
Reference-based resolution is already in production
The prefetch executor already resolves each node's input by reference, behind FLUX_EXEC_MEMORY_MODE, with a 17-type whitelist. The model the v2 proposes exists; the work is to widen it, not to design it.
B3wave 4
⚠missing, or blocking
Snapshot and DAG in workflow state grow with the run
The worker uses no continueAsNew anywhere. One workflow per run accumulates history with every activity scheduled and every value passed, and is terminated by the platform on exactly the largest runs. Passing state by reference, not by value, is what the execution key makes possible.
B4wave 4
⚠missing, or blocking
The v2's cycle validation is intra-graph
It catches cycles between nodes of the same flow. It does not catch flow A calling B calling A — flowCallerNode re-enters the whole orchestrator with no depth limit and no cycle detection.

PHASE 3 — Parallel wave loop
detail →
The heart of the v2, and where nearly all of the plan lands. Nothing here contradicts the design; everything here is a precondition for it.
+the plan builds it
Moving the loop and turning on parallelism are two deploys
The v2 describes the end state. The path there goes through shipping the workflow sequential first — allReady returning one id is today's behaviour. Shipping both together leaves a rollback unable to say which one broke it.
B4wave 4 B5wave 5
⚠missing, or blocking
The database hits its ceiling before throughput does
The worker pool sets no max — ten connections per process by default, with activity concurrency at ten. Connections scale linearly with replicas against a max_connections shared with the API, and the failure mode is too many clients on the API too.
S2wave 1
⚠missing, or blocking
Nothing limits what a run spends
The credit check is a boolean gate, not a budget, and charges are recorded after the fact. On a paid account there is no per-run ceiling — the first signal is the invoice.
S3wave 1
⚠missing, or blocking
Parallelism is only safe with full coverage
Nodes still running inline in the back do not write to their own row: they end with addConnectToNodes, which merges the producer's output into the target node's data. All-backend is safe because it is serial; all-worker is safe because every write is own-row. Mixing the two in parallel is a lost update.

PHASE 3½ — Special nodes
detail →
condition · arrayNode · subflowNode. The v2 is right to give them their own lanes — they genuinely break the one-dispatch-one-output semantics.
+the plan builds it
Control flow belongs to the workflow, not to an activity
conditionNode rewrites the engine's work queue and mutates a loop counter in place; arrayNode is a for over a sub-graph by index arithmetic. An activity's return value does not reshape the caller's iteration.
B6wave 5
⚠missing, or blocking
A child workflow turns the recursion into a fleet problem
Today flow A → B → A recurses until one process's memory runs out. As a child workflow, a durable platform sustains it across the whole fleet, with retries. The depth ceiling and the inter-flow cycle detection must exist before this phase.
S1wave 0
⚠missing, or blocking
The loop ceiling can be switched off by the node's own data
evaluateLoopCondition only applies the limit when loopBehavior is continue. On the other branch the limit is computed, reported to the UI and ignored — and the count is user data anyway.

+the plan builds it
The Object Caller breaks the semantics too
nodesBox mutates object data and session state mid-run. It is the only one in the group with extractable logic, but it needs two new callbacks and an explicit answer on ordering — today the engine serialises that by accident.

PHASE 4 — Finalisation
detail →
Assemble the result and persist the artefacts. Two things change home here, and one of them is a security matter.
⚠missing, or blocking
The run-log tree cannot live in the workflow
RunLogCollector keeps a hierarchical tree in memory, and the product's nested timeline depends on it. Keeping the tree inside the workflow makes state grow with the run — it collides directly with the history limit from phase 2. Event-sourced reconstruction is the only shape compatible with both.
E1wave 4
⚠missing, or blocking
redactSecrets is the only scrubbing point
It is the only place credentials are cleaned before reaching space_run_logs. It changes home along with the collector: a refactor that drops the hook turns a logging change into a credential disclosure.
E1wave 4
⚠missing, or blocking
Emails and callbacks are fire-and-forget
The ~300-line block at the end of every run fires axios.post and three email paths, each in a catch, with no retry. The Redis dedup keys already exist precisely to make retry safe — only the retry is missing.

PHASE 5 — Cancellation by signal
detail →
The v2 gets this one entirely right. The complement is only to say how much is gained and what has to be retired alongside.
▸the v2 already resolves it
Aligning beats porting
nodeCancelContext is AsyncLocalStorage and does not cross processes. Temporal already gives native cancellation through WorkflowHandle.cancel() and Context.current().cancelled, and propagates to child workflows for free — which phase 3½ will need.
E2wave 4
⚠missing, or blocking
The current design costs one timer per node
A sixty-node agent holds sixty setIntervals hitting the database. Behind a flag that is tolerable; on by default it becomes a performance offender. There is also a latent race: a 1500 ms cache over a 2000 ms poll leaves up to 3.5 s between the click and the effective cancel.

PHASE 6 — Errors and retry
detail →
RetryPolicy per node type. The piece the v2 needs already exists in the worker — worth crediting rather than rebuilding.
▸the v2 already resolves it
The error taxonomy is already there
UserConfigError, IntegrationError, ProviderError, TimeoutError and SystemError already exist in the worker, and that is what keeps a user's typo from retrying for thirty minutes. The v2's RetryPolicy derives from it.
⚠missing, or blocking
Fix the defects before the code is duplicated
The previewResponses trim uses strict equality at six sites; endNode is called twice on the same handle; api-caller-polling.ts has no importer. Once duplicated, each fix costs twice.

The rule that sets the order: the system is protected today by three accidents — the sequential loop, one queued run per replica and the blocking wait. None was designed as a safeguard, and all three disappear when phase 3 is switched on.

B flowService.resolveExecutionHistoryId()
src/app-api/folw/flow.service.ts:82-100
async resolveExecutionHistoryId(flow: Flow, requestedVersionId?: string, requestedHistoryId?: string): Promise<string | null>
Propósito: Decide de qual "snapshot" de nós/arestas a execução vai ler — flow_version_history_id (versão congelada) ou null (working copy live). Chamada duas vezes: uma dentro de (A), outra explicitamente pelo apiV2() para gravar flowVersionHistoryId no contexto.
Em resumo: pense nela como um "árbitro" que responde uma pergunta única: "de qual foto do agente eu vou executar agora?". Ela vai testando alternativas em ordem — se o flow nem tem versionamento ligado, roda a versão de trabalho atual; se veio um histórico específico no request, usa esse; se veio um versionId, busca o histórico correspondente dele; se o flow tem uma versão marcada como "deployada" (a de produção), usa ela como fallback; caso contrário, roda também a versão live. É o que garante que uma execução seja reproduzível: mesmo que alguém edite o agente cinco minutos depois, quem estava executando continua vendo exatamente a foto que começou a rodar.

D productService.assertOwnerCanRunFlow() condicional
src/app-api/product/product.service.ts:364-389
async assertOwnerCanRunFlow(flow: Flow): Promise<void> // throws se bloqueado
Propósito: Billing gate — verifica se o owner do flow (não o caller) tem plano ativo que permite executar agentes. Bloqueia flows cujo dono está em plano Vault (read-only).
Chamada apenas se !isNestedRunLog — não é aplicada a flows chamados via fluxBox/libraryNode internamente.
Em resumo: se a (C) era o porteiro do usuário, essa aqui é a régua de faturamento do dono do agente. Ela responde: "beleza, o cara pode rodar, mas quem paga a conta desse flow tem plano ativo pra rodar agentes?". Ela descobre quem é o "admin cobrável" do flow (se estiver numa company, é o admin da company; senão, é o próprio criador), consulta o plano ativo desse admin e, se o plano for do tipo Vault (read-only, típico de assinatura expirada), bloqueia a execução com 403 mesmo que o caller tenha permissão. Só roda no nível topo da execução — se este flow já é um sub-flow chamado por outro (via fluxBox/libraryNode), pula a checagem porque o billing do dono já foi validado lá em cima.

⚠️ Diferença crítica vs (C)
(C) checkIfUserCanRunFlow — verifica o caller (quem chamou a API)
(D) assertOwnerCanRunFlow — verifica o owner do flow

Um usuário livre pode ser bloqueado se estiver rodando um flow cujo dono está em Vault.
🎯 Por que só se !isNestedRunLog?
Se este flow foi chamado por outro flow (via fluxBox/libraryNode), a checagem de billing já foi feita no top-level. Chamar de novo em nested seria redundante e potencialmente confuso (mesmo owner, mesma resposta).
🔧 Vault plan
Plano "read-only" onde:
• product.can_run_flows = false
• product.can_create_items = false

Usado quando a assinatura expirou mas os dados devem permanecer acessíveis.
🔧 Ordem de resolução do owner (selectFlowAdmin)
1. Prioriza space company admin se flow está em space
2. Fallback pra companyUser company admin se flow é de companyUser
3. Senão retorna o user criador direto do flow

Isso significa que a cobrança/billing recai sempre no admin da company, não no dono real do flow em ambientes multi-tenant.
Resumo — o que sai de 1.3:
• getFlow populado com .nodes, .edges, .user, .folder, .folder.spaces, .folder.spaces.company, .folder.companyUser, .library
• flowVersionHistoryId (uuid ou null) — chave que amarra qual snapshot congelado usar

Observações para migração:
• As 3 queries de carregamento (flow + nodes + edges) são feitas no backend antes de qualquer decisão de dispatch. Se o worker for orquestrar, ele vai precisar dessa mesma tríade — ou receber tudo serializado no start do workflow, ou refazer as queries lá.
• A camada de permissões (C+D) é 100% relacional (users, company_user, user_product, folder.spaces) — replicá-la no worker significa expor esses schemas ou manter o gate no backend antes de iniciar o workflow.
• A cascata de selectFlowAdmin é sensível a mudanças de estrutura de company: qualquer refactor do multi-tenancy vai afetar o billing gate.

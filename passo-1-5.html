Passo 1.5 — Carregamento de objetos personalizados

Bloco em flux.service.ts:2439-2462. Resolve quem é o dono dos objetos (space, companyUser ou user) e carrega os UserObject daquele owner. Objetos são JSONs personalizados que o node nodesBox lê e (às vezes) escreve durante a execução.
Em resumo — o que esse passo faz
  • Descobre de quem é a gaveta de objetos: cascata em 3 opções mutuamente exclusivas — se o flow está num space, os objetos são do space (colaborativo); senão, se o usuário tem selectedCompanyId, confere no banco a relação CompanyUser; senão, fallback pros objetos pessoais do próprio user.
  • Puxa todos os objetos daquele dono: getObjectsByOwner monta um WHERE clause dinâmico (space_id / company_user_id / user_id) e faz SELECT * FROM user_objects sem paginação. Se o owner vier vazio, o WHERE vira {} — footgun que traz tudo de todo mundo.
  • Traduz entity → DTO: toJsonArray é um mapper puro que renomeia objectId para id, joga fora colunas de ownership/timestamps e devolve FluxObject[] no shape flat que o frontend e o nodesBox esperam.
  • Configura o carteiro de mutação: cria o closure onMutateObjectCallerData que permite ao handler do nodesBox reescrever a lista durante a execução — mudanças feitas por um nó ficam visíveis pro próximo. É reatribuição de referência (let), não mutação in-place.
  • Saída: objectCallerData = FluxObject[] pronto pra ser lido pelos handlers de nodesBox na Fase 3, mais o callback onMutateObjectCallerData que mantém essa lista sincronizada entre nós ao longo do run.
Contexto: objetos personalizados são estruturas de dados nomeadas (chave-valor + sessions) que o usuário define no editor e o nó nodesBox usa como storage. São carregados uma única vez aqui e passam a referenciar objectCallerData mutável ao longo do loop.

A Resolve ObjectOwner (3 fallbacks)
flux.service.ts:2439-2454
let objectOwner: ObjectOwner; // { userId? } | { companyUserId? } | { spaceId? }
Propósito: Decide de qual escopo os objetos personalizados vêm — space (compartilhado), companyUser (privado dentro de uma company) ou user (privado pessoal). Cascata em 3 casos exclusivos.
Em resumo: pense nessa parte como um cadastrador que precisa responder uma pergunta antes de qualquer coisa: "essa gaveta de objetos personalizados é de quem?". Ela testa em ordem: (1) se o flow vive dentro de um space, a gaveta é do space (compartilhada com o time); (2) se não tem space mas o usuário está logado numa company, ela vai no banco confirmar essa relação — se achar, a gaveta é do companyUser; senão cai pro pessoal; (3) se não veio nem space nem company selecionada, a gaveta é do próprio user. O resultado é um objetinho { spaceId }, { companyUserId } ou { userId } — mutuamente exclusivo — que os próximos passos usam pra filtrar exatamente uma prateleira no banco.

ObjectOwner é um union type mutually-exclusive
interface ObjectOwner { userId?: string; companyUserId?: string; spaceId?: string; }

🎯 3 modos de ownership de objetos
1. Space — objeto compartilhado entre todos os membros do space (colaboração)

2. CompanyUser — privado dentro de uma company (o user pertence a essa company mas o objeto não é público no space)

3. User — privado, atrelado apenas ao usuário (uso pessoal, fora de qualquer company)
📎 Precedência: por que space primeiro?
Se o flow está em um space, faz sentido usar os objetos daquele space (contexto colaborativo). Só cai pra companyUser/user se o flow não estiver em space nenhum.

Nota: selectedCompanyId é o "workspace ativo" do usuário — mesma company pode ter multiple users, cada um com seus próprios objetos.
🔧 Como é usado no buildWhereClause
Depois em (C), buildWhereClause traduz esse ObjectOwner na coluna correta da tabela user_objects:
• spaceId → WHERE space_id = X
• companyUserId → WHERE company_user_id = X
• userId → WHERE user_id = X

São 3 colunas diferentes na mesma tabela — só uma é populada por row.

⚠️ Fallback {} do buildWhereClause
Se por algum motivo o objectOwner ficar vazio (todos campos undefined), o WHERE clause vira {} — que em TypeORM significa "trazer todas as rows".

D objectsService.toJsonArray()
objects.service.ts:43-57

Propósito: Mapper puro. Converte a entity UserObject (que tem objectId, colunas de owner separadas, etc.) para o DTO FluxObject que o frontend/nodesBox espera (com id em vez de objectId, sem colunas de ownership).
Em resumo: é o tradutor — uma função pura, sem I/O, que só troca a embalagem. As entidades vindas de (C) têm um monte de coisa que o frontend não precisa ver (a PK real do banco, as colunas de dono, timestamps do TypeORM) e usam objectId como chave lógica. Aqui elas são remapeadas num formato mais enxuto: id (que na verdade é o objectId), name, text, sessions, etc. Depois desse passo, quem consumir a lista (o próprio nodesBox e o frontend) trabalha com FluxObject[] — sem risco de vazar detalhes internos do banco nem PK real.

E onMutateObjectCallerData (callback)
flux.service.ts:2460-2462
const onMutateObjectCallerData = (data) => { objectCallerData = data; };
Propósito: Closure que permite ao nodesBox mutar a lista de objetos durante a execução do agente. Sem essa referência mutável, mudanças feitas pelo nó não se propagariam pros próximos nós do mesmo run.
Em resumo: pense nele como um carteiro que fica entre os nós — quando um nodesBox altera algum objeto no meio da execução (grava um novo texto, muda a session ativa, adiciona uma linha), esse callback recebe a nova versão da lista e reatribui a variável objectCallerData no escopo pai. Assim, o próximo nó que ler a lista já vê o estado atualizado. É uma closure clássica de mutação: em vez de mutar o array no lugar, ele substitui a referência inteira pelo novo array que o handler devolveu. Segue o mesmo padrão de onMutateSchema e onUpdateTokens, e é o principal ponto de atrito pra qualquer migração pro worker — porque no worker os nós não compartilham essa memória e teriam que fazer round-trip pelo backend a cada mutação.

E2 Passado como argumento pro handler de nodesBox
Quando o loop principal (Fase 3) despacha um nó do tipo nodesBox, ele passa objectCallerData (valor atual) + onMutateObjectCallerData (callback pra mutação). O handler chama o callback se o object foi alterado, propagando pra próxima iteração.

Ver flux.service.ts:3575-3599, 4146-4174 (handler do nodesBox).
🎯 Padrão de closure mutation
É o mesmo pattern usado por onMutateSchema logo abaixo (linha 2465-2467) e por onUpdateTokens em Fase 3. Mantém a "fonte da verdade" no escopo do apiV2() e permite que services filhos atualizem sem passar referência de objeto.
⚠️ Race condition potencial
Se dois nós nodesBox rodarem em paralelo (não acontece no loop legacy hoje, mas em qualquer refactor de paralelismo virá à tona), a última chamada do callback ganha.

No worker isso seria pior porque o worker não compartilha essa closure — a mutação seria perdida.
🔧 Reatribuição, não mutação de array
O callback substitui a referência (objectCallerData = data) em vez de mutar o array in-place (objectCallerData.push(...)).

Isso é intencional: o handler do nodesBox retorna um novo array já com as mudanças aplicadas.
Resumo — o que sai de 1.5:
• objectOwner = ObjectOwner (space/companyUser/user, mutually exclusive)
• objectCallerData = FluxObject[] — lista dos objetos daquele owner, no formato flat esperado pelo frontend
• onMutateObjectCallerData = callback que o loop passa pro handler do nodesBox pra ele reescrever a lista durante a run
• Nenhum I/O pesado: 1 (raras vezes 2) SELECTs, sem paginação, sem cache
Observações para migração:
• A cascata de resolução do ObjectOwner (A) é business logic pura — replicável em qualquer lugar, mas precisa do flow.folder.spaces.id e do user.selectedCompanyId como input.
• O footgun do buildWhereClause retornando {} quando o owner é vazio é um alerta pra qualquer implementação nova: sempre garanta pelo menos userId antes de chamar.
• Se o worker precisar dos objetos, tem que receber o array já preparado no start do workflow OU fazer a query lá — mas nesse caso perde o padrão de closure mutation (o worker não pode alterar o array in-memory do backend depois).
• onMutateObjectCallerData é a maior dificuldade pra migração: nodesBox mutando objectCallerData durante a run é state compartilhado entre nós. No worker, cada nó executa isolado; qualquer mutação teria que ir via API call pro backend (custa round-trip por nó de nodesBox).
• Sem esforço de refactor, 1.5 pode continuar no backend mesmo depois da migração — é rápido e o resultado é passado nos start-args do workflow.

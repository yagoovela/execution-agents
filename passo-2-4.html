Passo 2.4 — Setup do RunLogCollector (plumbing)

Bloco em flux.service.ts:2290-2293 (init) e 3810-3818 (startLoopBody dentro do arrayNode). Diferente do 1.4 (que cria o collector via createRoot()), 2.4 é o plumbing cross-cutting — como o collector flui através de sub-runs (fluxBox/libraryNode) e iterações de loop (arrayNode).
Contexto: RunLogCollector é a espinha dorsal do observability da execução — captura árvore hierárquica de RunLogNodes por run. Em top-level, é criado em 1.4 via createRoot(); em sub-runs (agente que chama outro agente), é injetado como parâmetro; dentro de loops, é especializado via startLoopBody. Este passo mapeia os 3 modos.
Padrões de plumbing em 2.4
AInit pattern (injected ?? null) → BcreateRoot fallback (1.4) → CstartNode por iteração → DstartLoopBody (arrayNode) → EstartSubRun (fluxBox/library)
Resultado final: uma árvore de RunLogNodes montada em memória (via innerSteps + subRun) que é serializada em run_log_documents pelo spaceRunLogsService.
A Init pattern (injected vs null)
flux.service.ts:2290-2293
let runLogCollector: RunLogCollector | null = injectedRunLogCollector ?? null; const isNestedRunLog = !!injectedRunLogCollector;
Propósito: Detectar se este apiV2() é um run top-level ou sub-run chamado por outro agente (fluxBox/libraryNode). Sub-runs recebem o collector do pai como parâmetro (injectedRunLogCollector) — logs vão pro documento raiz do pai, não criam documento novo.
Em resumo: pense num cartório que anota tudo que aconteceu numa execução. Essa função é a "recepção" desse cartório — quando alguém chega, ela pergunta: "você é um cliente novo (top-level) ou tá vindo continuar um registro que já foi aberto lá em cima (sub-run)?". Se um agente chamou outro (via fluxBox ou libraryNode), o pai já entregou o "livro de registros" (o collector) na porta — a função só pega esse livro e continua escrevendo nele, e marca isNestedRunLog=true pra avisar o resto do fluxo que já tem alguém cuidando disso. Se não veio ninguém, ela deixa runLogCollector = null por enquanto e joga a criação do livro pra frente (pro passo 1.4).

1 injectedRunLogCollector presente? nested: reusa
2 senão top-level: null (vai criar em 1.4)

A2 Chamadores que injetam
fluxBox handler (flux.service.ts:4350) e libraryNode handler (4394) chamam this.apiV2({ ..., injectedRunLogCollector }) quando executam o sub-flow. Ambos pegam collector via startLibrarySubRun ou similar (ver Card E).
🎯 Por que passar collector, não criar de novo?
Um agente que chama 3 sub-agents cria 3 sub-documentos (via startFlowCallerSubRun) — mas todos vivem dentro do mesmo documento raiz. UI mostra a hierarquia. Se cada sub-run criasse doc próprio, perderia a árvore.
⚠️ Injected pode ser null mesmo pra sub-run
Se o parent não tinha logging habilitado (fora de space, ou space sem loggingEnabled), o parent tem runLogCollector = null. Aí ele passa null pro filho, e o filho não vai logar tampouco. Sub-run só loga se parent logava.
🔧 runLogSpaceId — sibling variável

B createRoot fallback (delegado ao 1.4)
flux.service.ts:2386-2437 · run-log-collector.ts:200-246
if (!isNestedRunLog && loggingEnabledForSpace && spaceOwnerId) { runLogCollector = RunLogCollector.createRoot({...}); }
Propósito: Se é top-level E o space tem loggingEnabled, cria o collector root. Se não, runLogCollector continua null e todos os runLogCollector?.startNode(...) viram no-ops via optional chain.
Em resumo: continuando a analogia do cartório — essa aqui é a abertura oficial do livro de registros. Só rola se três condições baterem: (1) é execução top-level, (2) o space tem logging ligado, e (3) tem um dono do space definido. Se tudo passar, chama createRoot() que monta um RunLogDocument zerado em memória e devolve o collector já plugado no scheduleUpsert pra ir salvando no banco. Se falhar, runLogCollector fica null — e aí entra o macete: o resto do código usa runLogCollector?.startNode(...) com optional chain, então tudo continua rodando normal, só que sem gravar log em lugar nenhum. É como ter um "modo silencioso" que não precisa de if em cada chamada.

C runLogCollector?.startNode() em cada iteração
flux.service.ts:3288-3295 · run-log-collector.ts:319-335
genericRunLogNode = isSubRunAnchorNode ? null : (runLogCollector?.startNode({ nodeId, nodeType, label, settings }) ?? null);
Propósito: Toda iteração do loop principal abre um RunLogNode (elemento na árvore) — exceto se o nó é anchor de sub-run (fluxBox/libraryNode), que precisa de tratamento especial (Card E).
Em resumo: aqui o collector vira cadastrador de linha por linha no diário da execução. Toda vez que o loop principal vai rodar um nó, essa chamada abre uma "entrada" nova na árvore com o nodeId, o tipo do nó, o rótulo e as settings já com as substituições {{...}} resolvidas — ou seja, o input real que o handler vai enxergar. A função devolve um handle (o genericRunLogNode) que depois vai ser usado no endNode pra fechar a entrada com o resultado. Tem uma exceção: se o nó é um fluxBox ou libraryNode (que dispara sub-execução), pula esse startNode genérico — o handler desses casos monta a estrutura correta com subRun (Card E). Cada push também aciona o flush pra ir salvando de forma incremental.

🎯 Ciclo de vida por nó

⚠️ Flush a cada evento
Toda startNode/endNode/startLoopBody/etc chama flushRoot(). Isso dispara scheduleUpsert — não faz UPSERT direto, mas agenda. Um flow de 200 nós = 400+ agendamentos. Vale conferir se o schedule tem debounce (provavelmente sim).
🔧 settings é o node.data pós-substituição
Já com {{...}} resolvidos. Isso é o snapshot do que o handler vai receber. Útil pra debugging: mostra o input real, não o template.
D startLoopBody (arrayNode iterations)
flux.service.ts:3810-3818 · run-log-collector.ts:252-275
const loopRunLogNode = runLogCollector?.startNode({...}); const loopRunLogCollector = runLogCollector?.startLoopBody(loopRunLogNode) ?? runLogCollector;
Propósito: Quando o loop principal encontra um arrayNode, cria um RunLogNode especial pro loop e devolve um sub-collector cujas entries vão em innerSteps desse nó. Cada iteração do body é registrada como filho do loop, não como sibling.
Em resumo: imagine que dentro do diário você tá abrindo uma pasta com sub-abas pra organizar melhor. Quando o run bate num arrayNode, essa função faz duas coisas: primeiro abre um nó "pai" no log dizendo "vou rodar N iterações"; depois entrega um collector especializado (o loopRunLogCollector) que, em vez de anotar as coisas ali no nível de cima, vai empilhando tudo dentro do innerSteps desse nó pai. Assim a UI consegue mostrar o loop expansível ("clica aqui pra ver as 50 iterações desse arrayNode"), em vez de despejar tudo numa lista plana gigante. Se o parent estiver desabilitado, cai no fallback e usa o collector normal — nunca quebra.

🎯 Por que sub-collector, não sub-node?
Poderia gravar cada iteração como sibling no doc raiz. Mas o schema de RunLogNode.innerSteps permite mostrar UI como árvore: expande arrayNode → vê iterações → cada iteração tem seus nodes. Muito mais legível que lista plana com 200 entries.
⚠️ Iterações não distinguidas por índice
Todas as iterações apendam em innerSteps — não há campo iterationIndex. Se você abre 3 iterações de 5 nós cada, vê 15 entries seguidas. Ordem preserva ordem de execução mas requer contar mentalmente.
🔧 startLibrarySubRun
Mesma coisa, mas kind='library'. Usado pelo libraryNode handler. Semanticamente idêntico ao loopBody, só muda o rotulo.
E startFlowCallerSubRun (fluxBox anchor)
run-log-collector.ts:277-317 · flux.service.ts:4350 (fluxBox)
const sub = runLogCollector?.startFlowCallerSubRun(parentNode, { flowId, flowName, input });
Propósito: Quando um fluxBox chama outro flow, cria um subDoc aninhado (não innerSteps — outro documento inteiro). O parent node ganha subRun em vez de innerSteps. UI mostra "este nó rodou este sub-flow inteiro".
Em resumo: se o loop era "abrir uma sub-aba", esse aqui é anexar um documento inteiro dentro do documento principal. Quando um nó fluxBox chama outro agente completo, essa função monta um subDoc novinho (com seus próprios rootFlowId, rootFlowName, nodes: [], etc.) e enfia ele no campo subRun do nó pai. Aí a UI consegue mostrar breadcrumb tipo "Agente A → Agente B → nó X" em vez de misturar tudo no mesmo nível. Detalhes importantes: o processId continua o mesmo (é a mesma execução física), o spaceId/orgId são herdados do ancestor (mesmo que o sub-flow seja de outro space) e tudo continua flushando pro mesmo documento raiz físico no banco — só que estruturado em camadas.

🎯 subRun vs innerSteps
innerSteps — nodes filhos do mesmo flow (loops, sub-tasks internas). Compartilha flowId/flowName.

subRun — chamou outro flow. Tem próprio rootFlowId/rootFlowName. UI mostra breadcrumb ("Agente A → Agente B → nó X").
⚠️ Herança de campos ancestor
subDoc.spaceId = ancestor.spaceId — sub-run herda sempre. Se o sub-flow tá em space diferente do parent, os logs vão pra org/space do parent. Pode não ser o desejado semanticamente, mas mantém a árvore consistente.
🔧 SubKind enum
'library' | 'flowCaller' | 'loopBody'. 3 categorias de sub-collector, cada uma com semântica levemente diferente. FlowCaller cria subRun/subDoc; outras 2 usam innerSteps.
Resumo — o que sai de 2.4:
• runLogCollector: RunLogCollector | null — pronto pra ser usado por handlers da Fase 3
• isNestedRunLog: boolean — flag consumida em 3 gates ao longo do run
• Padrão ?. em todos os call sites — logging opcional sem branches
• Árvore RunLogNode se monta em memória durante o run, flushada via scheduleUpsert
Observações para migração:
• Este é o observability layer — não é essencial pra execução (loop funciona com collector null), mas é crítico pra debugging/UI/billing.
• Worker não tem collector — ele emite eventos via notifyStatusActivity (Redis pub/sub) e escreve em execution_logs. Backend consome esses eventos e reconstrói a árvore no doc raiz.
• Sub-runs (fluxBox/libraryNode) só funcionam síncrono hoje — passam collector por parâmetro. Se algum dia sub-runs virarem async (worker), o collector precisa serializar via processId + emitir eventos.
• startLoopBody/startLibrarySubRun retornam outra instância — cuidado com quem usa qual em Fase 3. Bug clássico: usar runLogCollector em vez de loopRunLogCollector dentro do loop = iterações viram siblings do loop, não filhos.
• Flush a cada evento pode virar bottleneck em runs enormes. Debounce/batch no scheduleUpsert ajuda.
• Idealmente, RunLogCollector é stateless por chamada — recebe evento, emite pra sink (Redis/DB/nothing). Hoje mantém árvore em memória — replicar isso no worker é complicado.

Size the database connections before adding workers

Know, and enforce, how many Postgres connections the worker fleet can hold — before anything in this epic adds a replica.

Deliverable
A sentence
The capacity arithmetic, with real numbers and a supported replica count. The config change is trivial once it exists.

database.service.ts constructs new Pool({...}) with no max. node-postgres then defaults to ten connections per pool, per process — and the worker runs maxConcurrentActivityTaskExecutions: 10 (worker.service.ts), so a replica can hold ten busy connections and the total scales linearly with replicas.

max_connections is a hard wall, and the wall is shared with the API. The failure mode is not a slow worker — it is too many clients already on customer-facing requests. No connection proxy appears in the compose files or the infra.

The decisions this task needs

Two calls have to be made before the config change means anything, and both are recorded under PLAN D8. Each one below opens to the options considered, what each costs the customer and costs us, and the option we would pick.
▸Decision S2-aPLAN D8Recommended — confirmWhat sets the worker pool's max, and where does the number come from?
The spec states this as an assumption rather than a decision: max equal to maxConcurrentActivityTaskExecutions plus two, the two being headroom for the health check and for anything that opens a connection outside an activity. It is worth confirming out loud because of a detail that is easy to miss: the pool ceiling today is also ten — node-postgres's default — so 10 + 2 does not lower per-replica usage, it raises it by two and makes it deliberate. What the change actually buys is the timeouts that ship with it.
ADerived — activity concurrency plus twoassumption
The pool size is an expression, not a literal: it is computed from maxConcurrentActivityTaskExecutions, so the two cannot drift apart.
  • Raising activity concurrency cannot silently exceed the pool — the two move together
  • Setting max above the activity concurrency cannot help anyway: the worker has no activities to run on the extra connections
  • The +2 is named, not magic — the health check, and anything that opens a connection outside an activity
  • Twelve per replica is two more than today's implicit ten, so the arithmetic has to be redone with 12
Client effort: noneOurs: one expression in the pool config
BA fixed number from the environment
An env var holds the pool size, independent of the activity concurrency, so it can be turned down without a deploy.
  • Can be lowered during an incident without shipping code
  • Lets a constrained environment run a smaller pool than its concurrency suggests
  • Two numbers that have to agree, in two places, with nothing enforcing it
  • A pool smaller than the activity concurrency becomes contention that looks like a slow provider
Client effort: noneOurs: one env var, and a pair that can drift
CLeave it implicitnot viable
Keep the pool as it is: no max, no idleTimeoutMillis, no connectionTimeoutMillis.
  • Nothing to change today
  • The sizing is a library default, and a dependency bump can move it
  • Without connectionTimeoutMillis a saturated pool hangs the activity until its startToCloseTimeout — the mysterious failure rather than the diagnosable one
Client effort: noneOurs: every saturation looks like a hang
Our recommendation

A, with B as the escape hatch: derive the default, allow an env override. The derivation is what keeps the two numbers honest; the override is what lets an incident be handled without a deploy.

And ship the timeouts with it. idleTimeoutMillis and connectionTimeoutMillis are the half of this decision that actually changes behaviour — they turn “the activity hung until Temporal gave up” into “the pool refused, and said which pool”.

▸Decision S2-bPLAN D8Open — needs a callDoes the replica count stay bounded by max_connections, or does a pooler decouple them?
The task's “done when” requires the proxy decision to be recorded either way, which is the honest framing: not adopting a pooler is also a decision, and its consequence is that the supported replica count becomes a fixed number a capacity request has to renegotiate. The spec recommends PgBouncer in transaction mode and names the constraint that comes with it — which is load-bearing for two other tasks.
APgBouncer in transaction moderecommended
A pooler multiplexes many client connections onto few server connections, so the replica count stops being the thing that consumes max_connections.
  • The only option that makes “many workers” open-ended — replica count and connection count stop being the same number
  • pg_advisory_xact_lock survives it: it is transaction-scoped, already used in oauth-token.repo.ts, and planned for A7
  • No application change beyond a connection string
  • Transaction mode forbids session-level state — prepared statements, session settings, and session-level advisory locks, which would not survive
  • A new component in the path of every query, with its own failure modes and its own sizing
Client effort: noneOurs: one more component to run and page on
BNo proxy — spend the wall on a fixed replica budget
Skip the pooler and let the arithmetic produce a hard number: this database supports N worker replicas, and N is the ceiling until the database changes.
  • Nothing new to run — the arithmetic is the whole deliverable
  • No session-state constraint at all, so session-level advisory locks stay available
  • Every capacity increase becomes a database change, negotiated ahead of time
  • It is a ceiling on the epic itself — B5 multiplies the work each replica does, and the replica count is what absorbs that
Client effort: noneOurs: a number to renegotiate each time
CRaise max_connections
Leave the client side alone and buy room on the server, so the linear growth has further to run before it hits the wall.
  • The fastest thing to do during an incident
  • No new component, and no session-state constraint
  • The spec puts tuning Postgres out of scope — choosing this changes the task's boundary, not only its answer
  • Each connection costs a server-side process and its own working memory, so it trades throughput for connection count
  • It postpones the linear growth; it does not remove it
Client effort: noneOurs: buys time, not a ceiling
DA managed poolervariant of A
The same multiplexing as A, run by the platform instead of by us — the “or equivalent” the review leaves open next to PgBouncer.
  • The operational half of A without a component of our own to run
  • Failover handling comes with it
  • The same session-state constraint as A — it is the same pooling model
  • A cost per hour, and less control over pool sizing than PgBouncer gives
Client effort: noneOurs: a bill instead of a component
Our recommendation

A — but record it even if the answer turns out to be B. The arithmetic decides which: if the current database already supports the replica count this epic needs, B is honest, free, and revisitable. If it does not, A is the only option that removes the coupling rather than moving it.

One thing to test rather than assume, whichever wins: pg_advisory_xact_lock under transaction pooling, using the existing OAuth refresh path as the test. It is transaction-scoped, so it should survive — and “should” is not a test result.

What the task does, in three parts

1The pool that was never given a ceilingworker/src/modules/database/database.service.ts
Make the per-replica connection count an explicit number, and make a saturated pool fail fast instead of hanging.

The worker builds its pool like this:

new Pool({ host, port, user, password, database })

No max, no idleTimeoutMillis, no connectionTimeoutMillis. The first omission hands the sizing to a library default. The third decides what a saturated pool feels like: without it, a caller waiting for a connection simply waits, and the activity hangs until Temporal ends it at its startToCloseTimeout.

That is what this half of the task actually buys — a diagnosable incident instead of a mysterious one.

⚠ How it is today

Ten connections per replica by library default, and a saturated pool that hangs an activity until its startToCloseTimeout — a timeout that names Temporal, not the pool.

✓ How it will be

An explicit max, plus idleTimeoutMillis and connectionTimeoutMillis, so saturation returns a connection timeout naming the pool, in seconds rather than minutes.

2The arithmetic is the deliverableworker/src/modules/temporal/worker.service.ts · infra/compose
Write the capacity sum down with real numbers, and state how many worker replicas this database supports.

The sentence this task has to produce is this one:

max_connections >= (api_replicas x api_pool) + (worker_replicas x worker_pool) + migrations + operators

Every term on the right is knowable today, and only one of them is written down anywhere — the worker's activity concurrency. The output is a single number: how many worker replicas this database supports.

The config change is trivial once that sentence exists. Without it, the config change is a guess with a decimal point in it.

⚠ How it is today

Nobody can say how many workers this database supports. The answer is discovered by hitting the wall — and because the wall is shared, it is discovered by the API.

✓ How it will be

The number is written down next to the terms it came from, so the next capacity decision reads it instead of re-deriving it.

Out of scope — tuning Postgres

This task sizes the client side and states what the server side must support. Whether max_connections itself should be raised is a separate call — the second decision above.

3The one thing a transaction-mode pooler would breakoauth-token.repo.ts
Name the constraint honestly before adopting the pooler, and prove it with the path that already relies on it.

Transaction-mode pooling forbids session-level state: a client is given a server connection for the duration of a transaction, not of a session. Anything that outlives the transaction — a session setting, a prepared statement, a session-level advisory lock — does not survive.

pg_advisory_xact_lock is transaction-scoped by name, so it does survive. It is already used at oauth-token.repo.ts, A7 plans to use it for ordering, and S8 proposes an advisory lock per cron job name. The answer to this question is load-bearing for three tasks, not one.

⚠ How it is today

No proxy exists, so the question has never been asked — and two other tasks are about to plan around advisory locks.

✓ How it will be

The constraint is written down, and the OAuth refresh path is the test that proves pg_advisory_xact_lock still behaves under transaction pooling.

Tell S8 which lock it may use

If a pooler is adopted, S8's cron guard must be a transaction-scoped lock. A guard described as “taken at the top of the run and released at the end” is a session-level lock by instinct — and that is exactly the shape transaction pooling drops.

Under a pooler, holding the lock for the job means the job runs inside the transaction that holds it. That is a real constraint for a long purge, and it is better discovered here than in S8's PR.

Set max to 1 and run two concurrent activities. Confirm the second fails with a connection timeout naming the pool, rather than hanging until the Temporal timeout. The difference between those two failure modes is the difference between a diagnosable incident and a mysterious one.

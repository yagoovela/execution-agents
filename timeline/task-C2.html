Three separable pieces, all of them things that only existed to bridge the migration: the legacy single-node endpoint and its allowlist, the prefetch executor and its 17-type whitelist, and every migration flag this epic created.

The middle one is the reason this task carries a decision rather than a checklist. Either answer about the prefetch executor is fine. Leaving it undecided is not: a dormant second execution path is a maintenance tax nobody is paying attention to.

Our recommendation

Run the measurement first, and let it pick. The evidence available today points at B: the whitelist requires every node in a flow to be on it, and no LLM node is on it — so a flow with a commandTextNode is ineligible by construction. If that makes the eligible count near zero, there is nothing to promote and nothing to keep.

Two conditions on whichever answer wins. If A: the whitelist has to stop being a hand-maintained list and become derived from the A1 registry, or the epic ends with the fourth list it set out to remove. If C: a named owner and an expiry date, or it is A by neglect.

One sequencing note that is easy to miss: D2 is listed as gating Wave 4 because B3 needs the answer — but the measurement lives in this task, in Wave 6. The measurement has to be pulled forward, ahead of its own task. It is a query and a report, not a code change, so it can be.

What the task does, in four parts

1The legacy single-node endpointtemporal.controller.ts:71 · single-node-legacy.service.ts:132–150
Retire a router whose destination set becomes empty the moment every executable type runs in the worker.

/process/single-node-legacy lives at back/src/temporal/temporal.controller.ts:71, backed by single-node-legacy/single-node-legacy.service.ts. Its validateNode (:132–150) does three things: it refuses migrated types, it refuses mutating types, and it accepts only LEGACY_SINGLE_RUN_NODE_TYPES.

Follow that to its conclusion. Once every executable type runs in the worker, this endpoint accepts nothing — it becomes a router with an empty destination set. Retire it, and retire the allowlist that feeds it.

The front side is a hard prerequisite, not a courtesy: ProcessService.responseLegacy (front/src/service/processService.ts) must have no callers before the endpoint goes. A silently-dead endpoint the front still calls is worse than keeping it.

⚠ How it is today

One node type can be executed through two different endpoints with two different implementations, and which one you get depends on how the run was started.

✓ How it will be

One way to run a node. The legacy endpoint returns a clear 404/410, and the front has already stopped calling it.

2What this task must not removeD18 · flux.controller.ts:643, 839, 872, 888, 923
Name the endpoints that look legacy and are not, before a sweep takes them with the ones that are.

D18 keeps the whole batch-process family. None of the five is deprecated: POST /batch-process (:643), GET /batch-process/:id/status (:839), GET /batch-process/all (:872), POST /batch-process/:id/stop (:888) and GET /batch-process/:ids/download (:923).

The route stays as the entry point and its body moves into B7's durable workflow. The status, listing, stop and download endpoints are the surface a batch screen reads, so in this epic they gain a consumer rather than losing one.

They look like the legacy endpoint and are not

Both are older routes on the same controller, and both predate the worker. The difference is that one has no caller left and the other is about to get its first real one. Check the list above before deleting anything named batch.

3The prefetch executor — measure, then decideapp-api/flux/prefetch/ · flux.service.ts:1402–1431, 3198–3226
Answer D2 with two numbers instead of an opinion — and report what could not be determined as unverifiable, not as zero.

back/src/app-api/flux/prefetch/ is in production, behind FLUX_EXEC_MEMORY_MODE, which defaults to legacy. canUsePrefetchForFlow then requires every node in a flow to be in this 17-type whitelist:

imageGenerator webSearch voiceBoxNode audioReaderNode commandContentNode pullData pushData mcpNode thirdPartyIntegration libraryNode webCrawling reportBuilder sqlQuerier nodesBox comment label group

Read that list against the requirement that every node must be on it. There is no LLM node in it — a flow containing a commandTextNode is ineligible by construction. That is why the spec warns the eligible count may be near zero, and why the decision above cannot be made without running the query.

Two measurements, then: how many production flows satisfy canUsePrefetchForFlow, and — of those — how many actually ran with the flag on, and what it saved in memory, latency or row size.

⚠ How it is today

A second execution path is live in production, dormant by default, and nobody can say how many flows it would even apply to.

✓ How it will be

D2 is answered in writing, with the numbers behind it — and whichever answer wins, there is one execution path fewer to explain.

Unknown is not zero

PLAN §3.3.2 applied to the measurement itself: report flows whose eligibility you could not determine as unverifiable, not as ineligible. The prefetch decision must not rest on a count that quietly rounded unknowns to zero.

4The migration flagsPLAN §3.2
Remove each flag once its node has soaked, because a flag that outlives its migration is untested production behaviour.

Every flag from PLAN §3.2 is temporary by construction. They exist so that a routing change can be added disabled, proved, and flipped in a separate deploy — which is what makes each task independently revertible.

That justification expires. A flag that outlives its migration is a branch of production behaviour nobody tests, and it is the mechanism behind R1: two live paths and a switch between them.

⚠ How it is today

Every migration leaves a switch behind, and each switch is a production behaviour that has an owner only while somebody remembers it.

✓ How it will be

No migration flag from this epic remains. One implementation of each node, one dispatch registry, one engine.

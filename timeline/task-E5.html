Read from the account on 2026-09-18, read-only, so this task starts from facts rather than from a worry. Prod runs enhancedai-redis-prod — 3 × cache.t2.medium, Valkey 8.0.1, cluster mode off — on the AWS-managed default.valkey8 parameter group, whose maxmemory-policy is volatile-lru. Over the trailing 14 days: zero evictions, memory usage peaking at 1.9% (avg 1.3%), engine CPU peaking at 1.8%, and at most 383 keys in the whole instance.

Per §3.3.2 this is stated as measured, not assumed: the policy is wrong and the consequence is latent. It has never fired — zero evictions at 1.9% of capacity, with a keyspace of a few hundred items, is not a cache under any real pressure. That is exactly why this is debt with a bad blast radius rather than an incident, and exactly why it is a follow-up split out of S8 Part 3 rather than something that held the replica-safety fix S8 actually is.

What the task does, in four parts

1The only way to change the value: a custom parameter groupenhancedai-redis-prod · default.valkey8
default.valkey8 is AWS-managed and cannot be edited, so a new parameter group with maxmemory-policy = noeviction is not a preference — it is the only mechanism available.

Applied to prod, staging and dev. noeviction is safe precisely because the measurement above says nothing here depends on eviction to reclaim space: a keyspace of a few hundred items at 1.9% of a cache.t2.medium is not a cache doing work, it is a dedup ledger that happens to sit in Redis.

The trade being made is deliberate and stated plainly: noeviction converts a silent correctness failure — a key quietly disappears and a duplicate slips through — into a loud write failure — the write that would have pushed memory over the limit errors instead. A loud failure is only an improvement if something is watching for it, which is why Part 2 is not optional.

⚠ How it is today

volatile-lru silently deletes the TTL-bearing key that is closest to expiry when memory runs out — the delivery dedup key included, with nothing in the logs to say so.

✓ How it will be

noeviction refuses the write that would exceed maxmemory instead of deleting anything. The dedup key survives; the failure is visible.

Out of scope, on purpose

Redesigning flux.service.ts's email-sent: dedup mechanism itself is not this task. It is read here only as the thing being protected — the key shape (SET k '1' EX 86400 NX) is what makes it volatile and therefore evictable in the first place.

2A loud failure needs something watching for itCloudWatch alarms · per environment
Two alarms make the trade in Part 1 operable instead of merely different: one on DatabaseMemoryUsagePercentage, one on Evictions > 0.

The memory alarm gives warning before a write ever fails. The evictions alarm is a tripwire that should never fire again once noeviction is in effect everywhere — if it does, either the parameter group did not apply, or a different key population needs eviction and the policy choice needs revisiting, not silently overriding.

3Sizing for after B5: recorded, not resizedB5's pub/sub rate
The same measurement that condemns volatile-lru also answers the sizing question, in the other direction: roughly fifty times the headroom B5 would need.

The Redis engine peaks at 1.8% of one core and memory at 1.9%. Parallel dispatch raises the pub/sub rate substantially once it ships, but against this baseline no resize is indicated. Recording that baseline is the deliverable here; the number that would change it is the re-measurement after B5 is on, recorded next to this one rather than replacing it.

4Flagged, not fixed: no automatic failoverAutomaticFailover · MultiAZ
A real availability gap sits next to this task and is deliberately not folded into it.

AutomaticFailover and MultiAZ are both disabled on a three-node production group. Losing the primary loses the queues, the dedup keys and the pub/sub relay at once, with no automatic promotion. That is out of scope for this task, and it is flagged here rather than fixed silently, because it needs its own decision about downtime and cost — not one made as a side effect of an eviction-policy change.

Decision to write down — not this task's to make

Whether to turn on AutomaticFailover/MultiAZ on the production group is a cost-and-downtime call for whoever owns the infrastructure budget, made deliberately rather than inherited from this task's scope.

How it is proved

🔬 Verification
1
Negative controlrequired
Local Redis container, --maxmemory 16mb --maxmemory-policy volatile-lru: write a dedup key in the real shape (SET k '1' EX 86400 NX), fill past maxmemory, and watch the key disappear. That disappearance is the defect; see it before fixing it. Then switch to noeviction, repeat, and confirm the key survives and the filling write is what fails instead.
2
The parameter group is actually in effect
CONFIG GET maxmemory-policy against the instance, not the console's intention, on each environment. A pending-reboot parameter change is a classic way to believe a policy is applied when it is not.
3
The alarms actually fire
Breach both alarms on purpose in dev and confirm they fire, rather than trusting that a configured threshold is a working alarm.
✓ Done when
No environment can evict a dedup key, both alarms exist and have been seen to fire, and the post-B5 pub/sub measurement is recorded next to the pre-B5 baseline above.

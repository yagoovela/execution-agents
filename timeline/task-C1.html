This file is the procedure the A-track tasks follow, plus the two pieces that only make sense once.

Two implementations of one node do not coexist neutrally. They diverge, and the divergence is silent — someone fixes a bug in the inline handler that the worker module still has. Worse, while both exist, a flag misconfiguration means double execution (PLAN §6, R1).

flux.service.ts is around 9,500 lines. A migration that only adds is a migration that made the file worse — which is why deletion is part of the migration and not cleanup that happens afterwards.

What the task does, in three parts

1The per-node procedureback/src/app-api/flux/flux.service.ts
Three steps, executed by each A-track task as its node lands — not by a cleanup task months later.

The procedure is short and it is deliberately owned by the node's own task, because the person who just proved the behaviour is the only person who knows what was safe to remove.

  • The inline handler and its dispatch branch are deleted — not commented out, and not left behind a dead flag.
  • Anything only that handler used goes with it. flux.service.ts is around 9,500 lines; a migration that only adds made the file worse.
  • The A1 registry entry loses hasInlineTwin, so the one authoritative answer to “does this node have a second implementation?” stays true.
⚠ How it is today

Every migrated node has a twin in the back. They are equal until one of them is fixed, and then only one of them is fixed.

✓ How it will be

The migrated node has one implementation, and the flag-off path fails loudly instead of quietly doing nothing.

Deleting late is not the safe option

The instinct is to keep the inline handler “just in case”. That instinct is what creates R1: two live paths, one flag between them, and a duplicated side effect the first time the flag is wrong.

2The cross-node writes — the load-bearing halfback/src/app-api/folw/contants.ts
Stop a second writer from merging into a row someone else owns — the mechanism that makes mixed-mode parallelism unsafe.

Every inline handler ends with addConnectToNodes (folw/contants.ts), which calls modifyData to merge the producer's output into the target node's data. That is the mechanism that makes mixed-mode parallelism unsafe (analysis §7.4b), and it is the reason B5 needs its gate.

Once a node runs in the worker, its output reaches downstream nodes through persistNodeSuccess writing its own row. The cross-node write is then not merely redundant — it is a second writer on a row someone else owns.

Out of scope: removing addConnectToNodes while any executable node type still runs inline. It is correct for those. This task removes it path by path, as each path's last inline node leaves — which is why the tracking in Part 3 is the actual work here, not the deletion itself.

⚠ How it is today

A producer's output is merged straight into the target node's data. Safe only because the engine is sequential and holds the whole node array in memory.

✓ How it will be

A node writes its own row and nothing else. Parallel siblings cannot lose each other's writes, and B5's gate can eventually be retired with the risk it guarded.

3The end-state check is not a formalitythe run path · the PR description
Track which call sites still have a live inline caller, and treat a surviving caller as evidence that something was missed.

Two of the three steps are bookkeeping, and the bookkeeping is what makes the deletion safe:

  • Per node, as its A-task completes: delete the handler, the dispatch and the dead helpers.
  • Track which call sites of modifyData / addConnectToNodes still have a live inline caller. When a call site's last caller is gone, delete the call site.
  • When the last executable inline node is migrated, addConnectToNodes should have no callers on the run path. If it still does, something was missed — that is the check, not a formality.

And the reduction gets stated in the PR. “flux.service.ts is materially smaller” is a claim with a number behind it, and writing the number down is what stops the next migration from only adding.

⚠ How it is today

Nobody can say how many live inline callers a given helper has, so nobody can safely delete it — and it stays forever.

✓ How it will be

Each call site has a known set of live callers, the set empties as nodes migrate, and an empty set is the signal to delete.

3

How it is proved

🔬 Verification
1
Negative control — prove the path first, then break itrequired
Before deleting a handler, re-point the flag at the inline path and confirm the node still works. Then delete, and confirm the flag-off path now fails loudly rather than silently doing nothing. A deleted path that fails silently is indistinguishable in production from a node that produced empty output.
2
Double-execution guard — assert it, do not eyeball itrequired
For each migrated node, assert with a log or a counter that exactly one execution occurred per dispatch. This is R1, and it is the failure that shows up as a duplicated charge rather than as an error.
3
Diff downstream inputs after each call-site removal
After each modifyData call-site removal, run the flows that reach it and diff downstream node inputs against a pre-change run. The write being removed is the one that fed those inputs, so this is where a silent loss would appear.
✓ Done when
No executable node type has two implementations; addConnectToNodes has no callers on the run path; and flux.service.ts is materially smaller, with the reduction stated in the PR.

The decisions this task needs

These are the calls that have to be made before the code is written. Each one opens to the options considered, what each costs the customer and costs us, and the option we would pick.
▸Decision S5-aOpen — needs a callDo we authorise these two endpoints, or delete them by giving the worker its own S3 credentials?
The spec says this task may be superseded, so check before starting. Review §2.4 argues the worker should hold its own storage credentials, which would remove /worker/get-payload and /worker/store-payload entirely — and with them, the gap this task exists to close.
AAuthorise now, decide the bigger change laterrecommended
Add the run check to both endpoints this week. It is a few lines, because the key already encodes execId and nodeId.
  • Closes a live cross-tenant read now, without waiting on an architecture decision
  • Cheap enough that throwing it away later costs nothing
  • If the endpoints do get deleted, the deletion is simpler with the semantics already stated
  • Work that may be discarded
Effort: a few linesRisk: none
BGive the worker its own S3 credentialsbigger, better
The worker reads and writes large payloads directly, so they stop travelling through the API. Both endpoints are deleted.
  • Removes the endpoints, so the authorisation gap cannot exist
  • Large payloads stop making a round trip through the backend — less latency, less API load
  • Every worker replica needs scoped storage credentials, which is a real identity change
  • Scoping them per tenant is the hard part — an over-broad role recreates the same gap at a different layer
Effort: IAM + deploy per envRemoves: two endpoints
Our recommendation

A now, B on its own merits later. They are not really alternatives: A costs a few lines and closes a live gap, and B is a latency and architecture improvement that happens to make A redundant.

Doing A first is not wasted work — if B lands, deleting an endpoint whose authorisation rule is written down is easier than deleting one whose rule was never stated.

What the task does

1The key already carries the answernode-execution-store.ts
The endpoint refuses when the stated run and the key disagree — and the worker already has both values.

claimCheckKey(execId, nodeId, …) builds the key, so parsing it back out is trivial. The caller states which execId and nodeId it is acting for; the endpoint parses the key and refuses on a mismatch. Both values are already in ExecuteNodeActivityProps.

The same treatment applies to /worker/store-payload: a caller should not be able to write a payload into another run's key.

⚠ How it is today

A prefix check. Any valid internal key redeems any customer's node output, and can overwrite any customer's payload.

✓ How it will be

The key must match the run the caller declared. Refusals are logged with enough context to tell a bug from an attempt — a refusal that is invisible teaches nobody.

Out of scope

Replacing InternalApiGuard or introducing per-worker credentials. That is a larger identity change; this task closes the authorisation gap inside the existing boundary.

How it is proved

With a valid internal key, request another run's payload and confirm it currently succeeds. That demonstration is the whole justification for the task. Then confirm it is refused, and that the legitimate path is unaffected.
2
The large-payload path still works
Confirm the worker still resolves its own claim refs — including the large-payload case, which is the only path that exercises this at all.
3
Malformed keys fail closed
Confirm a malformed or truncated key fails closed, not open — a parse error must refuse, never fall through to the prefix check.
✓ Done when
A key can only be redeemed for its own run, writes are equally bound, refusals are logged, and the existing large-payload path still works.

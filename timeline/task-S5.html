Authorise the claim check, do not just guard it

A claim-check key can only be redeemed by the run it belongs to.
PR #1952 · Merged to `production` 2026-09-14 (`5bbdbfec`). Splits the claim-check problem in two: validation binds the key to a stored `node_executions` row via `parseClaimCheckKey`; authorisation requires a `runToken` (random UUID, `select: false`, never returned or logged) the caller cannot derive from the key alone. `ClaimCheckAuthzService` runs before `/worker/get-payload` and `/worker/store-payload` touch S3. Behind `feature_flags.claim_check_authz_enforce` — off logs "would have refused", on answers 403; a failed DB lookup refuses either way. PR's own before/after table demonstrates the fix against a real S3 bucket: run B presenting run A's key went from `200` (300KB of run A's payload leaked) to `403`; a path-traversal key attempt went from `400` to `403`. Flag's current on/off state in prod not independently re-verified here.

Watch out
The cheap fix is a placebo
The key contains execId and nodeId, so refusing when the caller's declaration disagrees with the key adds no authority at all. D28 settled that the endpoints stay.

/worker/get-payload validates a prefix and nothing else (worker.controller.ts:99). There is no check that the key belongs to the caller's run, tenant, or anything else.

The route sits behind InternalApiGuard, which is the right boundary and should stay. But it is a single shared secret, and this epic puts that secret on every worker replica — “we trust everything inside the perimeter” gets weaker with every host added to the perimeter.

The obvious fix does not fix it. The key is node-exec/{execId}/{nodeId}-{field}.json, so both values the caller would “declare” are already inside the key it presents. A holder of the shared secret reads them out of the victim's key and declares them back. This task therefore separates validating the key from authorising the caller, because only the second one is authorisation.

The decisions this task needs

These are the calls that have to be made before the code is written. Each one opens to the options considered, what each costs the customer and costs us, and the option we would pick.
▸Decision S5-aPLAN D28SettledDo we authorise these two endpoints, or delete them by giving the worker its own S3 credentials?
The spec said this task might be superseded, so it had to be checked before starting. It was, on 2026-09-09, and the answer is A: the endpoints stay. The reason is not that B is wrong — it is that B deletes the only place the check can live, and handing the worker the back's own credential is B by another name: it reduces the number of secrets, not the reach of each one.
AAuthorise now, decide the bigger change laterchosen
Bind the key to a stored row and the caller to a run token, on both endpoints. The back stays the sole holder of the S3 credential.
  • Closes a live cross-tenant read now, without waiting on an architecture decision
  • Keeps the enforcement point, which B removes
  • If the endpoints do get deleted, the deletion is simpler with the semantics already stated
  • The large-payload hop through the API stays — cheap today, expensive once B5 fans out
Effort: bind + token + testsRisk: ships dark behind a flag
BGive the worker its own S3 credentialsdeferred to its own task
The worker reads and writes large payloads directly, so they stop travelling through the API. Both endpoints are deleted.
  • Large payloads stop making a round trip through the backend — less latency, less API load
  • It deletes the enforcement point: with raw bucket access on every replica, “this key belongs to this run” has nowhere left to be checked, and a worker checking itself is not a check
  • Scoping credentials per tenant is the hard part — an over-broad role recreates the same gap at a different layer
  • The coupling it removes costs almost nothing today: 6 offloads in 3417 node executions on dev
Effort: IAM + deploy per envRemoves: the place the check lives
Our recommendation

Settled 2026-09-09: A. They were never really alternatives. A closes a live gap and, more importantly, keeps the one surface where authorisation is possible at all. B is a latency and coupling improvement whose security framing is backwards — it does not close the gap, it removes the place the gap could be closed.

Revisit B on its own merits when B5's fan-out makes the API hop expensive. By then this task will have paid for the authorisation, and deleting an endpoint whose rule is written down is easier than deleting one whose rule was never stated.

What the task does

1Derive from the key, never from the claimworker.controller.ts · claim-check.ts
The endpoint recovers execId and nodeId from the key itself and binds them to a stored row, so the decision never rests on anything the caller asserts.

parseClaimCheckKey lands next to claimCheckKey in claim-check.ts, so building and parsing a key share one home. /worker/get-payload then requires a node_executions row for the derived pair whose __claimRef envelope is the requested key. A key nobody stored is refused.

/worker/store-payload gets the inverse bind: the run row for that pair must already be open before a payload may be written into its key. Without that, “a caller cannot write into another run's key” is unreachable, because the key is derived from what the caller supplies.

What the caller declares is kept — in the refusal log, so a refusal reads as “declared X, key said Y”. That is what separates a bug from an attempt.

⚠ How it is today

A prefix check. Any valid internal key redeems any customer's node output, and can overwrite any customer's payload.

✓ How it will be

The key must name a run that really stored it, and a write must land on a run that is really open. Forged, guessed, enumerated, truncated and path-traversing keys are all refused, and every refusal is logged with context.

Validation is not yet authorisation

This bind kills every key that was never stored. It does not stop a holder of the shared secret who already knows a real key — that needs part 2.

2A run token the caller cannot forgeactivities.types.ts · run-token.ts · claim-check-authz.service.ts
The back mints a run-scoped token at dispatch; the worker carries it and presents it. This is the half that is actually authorisation.

ExecuteNodeActivityProps gains a runToken, issued by the back when it dispatches the activity and checked on both endpoints. Every node of the run inherits it, because every activity of that run is dispatched with it.

No chain propagation, on purpose. Checked on worker@origin/main: the worker executes no sub-flow at all — no parentRunId, no startChild, and no fluxBox, libraryNode, flowCaller or arrayNode module. Sub-flows still run in the back's legacy engine, so there is nothing to propagate through. Carrying the token down the chain becomes a Done-when line of S1 (which owns the parentRunId chain under D13) and of B6 (the child workflow, D17). That is what keeps this task standalone.

⚠ How it is today

Anything inside the perimeter is trusted, and the perimeter is one secret on every replica.

✓ How it will be

The caller proves which run it is acting for with something it could not have read off the key.

Out of scope

Replacing InternalApiGuard or issuing per-worker credentials. That is a larger identity change; this task closes the authorisation gap inside the existing boundary.

3Node ids need a contract, not luckclaim-check.ts · nodeId.ts · mcp-write.service.ts
Any rule that recovers a node id from a key refuses ids the key could not represent. Close that by contract, so a false refusal is impossible by construction.

claimCheckKey sanitises the id with replace(/[^a-zA-Z0-9_.-]/g, '_'), which is lossy. Introduce NODE_ID_PATTERN = /^(?!\.+$)[A-Za-z0-9_.-]{1,128}$/ — deliberately the same class the key preserves, so sanitising a valid id is the identity function.

Six producers exist and none of them enforces anything. The front generator is safe by accident, in three separate generations. The hole is MCP add_node: AddNodeDto.node is @IsObject() Record<string, unknown> and the service only checks for id collision, so a client id is persisted verbatim. The only id rule anywhere is assertGlobalStarterIdConvention, which merely requires a substring on globalStarter.

So: getNodeId becomes the single front producer with a pattern test, copy/paste goes through a deriveCopyId that also stops the -copy-copy chain, an assertNodeIdRedeemable in mcp-write.service.ts closes the MCP entry for new writes (the DTO's node is an untyped Record, so class-validator has nothing to hang a rule on), and comparison stays sanitised against sanitised so legacy ids outside the pattern still resolve.

One hazard to remember: several places pass the composite nodeId$handle (fluxBox_1$out). $ is sanitised too, so a composite arriving where an id is expected degrades silently.

⚠ How it is today

No id contract anywhere, and an MCP entry point that persists whatever a client sends.

✓ How it will be

One pattern, one front producer, a validated MCP entry, and a parser with a round-trip test behind it.

Measured before refusing, per §3.3.2

Dev and staging, 2026-09-09: 80523 nodes and 3432 executions, zero charset violations, zero false refusals; all 6 claim envelopes bind correctly and none depends on sanitisation. Prod was not measured — the implementer holds no prod bastion credentials and the requester chose to proceed, so the gap is recorded rather than hidden. The risk this closes is prospective: the MCP hole has simply not been exercised yet, which is why closing it now is cheap.

4Shipped dark, on a switch that already existsfeature_flags · FeatureFlagsPage.tsx
Reuse the feature-flag table and the admin screen instead of a new env var, so the rule can be measured on real traffic and flipped from inside the product.

Key claim_check_authz_enforce, inserted by migration because setEnabled does not upsert. The flag is a boolean, so it carries two modes: off computes the decision, serves the payload anyway and logs “would have refused”; on enforces. Off is the measurement window and the default — and it is a window with a deadline, not a resting state, because the gap is open while it is off.

Fail-closed dominates the flag. isEnabled swallows a read error and returns false, which would read as “log-only” when the database is down. That is harmless, because the bind is itself a query: an uncomputable decision refuses, flag or no flag. The flag only decides whether an already computed refusal is acted on. Stated because it is subtle and invites a wrong optimisation later.

The screen's list becomes API-driven, which needs care the API does not currently offer: there is no label column, so deriving one would silently rename the live “Node cancellation” switch; and maintenance_banner is deliberately absent from today's list, so an API-driven list would expose it as a toggle for the first time. Add label and adminVisible, backfill the banner as not visible, and render label ?? key with description ?? '' so a row can never come out blank. isEnabled also gains a few seconds of cache, invalidated on toggle so the screen takes effect at once.

⚠ How it is today

A rule that refuses would land enabled, measured only against stored rows.

✓ How it will be

It lands dark, states what it would have refused on real traffic, and is flipped from the admin screen in a separate deploy.

No new env var

Because it reuses feature_flags, §3.3.5 is not triggered and there is nothing to deploy per environment — the toggle is a row.

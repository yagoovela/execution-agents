Corrected 2026-08-24. An earlier version of this task claimed that (execId, nodeId) names 'a node within a run' and that loops break it in general. That is only half true, and the real situation is more interesting: execId means two different things depending on which path ran the node.

On the Temporal path processNodeViaTemporal mints a fresh id per node dispatch (flux.service.ts:681), so the pair is already unique. On the legacy path recordLegacyNodeStart is called with execId: runLogProcessId (flux.service.ts:3304) — the same value for every node in the run. One column, two incompatible meanings, and this epic is about to merge the two paths into one.

The decisions this task needs

One call has to be made before any code is written, and it constrains B3 and B6. The spec is explicit that it must be chosen deliberately and written down — because the merge of the two paths will otherwise pick a meaning by accident.
▸Decision B1-aRecommended — confirmWhich meaning survives the merge, and what actually travels between nodes?
The two paths disagree today and the epic is about to merge them. The spec names two candidates for the identity and asks for one to be picked and the reason written down here, because the choice constrains B3 (which makes this the transport) and B6 (which makes loop position meaningful).
Anode_executions.id is the referencerecommended
The existing primary key becomes the value that travels between nodes. (execId, nodeId) stays a lookup key and is never a transport.
  • Cheapest — the column already exists and is already unique
  • Keeps the Temporal meaning, which is already the stricter of the two and is what node_executions was documented to be: one row per node run
  • The only candidate that survives loops and parallelism with no discriminator at all
  • The reference is opaque in a log — you cannot read the loop position off it
  • The legacy call site still has to stop reusing runLogProcessId; the primary key does not fix the writer by itself
Client effort: none — run history keeps its rowsOurs: the column is already there
BAn iteration discriminator in the key
A third field is added so (execId, nodeId, iteration) is unique, and that triple is what travels.
  • The reference stays human-readable in logs — you can see which iteration you are looking at
  • Makes loop position explicit, which B6 will want anyway
  • The unique constraint can be declared on the triple, so the database enforces the meaning
  • More invasive — every writer and every reader learns a third field
  • It does not avoid the legacy work: that path must stop reusing runLogProcessId either way
  • A node that runs twice for a reason that is not a loop — a retry, a re-run — needs iteration defined for it too
Client effort: none, but a migration touches every rowOurs: a third field in every writer and reader
CLet the merge decidenot viable
Keep both meanings and let whichever path wins the merge define what the column means.
  • No work now
  • It is the spec's own warning: the merge will pick a meaning by accident
  • If the legacy meaning wins, B3's transport collides on every loop iteration
  • the rows[0] inside fetchNodeRow then decides which execution a consumer reads, and Postgres promises nothing about that
Client effort: noneOurs: a transport that is wrong on loops
Our recommendation

A — keep the Temporal meaning: one id per node execution, and make the legacy path conform. It is already the stricter of the two, it is what node_executions was documented to be, and it is the only one of the two that survives loops and parallelism without a discriminator.

B is not wrong, and it buys something real for B6 — but it buys it at the price of a third field in every writer and reader, and it does not remove the legacy work. If loop position turns out to be needed in logs, it can be added as a column later without being the identity.

Whichever wins, three things ship with it: a unique constraint or an explicit documented reason there is none, ORDER BY on every read that can match more than one row, and a targeted persistNodeSuccess.

What the task does, in three parts

1Make one row mean one executionnode-execution-store.ts:26–39 · new migration
Whatever the transport becomes, the write side has to stop producing rows that cannot be told apart.

openNodeExecution is a plain INSERT with no ON CONFLICT, and the table carries no unique constraint on (execId, nodeId) — only a plain index. On the legacy path, where execId is the run, that is enough to produce several indistinguishable rows for the same node.

  • A unique constraint, or an explicit documented reason there is none. Silence is what got us here.
  • The legacy call site stops reusing runLogProcessId and mints an id per execution, so both paths mean the same thing.
  • persistNodeSuccess becomes targeted — it writes the execution it owns, not every row that matches a pair.
⚠ How it is today

The same node executed twice under one execId produces two rows nothing can tell apart, and the writer updates both.

✓ How it will be

One row is one execution. The writer addresses exactly the execution it produced, and a second execution cannot overwrite the first.

Backfill is part of the change

Existing node_executions rows must remain readable. A migration that orphans historical rows breaks run history and the MCP run-status surface — both read this table, and neither is in this epic's blast radius by choice.

2Every read that can match more than one row gets an orderfetch-node-row.ts:31–47 · persist-node-success.ts:7–9
A read that relies on Postgres ordering is a coin flip that usually lands the same way — until it does not.

fetchNodeRow takes rows[0] with no ORDER BY. Postgres does not promise an order without one, so which execution a consumer reads is decided by the storage engine, not by the code. On the legacy path today that means a loop's consumer can read any iteration.

The rule is narrow and mechanical: no read that can match multiple rows relies on Postgres ordering. Where a single execution is meant, address it; where the latest is meant, say so.

⚠ How it is today

rows[0] with no ORDER BY — the consumer reads whichever row the engine returns first.

✓ How it will be

Either the read addresses one execution directly, or it states an order. Nothing is left to the storage engine.

3Billing is the one place where 'every matching row' may have been intendedflux.service.ts:710, 1998
sumChargesByExecution(execId, nodeId) aggregates by the same pair — and for a loop, summing every row is arguably the right answer.

Everywhere else in this task, matching several rows is the defect. Here it is plausibly the feature: a loop's cost is the sum across its iterations. Changing the identity without checking this is how a correct refactor produces a wrong invoice.

So the aggregate is re-expressed against whatever identity wins, and loop totals are proven unchanged before and after — not assumed unchanged because the code looks equivalent.

⚠ How it is today

Loop billing happens to work because the aggregate sums every row matching the pair — a behaviour nobody wrote down as intended.

✓ How it will be

The aggregate is expressed against the chosen identity, and the loop total is the same number before and after the change.

Out of scope

Changing loop semantics. B6 owns those; B1 only makes them addressable. And sub-flows do not share the parent's execution identity — a sub-flow is a different graph with its own scheduler state, so it gets its own run identity chained to the parent. TASK-S1 owns that chain.

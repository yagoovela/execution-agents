Shape
Two constructs
Control flow for two types, child workflows for two — and one run chain that has to cross the boundary.

These four do not compute values. They decide what runs next, or they run whole flows — and an activity's return value cannot reshape the caller's iteration (analysis §3.3–§3.7). That is why they were the four left behind while everything else migrated.

Once B4 exists, they stop being blocked and become the natural content of the workflow. That is the inversion this epic is built on: the thing that could not be an activity turns out to be the thing the workflow is for.

The decisions this task needs

One call is genuinely open here — the shape of an array iteration. The two below it are already settled and are recorded on this page only so that a reader of B6 does not re-open them: they were decided in S1, and three rules in this epic read their answers.
▸Decision B6-aOpen — needs a callIs an array iteration a loop inside the workflow, or a child workflow per item?
The spec leaves this one open in as many words: arrayNode becomes “a workflow loop; possibly a child workflow per iteration”. The reason it is a real fork is review §4.1: a Temporal workflow's history is bounded in both event count and size, the worker uses continueAsNew nowhere today, and “an arrayNode iterating a big list” is named there as one of the shapes that will hit the limit — on the biggest, most valuable customer runs first.
AA loop inside the flow workflowrecommended
The workflow iterates the array itself, re-dispatching the loop body per item, and reuses the continueAsNew boundary B4 already had to define.
  • The loop body already exists as computeLoopBody in the scheduler — no new derivation, and no per-item indices to re-derive
  • continueAsNew at an iteration boundary is exactly what review §4.1 asks B4 for, so there is one mechanism, not two
  • One workflow per run keeps the run identity, the run log and the billing attribution where E1 put them
  • The history grows with every iteration, so the continueAsNew boundary is load-bearing rather than a nicety — get it wrong and the biggest runs die
  • A failing item is retried inside the parent's history, so a pathological item makes the parent's history grow faster
Client sees: the loop they have todayOurs: the continueAsNew boundary matters
BA child workflow per item
Each array item runs as its own child workflow; the parent holds one pair of events per item instead of the whole body.
  • Each item's history is its own, so one huge item cannot exhaust the parent
  • Per-item cancellation and per-item retry come from the platform rather than from our loop
  • It composes with the same child-workflow machinery fluxBox needs anyway
  • A hundred-thousand-item processorArray becomes a hundred thousand workflows — S4's per-node ceiling is what stands between that and the fleet
  • Per-item start latency is paid on every item, including the trivial ones
  • The run log, the cancel key and the billing attribution have to be threaded per item, not once per loop
Client waits: a start per itemOurs: N workflows per array
CA loop by default, a child above a thresholdhybrid
Iterate inside the workflow for ordinary arrays and switch to a child workflow per item once the item count or the body size crosses a line.
  • Keeps A's cost for the common case and B's isolation for the case that actually breaks
  • Two control-flow paths in a workflow that has to be replay-deterministic, and the replay test has to cover both
  • The threshold is a number nobody can defend until the history measurement from B4 exists
Client sees: nothing, either wayOurs: two replay paths to prove
Our recommendation

A, decided against B4's history measurement rather than against taste. B4 already owes a continueAsNew boundary and a measurement of how much history a real run produces; an array loop is the same mechanism, at a different granularity. Adding a second construct before that measurement exists is guessing.

Keep B named and available. If the measurement shows a real corpus of arrays whose body alone exhausts a history segment, that is the evidence for the switch — and it is C, not a rewrite.

▸Decision B6-bPLAN D13SettledDoes a sub-flow share the parent's execution identity, get a disconnected one, or a chained one?
Settled — decided in TASK-S1, and inherited here. It is recorded on this page because B6 is the boundary where the answer stops being a field in one process and becomes something that has to cross into a child workflow. A sub-flow gets its own run identity plus an explicit parentRunId, forming a chain back to the origin run.
AAbsorb into the parent's runrejected
The sub-flow's nodes join the parent's run — one execution id, one scheduler state, one run.
  • Budget and cancellation are trivially one thing
  • It is a different graph — one scheduler state would hold two node sets and two termination conditions
  • The nested run-log timeline this task is required to preserve would be lost

BA disconnected runrejected
The child workflow starts a fresh, independent run with no link back to its caller.
  • Simplest to implement — it is nearly what happens today
  • There is no visited set, so the cycle refusal becomes impossible at this boundary
  • Every nesting level buys a fresh budget and a fresh cost ceiling — nesting becomes the way to defeat S3
  • Cancelling the parent leaves the children running, which is the opposite of what child workflows give for free

CIts own run, chained by parentRunIdsettled
The child gets its own run identity plus an explicit parentRunId, and the visited-flow set and depth counter travel with it across the boundary.
  • Depth and cycle read the chain — it is the visited set
  • Cancellation propagates along it, which Temporal child workflows give natively
  • S3's spend ceiling applies to the chain root, so nesting cannot reset it
  • The nested run-log timeline the product already shows is preserved
  • The chain has to be threaded through state that survives the crossing into a child workflow, not held in a closure
Client sees: the nested timeline, intactOurs: one field, carried across
Our recommendation

C, and it is decided — B6 inherits it rather than revisiting it. What B6 owes is not the choice but the plumbing: the chain has to exist at this boundary and not only inside one process.

The consequence to keep in view: a child workflow started without the chain is a child workflow with no ceilings at all — and unlike today, a durable platform will sustain that result across the whole fleet.

▸Decision B6-cPLAN D14SettledIs calling a flow already on the chain refused outright, or merely depth-limited?
Settled — decided in TASK-S1, and inherited here. A flow already on the chain is awaiting a return; asking it to start again from the top has no coherent semantics. The refusal applies at any depth and to the whole chain, not only the direct parent. B6 is where the guard has to keep working after sub-flows become child workflows — which is the reason S1 was scheduled in Wave 0 rather than next to this task.
ARefused outright, at any depthsettled
If the flow being called is already on the call chain, the child workflow is not started — no configuration, no depth at which it becomes allowed.
  • A flow on the chain is awaiting a return, so restarting it from the top is not a deep call, it is an incoherent one
  • Covers A → B → C → A, not only the direct parent — A is still waiting either way
  • The refusal message can name the chain, so the author sees which link closed the loop
  • A flow that legitimately re-enters itself with different inputs is refused too — no known real case
Client effort: noneOurs: the visited set, carried
BAllow it, capped by depthrejected
Treat a cycle as ordinary deep nesting and let the depth ceiling catch it a few child workflows down.
  • One control instead of two
  • It spends real money and real child workflows before refusing something that was never valid
  • The error says “too deep” when the truth is “this is circular” — the author fixes the wrong thing
Client pays: for a call that was never validOurs: the wrong diagnosis, at fleet scale
Our recommendation

A, and it is not a tunable — there is no depth at which calling back into a waiting ancestor becomes correct. The depth ceiling stays as a separate, weaker guard for the legitimate case: composition that is genuinely nested but not circular.

What B6 has to prove is only that the guard survived the boundary: the visited set and the depth counter must live in state that crosses into the child workflow, not in a closure that stayed behind in the parent process.

What the task does, in three parts

1Condition and loop as deterministic control flowback/src/app-api/flux/scheduler.ts
Express the two control-flow types as workflow constructs that replay to the same answer every time.

Temporal workflows must be deterministic on replay. That is not a style preference here — it is the constraint that decides how the code is written: loop counters and condition results must come from activity results or from workflow state, never from ambient time or randomness.

Two pieces of the scheduler already carry the semantics and should be used rather than re-derived:

  • completeCondition(state, id, handle) — the condition marks the handle it took, and the scheduler decides what that means for the work queue. The node stops rewriting the queue; it reports which branch it chose.
  • computeLoopBody — the loop body already exists. Use it instead of re-deriving the body from indices, which is what the inline arrayNode does today between firstId and loopingToId.

Out of scope: changing what a condition means or how a loop terminates. The evaluateLoopCondition behaviour, including the maximum-iteration guard, ports as-is.

⚠ How it is today

conditionNode mutates currentLoopCounter in place and rewrites the engine's work queue via newIds = findConnectedNodes(...). The queue is whatever the node last wrote into it.

✓ How it will be

The condition reports a handle, the scheduler owns the queue, and the whole thing replays to the same answer — which a test asserts, not a person.

2Child workflows for fluxBox and libraryNodeflux.service.ts:5400, 5717 · :2660, :3287
Carry across the boundary everything the parameter list carries today — and lose none of the three things that can be lost independently.

fluxBox executes another whole flow inside the node, inheriting the parent's run-log collector, cancel key and trigger counters. libraryNode is structurally the same, and the engine already treats them together (:2660, :3287) — so they migrate as one unit, or the contract gets written twice and the two copies drift.

Three properties travel today because everything shares a process. Each is carried by a different parameter, and each can be lost independently:

  • Cancellation propagation — native to Temporal child workflows, so this one gets easier, not harder.
  • Nested run logs — a child's node logs still have to appear under the parent, which is the timeline the product already shows.
  • Billing attribution — tokens are attributed to the parent's billingFlowId, not to the sub-flow's own id.
⚠ How it is today

A sub-flow is a function call inside the same process, so the collector, the cancel key and the counters are simply in scope.

✓ How it will be

A sub-flow is a child workflow, and each of those three is an explicit part of the child's input — verified one by one, because they fail one by one.

3The run chain has to cross the boundaryTASK-S1 · TASK-S3
Three ceilings read the chain, and none of them can be expressed if the chain stops at the process edge.

The child carries a parentRunId back to its caller, and the visited-flow set and the depth counter travel with it (TASK-S1). Three things depend on that chain existing at this boundary and not only inside one process:

  • The cycle refusal — it needs a visited set, and the visited set is the chain.
  • The depth ceiling — a counter that resets at the boundary is not a ceiling.
  • The spend ceiling that TASK-S3 applies to the chain root — without the chain, five levels of nesting buy five ceilings.

Which is why the sentence in the spec is phrased the way it is: a child workflow started without the chain is a child workflow with no ceilings at all — and unlike today, a durable platform will faithfully sustain the result across the fleet, retrying each level.

⚠ How it is today

Recursion degrades one backend process. Somebody restarts something, and the run never returns.

✓ How it will be

The chain crosses into every child workflow, so the cycle refusal, the depth ceiling and S3's spend ceiling all still apply — at fleet scale.

This is why S1 shipped in Wave 0

The guard has to exist before the platform learns to sustain the recursion reliably. What is a crash today becomes a self-healing, fleet-wide, billed loop the day this task ships.

How it is proved

🔬 Verification
1
Negative control — the loop that never ends, and the dead branchrequired
Make a loop's termination condition never fire and confirm the guard stops it — then confirm the workflow surfaces it as a real failure, not as a workflow that runs until its timeout. Do the same for a condition branch that marks the wrong handle: assert the dead branch is marked dead and its downstream nodes do not run.
2
Replay determinismrequired
Take a completed workflow history and replay it. Any non-determinism shows up here and nowhere else; this test is not optional for a control-flow workflow.
3
Nested runs — all three properties, separately
A fluxBox inside a flow must produce nested run logs, propagate cancellation from the parent, and attribute tokens to the parent. Verify all three, since each is carried by a different parameter today and each can be lost independently.
4
Loop billing matches the pre-migration totals
Per iteration, using the execution identity from B1. A loop is where an identity bug turns into a billing bug, and it is the cheapest place to catch one.
✓ Done when
All four types run in the worker; a replay test passes; nested runs keep their logs, cancellation and billing; and no executable node type remains inline.

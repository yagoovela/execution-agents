Added on 2026-10-26 from the code check of decision S6-a.

S6 shipped an egress policy and A9 shipped a second, stricter one. The check of decision S6-a, repeated on 2026-10-26 against back main 10e64b20 and worker main abf3b09d, found four places where a user-supplied URL still leaves the platform unchecked, or checked in a way that does not hold.

The most exposed is the back's /proxy route: an Express middleware registered before any Nest guard, which forwards to the origin in its url parameter. The front uses it to load images, so the fix authenticates and allowlists it rather than deleting it.

What the task does, in three parts

1Close /proxyback/src/main.ts
Require authentication and forward only to an allowlist of our own asset hosts.

The allowlist comes from configuration (CloudFront and the S3 buckets the image nodes write to), never from the request. Before it ships, count from the access logs which hosts /proxy serves today, so a real image host is not refused.

⚠ How it is today

Any caller, any URL, before every guard.

✓ How it will be

A token is required, and only our asset hosts are forwarded.

Keep working

ExpandImageModal.tsx and MaskImageEditModal.tsx load images through this route.

2One guard that pins the addressworker/src/modules/safe-fetch/
Make safe-fetch use the A9 egress module, and keep one deny-list.

Today safe-dispatcher.ts connects by hostname after the check, so the name resolves twice. The egress module already checks every address, pins the checked one through a lookup hook and checks each redirect hop again.

3Guard the back and sweep the restback/src/app-api/api_call/
Put POST /api_call behind the same check, and record every other outbound fetch of a user URL.

DownloaderService.downloadFile has no caller: delete it, or guard it if one turns up. Check first whether the plain fetch(url) calls in the audio transcriber, the Document AI reader and Push Data can receive a user URL.

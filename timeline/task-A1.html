Four independent lists answer “can the worker run this node type?”, and none of them references another (analysis §9.2.3): isTemporalNode with seven types, isWorkerRoutedIntegration with nine providers, MIGRATED_TEMPORAL_NODE_TYPES with the same seven, and a 17-type prefetch whitelist.

Two consequences are already live: thirdPartyIntegration takes the worker path inside a flow and the inline path from the legacy endpoint, and the worker's sqlQuerier and audioReaderNode modules are reachable by nothing (§9.4). Neither is a bug in any one list — they are what four lists that never look at each other produce.

The decision this task needs

One call has to be made before the registry can claim to be authoritative, and it is not an engineering trade-off — it is a fact nobody has looked up. It opens below with the options, what each costs the customer and costs us, and the three checks that settle it.
▸Decision A1-aPLAN D5Open — needs a callWhat are comment, label and group?
These three sit in PREFETCH_SUPPORTED_NODE_TYPES (flux.service.ts) and are not among the 48 registered front node types (analysis §9.2). The plan is blunt about why that blocks this task: the registry cannot be authoritative while three types in a live whitelist are unaccounted for. And the whitelist is all-or-nothing — canUsePrefetchForFlow requires every node in a flow to be in it — so whatever these three are, they decide whether a flow containing one gets the prefetch executor at all.
ADecorative canvas objects — put them on an explicit ignore listrecommended
They are annotations on the builder canvas, not executable nodes. Each gets a registry entry that says exactly that, and the prefetch whitelist keeps trusting them — now for a stated reason instead of by inheritance.
  • Keeps A1 behaviour-neutral, which is its mandate: a flow containing one of the three keeps the prefetch path it has today
  • Makes the registry authoritative — every entry in the whitelist has a row naming what it is
  • Gives the next decorative type a place to be declared, instead of a fourth list to be added to
  • It is only true after the greps. Written before them, it is an assertion the drift spec cannot check — the spec catches a missing worker module, not a wrong classification
Client effort: noneOurs: three entries and one test
BReal node types that were never registered in the front
They exist in stored flows and something executes them; the census of 48 counted registered front components, so it would have missed them. They get real registry entries with their real dispatch.
  • If any of the three does execute, classifying it as decorative is the worst available outcome — this option is the one that cannot be quietly wrong
  • The registry states what is true rather than what is convenient
  • It turns A1 into the discoverer of a migration, and A1 is behaviour-neutral by mandate — the work would belong to a Track A task, not to this one
  • Nothing in the analysis found an executor for any of the three; this option needs evidence it does not yet have
Client cost: unknown until measuredOurs: a new Track A task
CDead entries — delete them from the whitelistrejected
Nobody can name them, so remove the three from PREFETCH_SUPPORTED_NODE_TYPES and let the registry cover only what exists.
  • The shortest list is the easiest to trust, and a whitelist entry with no owner is exactly what rots
  • This is a behaviour change wearing a cleanup's clothes. Any stored flow containing one of the three stops satisfying canUsePrefetchForFlow and silently drops to the legacy path
  • It is a refusal, so PLAN §3.3.2 applies: measure it against the stored flows first and drive false refusals to zero. Deleting first and measuring never is the pattern that rule exists to stop
  • A1 is behaviour-neutral by mandate, so this cannot land in A1 in any case
Client cost: flows silently lose the prefetch pathOurs: an unmeasured refusal
Our recommendation

A — and the three things that settle it are an afternoon of work, not a research project.

1. Grep the three type strings across front/. If they render as canvas annotations and never reach a submit or a run handler, they are decorative and A is simply true. 2. Count the stored flows whose nodes carry those types — the same query also measures option C's blast radius, which is the number nobody has. 3. Check the prefetch executor's own is-non-executable.ts (analysis §9.2): if it already classifies them, the answer has been written down once and just never made it into the whitelist's reasoning.

Whichever way it lands, the answer goes into the registry, not into a review comment. That is the entire point of this task: the next person to ask should read a row, not repeat the greps.

What the task does, in four parts

1One registry, and six predicates that read itflux.service.ts · integration-executable-node.ts
One entry per node type, carrying the facts each caller already needs — so the callers stop carrying their own copy.

The registry module lives in back, keyed by node type, and holds exactly what the existing callers ask for:

{ workerModule, dispatch, integrationProviders?, prefetchSafe, mutating, hasInlineTwin }

Then all four predicates are re-expressed as reads of the registry, six functions in total: isTemporalNode, isWorkerRoutedIntegration, isMigratedTemporalNode, isLegacyRunnableNode, isMutatingNodeType and canUsePrefetchForFlow.

The function names stay. Call sites do not change, which keeps the diff reviewable — a refactor that touches every caller cannot be reviewed for behaviour neutrality, and behaviour neutrality is the whole claim.

⚠ How it is today

Adding a node type means remembering four edits in four files, and nothing tells you when you forgot one. Two types are already wrong because of it.

✓ How it will be

One entry per type. The six predicates read it, so forgetting becomes a test failure instead of a production surprise.

2basedOnType becomes a projection, with its contents unchangednode-reference-substitution.service.ts
Fold the fifth list in now, while it is only a projection — before B3 makes it the thing that decides what a consumer may resolve.

It stops being a parallel hand-maintained map and becomes a view over the registry. Its contents must not change in this task: the same fields referenceable, the same behaviour, node for node.

That constraint is what makes it safe to do here rather than inside B3. A projection whose output is byte-for-byte the old map is provable in a test; a projection that also improves the map is a behaviour change nobody asked for in a task that promised none.

⚠ How it is today

A hand-maintained whitelist of referenceable fields, edited from memory, with nothing checking the edit.

✓ How it will be

The same whitelist, derived. When B3 moves input resolution to the consumer, it reads one source instead of inheriting a second.

3A contract fixture two repos can share without a build graphworker/src/modules/nodes/nodes.types.ts
Make the worker's enum the authority on which modules exist, without pretending the two repos can import each other.

A node_types.contract.json lands in back, generated from the worker's NodeType enum, plus a spec that fails when the registry claims a workerModule the enum does not have.

The repos are separate submodules with no shared build graph, so this is a committed fixture with a regeneration script — not an import. That is a deliberate limitation: the fixture is only as fresh as the last regeneration, and the spec is what makes staleness loud instead of silent.

⚠ How it is today

The worker's enum and the back's lists are two independent claims about the same fact, and nothing has ever compared them.

✓ How it will be

A registry entry naming a module the worker does not have fails a spec by name. This fixture is also the artefact D2 publishes for agents to read.

4The invariant that turns stranding into a test failure
State the epic's rule once, as a spec: a node type may not have a worker module and inline dispatch at the same time.

The spec asserts it directly: no type may have workerModule: true and dispatch: 'inline' without an explicit strandedReason.

That is not an abstract rule looking for a violation. It is sqlQuerier and audioReaderNode today, and clearing them is exactly what A3 is for. The registry does not fix them — it makes them impossible to forget again.

⚠ How it is today

Two worker modules ship to production on every deploy and nothing routes to them. It took a document to notice.

✓ How it will be

The same state fails a spec that names the type, and clearing it is a task with an owner rather than a paragraph in an analysis.

Scope — what A1 must not do

A1 changes nothing about what any node type does. Same types dispatched, same refusals, same prefetch eligibility. The inconsistencies it exposes belong to the tasks that own them — A2, A3 and C1. This task only makes them visible in one place.

How it is proved

🔬 Verification
1
Negative controlrequired
Two observed failures, both stated in the PR. Delete one type from the registry, run the suite, and record which test went red and with what message. Then flip a dispatch value and confirm the behaviour-neutrality spec catches it. A registry whose tests do not fail when it is wrong is a fifth list with better formatting.
2
Behaviour neutrality, one case per typerequired
For all 48 registered types plus the 3 unaccounted ones, assert the new predicates return exactly what the old lists returned. Table-driven, one case per type — this is the test that makes the refactor safe, and it is the only artefact that can prove the claim in the fourth glance tile.
3
Measure before refusingrequired
PLAN §3.3.2. canUsePrefetchForFlow is a refusing rule. Run the new implementation against real stored flows and confirm the set of flows it accepts is identical to today's. Report any difference as a defect in this task, not as an improvement — a refactor that quietly accepts one more flow has changed behaviour, whichever direction it changed it in. While that run is open, record D2's numbers: how many stored flows satisfy the whitelist, how many ran with FLUX_EXEC_MEMORY_MODE=prefetch, and what it saved. Report them in the PR — B3 answers D2 with them (Wave 4) and C2 executes the answer (Wave 6).
4
No second source survives
“Done when” says the registry is the only place a node type's dispatch is declared. After the refactor, grep for the old list names: a predicate that still keeps its own copy makes the registry advisory rather than authoritative, and advisory is how this started.
✓ Done when
The registry is the only place a node type's dispatch is declared; the six predicates read from it; the drift spec is green; the behaviour-neutrality table covers every type; and no production behaviour changed.

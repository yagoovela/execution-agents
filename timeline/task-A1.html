What the task does, in five parts

1One registry, with two fields this correction addsflux.service.ts · integration-executable-node.ts · legacy-allowlist.ts · legacy-node-dispatch.ts
One entry per node type, keyed by node type, carrying the facts each of the nine lists currently answers separately.

The registry holds: { workerModule, dispatch, integrationProviders?, prefetchSafe, mutating, hasInlineTwin, dispatchConflict? }. hasInlineTwin and dispatchConflict are new, added by this correction. hasInlineTwin carries what A3's invariant already needed (workerModule: true with dispatch: 'inline'). dispatchConflict.legacyRunnable names the second, larger defect this correction found: a type can have dispatch: 'worker' and simultaneously be accepted by /process/single-node-legacy — two different code paths for the same node type, chosen by which endpoint the caller happened to hit. Today that is true for exactly three types: voiceBoxNode, webSearch, commandContentNode.

Re-express all nine predicates as reads of the registry. Keep the function names — call sites should not need to change, which keeps the diff reviewable.

⚠ How it is today

Nine lists answer the same question independently, and two live inconsistencies already exist because none of them references another.

✓ How it will be

One registry, read by nine predicates whose names do not change. Adding or fixing a type is one edit instead of up to nine.

2Register the four phantom types — D5, decided by measurementflux.service.ts · legacy-allowlist.ts · legacy-node-dispatch.ts
Naming them in the registry is what makes them accounted for. Removing them from the lists that trusted them would have been a false refusal for three, and an unmeasured guess for the fourth.

comment, label, group were the original three (decision D5, PLAN §7). This correction adds a fourth: voiceNode, present in LEGACY_SINGLE_RUN_NODE_TYPES and in legacy-node-dispatch.ts's shared case 'voiceBoxNode': case 'voiceNode': arm, but registered in no node-type source. All four get a registry entry marked phantom; none is removed. comment/label/group stay prefetch-safe, bound by a spec to NON_EXECUTABLE_NODE_TYPES so neither set can grow alone; voiceNode goes to A1c, because its own measurement was never run and it sits on a live endpoint's accept list rather than a permissive whitelist.

⚠ How it is today

Four types sit in live whitelists with no owner and no registration anywhere a developer would look.

✓ How it will be

The registry names all four and records that nothing can create them. Nobody has to re-derive it, and no list quietly lost a type it was relying on.

webCrawling is in neither MIGRATED_TEMPORAL_NODE_TYPES nor LEGACY_SINGLE_RUN_NODE_TYPES, so validateNode's isLegacyRunnableNode check falls through to the generic refusal instead of the correct "is migrated to Temporal" message every other worker-routed type gets. Whoever picks up this task decides which PR it lands in; either way it must land.

A caller hitting webCrawling through the legacy endpoint sees the wrong refusal message — generic, not the one every other worker-routed type gets.

✓ How it will be

webCrawling gets the same "is migrated to Temporal" message as the other thirteen isTemporalNode types.

5The dispatchConflict invariant, pinned to it.failing()back — jest 29.3.1
State the rule once, as a spec that stays green on arrival instead of red — because back has no CI running jest, and a red spec on arrival poisons every local run before this PR even lands.

The invariant: no type may be in both isTemporalNode and LEGACY_SINGLE_RUN_NODE_TYPES. As of back@origin/production 3804a524 this is false for exactly three types. Two things, not one spec: three named it.failing() cases, one per known-broken type (voiceBoxNode, webSearch, commandContentNode) — it.failing inverts reporting, so an assertion that genuinely fails today is reported as passing, keeping the suite green on arrival; the moment C1 deletes that type's inline twin, the assertion starts succeeding and it.failing reports that as a failure, which is the cue to drop that case. Plus one plain it() asserting the invariant for every other type, so a fourth type falling into the same trap later does not pass silently.

⚠ How it is today

The same inline-twin defect that thirdPartyIntegration has exists silently for three more types, with nothing naming it.

✓ How it will be

Three named it.failing() cases document exactly which types have the defect today, and turn red — loudly — the moment each one is actually fixed.

Shape
Delete, not port
The per-node poller and nodeCancelContext are removed — sixty nodes stop meaning sixty timers.

The current mechanism cannot move as-is: nodeCancelContext is AsyncLocalStorage, so it is blind the moment the handler runs in another process. The rest of it — a Postgres status column, a WebSocket signal, a poll — is portable, but it is not what you would build on Temporal.

Temporal already has this. WorkflowHandle.cancel() on the backend side and Context.current().cancelled on the worker side give cooperative cancellation with none of the polling. There is also a cost to carrying the current design forward: it runs one setInterval per node, so a sixty-node agent holds sixty timers hitting the database.

Our recommendation

A. It is the spec's answer and the two supporting facts are not close: the ALS context cannot move at all, and the portable remainder is a per-node timer we would be carrying into a bigger fleet. What the task does, in three parts

1Cancel becomes a workflow callback/src/temporal/temporal.service.ts · flux/node-cancel-watch.ts
The backend asks Temporal to cancel; the worker cooperates. Nothing polls.

The backend calls handle.cancel() when a cancel is requested, and the worker respects Context.current().cancelled. The per-node poller is retired along with nodeCancelContext.

The child-workflow case is the one that proves the design rather than merely implementing it: cancelling a run that is inside a fluxBox or a libraryNode has to stop the child too, and cancellation propagation is native for child workflows. That is a cheap test and a strong signal — the hand-built alternative would need that propagation written and maintained.

⚠ How it is today

A cancel writes a status column, emits a WebSocket signal, and each node's own setInterval polls the database for it — a sixty-node agent holding sixty timers.

✓ How it will be

The backend calls handle.cancel() and the worker checks Context.current().cancelled. The poller and nodeCancelContext are deleted, and child workflows stop for free.

Out of scope

Changing what cancellation means to the user, or cancelling side effects that already committed. A cancelled push that already reached Stripe stays sent.

2What the product keepsflux.service.ts:3192–3194, 4516–4530
Temporal cancels a workflow; it does not write the product's state. That part stays ours.

Two things survive the convergence unchanged. The cancel footprint — which node the run was on when it was cancelled — is shown to the user and stays. And finishCancelledNode must still mark state correctly, so a cancelled run does not look stalled: a run that was cancelled and a run that hung look identical from the outside unless someone writes the difference down.

The feature flag needs its own check before any of this leans on it. NODE_CANCEL_IN_FLIGHT_FLAG was added after the original design and is not proven at production scale — validate its current state rather than assuming it is on and working.

⚠ How it is today

The footprint and the cancelled state are written by the backend loop that owned the run and observed the cancel.

✓ How it will be

The same footprint and the same terminal state are written from the worker-owned run — the UX is unchanged, which is the point.

3State the latency, do not assume ita 1500 ms cache over a 2000 ms poll
Today up to 3.5 s can pass between the click and the effective cancel. Native cancellation should improve that — should is not a contract.

The 3.5 s is arithmetic, not measurement: a 1500 ms cache sitting over a 2000 ms poll. Replacing the poll with cooperative cancellation removes both terms, but the number that matters is the one measured on a real run, before and after.

The other measurement is the timers. Run a sixty-node agent and count active timers and the database query rate against the pre-change baseline — the claim that the poller is a performance offender in its own right is either demonstrable or it is not worth making.

⚠ How it is today

Up to 3.5 s, derived from the cache and poll intervals. Nobody has measured the real click-to-effective-cancel time.

✓ How it will be

A measured click-to-effective-cancel number, before and after, stated in the PR — along with the timer count for a sixty-node agent.

Decision to write down — the latency contract

'Should improve' is not a contract; a number is. Decide what click-to-effective-cancel the product promises, then measure against it — and if the measured number is worse than 3.5 s anywhere, that is a finding, not a rounding error.

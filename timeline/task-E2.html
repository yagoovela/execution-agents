The decisions this task needs

Four decisions. E2-a chose the mechanism on 2026-10-23; E2-b, E2-c and E2-d rescoped the task on 2026-10-26, after the production check.
▸Decision E2-aSettledDo we port the cancellation mechanism into the worker, or converge on Temporal's?
The spec answers this in its own title, and it is recorded here because port it is the default any team reaches for when a mechanism has to keep working somewhere else. Two facts decide it. nodeCancelContext is AsyncLocalStorage and cannot cross a process boundary at all, so 'identical semantics' is not actually on offer. And the portable remainder runs one setInterval per node — a sixty-node agent holds sixty timers hitting the database. Behind a flag that is tolerable; on by default and unoptimised it becomes a performance offender in its own right.
ATemporal-native cancellationrecommended
The backend calls handle.cancel(); the worker respects Context.current().cancelled. The per-node poller and nodeCancelContext are retired.
  • The mechanism already exists on both sides — the migration gets cancellation almost for free
  • Propagation into child workflows (fluxBox / libraryNode) is native, so B6's sub-flows inherit it
  • Sixty timers and their database queries disappear from a sixty-node agent
  • Latency should improve — today a 1500 ms cache over a 2000 ms poll can leave up to 3.5 s
  • The cancel footprint and finishCancelledNode still have to be wired by hand — Temporal cancels a workflow, it does not write the product's state
  • Cooperative cancellation only stops what checks it: an activity in the middle of a provider call finishes that call
Client effort: none — the cancel button is unchangedOurs: we delete more than we add
BPort the portable remainder
Keep the status column, the signal and the poll, and re-implement the per-node watch inside the worker — replacing the ALS context with something that crosses processes.
  • The semantics stay literally identical, so nothing about the footprint UX has to be re-reasoned
  • No dependence on Temporal cancellation semantics the team has not exercised yet
  • It carries one setInterval per node into a fleet that is about to have more replicas
  • The ALS context has no cross-process equivalent, so it has to be rebuilt anyway — 'identical' is not on offer
  • Child-workflow propagation would have to be written and maintained, when Temporal gives it
Client effort: noneOurs: sixty timers per agent, plus hand-written propagation
CCarry nodeCancelContext as it isnot viable
Keep the AsyncLocalStorage context and let the worker read it.
  • No work
  • AsyncLocalStorage does not cross a process boundary — the context is simply empty in the worker
  • The failure is silent: the cancel appears to succeed and the next node starts anyway
Client effort: noneOurs: a cancel that silently does nothing
Our recommendation

A. It is the spec's answer and the two supporting facts are not close: the ALS context cannot move at all, and the portable remainder is a per-node timer we would be carrying into a bigger fleet. The child-workflow test is the cheap proof — propagation is native there, and B is the option that would have to build it.

Two things must not be lost in the convergence. The cancel footprint — which node the run was on when it was cancelled — stays a product surface. And finishCancelledNode must still mark state correctly, so a cancelled run does not look stalled.

Before any of this leans on it, validate the current state of NODE_CANCEL_IN_FLIGHT_FLAG: it was added after the original design and is not proven at production scale. A flag assumed on is a flag nobody tested.

What the task does, in three parts

1What the ledger records when a generation is cancelledworker/src/modules/temporal/workflows/resolve-cancel-settlement.ts · process-single-node.workflow.ts
Make a cancelled generation legible in the ledger instead of silently free (D22).

We ask the provider to cancel, and what we can record depends on what it answers. If it reports the tokens spent up to that point, record the charge normally — exactly as a generation that completed. If it reports nothing, record what is available and mark the entry as cancelled or aborted by the user.

The open gap is the thrown-error path: resolveCancelSettlement receives output: null and charges nothing. The cancelled mark is the node_executions row (executionStatus: 'CANCELLED', cancelledAt), per E2-c — token_transaction gets no new column.

⚠ How it is today

A cancel that returns a cancelled output is charged its partial tokens; a cancel that arrives as a thrown error is charged nothing.

✓ How it will be

Both paths charge the tokens the provider reported, and the node_executions row is CANCELLED.

Never record zero

Zero for a cancelled generation that consumed tokens is the case that makes the ledger disagree with the provider's invoice — and it disagrees silently, which is why it is worth a rule rather than a habit.

2State the latency, do not assume ita 1500 ms cache over a 2000 ms poll
Today up to 3.5 s can pass between the click and the effective cancel on the inline loop. Should improve is not a contract.

The 3.5 s is arithmetic, not measurement: a 1500 ms cache (isCancelRequested) sitting over a 2000 ms poll. Measured on dev on 2026-10-26, from the cancel request to node_executions.cancelledAt for an in-flight text node: inline loop n=16, median 1.88 s, max 2.26 s; processFlow n=8, median 1.94 s, max 2.08 s.

The latency contract (2026-10-26)

A worker node stops within about 2.3 s of the cancel request on both engines. The bound is the worker's 2 s Temporal heartbeat throttle, not the back's cache and poll. The 3.5 s figure applies only to nodes the back runs itself, and it leaves with the poller in C1.

3What moved out, and whereE2-b → C1 · E2-d → B6
Two pieces cannot be delivered while the inline loop still executes nodes.

The per-node poller goes to C1. node-cancel-watch.ts, nodeCancelContext and the node_cancel_in_flight flag are deleted with the inline loop, after the B4 flag is on in production and after B6 moves the container types. Removing them earlier would leave an inline node stopping only between nodes.

D23 goes to B6. fluxBox, libraryNode and arrayNode are inline until B6 makes them workflow constructs, so nothing in E2 can deliver or prove the propagation.

Out of scope

Changing what cancellation means to the user, or cancelling side effects that already committed. A cancelled push that already reached Stripe stays sent.

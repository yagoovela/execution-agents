reportBuilder is pure compute plus one upload: it sorts data.variables by (y, x), escapes HTML, composes the document and calls uploadService.uploadText. Handler at flux.service.ts:9177, dispatched at :1343.

It is the only remaining node where a migration exercises the whole pipeline — registration, dispatch, persistence, notification — without a provider surface or a new contract obscuring a failure. That is what makes it the right canary, and not merely the easiest win.

The decision this task needs

One call has to be made before the code is written, and the spec names it: where the composed report is actually written. It opens to the two options, what each costs the customer and costs us, and the one we would pick.
▸Decision A4-aRecommended — confirmDoes the report upload go through /worker/generate-file, or does the worker get its own S3 client?
The spec names this one explicitly — “Decide the upload path”. uploadService.uploadText has no worker equivalent, but /worker/generate-file already exists and is the established contract. Analysis §3.1 says the same thing from the other side: the upload “has a direct equivalent in the existing /worker/generate-file callback, or can be re-implemented worker-side against the same bucket”. That “or” is the fork. It matters more than it looks, because the worker deliberately has no S3 client — which is exactly why the claim check travels through the API.
ACall /worker/generate-filerecommended
The worker composes the document and hands it to the callback the API already exposes. No storage credential ever reaches a worker replica.
  • It is the contract every migrated node that produces a file already uses — nothing new to learn or to review
  • Keeps the worker free of storage credentials, which is the property the claim-check design depends on
  • Nothing to deploy per environment — the canary stays a canary
  • The document makes a round trip through the API — the same anti-goal review §2.4 names for the claim check
Client effort: none — output is unchangedOurs: reuse one existing callback
BGive the worker its own S3 clientbigger question
uploadText is re-implemented worker-side against the same bucket, as analysis §3.1 allows. The report never touches the API.
  • Removes the round trip, in the direction review §2.4 argues for
  • The same change S5 weighs for the claim check — if it happens, this node comes along for free
  • Every worker replica needs scoped storage credentials — a real identity change, per environment
  • It makes the cheapest node in the catalogue the place where a credentials decision gets made, which is how a canary stops being one
Client impact: noneOurs: IAM + a deploy per environment
Our recommendation

A, and record it. The spec already states the preference — “prefer the callback over a second S3 client in the worker” — so what is open is not really which, but whether we write it down before the code exists. Write it down.

The reason is the canary: A4 exists to re-validate the activity template end to end, and a migration that also introduces a new credential path is no longer measuring the template. If the worker does get storage credentials, that is a whole-epic decision with S5's arguments behind it — not something the cheapest node in the catalogue smuggles in.

What the task does, in three parts

1The worker module, on sql-querier's shapeworker/src/modules/nodes/report-builder/
Reuse the shape a migrated node already has, so the only thing under test is the pipeline itself.

The module is a thin process(props) that does five things in order, and none of them is new to the worker:

  • Fetch the node row.
  • Validate the configuration, throwing UserConfigError when it is the author's mistake rather than ours.
  • Sort data.variables by (y, x), escape HTML, compose the document.
  • Call the file callback (Part 2).
  • persistNodeSuccess, and return the DTO.

Then the registry entry from A1, behind the flag — the new path lands disabled and is flipped in a separate deploy, per PLAN §3.2.

⚠ How it is today

The report is composed inside flux.service.ts, in the engine's process, dispatched from :1343.

✓ How it will be

The worker composes it, the registry says so in one place, and the flag still defaults to today's behaviour until it is flipped.

2The upload path/worker/generate-file
Settle where the composed document is written before any code assumes an answer.

uploadService.uploadText has no worker equivalent. /worker/generate-file does exist, and it is the contract every migrated node that produces a file already uses. The alternative — a second S3 client inside the worker — is a credentials change, not an implementation detail.

This is decision A4-a above. It is short, but it should be written down rather than discovered in review.

⚠ How it is today

The engine calls uploadService.uploadText in-process. The worker has no way to write the file at all.

✓ How it will be

The worker calls the established file callback and holds no storage credentials — the same property the claim check relies on.

3Prove it, flip it, delete the twinflux.service.ts:1343, 9177
A node is not migrated when its activity exists — it is migrated when the inline twin is gone.

Run both implementations over every distinct reportBuilder configuration in the dev database and diff the produced text. Then flip the flag in its own deploy. Then delete the handler at :9177 and the dispatch at :1343 — PLAN §3.4 point 4 is satisfied by deletion or by a guard that cannot double-fire, and here deletion is available.

One behaviour is easy to lose in a rewrite: empty variables returns early in the inline version. The worker has to match that, rather than politely producing an empty document.

⚠ How it is today

Two implementations of the same report could coexist, and only a reader comparing them by eye would notice they had drifted.

✓ How it will be

One implementation, proven equal over the stored configurations before the other one is removed.

The wave's latency regression starts here

Every node migrated in this wave becomes a blocking round trip until Wave 5 turns on parallelism (review §4.5, risk R4). reportBuilder is the first one and the cheapest, which makes it the best place to measure the round-trip cost every later node in the wave will pay.

DELIVERY-PLAN asks for the number per task, in the PR. A team surprised by it in production asks to roll the migration back; a team that was told the number expects it.

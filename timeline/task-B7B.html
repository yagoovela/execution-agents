Batch rows keep chat memory, a retried prepare writes once, and workflow runs keep their log steps

A batch row run through processFlow computes and records the same thing as the same row run through the API loop, a retried step writes one run, and every run whose nodes ran in the worker keeps its steps on the Logs page.
[868muzee4](https://app.clickup.com/t/9011479430/868muzee4) · `fix/868muzee4` (back #2121, worker #175) · Deployed to production on 2026-11-19, back first (back #2121 `5dfdbbf1` in the back deploy `062efa0e`, `api-task-definition-prod:858`; worker #175 in the worker deploy `21949f62`, `worker-task-definition-prod:104`; spec #118). Each batch row runs in a chat session of its own, keyed by its `runId`; scheduled runs keep the shared default session. Specified 2026-11-18 against back `4e759cf7`. A batch row runs a chat-memory `fluxObject` without its history because `prepare` skips the session preparation `apiV2` does; a retried `prepare` leaves an orphan run, because each call draws its own `runId`, so the workflow now owns the id (adds a worker change); a run whose nodes ran in the worker, through `apiV2` or `closeWorkerRun`, loses its Logs steps when `run_log_from_events` is off.

A13 restored the batch rows' Data Output value, callback and run logs. On the way it found three gaps it did not cause, on the paths B7 and B4 opened. Read again on 2026-11-18, two of them were wider than first written: a retried prepare leaves an orphan run, because each call draws its own runId, and the lost log steps hit closeWorkerRun too, the end that batch rows use in production.

The task closes the three gaps without restating what apiV2 already does: it calls the same session preparation, lets the workflow own the row's run id, and folds a worker run's log from its events.

What the task does, in three parts

1One session preparation, a session per rowback/src/app-api/flux/flux.service.ts
The apiV2 session block moves, as it is, into one method, prepareRunSessionNodes, that apiV2 and the batch-row preparation both call.

It clears memory on execution, loads the stored chat history and keeps chat: true on the first chat node only. Batch rows run five at a time, so sharing the default session would read other rows' turns in no fixed order. Decided on 2026-11-18: each row falls back to a chat session keyed by its own runId, so it starts with empty memory and records its turn there. Scheduled runs keep the shared default session.

⚠ How it is today

A chat-memory node answers without history.

✓ How it will be

It is prepared as through the API, in the row's own session.

2The workflow owns the row's run idworker process-batch.workflow.ts · back batch-run-preparation.service.ts
processRow draws the runId with the workflow's uuid4() and passes it to every attempt of prepareBatchRowRunActivity.

The back takes the optional runId, refuses one that is not a UUID, and falls back to its own when none is sent. Each Variable Input row gets an id derived from the run and the node, inserted with ON CONFLICT (id) DO NOTHING, so a second call writes nothing. Deploy order: back first, then worker.

⚠ How it is today

A retried prepare leaves an orphan run.

✓ How it will be

Two calls leave one run.

3Events are the log source for worker runsback flux.service.ts (openSpaceRunLog) · run-events.service.ts
A run whose nodes ran in the worker has a collector with no node entries; in off and shadow mode its end overwrote the run log with nodes: [].

A run opened for the worker now uses the events mode whatever the flag says, and a workflow-routed apiV2 run switches to it when it routes. The final log is folded from events; the collector document is written only when the rebuild returns nothing or throws. Inline apiV2 runs keep their behaviour.

⚠ How it is today

The Logs page shows nodes: [].

✓ How it will be

The Logs page shows the steps.

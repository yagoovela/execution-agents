The batch stalls at lastProcessedLine with a non-terminal status, and nothing resumes it.

/flux/batch-process calls this.processBatch(...).catch(...) (flux.controller.ts:560) — unawaited. The request returns immediately and the work continues detached inside the backend process.

processBatch (:574–706) is a sequential for loop over CSV rows. Per row it re-reads the batch, re-reads the row record, runs a complete flow via await this.fluxService.apiV2(…), writes the output, re-reads the batch and saves the pointer — four to five database round trips on bookkeeping before the run itself.

The decisions this task needs

One call, and the spec asks for it directly: with a workflow, a stall becomes either an automatic continuation or a visible failure — decide which, and make sure the status endpoint reflects it honestly.
▸Decision B7-aRecommended — confirmWhen a batch stalls, does the workflow continue automatically or fail visibly?
Today a stalled batch needs someone to notice: the loop dies with the process, the row pointer stops moving, and the status column keeps claiming the batch is running. A workflow removes the silence — but it does not by itself decide which non-silent answer the customer gets. The constraint that binds every option below: the existing /batch-process/:id/status must reflect the choice honestly, because a non-terminal status that will never move again is the exact defect being fixed.
AAutomatic continuation, always
The workflow retries the row and carries on. A deploy, a restart or a provider blip is invisible to the customer.
  • Durability is the whole reason this task exists — a deploy stops being a data-loss event
  • The customer never has to know that the platform restarted underneath their batch
  • A row that fails for a real reason — a bad CSV cell, a revoked credential — retries silently, and the batch takes hours with nobody told
  • Every retried row is a full flow run that costs money; without a bound, retrying is how a batch becomes an invoice
Client sees: a batch that is slow, not failedOurs: silent cost, no signal
BA visible failed workflow
The batch stops, the workflow is failed, and the status endpoint names the row it stopped on. A human decides what happens next.
  • Nothing is hidden — the state is terminal and it is true
  • A bad CSV is diagnosed at the row that is bad, instead of at the end of a long silence
  • It recreates today's stall with a better label — and the point of the workflow was that nobody should have to notice
  • A deploy in the middle of a legitimate batch becomes a customer-visible failure, which is a regression, not a fix
Client effort: restart the batch by handOurs: nothing hidden
CBounded continuation, then a visible failurerecommended
Infrastructure stalls resume automatically. A row that keeps failing is retried a bounded number of times, then the batch fails with that row named and every completed row preserved.
  • It separates the two failures that A and B confuse: the platform restarted is not this row is broken
  • The retry bound is what stops retries from becoming an unbounded cost — it is the same shape as every other ceiling in this epic
  • It maps onto Temporal's retry policy rather than being hand-rolled bookkeeping
  • The bound is a number somebody has to choose, and the honest default is not obvious before the first real batch fails
  • Two terminal shapes to represent in the status endpoint instead of one
Client sees: the failing row, by nameOurs: a retry bound to choose
Our recommendation

C. A and B are each right about one half: a stall caused by us should heal, and a failure caused by the data should be seen. Treating them as one event is what produces either a silent bill or a customer-visible failure for a deploy nobody asked about.

Whichever is chosen, the honesty requirement is not optional: /batch-process/:id/status must be terminal when the batch is over and must name the row when it failed. A status that says running forever is the defect this task exists to remove, and a workflow can reproduce it just as easily.

What the task does, in three parts

1One child workflow per row, and the pointer becomes stateflux.controller.ts:560, 574–706
Replace a detached loop with a durable one, and let the per-row bookkeeping collapse because the loop can finally trust its own memory.

The shape is a batch workflow with one child workflow per row, a concurrency cap, and the row pointer held as workflow state rather than a column that is re-read every iteration. continueAsNew goes at a row boundary — a large CSV is exactly the case that exhausts workflow history (review §4.1).

The per-row bookkeeping today looks like this, before the run itself:

per row: re-read the batch -> re-read the row record -> apiV2(...) -> write the output -> re-read the batch -> save the pointer

That re-reading exists because the loop cannot trust its own memory across a restart. A workflow can — which is why the collapse is a consequence of the change rather than a separate optimisation. The claim in the spec is four to five round trips per row: prove it or correct it.

⚠ How it is today

An unawaited for loop inside a request handler. Its progress lives in a column it re-reads because it cannot trust anything else.

✓ How it will be

A durable workflow with one child per row, a concurrency cap, and the pointer in workflow state — with continueAsNew at a row boundary so a large CSV cannot exhaust the history.

2The progress columns keep their meaningback/src/entities/batch_processing_file*.ts
The workflow becomes the writer of the surface the customer already watches — it does not replace it with a new one.

lastProcessedLine and the batch status columns stay, and they stay updated. They are the customer-facing progress surface, and the existing status and download endpoints read them. What changes is who writes them: the workflow, instead of a loop that re-read them to remember where it was.

This is what keeps the task revertible. The columns are the contract; the loop behind them is an implementation detail that this task replaces.

⚠ How it is today

The columns are both the progress surface and the loop's memory, which is why they are re-read four to five times per row.

✓ How it will be

The columns are only the progress surface. The workflow remembers where it is, and writes them because the customer reads them.

Out of scope

Changing the CSV format, the input mapping to varInputNodes, or the output shape. A row-for-row output comparison against a pre-change run is what proves it.

3Stop becomes cancellationflux.controller.ts:513–517, 710–800
Honour the stop endpoint through workflow cancellation, which reaches the rows already in flight.

Today /batch-process/:id/stop sets a flag the loop checks. That means a row already running finishes, and a loop that has already died never checks anything at all — stop on a stalled batch does nothing visible.

Through workflow cancellation, stop reaches the batch workflow and the row children already in flight. This is strictly better than today, and it is the same mechanism E2 aligns the rest of the system on.

⚠ How it is today

Stop sets a flag. In-flight rows run to completion, and a batch whose loop has already died ignores stop entirely.

✓ How it will be

Stop cancels the workflow, which cancels the row children in flight, and the batch reaches a terminal status the endpoint can report.

How it is proved

🔬 Verification
1
Negative control — restart it mid-runrequired
Start a batch, restart the backend mid-run, and confirm the batch stalls on main — that is today's behaviour and it should be seen once, by the person doing the work. Then confirm the workflow version resumes and completes.
2
Cost-ceiling interactionrequired
Run a batch whose total would exceed the tenant's budget and confirm S3 stops it at the ceiling, with the partially-completed rows recorded rather than lost.
3
Stop mid-batch, and land on a terminal status
Stop a running batch and confirm the in-flight rows cancel and the status is terminal — not a status that will simply never move again.
4
Row-for-row output comparison
Compare the outputs against a pre-change run of the same CSV, row for row. The CSV format, the input mapping and the output shape are all out of scope, so any difference is a defect and not a design choice.
5
Measure the bookkeeping reduction
Queries per row, before and after. The claim in this task is four to five round trips; prove it or correct it. A number nobody measured is the kind of claim that gets repeated for years.
✓ Done when
A batch survives a restart and resumes; lastProcessedLine and the status columns still tell the truth and reach a terminal state; stop cancels the rows in flight; outputs match a pre-change run row for row; and the bookkeeping reduction is measured, not asserted.

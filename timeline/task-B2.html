Two modules have to be reachable from the worker: flux/scheduler.ts — already the single source of ordering truth — and the node-reference substitution service. Both are pure: no NestJS injection, no database, no I/O.

That purity is what makes sharing cheap and copying tempting. It is also what makes copying dangerous: a second scheduler means the back and the worker can disagree about what runs next, and nothing would say so. The project rule is explicit — import the product's rule; never restate it.

The decisions this task needs

One decision, and it is the reason this task exists as a task rather than as a line inside B3. It is genuinely open: both answers are defensible, and the epic explicitly refuses to let it be decided by whoever writes the consuming code first.
▸Decision B2-aPLAN D1Open — needs a callShared package between back and worker, or copy-port with a drift test?
D1 in DELIVERY-PLAN.md, and the only one of the fifteen recorded as 'genuinely open'. The repos are separate submodules with no shared build graph and no root workspace, and the thirdPartyIntegration migration already chose copy-port once — for adapter code that dragged heavy dependencies. These two modules drag nothing, which is exactly the case where sharing is cheapest. Against that sits a fact worth stating plainly: no workflow runs jest in back (PLAN §3.5), so a drift test is only a guarantee if someone names where it runs.
AA shared npm packagerecommended
One privately published package holding both modules, consumed by back and worker as a normal dependency. Version bumps are explicit; the submodule-bump ordering is unchanged — submodule pushed before the superproject, always.
  • One implementation, so the back and the worker cannot disagree about what runs next
  • Version pinning makes an upgrade a deliberate act, and a regression is bisectable by version
  • The modules are pure, so the package has no runtime dependencies to reconcile between the two repos
  • A release process for two files: publish, bump, install — in two repos, on every change
  • A one-line fix becomes two PRs and a publish before it can ship anywhere
  • Needs a registry and credentials in both deploy paths — infra work that has no other reason to exist yet
Client effort: noneOurs: a release step on every scheduler change
BCopy-port with a drift testprior art
Each module is copied into the worker with a PORTED_FROM.md carrying the source SHA, plus a test that fails when the two copies diverge. This is what the thirdPartyIntegration migration did.
  • No build-graph change, no registry, no release step — it matches how the workspace already ships
  • A fix lands in one PR per repo, on the same branch name, in the same deploy
  • The drift test is genuinely cheap for a pure function: run both, compare the output
  • The drift test is the whole guarantee, and the back has no CI test run — where it runs must be stated, not assumed
  • A copy edited under time pressure drifts first and is discovered last
  • It is the most expensive possible place for that to happen: the two repos would disagree about execution order
Client effort: noneOurs: a drift test that must actually run
CA shared submodule or subtree
A third repository holds both modules and is pulled into back and worker as a git submodule or subtree.
  • One source of truth with no registry and no publish step
  • The workspace already runs on submodules, so the tooling is familiar
  • A third pointer to bump on every change, and a fourth repo in a workspace that just collapsed to one root
  • A stale pointer looks exactly like a fixed bug that never shipped — the workspace's most familiar failure
  • It keeps the sharing benefit but pays it in the currency the team already loses to
Client effort: noneOurs: a third submodule pointer to keep honest
DA monorepo
back, worker (and front) collapse into one repository with one build graph, and the two modules become a workspace package.
  • The question disappears permanently — one build graph, one test run, atomic cross-repo changes
  • Every later shared module is free, and this epic will want more of them
  • It is not this task: it changes CI, deploys, and the branching model of three repos at once
  • Every agent, skill and runbook that assumes the current layout has to be rewritten
  • Nothing in this epic is blocked by the layout, so the cost lands entirely outside the benefit
Client effort: noneOurs: CI, deploys and branching, for three repos
Our recommendation

A, the shared package — and B only if the release step is judged unaffordable. The two modules are pure and dependency-free, which is precisely the case the package tax is smallest for; and the thing being protected is not a helper, it is the answer to what runs next. A disagreement there is not a bug report, it is two systems executing different graphs.

The thirdPartyIntegration precedent does not carry: it chose copy-port for adapter code that dragged heavy dependencies, and the spec says so explicitly. Reusing its conclusion without its reason is exactly the drift this decision is about.

If B wins, it wins on one condition — name where the drift test runs. The back has no CI test run (PLAN §3.5), and a test nobody executes is a comment with extra steps. And if the drift test cannot be made to fail automatically at all, the spec already settles it: copy-port is not viable, and the answer is A.

One answer for both modules is simpler to explain. If they must diverge, the scheduler is the one that may not drift.

What the task does, in three parts

1Extract, without changing behaviourflux/scheduler.ts · node-reference-substitution.service.ts
Extraction is behaviour-neutral. The only thing that changes is where the file lives and who can import it.

Both modules move as they are. Nothing about ordering, edge classification or placeholder resolution changes in this task — if a behaviour needs fixing, it is C3's, and it is fixed before the copy exists, because after duplication each fix costs twice.

The batch sibling of nextReady — allReady — belongs to B4, not here. And nextReady itself stays: mcp-write.service.ts:1327 consumes the scheduler and is not part of this epic.

⚠ How it is today

The scheduler and the substitution service are reachable only from inside the NestJS app. The worker cannot ask what runs next without asking the API.

✓ How it will be

Both modules are consumable from the worker, with identical behaviour and the same consumers on the back side still working.

2The drift test, if copy-port winsPLAN §3.5 — the backend has no CI test run
A comment asking people to be careful is not a mechanism. The test has to fail when the copies diverge.

If copy-port is chosen, two artefacts ship with it: a PORTED_FROM.md per module carrying the source SHA, and a drift test that goes red when the two copies stop agreeing.

The uncomfortable part is where that test runs. No workflow runs jest in back (PLAN §3.5), so 'it is covered by a test' is not, by itself, a guarantee anybody will see. The runner has to be named — a repository, a pipeline, a schedule — not assumed.

⚠ How it is today

One implementation, in the back. Anyone editing it edits the only copy, and the worker cannot use it at all.

✓ How it will be

Either one shared implementation, or two copies with a test that fails when they diverge and a named place where that test actually runs.

The verification can veto the decision

The spec is blunt about this: if copy-port was chosen and the drift test cannot be made to fail automatically, copy-port is not viable — say so and revisit D1. That makes the negative control a gate on the decision itself, not just on the code.

3Equivalence over every stored flowbuildSchedulerState · planOrder
This is a pure function over data that already exists, so full coverage is achievable — take it.

Run both implementations over every stored flow's node and edge set and assert identical SchedulerState and identical planOrder. Not a sample: every flow. There is no cost to running a pure function over data at rest, and this is the last moment where a divergence is cheap to find.

⚠ How it is today

Equivalence between the two implementations would be assumed. Nothing compares them, because until now there is only one.

✓ How it will be

Every stored flow is replayed through both and asserted identical — SchedulerState and planOrder, node for node.

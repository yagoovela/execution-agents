The decisions this task needs

These are the calls that have to be made before the code is written. Each one opens to the options considered, what each costs the customer and costs us, and the option we would pick.
▸Decision C3-aOpen — needs a callDoes the previewResponses fix need a data backfill, or only a forward fix?
Changing === 10 to >= 10 stops new arrays from escaping the cap. It does nothing for arrays that already escaped and are sitting oversized in flows_nodes.data today. Whether any exist is a question about the stored data, not about the code — and the spec is explicit that it must be measured before it is decided.
AMeasure first, then deciderecommended
Ship the >= fix, and separately count how many stored previewResponses arrays are longer than ten. Let that number choose between B and C.
  • The forward fix ships immediately and cannot regress anything
  • If the count is zero, there is no migration to run — and an unnecessary data migration is its own risk
  • The count is a one-line query against a JSONB column
  • Two steps instead of one
Client effort: noneOurs: one query
BForward fix only
Change the comparison and stop there. Oversized arrays stay oversized, but stop growing, because the next append hits >=.
  • No data migration at all — the least risky thing you can do to a JSONB column
  • Growth stops immediately for every affected row
  • The front-end performance problem persists for whoever is already affected
  • Those rows never shrink — the trim only ever removes on append
Client effort: noneOurs: one character
CFix plus a backfill
Change the comparison and run a migration that trims every stored array back to ten.
  • Everyone affected gets the performance back, not just future runs
  • A write migration over a JSONB column on production data — the riskiest option here
  • Deletes stored customer output. If ten was never the right cap, this is irreversible
  • Pointless if the count turns out to be zero
Client effort: noneOurs: a production data migration
Our recommendation

A, and let the number decide. The measurement is cheap, and it is the difference between a justified migration and a gratuitous one.

Note that C also has a product question hiding inside it: trimming stored arrays deletes customer output. If any row is affected, that is worth one sentence of confirmation before the migration runs — not a silent cleanup.

Who decidesEngineering, after the countProduct if any row is affected

What the task does

1The proof burden on the deletionsnode-reference-substitution.service.ts · api-caller-polling.ts
Two of these defects are deletions, and a deletion made on a bad grep is the most expensive mistake on this list.

Items 3 and 5 both claim code is unreachable. That claim needs owner-anchored greps across back, front, worker, mcp-server and origin/production — not just the local checkout.

Dev can lag production. A symbol that has no importer on this branch may still be serving traffic from the deployed one.

⚠ How it is today

Two modules that look dead. One of them is about to be extracted into a second repository by B2, where it would then be maintained twice.

✓ How it will be

Each is either deleted with the proof recorded, or kept with the reason recorded. Either outcome is fine; an unproven deletion is not.

Out of scope

Anything that changes execution semantics. This task is for defects whose fix is behaviour-preserving in the normal case; a fix that changes what a run produces belongs to the task that owns that behaviour.

Owner-anchored greps across back, front, worker, mcp-server and origin/production, not just the local checkout. Record the proof in the PR.

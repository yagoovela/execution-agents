Today the API resolves a node's input and pre-saves it before dispatch: openNodeExecution INSERTs node_executions.input, and the worker only reads it — fetch-node-row.ts:6–10 selects input when execId is present, and never reads the live row.

This is partly built already. The prefetch executor is in production behind FLUX_EXEC_MEMORY_MODE=prefetch (analysis §9.2.1). So this is not a design task. It is: measure what exists, decide whether it is the destination, and move it to the worker side of the boundary.

Our recommendation

C first, then A or B on the number. This is the one decision in Wave 4 whose inputs do not exist yet, and pretending otherwise picks between a production-proven path and a dormant one on vibes.

Two conditions on the measurement itself. Report flows whose eligibility cannot be determined as unverifiable, not ineligible — C2's own verification says so, and a count that rounds unknowns to zero is how 'nobody uses it' becomes a self-fulfilling conclusion. And measure usage, not just eligibility: a flow that could have used prefetch but ran under legacy proves nothing about whether prefetch works.

If the measurement never arrives, choose B. The substitution module exists either way after B2, and one resolver is cheaper to own than two — the whitelist is a fourth list of node types in a codebase A1 exists to reduce to one.

What the task does, in three parts

1node_executions.input changes meaningnode-execution-store.ts · fetch-node-row.ts:6–10
It stops being a precondition for running and becomes a record of what the node ran with.

Today the column is load-bearing in the worst way: a node is not runnable until the API has resolved its input and written it, and the worker reads that write rather than the live row. That single fact is why the worker cannot own the graph — every node needs a round trip through the back to become runnable.

After this task the column is still written, and it must be: run history and debugging depend on it. What changes is that nothing waits for it.

⚠ How it is today

A node becomes runnable only after the API resolves and writes its input. The worker reads that row and never the live one.

✓ How it will be

A node becomes runnable from its references. node_executions.input still records what it ran with, so run history and debugging are unchanged.

The back's copy stays

Removing the back's resolution path is out of scope. It stays until this is proven (PLAN §3.2), and this step must be reversible above all others — it is the one that changes how a node becomes runnable at all.

2The eligibility gate is a refusing rulePLAN §3.3.2 — measure before refusing
Whatever decides 'this flow can resolve worker-side' refuses flows, and a false refusal is worse than the defect it fixes.

The prefetch whitelist is already such a gate, and the same discipline applies to whatever replaces it: classify every refusal against real stored flows as correctly refused or refused although it works, and drive the second count to zero.

Where eligibility cannot be determined, report the flow as unverifiable — not as ineligible. A count that quietly rounds unknowns to zero is how a gate ships looking safe.

⚠ How it is today

The whitelist refuses by node type and nobody has counted what it refuses. Dormant and broken look the same from here.

✓ How it will be

Every refusal is classified against stored flows, refused-although-it-works is zero, and the unknowns are reported as unknown.

3Equivalence, on all three key shapesthe substitution module from B2
Placeholder resolution has three key shapes per node in the schema, and the collision case is the one that decides correctness.

For a corpus of stored runs, resolve each node's input both ways and diff. The three shapes are the nodeId, the normalised ref-key, and the lowercased label alias — and the alias is where two nodes sharing a label collide.

That collision is not an edge case invented for the test: labels are user-typed, and two nodes called 'Prompt' in the same flow is a thing people do. Whichever implementation wins has to resolve it the same way the current one does, or a customer's flow quietly starts reading the wrong upstream.

⚠ How it is today

One implementation resolves placeholders, so nothing compares them. The alias collision resolves however it resolves.

✓ How it will be

Both implementations are run over stored runs and diffed, with the alias collision covered explicitly — the two agree or the task is not done.

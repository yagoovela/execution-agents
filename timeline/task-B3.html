What the task does, in four parts

1Placeholders resolve in the workerflux.service.ts · fetch-node-row.ts · worker/src/ported/back
The back writes the node's data with its placeholders unresolved; the worker fetches what they point at and substitutes.

The worker runs the three fetch operations on B2's ported NodeReferenceSubstitutionService, including on placeholders that arrive inside the *Data arrays. node_executions.input stops being a precondition for running and becomes a record of what the node ran with: the worker writes the resolved input back, because run history and the front read it.

Every placeholder that resolves today must resolve to the same value. If one stops resolving because the worker cannot fetch what it points at, that is a defect of this task, not an accepted loss.

⚠ How it is today

The back substitutes every placeholder and writes the resolved input; the worker reads it.

✓ How it will be

Behind a flag defaulting off, the worker substitutes from references and records what it ran with. The back's path stays selectable.

Fetch, and only fetch

Confirmed with the requester on 2026-09-02 and refined on 2026-10-09: the consumer loads what it needs through a reference — a node_executions row, or a claim-check payload through get-payload (the boundary S5 authorises) — and fetch-then-substitute is fetch. Selecting the field a handle stands for is fetch too, and moves in B3b. Extraction and OCR stay out (A8, D24).

The edge projection moves in B3b

In B3 the back keeps building the *Data entries (getOutputByType) and writes them with their placeholders unresolved. B3b moves that step to the worker on the same flag, so B4 needs no back callback per node.

2A minimal snapshot per rungenerateSchemaFromNodes · the run snapshot (new)
A placeholder can point at a node that does not execute in this run, and today it resolves from that node's content.

The substitution schema is built at run start from every node in the flow. Reading the same values from the live flows_nodes row later would pick up whatever a concurrent run wrote. The back records the run-start base once per run and hands the worker a reference to it.

The snapshot holds only what substitution reads. Chat history and starter files reach the node through the input the back still writes.

⚠ How it is today

The base lives in the back's memory for the life of the run.

✓ How it will be

The base is recorded once per run and read by reference, so two concurrent runs never see each other's values.

3Finding the run's upstreamsthe dispatch arguments
node_executions has no indexed run key, and B1 adds none.

The dispatch carries the run's completed { nodeId: execId } map — ids only. That is the shape B4's workflow will hold in its state, so B4 inherits it instead of replacing it. The worker applies the upstream outputs in completion order, because label aliases are last-write-wins and the order decides which node a shared label names.

⚠ How it is today

Upstream values come from the back's in-memory schema.

✓ How it will be

Upstream values come from their own rows, found by id.

4Equivalence, on every key shapethe substitution module from B2
Both paths are run over stored runs and the full data is diffed — or the task is not done.

Cover the three key shapes (nodeId, normalised ref-key, lowercased label alias), passthrough nodes, a placeholder inside a *Data entry, and two nodes sharing a label. The service and the prefetch alias-index resolve that collision differently; the worker must match the service, because that is what production runs.

⚠ How it is today

One implementation resolves placeholders, so nothing compares them.

✓ How it will be

Both are diffed over stored runs, collision and *Data included.

Negative controlrequired
On the new path, withhold the node_executions row of an upstream that did complete in this run, and confirm the node fails loudly instead of resolving to '' or to the literal placeholder. This is the failure the move can introduce, and it must never look like a prompt bug.

A reference to an upstream that did not run in this run resolves to '' today and must still do so. Measure how many stored flows rely on it before turning anything into an error.

Resolve each node's input both ways and diff the full data — the three key shapes, passthroughs, placeholders inside *Data, and the alias collision.

Concurrency
Two runs of the same flow with different starter inputs: each node resolves its own run's values.

Measure before refusing

The decision this task needs

This task is blocked on one call, and the call is not a preference — it is a fact about history that nobody has looked up. It opens below with both branches costed: what finishing costs, what deleting costs, and the third option that looks free and is not.

PLAN §7, D4 — and the two answers produce opposite work: finish the migration, or delete the modules. The plan proceeds on forgotten, and the evidence for that is the mcpNode release: it shows exactly what a finished migration looks like in this codebase — enum, module, isTemporalNode, allowlist, all moving together (analysis §12.5). These two have the module and nothing else. Against that template, “forgotten” reads better than “paused” — but reading better is not the same as being confirmed.

Add both to the A1 registry behind the flag, prove each against its inline twin field by field, flip the flag in a separate deploy, then delete the twins.
  • Two node types of coverage for the price of routing — the modules exist and were presumably tested when written
  • audioReaderNode has an inline version to diff against, a luxury no other migration in this epic has
  • It clears the A1 invariant, which is Wave 2's stated exit gate
  • If the modules were paused for a reason nobody wrote down, routing them ships that reason into production

BPaused — delete them
Delete both modules from the worker, remove the enum entries, and record why in the module's place.
  • Removes code that ships to every worker replica and can never run
  • It clears the A1 invariant just as exactly as routing does — deletion satisfies it too
  • Honest: an unfinished migration nobody intends to finish is better named than left lying around
  • Both types go back onto the migration backlog, so the work returns later at full price instead of the price of routing
  • Deleting a working module because its routing PR was lost is the most expensive kind of tidy-up
  • The note in its place is mandatory, not a nicety — a deleted module with no explanation invites someone to rewrite it in six months

Our recommendation

A, on the evidence — with the history check as the confirmation, not as a formality. Step 1 is cheap: the git history of the two worker modules and of isTemporalNode shows whether the routing PR was never written, or was written and reverted. A revert is the one finding that flips this to B, and it is the only finding that would.

Note what does not settle it: the modules looking finished. They look finished under either answer — that is exactly why the decision exists. And whichever branch wins, the deliverable has the same shape: nothing is left holding a worker module with inline dispatch, and the reason lives in the registry rather than in someone's memory.

What the task does, in three parts

1Answer D4 from the git history, not from memoryworker/src/modules/nodes/{sql-querier,audio-transcriber}/
The history distinguishes “the routing PR never followed” from “the routing was deliberately taken out”. Nothing else does.

Check the git history of both worker modules and of isTemporalNode. If the module landed and the routing PR never followed, that is the answer, and the task is “finish it”.

The template to compare against already exists. mcpNode moved through every gate at once — enum, module, isTemporalNode, legacy allowlist and the provider list — which is what a completed migration looks like here. These two have the first two and none of the rest.

⚠ How it is today

Nobody can say whether these two are unfinished work or abandoned work, so nobody touches them — and they ship anyway, every deploy.

✓ How it will be

The answer is written into the registry: either a real dispatch entry, or a deletion with the reason left in the module's place.

2Route them behind the flag, and prove them against the twinflux.service.ts — inline audioReaderNode() · sqlQuerierNode()
audioReaderNode has an inline version to diff against — a luxury the other migrations do not have. Use it.

Registry entries go in behind the flag, deployed disabled (PLAN §3.2). Then each type is proved against the real inline behaviour: same input, worker output compared to inline output field by field, on at least three real stored node configurations per type. Only then does the flag flip, in a separate deploy.

Three configurations is not a ritual number. One passing case proves the happy path; three stored ones are the cheapest way to find the field that the module never learned to fill.

⚠ How it is today

audioReaderNode's inline handler runs; the worker module is dead weight that ships anyway. Nothing has ever compared the two outputs.

✓ How it will be

The worker module runs, and it was proved field by field against the handler it replaces before the flag was flipped.

No silent fallback

With the flag on, a broken worker module must fail the run — not fall back to the inline handler. A fallback that masks the worker being broken is worse than the stranding this task fixes, because stranding is at least visible in a registry.

3Delete the twin, and make the flag-off path fail loudly
Deleting the inline twin is what turns two implementations back into one. Until then the node has two behaviours and one name.

This is C1's pattern, applied here as part of the node's own task. PLAN §5 rule 7 is explicit about why: delete the twin while the behaviour is fresh, not in a cleanup sweep months later.

After the twin is gone, one more check that is easy to skip: confirm the flag-off path fails loudly rather than doing nothing. A disabled flag with no handler behind it is a node that silently produces no output, which reads as “the node did not matter”.

⚠ How it is today

Two implementations of the same node type, one of them unreachable, and the registry cannot describe that state without an exception.

✓ How it will be

One implementation, in the worker. The A1 invariant passes with no strandedReason entries left, which is Wave 2's exit gate.

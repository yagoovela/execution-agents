S8wave 1Shipped

One fire per schedule, one run per cron

Running a second backend replica stops multiplying scheduled work — crons, user schedules and the email poll alike.
PR #1984 · Merged to `production` 2026-09-22 (`42306c06`). Part 1: every framework cron now runs inside `CronLockService.runExclusively`, a `pg_try_advisory_xact_lock` held for the life of the job, so N replicas do the work once instead of N times — `DISABLE_CRONS` was absorbed into the same guard. Part 2 took D26 (Bull repeatable jobs over the queue already in production) rather than a Temporal bridge workflow that B4 would delete; user schedules register one repeatable per schedule, the consumer re-reads the schedule, unregisters itself when the schedule or its flow is gone, and enqueues the run without waiting for it. Behind `repeatable_schedules`, seeded disabled. Part 4: inbound email is claimed in Redis with `SET <key> '1' EX 86400 NX` keyed on `Message-ID` (sha256 of the raw message when absent), and the same key rides along as the `api-v2` `jobId`. Part 3 went to E5 and the durable half of Part 2 to E4. Measured on two real replicas sharing one Postgres and one Redis, each control run a second time against a deliberately broken copy so the failure was observed: cron lock 1 executed / 1 skipped (broken: 2 interleaved); schedules 1 repeatable entry and 11 fires in 21s alternating replicas (broken: 2 entries, 20 fires); trigger completes in 14–68ms with one run per tick (broken: 3023ms); two identical `Message-ID`s produce one run. Recorded in `S8-REPLICA-HARNESS.md` with the probes in `scripts/s8-controls/`. One honest exception: `listPop3Emails` registers POP3 event handlers and returns, so its transaction commits while the conversation is still in flight and 4 of 22 ticks ran on both replicas at once. The lock is not at fault — it is exclusive whenever the job awaits its own work — and what protects inbound email is the Redis claim, not the lock; covering the poll would mean holding a Postgres transaction open across the whole conversation every tick. Control 5 also demonstrated the E5 risk concretely: under `volatile-lru` 0 of 100 dedup keys survived a fill; under `noeviction` all survived and the filling write took the OOM instead. Validated in dev on 2026-09-21 with the flag on: five consecutive two-minute ticks produced exactly one run each, and soft-deleting the schedule stopped the runs at the next fire with no restart, the consumer removing its own repeatable. Two things changed how the flag rolls out: the reconcile lives in `onModuleInit`, so turning it on in a running process registers nothing until the next boot; and it used to leave `delete()` on the new path while the in-process `CronJob` from boot kept running and charging, so teardown no longer sits behind the flag.

The decisions this task needs

Only one call is open here — the Redis question that used to sit beside it is now its own task, E5. It opens to the options considered, what each costs the customer and costs us, and the option we would pick.
▸Decision S8-aPLAN D12Recommended — confirmWhat makes a cron fire once, when fourteen of them fire on every replica?
Greps for leader, isLeader, CRON_ENABLED and an advisory-lock guard return nothing, so today the answer is “nothing”. The requirement is one mechanism for all fourteen, not fourteen guards — and the property worth optimising for is that nothing has to know how many replicas exist, because that is the number a deploy is allowed to change without telling anyone.
AAn advisory lock per job namerecommended
Each job takes a non-blocking advisory lock — pg_try_advisory_xact_lock, named after itself — at the top of its run, and it releases automatically when the transaction ends. A replica that cannot take the lock returns immediately and skips.
  • Nothing has to know the replica count — the mechanism is correct at one replica and at ten
  • It is the non-blocking sibling of a lock already used at three sites — flow-node.service.ts (×2) and session-state.service.ts — so there is no new dependency, only the right variant: those three call pg_advisory_xact_lock, which blocks and would make a losing replica wait for the winner and run the job anyway. pg_try_advisory_xact_lock is used nowhere yet, so this choice has to be made deliberately, not copied
  • It degrades correctly: the loser skips, and can say in a log line that it skipped
  • One mechanism covers all fourteen, including the POP3 poll in Part 4, and it absorbs DISABLE_CRONS — today an all-or-nothing flag checked at the top of six of the fourteen — instead of sitting beside it as a second guard
  • It puts a lock acquisition on the database this epic is already worried about — fourteen jobs, one of them every ten seconds
  • A transaction-scoped lock means the job runs inside the transaction that holds it, which is a real constraint for a long purge
Client effort: noneOurs: one guard, no new dependency
BA dedicated scheduler replica
One replica has cron enabled by environment; the others do not run crons at all.
  • The simplest thing that works, and trivially explainable
  • No per-tick database work at all
  • It makes that replica special, and a deploy that loses it loses every cron silently
  • Scaling and rescheduling now have to preserve an invariant the platform does not know about
  • Nothing detects the failure — the symptom is maintenance work that quietly stops happening
Client effort: noneOurs: a silent single point of failure
CLeader election
The replicas elect a leader and the leader runs the crons — the shape the review named first.
  • It survives losing the leader, unlike a designated replica
  • A standard, well-understood pattern
  • It is a distributed-systems component to run and reason about, for fourteen maintenance jobs
  • An advisory lock is leader election, scoped to one job and expiring by itself — with none of the machinery
Client effort: noneOurs: machinery out of proportion to the problem
DTemporal Schedules for all fourteenthe eventual answer for Part 2 — see E4
Move every cron onto the platform's native scheduling instead of an advisory lock.
  • One fire per schedule by construction, with pause, backfill and last-run visibility
  • It is the right destination for the user-facing schedules too — just not yet: E4 takes it once B4 gives the worker a whole-flow workflow to trigger. Part 2 ships D26's Bull repeatable jobs first, because today there is nothing for a Temporal Schedule to call
  • These fourteen are internal maintenance and have no reason to become workflows
  • Each cron would have to be reachable as a workflow or an activity — a large restructuring for a set of purges
Client effort: noneOurs: fourteen jobs restructured for no user-facing gain
Our recommendation

A for the fourteen framework crons — recorded as D12. The crons are internal maintenance and Temporal Schedules buy them nothing they need (review §11.3). Part 2 does not take Option D either, despite the first draft recommending Temporal Schedules there: D26 settled Bull repeatable jobs instead, because a Temporal Schedule can only trigger a workflow and the worker has none that runs a whole flow yet — that is B4. Option D is the right answer for the user-facing schedules, it is just E4's answer, not today's.

Whichever wins, the replica that skips must log that it skipped. A guard that silently does nothing is indistinguishable from a cron that stopped working, and the second one is discovered months later.

And stagger the 3AM cluster while you are there — six purges starting in the same minute is a self-inflicted load spike on the database S2 is already sizing.

What the task does, in four parts

1The fourteen cronsback/src/cronJobs/** · flow-node.service.ts · session-state.service.ts
One mechanism for all fourteen, so a second replica stops multiplying maintenance work.

@Cron is registered fourteen times across back/src, and there is no leader election. Every cron fires on every replica.

Some of that is waste: six purges all at EVERY_DAY_AT_3AM — purgeCanceledSubscriptions, purgeMcpIdempotencyKeys, purgeMcpTokens, purgeNodeExecutions, purgeSpaceRunLogs, purgeZapierWebhookPayloads — each running per replica against the same tables in the same minute. Some of it is not waste at all: chargeUsersPerClonedVoice (08:00 daily) debits customers through productService.chargeUserProduct, with no guard whatsoever — duplicated, it is not waste, it is a refund. mail.service.ts polls POP3 EVERY_10_SECONDS per replica, and markStuckSpaceRunLogs runs every ten minutes per replica.

A partial guard already exists. DISABLE_CRONS is checked at the top of six of the fourteen — purgeCanceledSubscriptions, purgeMcpIdempotencyKeys, purgeMcpTokens, purgeNodeExecutions, purgeZapierWebhookPayloads, syncAiModelsFromGateway — and is declared twice in .env.example, which is its own small bug. It is all-or-nothing: it can turn every cron off, never one replica only.

Stagger the 3AM cluster while you are there. Six purges starting in the same minute is a self-inflicted load spike on the database this epic is already worried about.

The lock is pg_try_advisory_xact_lock, not its blocking sibling. The three existing advisory-lock sites in the codebase — flow-node.service.ts (×2) and session-state.service.ts — all use pg_advisory_xact_lock, which blocks: it waits for the holder and then proceeds anyway. Copying that precedent produces a losing replica that waits for the winner's transaction and runs the job regardless — the exact defect this part exists to remove. pg_try_advisory_xact_lock is used nowhere in the codebase today, so there is no precedent to copy and the choice has to be made deliberately. The new lock absorbs DISABLE_CRONS rather than sitting beside it as a second guard.

⚠ How it is today

Every cron fires on every replica, so maintenance work is multiplied by the replica count — and the POP3 poll is multiplied every ten seconds.

✓ How it will be

One non-blocking guard (pg_try_advisory_xact_lock), taken per job name, so each cron runs once per tick regardless of how many replicas exist — and the replica that skipped says it skipped.

2User-scheduled flowsschedule.controller.ts · schedule.consumer.ts
Make a schedule fire once, and make the queue actually own the execution it appears to own.

Scheduled runs do not use a durable scheduler. They are registered in NestJS's in-process registry — schedulerRegistry.addCronJob — at two sites in schedule.controller.ts: create(), and getAllSchedules(), which has exactly one caller — the controller's own constructor, as a fire-and-forget promise at boot. Each replica still ends up with its own copy of every schedule and fires it independently: N replicas means N runs of the same schedule, each charged to the customer.

Four defects live in this code, all in scope:

  • The queue is not doing the work. The callback does await this.scheduleQueue.add('schedule-job', { … job: await this.fluxService.apiV2({ … }) }) — the run is awaited as an argument to the enqueue call, so the flow already executed synchronously inside the callback and only its result reaches the queue. Fixing the duplication without fixing this just duplicates it more efficiently.
  • update() never re-registers the cron. Changing a schedule's interval does nothing until the process restarts.
  • The registry is keyed by schedule.name, which is user-supplied and not unique. Two schedules with the same name collide, and create() throws for a name already registered at boot — the durable id has to be schedule.id.
  • The two registration sites send different payloads. create() sends {...body, spaceId} with a userId; getAllSchedules() sends {...schedule, webhook: true, spaceId} with a socketId. The same schedule behaves one way before the first restart and another way after — the entity shape is the survivor.

And a fifth thing, which is why "the queue owns the execution" needed a decision and not just a fix: ScheduleConsumer only emits a socket event, and only when data.userId is set — which only create() sets. Boot-registered schedules therefore notify nobody. The queue does not execute and does not reliably notify.

Settled 2026-09-18 as D26: Bull repeatable jobs, not Temporal Schedules. Bull 4.16.5 is already a dependency and ApiV2Queue / ApiV2QueueProcessor are already in production (src/jobs/apiV2Job/), with ApiV2QueueModel.params already carrying exactly the fields the callback passes today. The schedule state moves out of the per-replica SchedulerRegistry and into Redis, which Bull already manages and which dedupes a repeatable by its repeat key regardless of how many replicas registered it — keyed by schedule.id, not name.

What that buys, beyond stopping the duplication: the "callback stops awaiting the run" fix becomes structural rather than a discipline, because there is no callback left — the processor is the execution. getAllSchedules() leaves the codebase, taking defects 2, 3 and 4 with it. Corrected 2026-09-19, after implementation: the schedule queue is the mechanism, not a casualty of it — a repeatable job lives in a queue, so it now carries one repeatable per user schedule and ScheduleConsumer processes them; what is retired is the old shape, the callback that awaited a run and the boot-time socket emit. SchedulerRegistry survives in legacy-schedule-registrar.service.ts because §3.2 ships this behind a flag seeded disabled, so the old path is the one that runs while repeatable_schedules is off; it leaves when the flag is on everywhere. update() and delete() become removeRepeatable + add. Boot notification is deliberately dropped: the socket emit was already dead for every boot-registered schedule, so preserving it would mean building behaviour that never worked rather than keeping behaviour that did.

Keep the zombie-cron check — stop, delete, soft-delete when the flow is gone. It is the one part of this code already doing the right thing. It becomes a reconciliation over the schedule table at boot, which is also what recovers the repeatables if Redis is ever lost: the table stays the source of truth, Redis only holds the timer.

⚠ How it is today

Each replica holds its own copy of every active schedule and fires it independently — and the run happens inside the cron callback rather than in the queue.

✓ How it will be

One fire per schedule regardless of replica count, on Bull repeatable jobs keyed by schedule.id — with the queue structurally owning the execution — and the zombie check surviving as a boot reconciliation over the schedule table.

Why Bull now and Temporal later

A Temporal Schedule can only trigger a workflow, and the worker exposes three today — processSingleNode, processAgent, completionWorkflow — none of which executes a whole flow; that workflow is what B4 builds. Shipping Temporal here would have meant a bridge workflow plus an internal HTTP endpoint invented purely to give the schedule something to call, both thrown away the moment B4 lands. Building a bridge in order to demolish it is not a reason to delay this replica-safety fix, so S8 ships the mechanism that needs no bridge, and the durable scheduler becomes E4, blocked on B4.

The advisory lock stays the right answer for the fourteen framework crons — internal maintenance with no reason to become workflows, settled in D12 and not reopened.

3Redis — split into its own tasksplit out 2026-09-18 — see E5
Record why this half of the original scope now ships on its own, instead of blocking the replica-safety fix.

Split out on 2026-09-18 into E5. It is an infrastructure change with no application code in it, and the measurement says it is debt rather than an incident: production runs volatile-lru, which can evict the TTL-bearing dedup keys (flux.service.ts), but there have been zero evictions in fourteen days at 1.9% memory and 1.8% engine CPU. Holding this replica-safety fix for a defect that has never fired would have been the wrong trade.

4The POP3 pollmail.service.ts · deleteEmailsSequentially()
Make one delivered message produce exactly one run, without depending on a lock this code cannot see.

The email poll is one of the fourteen crons, so it fires every ten seconds per replica. There is no message-id dedup and no lock — greps for messageId, dedup, lock and NX return nothing. Messages are fetched, processed and only then deleted (deleteEmailsSequentially), so the window between fetch and delete spans the whole batch, including enqueueing the runs.

Be fair about today's risk. POP3 requires the server to lock the maildrop exclusively for the session, so a well-behaved provider refuses the second replica and duplicates may not occur now. That is exactly the problem: correctness depends on a lock this code does not take and cannot observe. Move the mailbox to IMAP or an API, or use a provider that permits concurrent sessions, and the failure becomes duplicate runs charged to the customer, with nothing to catch it.

Two independent guards, because the failure they prevent is a charge to a customer: Part 1's advisory lock covers the polling, and — independently of it — a claim on the message id. Corrected 2026-09-19, after implementation: the deterministic Bull jobId alone does not hold, because the enqueue sets removeOnComplete and Bull frees the id once the job is cleaned up, so a later redelivery enqueues a second run. The claim is a Redis SET <key> '1' EX 86400 NX keyed on Message-ID (sha256 of the raw message when the header is absent), and the same key rides along as the api-v2 jobId — one guard durable for 24 hours, one for as long as the job exists.

Reconsider the ten-second interval while you are there. It is a poll against a mailbox, and at one replica it is 8,640 connections a day.

⚠ How it is today

Every replica past the first fails to acquire the maildrop lock every ten seconds — and nothing in the code would notice if one of them succeeded.

✓ How it will be

The poll runs on one replica per tick, and a message that is somehow fetched twice still produces one run, because its claim key was already taken.

Confirm the schedule callback returns without waiting for the run — and that the run still happens. The failure mode of fixing this carelessly is a schedule that enqueues nothing.

The decisions this task needs

Two calls have to be made, and neither is decidable from this repository alone — one needs the database's opinion, the other needs infrastructure's. Each one below opens to the options considered, what each costs the customer and costs us, and the option we would pick.
▸Decision S8-aPLAN D12Recommended — confirmWhat makes a cron fire once, when thirteen of them fire on every replica?
Greps for leader, isLeader, CRON_ENABLED and an advisory-lock guard return nothing, so today the answer is “nothing”. The requirement is one mechanism for all thirteen, not thirteen guards — and the property worth optimising for is that nothing has to know how many replicas exist, because that is the number a deploy is allowed to change without telling anyone.
AAn advisory lock per job namerecommended
Each job takes a lock named after itself at the top of its run and releases it at the end. A replica that cannot take the lock simply skips.
  • Nothing has to know the replica count — the mechanism is correct at one replica and at ten
  • pg_advisory_xact_lock is already used in the codebase (oauth-token.repo.ts), so there is no new dependency
  • It degrades correctly: the loser skips, and can say in a log line that it skipped
  • One mechanism covers all thirteen, including the POP3 poll in Part 4
  • It puts a lock acquisition on the database this epic is already worried about — thirteen jobs, one of them every ten seconds
  • A transaction-scoped lock means the job runs inside the transaction that holds it, which is a real constraint for a long purge
Client effort: noneOurs: one guard, no new dependency
BA dedicated scheduler replica
One replica has cron enabled by environment; the others do not run crons at all.
  • The simplest thing that works, and trivially explainable
  • No per-tick database work at all
  • It makes that replica special, and a deploy that loses it loses every cron silently
  • Scaling and rescheduling now have to preserve an invariant the platform does not know about
  • Nothing detects the failure — the symptom is maintenance work that quietly stops happening
Client effort: noneOurs: a silent single point of failure
CLeader election
The replicas elect a leader and the leader runs the crons — the shape the review named first.
  • It survives losing the leader, unlike a designated replica
  • A standard, well-understood pattern
  • It is a distributed-systems component to run and reason about, for thirteen maintenance jobs
  • An advisory lock is leader election, scoped to one job and expiring by itself — with none of the machinery
Client effort: noneOurs: machinery out of proportion to the problem
DTemporal Schedules for all thirteenright for Part 2
Move every cron onto the platform's native scheduling — the same mechanism Part 2 adopts for user schedules.
  • One fire per schedule by construction, with pause, backfill and last-run visibility
  • It is the right answer for the user-facing schedules, and Part 2 uses it
  • These thirteen are internal maintenance and have no reason to become workflows
  • Each cron would have to be reachable as a workflow or an activity — a large restructuring for a set of purges
Client effort: noneOurs: thirteen jobs restructured for no user-facing gain
Our recommendation

A for the thirteen framework crons, D for the user-facing schedules in Part 2. That split is the review's amendment (§11.3), and it is deliberate: the crons are internal maintenance and Temporal Schedules buy them nothing they need, while the user schedules are customer-visible, durable, and want pause, backfill and last-run visibility an in-process registry cannot offer.

Whichever wins, the replica that skips must log that it skipped. A guard that silently does nothing is indistinguishable from a cron that stopped working, and the second one is discovered months later.

And stagger the 3AM cluster while you are there — five purges starting in the same minute is a self-inflicted load spike on the database S2 is already sizing.

▸Decision S8-bOpen — needs a callHow are the dedup keys protected from eviction — by a policy, or by a separate instance?
Redis backs three unrelated things: the Bull queues, the worker→backend pub/sub, and the delivery dedup keys. The dedup pattern itself is correct — SET key '1' EX 86400 NX, run-scoped (flux.service.ts) — and it is what stops a retried run from emailing a customer twice. Dedup keys are correctness state, not cache, and under allkeys-lru or allkeys-random they are evictable. This cannot be read from the repository; it has to be confirmed from infrastructure.
ASeparate the correctness state from the cacherecommended
Dedup keys move to their own instance, with a policy that cannot evict them. The queues and the bus keep theirs.
  • The only shape in which a cache filling up cannot cause a duplicate customer email
  • It also splits the availability story the review flags — losing one instance stops costing admission, visibility and duplicate suppression at once
  • Sizing for post-B5 pub/sub becomes a separate number from sizing for dedup
  • Another instance to run, connect to and monitor
  • A second connection string in every service that dedups
Client effort: noneOurs: one more instance to run
BOne instance, with a policy that cannot evict them
Keep everything on one instance and set an eviction policy that refuses to discard the dedup keys.
  • No new infrastructure, and one thing to monitor
  • The fastest to apply — it is a configuration change
  • The dedup keys carry a TTL (EX 86400), so every volatile-* policy can evict them too — the only single-instance policy that protects them is noeviction
  • Under noeviction a full instance starts refusing writes, which takes the queues and the bus down with it — the failure moves rather than disappearing
Client effort: noneOurs: one full instance stops everything
CMove the dedup into Postgres
Keep the dedup key as a uniquely-constrained row instead of a Redis key, so it cannot be evicted at all.
  • Eviction stops being a question — the guarantee comes from a constraint
  • It is durable across a Redis restart, which a key with a 24-hour TTL is not
  • It adds a write and a lookup per delivery to the database S2 is sizing, in the path B5 is about to multiply
  • The existing pattern is correct and already in production — replacing a working guard is a larger change than protecting it
Client effort: noneOurs: more load on the wall S2 is measuring
Our recommendation

A, and the sizing question travels with it. Parallel dispatch raises the pub/sub rate substantially, so today's headroom is not evidence for post-B5. Splitting the instances is what lets those two numbers be set independently instead of as one compromise.

E3 lands in the same wave and adds socket fan-out to the same bus — the two tasks have to produce one Redis sizing number together, not two.

Whichever is chosen, prove it: fill the instance past maxmemory and confirm a dedup key survives. An assumption about eviction is worth exactly as much as the test that proves it.

What the task does, in four parts

1The thirteen cronsback/src/cronJobs/** · oauth-token.repo.ts
One mechanism for all thirteen, so a second replica stops multiplying maintenance work.

@Cron is registered thirteen times across back/src, and there is no leader election. Every cron fires on every replica.

Some of that is waste: five separate purges all at EVERY_DAY_AT_3AM, each running per replica, against the same tables in the same minute. Some of it is not: mail.service.ts polls POP3 EVERY_10_SECONDS per replica, and markStuckSpaceRunLogs runs every ten minutes per replica.

Stagger the 3AM cluster while you are there. Five purges starting in the same minute is a self-inflicted load spike on the database this epic is already worried about.

⚠ How it is today

Every cron fires on every replica, so maintenance work is multiplied by the replica count — and the POP3 poll is multiplied every ten seconds.

✓ How it will be

One guard, taken per job name, so each cron runs once per tick regardless of how many replicas exist — and the replica that skipped says it skipped.

2User-scheduled flowsschedule.controller.ts
Make a schedule fire once, and make the queue actually own the execution it appears to own.

Scheduled runs do not use a durable scheduler. They are registered in NestJS's in-process registry — schedulerRegistry.addCronJob in create() and getAllSchedules() — so each replica holds its own copy and fires it independently. N replicas means N runs of the same schedule, each charged to the customer.

Two defects live in the same code, and both are fixed here:

  • The re-registration hides in a getter. getAllSchedules() is a plain method with no route decorator that walks every active schedule and registers crons as a side effect. Whatever calls it registers crons on that replica.
  • The queue is not doing the work. The callback does await this.scheduleQueue.add('schedule-job', { … job: await this.fluxService.apiV2({ … }) }) — the run is awaited as an argument to the enqueue call, so the flow already executed synchronously inside the cron callback and only its result reaches the queue.

Fixing the duplication without fixing the second one just duplicates it more efficiently. Either way, the callback stops awaiting the run — the scheduler owns the trigger and the workflow owns the execution.

Keep the zombie-cron check inside getAllSchedules() — stop, delete, soft-delete when the flow is gone. It is the one part of this code already doing the right thing.

⚠ How it is today

Each replica holds its own copy of every active schedule and fires it independently — and the run happens inside the cron callback rather than in the queue.

✓ How it will be

One fire per schedule regardless of replica count, on Temporal Schedules — with pause, backfill and last-run visibility the in-process registry cannot offer — and a callback that returns without waiting for the run.

Why Temporal Schedules here and a lock there

Greps for ScheduleClient, scheduleClient and createSchedule across the worker and back/src/temporal return nothing, so the platform's native scheduling is entirely unused. It gives by construction exactly what this part would otherwise build by hand.

The advisory lock stays the right answer for the thirteen framework crons, which are internal maintenance and have no reason to become workflows (review §11.3).

3Redis carries three unrelated responsibilitiesflux.service.ts · Redis/infra
Confirm from infrastructure what cannot be read from this repository, before parallelism raises the rate.

Redis backs the Bull queues, the worker→backend pub/sub, and the delivery dedup keys. The dedup is already a correct pattern — SET key '1' EX 86400 NX, run-scoped.

Two things to confirm, and neither of them can be read from this repository:

  • Eviction policy. Under allkeys-lru or allkeys-random, dedup keys are evictable, and the failure mode is duplicate customer emails and duplicate outbound webhooks.
  • Sizing for after B5. Parallel dispatch raises the pub/sub rate substantially. Today's headroom is not evidence for post-parallelism — and losing Redis loses admission, visibility and duplicate suppression at once.
⚠ How it is today

Three responsibilities with different correctness requirements share one instance and one eviction policy — and nobody working in this repository can say which policy it is.

✓ How it will be

The dedup keys are proven to survive memory pressure, and the bus is sized for the event rate parallel dispatch will produce.

4The POP3 pollmail.service.ts · deleteEmailsSequentially()
Make one delivered message produce exactly one run, without depending on a lock this code cannot see.

The email poll is one of the thirteen crons, so it fires every ten seconds per replica. There is no message-id dedup and no lock — greps for messageId, dedup, lock and NX return nothing. Messages are fetched, processed and only then deleted (deleteEmailsSequentially), so the window between fetch and delete spans the whole batch, including enqueueing the runs.

Be fair about today's risk. POP3 requires the server to lock the maildrop exclusively for the session, so a well-behaved provider refuses the second replica and duplicates may not occur now. That is exactly the problem: correctness depends on a lock this code does not take and cannot observe. Move the mailbox to IMAP or an API, or use a provider that permits concurrent sessions, and the failure becomes duplicate runs charged to the customer, with nothing to catch it.

Two independent guards, because the failure they prevent is a charge to a customer: Part 1's advisory lock covers the polling, and — independently of it — dedup by message id before enqueueing, using the same SET … NX pattern already used for delivery (flux.service.ts).

Reconsider the ten-second interval while you are there. It is a poll against a mailbox, and at one replica it is 8,640 connections a day.

⚠ How it is today

Every replica past the first fails to acquire the maildrop lock every ten seconds — and nothing in the code would notice if one of them succeeded.

✓ How it will be

The poll runs on one replica per tick, and a message that is somehow fetched twice still produces one run, because its message id was seen before.

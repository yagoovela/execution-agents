Shape
Three limits
X per node, Y per run, and a chain total. None of them subsumes the others.

evaluateLoopCondition (folw/helpers/helpers.ts) applies the limit on one branch only. On the other branch the limit is computed, reported to the UI through loopStatus and the condition-loop-status socket event — and then not applied.

Worse, on the capped branch the limit itself is node.data.loopCount — user data. A system-level maximum should not be reachable from node configuration.

The decisions this task needs

These are the calls that have to be made before the code is written. Each one opens to the options considered, what each costs the customer and costs us, and the option we would pick.
▸Decision S4-aPLAN D15Open — needs a callWhat are X, Y and the chain total?
The one genuinely open number in this epic. The spec is deliberate about this: the three ceilings must come from measurement against stored runs, not from taste. The options below are about how to choose them, not about which numbers to type.
AMeasure, then set above the observed maximumrecommended
Query the stored flows and runs for the largest loopCount, the largest processorArray, and the largest node-execution count any real run produced. Set each ceiling above that, with margin, and report the distribution.
  • Zero false refusals by construction — the ceiling is above everything that ever really ran
  • The distribution shows whether the maximum is a real workload or one outlier
  • Defensible in a review: the number has a provenance
  • Needs the query to run against real stored data before the code can ship
  • A future workload larger than anything seen so far will be refused — env vars mitigate
Client effort: noneOurs: one measurement pass
BPick round numbers now, tune later
Ship generous defaults — say 1000 iterations per node, 10000 executions per run — and adjust when something is refused.
  • Ships immediately, no measurement gate
  • Generous enough that most workloads never notice
  • Violates PLAN §3.3.2 — a rule that refuses must be checked against real data first
  • “Adjust when something is refused” means the first signal is a customer incident
  • A number with no provenance gets raised by whoever is on call, and never lowered
Client effort: noneOurs: incident-driven tuning
CReport-only first, enforce after a cyclepairs with A
Ship the counters recording what would have been refused, without refusing. Read the report after a full cycle, then turn enforcement on.
  • Catches workloads the historical query cannot see — anything that failed, retried or was never stored
  • The team sees the real distribution in production, not in a query result
  • Delays the guard by a full cycle, while the unbounded case stays live
  • Requires the counters to be built before they are useful
Client effort: noneOurs: a reporting mode
Our recommendation

A to pick the numbers, C to confirm them. The historical query gives a defensible starting value; report-only mode catches the workloads that query cannot see. Then enforce.

Whichever numbers come out, make all three env vars. A ceiling that needs a deploy to raise will be raised by disabling the check.

What the task does

1Why the static check is not enoughflux.service.ts · inline arrayNode branch
Three defences, in this order — and the third is the only one that answers the question that matters at 3 a.m.

1. Before the run — graph validation. Refuse what can be proven wrong without spending anything: cycles inside the graph, and a flow already on the call chain (S1).

2. During the run — X, per node. Stops the common case: one node looping on a condition that never turns false.

3. During the run — Y, per run, and the chain total. The backstop.

The third is not redundant, it is the only guarantee. Whether a flow terminates is not decidable by looking at it — the loop condition reads data that does not exist until the run happens. A static check can prove some flows wrong; it can never prove the rest right.

⚠ How it is today

A node whose loopBehavior is not continue loops forever with an always-true condition, and the limit that was computed is discarded.

✓ How it will be

X applies on both branches, independent of loopBehavior and of loopCount. The node's own limit still applies where it is lower — this is a ceiling, not a replacement.

Say which ceiling stopped it

loopStatus.reason already carries a human-readable reason — Loop limit exceeded (n/m). The new case needs its own wording, or a user will read “limit exceeded” and go looking for a limit they never set.

X also applies to arrayNode, which iterates a list rather than a condition. A processorArray of a hundred thousand items is the same runaway with a different shape.

2Y terminates the run, it does not merely stop schedulingflux/scheduler.ts
A run that ends ambiguously is worse than one that ends refused, because nobody can tell it from a hang.

Y counts executions, not distinct nodes: a node that runs forty times spends forty. When the budget is exhausted the run terminates deterministically, with a terminal state naming the budget.

The chain total resolves the chain root and accounts against it — the same mechanism S3 needs for cost. One counter carrying two limits, resolved at the same place, rather than two independent accountants that can disagree.

⚠ How it is today

Nothing counts how much a run has executed. A loop across several nodes is invisible to any per-node limit.

✓ How it will be

One counter bounds the run and the chain. As a side effect it bounds Temporal history growth, which is the other half of what B4's continueAsNew is for.

How it is proved

🔬 Verification
1
Negative control — Xrequired
A condition node with an always-true condition and loopBehavior set to anything but 'continue': watch it loop without bound on main, then confirm the ceiling stops it and the reason names the system limit rather than the node's.
2
Negative control — Y and the chainrequired
Build a flow that loops across several nodes rather than on one — the shape X cannot see — and confirm it runs unbounded on main, then confirm Y stops it with a terminal state naming the budget. Then nest that flow two levels deep and confirm the chain total stops it, rather than each level getting a fresh Y.
3
Measure before refusingrequired
PLAN §3.3.2. Find the largest loopCount and the largest processorArray in the stored flows, and the largest number of node executions any real run has produced. Set X and Y above all of them with margin — and report the distribution, not just the maximum. A ceiling chosen from one outlier is a ceiling nobody trusts.
4
The two reasons stay distinguishable
Confirm the UI still shows the node's own limit when that is what stopped the loop. The two reasons must not be confused, or the author debugs the wrong number.
✓ Done when
No node configuration and no graph shape can produce an unbounded run: X bounds one node, Y bounds the run, and the chain total bounds nesting. Every ceiling sits above the largest real value in the stored data. A run that hits any of them ends in a terminal state that names which one, and the three reasons are distinguishable from each other and from the node's own limit.

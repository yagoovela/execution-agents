Per-schedule cutover, reversible
Behind the same feature flag S8 introduced, defaulting to the Bull path. Every schedule is either a Bull repeatable or a Temporal Schedule, never both.

S8 Part 2 recommended Temporal Schedules for user-scheduled flows, and the recommendation was right about the destination and wrong about the timing. Shipping it during S8 would have needed two pieces of scaffolding invented purely to give a Temporal Schedule something to call: a runScheduledFlow workflow whose only job is to call back into the backend, and an internal HTTP endpoint for that activity to hit — one that, after S7 Part 2, also has to be reasoned about against the rate-limit guards. Both are thrown away the moment B4 lands a real flow workflow, so S8 shipped the duplication fix on a mechanism that needs no bridge, and the durable scheduler became this task.

S8 moved user schedules onto Bull repeatable jobs (D26): schedule state left the per-replica in-process SchedulerRegistry and moved into Redis, which Bull already manages, and ApiV2Queue — already in production — became the execution owner. Measured, not read from documentation: three simulated replicas registering the same schedule produced one repeatable and one execution per tick, against three per tick for the shape it replaced. That closes duplication and durability across restarts and deploys. It does not give pause/resume as a first-class operation, backfill, last-run visibility as scheduler state, or durability independent of Redis — Bull's repeatables live in Redis, and while the schedule table stays the source of truth S8 reconciles from on boot, that recovery is code this repo owns rather than a platform guarantee. Those four are what this task buys.

2

The decisions this task needs

One decision this task has to make and cannot inherit from S8: what a paused or down schedule does when it resumes. Temporal supports backfill natively, which only raises the question the spec states directly — the default is not obviously the one a customer wants, so it has to be asserted, not assumed.
▸Decision E4-aOpen — needs a callWhen a paused or down schedule resumes, does it replay the fires it missed, or skip to now?
Temporal Schedules support backfill as a native action, so the mechanism is not the open question — the product behaviour is. A daily report schedule and a five-minute polling schedule want opposite answers, and a default picked silently by whichever behaviour Temporal happens to ship is a default nobody chose on purpose.
ASkip to now, log what was missedrecommended
Resume runs the next scheduled fire normally; every missed occurrence is written to the schedule's history as missed, visible to the user, and never executed.
  • No surprise burst of spend or side effects the moment a paused or crashed schedule comes back
  • Consistent with this epic's posture elsewhere — never record a silent zero, never fire a silent surprise (E2's ledger rule, S3's spend ceiling)
  • Simple to reason about: at most one run per resume, regardless of how long the schedule was down
  • A customer whose schedule genuinely needed every occurrence (e.g. one report per missed day) loses data unless C is also offered
Client effort: none — the missed-run log is passiveOurs: the simplest Temporal Schedule policy to configure
BBackfill every missed fire
Resume replays each missed occurrence in order before returning to the normal cadence.
  • No data is silently skipped — every scheduled occurrence eventually runs
  • A schedule down for days replays days of runs the instant it comes back — the exact spend/side-effect burst A avoids
  • Unbounded by construction: the replay size is however long the outage was, which is not a number anyone chose
Client effort: noneOurs: an unbounded replay burst to reason about and rate-limit
CConfigurable per schedule
Expose the choice between A and a bounded backfill (capped at N missed fires) as a per-schedule setting.
  • Covers the daily-report case that A alone loses, without B's unbounded replay
  • A second surface to build, document and keep honest, for a need not yet demonstrated by a real customer ask
Client effort: a setting to understandOurs: the largest surface of the three
Our recommendation

A, as the default. A paused or down schedule is either deliberately paused or down because of a deploy or incident — replaying an unbounded backlog of missed fires the instant it resumes is a spend and side-effect surprise, not a service improvement, and it is exactly the shape of silent surprise this epic refuses elsewhere. Log what was missed so the gap is visible rather than swallowed.

C is not rejected, only deferred: if a real schedule genuinely needs every missed occurrence, a bounded per-schedule override is a smaller, later addition on top of A than B would be to retrofit safety onto. Whichever is chosen, write a test that asserts it — the spec is explicit that the default is not self-evidently correct, so it must not ship unassessed.

Who decidesEngineering, with product sign-off on the default

What the task does, in four parts

1The schedule's id becomes the Temporal schedule idback/src/app-api/schedule/schedule.controller.ts · schedule.service.ts
ScheduleController's create / update / delete drive ScheduleClient instead of ApiV2Queue's repeatable — keyed by the schedule's id, not its name.

The id-not-name rule is not new here — S8 already made this change, because a schedule's name is user-supplied and not unique. This task inherits it rather than re-deciding it: do not regress it while swapping the mechanism underneath.

⚠ How it is today

A schedule maps to a Bull repeatable keyed by the schedule's id, registered per replica and reconciled from the schedule table on boot.

✓ How it will be

A schedule maps to a Temporal Schedule with the same id — durable in Temporal, not reconstructed from a table on every boot.

2The schedule action targets B4's flow workflow directlythe flow workflow B4 introduces
No bridge workflow. If a Temporal Schedule here still needs an intermediate to call, B4 is not done and this task is not ready.

This is the fact that made the task wait for B4 in the first place, restated as the acceptance bar for this part: a Temporal Schedule can only trigger a workflow, and the only workflow worth triggering is the one that runs a whole flow. Anything short of that is the throwaway bridge S8 deliberately declined to build.

The fourteen framework crons are out

They stay on S8's advisory lock — internal maintenance with no reason to become workflows. Settled in D12 and not reopened here.

3The cutover is per-schedule, reversible, and cannot double-firethe feature flag S8 introduced
Behind the same flag, defaulting to Bull. Every schedule is a Bull repeatable or a Temporal Schedule, never both at once.

The risky moment is the transition, not the steady state on either side of it — which is why the negative control below flips the flag with two replicas running and counts fires, rather than trusting that one mechanism is off because the other is on.

4The zombie check becomes a schedule policyschedule.service.ts
Stop, delete, soft-delete when the flow behind a schedule is gone — the check S8 preserved has to survive the move as a schedule policy, not a callback body.

On Bull, this check runs inside the job's callback body. On a Temporal Schedule it has nowhere equivalent to live unless it is written as an explicit policy the schedule action consults — the difference is structural, not cosmetic, and it is why this gets its own part rather than a line inside Part 1.

How it is proved

🔬 Verification
1
Negative controlrequired
With the flag on for one schedule and two backend replicas, confirm exactly one run per fire — and confirm it was Temporal that fired it, not a surviving Bull repeatable. A green count proves nothing if both mechanisms are live and one of them is idle.
2
The rollback is clean
Flip the flag back and confirm the Bull repeatable resumes, with no fire lost and none doubled across the transition. The cutover is the risky part, not the steady state.
3
Pause, wait, resume
Pause a schedule, wait past a fire, resume, and confirm the chosen backfill behaviour — whichever option was picked in the decision above, assert it, because the default is not obviously the one a customer wants.
4
Kill Redis, confirm schedules still fire
That is the property this task adds over S8, so it is the one that has to be demonstrated rather than assumed.
✓ Done when
User schedules are Temporal Schedules, fire exactly once regardless of replica count, survive the loss of Redis, and expose pause, resume and last-run state. The Bull repeatable path is deleted, not merely disabled.

An architecture change
Back, front, worker and MCP. Estimate 70 to 110 h.

A non-chat Small Memory (fluxObject) keeps all its entries in its node's data jsonb, and stores each entry twice (entries and userSessionsChat.default). Every producer write reads, merges, sanitizes and saves the whole blob, the editor re-uploads both copies on every open, and every reader loads the whole blob to pick the last few entries.

The memory is therefore bounded by jsonb (about 255 MB per value), by a V8 string (about 512 MB) and by one process's RAM at several steps, and its write cost grows with its size. Chat memory already stores rows in session_state_entries (scope flowId:nodeId, ordered by seq) with a blob fallback; non-chat memory never does.

What the task does, in four parts

1Rows for non-chat memoryback session-state service · entity and migration
A14b-D1, recommended: session_state_entries with a new scope type smallMemory, plus flowVersionHistoryId, a unique contentHash for dedup and entryAt.

A write inserts one row per new entry, deduplicated by content (per session when sessions are on) and keyed by execId, so a redelivered run event adds nothing. Non-chat rows have no owner and stay shared by every user, as the blob is today (A14b-D3, recommended). Empty entries are skipped, and clearOnExecution deletes the rows at run start before the first append.

⚠ How it is today

Each write rewrites the whole memory.

✓ How it will be

Each write appends only its new entries.

2Readers read only what they needback edge-projection reader · worker
"Load Last X" and "Load First X" read at most X rows.

A14b-D2 is open: for "Load All Entries" on a huge memory, the recommendation is to keep the newest entries up to a byte cap and tell the reader how many were left out. The cap bounds worker RAM; memory content never enters Temporal history. The cap is sized from production memory sizes and the worker's RAM history.

3Switch without losing an entryback backfill job
A14b-D5, recommended: a Bull backfill turns every non-chat blob into rows with the same entries, order and timestamps; readers read rows first, and a later release stops writing the blob.

Two earlier backfills copied some non-chat memories into chat rows, and the flow read serves those rows as the memory's entries; this is checked on dev before the dual-read design, and those rows are never served as a non-chat memory's entries.

4Editor, MCP and versionsfront Small Memory component · MCP metadata · version copies
The editor loads one page and Clear deletes the rows; MCP get_agent and export_agent no longer embed every entry.

A14b-D4, settled 2026-11-24: publish and rollback copy rows, as the blob is copied today. Duplicating a flow copies its rows; a template or a chatbot share copies none.

4

How it is proved

🔬 Verification
1
Negative control
On main, a run against a memory of 100,000 entries reads and rewrites the whole blob; after the change it inserts one row per new entry and reads at most X rows for "Load Last X", measured by query count and peak RSS.
2
Dedup, cap and backfill
A repeated content or a redelivered run event adds no row; "Load All Entries" over the cap says how many entries were left out; the backfill keeps every dev memory's count, order, timestamps and hash.
3
Editor, MCP and versions
The editor opens a memory of 100,000 entries with one page and no re-upload; publish, rollback and duplicate copy the rows; MCP returns a memory node without every entry.
4
Parity
A14's parity corpus gives the same reader input and the same stored entries on both engines.
✓ Done when
A run against a memory of 100,000 entries reads and writes rows in proportion to its new entries, measured; A14's parity corpus still matches; no memory loses an entry in the backfill, checked by count and hash per memory on dev.

An extraction cache, batched writes, and the telemetry that makes the improvement measurable at all.

During a run, before the loop, the engine iterates every varInputNode (flux.service.ts:2772, 2806) and does real external I/O: extractionService.extractTextFromLink per link and awsService.uploadFile per file (:2834–2990), with an OCR mode chosen per input (typeOCR).

It is invisible to every dispatch gate, because it is resolved before nextReady ever runs — so it is not in isTemporalNode, not in the prefetch whitelist, and not in the census. It is nonetheless synchronous, external, and on the critical path of every run that has one.

What the task does, in three parts

1The extraction activityflux.service.ts:2772–2990
Free the backend while OCR runs, which is this task's entire justification.

The step documentation says it in one line — OCR “é síncrono e cega o backend”: it is synchronous, and it blinds the backend. A dedicated activity is a large win for agents with several files, because today the files are processed in the request, one after another, before a single node has run.

The activity takes the inputs, does the extraction and the upload, and returns the resolved values. The engine stops waiting on an external service while it holds the run.

⚠ How it is today

Every link and every file is extracted and uploaded inside the backend request, sequentially, before the loop starts. A slow OCR blinds the process.

✓ How it will be

The extraction is an activity. The backend is free while it runs, and a slow provider costs the run time — not the process.

Measure it, and say the number

The wave carries a latency regression by design — every node migrated here is a blocking round trip until Wave 5 (review §4.5, risk R4). This task is the one where the trade may go the other way, because the backend stops blocking on OCR.

That is a claim, and DELIVERY-PLAN asks for the number per task. Measure latency before and after, per input type — link, file, each OCR mode — and state it in the PR. Without the number, the justification is a hope.

2Three improvements that are cheap while the code is openpersistInputNodeData · extraction telemetry
Take the three wins the same source flags, because each of them is expensive to come back for.

The source that corrected the census also flags three improvements, each cheap while this code is being rewritten anyway:

  • Extraction cache, keyed by URL or file hash. Sub-flows re-extract the same file today — pure rework, paid for on every nesting level.
  • Batch the writes. persistInputNodeData runs one UPDATE per input, sequentially — a row-at-a-time write pattern in front of work that is already slow.
  • Telemetry. Nothing is logged today about OCR duration, file size or provider, which makes Phase-1 latency undiagnosable. Add it before changing the shape, so the change can be measured.

The order matters: telemetry first. A change whose justification is latency, shipped into a system that does not record latency, cannot be defended or reverted on evidence.

⚠ How it is today

The same file is extracted again in every sub-flow, each input is written with its own UPDATE, and no log says how long any of it took.

✓ How it will be

Extract once per URL or file hash, write the inputs in one batch, and have the duration, the size and the provider in the log before and after the change.

3What stays exactly as it isextractText · TASK-S6-SSRF-POLICY.md
Two things this task deliberately does not touch, and one it must wait for.

Renaming extractText is out of scope. The field holds URLs when isExtraction is false, which is confusing — but renaming a persisted field is its own migration, with its own risk, and it does not belong inside a latency change.

The egress policy comes first. Several of these inputs are user-controlled URLs, and this task moves the fetching into the worker, which holds the database password and the integrations key. S6 owns the policy, and this task does not ship a relocated fetcher until S6's decision exists and applies to it.

⚠ How it is today

A user-controlled link is fetched from the backend with nothing checking the address it resolves to.

✓ How it will be

The same link is fetched under one egress policy, from a host whose network position was written down first.

The decision lives in S6, and it is made with this move

S6 carries two open calls — the shape of the policy and the worker's network position — and the point of S6 is that they are answered with the relocation, because the relocation is what changes the risk. Nothing here is decided on this page.

How it is proved

🔬 Verification
1
Negative control — the empty inputrequired
Break the extraction call and confirm a test fails on the resolved input being empty, rather than the run continuing with a blank variable. Today a failed extraction can leave a placeholder resolving to nothing, which reads downstream as a bad prompt rather than a failed upload — that is the failure this test must pin.
2
Parity on real inputsrequired
Same link and same file, backend versus worker, byte-identical extracted text. Not a similar result — the same bytes.
3
Latency, before and after, per input typerequired
This task's whole justification is that the backend stops blocking. State the number — per input type, with the telemetry added before the change so both sides of the comparison exist.
4
Cache correctness
The same file in two nodes extracts once; a changed file does not serve a stale extraction. Both halves matter — a cache that never invalidates turns a fresh document into an old one silently.
✓ Done when
Extraction and OCR run as an activity, parity is proven on real inputs, the backend no longer blocks on them, and the before/after latency is recorded.

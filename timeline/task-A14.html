Shape
Three parts, no worker module
Only the second part needs new logic. No new write, no callback, no lock.

Small Memory does not execute. It is a container that the edge projection writes into when it is the target of an edge, and reads from when it is the source (edge-projection.ts, the fluxObject branches). On the back's loop that state lives in the loop's memory: a node that reads Small Memory sees what earlier nodes in the same run added. The back also loads the chat history before the loop and persists the memory and the assistant's answer around it.

The workflow engine has no process that holds a run's memory; each node runs on its own. Today the gap is hidden: fluxObject has no registry entry, so B4's gate refuses those flows. PLAN §8 called fluxObject configuration-time. That was wrong; this task corrects the consequence.

The decisions this task needs

One call, already made. The spec was rescoped on 2026-10-23: the first draft moved chat writes into the workflow behind A7's callback and lock.
▸Decision A14-aSettledHold Small Memory in the workflow, or derive it from stored executions?
The content of a Small Memory node at a given moment is the history at run start plus the outputs of the nodes that feed it and that completed before the reader was scheduled. Those outputs are already stored, one row per execution.
ADerive the contentsettled
The worker projection rebuilds the content from the seed and the stored rows, in completion order, with the ported projection code. It uses A7's read rule.
  • No new write, no callback, no lock
  • A7-D3 records that A14 needs no lock for this reason
  • No worker module is needed
BMove chat writes into the workflowfirst draft, dropped
The first draft moved chat writes into the workflow behind A7's callback and lock.
  • It needs a new write path, a callback and a lock that option A does not
Our recommendation

A. Persistence stays in the back, so the editor still sees the memory grow during the run.

What the task does, in three parts

1Chat history at run startflux.service.ts · B3b.1
Make both engines start from the same chat history.

The back already loads the chat history before the loop. It now writes it into the run seed snapshot (B3b.1), so the workflow engine reads the same value the back's loop starts from.

⚠ How it is today

The history lives only in the back's process, before its own loop.

✓ How it will be

The history is in the run seed snapshot, read by either engine.

2Small Memory content, derived instead of heldproject-node-input.ts · edge-projection
Rebuild what a reader sees from data that already exists.

This is the only part with new logic. The worker projection (project-node-input.ts) rebuilds the content from the seed and the stored execution rows of the feeding nodes, in completion order, with the ported edge-projection code. Only the writes that completed before the reader was scheduled count, per A7's read rule.

⚠ How it is today

A reader sees what earlier nodes added because one process holds the run's memory.

✓ How it will be

A reader sees the same content because it is rebuilt from the seed and stored rows.

3Persistence stays in the backflux.service.ts
Keep the editor and the chatbot seeing what they see today.

The back persists the memory to the canvas node (persistSmallMemoryEntries) and appends the assistant's answer, as today. On the workflow engine it does so from the B4 per-node events it already receives, so the editor still sees the memory grow during the run, and at run end for the answer.

In scope

fluxObject gets its registry class (none, through A11) and leaves BACK_ONLY_PROJECTION_NODE_TYPES.

Out of scope

Moving any node to the worker. Changing chat semantics, session keys or what the chatbot shows. Two overlapping chat turns on one session can still overwrite each other, as today; fixing that is a separate decision.

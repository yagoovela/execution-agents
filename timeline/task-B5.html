The eligibility gate means most flows simply stay sequential until their nodes are covered.

The persistence model already supports parallel siblings (analysis §7.3): node_executions is one row per execution, and persistNodeSuccess only merges into rows the activity owns. Two siblings cannot lose each other's writes.

What is not safe is mixed mode. A node still running inline in the back does not write to its own row — it ends with addConnectToNodes, which merges the producer's output straight into the target node's data (folw/contants.ts:2032, via modifyData at :2018–2024, 2056–2062). The gate is not a precaution, it is the correctness condition.

The decisions this task needs

Four calls this task forces and must therefore make. The first decides how parallelism reaches production; the other three are the parallel-execution UX that review §5 says will otherwise be decided by accident. Each one opens to the options, what each costs the customer and costs us, and the option we would pick.
▸Decision B5-aRecommended — confirmWhat turns parallelism on for a flow — the gate alone, or the gate plus a cohort?
Three controls are on the table and they are not alternatives: the eligibility gate is a correctness condition, a cohort is a blast-radius control, and a global switch is a rollback control. The open question is which of them is load-bearing. Someone will argue — reasonably — that an eligible flow is provably safe, so the cohort is ceremony. Note what the gate does not prove: it proves no lost update. It does not prove the per-provider budgets hold, that S3's tenancy cap is sized right, or that the three UX decisions below were answered well.
AAll three, layeredrecommended
Eligibility gates correctness, a cohort gates exposure — internal flows, then a small customer cohort, then general — and a global switch is the way back. Rollback is per flow first, then global.
  • Each control answers a different failure, so none of them is redundant
  • The provider budgets and the UX answers get exercised on flows we own before a customer meets them
  • Both rollback levels leave Wave 4's sequential workflow running — nothing has to be reverted to recover
  • Two more surfaces to build and to keep honest: cohort membership and a switch that is actually tested
Client effort: noneOurs: cohort list + kill switch
BThe gate alone, then general availability
Ship the eligibility predicate, and every flow that satisfies it runs in parallel from day one.
  • Simplest thing that is defensible — the gate really is the correctness condition
  • No cohort list to maintain, and no second surface to get wrong
  • The first flow to exercise a provider burst is a customer's, and the symptom is 429s shown as node failures
  • The three UX decisions land on customers on the same day they land in code
Client effort: none, but they are the pilotOurs: one predicate
CA global flag, flipped per environmentnot viable
One environment variable turns parallel dispatch on for everything running in that environment.
  • One line of configuration
  • It runs mixed-mode flows in parallel, which is the exact corruption this task exists to prevent
  • There is no per-flow way back, so the only rollback is “turn parallelism off for everyone”
Client risk: a silent lost updateOurs: no per-flow rollback
Our recommendation

A. The gate is not negotiable — it is the correctness condition and B is not wrong about that. The cohort is what buys the time to be wrong about the other three decisions on this page without a customer paying for it.

Order the ladder deliberately: eligibility first (it refuses nothing a customer can see), cohort second (internal flows have no support cost), global switch always. And keep the switch on a path someone has actually exercised — an untested kill switch is a story, not a control.

The one place B is right is push-type nodes. Handle it there, not globally: a node with an external side effect either completes or is recorded as unknown — never silently as aborted.

▸Decision B5-cRecommended — confirmTwo independent push nodes fire in graph order today. Is that a contract?
Nobody promised it, and nobody wrote it down — it falls out of the engine being sequential. Under fan-out it stops being true, and any customer who relied on the incidental ordering will experience it as a regression (review §5). This is a refusing-shaped change without a refusal: nothing errors, the order simply differs.
AIt was incidental — document it and let it gorecommended
Independent nodes are explicitly unordered. The scheduler's dependency edges are the only ordering guarantee, and a customer who needs an order expresses it as an edge.
  • It is the truth, and it is a rule a customer can act on — draw the edge
  • Preserving the accident means serialising exactly the nodes parallelism was bought for
  • The dependency edges already are the answer — review §4.4 says so; this states it instead of assuming it
  • A flow that works today can start doing its two side effects in the other order, with no error to point at

BPreserve it — side-effect nodes run in a serialised lane
Nodes classified as side-effecting keep running one at a time, in scheduler order, while pure nodes fan out.
  • No customer-visible regression at all
  • Keeps the parallelism where most of the time is actually spent — LLM and search nodes
  • Somebody has to define which types count as side-effecting, and that list will be wrong at the edges
  • It preserves an ordering nobody specified, which makes it a contract by accident — permanently

CPer-flow opt-outescape hatch
A flow can declare “keep my side effects ordered” and is then run with the serialised lane from B.
  • The customer who genuinely depends on the order says so, and pays the latency for it
  • Composes with A — it is A plus a named exception, not a different model
  • Invisible until somebody is already bitten, because nobody sets a switch for a problem they have not had
  • Another per-flow setting to explain, document and support

Our recommendation

A — but measure before declaring the regression theoretical. PLAN §3.3.2 applies even though nothing is refused: count the production flows that have two or more independent side-effect nodes in one ready set. If that count is zero, A is free. If it is not, those owners are the cohort to talk to before the switch is thrown.

Keep C in the drawer. Ship it if the count says somebody needs it — not before.

▸Decision B5-dRecommended — confirmWhen several siblings fail at once, which failure names the run?
Fail-fast stops at the first error today, so “the run's error” has one candidate. With a batch in flight several nodes can fail simultaneously (review §5), and every consumer of that field — the run page, the notification, the webhook payload — still expects exactly one. Note the interaction with this task's own determinism check: if the name is chosen by whichever failure landed first, the same flow failing the same way can name a different node on each run.
AFirst to fail, by time
The earliest failure to arrive names the run; the others are recorded on their own nodes.
  • Closest to today's wording, so nothing downstream has to change
  • Trivial to implement — it is what a race already produces
  • Non-deterministic: two runs of the same broken flow can blame different nodes
  • Support cannot reproduce a report, and a test cannot assert the message
Client sees: a different cause each timeOurs: nothing to build
BDeterministic tie-break, in scheduler orderrecommended
Among the nodes that failed, the first in the scheduler's own ordering names the run — the same answer on every replay.
  • The same flow failing the same way names the same node, every time
  • Makes the failure message assertable in a test and reproducible in support
  • Reuses the ordering the scheduler already owns — no new notion of “first”
  • The named node is not necessarily the one that failed first in time, which reads oddly in a log
Client sees: the same cause every timeOurs: a sort, not a subsystem
CThe run carries the whole failure setpairs with B
Every simultaneous failure is stored, and the run exposes a set plus one summary line.
  • Honest — when four nodes fail, four nodes failed
  • Diagnosis stops depending on which failure won a race
  • Every consumer of “the run's error” has to learn a new shape — UI, notification, webhook payload
  • Alone it does not answer the question: something still has to pick the summary line
Client sees: all the causesOurs: every consumer changes
Our recommendation

B for the name, C for the record. Store every simultaneous failure, and let the scheduler's ordering pick which one is shown. They are not competing answers: C makes the data honest and B makes the summary stable.

The reason to care is one row up on this page: this task has to prove that the same flow run twice produces the same result. A run whose error message is decided by a race fails that check for a reason that has nothing to do with the outputs.

What the task does, in four parts

1The eligibility gate is the whole taskA1 registry · folw/contants.ts:2032
Run a flow in parallel only when every executable node in it is a migrated type — read from one registry, not guessed.

The check is per flow, and it is a conjunction: parallel dispatch is allowed only when every executable node in that flow is a migrated type, read from the A1 registry. isMigratedTemporalNode's successor is exactly this predicate.

The spec is blunt about the boundary. Out of scope: anything that widens eligibility by relaxing the gate. If a flow is not eligible, the answer is to migrate its remaining nodes — never to make the check lenient.

⚠ How it is today

Batch size is one. A ready set of six independent nodes runs as six sequential round trips, and no gate exists because nothing needs one.

✓ How it will be

A flow whose nodes are all migrated dispatches its ready set as one batch. A flow with one inline node stays sequential and is counted, with the node type that disqualified it named.

Ineligible is a measurement, not a refusal

Nothing a customer does changes when a flow is ineligible — it runs the way it runs today. The list of ineligible flows, with the disqualifying type named for each, is the work queue for the A track.

2Concurrency budgets, per provider and per tenantreview §4.2 · S3
A global cap does not stop one wide graph from spending the whole budget on one provider.

The gate is about correctness. It says nothing about capacity. Unbounded fan-out produces bursts against OpenAI, Anthropic, Replicate and the integration APIs, and the first symptom is 429s surfaced to the customer as node failures — an error that looks like our platform breaking and is in fact us calling too fast.

  • Per provider — a concurrency budget derived from that provider's real rate limit, and shared across the fleet rather than counted per replica. A per-replica budget multiplies by the replica count, which is the number this epic exists to raise.
  • Per tenant — enforced by S3, which this task depends on. Without it, fan-out is a fairness bug: one customer's wide graph consumes the parallelism everyone else was going to use.
⚠ How it is today

One node in flight per run, so a burst is impossible and no budget is needed. The throttle is the sequential loop, and nobody chose it.

✓ How it will be

Fan-out is bounded by the provider's real limit and by the tenant's share. Excess is queued by us, not refused by the provider and shown to the customer as a failed node.

A global cap is not the same control

One number for the whole fleet still lets a single wide graph spend all of it on one provider, while the other providers sit idle and that customer's calls get 429s. Review §4.2 is explicit that this needs a per-provider, per-tenant budget — not just “pick a cap”.

3The preconditions, and why the order is not optionalreview §4.5
The blocking wait was providing back-pressure nobody designed. Removing it before the ceilings exist replaces a slow system with an unstable one.

await handle.result() was treated as pure waste. It is also back-pressure: while the backend blocks, it is not starting more work. The removal is still right; the ordering is not optional.

Wave 5's preconditions, all shipped in earlier waves:

  • S1 — the recursion ceiling. B6 turns sub-flows into child workflows, and a durable platform will sustain a cycle across the whole fleet.
  • S2 — the connection ceiling. The worker pool sets no max, so connections scale linearly with replicas against a max_connections shared with the API.
  • S3 — spend and tenancy: the per-run cost ceiling and the per-tenant concurrency cap, which is what makes the per-tenant half of Part 2 enforceable at all.
  • E3 — notifications that cross replicas, shipped before parallelism multiplies the event rate.
  • B5's own per-provider budget — the one precondition this task owns itself.
⚠ How it is today

Three accidents provide the ceilings: one sequential engine loop, one queued run per backend replica, and a blocking wait on every Temporal node. None of them was designed as a safeguard.

✓ How it will be

All three are gone, and every ceiling they were accidentally providing has an explicit owner that shipped first.

4What a parallel run looks like from the outsidereview §5 · PLAN §6 R4
Several nodes are RUNNING at once, and “which node is the run on” stops having one answer.

The builder shows per-node status today. With fan-out, several nodes are RUNNING at the same time — including in the cancel footprint the product already shows. That is a UI change, and it is the visible half of this task.

The other visible half is the number this epic was funded on:

  • Wide flows finish in the time of their slowest path rather than the sum of their nodes.
  • R4 in PLAN §6 predicted a latency regression from the A track — every migrated node is a blocking round trip until this task. This is where that claim is settled with numbers or not at all.
  • Determinism has to hold: the same flow run twice in parallel must produce the same final outputs.
⚠ How it is today

A flow with six independent nodes takes the sum of six round trips, and every node the A track migrated made that sum larger, not smaller.

✓ How it will be

The same flow takes the time of its slowest node, and the regression the A track introduced is measured against the pre-epic baseline.

Then confirm the gate refuses that flow. This is the test that justifies the gate; without having seen the corruption, nobody will keep the gate strict.

The same flow run twice in parallel must produce the same final outputs. Run it enough times to mean something, and record the count — “we ran it a few times” is not a result.

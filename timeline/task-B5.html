Turn on parallel dispatch

A flow whose nodes all run on the worker runs its ready nodes at once, up to a per-run cap (maxInFlight), so its wall-clock time approaches its slowest path instead of the sum of its nodes.

Dev checks (B5-T9) ran 2026-11-23 and 2026-11-24: checks 1, 2, 3 (a schedule run is parallel, batch rows stay sequential), 4 and 6 (two worker replicas, including a `WorkerShutdown` retry with no fail-fast cancel) pass; check 5 passes for the run list; the fan-out runs 1.84x faster and the reference shape 1.90x. Rollout
By company, behind two flags
parallel_dispatch (company allowlist, value = cap) and parallel_fail_fast. Turning the flag off restores sequential dispatch for new runs.

processFlow, the Temporal workflow that runs a flow on the worker, runs one node at a time: it takes one ready node, waits for it to finish, and only then takes the next. A flow with eight independent image generations therefore takes the sum of the eight. The engine was built to run independent nodes together, but nothing dispatches more than one.

Parallel nodes cannot overwrite each other. apiV2 sends a flow to the workflow only when it has no inline node (a type that runs inside the back); on the workflow path every node writes only its own row; and addConnectToNodes, which writes into another node's data, runs only before the run starts. The platform runs at most 10 nodes at once (1 worker replica, 10 activity slots), so B5 also caps each run.

What the task does, in six parts

1A parallel loop in processFlowworker/src/modules/temporal/workflows/process-flow.workflow.ts
On B6's version of the loop, the in-flight set fills up to maxInFlight and refills as each node settles.

The patch marker b5-parallel is recorded only when maxInFlight > 1; otherwise the current loop runs unchanged, with the same node order and history events, and histories recorded on B6 replay (B5-R1). The parallel loop calls nextReady until the set holds maxInFlight nodes, waits for the first to settle with Promise.race, applies its outcome (ok, failed or cancelled) in one synchronous step, and fills again (B5-R2). maxInFlight and failFast are optional fields of ProcessFlowInput and ChildFlowInput, and survive continue-as-new.

⚠ How it is today

One node at a time: a flow with eight independent image generations takes the sum of the eight.

✓ How it will be

Up to maxInFlight ready nodes run together; in dev a 4-wide fan-out ran 1.84x faster at 2.

2Rules per control-flow typeprocess-flow.workflow.ts · child-flow.workflow.ts
arrayNode, conditionNode, fluxBox and libraryNode run next to their siblings without breaking the loop's state.
  • arrayNode holds its body nodes while it runs. Iterations write the current item onto the array's single row, so they stay sequential; a body node never runs outside the loop (isHeldByArray), and two arrays whose bodies overlap run one after the other (B5-R3).
  • conditionNode: a dead-branch target has the condition as a gating predecessor, so a dead branch is never dispatched.
  • fluxBox / libraryNode: each call has its own run id, seed and workflow id, runs with the parent's maxInFlight and keeps its own S1 chain (B5-R4). A continue-as-new inside a sub-flow now resumes as a sub-flow, which fixes a B6 bug.
3Fail-fast, drain and continue-as-newprocess-flow.workflow.ts · activities.service.ts
The first genuine failure stops the run quickly without cancelling a sub-flow or a worker's drain.

Fail-fast (failFast on, failure not a WorkerShutdown) cancels the scope that holds every in-flight leaf node, records the reason on each cancelled node's row and its node_finished event, and waits for all of them to settle; fluxBox and libraryNode children run outside that scope and are awaited (B5-R5). Drain (flag off, or a WorkerShutdown) stops filling, lets every in-flight node finish, then fails the run; once a drain starts, a later failure cannot cancel. Continue-as-new happens only with no node in flight (B5-R6), and a failure during the drain wins over the continuation.

A scale-in drains, it does not cancel
A stopped worker gives its activities 100 s, then fails them with WorkerShutdown and retries once on another worker (A9c). Because B5 drains on WorkerShutdown, a scale-in never cancels healthy siblings (B5-R11).
4The back decides the cap per runback/src/app-api/flux/engine-selector.ts · flux.service.ts
resolveParallelDispatchArgs returns maxInFlight and failFast for the apiV2 and Temporal-schedule starts; batch rows get neither in v1 (B5-R7).

It returns clamp(floor(value ?? 2), 1, 4) when the flow passes canUseWorkflowForFlow and the company that owns the flow is on parallel_dispatch. One seed migration (SeedParallelDispatchFlags) creates parallel_dispatch (off, value 2) and parallel_fail_fast (on). The worker deploys first: it ignores absent fields.

5The run list shows every node in flightback/src/app-api/executions_logs/execution_logs.service.ts · FlowRunDto
Two places assumed one in-flight node: the run list and settleAbandonedRuns.

FlowRunDto.inFlightSteps lists every in-flight node (nodeId, execId, workflowId) from one json_agg; stepInterruptible is true only when every in-flight node can stop, and settleAbandonedRuns checks every in-flight workflow (B5-R9). The query measured at parity with the old one on a local 1-million-row copy; it was not measured on a production-sized copy.

6Ready for more replicasECS and RDS, read-only, 2026-11-19
B5 keeps no per-replica state, so it behaves the same with any number of worker and back replicas (B5-R11). Autoscaling for the worker, the back and the MCP server comes after B5; the Temporal server stays at 1 replica.
  • Cap and decision travel in the run input and live in workflow state; any back replica returns the same value.
  • DB connections: each worker replica opens a pool of 10 (S2). Check max_connections before raising the worker maximum.
  • Provider limits: B5b ships before the worker maximum goes above 1.
  • The Temporal database is the real ceiling: a db.t3.micro whose CPU credit balance fell to 40 of 288 over 14 days. Resize it before the internal rollout, and lower the cap or pause the rollout if CPU, credits or free memory degrade.
  • Cap ceiling: 4 is a code constant sized for 1 replica; raise it in the release that raises the worker maximum.
Open risk: tenant fairness with 1 replica
One run holds up to maxInFlight of the platform's 10 slots, and each sub-flow level asks for up to that many more (16 slot requests at 2 and depth 3, which queue and do not fail). Mitigation: default 2, batch sequential, internal allowlist; revisit with the queue wait measured in the internal rollout.
Accepted: fail-fast and side effects
A cancelled TRY_CANCEL sibling (integrations, pushData, sqlQuerier, mcp, largeMemory, fileSave) finishes its write and is recorded cancelled; a re-run repeats the write. The cancel reason on the Logs page and parallel_fail_fast are the mitigation.

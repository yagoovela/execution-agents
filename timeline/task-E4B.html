runScheduledFlow starts the flow straight as a processFlow child. The run never reaches the back's end of run, so the Data Output's email and callbacks are not sent and the run logs are not written. Before E4 a scheduled run went through the apiV2 job and did all of that.

Batch rows had the same gap; A13 closed it with a worker-to-back finish call. This task gives scheduled runs the same finish. On 2026-11-18 the scope widened: the Temporal path also ignored the schedule's variableInputs and seeded the run from the flow's saved values, so the back now seeds the run, the way it seeds a batch row.

What the task does, in three parts

1The back seeds the run from the scheduleback POST /worker/scheduled-run · prepareWorkflowSeed
Behind patched("e4b-scheduled-run-finish"), runScheduledFlow calls prepareScheduledRunActivity in place of the old seed activity.

The back seeds the run with the schedule's variableInputs through prepareWorkflowSeed, shared with batch rows, and refuses a deleted schedule. The seed rows carry the run type and the runId, so the Logs page lists one run per fire instead of a separate one-node run for the variable input.

⚠ How it is today

The run uses the flow's saved values.

✓ How it will be

The run uses the schedule's inputs.

2A finish step after the child returnsworker run-scheduled-flow.workflow.ts · back POST /worker/scheduled-run-outputs
After the processFlow child returns, finishScheduledRunActivity asks the back to close the run through closeWorkerRun, with run type cronjob and email on.

When processFlow itself fails, the run is finished as an error and the scheduled run still fails with that error. A child cancelled on its own is finished as cancelled. Three replay histories, without the finish, with it and with a failed child, replay on the new code.

⚠ How it is today

The run ends without delivery or logs.

✓ How it will be

The run ends through the back.

3Delivery once per runback flux.service.ts (closeWorkerRun)
Each delivery starts under the invocation id scheduled-run, so a retried finish delivers once.

The run writes flows_logs, space_run_logs and chat_logs through the helpers batch rows use. The chat_logs body is an explicit field list, so the schedule row and its owner are never copied. Pause, backfill and last-run state stay in E4.

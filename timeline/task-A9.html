Re-validated 2026-09-29
Seven premises were corrected against production; two of them would have made the task fail as first written.

The block at the end of every run (flux.service.ts:5329–5599) sends email through three paths — SMTP, Gmail, Microsoft — and posts a callback with axios.post. Nothing is retried. The api-v2 consolidated callback (apiV2Job.processor.ts) is a second site with the same gap.

The first draft said the hard half was done: the Redis dedup keys would make a retry safe. Checked against production, they would do the opposite — they are claimed before the send and never released, so a retried send would be suppressed for 24 hours. The keys stay; the order of operations around them changes.

The decisions

▸Decision D-A9-1SettledShould the run wait for delivery, including every retry?
Nothing inside the run waits on delivery: the output node has no source handle and delivery starts after the scheduler loop has finished. What would wait is the caller — /beta-v2, /run-public-flow, the chatbot final message, /api-v2's 30 s synchronous wait — and the parent of a sub-flow. When delivery is asynchronous, a failed attempt is scheduled again by the Temporal server after the backoff; the wait holds no worker slot and survives a back or worker restart.
AAsynchronous, retried server-sidechosen
The run starts a delivery workflow and returns; one activity per output node and channel; the terminal outcome is written to the flow log.
  • A retry budget of minutes fits, because nobody is blocked on it
  • An email failure stops failing the run, the parent run and the chat-log save
  • flow_execution_status reaches completed before the callbacks go out
BSynchronous, all retries
The run returns only after every attempt settles.
  • Past /api-v2's 30 s, the 300 s server timeout and the 600 s job timeout
  • A parent flow-caller node sits blocked for the whole budget
CSynchronous first attempt, asynchronous retries
Keep today's latency and move only the retries.
  • Keeps today's coupling and still needs the asynchronous path — two paths for no gain
Our recommendation
Settled with the user on 2026-09-29: A. If Temporal is unreachable when the run ends, back writes the Delivery failed row itself; there is no inline fallback, because an inline twin is what PLAN §3.4 forbids.
▸Decision D-A9-6SettledHow do the dedup keys stop suppressing the retry they were meant to protect?
The key names, formats and TTLs stay exactly as they are. What changes is the order: claim, send, confirm — and release on failure.
AClaim–send–confirmchosen
SET pending EX 300 NX → send → SET sent EX 86400; on failure DEL. A value of 1 left by the old code counts as sent.
  • A retry after a failure can claim again
  • A real duplicate is still suppressed for 24 hours
  • A worker dying between send and confirm resends after 300 s — at-least-once, stated rather than hidden
BPort unchanged
What the first draft asked for.
  • Every retry of a failed send is suppressed for 24 hours
Our recommendation
Callbacks get no Redis key: their idempotency is the X-FluxPrompt-Delivery-Id header (D-A9-8), identical on every attempt, which the receiver can use.
▸Decision D-A9-5SettledThe worker will post to customer URLs — how is that checked without deciding S6 for it?
A9 moves every user-controlled fetch of the delivery path into the worker, which holds the DB password. The guard is a module S6 extends, not a decision taken for S6.
AA minimal guard, report firstchosen
Resolve and pin the address on every hop; refuse loopback, link-local, private, unique-local and reserved ranges; EGRESS_POLICY_MODE defaults to report.
  • A subset of what S6 asks for, with an allow hook for its allowlist
  • Dev: every stored callback and attachment URL resolves public — zero would-be refusals
  • enforce waits for the prod measurement and a week in report
BNo guard until S6
Move the fetches as they are.
  • Moves an unchecked fetch next to the DB credentials

What gets built

1One delivery module in backOutputDeliveryService
Replace the inline block with one service that builds the plan exactly as today and starts the workflow.

Recipients, subject, text, template choice, attachment URLs, provider, callback URL and the sendEmail gate resolve as they do now. A plan up to 256 KB goes inline; a larger one goes through S3 — dev has an output body of 3 MB, and Temporal rejects a payload above 2 MB.

⚠ How it is today

271 inline lines at the end of apiV2, awaited by every caller.

✓ How it will be

One service, one workflow start, and the caller gets its answer without waiting for delivery.

2Delivery activities in the workerworker/src/modules/delivery
Send email and callbacks from the worker with a retry policy per channel.

Gmail and Microsoft send with tokens from the existing broker (/worker/refresh-oauth-token), verified to use the same token and client as today's path, so no refresh token moves. SMTP gets the EMAIL_* variables.

3The egress guardworker/src/modules/egress
Check the address the worker actually connects to, on every redirect hop.

One module used by every A9 call site and by nothing else yet; S6 extends it with the allowlist and the other call sites.

4A failure the customer can seeflows_logs
Put the delivery that finally gave up where the customer already looks.

The worker reports the terminal outcome to /worker/delivery-outcome; back writes one Delivery failed row with the channel, host and last code — never the full URL or the recipients. The only front change is one condition on the “Error info” button.

⚠ How it is today

A lost callback or an SMTP failure exists only as a log line.

✓ How it will be

A row in the flow's log table, next to the run it belongs to.

How it is proved

🔬 Verification
1
Negative control — the retry itselfrequired
A callback to an endpoint that returns 500, 500, 200 is delivered on attempt 3. Set maximumAttempts: 1 and watch it fail.
2
The retry is not suppressed by deduprequired
A send that fails once and then succeeds produces exactly one email. Restore claim-before-send-without-release and watch the second attempt be suppressed.
3
Double-send, in both directionsrequired
Run the email activity twice for the same run and node: the second is suppressed. Delete the key between them: it sends twice.
4
Egress, enforced and reportedrequired
In enforce, 169.254.169.254 and a 302 to 10.0.0.1 are refused; in report they go through and are logged; a DNS failure is retried, not refused.
5
Parity per path, and the failure surface
SMTP, Gmail and Microsoft each match their own before. A delivery that exhausted its retries is a Delivery failed row; a failing consolidated callback leaves the status at completed.
✓ Done when
Email and callback delivery run as worker activities with per-channel retry policies, started without the caller waiting; the inline block is gone; the dedup keys keep their names, formats and TTLs under claim–send–confirm, proven both ways; each email path matches its own before; a terminal failure is visible in the flow's log; the consolidated callback is covered; every callback carries the idempotency header; the egress guard ships in report; and each preserved defect is pinned by a test and filed.

The hard half is done
Idempotency already exists — the Redis dedup keys (email-sent:, email-content:). Retry with backoff is the missing half.

The block at the end of every run (flux.service.ts, ~300 lines) sends emails through three paths — mailService.sendMail, mailService.sendGmailEmail, microsoftMailService.sendMail — and fires HTTP callbacks with axios.post, each wrapped in a catch. Nothing is retried.

This is the cleanest activity candidate left in the codebase, and the hard part is already done: the Redis dedup keys are a run-scoped SET … EX 86400 NX plus a shorter content hash, built exactly so a repeated attempt does not double-send. Retry with backoff is the missing half, and it is what Temporal provides.

What changed on 2026-08-21 (PR #1902). The api-v2 consolidated callback — the one that summarises the run to the caller — moved out of flux.service.ts into apiV2Job.processor.ts (CALLBACK_TIMEOUT_MS = 10_000), and the run's state is now also written to flow_execution_status, read by GET /flux/executions/:id. So there are two callback sites, not one: the end-of-run block this task moves, and the processor's consolidated callback. Cover both, or state which one stays fire-and-forget and why.

Two channels, and why one retry policy will not do

ChannelPaths todayOn failure todayRetry policy after
EmailmailService.sendMail, mailService.sendGmailEmail, microsoftMailService.sendMailLost, with a log lineConservative
HTTP callbackaxios.post, each wrapped in a catchLost after thirty seconds of downtimeGenerous
Dedup, for bothRun-scoped SET … EX 86400 NX plus a shorter content hashAlready there, never used as a retry netPorted unchanged
The two policies must differ, and the reason is in the spec: a callback to a customer endpoint should retry generously — the endpoint is coming back — while an email should not retry into a rate-limited SMTP relay, where retrying is what makes the next attempt fail too. Inheriting one default for both is how a fix turns into an outage on the mail provider.
2

What the task does, in four parts

1One delivery activity per channelflux.service.ts
Give each channel a retry policy chosen for how that channel actually fails.

Email and callback become two activities, with retry policies chosen per channel rather than inherited. That is the whole design decision, and it is already made: a customer endpoint that returns 500 for a minute is exactly the case retry exists for, and an SMTP relay that is rate-limiting is exactly the case where retrying makes things worse.

⚠ How it is today

Each send is wrapped in a catch. A failure is a log line, and the run reports success while the customer never hears from it.

✓ How it will be

Each send is an activity with a retry policy someone chose. A transient failure resolves itself; a permanent one becomes a terminal state.

The wave asks for the number here too

DELIVERY-PLAN asks every task in this wave to measure the latency change and state it in the PR (review §4.5, risk R4). Delivery sits at the end of a run, so the round trip lands on the run's tail rather than between its nodes — measure it anyway, because “it is only at the end” is the kind of claim that turns out to be wrong on a run with many recipients.

2The dedup keys move unchangedflux.service.ts
Keep the exact mechanism that makes a second attempt safe, instead of re-deriving it worker-side.

The Redis keys are the reason retry is safe: a run-scoped SET … EX 86400 NX plus a shorter content hash, built so a repeated attempt does not double-send. They are not an implementation detail to re-derive — port them as they are.

A re-derived key that looks equivalent and differs in scope or TTL turns the safest part of this task into a double-sent email, which is the one failure a customer notices immediately.

⚠ How it is today

The keys exist and work, and nothing ever exercises them — there is no second attempt for them to suppress.

✓ How it will be

The same keys, in the activity, doing the job they were written for: the retry that Temporal drives cannot double-send.

3Extract the block while moving it~300 lines at flux.service.ts
Stop the shape that has kept anyone from adding retry for as long as the block has existed.

The review's source material calls this a candidate for an OutputDeliveryService. 300 lines of inline delivery is the reason nobody has added retry in the first place — the change was never small, so it never happened.

Extract it while it is being moved. Doing the two separately means reading the same 300 lines twice.

⚠ How it is today

Delivery is ~300 inline lines at the end of the run method, with three mail paths and the callback logic interleaved.

✓ How it will be

One delivery module, with the channels separated, which is what makes “add a retry policy” a small change next time.

4A failure surface, because retries create terminal statesrun log
Make a delivery that finally gave up visible to someone other than Winston.

Today a lost callback is invisible to the customer. With retries there is a terminal state — the attempt that gave up — and it should be visible in the run log at minimum.

Out of scope, deliberately: payload shapes, recipients, and when delivery is triggered. This task moves and retries; it does not redesign.

⚠ How it is today

A failed delivery exists only as a Winston line. The run shows as successful, and nobody outside the log knows the notification never arrived.

✓ How it will be

A delivery that exhausted its retries appears in the run log, as a terminal state, where the person debugging the run is already looking.

3

How it is proved

🔬 Verification
1
Negative control — the retry itselfrequired
Point a callback at an endpoint that returns 500 twice then 200, and confirm the delivery succeeds after retry. Then break the retry policy and confirm the test fails — a retry that is configured but never exercised is not a retry.
2
Double-send, in both directionsrequired
Force the activity to run twice for the same run and node and confirm the dedup key suppresses the second. Then delete the key and confirm it double-sends — that second half is what proves the key is load-bearing rather than decorative, and it is a customer-visible failure, so it deserves the proof.
3
Email parity across all three pathsrequired
Same recipients, same attachments, same body, before and after — for sendMail, sendGmailEmail and microsoftMailService.sendMail. Three paths means three ways for a body or an attachment to quietly change.
4
The failure is visible where people look
Confirm a terminal delivery failure appears in the run log rather than only in Winston. A retry that ends in silence is the same defect with more steps.
✓ Done when
Email and callback delivery run as activities with per-channel retry policies, the Redis dedup keys moved unchanged and were proven load-bearing in both directions, email output matches across all three paths, a delivery that exhausted its retries is visible in the run log, and the processor's consolidated callback (PR #1902) is either covered by the same activity or explicitly left fire-and-forget, with the reason in the PR — with payloads, recipients and triggers unchanged.

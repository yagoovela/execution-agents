The socket path is process-local. chatbotSocketByRun is a plain Map in the backend process (flux.service.ts — set when the run starts, deleted in the run's finally). A run whose socket was registered on replica A cannot be notified from replica B.

And there are two mechanisms. The worker publishes to Redis — room_status_updated, room_stream_chunk, completion_stream_chunk — which the backend relays via @EventPattern to Socket.io; the inline path writes to the socket directly. Two paths to maintain, two places to fix a bug, and they will drift — the same failure this epic is trying to end for dispatch lists.

The decisions this task needs

Only one call is open here — the rest of the task is settled by the spec. It is also the one that decides whether the transport change delivers what it was bought for. It opens to the options considered, what each costs the customer and costs us, and the option we would pick.
▸Decision E3-aOpen — needs a callWhat makes any replica able to deliver to a client connected to another?
The spec settles the publish side: everything publishes to Redis, the socket layer only consumes, and the worker's existing mechanism is the survivor because it already works across processes. It does not settle the last hop — it asks for “a Redis adapter for Socket.io, or an equivalent”. That is the open call, and it is the one that decides whether unifying on Redis solves the problem or merely moves it.
AThe Socket.io Redis adapterrecommended
Every backend replica subscribes through the adapter, so an emit to a room reaches the client whichever replica holds its connection. Rooms replace the hand-rolled map.
  • It is the mechanism the socket library ships for exactly this problem — there is nothing to design
  • Redis is already in the path — queues, worker→backend pub/sub, dedup — so there is no new dependency
  • It deletes the process-local Map rather than distributing it. The map is the bug
  • Every replica receives every event and filters, so cost grows with replicas × event rate — and B5 raises the event rate on purpose
  • It lands on the same Redis instance S8 Part 3 is already being asked to size
Client effort: none — no payload changesOurs: one adapter, plus Redis headroom to confirm
BA run→replica routing table
Keep our own map, but store which replica holds each run's socket in Redis, and forward each event to that replica only.
  • Only the replica that can deliver receives the event, so traffic does not grow with replica count
  • The shape is familiar — it is chatbotSocketByRun with the process boundary made explicit
  • It is writing the adapter ourselves — reconnection, replica death, stale entries and a client that reconnects elsewhere mid-run all become our bugs
  • More state to keep correct, for a saving that only matters at a replica count we do not have yet
Client effort: noneOurs: an adapter we maintain
CPostgres LISTEN/NOTIFY as the bus
Publish run events through the database instead of Redis, and have each replica listen on it.
  • One less system in the correctness path, and Postgres is already the system of record
  • Events would survive a Redis outage
  • It puts a high-rate event stream on the database S2 calls the first thing that breaks
  • NOTIFY payloads are capped, and room_stream_chunk is a stream of content
  • LISTEN holds a session-level connection per replica — exactly what the transaction-mode pooler S2 recommends does not support
Client effort: noneOurs: load and a session on the wall S2 is sizing
DSticky sessionsnot sufficient
Pin each client to the replica holding its run, so the process-local map keeps working as it does today.
  • No transport change at all — the cheapest thing that appears to work
  • It does not survive a deploy or a restart mid-run, which is precisely when a long run still needs its events
  • It makes the load balancer part of the correctness argument, where nothing tests it
  • It does nothing for the worker→backend direction, which is where most events already originate
Client effort: noneOurs: correctness moves into the load balancer
Our recommendation

A. The rest of this task is already settled — one publish path, the worker's mechanism survives, payloads do not change. The only reason this is a decision at all is that the adapter is what makes “publish to Redis” actually reach a client; choosing wrong here ships the transport change without the property it was bought for.

Size it with S8, not after it. Both tasks are in this wave, both add traffic to the same Redis, and B5 multiplies what they add. One number, agreed once.

And it ships behind a flag with the old path intact for one cycle. This is the riskiest change in the wave, because a transport that silently drops one class of event looks exactly like a slow run.

What the task does, in three parts

1One publish path, and a socket layer that only consumesflux.service.ts
Collapse two mechanisms into one, so a bug has one place to be fixed instead of two places to drift.

Two mechanisms exist today. The worker publishes to Redis — room_status_updated, room_stream_chunk, completion_stream_chunk — which the backend relays via @EventPattern to Socket.io. The inline path writes to the socket directly.

Two paths means two places to maintain and two places to fix a bug, and they will drift — the same failure this epic is trying to end for dispatch lists.

The worker's mechanism is the survivor. It already works across processes, which is the property being bought. Everything publishes to Redis; the socket layer only consumes.

⚠ How it is today

Two mechanisms. chatbotSocketByRun is a plain Map in the backend process, set when the run starts and deleted in the run's finally, and the inline path writes into it directly.

✓ How it will be

One publish path. The inline path's direct socket writes are gone, not merely unused, and the socket layer has one job.

2The last hop is the part that is still process-localback/src/app-api/gateway/gateway.ts
Make the delivery step replica-independent, so unifying on Redis solves the problem instead of moving it.

Publishing to Redis crosses the worker → backend boundary. It does not cross the backend replica → client one: a run whose socket was registered on replica A still cannot be notified from replica B, because the connection lives in one process's memory.

That is why the spec asks for an adapter, or an equivalent, in the same breath: without it, unifying on Redis moves the problem rather than solving it.

⚠ How it is today

A run registered on replica A cannot be notified from replica B. It is a blocker for horizontal scale, and it is already latent — it does not need the worker migration to bite.

✓ How it will be

Any replica can deliver to any connected client, and the process-local map stops being the thing that decides who can be reached.

3Type the status stringsworker/src/modules/notification/notification.service.ts · temporal.controller.ts · router.controller.ts
Make a typo across the process boundary a compile error instead of a status the UI silently ignores.

'PENDING' | 'RUNNING' | 'COMPLETED' | 'FAILED' | 'CANCELLED' are free strings on both sides of a process boundary today — the worst place for a typo, because it fails silently as a status the UI does not recognise.

⚠ How it is today

A misspelled status crosses the boundary, is relayed, is delivered, and disappears at the last step — with no error raised anywhere along the way.

✓ How it will be

One shared union on both sides. A misspelled status does not compile.

Out of scope — the payloads

Changing the event payloads the front consumes. This is a transport change; a payload change in the same task would make a regression impossible to attribute.

How it is proved

🔬 Verification
1
Negative controlrequired
Register a run's socket on one replica and emit from another; assert the client receives it. Run that test before the change and watch it fail — that failure is the bug, and demonstrating it is what justifies the work.
2
Ordering per node under parallel dispatch
A node's RUNNING must never arrive after its COMPLETED. Worth asserting explicitly, because parallelism is what makes it possible.
3
No lost events with several nodes streaming
With several nodes streaming at once, count emitted versus received. A transport that drops under load looks exactly like a slow run, which is why the count has to be explicit.
4
The inline writes are gone, not merely unused
Confirm the inline path's direct socket writes were deleted. A second path that is unreachable today is a second path someone reaches tomorrow.
✓ Done when
One publish path, delivery works across replicas, statuses are typed, and ordering holds under parallel dispatch.

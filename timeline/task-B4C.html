On the workflow path (processFlow), no {{...}} placeholder in a node's text is replaced. The node receives the literal text, for example {{topic.text}}, and sends it to the model or the API.

The legacy loop builds a substitution schema from every node at run start (generateSchemaFromNodes) and updates it after each node runs (updateSchemaWithNodeOutput); with worker_input_resolution on, it stores that schema as the snapshot base and each dispatch as a delta, so the worker rebuilds it exactly (B3). The B4 path writes base = {}, each open writes an empty delta, and processFlow passes an empty journal. No task owned it. API runs and schedules are not affected yet, because engine_in_workflow and temporal_schedules are off in production.

What the task does, in three parts

1Seed the snapshot base with the back's own schemaback/src/app-api/flux (run seed)
The seed writes the snapshot base with generateSchemaFromNodes over the nodes after run inputs are applied, instead of {}.

The base holds the text fields of every referenceable node and lives in run_substitution_snapshots.base, not in Temporal history. A textBox with an empty text is filled from its textData, as generateSchemaFromNodes does.

⚠ How it is today

The workflow path seeds an empty base.

✓ How it will be

Run inputs, batch row values and stored node values resolve.

2Overlay the outputs of nodes that already finishedworker (input resolution) · processFlow
Before a node resolves, the worker overlays the outputs of nodes that finished earlier in the run, in the legacy order.

Either through the ported updateSchemaWithNodeOutput, or by processFlow passing a real journal so that each finished node records its delta; the design picks one. References inside an arrayNode iteration follow the legacy per-iteration values (B3.1), the schema carries over continueAsNew, and a claim-checked output resolves through its claim ref. Under B5, a node sees only the outputs of nodes that finished before it was dispatched.

⚠ How it is today

{{writer.text}} stays literal after writer ran.

✓ How it will be

It resolves to writer's output, as on the legacy loop.

3Parity on every entry pointbatch rows · API runs · schedules · child runs
Batch rows in production resolve placeholders again, and API, scheduled and child runs match the legacy loop placeholder for placeholder.

Out of scope: a bare {{label}} that resolves to [object Object] and unknown keys that stay literal are legacy behaviour, and parity keeps them. Seed pruning is B4b-D1, after this task.

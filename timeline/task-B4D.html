Back seed and worker projection
Estimate 12 to 28 h, uncalibrated. The order rule is extracted from the back's addConnectToNodes and ported, never restated.

On dev on 2026-11-26, probe X1 (two mathFunction nodes into one Data Output) returned first runs, second runs with engine_in_workflow off and second runs, first runs with it on. A chat flow with two AI Text Generators changed its answer text and its stored assistant entry the same way.

The legacy order is not completion order. apiV2 empties the Data Output at run start, and its first addConnectToNodes call writes an entry for every source, in the order each source first appears in the flow's edge list. The worker adds entries in the order it reads the target's incoming edges, from a query with no ORDER BY. Batch rows and schedules (prepareWorkflowSeed) skip the run-start reset, so they start from the canvas order, which is the order of whichever engine ran last.

What the task does, in three parts

1The seed holds the legacy orderback/src/app-api/flux (run seed)
Before runApiV2ViaWorkflow and prepareWorkflowSeed write a seed, they run one addConnectToNodes pass over a copy of the seed nodes, as applyVariableInputsToSeedNodes already does.

The pass works on a copy, so the legacy loop does not change. A simulation on the main engine files shows that a prefilled seed keeps A, B, C even when the worker reads the edges in reverse.

⚠ How it is today

An API seed without variable inputs holds an empty textData.

✓ How it will be

Every source has its entry in the legacy order before the workflow starts.

2One run-start resetback node-output-reset.ts · apiV2 · prepareWorkflowSeed
The Data Output reset moves out of apiV2 into node-output-reset.ts, next to clearRunOutputForSeed, and both apiV2 and prepareWorkflowSeed call it.

B7b set the precedent of aligning prepareWorkflowSeed with apiV2. As a side effect, a source on a dead branch no longer keeps its canvas text on a batch or schedule seed.

⚠ How it is today

A batch row starts from the canvas order and old texts.

✓ How it will be

A batch row lists the legacy order with this run's texts.

3The worker walks sources in the legacy orderback folw/helpers/edge-projection.ts · worker projectNodeInput
The source order of addConnectToNodes becomes an exported function that sync:ported-engine ports; addConnectToNodes and projectIntoNode both call it.

The worker applies it to the run's edge list in the order the back loaded it (run_seeds.payload.edges), not to the unordered edge query. The seed is data written before the workflow starts and the projection runs in an activity, so no workflow code changes and no patched() gate is needed. Open: where the worker gets the edge order on the legacy loop's B3b path, which has no run_seeds row (B4d-D1).

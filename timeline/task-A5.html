What the task does, in four parts

1The shared provider layerworker/src/modules/ai-provider/image/
Write each provider path once, so the two nodes cannot drift apart later.

One entry per path, ported from the back's services. Behaviour port only — no redesign of provider selection. The layer is the reason the two nodes are one task: migrating them separately means writing this twice and letting the two copies diverge, which is the failure mode this epic keeps finding in the dispatch lists.

⚠ How it is today

Six provider paths live inside the engine handler, and a second node reaching the same providers would copy them.

✓ How it will be

One layer in the worker, consumed by both nodes, with one place to fix when a provider changes.

2imageGenerator: prove, flip, delete the twinflux.service.ts:1145, 6972
Move an execution that already works, without changing a single thing a customer can observe.

The module, the registry entry behind the flag, the proof, the flip, then the deletion of the handler at :6972 and the dispatch at :1145.

Prompt resolution is the detail that carries the behaviour. Seven prompt fields — prompt, subject, environment, tone, view, style, negativePrompt — with placeholder interpolation against the resolved run schema. That is the same pattern every migrated node with variable inputs already uses; it is established, not new.

⚠ How it is today

One handler chooses among six providers inside the engine process, and its billing is written from there.

✓ How it will be

An activity chooses among the same six through the shared layer, and bills through /worker/charge-tokens — with the rows proven to match.

3imageReaderNode: the half that adds executionfront/src/components/nodes/ImageReader.tsx (Run path)
Give the ninth front-driven type the dispatch the other eight get in A6 — over the layer built in Part 1.

This module sits on the same provider layer, but the work around it is different in kind: imageReaderNode is one of the nine front-driven types, so nothing executes it server-side today. It needs an engine dispatch that does not exist, and the front's Run button has to stop calling the providers directly once it does.

That is a behaviour change for existing flows, not a refactor — which is why this half waits for D3.

⚠ How it is today

In a headless run the node contributes whatever the last manual click left behind, or nothing at all.

✓ How it will be

The engine dispatches it like any other node, and the browser stops being the only place it can run.

This half is gated by D3, and D3 lives in A6

Do not answer it here. D3 asks whether the nine front-driven types running headless is a fix or a customer-visible behaviour change, and the plan treats it as a product change requiring sign-off that gates the whole wave.

Ship Part 1 and Part 2 without waiting. Part 3 starts when D3 has an answer.

4Timeouts chosen, not inheritedworker/src/modules/temporal/workflows/configs.ts
Set each provider's timeout deliberately, because image generation is slow enough that the default is a guess.

The spec is direct about it: image generation is slow enough that the default startToCloseTimeout is a guess, not a decision. Set it per provider path, in configs.ts, with the slowest real generation as the input rather than a round number.

⚠ How it is today

The inline handler waits as long as the provider takes, inside the request, with no stated bound.

✓ How it will be

Each provider path has a timeout someone chose, so a slow provider fails as a timeout instead of hanging the run.

And the wave's latency regression applies here too

Both nodes become blocking round trips until Wave 5 turns on parallelism (review §4.5, risk R4). On an image node the provider call dominates the wall clock, so the added hop is a smaller share of the total than it is for A4's reportBuilder — but measure it and state the number in the PR anyway, per DELIVERY-PLAN.

How it is proved

🔬 Verification
1
Negative control — one per provider pathrequired
For each provider path, break the selection so it falls through to the wrong provider, and confirm a test catches it. Six paths means six ways to silently call the wrong API; a suite that only exercises the default path is not protection.
2
Billing parity against real runsrequired
For the same prompt and model, the token_transactions rows written by the worker must match what the inline path wrote. Compare against real stored runs, not synthetic ones.
3
Model-access refusal, measured firstrequired
A model the user is not entitled to must produce the same refusal through /worker/validate-model-access as it does inline. PLAN §3.3.2 applies: run the check against real entitlements and drive false refusals to zero — a user refused a model they own is worse than the defect.
4
One layer, not two
Confirm both node modules consume ai-provider/image/ and neither carries its own copy of a provider call. The shared layer is the reason these two are one task — if it ends up bypassed, the task did not happen.
5
State the latency number
DELIVERY-PLAN, wave 3. Both nodes become blocking round trips until Wave 5. Measure per provider path and state the numbers in the PR.
✓ Done when
Both types satisfy PLAN §3.4, they share one provider layer, billing matches the inline path on real runs, timeouts were chosen per provider, and both inline handlers are deleted.

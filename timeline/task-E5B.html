What the task does, in four parts

1Four alarms, prod onlyCloudWatch alarms
Create the memory, keys-gap, latency and engine CPU alarms on the prod Redis, each with a recovery notification.

Decided on 2026-11-17. There is no alarm in dev or staging, because nobody acts on those alerts and both run far from every threshold. There is no Evictions alarm: under noeviction a full Redis refuses writes, which the memory alarm reports first, and CloudWatch bills an alarm for as long as it exists, even with its actions disabled.

The latency and engine CPU alarms take the highest value over the three nodes, so they keep working when another node becomes primary. The memory and keys-gap alarms read the primary, which is safe while automatic failover stays disabled.

⚠ How it is today

No Redis alarm exists.

✓ How it will be

Four prod alarms, each with a recovery notice, for USD 1.20 a month.

2A separate email topicSNS topic <code>Enhancedai-Redis-Alerts-PROD</code>
Each alarm and recovery notifies a new topic, so Redis alerts do not reach the external subscribers of the existing topics.

The recipient is the team list, decided on 2026-11-18. Out of scope: re-measuring the pub/sub rate after B5, and the automatic failover and multi-zone decision, which stays separate as in E5.

3Latency and the golden signalsCloudWatch alarms
Cover Redis latency and CPU, and record which alarm covers each golden signal.

Added on 2026-11-13, after the S4b production check found Redis command timed out in the back every day. Measured over 14 days: Redis itself is fast, with production p99 at most 2 ms and engine CPU at most 4%. The timeouts come from the back: its 250 ms timer fires late when its event loop is blocked, in one burst a day between 14:05 and 14:20 UTC, weekends included. So the two alarms stay quiet today and fire only when Redis itself degrades.

  • Latency: the latency alarm, on the server side.
  • Errors: no alarm yet. The only Redis error seen is the back timeout, and an alarm on it would fire every day until the burst is fixed in the back.
  • Saturation: memory, engine CPU and keys without a TTL. Connections stayed under 100 in prod, far from any limit.
  • Traffic: no alarm, because no threshold separates good from bad traffic.
⚠ How it is today

Nothing tells anyone when Redis gets slow.

✓ How it will be

A latency alarm and a CPU alarm in prod, and a map of each golden signal.

4One script to apply and check, and the threshold of 600<code>scripts/e5-controls/</code>
Apply the four alarms from the values recorded in the spec, and check them before and after, read-only.

apply-prod.sh runs four steps in order: check replays the four rules over the last 14 days without writing; apply asks for a typed confirmation and creates the topic, the subscription and the alarms; verify fails unless the subscription is confirmed and each alarm matches the spec; fire-test forces each alarm to ALARM and waits for it to return to OK. The user runs every AWS write.

The keys-gap ceiling is 600, decided on 2026-11-18. The count includes the Bull queue keys, so it rises while jobs wait: it stays near 150, one point reached 525 during the A9b and S8c deploy, and its highest value held for three points in a row was 391. 600 is 4 times the usual level and 53% above that peak, so a slower deploy raises no false alarm, while a writer that keeps adding keys without a TTL still crosses it.

Validated on 2026-11-17 and 2026-11-18 with nothing applied: the read-only check passed for all four alarms over 14 days, and failed on each deliberate break (a ceiling of 300, a wrong metric name, an invalid operator). A stand-in for the AWS CLI recorded 0 writes. On 2026-11-18 the user ran apply: each alarm moved to OK within two minutes.

⚠ How it is today

The thresholds and the recipient were open.

✓ How it will be

Both are recorded in the spec, and one script applies and verifies them.

Added on 2026-11-11 when E5 closed. No application code.

On 2026-11-11 dev, staging and prod all run a noeviction Redis, so a full Redis refuses writes instead of silently dropping the dedup keys. That is only an improvement if someone is watching memory, and the account has no ElastiCache alarm.

The task creates the three alarms E5 decided on, in each environment, and sends them to a new email topic per environment so Redis alerts do not reach the subscribers of the existing topics.

1

The three alarms, and what each watches

AlarmMetricRule
Memory usageDatabaseMemoryUsagePercentage, maximumAbove 50% for two periods of 300 s
EvictionsEvictions, sumAbove 0 in 300 s
Keys without a TTL outside BullMetric math: items minus volatile itemsAbove a threshold per environment
2

What the task does, in two parts

1Three alarms per environmentCloudWatch alarms
Create the memory, eviction and keys-gap alarms in dev, staging and prod, each with a recovery notification.

The keys-gap threshold is set for dev and staging; for prod it comes from a fresh TTL audit. A script prints the commands and changes nothing until it is told to apply; the person who owns the account runs every AWS write.

⚠ How it is today

No ElastiCache alarm exists.

✓ How it will be

Three alarms per environment, each with a recovery notice.

2A separate email topic per environmentSNS topics
Each alarm and recovery notifies a new topic, so Redis alerts do not reach the existing external subscribers.

Out of scope: re-measuring the pub/sub rate after B5, and the automatic failover and multi-zone decision, which stays separate as in E5.

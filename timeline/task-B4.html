allReady() returning a single id is today's behaviour. Nothing gets faster — that is the success criterion.

Two changes hide inside 'move the graph': relocating the loop, and letting it dispatch more than one node. Shipped together, a rollback cannot tell you which one broke the run. Shipped apart, each one is a one-line flag.

Sequential is also nearly free to express: allReady() returning a single id is today's behaviour. B4 builds the batch-capable machinery and configures it to a batch size of one. What it does pay back is the blocking wait — await handle.result() at flux.service.ts:507, which makes every migrated node a synchronous round trip today (analysis §9.2.2).

The decisions this task needs

One decision, and it is the one the architecture review added after the fact. The rest of this task is a port with a flag; this part is a ceiling that does not exist yet anywhere in the worker.
▸Decision B4-aOpen — needs a callWhere does continueAsNew cut the run, and at what number?
Review action #7, added to B4 after the plan was written. A Temporal workflow accumulates history events, and both the event count and the total size are capped. The worker uses no continueAsNew anywhere today, so one workflow owning an entire flow run grows with every activity scheduled and completed and every value passed — and it will be terminated by the platform on exactly the largest, most valuable customer runs (review §4.1). The spec makes two things non-optional: a boundary, and state by reference. The boundary is the open part — iteration count or node count. Pick one, state the number, and prove it by running a graph past it.
ANode-execution countrecommended
The workflow counts node executions and calls continueAsNew at a stated number, carrying the scheduler state forward by reference.
  • It counts the thing that actually produces history — every node execution is activities scheduled and completed
  • It fires on every graph shape, including a wide graph that never loops
  • It shares its unit with S4's per-run budget, so the two numbers can be read against each other instead of drifting apart
  • A single execution that passes a very large value still grows history faster than the count suggests — size is the other cap
  • The number has to be re-derived if the average activity count per node changes
Client effort: none — a continued run is still one runOurs: one counter, plus the boundary test
BLoop-iteration count
The workflow continues as new after a stated number of loop iterations — the shape that most obviously grows without bound.
  • Aims directly at the known growth case: a long loop, or an arrayNode over a big list
  • Easy to explain to whoever is debugging a run that continued
  • A wide graph with no loop at all can still exhaust history — the boundary simply never fires
  • It measures a proxy rather than what accumulates, so the ceiling is only as good as the correlation
Client effort: noneOurs: a boundary that misses wide graphs
CNo continueAsNew — lean on S4's ceilingnot viable
S4 already bounds node executions per run, and that bounds history growth. Let that ceiling be the only limit.
  • Nothing new to build in B4, and one number instead of two to keep consistent
  • S4's ceiling is deliberately set above the largest real run — so the largest real runs are exactly the ones it does not stop
  • S4's own spec calls itself 'the other half of what B4's continueAsNew is for' — a complement, not a replacement
  • The residual failure is platform termination of a customer's biggest run, which is not a failure we get to explain away
Client effort: noneOurs: the largest customer runs stay terminable
Our recommendation

A — node-execution count — with the number derived from the measurement the task already owes. Run the widest and the longest real flow available, record the event count and the history size at completion against the platform's limits, then set the boundary below that with margin and run a graph past it. State the number in the PR; a ceiling nobody wrote down is not a ceiling.

B is not wrong so much as partial: it aims at loops, and loops are only one of the two shapes that exhaust history. If loop iterations turn out to dominate in the real measurement, A still catches them — the reverse is not true.

Whichever boundary wins, the second requirement is not negotiable: state by reference, never by value. The workflow carries the ids B1 settles, and the payloads stay in Postgres and S3. Passing a resolved input through workflow state puts node output into the history and reintroduces the same failure from the other side.

What the task does, in three parts

1The workflow owns SchedulerStatenew flow workflow · scheduler.ts from B2
Everything the API's loop does with the scheduler, the workflow does — with a batch size of one.

The workflow owns the state, calls allReady(), dispatches, and applies markCompleted / markDead / completeCondition as results arrive.

allReady(state): string[] is added alongside nextReady, draining every eligible id and marking each scheduled. nextReady stays — mcp-write.service.ts:1327 uses the scheduler too and is not part of this epic.

The back's role shrinks to three things: start the flow workflow, serve the callbacks it already owns — billing, model access, S3, file generation — and read the result. It stops being the loop. A flag selects engine-in-back versus engine-in-workflow, per flow, defaulting to back.

⚠ How it is today

The API's loop calls nextReady, dispatches one node, and blocks on await handle.result() before asking for the next one.

✓ How it will be

The workflow calls allReady() and dispatches the batch it returns — configured to one. Identical order, no blocking round trip through the back.

What stays out

Batch size above one — that is B5, in the next wave. Control flow and sub-flows — B6. Deleting the back's loop — C1/C2, after this has soaked. The backend loop stays in place through this whole wave and is only removed in Wave 6.

2History is a storage medium, and it is boundedreview §4.1 — a gap found after the plan was written
Two requirements, and neither is optional: continueAsNew at a boundary, and state carried by reference, never by value.

A Temporal workflow accumulates history events, and both the event count and the total size are capped. The worker uses no continueAsNew anywhere today. One workflow owning an entire flow run therefore grows with every activity scheduled and completed and every value passed — and it will be terminated by the platform on exactly the largest, most valuable customer runs.

The second requirement is where the wave's tasks meet: the id-based transport from B1 is what makes by-reference possible. The workflow carries ids; the payloads stay in Postgres and S3. Passing a resolved input through workflow state would put node output into the history — the same failure by another route.

⚠ How it is today

No continueAsNew anywhere in the worker. A run's history grows with every activity and every value passed, until the platform terminates it — biggest runs first.

✓ How it will be

The workflow continues at a stated boundary and carries ids, not payloads. The ceiling is a number someone wrote down and proved by running a graph past it.

3A skipped node has to be loudflux.service.ts:4735–4778 · flux/node-cancel-watch.ts
The characteristic failure of a scheduler port is a node that is silently never run.

The back warns today when a node ends outside completed or dead (flux.service.ts:4735–4778). The workflow needs the equivalent, because unprocessed-node detection must survive the move.

The related property is failing fast. A graph engine whose failure mode is 'hangs for thirty minutes until the Temporal timeout' is not shippable — the stall has to be detected by the engine, not by the platform. Cancellation must also still work end to end, including the in-flight flag in flux/node-cancel-watch.ts; E2 is what makes that native rather than ported.

⚠ How it is today

The back warns about a node that ended outside completed or dead. In a workflow-owned run, nobody is watching for it.

✓ How it will be

The workflow detects the stall itself and says which node it was, instead of waiting for the Temporal timeout to end the run.

For a corpus of stored flows, assert the workflow executes nodes in the same order the back's loop does, node for node. With batch size one this must be exact: any divergence is a defect in the port, and this is the last moment it is cheap to see.

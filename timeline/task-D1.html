Starting point
An audit, not a blank page
docs/worker/ is already populated — and it describes a system more migrated than the one that runs.

The registration chain is seven layers and all of them are load-bearing: module, enum entry, temporal.module.ts, activities.service.ts, the worker.service.ts binding, the workflows/configs.ts proxy, and the process-single-node.workflow.ts case.

Miss one and you get a node that appears to run and does nothing, or a workflow that throws "Node type X not supported" from the default branch. That failure is invisible in review and obvious only at runtime — which is exactly why this is a task and not a README line.

What the task does: the audit, then six subjects

1The audit — production, branch, or intentiondocs/worker/**
Establish, page by page, which system each existing page is actually describing.

This is not greenfield. docs/worker/ is populated and must be audited and extended, not recreated. Two gaps are visible from the listing alone: the node/ pages document types the back does not route — sql-querier and audio-transcriber are A3's stranded modules — and pt-br/ contains only environment-variables.mdx.

So the docs already describe a system more migrated than the one that runs. The spec also lists mcp among them; the re-validation of 2026-08-24 records that mcpNode shipped completely, which moved that page from intention to production without anyone editing it. That is exactly the drift the audit exists to catch — in both directions.

⚠ How it is today

A reader cannot tell whether a page describes production, a branch or a plan — and two of the documented node types are not routed by the back at all.

✓ How it will be

Every page states which of the three it describes, and the audit result is recorded — that record is part of the definition of done.

Not to be confused with decision D1

This page is task D1 — developer documentation. Decision D1 in PLAN.md §7 is a different thing entirely: shared package versus copy-port for the scheduler and the substitution service. It belongs to B2 and it gates Wave 4.

Same letter, unrelated subjects. Anyone writing about either should say which one they mean.

3How to add a node type — the seven layersthe registration chain
Turn the chain into something a person follows while working, with the failure each omission produces.

The seven layers, in order, each with the failure its omission produces. Written as a checklist someone can follow while working, not as an essay — the reader is mid-task with an editor open, not reading for background.

The two failures to name explicitly are the ones the chain actually produces: a node that appears to run and does nothing, and "Node type X not supported" thrown from the default branch of the workflow.

⚠ How it is today

Seven load-bearing steps live in the heads of the people who have done it, and the omission is invisible until runtime.

✓ How it will be

A checklist with the failure attached to each step, tested by someone who had never done it before.

4Callback reference and error taxonomy/worker/* callbacks · NodeError subclasses
Document the two contracts a node author gets wrong most expensively.

Callbacks: /worker/store-payload, /worker/get-payload, /worker/validate-model-access, /worker/charge-tokens, /worker/generate-file, plus whatever A7 adds. Request, response, when to use, and when not to. The first two — the claim check — have no page in the listing above at all.

Errors: UserConfigError, IntegrationError, ProviderError, TimeoutError, SystemError — which to throw when, and what each does to retries. Getting this wrong makes a user's typo retry for thirty minutes, which is the sort of defect that looks like an outage and bills like one.

⚠ How it is today

The claim-check callbacks are undocumented, and the retry consequence of each error class is folklore.

✓ How it will be

Both are reference pages: every callback with its request and response, every error class with what it does to retries.

5Persistence contract — and why parallelism is safeown-row writes · JSONB merge · claim check above 256 KB
Write down the property the whole parallel plan rests on, before Wave 5 depends on it being understood.

Own-row writes only, the JSONB merge, and the claim check above 256 KB — and why this is what makes parallelism safe. A node author who writes into another node's row breaks a guarantee they never knew they had, and the failure appears much later, in a parallel run, as a lost update.

⚠ How it is today

The rule exists in the code and in the review, and a new node module can violate it without anyone noticing until a parallel run.

✓ How it will be

The rule is stated with its reason, so the person about to break it reads why the shortcut is not one.

6Running and debugging locallydocker-compose.devdb.yaml · Temporal · node_executions
Get a developer from “it did not work” to the actual failure without asking someone who already knows.

The docker-compose.devdb.yaml stack, finding a run in Temporal, reading node_executions, and the worker's log surface. development.mdx exists; the listing carries no page for the other three, which are exactly the steps someone needs at the moment a node silently does nothing.

⚠ How it is today

Debugging a local run is passed on verbally, so the newest person is the slowest at exactly the failure that is hardest to see.

✓ How it will be

One page: bring the stack up, find the run, read the row, read the log. In en and pt-br, like every other page here.

How it is proved

🔬 Verification
1
Negative control — and it is a real one hererequired
Have someone who has not done it add a trivial node type following only the page. If they produce a node that silently does nothing, the page is wrong — that is the failure to look for, because it is the one the seven-layer chain actually produces. Record what they hit.
2
Every reference resolves, and the SHA is statedrequired
Every file path and line reference is checked against the current code at the time of writing, and the commit SHA is stated on the lifecycle page. A stale line number in documentation is worse than none: it sends the reader to confidently wrong code.
3
The audit is recorded, not just performed
Which existing page described production and which did not — written down. The node/ pages for the stranded modules are the ones to state explicitly, in both directions.
4
env-vars-sync if any page documents an env var
The skill keeps .env.example, the audit README and the Mintlify environment pages in step. A documented variable that exists in only one of the three is the next stale page.
✓ Done when
The audit is recorded (which existing page described production and which did not), the six subjects are covered in en and pt-br, someone unfamiliar has added a node type using only them, and every reference resolves. Each A-track task adds its own node's page as part of PLAN §3.4 point 7 — this task does not backfill them at the end.

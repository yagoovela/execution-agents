Decide voiceNode

Decide, on a measurement, whether voiceNode is removed from the legacy single-node surface or kept with a stated reason — and record which. A1 removed neither, because the measurement that settled the other three phantom types never looked at this one.
PR #1991 · Merged to `production` 2026-09-23 (`a90d1ae6`). Measured 2026-09-22 against production and dev, read-only, all time, with `commandTextNode` and `voiceBoxNode` as control rows: `voiceNode` is 0 stored nodes on live canvases (prod control 41,868 / 338), 0 in version history, 0 in the deprecated pre-migration `flows.nodes` JSON across 14,818 prod flows (controls 14,270 / 273), and 0 executions. Decided **removed** from both places — the registry entry is deleted and the shared `case 'voiceBoxNode': case 'voiceNode':` arm is split so `voiceBoxNode` keeps its handler. The `node_executions` zero is deliberately not the deciding number (its window only opens 2026-08-23); `validateNode()` reads the type off the stored node, so `flows_nodes` plus the pre-migration JSON column leave no window a `voiceNode` could hide in. It was never a front node type in the whole history of `nodeTypes.tsx`. Opposite verdict from `comment`/`label`/`group` on purpose: that is the permissive prefetch whitelist, this is a live endpoint's accept list. Negative-controlled twice — the half-removal the task asked for went red on the drift spec, and re-adding the entry turned all 5 new assertions red, then green again at 246 passed. The production snapshots keep `voiceNode` verbatim; the departure is declared in a named `MEASURED_REMOVALS` list with a companion test that the removal is real.

Added 2026-09-22, split out of TASK-A1 on the day A1 shipped. A1's Scope instructed the removal of four phantom types. Three of them — comment, label, group — were measured and the removal was reverted: the prefetch executor already skips them, so whitelisting them is precisely what stops a canvas decoration from costing a flow its prefetch eligibility, and removing them would have been a false refusal.

voiceNode was never measured at all. It could therefore neither be removed nor declared safe, and shipping it either way on the strength of a measurement that did not look at it would have repeated the error A1 had just finished recording. That is the whole reason this task exists as a task instead of a line item.

It is registered in no node-type source — not front/src/util/nodeTypes.tsx (46 types), not back/src/app-mcp/node-types/node-type-metadata.ts (50 entries). Nothing in the product can create one today. Yet two live places still trust it.

This is not the prefetch whitelist, and that difference is the point. The prefetch whitelist is permissive — an extra entry costs nothing, which is exactly why removing the other three would have been the harmful move. This is the accept list of a live endpoint, so the asymmetry runs the other way: if no stored node carries the type, the arm is dead surface and removing it shrinks the legacy endpoint (what C2 wants); if some old flow does carry one, removing it turns a request that works today into a refusal.

What the task does

1Measure, with a control rowproduction, read-only
Two questions, because a type can be stored without ever being called, and called without being stored.

Does any stored node carry type = 'voiceNode' — in flows_nodes, live canvases and version history, since a legacy request can name a node from an old version? And did any node_executions row with that type ever run, how recently?

Include a control row for a type known to be present (e.g. commandTextNode), so an empty result set cannot be mistaken for a measured zero. A1's D5 measurement did exactly this, and it is what made its zeros worth trusting.

2Decide, and write the decision downTASK-A1C-VOICENODE-PHANTOM.md
Either outcome is valid. What is not valid is applying one silently in code.

Remove the accept verdict and the switch arm, or keep the type with a note stating why and on what evidence. Record the numbers alongside the decision, the way A1 recorded D5's.

3Let the existing drift spec catch a half-removalnode-dispatch-invariants.spec.ts
A1 already pins the switch arms against the registry, so the two places cannot diverge quietly.

The spec asserts the switch handles exactly registeredNodeTypes().filter(legacyEndpointAccepts) plus the known-unreachable arms. Dropping the arm while leaving accept in the registry — or the reverse — fails the suite. Confirm that is what actually happens before trusting the change.

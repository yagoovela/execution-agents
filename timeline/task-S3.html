Shape
Two limits, one counter
A spend ceiling on the chain root, and a per-org concurrency cap. The counter is shared with S4.

Spend. assertCompletionCredits (product.service.ts:265–284) is a boolean gate: for INTRO products it checks trialTokens > 0; otherwise, having a subscription is enough. Per node, getUserProductFromFlow checks entitlement to a model, not remaining budget. Charges are recorded after the fact into token_transactions. Nothing decrements an allowance, and nothing aborts a run that has already overspent.

Tenancy. There is no per-tenant concurrency cap anywhere. Today it is masked: the Bull processor declares @Process with no concurrency option (apiV2Job.processor.ts:33), so each backend replica runs one queued run at a time. That accidental serialisation is doing real protective work — and B5 removes it deliberately.

The decisions this task needs

Three calls have to be made before this ceiling can be written, and two of them are visible to the customer. Each one below opens to the options considered, what each costs the customer and costs us, and the option we would pick.
▸Decision S3-aPLAN D7Recommended — confirmWhen a run hits its cost ceiling, does it abort, degrade, pause, or only warn?
The spec states this as an assumption: the run aborts rather than degrades. It is worth confirming out loud, because the alternatives are all things a product team can reasonably want — and three of them either produce output the user did not ask for or leave a run in a state nothing owns.
AAbort with a typed errorassumption
The charge call refuses, the run ends, and the error carries the ceiling and the spend so the UI can say what happened.
  • Honest and cheap to explain — the run stopped, and here is the number it stopped at
  • The failure lands at the moment the money would have been spent, not at the invoice
  • A typed error is something the front can render specifically, instead of a generic failure
  • A long run that was nearly finished is lost, and the spend up to that point is real
  • Whatever the run was going to deliver does not arrive — so the ceiling has to be right, which is what the measurement is for
Client effort: raise the ceiling, or split the flowOurs: one check where the charge already is
BDegrade to a cheaper model
On reaching the ceiling, the run continues on a smaller or cheaper model instead of stopping.
  • The run finishes, and the customer gets something
  • Spend keeps falling instead of stopping dead
  • It hides the problem and produces output the user did not ask for — the flow named a model on purpose
  • A silent quality change is the worst kind of surprise in an automation something else consumes downstream
  • Every node type would need a defined fallback, and some have none
Client effort: discover it happenedOurs: a fallback matrix per node type
CPause and ask
The run suspends at the ceiling and waits for the owner to approve more spend.
  • No work is thrown away, and the decision goes to the person who pays
  • It is the right answer for an expensive, long, human-supervised run
  • A background execution system has nobody watching at 3 a.m. — a paused run is an abandoned run
  • It needs a resume path, a timeout on the pause, and a place in the UI that does not exist yet
  • Held state costs something: a paused run occupies a slot in the tenancy cap while it waits
Client effort: be there to answerOurs: a resume path and a new run state
DWarn onlyfirst deploy
Emit the metric and the notification at the ceiling, and let the run continue.
  • No run is ever refused, so there are no false refusals to measure
  • It is the correct first stage of the rollout — see the recommendation
  • On its own it is not a ceiling. It is a smoke alarm wired to nothing
  • The unbounded-spend risk this task exists to close stays open
Client effort: noneOurs: the exposure stays open
Our recommendation

A, with D as the first deploy. Ship the counter, the metric and the notification with enforcement off. That is what makes the historical replay below possible against live traffic, and it is what PLAN §3.2 asks for anyway: the new path lands disabled and is flipped in a separate deploy.

The spec already requires both limits to emit a metric before they emit an error. A ceiling nobody can see being approached will be discovered by being hit.

B is the one to reject explicitly rather than leave on the table. Degrading is a silent product change made by an infrastructure control, and the person who notices is the one reading the output a week later.

▸Decision S3-bPLAN D9Recommended — confirmAt the per-tenant concurrency cap, is the extra run queued or rejected?
Note the deliberate contrast with S7 and D11, where a caller over the rate limit gets a 429. The two look like the same question and are not. At admission, the caller may not be entitled to anything at all, and queueing an unbounded inbound flood only moves it. Here the caller is already entitled to the work — the organisation has runs to execute and the fleet is busy. Rejecting would turn a capacity limit into an error the customer sees.
AQueue the excessassumption
Runs over the cap wait at admission and start when a slot frees. The limit becomes latency, not failure.
  • Latency is the correct trade for a background execution system — nobody is holding the phone
  • No client-side retry logic, and no run is lost
  • The same submission behaves identically whether the fleet is busy or idle
  • A queue with no ceiling of its own is a way to hide a much larger problem
  • “Queued” has to be visible, or a slow run and a waiting run look the same to the customer
Client effort: noneOurs: a queued state the UI must show
BReject over the cap
The submission is refused and the customer is told to try again later, the way S7 refuses at the rate limit.
  • Immediate, unambiguous feedback
  • No queue to size and no hidden backlog
  • It turns a capacity limit into an error the customer sees, for work they are entitled to run
  • A scheduled or webhook-triggered run has nobody to retry it — the work is simply lost
Client effort: handle a refusal, or lose the runOurs: nothing to queue
CA global cap only, with no per-tenant splitnot viable
Bound the total number of concurrent runs across the fleet without asking whose they are.
  • Protects the fleet with a single number
  • It is a fairness bug, not a capacity control — one organisation's wide graph can hold the whole cap and starve every other tenant
  • The review is explicit that a global-only cap is too weak
Client effort: noneOurs: starvation, with a limit in place
Our recommendation

A, and make the waiting visible. Queueing is only the correct trade while the customer can tell a queued run from a stuck one — otherwise the fairness fix is delivered as a mystery.

Write the contrast with S7 down where both are implemented. Two limits in the same codebase, one rejecting and one queueing, will look like an inconsistency to the next person unless the reason is next to the code: at admission the caller may not be entitled to anything, and here they already are.

▸Decision S3-cRecommended — confirmIs the default ceiling a global constant, a column on the product, or a per-org value?
The spec's assumption is that the default is derived from the plan, not from a global constant — a single number is wrong for both ends of the customer range. This is also the decision that determines whether the historical replay below has one threshold to test or one per plan.
AA column on the product, overridable per orgassumption
The ceiling lives on the product with a conservative default, and an org-level override handles the exceptions a plan cannot express.
  • A single number is wrong for both ends of the customer range
  • The override is the pressure valve that keeps a false refusal from becoming an escalation
  • It sits next to the entitlement checks that already read the product
  • A migration, and a value to backfill for every existing product
  • The measurement has to be replayed per plan, not once
Client effort: none, unless they need an overrideOurs: a column, a migration, a per-plan replay
BOne global constant
A single ceiling for everyone, read from the environment.
  • One number to set, and one number to replay against history
  • Ships without a migration
  • Low enough for the smallest plan is far too low for the largest customer, and the reverse
  • The first exception makes it a per-org value anyway — informally, and in code
Client effort: the wrong ceiling for most of themOurs: one env var
CPer-org only, with no plan default
Every organisation carries its own ceiling, set when it is onboarded.
  • Exactly right for every customer, by construction
  • A new organisation with no value set has no ceiling — which is the failure mode being fixed
  • It becomes a manual step in onboarding, and manual steps get skipped
Client effort: noneOurs: an unbounded default by omission
Our recommendation

A. The important half is the default: a plan column with a conservative value means a new product is bounded on the day it is created, and the per-org override means a false refusal is a support action rather than a deploy.

Out of scope, and worth saying out loud: this task does not change pricing, plan structure, or how charges are computed. The ceiling reads numbers that already exist.

What the task does, in four parts

1The ceiling belongs to the chain, not to the runTASK-S1 · D13
Stop nesting from multiplying the ceiling, and build one accountant instead of two.

S1 settles that a sub-flow gets its own run identity plus a parentRunId. That makes a per-run ceiling defeatable by nesting: five levels buy five ceilings, and recursion becomes the way around the limit.

So the charge call has to resolve the chain root and account against it. This is cheap — the chain is already needed for depth, cycle and cancellation — but it has to be stated, because a ceiling that recursion can multiply is not a ceiling.

One counter, two limits. S4 needs the same chain-root accounting for its node-execution budget. Build it once and carry both units — cost and executions — rather than two accountants that resolve the chain independently and can disagree about where the root is.

⚠ How it is today

The ceiling does not exist at all; and if it were added per run, every sub-flow call would reset it. Nesting would be the documented way to spend without limit.

✓ How it will be

One counter, resolved at the chain root, carrying cost for this task and node executions for S4. Nesting adds to the total instead of starting a new one.

Where the root is resolved must be one answer

Two accountants that each walk the chain will eventually disagree about the root — on a retry, on a partially-written chain, or when a sub-flow is cancelled mid-way. One resolution, read by both limits.

2The check goes where the charge already isback/src/temporal/worker.controller.ts:126
Put the ceiling in the one call that keeps working after the loop moves into the worker.

The ceiling is checked at charge time, in the same call that already records the spend. Two reasons, and the second is the one that matters for this epic:

  • It is the cheapest place — the number is already being computed and written
  • It is the only place that keeps working once the worker owns the loop. A check inside the backend engine loop stops being on the path the moment B4 moves that loop

It also needs no new plumbing: /worker/charge-tokens already carries execId.

⚠ How it is today

assertCompletionCredits answers “may this account run at all”, once, and charges land in token_transactions afterwards with nothing reading the total back.

✓ How it will be

Every charge is checked against the chain total before it is recorded, and the abort carries the ceiling and the spend.

3The tenancy cap, enforced where runs are admittedback/src/jobs/apiV2Job/apiV2Job.processor.ts:33
Keep one organisation from occupying the fleet once the accidental serialisation is gone.

A cap on concurrent runs per organisation, enforced where runs are admitted, with excess runs queued rather than rejected.

The reason it is not needed today is an accident: @Process is declared with no concurrency option (:33), so each backend replica runs one queued run at a time. B5 removes that on purpose. Until then the fairness bug is latent; after it, one organisation's wide graph can occupy the whole worker fleet.

Both limits emit a metric before they emit an error. A ceiling nobody can see being approached will be discovered by being hit — and the first person to discover it will be a customer.

⚠ How it is today

No per-tenant cap exists anywhere in the flux or job paths. One queued run per backend replica is the only thing standing in for one.

✓ How it will be

Concurrency is capped per organisation at admission, the excess waits instead of failing, and the approach to both limits is visible before either is reached.

Out of scope

Changing pricing, plan structure, or how charges are computed. This task adds a ceiling over numbers that already exist.

4Check the credit before the run, not on each nodeD19 · D20 · the pre-flight gate S1 already runs
Refuse work that was never going to finish, before any of it is paid for.

The ceiling is not a property of a node evaluated at dispatch time. S1 already runs a gate between building the DAG and starting to spend, and S4 already validates the graph there; extend that gate to credit. Does this flow need credit, and is there enough — asked once, before anything runs.

Refusing there turns a bill into an error message. It is also the reason the registry does not need a per-type can this spend flag: nothing has to be classified at dispatch time if the question is answered before dispatch begins.

⚠ How it is today

Nothing is asked before the run. The first signal that a flow could never afford itself is the charge it already made.

✓ How it will be

The gate asks once, before spending. A flow with no credit fails with a message instead of a partial bill.

It does not replace the charge-time ceiling

A pre-flight check answers can this flow spend, never will it — the branch taken depends on data that does not exist until the run happens. That is the same argument S4 makes for keeping a runtime budget, and it applies here unchanged. The two answer different questions and both are needed.

How it is proved

🔬 Verification
1
Negative control — spendrequired
Build a flow that loops until it exceeds the ceiling, run it with the check disabled, and record what it costs. Then enable it and confirm the run aborts at the ceiling with the spend and the limit in the error. The first half of that test is the justification for the second.
2
Measure before refusingrequired
PLAN §3.3.2, and here it is load-bearing. Compute what the proposed ceiling would have done to every real run in the stored history. Any run that legitimately completed and would now be aborted is a false refusal, and that count must be zero before this ships. Report runs whose cost cannot be reconstructed as unverifiable, not as passing.
3
Tenancy — and the starvation it prevents
Two organisations, one submitting a wide graph: assert the second one's run still starts within a bounded wait. Then remove the cap and watch it starve — that is the fairness bug, and seeing it is what makes the cap defensible.
4
The metric fires before the error does
Confirm that approaching each limit is observable before it is hit — not only that the refusal is logged. A ceiling whose only signal is the failure teaches nobody anything until it has already cost a run.
✓ Done when
A run cannot exceed its ceiling, no historical run would have been falsely aborted, one tenant cannot occupy the fleet, and both limits are observable before they are hit.

The back refuses thirdPartyIntegration on the legacy single-node endpoint, which the old front still calls. No node execution moves: the task classifies, and fixes what the classification exposed.

The registry can say worker or inline, but it cannot say "does not execute". B4's gate (canUseWorkflowForFlow, back/src/app-api/flux/engine-selector.ts) accepts a flow only when every node has flowDispatch: 'worker' or is one of five hard-coded passive types. An unregistered type fails the gate. So a Data Input, a sticky note or a Small Memory node keeps the whole flow on the back's loop, and the loop can never be deleted.

Eighteen front or MCP types have no registry entry. The front's nodeTypes has 46 keys; the MCP's NODE_TYPE_METADATA has 50, the 46 plus four MCP-only types. The "does not execute" rule lives in four hand-kept copies that do not agree: the prefetch copy has three types on purpose, and the gate, the apiV2 log and the worker's NON_EXECUTABLE_TYPES (behind a "Keep in sync" comment) have five. A spec binds the registry to the prefetch copy; nothing binds the three five-type copies.

What the task does, in nine parts

1An execution field on every entryback/src/shared/node-dispatch/node-dispatch-registry.ts
Give every registry entry one of six values, classified from the code that reads or writes the type at run time, not from its name.

In a run, every value comes from one of two places, and no node writes into another: the run seed (run_seed_nodes, the canvas snapshot plus the bound run inputs) and the node_executions rows of that runId. A source has a value that the projection resolves, from the seed when nothing feeds it or from its upstream producer when it is a pass-through. A visual node has no value, and its edges carry nothing.

sink and state are roles, not a location. They stay true after A13 and A14 move the work into the workflow; each of those tasks changes the gate to accept its class, and nothing else. Every back, sink or state entry names its owner task in handoffOwner, and the drift spec fails on one without it, so a new exception cannot land without an owner.

execution sits next to flowDispatch; it does not replace it. C2 removes flowDispatch when it deletes the back's loop. The class is registry metadata: node data stays as it is, and the projection resolves through the edge, not through a display node's cached textData.

⚠ How it is today

The registry says worker or inline. A type that does not execute has no value to say so, and 18 types have no entry.

✓ How it will be

Every canvas and MCP type has a class, and every exception names its owner.

Out of scope — later steps of the same model

The scheduler stops scheduling source and visual nodes and links a consumer straight to the producer behind a pass-through. It changes classifyEdge and buildSchedulerState in both engines together, and a conditionNode that prunes a branch must also prune the consumer behind it.

A display node shows its producer's value instead of a copy. It reads the producer's canvas row, not node_executions, because production slims run rows after 7 days and deletes them after 30. C1 needs this in place first.

2A source that feeds a node fails today — fix the projectionworker process-flow.workflow.ts · project-node-input.ts
Make a source deliver its value under B4, fixed or pass-through, before the gate accepts it.

The workflow skips a passive node and marks it completed without a node_executions row. The projection then puts it in completedSourceIds, and project-node-input.ts throws missingSourceError before it reaches fromSeed, which would have delivered the right value. A spec pinned the throw with a textBox source. So under B4, textBox → commandTextNode already fails; dev has engine_in_workflow off, so nobody hit it.

The fix keeps skipped source and visual nodes out of the completed set given to the projection, so the projection walks past them: to the producer's row for a pass-through, or to fromSeed for a fixed value.

tableProcessor and dynamicSettingsNode leave the back-only projection list (changed 2026-10-29). The worker projection test serves both from the run seed and matches the back's modifyData, and a dev read (a11-q5-backonly-shape.sql) confirmed the shapes the tests use. The gate keeps only the class check, and a drift test fails if a type still flagged backOnlyProjection is ever accepted by class.

Open item — display nodes under B4

Under B4 nothing copies a producer's output into a display textBox or richTextBox, so the canvas may stop showing it once the flag is on. Check this on the local stack before the flag goes on in production. The fix is the second later step in part 1, and C1 is its natural owner.

3No path runs an integration node inlineflux.service.ts · legacy-node-dispatch.ts · worker payload builder
Class thirdPartyIntegration and hubSpotCRM as worker, and replace every inline fallback with a refusal.

Every real provider already goes to the worker. The front offers ten providers and nine are in the registry's integrationProviders; the tenth, microsoft, is only the account connection card, and its Excel, Word, PowerPoint, OneDrive and Outlook work already runs in the worker. What fell inline was a node with an empty, unknown or differently-cased provider: it got Unknown provider, and the next node received empty text. On dev, 7 of 37 nodes did.

  • Both types get flowDispatch: 'worker' and execution: 'worker', and the contract is regenerated.
  • The inline fallback in the main loop and in executeSingleNode becomes a user-facing error that names the missing provider.
  • Both get legacyEndpoint: 'refuse-migrated', and the thirdPartyIntegration case in dispatchLegacyHandler is deleted.
  • The worker trims and lowercases the provider in the payload builder, so the adapter lookup and payload.provider see one value. A spec binds the worker's adapter keys to the registry's providers.
  • The apiV2 loop keeps its literal node.type === 'thirdPartyIntegration' branch, because flux.service.worker-dispatch.spec.ts finds each worker type by that literal. C2 deletes the loop.
Owned elsewhere

A7 owns the arrayNode loop body, which has no branch for either type and writes a false success; once A11 sets them to worker, A7's registry-driven dispatch reaches them. S9 (868mpn1h3) owns runtime credential authorization: the worker resolves an integrationId without checking that the executing user may use it.

4Derive every dispatch list from the fieldengine-selector.ts · is-non-executable.ts · node-input-projection.ts · sync-ported-engine.ts
Replace the hand-kept dispatch lists and the gate's literal types with values read from the registry.

Derived from execution: the three five-type passive copies, the worker's NON_EXECUTABLE_TYPES, BACK_ONLY_PROJECTION_NODE_TYPES in back and in the worker's port, and the B4 gate, which accepts a flow when every node is worker, source or visual. The worker imports nothing from back: it gets the class map as a dependency-free back file in PORTED_ENGINE_FILES, checked by the ported-engine drift spec.

Every visual type is prefetch-safe (changed 2026-10-29). stickyNote, nodesGroup and the four deprecated types join comment, label and group, so a decoration no longer costs a flow its prefetch eligibility. NON_EXECUTABLE_NODE_TYPES is now the visual class, and the production oracle declares the six additions in MEASURED_PREFETCH_ADDITIONS.

⚠ How it is today

Four copies of the passive list, one of them in another repository behind a "Keep in sync" comment.

✓ How it will be

No hand-kept dispatch list remains. The gate, the log, the prefetch check and the worker read one source.

Out of scope

Type lists that answer other questions are not dispatch verdicts and stay: DATA_SINK_TYPES, SIDE_EFFECT_TYPES, node-output-reset.ts, node-abort-capability.ts, agent-node-catalog.ts and the worker's TEXT_PASSTHROUGH_TYPES.

5Remove the four deprecated types, and never let a saved one block a flownode_types.enum.ts · node-type-metadata.ts · flow-node.service.ts · the front placeholder
Take webNews, webMedia, webLocations and varInputForm out of the product, while the 47 saved nodes on dev keep working.

Changed 2026-10-29: the four leave the back's NodeType enum as well as the MCP metadata, the per-type tables in back, front and the worker's ports, and the seeder's "Sales funnel" flow. They stay in one deprecated list in the dispatch registry, as visual entries. No front component renders them and no code executes them.

A saved node of these types must not stop anyone from opening, reading, editing, saving, copying or restoring a flow:

  • Front. A placeholder says the node type was removed and lets the user delete it, instead of hiding it. It uses the back's wording, and a back drift spec fails if the two diverge.
  • Back. PATCH /flow/add-node refuses a new node of a deprecated type; every update, copy, version and import path, POST /flow and the external api-flows create included, keeps accepting an existing one.
  • MCP. get_agent and get_run_nodes mark the node as deprecated, check_agent_integrity lists it without failing ok, and add_node, update_node and connect_nodes refuse it. Every other edit works, remove_node included.
  • Runs keep skipping it, on both engines. The back CLAUDE.md section "Removed node types" describes every path that carries one.

Bug found on main and fixed here. toNodeEntity (flow-node.service.ts) resolves every node type through the MCP catalog, which already hid the four. So a full save of a flow that holds one failed with "Unknown node type: webNews", and the front, which filtered the node out on load, then deleted it on its next full-graph save without telling the user. A11 keeps a deprecated type as stored, and deprecated-node-persistence.spec.ts covers the full save, the data-only save and the version paths.

Later — owned by C2 (wave 6)

C2's section 4 counts the saved nodes live and in version history on production, deletes them and their edges through an internal endpoint with a dry run, and only then removes the deprecated list, the validator rule, the MCP marker and the front placeholder.

6Editor chain runs reach the next nodefront useTemporalFlowExecution.ts · flowTriggerTokens.ts · Node.tsx
Make the node menu's chain runs work, through one driver and one route.

The node menu's two chain commands write data.flowTrigger on a node; the node runs, and its completion writes the trigger on the next node. The local E2E on 2026-10-29 found that this chain stopped after the first node for every runnable type except outputController, on main too.

  • The hook types dispatched to POST /process/single-node, which passes no execId; the worker cast ''::uuid and threw, so the hand-off never fired. Seven other types went to the legacy single-node endpoint, which refuses webSearch, mcpNode, reportBuilder, audioReaderNode and, since A11, thirdPartyIntegration with a 422.
  • AiTextGenerator, WebSearch and ProcessCounter ran a step but never handed off; McpClient had no chain run; Large Memory dispatched twice; the voice node never ran; the run-from-here command skipped the node after the clicked one.

Decision: useTemporalFlowExecution is the only chain driver of the 18 components that call it. It dispatches through /flux/execute-single-node, the route the Run button uses, which checks access, writes the node_executions row, returns an execId and honours the open version. A component with its own Run handler passes it as runNode, so a chain step flushes local edits like its Run button. Every new trigger gets a dispatchToken that only the tab that created it can claim, once, so a stale trigger saved in the database or a second open tab runs nothing. A removed node type is walked through, not run. The legacy run list was left empty and deleted. The server-side "run from node" was rejected as one to two days of change to both schedulers.

Left as on main

Twelve other components still run their own chain step from a flowTrigger effect, without the token check, among them OutputControllerNode, DecisionPaths, FlowCaller and TableProcessor. They are not in the D3 scope, and moving them needs the same per-component proof. A follow-up task decides it.

7A drift spec, and the end state as testsfront/src/util/nodeTypes.tsx · node-type-metadata.ts · node_types.enum.ts
Make the next unregistered type fail a test instead of quietly keeping flows on the back's loop.

The rule that prevents the next gap. A drift spec fails when a type exists in the front's nodeTypes.tsx, in node-type-metadata.ts or in the NodeType enum without a registry entry, when a derived list disagrees with the registry, and when a back, sink or state entry has no handoffOwner. Back CI checks out one repository, so the spec reads the committed NODE_HANDLE_REGISTRY and reads the live front only when FRONT_REPO_PATH or ../front exists.

The end state as tests. Three expected-failure tests (it.failing), each with the task that turns it into a plain test:

  • No type is classed back — turned plain by C2, when the last one leaves.
  • The gate accepts a flow that holds a sink — turned plain by A13.
  • The gate accepts a flow that holds a state node — turned plain by A14.
8Two fixes found on the wayflow-version.controller.ts · back/scripts/generate-node-handle-registry.ts
Fix two defects that the local E2E and the A11 front imports exposed.

The versions list no longer fails without paging parameters. GET /flow/:flowId/versions declared page: number = 1, but the global ValidationPipe turned a missing value into NaN, so TypeORM failed with a 500. DefaultValuePipe plus ParseIntPipe now give page 1 and page size 10. The front always sends both values, so users did not see it.

The handle registry generator no longer depends on import order. It followed every relative import from a node component and cut each closure at 80 files or depth 8, so the voice node's import of the settings modal broke node-handle-registry.spec.ts. The closure now stops at src/views, Modals, settings and Integrations, the limits are 400 files and depth 20, and a closure that reaches them throws instead of being cut. The largest is 199 files. The base front and the A11 front generate the same registry, so connect_nodes accepts the same handles as before.

9Deploy order: worker, then front, then backworker · front · back
Ship the three repositories in the one order where no step breaks a run.

Worker first: a back without the A11 worker would send source and visual types that the old worker does not skip. Front before back: the back moves thirdPartyIntegration to refuse-migrated on the legacy single-node endpoint, and the front on main sends chain steps of that type there. The new front only calls /flux/execute-single-node, which the back on main already serves.

Known effect

A tab that still runs the old bundle after the back deploy gets a refusal on a thirdPartyIntegration chain step until it reloads.

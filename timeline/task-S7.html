Authenticate and rate-limit the entry points

A run can only be created by someone entitled to create it, and no caller can create an unlimited number of them.

Three of the four ways to start a run are effectively unauthenticated — the webhook route, the email trigger for public flows, and the email trigger for private flows via a forgeable From header. None of the four is rate limited.

Every other ceiling in this epic — the sub-flow depth limit, the execution budget, the tenant spend cap — sits behind admission. If anyone can open the door an unlimited number of times, none of those ceilings is a guarantee.

The decisions this task needs

These are the calls that have to be made before the code is written. Each one opens to the options considered, what each costs the customer and costs us, and the option we would pick.
▸Decision S7-aOpen — needs a callHow does the webhook secret travel, so the customer does not have to build an auth system?
The spec says “a per-flow webhook secret” but never says where it goes. That is this decision. The framing that matters: this is not “add authentication”, it is stop using a non-secret identifier as the secret. Today the credential is the flowId — a UUID that travels through published interfaces, chatbot routes, shared links and the MCP surface. It is secret by accident, and it cannot be rotated because it is the primary key. Whatever we pick below, the flow id leaves the URL and a rotatable token resolves the flow.
AToken in the URL pathdefault
POST /flux/hooks/<token> — the customer copies one URL and pastes it. The token resolves the flow; the flow id never appears.
  • Works in every tool, including the ones whose only field is “URL”
  • This is what Zapier, Make, Trello and Asana do — the URL is the credential
  • Rotating it is re-copying a URL, not a code change
  • Bearer secret in a URL: it reaches ALB access logs, APM traces and error trackers unless actively scrubbed
  • Anyone who sees the URL can trigger the flow
Client effort: paste a URLOurs: log scrubbing is mandatory
BSame token, in a headeralready the pattern
The customer sends the token as a request header. This mechanism already exists — ApiKeyGuard reads headers['api-key'] today (apikey.guard.ts).
  • Does not land in access logs, Referer or analytics
  • No new transport to build — the guard pattern is already in the codebase
  • Some callers cannot set headers at all — a CRM field, a legacy form, a no-code step
  • Alone, it excludes exactly the customers this task is trying not to burden
Client effort: one headerOurs: reuses the existing guard
CHMAC signatureopt-in
The caller signs the body with a shared secret and sends the digest, the way Stripe and GitHub webhooks work. We verify the signature and a timestamp.
  • The secret never travels; a captured request cannot be replayed
  • The answer a customer's security team will ask for by name
  • Requires the customer to write code — the exact demand this task exists to avoid
  • Cannot be the default without breaking every no-code caller
Client effort: an implementationOurs: one verifier
Our recommendation

All three, as a ladder on one token — A is the default and nobody is forced to climb. A customer who can only paste a URL is safe; a customer who can set a header is safer; a customer with a security team gets HMAC. One secret, three transports.

Prefer path over ?token=: query strings leak in more places by default — Referer, proxy logs, analytics, and error trackers that capture the full req.url. Accept both for compatibility, but document and show the path form.

Four things make a URL token defensible rather than a shortcut: one token = one flow (a leak costs one flow, not the account), two active tokens at once so rotation is not a breaking change, one-click revocation, and log scrubbing — the one that bites, because the ALB access log records the full path into S3.

▸Decision S7-bRecommended — confirmWhat is public: true allowed to permit on a trigger?
Today this is not a decision anyone made — it is an artefact of a broken where. The first branch of the OR has no public condition, so the second is dead and every flow matches. Fixing the predicate forces the question the code was never asked: does “public” describe who may read a flow, or who may spend its owner's money?
APublic means readable, never executablerecommended
Execution always requires the token, public or not. public keeps governing discovery and the published interface, and nothing else.
  • One rule for every trigger — nothing to reason about per flow
  • A leaked flow id stops being a spend vector entirely
  • Matches what customers already assume “public” means
  • If any customer relies on an open trigger today, this breaks them — the deprecation window has to find them first
Client effort: noneOurs: fix the predicate
BAn explicit “anyone may trigger” setting
A separate per-flow switch, off by default, distinct from public. Turning it on requires a rate limit and a spend ceiling on that flow.
  • Keeps the genuinely open use case — a public form, a demo, a status hook
  • The owner opts in knowingly, with the cost cap in the same screen
  • A second concept to explain, document and support
  • An open trigger is a spend vector by design — the caps become load-bearing
Client effort: one toggleOurs: UI + caps + docs
CLeave it as it isnot viable
Keep the current behaviour, in which the public flag has no effect on the webhook route and every flow is triggerable by id.
  • Breaks nothing today
  • It is the live defect this task exists to close
  • Private flows stay executable by anyone holding an id that was never treated as a secret
Client effort: noneOurs: the exposure stays
Our recommendation

A, with B available only if a real customer asks for it. Do not ship B speculatively: an open trigger is a spend vector, and every one that exists has to be watched.

Whichever is chosen, write it down — the point of this decision is that today nobody can say what public was supposed to mean here, and the next person to read the where clause will guess again.

▸Decision S7-cRecommended — confirmHow is the email sender verified, without asking anyone to configure anything?
Agents are started by email too. The flow is resolved from a UUID in the recipient's local part (mail.service.ts), then From, Subject, the body and the attachments are fed into the flow's varInputNode. For a private flow the only check is that the From header matches the owner — and greps for dkim, spf, dmarc in app-api/mail/ return nothing. For a public flow there is no sender check at all.
AThe address is the credentialrecommended
<token>@upload.fluxprompt.com — a high-entropy token, not the flow id. Possession of the address is the authorisation. This is Trello's and Asana's email-in pattern.
  • Zero configuration for the customer — they save a contact
  • Enforceable in this codebase today; does not depend on the mail provider's headers
  • Rotates per flow, and stops leaking the internal flow id
  • Email addresses leak by nature — CC, reply, forward, saved in someone's contacts
  • Rotation is more disruptive than a webhook URL: the customer may have automations pointing at it
Client effort: save an addressOurs: token lookup instead of a UUID regex
BVerify DKIM / SPF / DMARC
Check the authentication results at the mail boundary before the message is trusted, so a forged From is rejected on its own merits.
  • The standard answer, and the only one that makes From mean anything
  • Composes with A — it can be added later without undoing it
  • Depends on headers the mail provider supplies, and on its configuration
  • Legitimate senders fail DMARC often enough that this refuses real traffic — mailing lists, forwarders
Client effort: noneOurs: provider-dependent
CSender allowlist per flowpairs with A
The owner types which addresses may trigger this flow. The message must come from one of them and reach the secret address.
  • Cheap for the customer, and it is a control they understand
  • Turns a leaked address into a much smaller problem
  • From is forgeable, so alone it authenticates nothing
  • Only defence in depth — never the primary control
Client effort: type addressesOurs: one list field
Our recommendation

A now, C alongside it, B later. A is the primary control and it is the one that costs the customer nothing. C composes with it for free and shrinks the damage when an address inevitably leaks. B is the more standard answer and can be layered on afterwards without undoing either.

One correction to the spec as written: it proposed <flowId>+<token>@…. Drop the flow id. Keeping it exposes an internal identifier and makes the address partly guessable, for no benefit — the token can resolve the flow on its own.

▸Decision S7-dRecommended — confirmAt the limit, does the caller get a 429 or does the run get queued?
The Bull processor's concurrency (AGENT_CONCURRENCY, default five per replica) already throttles execution. It does not throttle admission — the queue still grows, and a row, a log line and a dedup key are written for every call on the way in. This decision is about what happens at the door.
AReject with 429 and Retry-Afterrecommended
Excess calls are refused before anything is written. The caller is told when to come back.
  • Queue depth and row count stop growing — which is the entire point
  • 429 + Retry-After is what every webhook client already knows how to handle
  • A legitimate caller above the limit loses that call unless it retries
Client effort: honour a 429Ours: a throttler guard
BAccept and queue
Admit everything and let the queue absorb the burst, the way S3 handles excess tenant runs.
  • No legitimate call is ever lost
  • No client-side retry logic needed
  • Queueing an unbounded inbound flood just moves it — the writes still happen
  • The failure arrives later and further from its cause
Client effort: noneOurs: the growth is unbounded
Our recommendation

A — and note the deliberate contrast with S3. There, excess tenant runs are queued, because that caller is already entitled to the work. Here the caller may not be entitled to anything at all. Admission is the one place where rejecting is the right answer.

Both halves of this task refuse customer traffic, so PLAN §3.3.2 applies: count real calls per flow and per key over a full cycle, set the limits above the observed peak with margin, and run in report-only mode first. A legitimate caller refused is a production incident, not a test failure.

What the task does, in three parts

1The webhook entry pointflux.controller.ts
Close a route that lets anyone who knows a flow id execute that flow and charge its owner.

POST /flux/api-v2-webhook is @Public() (flux.controller.ts), so it opts out of the global auth guard. It then resolves the flow like this:

where: [ { id: query.flowId }, { id: query.flowId, public: true } ]

The first branch of the OR has no public condition, which makes the second one dead: any flow matches, public or private. The rest of the handler contains no secret, no token and no ownership check — only if (!flow).

Anyone who knows a flow id can execute that flow and charge its owner. The only barrier is that the id is a UUID — and flow ids travel through published interfaces, chatbot routes, shared links and the MCP surface.

⚠ How it is today

Anonymous POST with a flow id starts a run on a private flow. No secret is checked, no owner is checked, and the bill lands on the flow's owner.

✓ How it will be

A per-flow webhook secret is verified before anything else runs, and the public predicate is corrected so the two branches actually mean different things.

Decision to write down

What is public: true supposed to permit here? If public flows are meant to be webhook-triggerable by anyone, say so explicitly and cap them under Part 2 — do not leave it as an artefact of a broken where.

Migration matters more than the fix

Existing integrations call this URL today. Ship the secret as optional, with a deprecation window and a metric counting unauthenticated calls per flow, then enforce.

Turning it on cold breaks every customer webhook silently, and the failure looks like “my automation stopped” rather than “my webhook is unauthenticated”.

2Rate limiting, on every entry pointflux.controller.ts
Cap admission by the thing that pays, so a flood is refused at the door instead of being written to the database first.

There is no ThrottlerModule, no @Throttle and no ThrottlerGuard anywhere in back/src. Every run-creating route accepts unlimited requests: /flux/api-v2 (API key), /flux/api-v2-webhook (public), /flux/batch-process and /flux/execute-from-canvas.

The Bull processor's concurrency (AGENT_CONCURRENCY, default five per replica) throttles execution, not admission — the queue still grows, and rows, logs and dedup keys are written on the way in.

Scope. Limits keyed by the thing that pays: API key, organisation, and flow for the webhook route. Not by IP, which is meaningless for server-to-server callers.

⚠ How it is today

Unlimited requests are accepted and persisted. Refusing later, in the queue, still costs a row, a log line and a dedup key per call.

✓ How it will be

Excess calls get 429 with Retry-After before anything is written. Queue depth and row count stop growing.

Assumption to confirm — reject, do not queue

Admission is the one place where rejecting is right: queueing an unbounded inbound flood just moves it.

Note the deliberate contrast with S3, where excess tenant runs are queued — there the caller is already entitled to the work.

3The email triggermail.service.ts
Stop trusting a header anyone can type, and decide what a public flow's email address is actually allowed to do.

Agents are also started by email. mail.service.ts resolves the flow from the local part of the recipient address — the format the service itself advertises is uuid@upload.fluxprompt.com — then feeds From, Subject, the body and any attachments into the flow's varInputNode and enqueues a run.

Its authorisation is the weakest of the four entry points:

  • Public flow → no sender check at all. Anyone who emails the address runs the flow, charged to the owner, and controls the prompt — which, in a flow containing a push node or an integration, means driving side effects with the owner's credentials.
  • Private flow → the sender's From header is matched against a user and compared to flow.user. Greps for dkim, spf, dmarc and authentication-results in app-api/mail/ return nothing, so nothing verifies the message came from the address it claims. The check is a request for the attacker to type the owner's email address — which is not secret.

Scope. Verify the sender — DKIM/SPF/DMARC at the boundary, or move the secret into the address (<flowId>+<token>@…) so possession of the address is the credential. Either is defensible; trusting From is not.

Decide, and write down, what a public flow's email trigger is allowed to do. “Public” should probably mean readable, not “anyone may spend the owner's tokens and drive their integrations”. If public email triggers stay, cap them explicitly under Part 2 and treat their input as untrusted for any node with side effects.

Keep the existing bounce-back replies — telling a sender “flow not found” or “unauthorized” is good behaviour, and it is already there.

⚠ How it is today

A message with the owner's address typed into From passes the private-flow check. A public flow does not even check that much.

✓ How it will be

Possession of a per-flow address token — or a verified DKIM/SPF/DMARC result — is what admits the message. A typed From admits nothing.

Assumption to confirm — address token over DKIM

The address-token option is preferred: it is enforceable in this codebase today, does not depend on the mail provider's headers, and rotates per flow.

DKIM verification is the more standard answer and can be added later without undoing it.

The decision this task needs

One call has to be made before the first merge, and it is about the route rather than the code. It opens below with the options, what each costs the customer and costs us, and the recommendation.
▸Decision A2-aOpen — needs a callStaging is behind production for this file. Do we fix staging, route around it, or promote through it as it is?
The spec makes this a precondition, not an afterthought. As of 2026-08-21 back@origin/staging still carried the pre-release six providers while production carried eight — staging is behind its own destination for this file. A promotion routed through it is not a rehearsal: it will either re-break production by carrying the older list forward, or silently pass and prove nothing. This set is six node types and two providers at once, so it is the worst possible release to rehearse badly.
ABring staging up to production firstrecommended
Reconcile staging with production for this file before the promotion branch touches it, so the soak happens against a real pre-production state.
  • The soak means something again, and the “re-break or silently pass” fork simply disappears
  • Whatever made staging drift is found now, while one file is involved, instead of during a release with eight changes in flight
  • Every later task in the epic inherits a staging that can be trusted
  • It is a second reconciliation stacked on the one this task already owns
  • It needs whoever owns the release route to confirm the drift was not deliberate — that is a person, not a command
Client effort: noneOurs: one extra reconciliation, up front
BRoute around staging, as the mcpNode line evidently did
Promote develop → PR to production, and accept that staging is not on this path. Analysis §10.3 is explicit that whatever route the 2026-08-21 release took, it did not go through staging.
  • Demonstrably a route that works — a complete node type reached production through it
  • No second reconciliation, so the task stays the size the plan assumed
  • The promotion loses its rehearsal, on the largest single coverage change in the epic
  • It makes the drift permanent: the next task inherits a staging that is further behind than this one found it
  • If it is the real route, it is undocumented — and an undocumented route is one person's knowledge
Client cost: an unrehearsed release of eight changesOurs: nothing extra
CPromote through staging exactly as it isrejected
Merge the promotion into the stale branch and ship from there, treating the soak as green because it was green.
  • Nothing to decide and nothing extra to do
  • This is the case the spec names: the older provider list travels forward and re-breaks production
  • Or the merge resolves in production's favour and the soak proved nothing — reported as a green gate either way
  • A green gate that means nothing is worse than no gate, because the next release trusts it more
Client cost: a possible production regressionOurs: a gate we can no longer trust
Our recommendation

A — and confirm the cause before choosing, because the confirmation is one conversation. “Is staging deliberately out of the path for this file?” has an owner, and asking is cheaper than discovering.

If the answer turns out to be yes, then B is not a workaround — it is the documented route, and this task should write it down as one. What must not happen is C by default: merging into a branch that is behind production and calling the result a soak.

What the task does, in three parts

1Find out what is blocking the merge, before mergingorigin/chore/merge-868k8twjb-develop-20260805
A branch that has survived a whole release cycle unmerged is telling you something. Assume “merge conflict” only after looking.

Then create the reconciliation branch and merge both lines. Expect conflicts: the dev branches moved a long way while the migration was in flight.

Union resolution — keep both sides, lose no code. -X ours is banned here; it produces a clean merge that silently discards a side, which is the one failure mode this reconciliation cannot survive. The policy was already paid for once and written down: worker-thirdparty-integration-migration/DEV-RECONCILIATION.md. Follow it rather than rediscovering it.

⚠ How it is today

Six finished modules sit on a branch that has reached no environment, and no written record says why.

✓ How it will be

The two lines are reconciled with every side kept, the blocker is named, and the six are on a branch that ships.

Scope — what this task does not do

No change to what those modules do. If a module fails the definition of done, that failure becomes its own task — do not fix it inside the promotion. A promotion that also repairs things cannot be reverted by not promoting, and “revert by not promoting” is the entire reason this task is cheap.

2Verify the registration chain — then verify the back side existsworker/src/modules/nodes/nodes.types.ts
A worker module with no registry entry on the back is a stranded module — the exact defect A3 exists to clear. Do not create two more of them.

Confirm the merged nodes.types.ts has every enum entry, and that each one has its full registration chain:

  • The worker module itself
  • The activity
  • The binding
  • The workflow proxy
  • The case in process-single-node.workflow.ts

Then the half that is easy to skip: confirm the back actually routes it. If it does not, the registry entry is added here, behind the flag from PLAN §3.2 — added disabled, proved, and flipped in a separate deploy.

Each of the six, and both providers, is measured against PLAN §3.4's seven-point definition of done. A node is not done when its activity exists.

⚠ How it is today

The worker half exists and was presumably tested when written. Nothing has ever checked whether the back would route to it.

✓ How it will be

Every one of the eight is checked on both sides, and the check is the A1 registry rather than a reviewer's memory.

3Ship it — and prove the inline twin does not also firedevelop → staging → PR to main
The failure mode of a promotion is not “it does not run”. It is “it runs twice”.

The route is develop → soak → staging → soak → PR to main, with the staging question answered first.

PLAN §6 R1 names the risk in this exact shape: a node routed to the worker whose inline twin still fires — a duplicated charge, a duplicated message. It is rated critical, and this task turns on six node types and two providers at once. With the flag on, the inline handler must not fire, and that has to be log-asserted rather than assumed.

⚠ How it is today

Six finished modules exist and never run. The nodes execute inline, exactly as they did before the modules were written.

✓ How it will be

They run in the worker — once — with the activity visible in Temporal and the inline path proven silent.

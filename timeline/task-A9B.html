Added on 2026-11-11 from A13, re-scoped on 2026-11-12, reviewed on 2026-11-13, in production since 2026-11-18.

Fifteen async runs were reported stalled from 2026-11-04 to 2026-11-12, and every one fell on a back production deploy. Each run had started on the old ECS task, which kept taking Bull jobs while it drained. That task's PID 1 was a shell that did not forward SIGTERM, so ECS killed node with the run in flight, and the new task then reported the stall. In 4 of the 15 runs, a node that the worker was still running finished and was charged after the stall, about 7,000 credits in total, while the run ended error with no outputs.

The task was first written for a frozen process that resumes after its stall report and delivers a second time. That case occurred 0 times in 15, but stays reachable through a lost Bull lock. So on 2026-11-12 the task was re-scoped: stop deploys from killing runs first, then make every end of a run go through one claim. On the B4 path a deploy charges the whole run and still reports error, which is why this task blocks the B4 flag.

What the task does, in five parts

1Graceful shutdownback/dev.sh · back/src/main.ts · api-task-definition-prod
SIGTERM reaches node, the process takes no new job, and a legacy run gets up to 100 s to finish.

dev.sh ends with exec node and starts the database seed under setsid; the task definition sets initProcessEnabled, so an init process is PID 1, forwards SIGTERM to node and reaps orphans (A9b-D7). exitAfterClose closes the app and exits with 0. A new BullShutdownService pauses every instance of each consumed queue, and the api-v2 processor waits at most 100 s for its jobs that are not B4 jobs, then closes its queue.

The container's stopTimeout is 120 s, the Fargate maximum, and the target group's deregistration delay drops from 300 s to 180 s (A9b-D8). The api-v2 job timeout becomes the run ceiling plus 1 h instead of 600 s.

⚠ How it is today

A shell is PID 1; node is killed with the run in flight.

✓ How it will be

node pauses its queues, waits for its runs and exits with 0.

2One terminal outcome and the stored planflow-execution-status.service.ts · mcp-run-status.service.ts
Every writer claims the run's end through a compare-and-set on its status; the first claim wins (A9b-D3).

The claim returns whether it won, and the MCP run status gets the same guard. The winner stores the run's delivery plan in end_delivery, cleared once its delivery has started (A9b-D12). A loser writes no status and only starts the winner's stored plan, so a winner that dies before its delivery starts is still delivered. The run's end delivery uses the run id as its invocation id, so a retried end does not deliver twice (A9b-D10).

⚠ How it is today

Both ends deliver; the MCP status keeps whichever writes last.

✓ How it will be

One status and at most one delivery, whichever end comes first.

3Legacy stall: interrupt, recorded cost, child runsapiV2Job.processor.ts · stalled-run-cleanup.service.ts
A legacy run that lost its process interrupts its steps in flight and records its real cost, with no refund and no resume (A9b-D4, A9b-D5).

Two recompute passes, at 5 min and 35 min, are scheduled before the claim, so a throw after the claim still leaves them (A9b-D14). Library and flow-caller child runs list their run ids in a Redis set of their parent, which the recompute reads (A9b-D11). No one writes a cancel request at a stall, because a cancel on the root run id would also stop the run's triggerOnly children (A9b-D15).

⚠ How it is today

The run ends error with a recorded cost of 0 while the ledger holds every charge.

✓ How it will be

After the final pass, the recorded cost equals the run's charges.

4B4: the worker triggers the finishworker process-flow.workflow.ts · back flux.service.ts
A B4 run keeps its live end, and any live back finishes it when its handler is gone (A9b-D6).

At its end, processFlow calls a finish activity. The back writes a reduced end only when no live handler holds the Bull job, so a run whose back task died is finished with no back waiting for it. Library and flow-caller children stay on the legacy loop until B6 (A9b-D13). A plain Error in processFlow code now fails the workflow with a non-retryable ApplicationFailure instead of retrying its task forever (A9b-D16). A batch row whose processFlow child fails now finishes its run as error.

⚠ How it is today

The worker charges every node, nothing writes the end, and the stall report marks the run error.

✓ How it will be

Any live back writes one status, at most one delivery and a cost equal to the charges.

5No run stays unfinishedunfinished-run-reaper.service.ts · flag unfinished_run_reaper
A cron closes any async run in_progress past its limit, or pending past 24 h, and stops its processing (A9b-D9).

The limit is the run ceiling plus 30 min, or the flag's value when it is larger. The cron also starts every stored plan that no one started, and skips a run while Temporal cannot be reached. A row older than 7 days is closed with status, error and cost only, with no callback and no email, and each tick reads at most 100 rows per select, oldest first (A9b-D17). Its error texts are fixed messages in the tone of the stall message (A9b-D18).

A seed migration creates unfinished_run_reaper off, and it stays off in production after the release: turning it on is a separate decision. Production held 49 runs in_progress for over 7 days on 2026-11-17; the first tick after the flag goes on closes them with no callback.

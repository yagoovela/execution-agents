Measure, then one call
Added on 2026-10-23 from the node coverage audit. One node type, nothing else.

A6 listed webTrends among the front-driven types, in stage 1, and shipped without it. No decision was recorded. The front still calls SerpService directly from WebTrends.tsx, so the node never runs in a flow: it produces output only when a user clicks Run in the builder.

This task closes that gap one way or the other. It measures real usage first, and then either migrates the type as A6 migrated its siblings, or retires it from the canvas and the MCP metadata.

The decisions this task needs

One call, and the spec does not make it in advance: measure, then either migrate or retire. The numbers from part 1 decide it.
▸Decision A6b-aOpen — needs a callMigrate webTrends to the worker, or retire it?
Today the type sits in neither state: it is on the canvas and in the MCP metadata, but no engine executes it. The spec accepts either answer, as long as the decision and its numbers are recorded and the type ends up worker or removed.
AMigrate it, as A6 migrated its siblings
Follow the same three-part scope as A6: an activity, engine dispatch for the first time, and the Run button routed through POST /process/single-node with the direct SerpService call deleted.
  • A6 counted it as almost free: the SerpApi client is already in the worker, inside web-search
  • Flows that hold it stop using whatever the last manual run left behind
  • It is a behaviour change for any stored flow that holds the node: it starts producing fresh output
BRetire it
Remove the type from the canvas and from node-type-metadata.ts, so no new flow can hold it.
  • No new activity, no new dispatch, nothing more to maintain
  • Stored flows that hold it lose the node, so the measurement has to show how many there are first
Where it stands (2026-10-23)
Open: the worker owner confirms migrate or retire before the work starts, with the usage numbers from the scope.

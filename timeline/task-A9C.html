Worker and task definitions
In production since 2026-11-19 (worker #174, worker-task-definition-prod:106).

No worker task definition set stopTimeout, so ECS killed the worker 30 s after SIGTERM, when its 30 s grace ended. At that moment the Temporal SDK cancels every activity in flight, and two helpers turned that cancel into a cancel the workflow did not ask for: runCancellableNode settled textGenerator and apiCaller as cancelled, and runNodeActivity re-threw the abort. No node activity retried: every one ran with one attempt, except largeMemory.

The production query of node durations over 30 days set the values: 17 % of textGenerator runs (1,827 of 10,703) last over 100 s, so the drain alone does not save them, while apiCaller never passed 62.3 s, so the drain covers almost every activity that writes to a customer system.

What the task does, in four parts

1A 100 s drain on a worker deployworker/src/modules/temporal/temporal.constants.ts · worker-task-definition (dev, staging, prod)
The worker sets shutdownGraceTime 100 s and shutdownForceTime 110 s, and each worker task definition sets stopTimeout 120 s, the Fargate maximum.

A release script registers a revision from the live one with only stopTimeout changed, and refuses during a rollout or when the latest revision is not the live one. It ran on dev, staging and prod before the worker code shipped. A spec keeps grace < force < stopTimeout ≤ 120 s.

⚠ How it is today

ECS kills the worker at 30 s.

✓ How it will be

In-flight activities get up to 100 s.

2The WorkerShutdown failureworker/src/modules/nodes/shared/worker-shutdown.ts
One helper, failIfWorkerShutdown, reads the SDK's cancellation details when an attempt sees an abort.

When the workflow asked for the cancel, a user cancel wins and the node ends cancelled with its partial charge, as before. Otherwise, on a worker shutdown, the attempt fails with a retryable WorkerShutdown failure. Both runCancellableNode and runNodeActivity call it before their own abort handling.

⚠ How it is today

A deploy cancel looks like a user cancel.

✓ How it will be

A deploy cancel is a retryable failure.

3One retry per proxy group, only on a worker lossworker/src/modules/temporal/workflows/retry-policies.ts · configs.ts
Each proxy belongs to one class: safe, provider-cost, keyed or not-safe. The long safe and provider-cost proxies and largeMemory get two attempts.

A retry fires only on WorkerShutdown or a heartbeat timeout: every node error category and a start-to-close timeout are non-retryable. not-safe proxies (apiCaller, thirdPartyIntegration, mcp, pushData, fileSave, counter, sqlQuerier, scripting, completion) keep one attempt, so a deploy never sends a second request to a customer system. The customer is charged once: the workflow's charge runs after the final attempt, and the four activities that charge inside themselves rely on the unique index on the charge.

⚠ How it is today

Every node activity has one attempt.

✓ How it will be

A cut activity that is safe to repeat runs once more.

4A heartbeat for displayBox, a retry-tolerant largeMemory deleteworker/src/modules/temporal/activities/activities.service.ts · nodes/large-memory/large-memory.service.ts
displayBox reached 301 s in production, so it beats through the keep-alive heartbeat with a 30 s timeout.

On a retry attempt, a largeMemory delete that finds no file counts it as already deleted; on the first attempt it fails as before. Its non-retryable list now names the category strings.

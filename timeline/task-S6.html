Watch-out
It refuses network traffic
The most disruptive kind of refusal there is. PLAN §3.3.2 is not a formality here — it is the gate.

/downloader?url= takes a user URL (downloader.controller.ts:34), and the scraper, api-caller and crawling paths take user URLs too. Searching those modules for private-range or metadata blocking — 127.0.0.1, 169.254, localhost, isPrivate — returns nothing.

This is pre-existing; the epic did not create it. But the epic moves these callers into the worker, which sits in a different network position while holding the database password and the integrations encryption key — and today the tasks that do the moving say nothing about it.

Four things a policy has to get right

What the policy must doThe bypass it closesIf it is skipped
Check the resolved address, not the stringA hostname the attacker controls that resolves to a private addressDefeated by one DNS record
Block loopback, link-local, private and unique-local by default169.254.169.254 — the cloud metadata endpoint — and internal hostnamesThe textbook SSRF
Re-check on every redirect hopA permitted host that 302s to a blocked addressThe standard bypass
Keep a per-organisation allowlistNot an attack — the failure here is oursThe policy gets disabled wholesale
The list above is what the spec settles. What it deliberately leaves open is the shape of the policy and the worker's network position — and the second one decides whether this whole epic is moving URL fetchers into a safer place or a more dangerous one. Both are below, with what each option refuses and what it lets through.

The decisions this task needs

▸Decision S6-aOpen — needs a callWhat shape does the egress policy take — and what does each shape actually refuse?
The spec fixes three properties and one escape hatch: check the resolved address, not the string; block loopback, link-local (including 169.254.169.254), private ranges and unique-local by default; re-check on redirect; and keep a per-organisation allowlist so a policy with no exception path does not get disabled wholesale. It does not fix the shape. That is this decision, and it is the one that decides what stops working — so PLAN §3.3.2 applies with full force: this rule refuses network traffic, which is the most disruptive kind of refusal in the product.
ADeny-list on the resolved addressthe policy
Resolve the hostname, check every resolved address against the blocked ranges, refuse if any matches, and repeat on each redirect hop. An organisation can allow a specific internal host.
  • Refuses the textbook case and almost nothing else — the smallest refusal surface, which is what PLAN §3.3.2 asks for
  • One rule at the fetch layer both repos share, rather than a check per node that the next node forgets
  • The escape hatch exists, so the first legitimate internal endpoint does not become a reason to turn the policy off
  • It is check-then-connect: between the check and the socket the name can resolve to something else — see option D
  • A customer's genuinely internal endpoint is refused until someone adds it to the allowlist
Client effort: none, unless they fetch an internal hostOurs: one fetch layer, in two repos
BAllowlist per tenant — deny everything elsenot viable as a default
Each organisation declares the hosts its nodes may fetch. Anything not declared is refused, private or public.
  • Strongest containment — an unknown host is unreachable even if the range check has a hole
  • Makes the blast radius of a tampered node configuration very small
  • It refuses the product's normal use: a crawler, an api-caller and a summariser exist to fetch a URL the user just typed
  • The false-refusal count starts near 100%, and PLAN §3.3.2 says drive it to zero
  • Every new URL becomes a support request
Client effort: declare every host firstOurs: a registration UI, and the tickets
CA central egress proxy that enforces the policyinfra option
Both repos fetch through a proxy that owns the rule. The application stops deciding; the network position enforces it.
  • One enforcement point for back, worker and anything added later — a new fetcher cannot bypass it by picking a different HTTP client
  • The report-only cycle produces a single log, in one place, instead of two repos' worth
  • Infra work with a deploy per environment, and it becomes a hard dependency on the run path — if the proxy is down, every fetch is
  • It does not by itself answer the rebinding question, which still lives in whoever resolves the name
Client effort: noneOurs: infra, per environment, on the run path
DResolve, pin, connect — rebinding-safe by constructionthe mechanism
The resolver returns the addresses, the policy checks them, and the connection is made to the address that was checked rather than re-resolving the name. Every redirect hop repeats it.
  • Closes the gap A leaves open: the string, the DNS answer and the socket cannot disagree
  • It is what makes “check the resolved address” actually true rather than nearly true
  • An HTTP-client-level change in both repos — a custom agent or resolver, which some clients make awkward
  • On its own it is not a policy: it is the mechanism a policy needs
Client effort: noneOurs: a resolver in two HTTP layers
Our recommendation

A as the policy, D as its mechanism. They are not competing options — A decides what is refused and D decides that the refusal cannot be walked around between the check and the connection. Shipping A without D produces a control that reads correct and is defeated by a DNS record the attacker owns.

C only if the network-position decision below puts the worker behind a proxy anyway. As a standalone project it buys one enforcement point at the price of a new single point of failure on the run path; as a by-product of a restricted subnet it is nearly free.

B is not viable as a default and is listed so the option is refused on the record rather than in a corridor: fetching a URL the user just typed is the product. Keep its shape for the per-organisation allowlist, where it belongs — as an exception path, not the rule.

Whatever is chosen, the measurement is the same and it is not optional: sample the real URLs stored in node configurations, classify each as would still work or would now be blocked, drive the second to zero, and treat anything unresolvable as unverifiable, not blocked. Then run report-only for a full cycle before enforcing.

▸Decision S6-bOpen — needs a callWhere does the worker sit, and what is it allowed to reach?
The spec makes this an explicit deliverable, not a background assumption: “a decision on the worker's network position, written down: which subnet, which instance role, what it can reach.” It is what decides whether relocating the fetchers is an improvement or a regression. The worker holds the database password and the integrations encryption key, and review §3.2 says whether the move is better or worse depends entirely on its subnet and its instance role. The three options below are not preferences — they are the three possible answers, and the first job is to find out which one is true today.
AThe worker reaches less than the APIaim for this
A subnet whose egress is limited to what the activities actually need, and an instance role scoped to the worker's own resources. The relocation is then a documented security improvement — and the spec says to state it as one.
  • Turns an unknown into a stated improvement: a compromised fetcher reaches less than it does today
  • Writes the sentence review §3.2 says the tasks currently lack
  • Defence in depth: a bug in the code-level policy is no longer a full SSRF from a privileged host
  • Someone has to enumerate what the activities legitimately reach — providers, Temporal, the API, storage — and keep the list current
  • A missing entry looks like a node failure rather than a network refusal, unless the error says which it is
Client effort: noneOurs: enumerate egress, and keep it current
BThe worker reaches the same as the API
No network change. The code-level policy from S6-a is the only control, and the relocation is risk-neutral by construction.
  • Nothing to deploy — the move genuinely changes nothing about the exposure
  • Honest and quick to write down, which is most of what this decision is for
  • The worker still holds the database password and the integrations key with unrestricted egress, so a policy bug is a privileged SSRF
  • One control, no depth: the code-level policy has to be right the first time
Client effort: noneOurs: a policy bug becomes a privileged SSRF
CThe worker reaches more than the APIcompensate first
The spec's own branch: the move needs compensating controls before it ships — scope the instance role, restrict the subnet, or hold the relocated fetchers until the network position changes.
  • The one branch where relocating without changes would be a regression, caught before it ships rather than after
  • It gives A6 and A8 a concrete precondition instead of a vague worry
  • The nine front-driven types and the extraction activity wait on infra work
  • The waiting is invisible unless someone states it as a dependency on the wave plan
Client impact: headless execution waitsOurs: infra work before A6 and A8 ship
Our recommendation

Look it up before the first relocated fetcher ships, and write the answer into the task. This is the rare decision whose first half is a fact, not a preference: compare what the API can reach with what the worker can reach, today, in each environment.

Aim for A. It is the only branch where the move makes things better rather than merely not worse, and it is the branch that lets the epic say out loud that migrating a URL fetcher into the worker was a security improvement.

If the answer is B, say so plainly and accept that S6-a is the only control. If it is C, then A6 and A8 do not ship their fetchers until the controls exist — which is exactly what both tasks already say, and this is where that sentence gets its meaning.

What the task does, in three parts

1One policy, at the fetch layer both repos sharedownloader.controller.ts:34 · app-api/{scraper,api_call}/ · worker HTTP layer
Put the rule where every fetch passes, so a node cannot opt out of it by being written later.

Not per node — per fetch layer. The fetchers this epic relocates are webCrawling, webAmazon, secApiNode, usCensusNode, documentSummarizer and fileSave (via /downloader), plus apiCaller, which is already in the worker. A per-node check would have to be added seven times and remembered an eighth.

⚠ How it is today

Every one of those paths accepts a user URL and connects to it. Nothing resolves it, nothing classifies the address, nothing looks at the redirect.

✓ How it will be

One policy object, consulted by the shared fetch layer in both repos, on the first request and on every redirect hop.

2Measure, then report-only, then enforcePLAN §3.3.2
Make sure the rule refuses only what it is supposed to refuse, before it is allowed to refuse anything.

This rule rejects network traffic, which is the most disruptive kind of refusal in the product: the customer does not see “blocked”, they see a node that stopped working. So the sequence is fixed:

  • Sample the real URLs stored in node configurations, and classify each as would still work or would now be blocked.
  • Drive the second count to zero before enabling anything. A legitimate URL refused is worse than the defect being fixed.
  • Anything unresolvable is unverifiable, not blocked — report it as unknown rather than counting it as a pass.
  • Report-only for a full cycle: log what would be blocked, and only then enforce.

Auditing every existing customer URL is explicitly out of scope. This is the measurement, not a remediation project.

⚠ How it is today

No rule, so no false refusals — and no true ones either. Every internal address is reachable from a node configuration.

✓ How it will be

A rule that ran for a full cycle in report-only mode with a known false-refusal count of zero before it started refusing anything.

3The worker's network position, written downinfra network/subnet definitions
Answer the question the review says the moving tasks currently do not even ask.

Which subnet, which instance role, what it can reach. If the worker can reach less than the API, moving these fetchers is a security improvement and should be stated as one. If it can reach more, the move needs compensating controls before it ships.

That is decision S6-b above. Its first half is a lookup, not an opinion — and it has to happen before A6 and A8 relocate a fetcher.

⚠ How it is today

Nobody can say whether the worker reaches more or less than the API, so nobody can say whether the migration improves or worsens this exposure.

✓ How it will be

The position is documented per environment, and the epic can state which of the two it did — with the answer, not with a hope.

An allowlist with no exception path is a policy that gets turned off

The per-organisation escape hatch is not a weakening of the policy — it is what keeps the policy alive. Some customer will have a legitimate internal endpoint, and a control with no way to say yes to it gets disabled wholesale the first time it costs someone a run.

How it is proved

🔬 Verification
1
Negative control — demonstrate the finding firstrequired
Point an apiCaller node at 169.254.169.254 and confirm it currently returns metadata. That is the finding: demonstrate it in a controlled environment before fixing it, and keep the test.
2
Redirect bypassrequired
A permitted host that 302s to a blocked address must be refused at the redirect, not followed because the first hop looked clean.
3
Measure before refusingrequired
PLAN §3.3.2. Sample the real URLs stored in node configurations, classify each as would still work or would now be blocked, and drive the second to zero before enabling. Anything unresolvable is unverifiable, not blocked.
4
Report-only for a full cyclerequired
Enable in report-only mode first and log what would be blocked, for a full cycle, before enforcing. The wave's exit gate names this explicitly.
5
The rebinding case, if D is taken
A name that passes the check and then resolves to a private address on the second lookup must not connect. If the implementation cannot fail this test, it is not checking the resolved address — it is checking a string that happened to resolve once.
✓ Done when
Egress is policy-controlled at the shared fetch layer, redirects are re-checked, the worker's network position is documented, no legitimate stored URL is blocked, and the policy ran in report-only mode before enforcement.

The decisions this task needs

These are the calls that have to be made before the code is written. Each one opens to the options considered, what each costs the customer and costs us, and the option we would pick.
▸Decision S1-aPLAN D13SettledDoes a sub-flow share the parent's execution identity, get a disconnected one, or a chained one?
This one is settled, and it is recorded here because three other rules in this epic read the answer. Whatever identity a sub-flow gets determines how depth, cancellation and the spend ceiling can even be expressed.
AAbsorb into the parent's runrejected
The sub-flow's nodes join the parent's run — one execId, one scheduler state, one run.
  • Budget and cancellation are trivially one thing
  • It is a different graph — one SchedulerState would hold two node sets and two termination conditions
  • The nested run-log timeline the product already shows would be lost
Rework: the schedulerLoses: nested run log
BA disconnected runrejected
The sub-flow starts a fresh, independent run with no link back to its caller.
  • Simplest to implement — it is nearly what happens today
  • There is no visited set, so cycle detection becomes impossible
  • Every nesting level buys a fresh budget and a fresh cost ceiling — recursion becomes the way to defeat the limit
  • Cancelling the parent leaves the children running
Effort: noneDefeats: S3 and S4
CIts own run, chained by parentRunIdsettled
The sub-flow gets its own run identity plus an explicit parentRunId, forming a chain back to the origin run.
  • Depth and cycle read the chain — it is the visited set
  • Cancellation propagates along it, which Temporal child workflows give natively
  • Budget aggregates over it, so nesting cannot reset the ceiling
  • The nested run-log timeline is preserved
  • A chain has to be threaded through state that survives the move to child workflows
Effort: run context fieldEnables: S1, S3, S4, E2
Our recommendation

C, and it is decided. The easy-to-miss consequence is the third bullet: with a per-run ceiling and a sub-flow creating a new run, five levels of nesting would buy five ceilings. Recursion becomes the way around the limit. TASK-S3 is amended so the ceiling applies to the chain.

Who decidesEngineering — settled
▸Decision S1-bPLAN D14SettledIs calling a flow already on the chain refused outright, or merely depth-limited?
The depth ceiling and the cycle rule are different rules with different justifications, and the second is stronger. Treating them as one control is the mistake this decision exists to prevent.
ARefused outright, at any depthsettled
If the flow being called is already on the call chain, the call is refused — no configuration, no tunable depth at which it becomes allowed.
  • A flow on the chain is awaiting a return. Asking it to start again from the top has no coherent semantics
  • Covers A → B → C → A, not only the direct parent — A is still waiting either way
  • The message can name the chain, so the author sees which link closed the loop
  • A flow that legitimately re-enters itself with different inputs is refused too — no known real case
Client effort: noneOurs: a visited set
BAllow it, capped by depth
Treat a cycle as ordinary deep nesting and let the depth ceiling catch it a few levels down.
  • One control instead of two
  • Spends real money and real runs before refusing something that was never valid
  • The error says “too deep” when the truth is “this is circular” — the author fixes the wrong thing
Client effort: noneOurs: wrong diagnosis
Our recommendation

A — refused always, and it is not a tunable, because there is no depth at which calling back into a waiting ancestor becomes correct.

The depth ceiling stays as a separate, weaker guard for the legitimate case: composition that is genuinely nested but not circular.

Who decidesEngineering — settled
▸Decision S1-cPLAN D6Recommended — confirmWhat is the depth ceiling, and can it be raised without a deploy?
Unlike the cycle rule, this one refuses flows that might work. That makes it subject to PLAN §3.3.2: measure it against the stored flows first, and drive false refusals to zero before shipping.
A3, as an env varassumption
A default of three levels, readable from the environment so it can be raised without a deploy when a real flow needs more.
  • Covers composition of reusable building blocks without allowing accidental deep nesting
  • A wrong guess is a config change, not an incident
  • If real flows already nest deeper than three, this number is wrong — the measurement decides, not the default
Client effort: noneOurs: one env var
BPer-plan or per-tenant
The ceiling varies by customer tier, the way quota limits do.
  • A large customer with a deep legitimate composition is not blocked by a global number
  • A safety guard that varies by billing tier is a safety guard nobody can reason about
  • Needs a plan-limits surface that does not exist yet for this
Client effort: noneOurs: plan-limit plumbing
CNo ceiling — rely on the cycle rule alone
Refuse cycles, and let legitimate nesting go as deep as it likes.
  • No false refusals at all
  • Nothing to measure, nothing to tune
  • A non-circular chain can still be arbitrarily deep and arbitrarily expensive
  • Under B6 each level is a child workflow with its own retries — depth multiplies fleet load
Client effort: noneOurs: unbounded nesting cost
Our recommendation

A, with the number decided by the measurement and not by this document. Walk the stored flows: for every flow containing a fluxBox or libraryNode, compute the real maximum nesting depth. Classify each as would still work or would now be refused, and drive the second count to zero.

A ceiling that refuses working customer flows is worse than the recursion it prevents.

What the task does

1Why now, rather than with B6flux.service.ts:5611–5622
The guard has to exist before the platform learns to sustain the recursion reliably.

Today the blast radius is one backend process. It degrades, the run never returns, and somebody restarts something.

B6 turns sub-flows into Temporal child workflows — and a durable platform will faithfully sustain the recursion across the whole fleet, retrying each level. What is a crash today becomes a self-healing, fleet-wide, billed loop tomorrow.

⚠ How it is today

Two flows referencing each other recurse until the process dies. Each level is a full run with its own rows, its own log tree and its own token spend.

✓ How it will be

The second entry into a flow already on the chain is refused with a message naming the chain, before anything is spent.

2Pre-flight validation, before anything is spentflux.service.ts — v2 phase 2
Where the answer is knowable before the run, give it before the run — and turn a bill into an error message.

The chain guard is a run-time refusal: it fires after the run has started. Some of the same answers are provable earlier, in the gate the v2 already runs between building the DAG and starting to spend.

What is provable statically:

  • A cycle inside the flow's own graph — the v2 already checks this
  • A cycle in the flow-call graph reachable from this flow: A → B → C → A, walking fluxBox/libraryNode targets transitively. This is new, and it is the combinatorial case — B must not be reachable from C, and C must not reach A or B, all the way down
  • A chain that would exceed the depth ceiling before it runs a single node

What it cannot prove is termination in general — the loop conditions read data that does not exist until the run happens. That is why the static check does not replace the runtime budget in S4; the two answer different questions.

Scope — what this task does not do

It does not change what a sub-flow does when it runs legitimately. This task only refuses.

After B6, Temporal re-runs the recursion across the fleet. Each nesting level gets its own retries.

The flowCallerNode calls this.apiV2() for the selected sub-flow in flux.service.ts. That call re-enters the whole orchestrator. The libraryNode calls it the same way. Neither call site checks depth or cycle. The parentFlowId field only records billing attribution.

A flow A that calls B while B calls A recurses until the backend process runs out of resources. Each recursion level opens a complete run. Each run holds its own scheduler state, its own node_executions rows, its own run-log tree, and its own token spend.

The decisions this task needs

The engineering team must settle these decisions before the code is written. Each decision below lists the options considered, the cost to the customer, the cost to us, and the recommended option.
▸Decision S1-aPLAN D13SettledDoes a sub-flow share the parent's execution identity, get a disconnected one, or a chained one?
The engineering team already settled this decision. The document keeps it because three other rules in this epic read the answer. The identity a sub-flow receives defines how the depth ceiling, the cancellation, and the spend ceiling are expressed.
AAbsorb into the parent's runrejected
The sub-flow reuses the parent's run. A single execId, a single scheduler state, and a single run cover both flows.
  • The budget and the cancellation apply to a single run.
  • The sub-flow is a different graph. A single SchedulerState would have to hold two node sets and two termination conditions.
  • The product loses the nested run-log timeline it already shows.
Rework: the schedulerLoses: nested run log
BA disconnected runrejected
The sub-flow starts a new independent run. The run has no link back to the caller.
  • The team implements this option with almost no code change. The behavior stays close to what happens today.
  • The run has no visited set. The guard cannot detect a cycle.
  • Each nesting level receives a new budget and a new cost ceiling. Recursion becomes the standard way to bypass the limit.
  • Cancelling the parent run does not cancel the child runs.
Effort: noneDefeats: S3 and S4
CIts own run, chained by parentRunIdsettled
The sub-flow receives its own run identity and an explicit parentRunId. The parentRunId chain reaches back to the origin run.
  • The depth check and the cycle check read the chain. The chain is the visited set.
  • The cancellation propagates along the chain. Temporal child workflows provide that propagation natively.
  • The budget aggregates over the chain. A nested sub-flow cannot reset the ceiling.
  • The product keeps the nested run-log timeline.
  • The engineering team must thread the chain through state that survives the move to child workflows.
Effort: run context fieldEnables: S1, S3, S4, E2
Our recommendation

The engineering team chose Option C. The third pro deserves attention. If the ceiling applies per run and a sub-flow opens a new run, five nesting levels grant five separate ceilings. Recursion becomes the shortcut around the limit. The team updated the TASK-S3 document so the ceiling applies to the whole chain.

▸Decision S1-bPLAN D14SettledIs calling a flow already on the chain refused outright, or merely depth-limited?
The depth ceiling and the cycle rule are two different rules with two different justifications. The cycle rule is the stronger of the two. The engineering team must not treat both rules as a single control.
ARefused outright, at any depthsettled
The guard refuses any call to a flow that already appears on the call chain. No configuration and no depth value change this rule.
  • A flow on the chain is already waiting for a return value. A restart of the same flow from the top has no coherent semantics.
  • The rule covers A → B → C → A, not only the direct parent. The flow A remains waiting for a return in either case.
  • The error message names the chain. The author sees which link created the cycle.
  • The guard also refuses a flow that legitimately re-enters itself with different inputs. The team has no record of such a case in production.
Client effort: noneOurs: a visited set
BAllow it, capped by depth
The guard treats a cycle as ordinary deep nesting. The depth ceiling catches the cycle a few levels down.
  • One control covers both cases.
  • The system consumes real money and real runs before the guard refuses a call that was never valid.
  • The error message says “too deep” when the actual cause is a cycle. The author fixes the wrong problem.
Client effort: noneOurs: wrong diagnosis
Our recommendation

The engineering team chose Option A. The rule refuses the call always and does not accept configuration. No depth value makes a call back into a waiting ancestor correct.

The depth ceiling stays as a separate, weaker guard. That guard covers the legitimate case of composition that is genuinely nested but not circular.

▸Decision S1-cPLAN D6Recommended — confirmWhat is the depth ceiling, and can it be raised without a deploy?
This rule refuses flows that might work, unlike the cycle rule. The rule falls under PLAN §3.3.2. The engineering team must measure the ceiling against the stored flows first. The team drives false refusals to zero before shipping.
A3, as an env varassumption
The default value is three levels. The guard reads the value from the environment. The team raises the ceiling without a deploy when a real flow requires more.
  • The ceiling covers composition of reusable building blocks. The ceiling rejects accidental deep nesting.
  • A wrong initial value becomes a configuration change, not an incident.
  • Real flows may already nest deeper than three levels. In that case, three is the wrong value. The measurement decides the ceiling, not the default.
Client effort: noneOurs: one env var
BPer-plan or per-tenant
The ceiling varies by customer tier. The quota limits already vary the same way.
  • A large customer with a deep, legitimate composition avoids the block from a global number.
  • A safety guard that varies by billing tier becomes a guard the team cannot reason about.
  • The system requires a plan-limits surface that does not yet exist for this control.
Client effort: noneOurs: plan-limit plumbing
CNo ceiling — rely on the cycle rule alone
The guard refuses cycles only. The legitimate nesting continues to any depth.
  • The system produces no false refusals.
  • The team has no measurement to run and no value to tune.
  • A non-circular chain can still reach arbitrary depth and arbitrary cost.
  • Under B6, each level becomes a child workflow with its own retries. The depth multiplies the load on the fleet.
Client effort: noneOurs: unbounded nesting cost
Our recommendation

The engineering team recommends Option A. The measurement decides the number, not this document. The engineer iterates over the stored flows. For every flow that contains a fluxBox or libraryNode, the script computes the real maximum nesting depth. The script classifies each flow as would still work or would now be refused. The team drives the second count to zero.

A ceiling that refuses working customer flows is worse than the recursion the ceiling prevents.

What the task does

1Why now, rather than with B6flux.service.ts
The guard must ship before the Temporal platform becomes able to sustain the recursion reliably.

Today the blast radius is one backend process. That process degrades. The run never returns. An operator restarts the process.

The B6 task turns sub-flows into Temporal child workflows. The Temporal platform then re-runs the recursion across the fleet, with retries on each level. A crash today becomes a fleet-wide, retried, billed loop tomorrow.

⚠ How it is today

Two flows that reference each other recurse until the backend process runs out of resources. Each level is a full run. Each run holds its own rows, its own log tree, and its own token spend.

✓ How it will be

The guard refuses the second entry into a flow already on the chain. The error message names the chain. No spend occurs before the refusal.

2Pre-flight validation, before anything is spentflux.service.ts — v2 phase 2
The pre-flight gate returns the answer before the run when the answer is knowable before the run. The gate converts a billing event into an error message.

The chain guard is a run-time refusal. The guard fires after the run has already started. The v2 architecture already runs a static gate between building the DAG and starting to spend. Some of the same answers become provable in that static gate.

The static gate can prove the following cases:

  • A cycle inside the flow's own graph. The v2 already checks this case.
  • A cycle in the flow-call graph reachable from this flow, for example A → B → C → A. The check walks fluxBox/libraryNode targets transitively. This case is new and combinatorial. B must not be reachable from C, and C must not reach A or B, all the way down.
  • A chain that would exceed the depth ceiling before executing a single node.

The static check cannot prove termination in general. The loop conditions read data that only exists at run time. The static check does not replace the runtime budget in S4. The two checks answer different questions.

Scope — what this task does not do

The task does not change what a sub-flow does when the sub-flow runs legitimately. The task only refuses.

The PLAN §3.3.2 applies here without exception. The script iterates over the stored flows. For every flow that contains a fluxBox or libraryNode, the script computes the real maximum nesting depth and detects existing cycles. The script classifies each flow as would still work or would now be refused. The team drives the second count to zero. The team either raises the ceiling or contacts the flow owners.
3
Report existing cycles separately
Those flows are already broken today. The guard turns the failure from fatal into legible. The team must notify the flow owners. The team must not refuse the flows silently.
4
The guard survives the boundary
The chain, the visited set, and the depth counter must live in the run context that already crosses into child workflows. The engineer must not place them in a closure. The engineer confirms the three fields remain in place after B6 moves sub-flows to Temporal.
✓ Done when
The guard refuses cycles with a clear message. An env-configurable ceiling caps the depth. The team measured the stored flows and no working flow is refused. The guard lives in state that survives the move to child workflows.

Today nodesBox reads data.selectedId against objectCallerData — the engine's in-memory array for the run — reads the latest session state for {scopeType:'object', scopeId, sessionKey, ownerUserId}, then writes the object's content and publishes it through onMutateObjectCallerData. It mutates data, not control, unlike conditionNode, arrayNode, fluxBox and libraryNode, which belong in the workflow (B6).

The review on 2026-10-23 found that no object write exists — a write lives only in that array — and that no execution record exists either, so the value a run used cannot be recovered. It found four entry paths, not three, and a race across runs, not only across branches. It also found that the back's loops skip or inline several worker types, so that work moved here from the coverage audit's A12.

What the task does, in six parts

1An execution record, and consumers by referenceworker/src/modules/nodes/object-caller/
Every nodesBox execution has a node_executions row on both engines, and a consumer can say which write it read.

The activity writes the row like every worker node. A consumer records which writer execution it read, not a copy of the object text, so object text a run produces is stored once, in the writer's row, under a retention policy decided in this task.

Read rule: a consumer reads the writes that completed before it was scheduled, not the latest at read time, so a Temporal retry reads the same value.

⚠ How it is today

A write lives only in the run's in-memory objectCallerData; the value a run used cannot be recovered afterwards.

✓ How it will be

The run's nodesBox rows are the source of truth, else the stored template in flow_objects.

2Implicit ordering edgesback/src/app-api/flux/scheduler.ts
Two callers of one object have no edge between them, so the scheduler derives one (A7-D6).

buildSchedulerState derives ordering edges from object access — writer to writer, writer to reader — in today's tie-break order. Both engines use it: the back's loop is the same DAG scheduler run one node at a time, so the order does not change there and stays defined when B5 dispatches a batch. It reaches the worker through B2's sync.

3Session writes through one locked callbackback/src/app-api/session_state/
One implementation, in the back, idempotent per execId + nodeId (A7-D2), ordered by an advisory lock (A7-D3).

The callback calls sessionStateService for the object scope. One lock per objectId:sessionKey:ownerUserId covers read, merge and append in one transaction, with SET LOCAL lock_timeout; clearObjects takes the same lock. Every append carries execId and flowId. The back resolves the object owner once per run and carries it in the run seed (A7-D7).

⚠ How it is today

readLatest then append has no lock across runs, and session rows have no execId or flowId.

✓ How it will be

Two concurrent session writes keep both updates, and each row says which run wrote it.

4Read side switched by the B4 flagback/src/app-api/flux/node-input-projection.ts
Flipping nodesBox to flowDispatch: 'worker' must not hand downstream nodes empty text (A7-D8).

With the flag off, the back's loop keeps feeding downstream nodes from objectCallerData, now updated from the activity's result. With the flag on, the worker projection reads by reference: getOutputByType resolves a nodesBox source from the run's rows. A shadow comparison on the back's loop logs any difference before the flag is turned on, as B3b did.

⚠ How it is today

Under processFlow, the worker projection passes undefined as objectCallerData, so downstream nodes get empty text.

✓ How it will be

Both engines feed the same value, and the shadow proves it before the flag flips.

5Delete the inline handler on all four pathsback/src/app-api/flux/flux.service.ts
Characterise first, then delete objectCaller() from the full run, loop body, single node and prefetch paths.

No test covers objectCaller or clearObjects today, so parity tests go on the back first and then run against the worker path. Set prefetchSafe from what the activity really needs. If any callback remains, model it on /node-credit-gate or /run-events, not on /store-payload.

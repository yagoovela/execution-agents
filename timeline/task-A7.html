Its own logic is about 130 lines. The work is entirely in what has to exist around it.

Today nodesBox reads data.selectedId against objectCallerData — the engine's in-memory array for the run — reads the latest session state for {scopeType:'object', scopeId, sessionKey, ownerUserId}, then reads and/or writes the object's content and publishes the change back through onMutateObjectCallerData so later nodes see it. Handler at flux.service.ts:6834; call sites :1370, :2580, :3575, :4146.

It is the only one of the five mutating nodes with extractable logic. conditionNode, arrayNode, fluxBox and libraryNode are control flow — they decide what runs next, and belong in the workflow (B6). nodesBox mutates data, not control (analysis §3.5).

2

The decisions this task needs

One call, and the spec names it outright: pick one and state why. It is the item the analysis says will be underestimated, and the one PLAN §6 tracks as risk R5.
▸Decision A7-aRecommended — confirmAdvisory lock, or an idempotent activity, for two Object Callers on the same object?
Today the engine serialises every Object Caller in a run through one in-memory array. Once they are independent activities that serialisation is gone, and two callers touching the same object have no order at all. The spec offers exactly two acceptable answers and says “pick one and state why — do not ship without addressing it and hope the ordering holds.” One constraint narrows the menu before it opens: changing object semantics is explicitly out of scope.
Apg_advisory_xact_lock per objectrecommended
The activity takes a transaction-scoped advisory lock keyed by the object before its read-modify-write, so two Object Callers on the same object serialise. The pattern is already in the worker — third-party-integration/oauth-token.repo.ts:7.
  • It is a working pattern already in this codebase, not a design — review §6 lists it as something to keep
  • It becomes the ordering authority the in-memory array used to be, which is precisely what is being removed
  • It can be tested deterministically — hold the lock explicitly in the test instead of racing on timing
  • Object semantics are untouched: read, transform, write back still means what it means today
  • It holds a database lock inside an activity, so a slow write holds a connection — the resource S2 just finished sizing
  • Held around an external call it becomes a fleet-wide stall, so the boundary has to be drawn tightly and on purpose
Client sees: the order they have todayOurs: one lock on the S2 budget
BAn idempotent activity
Express the write so repeating it or re-ordering it converges to the same object — an append or a keyed merge rather than a read-modify-write.
  • No lock, no held connection, and activity retries stop being a hazard — the platform retries by design
  • It is the answer that scales without a coordination point, if the node can be expressed that way
  • Object Caller reads the object, transforms it and writes it back — that composition is not idempotent, and making it so means changing what the node does
  • Changing object semantics is explicitly out of scope for this task, so this option needs its own product decision first
Client risk: the node changes meaningOurs: a product decision first
CShip it and hope the ordering holdsrejected by the spec
Migrate the node without an ordering answer, on the grounds that two Object Callers on one object in one flow is rare.
  • Ships the fastest, and most flows will never notice
  • The spec forbids it in as many words, and R5 exists because someone already predicted this failure
  • The failure is a silently wrong object, discovered later by a customer, with no error to trace back
Client risk: a silently wrong objectOurs: an unreproducible bug report
Our recommendation

A — the advisory lock — and write the rationale into the task file, because the spec's definition of done asks for exactly that. The deciding argument is not that locks are elegant; it is that B requires changing what Object Caller means, and this task says it will not.

Draw the lock boundary on purpose: around the read-modify-write only, never around a provider call. A lock held across an external request turns a slow API into a fleet-wide stall, and it consumes a connection from the budget S2 just sized.

What the task does, in three parts

1An object-state callbackback/src/temporal/worker.controller.ts
Give the worker read and write access to object content without inventing a new contract shape.

The first of the two contracts that have to exist before the node can move: a read-and-write callback exposing objectsService. The spec is specific about the shape — model it on the existing /worker/store-payload contract rather than inventing one. A new shape here is a fifth thing for the next person to learn.

⚠ How it is today

The handler reaches objectsService directly, in process, through the engine's objectCallerData array.

✓ How it will be

The activity reads and writes object content through a callback with a stated contract — the same boundary every other worker node already uses.

2A session-state callbackback/src/app-api/session_state/
Mirror readLatest and appendEntries for the object scope, with the same semantics the inline path has.

The second contract mirrors sessionStateService.readLatest and appendEntries for the object scope. The key the node reads with today is {scopeType:'object', scopeId, sessionKey, ownerUserId}, and all four parts of it have to survive the crossing — a callback that drops ownerUserId reads someone else's session.

Parity here is checkable against real data, and the verification section says to check it that way: the callback must produce the same rows the inline path produces, on real stored objects.

⚠ How it is today

Session state is read and appended in the same process that runs the node, so scoping is whatever the call site passed.

✓ How it will be

The scope is carried explicitly across the callback, and parity with the inline path is proved on stored objects rather than assumed.

3Ordering — the part that will be underestimatedflux.service.ts:6834 · oauth-token.repo.ts:7
Whatever replaces objectCallerData has to be the ordering authority, or the node has to become idempotent.

The in-memory array was doing more than caching. It was the run's ordering authority: every Object Caller in the run went through it, one at a time, in the process that owned the loop. That property is not written down anywhere and it disappears silently the moment the node becomes an activity.

The analysis is direct about it: of the three things a worker activity would need here, item 3 is the one that will be underestimated (§3.5). The two callbacks are contracts; this is a concurrency property.

⚠ How it is today

Two Object Callers on the same object are ordered by accident — because one process holds one array and runs one node at a time.

✓ How it will be

The chosen mechanism is the ordering authority, it is written down with its rationale, and a deterministic test proves it holds.

Out of scope

Changing object semantics, session-state scoping, or the chat behaviour built on it. The chat path — fluxObject / nodesBox with chat enabled — is written at run finalisation (flux.service.ts:5222), outside this node, and must be unaffected.

Three stages
One task because the three stages share the same three-part scope — not because they are one deploy.

These eight types are front-driven: the component calls a backend endpoint directly and bypasses the flow engine (analysis §4.1). They produce output only when a user clicks Run in the builder. In an API, cron, chatbot, form or MCP run the engine never dispatches them, so the flow uses whatever the last manual run left behind — or nothing.

fileSave is the sharpest case. It is listed in SIDE_EFFECT_TYPES (flux/scheduler.ts), so the scheduler deliberately protects it from being pruned — yet nothing executes it server-side. Its uploadToDrive() runs in the browser against a localStorage OAuth token, so it cannot run headless even in principle.

The decision this task needs

One call gates the whole wave, and it is not an engineering call. It is the difference between a defect we fix quietly and a change customers are told about — and the honest part is that flows which produced stale output in silence will start producing fresh output, with the spend and the side effects that come with it.
▸Decision A6-aPLAN D3Open — needs a callDo the eight front-driven types running headless count as a fix, or as a behaviour change customers must be told about?
This is the strongest call in the wave, and the plan gates the whole wave on it: “it needs the D3 answer before this wave, not during it”. Today these nodes produce output only when someone clicks Run in the builder. In an API, cron, chatbot, form or MCP run the engine never dispatches them, so the flow uses whatever the last manual run left behind — or nothing. Analysis §4.2 puts it plainly: if a customer has an animationNode or a documentSummarizer in a scheduled flow, that flow is silently producing stale output today.

Fixing it is almost certainly right. It is also visible: a flow that has been quietly reusing an old value starts producing a fresh one — with fresh provider spend, and, for fileSave, a fresh upload into someone's Drive folder. That is why PLAN §7 treats D3 as a product change requiring sign-off, not a refactor.

ATreat it as a bug and fix it silently
Ship the dispatch, announce nothing. The flows simply start doing what their authors always believed they were doing.
  • It is what customers already assume is happening — nobody configured a node in order for it not to run
  • No coordination cost, no cohort, no message to write
  • One behaviour everywhere, immediately
  • Scheduled output changes with no warning — anything downstream that consumes it sees the change first
  • New provider spend appears on the invoice for nodes that never charged in a headless run
  • For fileSave, a scheduled run starts writing files into a Drive folder that has never received one
Client effort: noneOurs: every surprise arrives as a ticket
BTreat it as a behaviour change, with comms and cohortsrecommended
Find the flows that contain one of the eight and have a headless trigger, tell their owners what will start happening, then enable per cohort behind the flag PLAN §3.2 already requires.
  • It is the answer the plan asks for — explicit, signed off, and recorded before the wave starts
  • The owners of affected flows hear about the new spend before the invoice does
  • The flag and the per-flow rollback already exist for other reasons, so the cohort costs almost nothing extra
  • The query that finds the affected flows is also the measurement the wave exit gate wants
  • Someone has to write the query and send the message, and stage the enablement
  • Slower than A — the fix waits on a human loop
Client effort: read one messageOurs: a query, a message, a staged rollout
CLeave headless unsupported — but refuse it out loud
Keep the eight builder-only, and make validation refuse a flow that pairs a headless trigger with one of them, instead of silently skipping the node at run time.
  • No behaviour change and no new spend
  • It still fixes the silent half of the defect: the flow says so instead of passing a stale value off as output
  • Cheapest of the three — one validation rule
  • It refuses work customers are asking for, and giving these eight server-side execution is the entire point of A6
  • It is a refusal, so PLAN §3.3.2 applies: measure it against the stored flows first, or it becomes the false refusal
  • Leaves fileSave permanently browser-bound even though the server-side token already exists
Client effort: edit the flow, or drop the nodeOurs: one validation rule
Our recommendation

B — and borrow C's honesty for the gap. While a flow is still waiting for its cohort, the run log should say the node was not executed, rather than let a stale value pass as this run's output. That single line turns the remaining months of the rollout from a silent defect into a stated limitation.

The distinction that decides the cohort order is spend and side effects, not node count: fileSave writes into a customer's Drive and documentSummarizer is LLM-backed and bills, so those flows are what the message is for. A flow whose only affected node reads a public data source is the safe cohort to start with.

A is not wrong, it is just untimed. The plan already recorded this as a product change; shipping it as a silent fix contradicts a decision that has been written down since PLAN §7, and the first person to notice will be a customer reading an invoice.

What the task does, in five parts

1Three things, and the second exists for no other task in this epicanalysis §4.1, §4.3
Name the scope precisely, because “migrate these nodes” describes something that cannot happen — nothing executes in the back today.

The scope is not “move code from the back”. It is three things:

  • Implement the activity — the normal seven-layer registration chain.
  • Make the engine dispatch the type for the first time, including declaring its dependency edges to the scheduler so it runs in the right order. No other task in this epic adds a dispatch that never existed.
  • Decide what the front's Run button does afterwards: route it through ProcessService.response (POST /process/single-node) like every migrated node, and delete the direct provider call.
⚠ How it is today

A headless run skips the node entirely. Whatever data.text the last manual click left behind is what the rest of the flow consumes.

✓ How it will be

The engine dispatches the node like any other, in dependency order, and the value the flow consumes was produced by this run.

Two paths is how the four lists diverged

Keeping the direct provider call “as a preview path” alongside the new dispatch is exactly the pattern that produced four uncoordinated dispatch lists in the first place. The Run button routes through the same execution as everything else, and the direct call is deleted, not merely unused.

2Stage 1 — the three that are almost freeflux/scheduler.ts · flux.service.ts
Ship the three types whose provider clients are already in the worker, and fix the one that cannot run headless even in principle.

webTrends and webAmazon need no provider work at all — the SerpApi and Scraper clients are already in the worker, inside web-search and web-crawling.

fileSave is the most valuable of the three and the worst offender. The server-side token already exists (user.googleRefreshToken) and the engine already refreshes it — but only when the flow has pullData/pushData with provider = google (flux.service.ts). Extend that condition; do not build a second refresh path.

⚠ How it is today

The scheduler protects fileSave from being pruned as a dead branch, and then nothing runs it. The upload happens in a browser tab, against a token in localStorage.

✓ How it will be

A scheduled run uploads to Drive with the server-side token, with no browser involved — and the refresh condition that already exists is the one that does it.

3Stage 2 — port a small clientback/src/app-api/{sec,census_data,summarize}/
Three types whose backend module is a thin HTTP client, so the port is volume rather than design.

secApiNode (app-api/sec), usCensusNode (app-api/census_data) and documentSummarizer (app-api/summarize). No credentials beyond an env key — except documentSummarizer, which is LLM-backed and therefore uses the existing billing and model-access callbacks rather than anything new.

All three are on S6's list of relocated fetchers, so its egress policy applies to them before they ship.

⚠ How it is today

Three backend modules that only a front component ever calls, and only when a person is watching.

✓ How it will be

Three worker modules the engine dispatches, with the LLM-backed one billing through the same contract as every other LLM node.

4Stage 3 — asset providers, and timeouts that are chosenworker/src/modules/temporal/workflows/configs.ts
The two long-running types, where an inherited timeout is a guess that surfaces as a failed run.

commandMusicNode (Replicate) and animationNode (Luma + Runway). Both produce assets, so both use /worker/generate-file; both are long-running, so both need their startToCloseTimeout and heartbeatTimeout chosen deliberately rather than inherited.

⚠ How it is today

A video or a track is generated in a browser tab, and a closed tab is a lost generation.

✓ How it will be

The generation is an activity with a timeout someone chose and a heartbeat that proves it is still alive.

The wave's latency regression applies to all eight

Every node this wave migrates is a blocking round trip until Wave 5 turns on parallelism (review §4.5, risk R4). For these eight the comparison is unusual: the headless path had no latency because it did not run at all. Measure the builder path before and after, and state the number in the PR — that is the comparison a customer will actually feel.

5The egress policy ships with the move, not after itTASK-S6-SSRF-POLICY.md
Several of these nodes fetch user-controlled URLs, and this task moves them into the host that holds the database password.

There is no SSRF protection today (review §3.2), and whether relocating these fetchers improves or worsens the exposure depends on the worker's network position — which nobody has written down.

S6 owns the policy. This task does not ship a relocated fetcher until S6's decision exists and applies to it. The point of S6 is that the decision is made with the move, because the move is what changes the risk.

⚠ How it is today

A node can point at an internal hostname or the cloud metadata endpoint, from the backend, with nothing checking the address.

✓ How it will be

The same fetch runs under one egress policy, from a host whose network position is documented — and the policy ran in report-only mode first.

The policy is decided in S6, on this page's schedule

S6 carries two open calls — the shape of the policy and the worker's network position. Both are answered on the S6 page, and both must be answered before Stage 1's webAmazon and Stage 2's three clients relocate their fetches.

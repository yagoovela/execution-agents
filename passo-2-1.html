Passo 2.1 — buildSchedulerState (DAG scheduler)

Bloco em scheduler.ts:152-293 (planOrder: 412-425). Constrói o estado do scheduler DAG que vai reger o loop principal: classifica arestas em control / condition / data / global, calcula alcançabilidade a partir do starter, remove backedges (ciclos), monta contadores de predecessores e devolve a fila inicial de nós prontos (ready).
Em resumo — o que esse passo faz
  • Etiqueta cada aresta do canvas: passa por todas as ligações entre nós e coloca um rótulo (global, control, condition, data) que diz se aquela aresta bloqueia execução ou não.
  • Descobre quem entra na festa: partindo do starter, calcula o Set de nós reachable — quem não estiver nele fica dormindo o run inteiro, mesmo desenhado no canvas.
  • Remove ciclos do grafo: um DFS com coloring (branco/cinza/preto) identifica as backedges (típico de arrayNode que volta pro início) e as ignora, pra não travar os contadores de predecessores.
  • Monta o "painel de controle" do loop: pra cada nó, calcula quantos predecessores tem no total e quantos são gates (control+condition), inicializa contadores em zero e popula o ready[] só com nós de in-degree 0.
  • Saída: um SchedulerState mutável de 12 campos (ready, forwardDeps, conditionEdges, contadores, sets vazios de completed/dead/scheduled) que o loop da Fase 3 vai consumir — puro CPU, zero I/O, O(V+E).
Contexto: este é o coração do algoritmo de execução. Todo o loop da Fase 3 depende do SchedulerState que sai daqui — nextReady(), markCompleted(), markDead(), completeCondition() operam nas estruturas montadas em 2.1. É código puro (sem I/O, sem async), determinístico, ~140 linhas — pode virar unit test trivial.
Cadeia de operações em 2.1
AclassifyEdge → Breachable + pullProviders/Consumers → CfindBackEdges (DFS) → DMonta preds + gating + ready → EplanOrder (debug)
Resultado final: SchedulerState com 12 campos que o loop consome — ready[], forwardDeps, conditionEdges, contadores de preds/gating, sets de completed/dead/scheduled.
A classifyEdge()
scheduler.ts:46-57
function classifyEdge(edge, starterSourceId): 'control' | 'condition' | 'data' | 'global'
Propósito: Categoriza cada aresta em uma de 4 classes. Essa classificação determina como o scheduler trata a dependência: control/condition gateiam execução; data passa valor mas não bloqueia por si só; global não conta como dep.
Em resumo: pense nessa função como o cadastrador das arestas — ela pega cada linha que liga um nó a outro no canvas e coloca uma etiqueta em cada uma. Olhando pro handle de saída, ela decide: "essa aqui é global (vem do starter, não trava ninguém)", "essa é control (fluxo explícito, tem que respeitar a ordem)", "essa é condition (saída de if/switch, pode matar a branch se o teste der errado)" ou "essa é data (só entrega um valor)". É uma cascata de 5 checks, e o primeiro que bater ganha. O rótulo é o que vai dizer pro resto do scheduler se aquela aresta bloqueia execução ou não.
🪜 Cascata de classificação
1 source === starterSourceId || handle = 'a' global
2 handle = 'outputFlow' control
3 handle bate em /outputHandle-[01]/ ou /conditionHandle-[TF]\d+/ condition
4 tem targetHandle data
5 nenhum global (fallback)
↓
isDependencyEdge = control || condition || data
Ou seja: só arestas global são ignoradas no cálculo de dependência. As demais viram nós no grafo de precedência.
scheduler.ts:59-65
🎯 Semântica das 4 classes
global — starter/globals (não gateiam nada, todo run começa com)
control — fluxo explícito (aresta outputFlow): "só rode depois deste"
condition — saída de conditionNode: pode marcar branch como dead
data — aresta de valor: dep de precedência mas não força ordem no DAG se já resolvido
🔧 Handles hardcoded
GLOBAL_HANDLE = 'a', CONTROL_HANDLE = 'outputFlow', regex outputHandle-[01] (bool if/else) e conditionHandle-[TF]\d+ (switch). Se o front cria um handle com nome fora desses padrões, ele cai em data ou global por acidente.
⚠️ Fallback silencioso pra global
Aresta sem sourceHandle e sem targetHandle → global. Se um bug no front criar aresta assim entre 2 nós de negócio, o scheduler não vai gatear a execução — pode causar race na Fase 3.
B reachableFrom + pullDataProviders + pullSinkConsumers
scheduler.ts:113-220
// BFS a partir do starter, depois expande por data-providers e data-sinks até fixed point
Propósito: Descobrir quais nós vão realmente rodar neste run. Só nós alcançáveis a partir do flow-global-starter via arestas control/condition entram na base, e depois puxa data providers (nós cujo output alimenta um nó alcançável) e data sinks (output/varInput consumers). Fixed point até estabilizar.
Em resumo: essa etapa é o vigia que decide quem entra na festa. Ela parte do nó starter e vai andando pelas arestas de control/condition pra montar um primeiro grupo de nós "com convite"; depois faz uma passada puxando quem alimenta esses nós com dados (os providers), e uma outra passada puxando quem recebe resultado deles (os sinks tipo outputController, varInputNode). Roda em fixed point — repete até nada mudar. No final sobra um Set chamado reachable, e quem não está nele nem existe pro loop: mesmo estando desenhado no canvas, o nó fica dormindo o run inteiro. É o que evita rodar um apiCaller desconectado só porque ele está pendurado por lá.

🎯 Por que 2 fases?
Fase 1 é a expansão "completa" (traz tudo que alimenta os nós de negócio, mesmo side-effects como apiCaller). Fase 2 corrige overshoot: se um output-sink virou alcançável e precisa de mais providers, só puxa se não for side-effect (evita disparar apiCaller só pra popular um output).
📎 SIDE_EFFECT_TYPES
apiCaller, mcpNode, thirdPartyIntegration, pushData, hubSpotCRM, fileSave. Set fechado em scheduler.ts:29-36. Adicionar tipo novo aqui muda semântica de alcançabilidade — cuidado.
📎 DATA_SINK_TYPES
outputController, outputObjectNode, varInputNode. Só esses 3 são puxados pela regra "consumer alcançável se produzido por alcançável". scheduler.ts:23-27.
🔧 orchAdj vs dataAdj
Duas listas de adjacência separadas: orchAdj só tem control+condition (usada na BFS inicial); dataAdj/reverseDataAdj só tem data (usada na expansão). Bug clássico é misturar as duas.
C findBackEdges()
scheduler.ts:130-150
function findBackEdges(roots, adj: depAdj): Set<`${src}->${tgt}`>
Propósito: DFS clássico com coloring (0=white/unvisited, 1=gray/on-stack, 2=black/done) pra detectar backedges no grafo de dependência. Backedges são ignoradas na montagem de forwardDeps/preds — sem isso, ciclos travariam nextReady (nunca zera predecessores).
Em resumo: imagina que o grafo tem um arrayNode que volta pro início pra iterar: isso é um ciclo, e ciclo em DAG é veneno pro scheduler (o contador de predecessores nunca chega a zero, então nextReady nunca acha o nó pronto e o loop trava). Essa função é o faxineiro que sai passeando pelo grafo com uma marcação de três cores (branco = não visitei, cinza = estou dentro, preto = já saí) e, sempre que topa com uma seta apontando pra alguém que ainda está "cinza" (ou seja, tem a mesma seta subindo pela pilha), marca aquela aresta como backedge. Essas backedges ficam num Set e são simplesmente ignoradas na hora de montar as dependências — o loop lógico do array vira problema do handler de arrayNode na Fase 3, não do scheduler.

⚠️ DFS recursivo — risco de stack overflow
Flow com > ~5000 nós encadeados em série pode estourar o call stack do Node. Não é caso real hoje (nenhum flow em prod chega perto), mas é limitação latente. Migrar pra DFS iterativo com stack explícito eliminaria.
🎯 Por que ignorar backedge?
Se A → B → A é um ciclo, um dos dois nós tem in-degree ≥ 1 pra sempre — nextReady nunca acha ele pronto. Removendo o backedge do grafo de deps, o loop principal consegue rodar A, depois B (que agora tem in-degree 0), e o loop lógico vira responsabilidade do arrayNode handler em Fase 3.
🔧 Chave ${node}->${next}
String literal, não tupla. Concat direto. Se algum nodeId contiver a substring ->, colisão. Como IDs são UUIDs no front, seguro na prática.
D Monta forwardDeps + preds + gating + ready[]
scheduler.ts:232-292
return { nodeIds, forwardDeps, conditionEdges, totalPreds, resolvedPreds, deadPreds, gatingPairs, totalGating..., ready: [], completed: Set(), dead: Set(), scheduled: Set() }
Propósito: Materializar o estado final que o loop vai mutar. Cada nó tem 6 contadores (total/resolved/dead × preds/gating) que markCompleted/markDead/completeCondition incrementam em O(1) durante o run. ready[] começa com nós de in-degree 0.
Em resumo: essa aqui é o montador do painel de controle que o loop de execução vai usar do início ao fim. Passando aresta por aresta, ela vai enchendo mapas: pra cada nó quantos predecessores totais existem, quantos deles são "gates" (control+condition, os que podem matar o nó), quais são as arestas de saída pra propagar depois, e quais saídas de conditionNode devem ser lembradas pra quando o if resolver. No fim inicializa contadores zerados de "resolved" e "dead" pra cada um e monta o ready[] inicial só com quem não tem predecessor nenhum — esses são os primeiros a rodar. Daqui pra frente, cada markCompleted/markDead/completeCondition vai só incrementar esses contadores em O(1) e mover nós pro ready conforme forem se liberando.

Nós sem predecessores = pontos de entrada do DAG. Tipicamente: os targets do starter, e globals. É o array que nextReady() vai shift() na Fase 3.

🎯 Por que 2 contagens (preds vs gating)?
preds = todas as deps (control+condition+data). Só quando todas resolvidas o nó pode ir pra ready.

gating = subset (só control+condition). Se todos os gates que sobraram estão mortos, o nó também morre (não roda).

Data edges contam pra ordem mas não podem "matar" o nó sozinhas.
📎 conditionEdges guarda todas as arestas de condition por source
Usado pelo completeCondition(schedState, id, takenHandle) pra decidir qual branch vira dead quando um conditionNode resolve. Ver scheduler.ts:366-389.
🔧 Sets vazios pre-alocados
completed, dead, scheduled começam vazios. O loop popula on-the-fly. scheduled evita re-enfileirar o mesmo id se nextReady for chamado após já ter servido.
⚠️ Todas as estruturas são Map/Set
Rápido em memória, mas não são serializáveis pra Redis/Postgres direto. Se algum dia o scheduler precisar sobreviver a um crash do backend, precisa serializer custom.
E planOrder()
scheduler.ts:412-425
function planOrder(nodes, edges, starterSourceId): string[] // ordem topológica linear
Propósito: Roda o scheduler a seco — chama buildSchedulerState + loop nextReady → markCompleted até esvaziar, sem executar handlers. Só devolve a ordem em que os nós iriam rodar. Usado pra popular allNodesIds no flux.service pra debug/UI.
Em resumo: é um ensaio geral do agente sem ninguém no palco. Ela chama tudo que a D montou e simula o loop: pega o próximo nó pronto, "marca como completo" (sem executar de verdade, sem gastar token, sem chamar API), pega o próximo, e assim por diante até acabar. O que sai é só a lista ordenada dos IDs na sequência em que iriam rodar — usada em allNodesIds pra debug, previews e alguns asserts. Cuidado com uma pegadinha: como ela nunca chama completeCondition nem markDead, o ensaio assume que todos os branches são tomados — então a lista é o "cenário máximo", não necessariamente o que vai acontecer num run real com condições.
export function planOrder(nodes, edges, starterSourceId): string[] { const state = buildSchedulerState(nodes, edges, starterSourceId); const order = []; let id; while ((id = nextReady(state)) !== null) { order.push(id); markCompleted(state, id); } return order; }

⚠️ Não considera conditions
planOrder só chama markCompleted — nunca completeCondition ou markDead. Ou seja: assume que todo branch é tomado. Ordem gerada é a hipótese máxima, não o que vai rodar de verdade num run com condições.
🎯 Custo
É basicamente o dobro do trabalho do build — chama buildSchedulerState de novo e depois faz uma passada topológica. Rodado a cada run. Poderia ser cacheado por (flowId, version) já que é determinístico só a partir de nodes+edges, mas hoje não é.
🔧 buildSchedulerState é chamado 2 vezes no run
1x aqui pra schedState (flux.service.ts:3136) e 1x dentro de planOrder pra allNodesIds. Poderia reusar o mesmo state, mas requer markCompleted ser não-destrutivo (não é).
Resumo — o que sai de 2.1:
• schedState: SchedulerState — mutável, consumido pelo loop da Fase 3
• allNodesIds: string[] — ordem topológica pra debug/UI
• Zero I/O; puro CPU; ~O(V+E) na maioria dos casos
• Nós fora do reachable ficam invisíveis pro run (nunca executados)
Observações para migração:
• Essencial e código puro — é o menor risco de migrar. Pode virar biblioteca compartilhada backend/worker com zero mudança semântica.
• Worker não precisa rodar scheduler hoje (cada activity é um nó isolado). Se algum dia o worker orquestrar sub-DAGs, esse mesmo módulo funciona.
• Cachear buildSchedulerState por (flowId, versionId) elimina uma rodada por run. Custo trivial hoje mas cresce linear com nº nós.
• Formalizar interface pública (só exporta buildSchedulerState/nextReady/markCompleted/markDead/completeCondition) antes de qualquer refactor — hoje é fácil alguém importar helper interno sem querer.
• Adicionar tipo em cima de handles: as regex outputHandle-[01] e conditionHandle-[TF]\d+ são strings mágicas — enum tipado no front que gera esses handles seria mais seguro.

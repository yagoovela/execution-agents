Passo 5.2 — mcpRunStatusService.markFinished

Bloco em apiV2Job.processor.ts:58-67 (path sucesso) e 80-88 (path erro). Não vive no FluxService.apiV2 — vive no processor do Bull queue. Só roda quando request veio pelo endpoint MCP e o job foi enfileirado via Bull.
Em resumo — o que esse passo faz
  • Tracking dedicado do MCP: esse passo não vive no FluxService, e sim no processor do Bull. É opt-in via flag mcpTracking — se o run não veio pelo endpoint MCP, tudo aqui é pulado. Serve pra dashboards específicos (latência, error rate, tokens por MCP token).
  • Pareamento markRunning / markFinished: na entrada do job, o processor grava a row em mcp_run_status com status: 'in_progress' e startedAt=NOW(). No fim, atualiza com o resultado — fecha o par do começo ao fim do lifecycle.
  • Success path — deriva status de nodeError: quando apiV2() retorna sem lançar, o processor lê result.nodeError. Se null → 'completed'; se string → 'error' (nó falhou mas o run terminou). Grava totalTokensUsed, totalCost, durationMs e errorMessage.
  • Error path — tokens/cost zerados: se apiV2() lançou (5.1), o catch do processor marca status: 'error' com tokens: 0, cost: 0. Limitação atual — o processor não tem acesso ao acumulador do run, então crash catastrófico fica subcontado em analytics de custo. Depois faz throw error pro Bull marcar o job failed.
  • Saída: 1 UPDATE em mcp_run_status (só se veio via MCP), com status final, tokens, cost, duração e error. Cleanup do MCP fica separado de execution_logs pra não poluir queries dos outros run_types.
Contexto: MCP (Model Context Protocol) é uma layer separada — permite outros LLMs chamarem o Flux como tool. Cada chamada MCP dispara um job Bull; esse tracking permite analytics de "quantos runs de MCP rodaram", latência, error rate por token MCP. Fora do main path do FluxService — vive no processor.

BmarkFinished (success path)
apiV2Job.processor.ts:58-67
await this.mcpRunStatusService.markFinished({ id: processId, status: result.nodeError ? 'error' : 'completed', tokens: result.totalTokensUsed, cost: result.totalCost, durationMs: Date.now() - startedAt, errorMessage: result.nodeError ?? null })
Propósito: Após fluxService.apiV2() retornar (sem throw), fecha o tracking. Status = 'error' se nodeError presente no retorno, senão 'completed'. Grava tokens totais, cost total, duração em ms, errorMessage.
Em resumo: pareamento com markRunning. Quando apiV2() retorna sem crash, o processor pega o result (que tem nodeError, totalTokensUsed, totalCost) e faz update na row de mcp_run_status. Status é derivado de result.nodeError: se null = 'completed' (sucesso limpo); se string = 'error' (algum nó falhou mas o run terminou sem crash top-level — a Fase 4 catch em 3.8 fez fail-fast). durationMs é Date.now() - startedAt — startedAt foi marcado pelo processor no início. Preciso pra latency dashboards. errorMessage é o próprio nodeError (a string amigável do 4.5) — dá pra MCP client mostrar UI apropriada. UPDATE via TypeORM.

🎯 3 estados possíveis
Status: 'pending' (nunca setado explícito — default do INSERT), 'in_progress' (markRunning), 'completed' | 'error' (markFinished). Cancel não tem status próprio aqui — cancel de MCP é raro/inexistente.
📎 nodeError vs error crash
Se agente falhou por handler bug (fail-fast em 3.8), nodeError é string mas apiV2 retornou normalmente. Se agente crashou catastrófico (5.1), apiV2 lançou — vai pro fn C.
CmarkFinished (error path)
apiV2Job.processor.ts:80-88
catch (error) { if (params.mcpTracking) { await mcpRunStatusService.markFinished({ id: processId, status: 'error', tokens: 0, cost: 0, durationMs, errorMessage: error.message }); } throw error; }
Propósito: Se fluxService.apiV2() lançou (não retornou), o processor pega no catch. Marca mcp_run_status com status='error', tokens=0, cost=0 (não tem acesso ao acumulador), errorMessage=error.message. Re-throw pro Bull marcar o job como failed.
Em resumo: paralelo do B, mas em catch. Diferença crítica: aqui não tem acesso ao totalTokensUsed/totalCost — o result nunca foi retornado. Passa 0 pra ambos. Isso é limitação do design atual — em teoria, o backend poderia expor essas variáveis via chargeContext ou outro pattern pra o processor recuperar. Mas hoje, run com crash catastrófico não é billed. Boa notícia pro user (não paga por crash), ruim pra analytics de custo real. errorMessage é a mensagem crua da exception. Depois faz throw error pra Bull marcar failed — sem isso o Bull não sabe que foi erro e faria retry.
// apiV2Job.processor.ts:80 } catch (error) { if (params.mcpTracking) { await this.mcpRunStatusService.markFinished({ id: processId, status: 'error', tokens: 0, // não tem acesso ao acumulador cost: 0, durationMs: Date.now() - startedAt, errorMessage: error.message, }); } throw error; // Bull marca job failed }
⚠️ Tokens/cost zerados em crash
Se agente crashou no meio, tokens/cost já cobrados no banco (token_transactions) NÃO aparecem em mcp_run_status. Dashboard "custo por MCP token" fica subcontagem.
🎯 Re-throw pra Bull
Sem throw error, Bull acharia job = OK (returned nothing). Precisa propagar pra retry logic funcionar.
DTabela mcp_run_status
mcp/entities/mcp-run-status.entity.ts
@Entity('mcp_run_status') class McpRunStatus { id: string PK; status: 'pending' | 'in_progress' | 'completed' | 'error'; tokens: number; cost: number; durationMs: number; errorMessage: string; startedAt, endedAt: Date; }
Propósito: Table dedicada pra MCP tracking. Uma row por processId (job Bull). Analytics: SUM tokens por mcpTokenId, latency percentiles, error rate. Separada de execution_logs pra não poluir queries de non-MCP com filtros.
Em resumo: tabela pequena e focada. Uma row = um run MCP. Chave é o processId (mesmo do runLogProcessId) — permite JOIN com execution_logs, space_run_logs, node_executions. Colunas específicas de MCP tracking: status como enum-like (string mas com valores restritos), durationMs pra latency, errorMessage pra debug. Sem flowId/userId — dá pra JOIN se precisar via processId. Dashboard "meus MCP calls" filtra por userId via join.

🎯 Por que separado de execution_logs
MCP tracking é opt-in por mcpTracking flag. Manter em tabela separada evita coluna nullable em execution_logs e poluição de queries pra outros run_types.
Resumo — o que sai de 5.2:
• 1 UPDATE em mcp_run_status (só se veio via MCP)
• Row completa: status final, tokens, cost (0 em crash), duration, error
• Roda antes do throw propagar em erro path — cleanup garantido
Observações para migração:
• MCP tracking é opcional e isolado — só afeta MCP endpoints. Migração pode ficar pra depois.
• Zerar tokens/cost em crash é dívida — refactor pode expor essas vars via chargeContext ou callback pro processor ler.
• Tabela dedicada é bom pattern (evita "God table" execution_logs) — manter.
• Não bloqueia migração de agentes normais.

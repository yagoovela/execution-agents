Decisão prefetch vs legacy loop novo pós-doc
Modelo de memória alternativo · desligado em produção (opt-in por env var)
Contexto — por que essa decisão existe: No loop legacy (Fase 3), o backend mantém em memória um schema gordo (nodeSubstitutionSchema) que acumula o output completo de todos os nós já executados. Cada nó novo faz applySubstitutionToObject sobre esse schema inteiro pra resolver seus {{...}}, mesmo referenciando só 1 ou 2 upstreams. Em agentes grandes (100+ nós, com respostas de LLM longas), esse schema fica com megas de JSON vivendo na heap por toda a execução — é o principal ofensor de perf.

O modo prefetch resolve isso invertendo o fluxo: pra cada nó, primeiro escaneia quais refs ({{...}}) ele realmente usa, e só então puxa do banco (node_executions) as saídas desses upstreams específicos. Nada de schema gigante mutando em memória. Ainda roda tudo in-process no backend (não envolve worker/Temporal), só troca o modelo de propagação de dados.
Duas condições precisam ser verdadeiras: isPrefetchMode() && canUsePrefetchForFlow(newFlows)
1. isPrefetchMode() — lê process.env.FLUX_EXEC_MEMORY_MODE. Só é true se estiver exatamente 'prefetch' (default é 'legacy').
2. canUsePrefetchForFlow(newFlows) — varre todos os nós do flow e confere se cada tipo está numa whitelist hardcoded. Basta 1 nó fora da lista pra reprovar.
flux.service.ts:177, 1402-1431, 3198-3226 · prefetch/memory-mode.ts
SIM → runApiV2FlowLoopPrefetch()
Chama runPrefetchFlow(nodes, deps). Loop parecido com o legacy (mesmo scheduler, mesmos handlers), mas:
• A cada nó pronto → scanPlaceholderRefs descobre só as refs desse nó
• loadOutputsByRefs puxa apenas as saídas necessárias do node_executions
• Monta um schemaForNode pequeno e local (não muta um schema global)
• Guarda ponteiros (OutputPointer) — rowId, tipo e tamanho — em vez do payload

Retorna { processed, failed, pointer } pro caller montar o resultado final com assembleFinalOutputsFromDb.
flux.service.ts:1433 · prefetch/prefetch-flow-executor.ts
NÃO → cai na Fase 3 (loop legacy padrão)
Caminho usado em produção hoje. Cai aqui em 3 cenários:
• Env var não está setada como 'prefetch' (default)
• Env var está, mas o flow tem qualquer nó fora da whitelist (mais comum — praticamente todo agente real usa textGenerator, que não está na lista)
• Nesse segundo caso o backend loga flux.prefetch.fallback com reason: 'unsupported_node_type_present'
flux.service.ts:3219-3226
Whitelist atual (canUsePrefetchForFlow): imageGenerator, webSearch, voiceBoxNode, audioReaderNode, commandContentNode, pullData, pushData, thirdPartyIntegration, mcpNode, libraryNode, webCrawling, reportBuilder, sqlQuerier, nodesBox, comment, label, group.

Ausências notáveis: textGenerator, scripting, apiCaller, mathFunction, counter, displayBox, chatNode, condition, arrayNode. Ou seja: qualquer flow que use LLM ou controle de fluxo cai no legacy. Na prática, o prefetch hoje só roda em agentes muito simples/lineares — o rollout é gradual, tipo por tipo de nó.

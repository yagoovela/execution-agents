AhandledAdvance flag
flux.service.ts:3242 (declara), 3572 (seta), 4730-4732 (usa)
let handledAdvance = false; ... if (!handledAdvance) { markCompleted(schedState, id); } scheduledId = nextReady(schedState);
Propósito: Flag que sinaliza se o próprio handler já chamou markCompleted ou completeCondition. Se sim, o loop não chama markCompleted de novo no final. Assim, handlers especiais (condition, arrayNode quando encerra) controlam seu próprio avanço; o resto depende do fallback padrão.
Em resumo: é um flag de "já cuidei disso". Alguns tipos de nó — principalmente conditionNode — precisam de lógica especial pra avançar o DAG: em vez de só marcar completed, precisam também matar branches não-tomadas via completeCondition. Como o loop não conhece essa distinção diretamente, cada handler seta handledAdvance = true quando decide fechar seu próprio avanço. No final do try (linha 4730-4732), o loop checa: se handledAdvance é false, chama markCompleted padrão; se true, respeita o que o handler fez. Simples mas frágil — se um handler novo esquecer de setar a flag e fizer avanço próprio (chamando por exemplo completeCondition), o loop chama markCompleted em cima, e como esse é idempotente (early-return em state.completed.has(id)), não quebra. Mas se houver outras variantes de avanço no futuro, precisa cuidar. Padrão pouco documentado — só sabendo lendo o dispatch inteiro.

Propósito: Fecha o nó marcando-o como completed e resolvendo vivo a dependência de todos os seus forwardDeps. Fallback padrão pra todos os tipos que não precisam de lógica especial de branching.
Em resumo: caminho comum — o handler terminou o nó normal, agora libera os sucessores. Já detalhamos em profundidade no passo 3.1 (fn C — markCompleted). Aqui é onde é chamado: no fim do try se handledAdvance é false. Não recebe handle nem taken info — apenas resolve todos os forward deps como "vivos" (não-dead). Se o nó atual tem 3 sucessores, os 3 recebem resolvedPreds++; os que baterem com totalPreds viram ready. Idempotente — chamar 2× é seguro.

Propósito: Especialização pra nós de decisão (conditionNode). Mata branches não-tomadas via resolvePred(..., predWasDead=true). Recebe o handle tomado (string tipo 'outputHandle-0') — arestas que combinam propagam viva, as que não combinam propagam morte.
Em resumo: caminho especial pra conditionNode. Já detalhamos a lógica interna no passo 3.1 (fn D — completeCondition). Aqui vemos quem chama: o dispatch do conditionNode em flux.service.ts:3540-3573. Depois de avaliar as condições e escolher qual handle tomar, o handler chama resolveConditionHandle(condNode) pra extrair a string ('outputHandle-0', 'outputHandle-1', 'conditionHandle-T0', etc.) e passa pra completeCondition. A função interna itera conditionEdges[conditionId], comparando edge.sourceHandle com o taken — arestas que batem seguem normal, as que não batem viram dead. Pra arrayNode existe menção em flux.service.ts:4013 — mas confirmando o código, quando o arrayNode termina de iterar (linha 4346), ele chama markCompleted, não completeCondition. O comentário "4013 — arrayNode chama completeCondition também?" do diagrama não é preciso — arrayNode usa markCompleted padrão.

⚠️ resolveConditionHandle pode retornar null
Se o condition não conseguiu decidir (bug, todos os handles resolveram falso), resolveConditionHandle pode devolver null. Passa null pra completeCondition — todas as arestas viram dead (efeito equivalente ao DEAD_HANDLE).
🔧 stoppedByLoopBehavior
Case especial no handler de condition: se idxCondition < -1 (loop terminou sua iteração), seta stoppedByLoopBehavior=true e chama markCompleted normal em vez de completeCondition. Sinaliza pra Fase 4 que run terminou por "loop chegou ao fim" e não por erro.
DVolta ao nextReady (fecha o loop)
flux.service.ts:4733
scheduledId = nextReady(schedState);
Propósito: Última linha do corpo do while. Requesta o próximo id ao scheduler. Se retornar não-null, o while continua na próxima iteração; se null, sai — Fase 4 começa.
Em resumo: é o encerramento do turno. Depois de tudo o que aconteceu no nó (busca, substitution, log, dispatch, handler, endNode, error check, advance), a última coisa é: "e agora, tem mais alguém pronto?". nextReady devolve o próximo id ou null. Se id, o while volta pro topo, o cancellation check roda de novo, e todo o ciclo se repete. Se null, sai — a Fase 4 começa com unprocessedNodeIds = [...] e todo cleanup. É o mesmo nextReady do 3.1 — não uma variante. Simetricamente completa o loop.

Resumo — o que sai de 3.11:
• schedState.completed ganhou o id do nó atual

• Branches não-tomadas de condition viraram dead

Observações para migração:
• Scheduler puro é portável — mas o pattern handledAdvance flag é frágil. Refactor pode formalizar em um contract: "handler retorna { advance: 'default' | { condition: handle } | { skip: reason } }".
• completeCondition + handle names literais ('outputHandle-0') sensível a typo — validar handles no build ou usar constantes tipadas.
• É essencial — sem essa lógica o run trava. Migração deve preservar semantica de branches mortos.

A chargeContext.enterWith({ execId, nodeId })
product/charge-context.ts:1-8 · flux.service.ts:3263-3266
chargeContext = new AsyncLocalStorage<ChargeContext>() · interface ChargeContext { execId?: string; nodeId?: string; }
Propósito: Injeta { execId, nodeId } no async context do Node.js. Qualquer chamada assíncrona feita dentro do try abaixo (LLM, HTTP, DB) que chame chargeContext.getStore() recebe esses valores sem precisar passar por argumento. É o mecanismo central de bilhetagem por nó.
Em resumo: é o crachá invisível que o funcionário coloca antes de começar a trabalhar — quem precisar saber "quem tá fazendo esse trabalho agora?" só olha pro crachá, ninguém precisa perguntar. Tecnicamente é AsyncLocalStorage, um recurso nativo do Node.js que carrega dados através de async chains sem poluir assinaturas de função. Antes do handler rodar, o loop chama chargeContext.enterWith({ execId, nodeId }) — pronto, todo await feito dentro daquele contexto (chamada de LLM, HTTP externo, query TypeORM) enxerga esses valores via chargeContext.getStore(). Isso é essencial pra billing: quando o AnthropicService ou o OpenAIService vai cobrar tokens, ele nem sabe que tá rodando dentro de um agente — só chama updateTokens(delta). O ProductService lê o contexto, extrai execId+nodeId e insere em token_transactions com metadata correta. Sem ALS, cada método provider precisaria receber esses ids por argumento explícito — e como esses services são compartilhados com rotas API públicas, isso poluiria a assinatura toda. Ponto de fragilidade: enterWith não é auto-limpo — se algum callback assíncrono escapar do try do nó, ele continua vendo o contexto antigo. Não acontece em prática (o try engloba tudo), mas é o tipo de coisa que quebra silenciosamente se o refactor não for cuidadoso.

🎯 Por que AsyncLocalStorage e não parâmetro?
Passar execId+nodeId por argumento em toda chamada de LLM/HTTP/DB seria assinatura poluída. Provider services (Anthropic, OpenAI, etc.) são compartilhados por rotas API e por execução de agente — não podem ter esse contexto no signature.

ALS resolve: contexto lexical num async chain sem envenenar interfaces.
⚠️ enterWith não é "escopado"
Diferente de .run(store, fn), o enterWith não é auto-limpo quando o try termina. Se o próximo nó também chamar .enterWith, o valor é sobrescrito — o que é ok pra este uso. Mas se algum callback assíncrono escapar do try (não deveria acontecer, mas...) ele continua vendo o contexto antigo.
🔧 nodeCancelContext usa o mesmo pattern
Logo abaixo, linha 3268: nodeCancelContext.enterWith(cancelWatch.entry). Também ALS, também injeta contexto pra que interceptors de fetch/axios possam abortar. Ver detalhamento do Cancellation check.
📎 Sub-runs (fluxBox, libraryNode) reentram
Quando um nó container dispara um sub-flow, o loop nested faz seu próprio enterWith com o novo nodeId dos nós de dentro. Voltando pro parent, o contexto do parent precisa ser restaurado — hoje isso é feito pela cadeia async natural (o parent segue seu próprio async context).

Propósito: Decide se o coletor deve criar um RunLogNode "achatado" ou pular. Nós container (fluxBox, libraryNode) delegam a criação do log pro handler deles, que chama startFlowCallerSubRun/startLibrarySubRun — cria um documento aninhado próprio com toda a hierarquia interna.
Em resumo: é uma peneira pra evitar log duplicado. fluxBox e libraryNode são nós "container" — eles não fazem trabalho próprio, disparam outro agente inteiro internamente. Se o coletor criasse um RunLogNode simples aqui (o container) e depois o handler desses tipos criasse um subRun completo com toda a hierarquia do agente filho, o timeline da UI ficaria com dois registros pro mesmo container: um raso e um profundo — confuso. A solução: pra esses tipos, o coletor pula (genericRunLogNode = null) e delega a criação do log pro próprio handler, que via startFlowCallerSubRun constrói um RunLogDocument aninhado com todos os nós internos do sub-flow. Efeito colateral do null: o passo 3.9 (endNode) também é skipado — o handler é responsável por finalizar seu próprio sub-log. Também é o único lugar do loop com "conhecimento hardcoded" sobre esses dois tipos específicos — deveria idealmente ser uma flag no metadata do node type, não uma comparação inline. Refactor pequeno mas simbólico da direção da migração.

Em resumo: é o escrivão que abre uma pasta pro nó atual na "árvore do run". Só trocar o ponteiro faz o mesmo startNode gerar hierarquia certa em qualquer contexto. 🎯 Por que trace uniforme?
Analytics, replay, debug — todos querem uma tabela única de execuções. Se só nós Temporal aparecessem, um agente com mix de textGenerator (Temporal) e conditionNode (inline) teria histórico "furado".

Também é o que permite o UI de execution log mostrar todos os passos numa timeline consistente.
📎 Quem escreve o "finish" desses rows?
recordInApiNodeError (linha 3303, 4593-4720) escreve o resultado de nós legacy — status='FAILED'/'COMPLETED', outputData, errorMessage. Não é o worker (path Temporal usa persistNodeSuccess).
⚠️ Async não-espera é tentador
O await aqui atrasa o dispatch. Em nós rápidos (condition, math) esse INSERT vira ~5-10ms de latência por nó. Não é elegível pra remover porque o UPDATE seguinte precisa dessa row existir.
🔧 Diferença pro path Temporal
No path Temporal, o INSERT em node_executions é feito por createNodeExecution dentro de processNodeViaTemporal (passo T2) — com metadata.workflowId populado. Aqui (legacy) o INSERT é sem workflow — indica execução inline no próprio processo do backend.
E spaceRunLogsService.scheduleUpsert (autoflush)
space_run_logs/space_run_logs.service.ts:92-120
scheduleUpsert(params: { spaceId; rootFlowId; doc: RunLogDocument }): void
Propósito: Callback registrado no runLogCollector. Cada flushRoot (disparado por startNode/endNode/finalize) agenda um UPSERT debounced em space_run_logs. Sem debounce, um run com 100 nós faria 200+ writes; com debounce, agrupa mudanças recentes num único write.
Em resumo: é o timer da secretária que evita reimprimir a mesma pilha de papel 200 vezes. O coletor quer gravar rápido no banco pra UI ver a timeline atualizada em quase-tempo-real. Mas cada startNode/endNode disparando UPSERT direto faria uma rajada absurda de writes num run com muitos nós. A solução: cada chamada de flushRoot vira scheduleUpsert(doc), que faz setTimeout(FLUSH_DEBOUNCE_MS) e guarda o timer num Map por processId. Se outra chamada chegar antes do timer disparar, cancela o anterior e reinicia — só grava quando fica quieto por N ms. Rajadas de mudança viram 1 write. Padrão simples de debounce. No fim do run (passo 4.4), runLogCollector.finalize() chama spaceRunLogsService.flushNow(processId) — força write imediato, garantindo que o registro final tá no banco antes do backend responder. O risco: se o backend crashar entre o último flush e o finalize, o batch em andamento se perde — o log fica congelado no penúltimo estado, com nós ainda em in_progress. É otimização, não correção — se remover, semântica não muda, só custo aumenta. Pode ser adiado no plano de migração.
E1 Debounce map keyed by processId
this.pendingFlushes: Map<processId, { timer, spaceId, rootFlowId, doc }>. Cada chamada:
1. Clear timer anterior (se existir)
2. setTimeout(FLUSH_DEBOUNCE_MS, () => upsert(doc))
3. Guarda o novo timer no map

Efeito: só grava se ficar quieto por N ms. Rajadas de atualização (start+end de vários nós) viram 1 write.

🎯 flushNow em 4.4
No fim do run (Fase 4 passo 4.4), runLogCollector.finalize() chama spaceRunLogsService.flushNow(processId) — cancela debounce e força write imediato. Garante que o registro final está no banco antes do backend retornar.
⚠️ Se o run crashar, debounce perde
Se o backend crashar entre startNode e finalize, o último batch de mudanças (que ainda tava no timer) some. Fica registrado em space_run_logs só o estado do último flush efetivo.

Em prática significa: crash log pode ficar com nó em in_progress mesmo depois de terminar — não é reconstitutível sem replay.
🔧 Uma row por processId
space_run_logs tem PK processId — o run inteiro vira uma única row com JSONB gigante. UI de timeline lê essa row inteira. Escalar pra runs muito grandes vai virar um problema de tamanho de row / query time.
Resumo — o que sai de 3.4:
• chargeContext.getStore() agora retorna { execId, nodeId } pra qualquer service assíncrono chamado abaixo
• genericRunLogNode — RunLogNode com status='in_progress' vivo no coletor (null pra fluxBox/libraryNode)
• space_run_logs ganhou um flush agendado (debounced) refletindo o novo nó
• node_executions ganhou uma row com input resolvido pra nós legacy (não vale pra Temporal)
• 1 INSERT (só pra legacy), 1 UPSERT debounced
Observações para migração:
• chargeContext depende de single-process — no worker, o handler roda em outro processo/máquina e não vê a ALS do backend. O worker cobra via HTTP /worker/charge-tokens (W7) passando execId/nodeId explícitos — pattern superior que o backend pode adotar também.
• RunLogCollector hierárquico com innerSteps/subRun é parte essencial da UX (timeline aninhada). Migração precisa preservar. Como o coletor vive no processo do backend, a migração pro worker envolve serializar RunLogNode pra o backend agregar — ou expor um serviço centralizado.
• O redactSecrets é o único ponto onde credenciais são higienizadas antes de log. Qualquer refactor precisa manter esse hook — vazar em space_run_logs é evento de segurança.
• Debounce de scheduleUpsert é otimização, não correção — se remover, a semântica não muda, só o custo. Pode ficar de fora do MVP da migração.
• recordLegacyNodeStart só existe pra manter parity com Temporal. Quando tudo for pro worker, essa função vira dead code — bom sinal do progresso da migração.
• É essencial e cross-cutting — deve ser tratado como subsistema no plano de migração, não como parte do handler de nó individual.
